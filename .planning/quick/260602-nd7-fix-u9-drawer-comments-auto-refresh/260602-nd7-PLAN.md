<objective>
Fix the Phase 36.3.7.11 U9 UAT failure: while the kanban dashboard drawer is
open on a task, a cross-process `cargo run -p ironhermes-cli -- kanban
comment <id> "..."` write does NOT cause the drawer's COMMENTS section to
auto-refresh. The D-21 contract (drawer auto-refreshes within 500ms via a
200ms-debounced per-task event counter, without closing the drawer) is
broken.

**Diagnosed root cause** (NOT one of the (a)/(b)/(c) hypotheses in the
defect notes; the read of the current code rules them out):

The dashboard's live-update pipeline is `task_events` row written -> tail
consumer broadcasts `KanbanWsEvent::TaskEventBatch` -> screen-level WS
handler increments `per_task_event_counter[task_id]` (200ms debounce) ->
drawer's `use_resource` for comments re-runs because its closure reads the
counter. The break is at the *producer* end: `KanbanStore::add_comment`
(`crates/ironhermes-kanban/src/store.rs:547-568`) writes a row to
`task_comments` but does NOT append a corresponding row to `task_events`.
Because no `task_events` row exists, the dashboard tail consumer has
nothing to broadcast, the per-task counter never bumps, and the drawer's
comments resource never re-runs. Manually closing + reopening the drawer
re-runs the resource for an unrelated reason (`task_id` signal transitions
None -> Some(id)) so the new comment becomes visible by accident.

The phase constraint "events.rs is frozen surface (Phase 36.3.7.6 already
locked the variant set) — Don't add new event kinds" forbids adding a
`KanbanEventKind::Comment` variant. The fix therefore reuses the existing
`KanbanEventKind::Edited` variant (already used at
`crates/ironhermes-kanban/src/events.rs:100` for non-status mutations like
assignee/priority changes) with a payload that disambiguates `comment` as
the edit subkind. This is a one-line additional store write inside
`add_comment` plus a payload-tagged JSON blob; no enum churn, no protocol
churn, no UI churn.

**Why not fix at the screen-level WS handler instead:** the handler at
`screens/kanban.rs:153-194` increments the counter for EVERY event row in
the batch regardless of kind (no kind filter exists there), so it already
behaves correctly — the problem is that NO row arrives. Fixing the
producer is the only way to honor D-21 end-to-end and is also the only
way to keep the contract observable from a kanban-crate-level test (no
need to spin up a WASM/Dioxus test harness for an integration test).

Purpose: U9 is the only UAT FAIL carved out of Phase 36.3.7.11; closing
it satisfies the D-21 contract end-to-end and lifts the carve-out.
Output: 3 file changes; 1 new test file (producer end); 1 augmented test
in the existing drawer source-string suite (consumer end); both pin the
bilateral contract so the same defect cannot ship again.
</objective>


already the catch-all for non-status mutations per its current uses).
