# Cross-AI Plan Review — Phase 21.1: Slash Commands

> **Note:** Phase 21.1 already shipped on 2026-04-18. This is a **retrospective review** of the plan quality, useful for: (a) calibrating planning rigor for future phases, (b) identifying behavioral gaps that may have made it into the shipped code and warrant verification, (c) feeding into `/gsd:plan-phase --reviews` for any future amendment plans.

## Codex Review

**Model:** `gpt-5.5` (OpenAI Codex CLI v0.125.0, reasoning effort: high)

### Summary

Overall, the plans are solid and directionally right: they separate command resolution from platform handling, preserve caller-level interception before `AgentLoop`, and explicitly cover alias/prefix behavior, platform filtering, and CLI/gateway replacement. The main weakness is that the plans focus heavily on registry mechanics but leave some operational semantics under-specified, especially gateway running-agent behavior, skill fallback behavior, `/model --global`, and message-size/error handling. Plan quality rated as good, but with several medium-risk gaps that could become regressions despite tests passing.

### Strengths

- Clear dependency split: Plan 21.1-01 builds the core router; Plan 21.1-02 wires it into CLI and gateway.
- Resolution order is well specified: exact → alias → prefix → not found, with platform filtering.
- Good decision to keep unknown slash commands as pass-through per D-08.
- Duplicate name/alias detection at router construction is a useful guardrail.
- Platform availability is treated as first-class metadata instead of reintroducing hardcoded CLI/gateway branches.
- CLI extension-first behavior is explicitly preserved.
- Tests cover important semantic priorities: exact over prefix, alias over prefix, and platform exclusion.
- Threat modeling is unusually concrete for a slash-command phase.

### Concerns

- **HIGH:** Running-agent guard behavior is not fully specified or enforced. Research says gateway commands should be queued while an agent is running except `/stop`, `/new`, `/queue`, `/status`. The plans add `agent_running: Arc<AtomicBool>` but do not clearly define where the bypass/queue decision happens. If this is only exposed in `CommandContext`, the critical behavior can easily be missed by handlers or callers.

- **HIGH:** `Arc<AtomicBool>` is probably insufficient for gateway concurrency semantics. It can tell whether something appears to be running, but it does not model ownership, queued work, cancellation, per-chat/session state, or ordering. There are TOCTOU races around checking the flag, dispatching commands, and starting/stopping agent turns.

- **MEDIUM:** Command count drift is a real planning smell. Context says full parity around 44 commands; research says 38 registry commands plus 5 additions; Plan 01 says "44+" but enumerates 50. That should be reconciled before implementation because it affects completeness tests, help output, TODO accounting, and claims of parity.

- **MEDIUM:** The skill catch-all needs sharper rules. D-06 says built-ins first, then skills, and "skills never shadowed by prefix matches." The plan should explicitly define cases like `/mem` when there is a `memory` built-in and a `mem` skill, or `/foo` where `foo` is both an alias and a skill. Without tests, this can regress.

- **MEDIUM:** Empty slash inputs are not called out. `/`, `/ `, `//`, and `/@botname` in gateway should have deterministic behavior: likely pass-through or friendly help, but not ambiguous, panic, or empty-name lookup.

- **MEDIUM:** Telegram output limits are not considered. A generated `/help` over 50 commands with descriptions/categories could exceed or approach Telegram's 4096-character limit, especially if TODO status or aliases are included. Gateway help likely needs concise formatting or chunking.

- **MEDIUM:** Optional dependencies in `CommandContext` need explicit failure semantics. If `skill_registry`, config, memory/session store, or model settings are `None`, handlers should return clear `CommandResult::Error` or `PassThrough`, not silently degrade or produce misleading TODO output.

- **MEDIUM:** `/model --global` is under-planned. If research called it out and parity requires it, deferring it without a clear TODO contract risks shipping a command that appears to work but only changes local/session state.

- **MEDIUM:** Static-grep regression tests in Plan 02 are brittle and low-signal. They can prove a string disappeared or `CommandRouter` appears, but not that behavior is correct. Integration tests should exercise actual CLI/gateway command dispatch paths.

- **LOW:** Unicode handling is underspecified. Lowercasing and trimming may behave unexpectedly for non-ASCII input. Since command names are likely ASCII, the router should document that built-in command resolution is ASCII-oriented and reject/control non-ASCII names predictably.

- **LOW:** Very long commands are not addressed. O(n<50) lookup is fine, but callers should avoid unbounded allocations, huge ambiguous output, or logging giant user input verbatim.

- **LOW:** `PlatformFilter` naming appears redundant or unclear: `All` and `Universal` sound equivalent. Ambiguous platform taxonomy can cause future mistakes.

- **LOW:** `handlers::dispatch(&router, ...)` creates a slightly awkward dependency where handlers need the router for help output. It is acceptable short-term, but it couples command execution to registry introspection.

### Suggestions

- Add an explicit gateway guard policy before dispatch: if `agent_running` for the session is true, only allow `/stop`, `/new`, `/queue`, and `/status`; queue or reject others exactly as intended.

- Replace or supplement global `Arc<AtomicBool>` with per-session running state, ideally something that can represent `Idle`, `Running`, `Cancelling`, and `Queued`.

- Reconcile the command inventory in the plan: one authoritative table with source parity status, platform availability, aliases, handler status, and TODO reason.

- Add tests for `/`, `/ `, unknown slash commands, ambiguous prefixes, prefix-vs-skill conflicts, alias-vs-skill conflicts, and platform-filtered aliases.

- Add gateway behavior tests instead of relying on static grep: `/help`, `/new`, `/clear`, unknown `/whatever`, CLI-only command on gateway, and command during running-agent state.

- Make `CommandContext` dependency failures explicit per command. For example: `/skills` with no skill registry returns "skill registry unavailable in this context," not a generic TODO.

- Keep generated help platform-specific and bounded. For Telegram, either paginate/chunk or show compact categories with aliases omitted unless requested.

- Define `/model --global` behavior now, even if implemented as a TODO stub. The command should not imply global persistence unless it actually writes global config.

- Consider making help rendering a method on `CommandRouter` or a separate formatter module instead of having generic handlers depend on the router.

- Add a registry validation test that asserts the exact expected command names by sorted snapshot. That would catch accidental count drift better than duplicate checks alone.

### Risk Assessment

**MEDIUM.** The architecture is sound, and the two-wave dependency ordering is reasonable. The main risks are behavioral rather than structural: running-agent concurrency, command inventory drift, weak gateway tests, and underspecified edge cases around skill fallback and optional dependencies. If those are tightened, the plan would drop to low risk.

## Consensus Summary

> **Caveat:** Only one external reviewer ran (codex). No cross-AI consensus is possible. Findings below are codex's alone — no second reviewer validated them. Treat as a single expert opinion, not a consensus.

### Top HIGH-Severity Findings

1. **Running-agent guard is unspecified at the dispatch boundary.** `agent_running: Arc<AtomicBool>` is added to `CommandContext` but neither plan defines where the bypass/queue decision is enforced. The hermes-agent reference (gateway/run.py:1735-1852) treats this as load-bearing — `/stop`, `/new`, `/queue`, `/status` bypass; everything else queues. **Action:** verify the shipped gateway handler actually enforces this; if not, this is a behavioral regression vs. hermes-agent parity worth a follow-up fix plan.

2. **`Arc<AtomicBool>` doesn't model per-session state.** Single global flag can't represent multiple concurrent chats each with their own agent turn. TOCTOU races possible between `load()` and dispatch. **Action:** verify whether shipped gateway uses one global flag or per-session state.

### Notable MEDIUM-Severity Findings

- **Command count drift** (44 in headline vs. 50 enumerated). The shipped code shows 49 commands per PROJECT.md ("CommandRouter with 49 commands") — closer to the enumerated count than the headline. The plan's TDD `assert!(build_registry().len() >= 44)` is satisfied but masks the inconsistency.
- **Skill catch-all conflict rules** (built-in alias vs. skill name) lack explicit tests.
- **Empty/malformed slash inputs** (`/`, `/ `, `//`, `/@botname`) have no defined behavior.
- **Telegram 4096-char limit** not considered for generated `/help` — 49 commands × ~60 chars each could blow the limit.
- **Optional `CommandContext` deps** lack defined failure semantics — `None` skill_registry returns "No skills loaded" which is indistinguishable from "no skills installed."
- **`/model --global`** parsed but persistence behavior undefined.
- **Static-grep tests in Plan 02** verify symbols exist but not that behavior is correct.

### Recommended Follow-Up Actions

If this phase is treated as load-bearing for v2.1 (it is — SKILL-12/13/14 are foundations), consider:

1. **Verify running-agent guard behavior** in the shipped gateway handler — does it actually queue non-bypass commands during an active agent turn?
2. **Add the missing edge-case tests** (empty slash, conflict rules, Telegram length) as a gap-closure plan if not already covered in 21.1-VERIFICATION.md.
3. **Audit `/model --global`** — does it persist to config.yaml or only session state?
4. **Replace static-grep tests** with behavioral integration tests over time (no rush — current shipped code is presumably working).
