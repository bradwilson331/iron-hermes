## Phase Boundary

This phase ships `kanban_swarm` as both a CLI verb (`hermes kanban swarm`) and an LLM tool (`kanban_swarm`) — one atomic dispatch that materializes a multi-card kanban graph for orchestrator fan-out. After this phase, the LLM tool surface grows from **9 → 10 tools** and the v1-NOTE marker at `docs/kanban/reference.md:664` is reconciled. The phase is structurally lighter than the ROADMAP stub implied because the sibling 36.3.7.5 + 36.3.7.6 phases already locked all the cross-cutting structural decisions (crate-isolation fence, tool-mounts-store-directly pattern, bilateral-tracing-by-construction, develop-direct single-plan, receiver-test layout, docs-reconciliation gate shape).

The swarm graph is created atomically in a **single `BEGIN IMMEDIATE` transaction** against `KanbanStore` via a NEW `store.create_swarm(...)` sibling method (mirrors the `store.insert_link_checked` sibling pattern from 36.3.7.6 — a new fn alongside the existing `create_task` rather than mutating it). The shape of the graph is locked below (D-topology-shapes); the inserts inside the transaction are: 1 root card (status=`done`), N worker cards (status=`todo` with `parents=[root]`), optionally a verifier card (status=`todo`, `parents=[w1..wN]`), optionally a synthesizer card (status=`todo`, `parents=[verifier]` if verifier present else `[w1..wN]`), 1 optional `task_comment` row on the root carrying the initial blackboard JSON. Failure on any step rolls the whole graph back.

The 3 material design questions the user resolved during discussion (and that downstream agents must NOT re-derive):

1. **Graph topology** → all 4 shapes accepted; verifier and synthesizer independently optional (D-topology-shapes).
2. **`workers` input shape** → array-of-string OR array-of-object via nested `oneOf` (D-worker-shape).
3. **Blackboard semantics** → optional `--blackboard <json>` / `--blackboard-file <path>` seeds one `task_comment` on root at creation; workers discover root by walking parents via existing `kanban_show` (no spawn-contract change) (D-blackboard-init + D-root-discovery).
4. **Slash surface (`/kanban swarm`)** → DEFERRED; matches the 36.3.7.6 pattern for link/unblock/heartbeat (D-slash-deferred).

## Implementation Decisions

### Graph topology

- **D-topology-shapes (LOCKED):** swarm accepts 4 graph shapes. Verifier and synthesizer are independently optional. Mapping to reference.md §740 patterns:
  | Shape | Topology | Pattern |
  |---|---|---|
  | 1 | `root → [w1..wN]` | P1 Fan-out |
  | 2 | `root → [w1..wN] → verifier` | Fan-out + verify |
  | 3 | `root → [w1..wN] → verifier → synthesizer` | Full 4-tier (reference.md §664 example) |
  | 4 | `root → [w1..wN] → synthesizer` | P3 Voting/quorum |
  **Rationale:** The 4 shapes correspond directly to documented multi-agent patterns. Forcing 4-tier (as the §664 example suggests verbatim) would block the common fan-out-only case (P1). Requiring verifier (no synth-without-verifier) would block the P3 quorum pattern where multiple workers feed one synthesizer that picks/merges. User explicitly grounded the decision in the patterns table at §740.
  **Implementation:** when synth is present but verifier absent, synth's `parents = [w1..wN]` directly (not `[verifier]`).

- **D-root-status-done (DERIVED, LOCKED):** root card is inserted with `status='done'` directly — bypassing the normal triage/ready/todo logic in `create_task`. Rationale: the root is a structural blackboard, not work for an assignee to claim. Dispatcher must not pick it up. `done` status also satisfies the existing parent-gate logic — children with `parents=[root]` (workers) and `parents=[verifier]` (synth) etc. promote from `todo` → `ready` once all parents are `done`. Since root starts `done`, workers promote to `ready` immediately on the next dispatcher tick.

- **D-root-assignee (DERIVED, LOCKED):** root card's `assignee` field = `$HERMES_PROFILE` (the invoking orchestrator's profile slug), same as `created_by`. Rationale: must be a valid profile per `validate_profile_name`; using the orchestrator profile preserves audit-trail provenance. If `$HERMES_PROFILE` is unset (orchestrator-via-CLI direct invocation without a profile), the CLI verb errors out at parse time with `--profile is required` (or, equivalently, the tool wraps the existing `validate_profile_name` error). No magic `__swarm__` sentinel assignee — that would require validator changes.

- **D-root-ended-at (DERIVED, LOCKED):** root card's `ended_at = now()` (same timestamp as `created_at`) since it ships pre-`done`. Mirrors the existing `complete_task` end-time-set pattern. Worker/verifier/synthesizer cards have `ended_at = NULL` at creation (they start `todo`).

### Tool input shape

- **D-worker-shape (LOCKED):** `workers` accepts EITHER `Array<String>` OR `Array<Object>` via nested `oneOf` inside the property's schema (NOT top-level — top-level boolean combinators were banned in 36.3.7.2 for Anthropic compat). String form: each string is an assignee slug; per-card title auto-generated as `"<goal> — worker {i+1} of {N}"`, body inherited from the tool-level `body` arg (if provided) or `null`. Object form: each element is `{assignee: String (required), title?: String, body?: String}`; missing title falls back to auto-generated; missing body falls back to tool-level `body`.
  **Schema snippet (locked):**
  ```json
  "workers": {
    "description": "...",
    "oneOf": [
      { "type": "array", "items": { "type": "string" }, "minItems": 1 },
      { "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "assignee": { "type": "string" },
            "title": { "type": "string" },
            "body": { "type": "string" }
          },
          "required": ["assignee"]
        },
        "minItems": 1
      }
    ]
  }
  ```
  **Rationale:** matches both P1 (homogeneous fan-out, 10 reviewers do the same thing) and P8 (fleet farming, 50 social accounts each with distinct body). One schema property; tool's `execute()` normalizes to `Vec<KanbanWorkerSpec>` before calling `store.create_swarm`. Precedent: `kanban_create::max_runtime` already uses nested `oneOf` at create.rs:138-144 — the same Anthropic-compatible pattern.

- **D-cli-worker-flags (LOCKED):** CLI exposes two mutually-exclusive flags: `--workers a,b,c` (flat, comma-separated, parsed into `Vec<String>`) AND `--workers-json '[{"assignee":"a"},...]'` (rich, parsed via `serde_json::from_str::<Vec<KanbanWorkerSpec>>`). Exactly one MUST be present at parse time; both → error `--workers and --workers-json are mutually exclusive`; neither → error `--workers or --workers-json is required`. The `--workers-json` flag is NOT exposed in the slash command (slash is deferred entirely per D-slash-deferred, so the question is moot).

- **D-shared-vs-per-card-fields (LOCKED):** these fields are SHARED across all swarm cards (root + workers + verifier + synth), set once at the tool level: `workspace`, `skills`, `tenant`, `priority`, `max_runtime`, `max_retries`. These are PER-CARD (rich-form only): `title`, `body`. These are PER-ROLE (one each at the tool level): `verifier` (assignee), `synthesizer` (assignee). Rationale: ROADMAP §624 says explicitly "shared assignee defaulting per task, shared parent, shared skills set, shared workspace." Per-card override beyond title/body is OUT of scope for v1 (planner MAY revisit if research surfaces a compelling need, but the locked default is shared-only).

### Blackboard semantics

- **D-blackboard-init (LOCKED):** swarm accepts an OPTIONAL `blackboard: <json>` arg (LLM) / `--blackboard <json-string>` / `--blackboard-file <path>` (CLI; mutually exclusive). When present, the transaction appends ONE `task_comment` row to the root card with `body = serde_json::to_string(&blackboard)?`, `author = "swarm"`. When absent, root has zero comments at creation (workers can `kanban_comment` to seed it during execution if needed). The comment id is returned in `SwarmGraphIds.blackboard_event_id: Option<i64>`.
  **Author convention:** `"swarm"` is a literal string sentinel; it bypasses `validate_profile_name` because `task_comments.author` is a free-text column per the existing schema (verify during planner research — if it IS validated, fall back to `$HERMES_PROFILE` and prefix the JSON body with `[swarm-init]`).
  **JSON shape:** ANY valid JSON. Tool does NOT impose a structure. Workers parse it themselves. Common shapes by convention (NOT enforced): `{shared_context: "...", artifacts: [...], constraints: [...]}`.

- **D-root-discovery (LOCKED):** workers discover the root card by walking parents via the existing `kanban_show` LLM tool — NO new env var, NO spawn-contract change. The locked topology guarantees:
  - Worker has exactly 1 parent: the root (`kanban_show $HERMES_KANBAN_TASK` → `parents: [<root_id>]`).
  - Verifier has N parents (the workers); walking any one of them lands on the root.
  - Synthesizer has either 1 parent (verifier) or N parents (workers when no verifier); 1-2 hops to root.
  - Workers/verifier/synth then `kanban_show <root_id>` to read the blackboard JSON from comments.
  **Rationale:** the 9-env-var worker spawn contract (`HERMES_KANBAN_TASK`, `HERMES_KANBAN_RUN_ID`, `HERMES_PROFILE`, ...) is locked by INV-36.3.7 invariants. Adding `HERMES_KANBAN_SWARM_ROOT` would require modifying `crates/ironhermes-kanban/src/worker_spawn.rs::build_kanban_worker_env` and the 9-env-contract test in `tests/argv_receiver_36_3_7_0.rs` — out of scope. The parents-walk path already works today; documenting it via the `kanban_guidance.rs` constant (planner picks: append a brief paragraph OR new appendix to KANBAN_GUIDANCE explaining the swarm-root-walk pattern) is the only adjacent edit.

- **D-no-blackboard-validation (LOCKED):** the `blackboard` arg is opaque JSON — swarm does NOT parse, validate, or impose a schema on it. Anything `serde_json::Value` accepts is accepted. Rationale: blackboard semantics are domain-specific (research swarm vs PR sweep vs fleet farming have different shared-context shapes). Enforcing a structure here would either be wrong for half the use cases or so generic it's useless.

### Slash surface

So `/kanban swarm ...` from any gateway platform routes to the CLI-redirect message (`store.deferred_subverb_message("swarm")` → "Use `hermes kanban swarm ...` directly — slash surface not wired in v1.").

  **Implementation:** the 1-line addition to `DEFERRED_KANBAN_SUBVERBS` is the entire gateway-side surface change. The deferred-message routing at handlers.rs:1285 handles the rest verbatim.

### Idempotency + atomicity

- **D-idempotency-suffix-scheme (LOCKED):** when `idempotency_key = "k"` is provided, per-card keys are deterministic suffixes:
  | Card | Key |
  |---|---|
  | root | `"k:root"` |
  | worker i (0-indexed) | `"k:worker:{i}"` |
  | verifier | `"k:verifier"` |
  | synthesizer | `"k:synthesizer"` |
  Re-invocation with the same `idempotency_key` short-circuits via the existing `find_by_idempotency_key` lookup on each card. Because the atomic transaction guarantees the graph is either fully present or fully absent, the re-invocation path is "look up root by `k:root` — if present, walk task_links to gather worker_ids/verifier_id/synth_id; return existing SwarmGraphIds." Partial-graph recovery is not a real case.

- **D-atomic-transaction (LOCKED):** `store.create_swarm` wraps the entire graph creation (N+1+0..2 task inserts, N+0..2 task_links inserts, 0..1 task_comment insert, N+1+0..2 task_events Created-row inserts) in a single `BEGIN IMMEDIATE` transaction via `Connection::transaction_with_behavior(TransactionBehavior::Immediate)`. On any insert error: explicit rollback before propagating the error. Mirrors the 36.3.7.6 `insert_link_checked` pattern (store.rs:444-481) and the older `block_task` pattern (store.rs:773). Concurrent writers under WAL mode are correctly serialized by `BEGIN IMMEDIATE`'s write-lock acquisition.

- **D-no-create-task-reuse (LOCKED):** `create_swarm` does NOT call `create_task` internally. Inserts are inlined inside the transaction handle (`tx.execute(...)`) using the same INSERT statement shape as `create_task` at store.rs:243-267. Rationale: `create_task` takes `&mut self` and runs its own autocommit per statement — calling it inside an outer transaction would either deadlock or break atomicity. Inlining keeps the transaction boundary clean. The duplicated INSERT statement is acceptable given the structural difference (swarm cards have computed fields like root's `status='done'` + `ended_at=now()` that `create_task` doesn't produce).
