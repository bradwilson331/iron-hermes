# Phase 36.3.7.7: Code Review Report

**Reviewed:** 2026-05-30T00:00:00Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

The Phase 36.3.7.7 swarm-helper implementation lands a coherent end-to-end vertical slice: `KanbanStore::create_swarm` (atomic graph materialization with idempotency replay), `KanbanSwarmTool` (orchestrator LLM tool with nested-oneOf workers schema and structured rejection envelopes), `cmd_swarm` (CLI verb with `--workers` / `--workers-json` mutual exclusion), `DEFERRED_KANBAN_SUBVERBS` membership for `"swarm"`, and reconciled docs in `reference.md` §§14/209/664/742. Core topology is correct across all four shapes (fan-out only, +verifier, full 4-tier, P3 quorum), the `BEGIN IMMEDIATE` rollback path is well-tested by `swarm_invalid_assignee_rolls_back_whole_graph`, and the `parent_handoffs` root-discovery contract is documented in `KANBAN_GUIDANCE`.

That said, adversarial review surfaces one BLOCKER (CLI `parse_duration_secs` divergence breaks the documented `--max-runtime` contract for `s` / `d` suffixes), and eight WARNING-tier defects: a concurrent first-create race in the idempotency-replay path, `SwarmGraphSpec.body` plumbing dead in two surfaces, schema/option drift between `--max-runtime`, swarm tool error-mapping that swallows `TenantMismatch` / `LinkCycle` / `RelativeDirWorkspace` into a generic `store_error` envelope, idempotency replay silently dropping `blackboard_event_id`, the `std::mem::forget(dir)` test-helper disk leak, and several `unsafe { env::set_var/remove_var }` usages from async tokio tests that race when run with `--test-threads > 1`. None of the warnings prevent shipping, but several should be fixed before users hit them in production.

## Critical Issues

### CR-01: CLI `parse_duration_secs` rejects `s` and `d` suffixes accepted by the tool

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:145-153`

**Issue:** The CLI's `parse_duration_secs` only handles `m` (minutes), `h` (hours), and bare integers. The tool's `parse_max_runtime` (in `tools/create.rs:55-71`) handles `s`, `m`, `h`, `d`. The CLI verb's `--max-runtime` doc comment (`mod.rs:268`) advertises `"e.g. '30m', '2h', or seconds"` but the underlying parser will reject `30s` (anyhow! "Invalid duration") even though the schema documents that as a supported value at the tool surface. More importantly, the reference doc and idiomatic Kanban CLI examples elsewhere use `--max-runtime "1d"` style. Calling `hermes kanban swarm <goal> --workers foo --max-runtime 1d` errors out at parse-time, whereas calling the same on the LLM tool succeeds. This is a load-bearing behavioral divergence: the CLI is documented as the human-facing parity surface for the tool (`reference.md:679` — "the argument surface, flags, and output format are identical across CLI, `/kanban`, and `hermes kanban`").

The same bug already exists in the older `cmd_create` path (same file, same helper), but Phase 36.3.7.7 has now hard-wired a second consumer (`cmd_swarm` line 492-495) into the broken parser, doubling the surface area before fixing it.

**Fix:**
```rust
// crates/ironhermes-cli/src/kanban/commands.rs
fn parse_duration_secs(s: &str) -> Result<i64> {
    // Delegate to the same parse used by parse_max_runtime so CLI <-> tool stay aligned.
    let trimmed = s.trim();
    if trimmed.is_empty() {
        return Err(anyhow!("empty duration"));
    }
    let split_pos = trimmed.find(|c: char| !c.is_ascii_digit());
    match split_pos {
        None => trimmed
            .parse::<i64>()
            .context("Invalid duration (use e.g. '30s', '30m', '2h', '1d', or seconds)"),
        Some(pos) => {
            let (num_str, suffix) = trimmed.split_at(pos);
            let n: i64 = num_str
                .parse()
                .context("Invalid numeric prefix in duration")?;
            match suffix {
                "s" => Ok(n),
                "m" => Ok(n * 60),
                "h" => Ok(n * 3600),
                "d" => Ok(n * 86400),
                other => Err(anyhow!("Unknown duration suffix '{other}' (expected s/m/h/d)")),
            }
        }
    }
}
```

Alternatively, re-export `parse_duration_str` from `ironhermes-kanban::tools::create` and call it here so there is a single source of truth.

## Warnings

### WR-01: Concurrent first-create race in `create_swarm` idempotency replay

**File:** `crates/ironhermes-kanban/src/store.rs:620-670`

**Issue:** The idempotency replay block uses `find_by_idempotency_key` (auto-commit reads) OUTSIDE the `BEGIN IMMEDIATE` transaction. When two callers race the same `k:root` key:

1. T1 looks up `k:root` → None
2. T2 looks up `k:root` → None
3. T1 opens `BEGIN IMMEDIATE`, inserts root with key `k:root`, commits
4. T2 opens `BEGIN IMMEDIATE` (blocks then proceeds), tries to insert root with `k:root`, fails with `UNIQUE constraint` (`tasks.idempotency_key` is `UNIQUE`, schema.rs:41).

T2 receives `KanbanError::Sqlite(rusqlite::Error)` — NOT a replay of T1's graph. The contract documented in the function's doc-comment ("Re-invocation with the same key short-circuits via `find_by_idempotency_key` on `k:root`") quietly fails for true concurrent first-creates. The 36.3.7.x integration tests don't cover this because they're single-threaded.

The probability of the race is low (orchestrators tend not to fan out the same swarm twice in parallel), but the failure shape is silent and misleading — the second caller can't tell whether they were rejected because of a duplicate or a genuine DB error.

**Fix:** Move the idempotency lookup INSIDE the transaction (immediately after `BEGIN IMMEDIATE`), so the second caller blocks until T1 commits and then sees the existing row. The replay walk can also live inside the same tx since reads are cheap:

```rust
let tx = self.conn.transaction_with_behavior(TransactionBehavior::Immediate)?;
if let Some(ref kr) = key_root {
    // Use `tx`, not `&self`, for the lookup so it observes T1's commit.
    let existing: Option<Task> = tx.query_row(
        "SELECT ... FROM tasks WHERE idempotency_key = ?1",
        params![kr],
        Self::row_to_task,
    ).optional()?;
    if let Some(existing_root) = existing {
        // walk replay inside tx, then tx.commit() (no-op) or drop(tx)
        ...
        return Ok(SwarmGraphIds { ... });
    }
}
```

Alternatively, catch the `UNIQUE constraint` SQLite error after the failed insert and replay then — but that's an after-the-fact bandage; the in-tx lookup is the clean fix.

### WR-02: Idempotency replay silently drops `blackboard_event_id`

**File:** `crates/ironhermes-kanban/src/store.rs:660-668`

**Issue:** When the replay path returns the existing graph, `blackboard_event_id: None` is hardcoded even if the original creation produced one. The doc-comment acknowledges this with "callers re-using `idempotency_key` are expected to ignore this field on replay" — but no caller-side code enforces or surfaces that contract. The `KanbanSwarmTool::execute` success envelope (`tools/swarm.rs:343-349`) returns the field verbatim, so an orchestrator that uses the `blackboard_event_id` to look up the blackboard comment will get `null` on retry/replay and either crash or silently fail.

The blackboard comment rowid is trivially recoverable inside the replay path with a single `SELECT MIN(id) FROM task_comments WHERE task_id = ?1 AND author = 'swarm'`.

**Fix:** During replay, query the blackboard row:
```rust
let blackboard_event_id: Option<i64> = self
    .conn
    .query_row(
        "SELECT MIN(id) FROM task_comments WHERE task_id = ?1 AND author = 'swarm'",
        params![&root_id],
        |r| r.get::<_, Option<i64>>(0),
    )
    .optional()?
    .flatten();
```

### WR-03: `SwarmGraphSpec.body` is reachable but never plumbed from CLI or tool

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:499-514`, `crates/ironhermes-kanban/src/tools/swarm.rs:307-322`

**Issue:** `SwarmGraphSpec` exposes a `body: Option<String>` field documented as "Shared body fallback for flat-form workers" (`types.rs:310`). `create_swarm` uses it via `let body = w.body.clone().or_else(|| spec.body.clone());` at `store.rs:744`. But:

1. The CLI verb (`mod.rs:233-279`) has NO `--body` flag.
2. The LLM tool schema (`tools/swarm.rs:145-215`) has NO top-level `body` property.
3. Both `cmd_swarm` (line 513) and `KanbanSwarmTool::execute` (line 321) hardcode `body: None`.

Result: flat-form workers (`--workers a,b,c`) ALWAYS receive `body = None`, never inheriting any shared instruction text. The functionality is implemented end-to-end inside `create_swarm` but completely dead at both surfaces. Either expose it or delete the unused field to avoid future confusion.

**Fix:** Add `body: Option<String>` to both the CLI verb (`#[arg(long)]`) and the tool schema, then plumb through to `SwarmGraphSpec.body`. Alternatively, document explicitly in `SwarmGraphSpec.body` that it's a private internal field reserved for future use, and remove it from the public type signature.

### WR-04: `KanbanSwarmTool` error mapping collapses TenantMismatch / LinkCycle / RelativeDirWorkspace into a generic `store_error`

**File:** `crates/ironhermes-kanban/src/tools/swarm.rs:326-340`

**Issue:** The `execute` path matches only on `KanbanError::Other` to extract a structured `reason` ("invalid_assignee" / "empty_workers" / "store_error"). But `create_swarm` can return `KanbanError::RelativeDirWorkspace(_)` (line 604 calls `validate_dir_workspace` which returns this variant), plus theoretically `KanbanError::TenantMismatch` and `KanbanError::LinkCycle` if any future change introduces cross-tenant or cycle paths inside the swarm tx. All of those fall through the `Err(e) => return Ok(reject("store_error", ...))` catch-all, losing the structured reason code that orchestrator agents are expected to pattern-match on.

This is the same anti-pattern the per-tool rejection envelopes were designed to avoid — sibling tools (`KanbanLinkTool`, `KanbanUnblockTool`) map `LinkCycle` to `"link_cycle"` and `RelativeDirWorkspace` to `"invalid_workspace"`. The swarm tool should mirror that discipline.

**Fix:**
```rust
Err(e) => {
    let reason = match &e {
        crate::error::KanbanError::RelativeDirWorkspace(_) => "invalid_workspace",
        crate::error::KanbanError::TenantMismatch { .. } => "tenant_mismatch",
        crate::error::KanbanError::LinkCycle { .. } => "link_cycle",
        crate::error::KanbanError::TaskNotFound(_) => "task_not_found",
        _ => "store_error",
    };
    return Ok(reject(reason, &format!("{e}")));
}
```

### WR-05: `unsafe { env::set_var / remove_var }` from async tokio tests races with sibling tests

**File:** `crates/ironhermes-kanban/tests/tools_smoke.rs:94, 102, 152-156, 184-185, 213-214, 271-272, 314-315, 372-373, 452, 463, 520-530, 562-569, 601-602` and others

**Issue:** The test module liberally uses `unsafe { std::env::set_var(...) }` / `remove_var(...)` from inside `#[tokio::test]` async fns. The author added an `ENV_LOCK` mutex (line 36) to serialize access, but:

1. Not every test acquires the lock (`kanban_show_unavailable_without_env`, `kanban_show_available_with_explicit_enable`, `kanban_create_idempotency_key_dedups`, etc. modify env without taking `ENV_LOCK`). These can race against each other and against lock-acquiring siblings.
2. Even with the lock, tokio executes async tests on a multi-threaded runtime by default. The Rust 2024 `unsafe { set_var }` contract requires no concurrent FFI / threaded reads of the env, which the tokio runtime cannot guarantee.
3. `is_available_respects_env` in `swarm.rs:365-377` calls `remove_var` without taking the module-level `ENV_LOCK` (it's a different test module/file — there is no cross-file serialization).

Result: depending on `--test-threads` and tokio runtime config, these tests can intermittently fail with `task not found: t_<other-test's-id>` (acknowledged in the source comment at line 30).

The Phase 36.3.7.x baseline acknowledges this — but the new `swarm.rs` `is_available_respects_env` test re-introduces the bug without taking the cross-file lock.

**Fix:** Convert to a process-spawn or `serial_test` crate gating; or refactor the tools to accept env config via dependency injection so tests never touch process env. Short-term, at least ensure every test that touches env takes the same lock. The cross-crate `is_available_respects_env` test in `tools/swarm.rs:365-377` should either be moved into `tests/tools_smoke.rs` so it can share `ENV_LOCK`, or use its own static lock.

### WR-06: `std::mem::forget(tempdir)` leaks DB files on every test run

**File:** `crates/ironhermes-kanban/tests/tools_smoke.rs:46`, `crates/ironhermes-kanban/src/tools/swarm.rs:361`

**Issue:** `make_store()` does `std::mem::forget(dir)` so the tempdir survives. This intentionally leaks the temp directory and its DB file on every test invocation. Over a full CI run with ~30 swarm tests, that's 30 `kanban_test*.db` directories that persist under `/tmp` until something else (OS / cron) cleans them up.

This was inherited from earlier phases and is not new to 36.3.7.7, but the Phase 36.3.7.7 swarm tests increase the leak rate significantly (10+ new tests calling `make_store`).

**Fix:** Move the `TempDir` into the `KanbanStore` struct as a `_keep_alive` field that's `Option<TempDir>` so the DB file is owned and dropped together. Alternatively use `tempfile::TempDir::keep()` which is the explicit "I know what I'm doing" API in modern `tempfile`. Don't paper over with `mem::forget`.

### WR-07: Flat-form CLI worker parsing silently coerces whitespace-only entries

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:450-460`

**Issue:** The CLI flat-form parsing does:
```rust
.split(',').map(str::trim).filter(|s| !s.is_empty())
```
This drops empty entries between commas but does NO validation — so `--workers ",,,,"` parses to an empty `Vec<KanbanWorkerSpec>`, hits the line 472-474 fallback check, and emits `"workers must contain at least one entry"`. Fine for empty.

BUT `--workers "alice,,bob"` silently produces `[alice, bob]` (the empty entry between commas is filtered). The user sees a 2-worker swarm even though their input syntactically requested 3. Same issue for `--workers " ,alice"` (leading empty trimmed away). This makes copy-paste mistakes invisible.

The `kanban_swarm` LLM tool's `normalize_workers` (`tools/swarm.rs:73-121`) is correctly strict: empty strings in an `Array<String>` would fail later assignee validation. The CLI path bypasses that strictness by silently dropping the empty entries before validation runs.

**Fix:** Distinguish "trailing comma" (forgiving) from "empty middle entry" (error). Or just don't filter — let empty entries fall through to `validate_profile_name` which will reject them with a clear error:
```rust
.split(',').map(|s| s.trim().to_string()).collect::<Vec<_>>()
// no filter — let validation reject empty entries
```

### WR-08: Swarm worker `validate_profile_name` runs twice — once in tool/CLI, once in `create_swarm`

**File:** `crates/ironhermes-kanban/src/tools/swarm.rs:286-304`, `crates/ironhermes-kanban/src/store.rs:587-600`

**Issue:** Both `KanbanSwarmTool::execute` (lines 286-304) AND `create_swarm` (lines 587-600) call `validate_profile_name` on every assignee. The tool layer rejects invalid names with a structured envelope (`{"status":"rejected","reason":"invalid_assignee", ...}`), but `create_swarm` re-runs the same check and would map the error into `KanbanError::Other` → `"invalid_assignee"` reason at the catch site (line 332).

This is defensible (defense in depth — the store doesn't trust callers), but it's duplicated work and a future-maintenance trap: if the tool's pre-check is loosened (e.g., to allow `"none"` as a sentinel for unassigned), it'll mysteriously still get rejected by the store. Pick one layer as canonical and document the other as belt-and-suspenders.

**Fix:** Either remove the tool-side check (rely on `create_swarm`'s normalization path) or document the pre-check as advisory ("structured rejection envelope for UX; store enforces"). The current redundancy isn't a bug today, but it's the kind of soft coupling that bites later.

## Info

### IN-01: Hardcoded `"swarm"` author sentinel for blackboard comments has no schema-level guarantee

**File:** `crates/ironhermes-kanban/src/store.rs:916, 922`

**Issue:** The blackboard `task_comments.author = "swarm"` value is a magic string literal in `create_swarm`. The schema does not constrain `author` (free-text per the doc comment), so a sibling test or future feature could insert a comment with `author = "swarm"` that workers would mis-identify as the blackboard. Workers using the documented `comments[0]` heuristic (per `kanban_guidance.rs:97`) are also vulnerable to mis-ordering if non-blackboard comments are added before root creation completes in some future async path.

**Fix:** Promote `"swarm"` to a `pub const SWARM_BLACKBOARD_AUTHOR: &str = "swarm"` exported from `types.rs` so workers and tests can refer to it symbolically. Document the contract.

### IN-02: `KANBAN_GUIDANCE` swarm discovery section assumes 2-hop topology only

**File:** `crates/ironhermes-kanban/src/kanban_guidance.rs:91-99`

**Issue:** The "Swarm graph root discovery" section says "The root card is the parent of each worker (1 hop)" and "Verifier and synthesizer cards are 2 hops from root (via any worker for verifier, via verifier for synth in the 4-tier shape)". For the P3 quorum shape (synth direct on workers, no verifier), the synthesizer is 2 hops from root via a worker — matches. For the verifier-only shape (no synth), verifier is 2 hops — matches. Fine.

But for a verifier worker, walking `parent_handoffs` returns N parent IDs (one per worker), and the guidance text says "The root card is the parent of each worker" — implying 1 parent. A verifier would have N parents, and the guidance doesn't say which one to follow to root. Verifier reads N worker-IDs from `parent_handoffs`, picks one, then walks its parents. The text glosses over this.

**Fix:** Tighten the guidance text:
> "Workers in a swarm graph have exactly one parent (the root). Verifier and synthesizer cards have N parents (the workers in the P3 quorum shape, or [verifier] in the 4-tier shape). To find the root, pick any parent ID from `parent_handoffs` and recursively walk parent_handoffs until you reach a card with no parents; that's the root. The blackboard is `comments[0].body` on root, with `author='swarm'`."

### IN-03: Unused `Subscription` re-export pulled into `lib.rs:72`

**File:** `crates/ironhermes-kanban/src/lib.rs:71-74`

**Issue:** `pub use types::{KanbanStatus, KanbanWorkerSpec, Subscription, SwarmGraphIds, SwarmGraphSpec, Task, TaskComment, TaskLink, TaskRun};` adds the new swarm types `KanbanWorkerSpec`, `SwarmGraphIds`, `SwarmGraphSpec` next to pre-existing exports. Nothing is broken; just noting that the alphabetical grouping is now ambiguous since `Subscription` is from a different phase. Cosmetic.

**Fix:** Group swarm-related exports together with a comment header or split into a separate `pub use types::swarm::*` namespace.

### IN-04: CLI `cmd_swarm` doesn't emit structured rejection on `--workers-json` parse failure

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:461-463`

**Issue:** When `--workers-json` JSON fails to parse, `serde_json::from_str` is wrapped with `context("Invalid --workers-json")` and propagated as `anyhow::Error` → `Err(...)` from `cmd_swarm`. The handler then exits with whatever `Err` rendering the CLI top-level does (typically `eprintln!("error: {e}")` + exit code 1). The OTHER mutually-exclusive cases (`Some,Some` and `None,None`) also bubble as `Err(anyhow!(...))`. The CLI doesn't follow the LLM-tool's `{"status":"rejected","reason":"...","detail":"..."}` envelope pattern — but that's likely intentional (humans get readable stderr, tools get JSON). Worth confirming in CLI ergonomics review.

**Fix:** None required. Note for the team: confirm that human CLI users see a readable error, not a serde stack trace, on bad `--workers-json`.

### IN-05: `swarm_cli.rs` tests don't cover the conflicts_with negative path

**File:** `crates/ironhermes-cli/tests/swarm_cli.rs`

**Issue:** Three tests cover happy-path parsing (flat, rich, reference example) but none verify that `--workers a,b --workers-json '[]'` is REJECTED by clap. The `conflicts_with = "workers_json"` / `conflicts_with = "workers"` annotations in `mod.rs:238, 241, 250, 253` are critical correctness invariants; a future clap upgrade silently dropping that attribute would not be caught. Same applies to `--blackboard X --blackboard-file path`.

**Fix:** Add tests like:
```rust
#[test]
fn swarm_verb_rejects_both_workers_and_workers_json() {
    let r = TestCli::try_parse_from([
        "hermes", "kanban", "swarm", "g",
        "--workers", "a",
        "--workers-json", "[]",
    ]);
    assert!(r.is_err(), "clap must reject mutually exclusive --workers and --workers-json");
}
```

### WR-03: `SwarmGraphSpec.body` plumbed but unused at both surfaces

**Skip reason:** Adding `--body` to the CLI verb AND a top-level `body`
property to the `kanban_swarm` LLM tool schema expands the public API

is exercised internally as the shared-body fallback when a rich-form
worker omits per-card body); it just is not user-reachable. No
behavioral bug — both surfaces hardcode `body: None`, which the existing
swarm tests cover. Defer to a focused "expose shared swarm body" phase
that also documents the inheritance rule in `KANBAN_GUIDANCE`.

### WR-05: `unsafe { env::set_var/remove_var }` racing in tokio tests

**Skip reason:** Requires either (a) adopting the `serial_test` crate as a
new workspace dependency, or (b) refactoring all 9 kanban tools to accept
env config via dependency injection so tests never touch the process env.
Either approach touches the test harness across multiple files and
phases (the bug pre-existed 36.3.7.7 — the swarm phase only added one
new offender, `tools/swarm.rs::is_available_respects_env`). The existing
`ENV_LOCK` mutex covers tests inside `tools_smoke.rs`; cross-file lock
coverage is a test-harness-wide refactor. Tracked for a future
"deflake-kanban-tests" phase.

### WR-06: `std::mem::forget(tempdir)` leaks DB files

**Skip reason:** Pre-existing across all kanban test modules
(`tests/tools_smoke.rs` + `tools/swarm.rs::tests` + `tools/create.rs::tests`).
The fix (move `TempDir` into a `_keep_alive: Option<TempDir>` field on
`KanbanStore`) changes the public struct shape and would require updating
every test that constructs a `KanbanStore` plus every production caller.
Out of scope for a hot-fix pass; tracked for the same
"deflake-kanban-tests" phase as WR-05.

### WR-08: `validate_profile_name` runs twice (tool + store)

**Skip reason:** Reviewer notes "this isn't a bug today" — defense-in-depth
is the correct posture for the store layer (it must not trust callers),
and the tool-side pre-check exists to produce a structured rejection
envelope for the orchestrator. Removing either layer creates risk:
removing the tool check loses structured rejection shape; removing the
store check trusts caller-provided input at the persistence boundary.
The right action is a doc-comment on the tool check that says "advisory;
store enforces" — pure documentation, not a code fix. Tracked as a
follow-up "code comment audit" pass.
