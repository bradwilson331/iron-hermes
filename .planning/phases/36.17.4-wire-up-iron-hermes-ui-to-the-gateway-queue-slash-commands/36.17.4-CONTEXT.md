# Phase 36.17.4: wire up iron_hermes_ui to the gateway queue + slash commands - Context

**Gathered:** 2026-05-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Bring real FIFO queueing to the `iron_hermes_ui` Dioxus web surface so `/queue <message>` and the queue-aware slash commands behave the same way they already do on Telegram (post-36.17.2.1) and the ratatui TUI (post-36.17.3). Today's web UI rejects a second message while a turn is in flight with `"Another request is already in progress"` (`crates/iron_hermes_ui/src/server/ws.rs:204-214`). This phase replaces that rejection with FIFO queueing that drains automatically after each turn, plus a full `Queue: N` status pill + inline transcript-line feedback on the wasm client.

The `MessageQueue<K>` trait, `QueueError`, `SessionKey`, and `MAX_QUEUE_DEPTH=128` constant already live in `ironhermes-core::queue` (Phase 36.17.3 Plan 01). The gateway's `SessionQueue` is the production implementor. This phase is the **second non-gateway consumer** of the trait (TUI was first).

**In scope:**
- `AppState` (`crates/iron_hermes_ui/src/server/state.rs`) gains:
  - `queue: Arc<dyn MessageQueue<SessionKey>>` — a single shared `SessionQueue`, keyed per session_id.
  - `queue_paused: Arc<std::sync::Mutex<HashMap<String, Arc<AtomicBool>>>>` + `get_or_create_paused_flag(session_id)` mirroring the existing `running_agents` / `get_or_create_running_flag` pattern at `state.rs:230-238`.
- Per-session `SessionKey` constructed as `SessionKey { platform: Platform::Web, chat_id: session_id.clone(), user_id: "web".into() }` (D-01).
- WebSocket recv-loop (`ws.rs`) changes:
  - Replace the in-flight reject at `ws.rs:204-214` with `app_state.queue.try_push(&key, message)` + cap-hit fork.
  - Post-turn self-drain: when the spawned turn task finishes, the recv-loop checks `!paused.load() && queue.pop(&key) == Some(text)` and re-spawns `run_web_turn` with the popped text on the same WS (D-02). The "wake-up" needs a tokio::select! arm watching the JoinHandle (planner picks the exact mechanism — extra select! arm vs Notify vs keepalive-tick poll).
- New `ChatStreamEvent::QueueUpdated { depth: u32, paused: bool }` variant in `crates/iron_hermes_ui/src/protocol.rs` (D-03). Emitted on every push, pop, pause toggle, unpause, and queue clear. Mirrors the payload-free `SubagentEvent {}` precedent at `protocol.rs:38` but carries the depth + paused snapshot directly.
- Inline confirmation Delta lines (D-03):
  - `/queue <text>` success → `tx.send(Delta { text: "Queued: \"<text>\" (N in queue)\n" })` + `tx.send(QueueUpdated { depth: N, paused })` + `tx.send(Finished { total_tokens: 0 })`.
  - Cap-hit → `tx.send(Delta { text: "Queue is full (128/128). /stop or /flush to drain.\n" })` + `Finished`.
- Slash command wiring inside the existing `ResolveResult::Exact | PrefixMatch` arm in `ws.rs:237-336`:
  - `/queue` — push via `queue.try_push`, emit Delta + QueueUpdated + Finished as above.
  - `/pause` (already a registered `CommandResult::PauseQueue` variant from 36.17.3-02) — `fetch_xor(true, SeqCst)` toggle on the per-session paused flag; emit `QueueUpdated` + `Delta { text: "Queue paused. (N queued)\n" }` + `Finished`.
  - `/unpause` alias (NOT `/resume` — registry collision documented in 36.17.3-CONTEXT.md D-06) — `swap(false, SeqCst)` explicit set; emit `QueueUpdated` + `Delta { text: "Queue resumed.\n" }` + `Finished`. If already false, emit informational `"Queue was not paused.\n"`.
  - `/new` and `/reset` — call `queue.clear(&key)` AND `paused_flag.store(false, SeqCst)` BEFORE the existing `reset_web_session` call at `ws.rs:308`. Emit `QueueUpdated { depth: 0, paused: false }` first (D-04).
  - `/stop` — clear queue + reset paused; emit `QueueUpdated { depth: 0, paused: false }` + `Delta { text: "Queue cleared. Current turn finishing.\n" }` + `Finished`. **Does NOT abort the in-flight turn** (D-05 — documented divergence from TUI D-08 / gateway 36.17.2 /stop semantics; in-flight cancel is deferred).
- Wasm client UI (D-03):
  - Render `Queue: N` / `Queue: N (paused)` pill in the HermesApp status bar with hide-when-zero discipline (mirrors TUI 36.17.3 D-09 + Plan 04).
  - Render Delta lines from queue events as inline transcript lines using the existing Delta render path (no new component).
  - Pill state is driven by a `Signal<(u32, bool)>` updated on `QueueUpdated` receipt — same pattern as `subagent_events: Signal<u64>` at `protocol.rs:30-38`.

**Out of scope (carried forward):**
- **In-flight turn cancellation on `/stop`** — D-05 explicitly defers wiring a `CancellationToken` through `TurnRequest` / `AgentRuntime::run_turn` / `agent_loop`. `/stop` here only clears the queue. A future phase can land cooperative cancel for true TUI/gateway parity.
- **Per-session background drain task** — D-02 picks WS recv-loop self-drain; the gateway-style Notify-wake worker pattern is not adopted. Trade-off: if all WS connections die mid-queue, items sit idle until any tab reconnects + sends a message. Acceptable for single-operator web use.
- **Multi-tab fairness / broadcast** — two tabs on the same session_id share the queue (D-01), but `QueueUpdated` events only reach the WS that performed the push/pop. Other tabs see depth drift until they take an action of their own. A broadcast-channel subscriber registry per session_id is deferred.
- **`/flush` slash command** — referenced in the cap-hit message as forward-compat hint but not implemented (matches 36.17.3 deferral).
- **`/status` slash command** — redundant with the status-bar pill (D-09 carry-forward from 36.17.3).
- **Discord/Slack/REST consumers of the trait** — covered by `[[project_multiplatform_gateway_scope]]` deferrals.
- **Queue persistence across server restarts** — in-memory only, matches gateway + TUI.
- **Cross-session broadcast of QueueUpdated** — only the WS that triggered the change receives the typed event in this phase.

<decisions>
## Implementation Decisions

### Queue Scope & Keying
- **D-01:** Per-session_id queues owned by `AppState`. Single `Arc<dyn MessageQueue<SessionKey>>` instance — `SessionQueue` from gateway — shared across all WS connections. Each connection constructs `SessionKey { platform: Platform::Web, chat_id: session_id.clone(), user_id: "web".into() }` at the call site. Queue survives WS disconnect/reconnect. Two browser tabs on the same session_id share the queue. **Rationale:** mirrors the existing `running_agents` + `nudge_turns` per-session-id pattern at `state.rs:38-49`; mirrors gateway's per-session model exactly; user-validated against TUI's fixed-key alternative.
- **D-01a:** Per-session `Arc<AtomicBool>` paused flags live in `AppState.queue_paused: Arc<std::sync::Mutex<HashMap<String, Arc<AtomicBool>>>>` with a `get_or_create_paused_flag(&self, session_id: &str) -> Arc<AtomicBool>` method mirroring `get_or_create_running_flag` at `state.rs:230-238` byte-for-byte (entry-or-insert, Mutex never held across .await). Same unbounded-growth tradeoff accepted as `running_agents`.

### Drain Mechanism
- **D-02:** WS recv-loop self-drain. After a turn's `JoinHandle` reports `is_finished()`, the recv-loop checks `!paused && queue.pop(&key).is_some()` and immediately spawns the next `run_web_turn` against the same WS using the popped text. **The exact wake-up mechanism (extra `tokio::select!` arm watching the JoinHandle vs. a tokio::Notify the spawned task fires on drop vs. checking on the existing keepalive tick) is planner's discretion** — see Claude's Discretion below. The current WR-02 `is_finished` post-check on next frame (`ws.rs:198-202`) is the existing seam; planner determines whether to extend it inline or add a dedicated wake-up signal so drain happens without waiting for the next inbound frame.
- **D-02a:** Multi-tab fairness: whichever WS connection's recv-loop fires the drain check first will pop and spawn. Other tabs are not notified of the pop. Acceptable; multi-tab broadcast is explicitly deferred.
- **D-02b:** If a WS dies mid-chain (close frame, transport error), queued items sit in `AppState.queue` until any tab on the same session_id reconnects and sends a message — at which point the recv-loop's drain check picks them up. No background "orphan drain" worker.

### Client Visibility Surface
- **D-03:** Two complementary surfaces:
  - **Typed event:** new `ChatStreamEvent::QueueUpdated { depth: u32, paused: bool }` variant in `protocol.rs`. Emitted on every push, pop (just BEFORE spawning the next turn), pause toggle, unpause, and queue clear. Mirrors the `SubagentEvent {}` external-tagged precedent; serializes to `{"QueueUpdated":{"depth":3,"paused":false}}`.
  - **Inline Delta:** human-readable confirmation lines emitted as `ChatStreamEvent::Delta` for `/queue` (`"Queued: \"<text>\" (N in queue)\n"`), cap-hit (`"Queue is full (128/128). /stop or /flush to drain.\n"`), `/pause` (`"Queue paused. (N queued)\n"`), `/unpause` (`"Queue resumed.\n"` or `"Queue was not paused.\n"`), and `/stop` (`"Queue cleared. Current turn finishing.\n"`).
- **D-03a:** Wasm UI scope **included this phase**: status-bar `Queue: N` / `Queue: N (paused)` pill with hide-when-zero discipline, driven by a `Signal<(u32, bool)>` set from `QueueUpdated` events (same pattern as `subagent_events: Signal<u64>` at `protocol.rs:30-38`). Inline Delta lines render through the existing Delta path with no new component.
- **D-03b:** Pill location in the HermesApp tree is planner's discretion — the user instructed `HermesApp` is the active root (`[[project_warp_vs_hermes_app_active_root]]`), not `WarpHermes`. Planner identifies the exact status-bar render site in HermesApp's component tree (shell_legacy/status_bar.rs is the prototype; HermesApp may already have an equivalent).

### Slash Command Ordering
- **D-04:** `/new` and `/reset` MUST call `queue.clear(&key)` AND `paused_flag.store(false, SeqCst)` BEFORE the existing `reset_web_session(&session_id)` call at `ws.rs:308`. Carries forward 36.17.3 D-07 and the Pitfall 5 ordering invariant from 36.17.1.
- **D-04a:** `/stop` arm ordering: `queue.clear(&key)` → `paused_flag.store(false, SeqCst)` → emit `QueueUpdated { depth: 0, paused: false }` → emit Delta → emit Finished. **No `JoinHandle::abort` and no `cancel_token.cancel()`** — the in-flight `run_web_turn` task completes naturally (D-05).

### /stop Semantics — Documented Divergence
- **D-05:** `/stop` on web is **clear-queue-only** for this phase. The current `run_web_turn` constructs `TurnRequest { cancel_token: None, .. }` at `state.rs:290` and there is no `CancellationToken` field on `AppState`. Wiring true in-flight cancel would require (a) a per-session `CancellationToken` map on `AppState`, (b) threading it into `TurnRequest`, (c) `AgentRuntime::run_turn` honoring it cooperatively. That work is **deferred to a follow-up phase** for scope. The Delta message `"Queue cleared. Current turn finishing.\n"` is the user-facing acknowledgement of this divergence.
- **D-05a:** Divergence from canonical 36.17.3 D-08 / 36.17.2 `/stop` semantics is explicit and ADR-worthy. Planner records it in `36.17.4-PLAN.md` decisions section + ROADMAP.md goal line.

### Cap, Constants & Slash Surface (carried forward — locked at core level)
- **D-06:** Cap = `ironhermes_core::queue::MAX_QUEUE_DEPTH` (128). `try_push` returns `QueueError::CapacityReached`. Cap-hit Delta message is the exact string above (terminal bell omitted — web is browser, not terminal).
- **D-07:** `/pause` alias is **`/unpause`** (NOT `/resume`). Registered as `CommandResult::PauseQueue` / `CommandResult::UnpauseQueue` in `ironhermes-core::commands` via 36.17.3 Plan 02. Web handler adds match arms; no new core variants needed.
- **D-08:** `is_bypass("queue") == true`, `is_bypass("pause") == true`, `is_bypass("unpause") == true`, `is_bypass("new") == true`, `is_bypass("reset") == true`, `is_bypass("stop") == true` — already shipped in `ironhermes_core::commands::running_agent`. The existing `is_bypass(&def.name)` check at `ws.rs:242` will route all queue-touching slashes around the running-agent guard correctly without code changes.

### Regression Test Surface
- **D-09:** New integration test file `crates/iron_hermes_ui/tests/web_queue_*.rs` (planner picks split — likely one `web_queue_drain.rs` for the FIFO + recv-loop drain path, one `web_queue_controls.rs` for `/pause` / `/unpause` / `/new` / `/stop`, one `web_queue_protocol.rs` for `QueueUpdated` serde shape + emit-on-every-state-change). Mirror the 36.17.3 test triplet (`tui_queue_drain.rs`, `tui_queue_controls.rs`, `status_line_queue_pill.rs`).
- **D-10:** Driving the WS recv-loop in tests is non-trivial. The existing test seams in iron_hermes_ui include `wave0_smoke.rs`, `running_agent_guard_web_tests.rs`, `websocket_lifecycle_parity.rs`, `server_runtime_parity.rs` — planner identifies the highest-leverage seam (likely WS-level integration via the existing fullstack test scaffolding) and writes the FIFO drain assertion using real `app_state.queue.try_push` + spawned `run_web_turn` cycles.
- **D-11:** `QueueUpdated` serde shape test required, locking `{"QueueUpdated":{"depth":3,"paused":false}}` external tagging (mirrors the `SubagentEvent` shape test at `protocol.rs:48-59`).
- **D-12:** Phase gate: full `cargo test -p iron_hermes_ui` green AND full `cargo test -p ironhermes-gateway` still green AND `cargo test -p ironhermes-cli` (TUI) still green (no regression in the two prior trait consumers). `cargo check --workspace --all-features` green.

### Claude's Discretion
- **Drain wake-up mechanism (D-02):** extra `tokio::select!` arm watching `turn.handle` vs. tokio::Notify the spawned task fires on completion vs. checking only on the existing 5-second keepalive tick. Planner picks based on latency analysis (keepalive-tick poll = up to 5s delay before drain starts; select-arm = immediate). Recommend the select-arm or Notify path; keepalive-tick poll is acceptable but visibly laggy.
- **Pill render location in HermesApp:** planner identifies the active status-bar render site (shell_legacy/status_bar.rs is the prototype; the active HermesApp may have its own status surface — `[[project_warp_vs_hermes_app_active_root]]`).
- **Whether to emit `QueueUpdated` for ambient pops (auto-drain) or only for explicit slash-driven state changes** — recommend emit on every change for live pill accuracy; planner finalizes.
- **`/pause` and `/unpause` confirmation Delta exact text** — proposals above ("Queue paused. (N queued)" / "Queue resumed." / "Queue was not paused.") are recommendations; planner can adjust for tone.
- **Test split (`web_queue_drain.rs` / `web_queue_controls.rs` / `web_queue_protocol.rs` vs. one file)** — planner picks based on the available test seam.
- **Whether to add an ADR (`.planning/ADR-`) for the D-05 `/stop` divergence or capture it only in PLAN.md decisions** — recommend PLAN.md decisions + ROADMAP.md goal line + REQUIREMENTS.md note; promote to ADR only if reviewer flags.

- User explicitly accepted that two browser tabs share the queue but only the tab that triggers the push/pop receives `QueueUpdated` (multi-tab broadcast deferred). The depth-drift between tabs is a known acceptable behavior for this phase.
