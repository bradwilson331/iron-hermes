## Queue scope / keying

| Option | Description | Selected |
|--------|-------------|----------|
| Per session_id (gateway-style) | AppState owns `Arc<dyn MessageQueue<SessionKey>>`; key = `SessionKey { platform: Web, chat_id: session_id, user_id: "web" }`. Survives WS reconnect. Multi-tab on same session shares queue. Mirrors gateway's per-session model + the existing `running_agents` / `nudge_turns` pattern at `state.rs:38-49`. | ✓ |
| Per WS connection (TUI-style fixed key) | Each WS holds its own `Arc<dyn MessageQueue<SessionKey>>` with a fixed key. Queue dies with the connection. Two tabs on same session_id have separate queues. Simpler; matches TUI 36.17.3 exactly. | |

**User's choice:** Per session_id (gateway-style).
**Notes:** Drives D-01 + D-01a. AppState owns one shared `SessionQueue` keyed per session_id. Per-session paused flags mirror `running_agents` pattern byte-for-byte via a new `get_or_create_paused_flag` method. Multi-tab depth drift is accepted; broadcast across tabs is deferred.

## Drain mechanism on web

| Option | Description | Selected |
|--------|-------------|----------|
| WS recv-loop self-drain | After `JoinHandle::is_finished()`, the recv-loop pops + spawns next turn on the same WS. Pure extension of the existing WR-02 check at `ws.rs:198-202`. No background tasks. | ✓ |
| Background per-session drain task | AppState spawns per-session_id worker; tokio::Notify wake; calls `run_web_turn` directly; broadcasts to subscribed WS via broadcast channel. Gateway-parity, but new infrastructure (broadcast + subscriber lifecycle). | |
| Drain inside the spawned turn task | Each spawned turn task loops: `run_web_turn` → check queue → re-run. One JoinHandle handles the full chain. Harder to insert `/pause` mid-chain; `/stop` must abort the chain not just one turn. | |

**User's choice:** WS recv-loop self-drain.
**Notes:** Drives D-02 + D-02a + D-02b. Wake-up mechanism (extra `tokio::select!` arm vs Notify vs keepalive-tick poll) is planner's discretion — recv_raw blocks, so the existing WR-02 next-frame check is too laggy; planner picks a dedicated wake signal. Trade-off accepted: if WS dies mid-queue, items idle until any tab on the same session reconnects + acts.

## Client visibility surface

| Option | Description | Selected |
|--------|-------------|----------|

**User's choice:** Typed event + Delta + full wasm UI.
**Notes:** Drives D-03 + D-03a + D-03b. Pill driven by `Signal<(u32, bool)>` updated on `QueueUpdated`, mirroring the `subagent_events: Signal<u64>` precedent. Pill render location is planner's discretion — must target HermesApp (active root), NOT WarpHermes legacy shell, per `[[project_warp_vs_hermes_app_active_root]]`. Inline Delta lines render through the existing Delta path with no new component.

## /stop semantics on web

| Option | Description | Selected |
|--------|-------------|----------|
| Clear queue + reset paused only (current turn finishes) | No new cancel plumbing. In-flight `run_web_turn` finishes naturally. Documented divergence from TUI D-08 / gateway 36.17.2 `/stop`. | ✓ |
| Wire CancellationToken into TurnRequest | Per-session token map on AppState; threaded into `TurnRequest`; `run_turn` cooperative cancel. True parity. Larger scope — touches `ironhermes-agent` cancel surface. | |
| JoinHandle::abort on the spawned ws task | Hard kill the tokio task. No agent_loop changes. Risk: torn-down state mid-LLM-call, SQLite mid-write, partial state. | |

**User's choice:** Clear queue + reset paused only (current turn finishes).
**Notes:** Drives D-05 + D-05a + D-04a. Documented divergence from canonical 36.17.3 D-08 / 36.17.2 `/stop`. User-facing Delta `"Queue cleared. Current turn finishing.\n"` acknowledges the divergence. The full CancellationToken plumbing (per-session token map → TurnRequest → AgentRuntime::run_turn → agent_loop cooperative cancel) is deferred to a plausible follow-up "36.17.5 web /stop in-flight cancel parity". JoinHandle::abort path explicitly rejected due to mid-LLM-call partial-state risk.

## Claude's Discretion

Items where the user did not pin a specific answer and the planner has flexibility:

- **Drain wake-up mechanism (D-02):** select-arm watching JoinHandle vs tokio::Notify on completion vs keepalive-tick poll. Recommend select-arm or Notify for immediate drain; keepalive-tick is acceptable but adds up to 5s latency.
- **Pill render location in HermesApp:** planner identifies the active status-bar component (shell_legacy/status_bar.rs is the prototype, not the active root).
- **Whether `QueueUpdated` fires on ambient pops (auto-drain) or only on slash-driven changes** — recommend emit on every change for live pill accuracy.
- **Exact pause/unpause confirmation Delta text** — proposals captured in CONTEXT.md D-03; planner tunes for tone.
- **Test file split** — single file vs `web_queue_drain.rs` + `web_queue_controls.rs` + `web_queue_protocol.rs`. Mirrors TUI triplet; planner picks based on available test seam.
- **Whether to author an ADR for the D-05 `/stop` divergence** — recommend PLAN.md decisions + ROADMAP.md goal line + REQUIREMENTS.md note; promote to ADR only if reviewer flags.
