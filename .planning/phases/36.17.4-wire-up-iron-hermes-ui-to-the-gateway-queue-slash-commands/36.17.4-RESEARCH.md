## Summary

Phase 36.17.4 wires `iron_hermes_ui`'s WebSocket surface to the `MessageQueue<SessionKey>` trait that shipped in 36.17.3, delivering FIFO queueing parity with Telegram (36.17.2.1) and the ratatui TUI (36.17.3). The changes land in three layers: (1) `AppState` gains `queue` + `queue_paused` fields in `state.rs`; (2) the `ws_chat` recv-loop in `ws.rs` replaces the hard rejection at lines 204-214 with `queue.try_push` + a self-drain mechanism triggered when the current turn completes; (3) the wasm Dioxus client in `hermes_app/mod.rs` gains a `QueueUpdated` event handler and a `Signal<(u32, bool)>` that drives a status-bar pill in `AppFooter`.

The TUI phase (36.17.3) is the direct analog. All trait types (`MessageQueue<K>`, `QueueError`, `SessionKey`), all `CommandResult` variants (`Queued`, `PauseQueue`, `UnpauseQueue`), and the `is_bypass` list are already shipped and require NO changes to `ironhermes-core`. The gateway's `SessionQueue` is the concrete implementor; `AppState` instantiates one via `Arc<SessionQueue>` cast to `Arc<dyn MessageQueue<SessionKey>>`.

**Primary recommendation:** The recv-loop self-drain should use Option A (extra `tokio::select!` arm watching `turn.handle`) because the existing `ws_chat` loop is already a three-arm `tokio::select!` (`socket.recv_raw` | `maybe_event` | `keepalive.tick`). Adding a fourth arm watching `turn.handle` fires immediately on turn completion with zero additional state and is robust to panics inside the spawned task (JoinHandle completion fires even on panic). Option B (Notify) is structurally heavier. Option C (keepalive tick) introduces up to 5 seconds of latency before drain begins.

**Critical gap found:** CONTEXT.md D-08 states `is_bypass("pause")` and `is_bypass("unpause")` are already true. **This is INCORRECT as-shipped.** The actual `is_bypass` in `crates/ironhermes-core/src/commands/running_agent.rs:45` matches only `"stop" | "new" | "status" | "queue"`. In the TUI (36.17.3), `/pause` and `/unpause` work because the TUI dispatch layer intercepts them BEFORE the `is_bypass` guard fires (the TUI uses `app.agent_running` not the bypass list for the `pause`/`unpause` commands). The web `ws.rs` uses the same pattern: the `is_bypass(&def.name)` check at line 241 would block `/pause` and `/unpause` when a turn is in flight. Either (a) `is_bypass` must be updated to add `"pause"`, or (b) the web slash dispatch must intercept `"pause"` before the is_bypass gate exactly as the TUI does. Option (b) is safer — it does not modify core and matches the TUI pattern. Planner must decide and document.

## Research Finding 1: Drain Wake-Up Mechanism (D-02 — Planner's Discretion)

### Current recv-loop structure (`ws.rs:114-530`)

The existing `ws_chat` loop is a `tokio::select!` with three arms:

```rust
loop {
    tokio::select! {
        raw = socket.recv_raw() => { ... }           // arm 1: inbound frames

        maybe_event = async {                         // arm 2: agent stream → client
            match in_flight_turn.as_mut() {
                Some(turn) => turn.rx.recv().await,
                None => std::future::pending().await,
            }
        } => { ... }

        _ = keepalive.tick() => { ... }              // arm 3: 5-second ping
    }
}
```

The WR-02 opportunistic clear at lines 198-202 already checks `turn.handle.is_finished()` at the top of arm 1, before the busy-gate at 204-214. This is the existing seam — but it only fires when a new inbound frame arrives, not when the turn finishes.

### Option A: Fourth `tokio::select!` arm watching the JoinHandle

```rust
// arm 4 — fires immediately when the spawned turn task finishes
// (including panic exit — JoinHandle completion is guaranteed on panic)
_ = async {
    match in_flight_turn.as_mut() {
        Some(turn) if !turn.handle.is_finished() => turn.handle.by_ref().await,
        _ => std::future::pending().await,
    }
} => {
    // Turn just finished. Attempt drain if not paused.
    if let Some(turn) = in_flight_turn.take() {
        // join to surface any panic error
        if let Err(e) = turn.handle.await {
            warn!(session_id = %turn.session_id, reason = %e, "turn task join failed");
        }
    }
    // Drain: check paused + queue
    let session_id_for_drain = /* captured from in_flight_turn.session_id before take */;
    let key = SessionKey { platform: Platform::Web,
                           chat_id: session_id_for_drain.clone(),
                           user_id: "web".into() };
    let paused = app_state.get_or_create_paused_flag(&session_id_for_drain)
                          .load(Ordering::SeqCst);
    if !paused {
        if let Some(text) = app_state.queue.pop(&key) {
            let depth = app_state.queue.len(&key);
            // emit QueueUpdated BEFORE spawning next turn
            let _ = tx_for_drain.send(ChatStreamEvent::QueueUpdated {
                depth: depth as u32, paused: false
            });
            // spawn next run_web_turn (same pattern as the primary spawn at ws.rs:363-447)
            // ... set in_flight_turn = Some(InFlightTurn { ... })
        }
    }
}
```

**Latency:** immediate — fires as soon as tokio schedules the JoinHandle completion future.

**Complexity:** medium — requires tracking `session_id` before `in_flight_turn.take()`, and cloning the `tx` channel sender for the drain arm to emit `QueueUpdated`.

**Robustness to panic:** JoinHandle resolves to `Err(JoinError)` on panic — the drain arm still fires and the drain check proceeds; the previous turn's error is logged.

**Code-touch surface:** ws.rs only — no new AppState fields beyond `queue` + `queue_paused`.

**Pitfall:** `JoinHandle::by_ref()` is the correct call for polling without consuming (allows re-poll on next iteration). However, once the handle resolves, `by_ref().await` again is a no-op that returns immediately — so this arm must only be active when `in_flight_turn` exists AND the handle is not yet finished. The `!turn.handle.is_finished()` guard in the async block handles this: when `None` or already finished, it returns `pending()` to suppress the arm.

**Simpler alternative:** Drop the `by_ref()` approach and instead use the JoinHandle normally — take the JoinHandle out of `InFlightTurn` for the drain arm, store it as a local `Option<JoinHandle>`. But this complicates `in_flight_turn.take()` ordering. The cleanest approach:

```rust
// After turn.rx.recv() returns None (arm 2 — channel closed = turn finished):
None => {
    // Turn's tx dropped → channel closed → turn is done.
    if let Some(turn) = in_flight_turn.take() {
        if let Err(err) = turn.handle.await {
            warn!(session_id = %turn.session_id, "turn task join failed");
        }
        // DRAIN: attempt next queued item
        drain_next_queued(&app_state, &turn.session_id, &tx).await;
    }
}
```

**RECOMMENDATION: Use the existing `arm 2 None` branch as the drain trigger.** This is the natural "turn is done" signal — the rx channel closes when the spawned task's `tx` is dropped (last drop is at end of the spawn block). No fourth arm needed. The `None` case in arm 2 already awaits the JoinHandle (line 488: `turn.handle.await`). The drain logic inserts AFTER the `.await`.

This is **Option A simplified** — zero new select arms, uses the existing `None => { ... }` completion branch in arm 2. Latency: immediate (fires as soon as the channel closes, which happens when the spawned task drops its tx). This is the lowest-complexity Option A variant and the most idiomatic.

**Code shape (exact, insertable):**

```rust
// ws.rs arm 2 None => branch (around line 486-498), EXTENDED:
None => {
    if let Some(turn) = in_flight_turn.take() {
        let session_id_done = turn.session_id.clone();
        if let Err(err) = turn.handle.await {
            warn!(
                session_id = %turn.session_id,
                reason = %err,
                in_flight = false,
                "turn task join failed"
            );
        }
        // Phase 36.17.4 (D-02): WS recv-loop self-drain.
        // Emit QueueUpdated BEFORE spawning next turn (D-03).
        let key = ironhermes_core::session::SessionKey {
            platform: ironhermes_core::types::Platform::Web,
            chat_id: session_id_done.clone(),
            user_id: Some("web".into()),
        };
        let paused_flag = app_state.get_or_create_paused_flag(&session_id_done);
        if !paused_flag.load(std::sync::atomic::Ordering::SeqCst) {
            if let Some(queued_text) = app_state.queue.pop(&key) {
                let depth_after = app_state.queue.len(&key);
                // Emit QueueUpdated BEFORE spawning (D-03 — pill updates before next Delta)
                // NOTE: tx here is the channel for the DRAIN turn, freshly created below.
                // We emit QueueUpdated via the socket directly (not via a new tx):
                let qu_event = ChatStreamEvent::QueueUpdated {
                    depth: depth_after as u32,
                    paused: false,
                };
                let _ = socket.send_raw(Message::Text(
                    serde_json::to_string(&qu_event).unwrap_or_default()
                )).await;
                // Spawn next turn (mirrors primary spawn block at ws.rs:363-447)
                let (tx_drain, rx_drain) = mpsc::unbounded_channel::<ChatStreamEvent>();
                // ... (full spawn body, same as primary spawn)
                in_flight_turn = Some(InFlightTurn {
                    session_id: session_id_done,
                    rx: rx_drain,
                    handle: /* tokio::spawn(...) */,
                });
            }
        }
    }
}
```

**Note on QueueUpdated emission before spawning:** The CONTEXT requires `QueueUpdated` emitted "just BEFORE spawning the next turn." In the None branch, this means emit to the socket directly (not through the new turn's tx channel, which doesn't exist yet). Since we `await` the socket send, this is clean — the send completes before spawn.

### Existing recv loop (`hermes_app/mod.rs:176-264`)

Insert AFTER `SubagentEvent {}` arm (or before — ordering within a match is irrelevant for correctness; after is cleaner):

**No `.await` in this arm** — `queue_state.set(...)` is synchronous. The signal borrow safety rule is satisfied trivially.

## Research Finding 6: Drain Ordering Subtlety (D-03 Emit-before-spawn)

The TUI `maybe_drain_queue` in `app.rs` (36.17.3) does NOT emit a `QueueUpdated` — the TUI updates the status bar by reading `queue.len()` live per render frame (Pitfall 5 in TUI research). There is no typed event in the TUI protocol.

For the web surface, `QueueUpdated` is the ONLY mechanism to update the wasm client's queue pill (there is no live-per-frame render equivalent). Therefore the web surface MUST emit `QueueUpdated` before spawning the next turn.

**Ordering constraint:** emit `QueueUpdated { depth: N-1, paused: false }` (after pop, N-1 items remain), then spawn next turn. This ensures the pill decrements before the first Delta from the next turn arrives. If the order is reversed (spawn first, then QueueUpdated), the client sees the next turn's Delta before the pill updates, which would be briefly confusing.

Since the drain emits `QueueUpdated` directly to `socket.send_raw(...)` (not through the new turn's tx channel), the socket send is `await`ed before the spawn — ordering is guaranteed.

**TUI did NOT face this:** TUI uses a side-channel (live render read) so no ordering constraint existed for 36.17.3's drain. The web phase is more strict on this ordering.

## Common Pitfalls

### Pitfall 1: is_bypass Gap for "pause" / "unpause"

**What goes wrong:** `/pause` and `/unpause` are rejected with `AGENT_RUNNING_REJECT_MSG` when a turn is in flight, because `is_bypass("pause")` returns `false`. CONTEXT.md D-08 incorrectly states they are already bypassed.

**Why it happens:** The `is_bypass` function in `running_agent.rs` was not updated in 36.17.3 (the TUI works because its `handle_session_control` dispatch is after the guard, and the TUI's pause-during-running-turn rejection is arguably correct UX). The CONTEXT.md assertion overstated what shipped.

**How to avoid:** Either add `"pause"` to `is_bypass` in `running_agent.rs` (clean fix, matches stated intent) OR intercept `"pause"` before the `is_bypass` gate in `ws.rs` (same as the D-08 note for `"queue"` which IS already bypassed). Adding to `is_bypass` is recommended.

**Warning signs:** Tests for `/pause` while a turn is running return `AGENT_RUNNING_REJECT_MSG` instead of pausing.

### Pitfall 2: QueueUpdated Emitted After Spawning Instead of Before

**What goes wrong:** Client sees Delta from the new turn before the pill decrements. The queue depth in the wasm client is temporarily wrong (N instead of N-1) during the first delta of the next turn.

**Why it happens:** The drain spawns the next `run_web_turn` before emitting `QueueUpdated`.

**How to avoid:** Always emit `QueueUpdated` via `socket.send_raw(...)` BEFORE the `tokio::spawn(...)` call. Since `socket.send_raw` is `.await`ed, the frame reaches the client before the spawn task starts.

**Warning signs:** During drain, the pill shows old depth for a brief moment then jumps.

### Pitfall 3: Holding std::sync::Mutex Lock Across .await

**What goes wrong:** Compiler error or deadlock if the `queue_paused` Mutex guard is held across any `.await` point.

**Why it happens:** `get_or_create_paused_flag` returns `Arc<AtomicBool>` (already released from the Mutex). This is safe. The pattern mirrors `get_or_create_running_flag`. The pitfall only occurs if the planner introduces a borrow of the Mutex guard across `.await` rather than using the returned Arc.

**How to avoid:** Always call `get_or_create_paused_flag(session_id)` and immediately clone the returned `Arc<AtomicBool>`. Never hold the Mutex guard across any `.await`. This is the existing pattern — `get_or_create_running_flag` does it correctly at `state.rs:234`.

**Warning signs:** `Send + Sync` compile errors mentioning `MutexGuard`.

### Pitfall 4: Signal Borrow Across .await in Dioxus Wasm Client

**What goes wrong:** Runtime panic in WASM: `BorrowError` when `GenerationalRef` is held across an `.await` boundary (clippy.toml enforced, Dioxus 0.7 specific).

**Why it happens:** If the `queue_state.read()` borrow in the recv loop or `AppFooter` is not dropped before any `.await`.

**How to avoid:** Read signal into a `let` binding, use the value, let the borrow drop at `;`. Pattern: `let (depth, paused) = *queue_state.read();` — the `*` dereferences the `GenerationalRef<(u32,bool)>` to a copy (both `u32` and `bool` are `Copy`), dropping the borrow immediately.

**Warning signs:** Clippy lint `clippy::await_holding_refcell_ref` or runtime `BorrowError` panic in WASM.

### Pitfall 5: /new and /reset Must Clear Queue BEFORE reset_web_session

**What goes wrong:** Session is cleared first, then queue.clear runs — the in-flight drain from the previous session context sees a non-empty queue and spawns a turn against the freshly-cleared session, injecting stale messages into the new session.

**Why it happens:** Incorrect ordering in the `CommandResult::NewSession` arm.

**How to avoid:** Mandatory order: `queue.clear(&key)` → `paused_flag.store(false)` → emit `QueueUpdated { depth: 0, paused: false }` → `reset_web_session(&session_id)`. This is D-04, mirroring 36.17.3 D-07 and the 36.17.1 "Pitfall 5" ordering invariant.

**Warning signs:** After `/new`, old queued messages appear in the new session's transcript.

### Pitfall 6: /stop Delta Message Order (D-04a)

**What goes wrong:** `queue.clear` is called AFTER the Delta message is emitted, so `len()` in the message text shows the pre-clear depth.

**How to avoid:** Order: `queue.clear` → `paused.store(false)` → emit `QueueUpdated { depth: 0, paused: false }` → emit Delta → emit Finished. The clear happens first; the Delta text is `"Queue cleared. Current turn finishing.\n"` (fixed string, no depth count).

### Pitfall 7: in_flight_turn.take() Before session_id Access

**What goes wrong:** Calling `in_flight_turn.take()` consumes the `InFlightTurn` struct, making `session_id` inaccessible for the drain key construction.

**How to avoid:** Clone `session_id` BEFORE calling `take()`:


### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Queue spam DoS | Denial of Service | `MAX_QUEUE_DEPTH = 128` per-session cap; `CapacityReached` returned on overflow; cap-hit Delta informs user |
| Stale queue across session reset | Tampering | D-04 ordering: `queue.clear` before `reset_web_session` — same mitigation as 36.17.1 Pitfall 5 |
| Drain reentry (double-spawn) | Denial of Service | D-02 drain fires only in `None =>` arm (natural completion signal) — cannot fire while a turn is in flight (turn.rx is still open) |
| Multi-tab queue injection | Spoofing | Accepted per D-02a — two tabs on same session_id share the queue; no cross-session bleed (key is per session_id) |
