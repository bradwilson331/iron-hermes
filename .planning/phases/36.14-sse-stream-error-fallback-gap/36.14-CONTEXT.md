# Phase 36.14: SSE Stream Error Fallback Gap — Context

**Gathered:** 2026-05-26
**Status:** Ready for planning
**Source:** Config debug session / fallback mechanism audit

<domain>
## Phase Boundary

The `AgentLoop` provider fallback chain (PROV-07, closed in Phase 27.1.4.1 and extended in 27.1.4.1.1) has a silent failure path that prevents fallback from triggering when a streaming LLM provider returns HTTP 200 but places an error payload **inside the SSE stream body** rather than using an HTTP error status code.

### The gap in precise terms

`LlmClient::chat_completion_stream` in `crates/ironhermes-agent/src/client.rs` checks the HTTP response status before spawning the stream consumer task:

```rust
// client.rs ~line 246
let status = response.status();
if !status.is_success() {
    let body = response.text().await.unwrap_or_default();
    anyhow::bail!("Streaming chat completion failed ({}): {}", status, body);
}
```

When the provider returns a non-2xx status, the error propagates correctly, `classify_llm_error_typed` classifies it, and `should_fallback = true` reaches the fallback-activation block in `agent_loop.rs`.

However, some providers — including OpenRouter — return **HTTP 200** and then send an error payload as a regular SSE data line:

```
data: {"error":{"message":"qwen/1qwen3.7-max is not a valid model ID","code":400}}
data: [DONE]
```

The spawned stream consumer tries to deserialize each data line as `ChatStreamChunk`:

```rust
// client.rs ~line 325
match serde_json::from_str::<ChatStreamChunk>(data) {
    Ok(chunk) => { /* process */ }
    Err(e) => {
        debug!("Failed to parse stream chunk: {} — data: {}", e, data);
        // ← silently dropped at DEBUG level only
    }
}
```

The error JSON fails to parse as `ChatStreamChunk`, is silently discarded, and the stream ends cleanly when `[DONE]` arrives. `call_llm_streaming` returns `Ok((empty_message, None))` — which lands in the `Ok(result)` branch in `agent_loop.rs`. The fallback condition (`Err(err)`) is **never reached**. The configured `fallback_providers` chain never activates. The user receives a silent empty response.

### Why this surfaces in practice

OpenRouter's routing model makes this common:

1. **Valid-format but unknown model ID** — OpenRouter validates model IDs lazily in some cases. If the request reaches the routing layer before validation, OpenRouter may return HTTP 200 then surface the error in-stream rather than returning HTTP 400 immediately.
2. **Upstream provider errors** — When OpenRouter successfully connects to an upstream (e.g., Qwen) but that upstream rejects the request, the error may propagate back as an SSE error event at HTTP 200 rather than a forwarded HTTP error status.
3. **Transient quota / routing failures** — Mid-stream routing failures on OpenRouter can manifest as SSE error events at HTTP 200.

### Real-world repro

Config with `model.default: qwen/qwen3.7-max` (misspelled) and `fallback_providers: [ollama]`:
- OpenRouter receives the request, HTTP handshake succeeds (200)
- OpenRouter sends `data: {"error":{"message":"qwen/qwen3.7-max is not a valid model ID","code":400}}`
- Stream parser discards the error chunk at `debug!` level
- `call_llm_streaming` returns `Ok((message with None content, None usage))`
- Agent loop treats this as a successful LLM turn with an empty assistant message
- Fallback to ollama never fires

### Prior art

Phase 27.1.4.1 closed the *wiring* gap (`wire_fallback_if_configured` at every `AgentLoop` construction site).
Phase 27.1.4.1.1 closed the *transport classifier* gap (detect `connection refused` / DNS / TCP errors with no HTTP status).
This phase closes the *SSE error event* gap: provider reachable + HTTP 200 + error in stream body.

Together these three phases fully cover PROV-07 across all failure modes.

<decisions>
## Implementation Decisions

### D-01: Error detection strategy — parse first, inspect for `"error"` field on parse failure

When `serde_json::from_str::<ChatStreamChunk>(data)` fails, attempt a second parse as `serde_json::Value` and check for a top-level `"error"` key. If present, treat the SSE line as a provider error event.

**Rationale:** This is the minimal-blast-radius approach: it only activates when the chunk already failed `ChatStreamChunk` deserialization (zero regression surface on the hot path). A `serde_json::Value` parse of a known-small SSE line is negligible overhead. Alternatives considered:
- `#[serde(untagged)] enum ChatStreamChunkOrError` — elegant but changes the primary deserializer for every chunk; risk of serde tag-resolution edge cases.
- Regex pre-scan for `"error"` — string matching before JSON parse; brittle (e.g. a model that returns a content delta containing `"error"` would false-positive).
- Structured `reqwest::Response` introspection — not applicable; we're already inside the spawned byte-stream task at this point.

### D-02: Error propagation mechanism — new `StreamEvent::ProviderError(String)` variant

Add a `StreamEvent::ProviderError(String)` variant to the `StreamEvent` enum. The stream consumer task sends this event and returns immediately (same pattern as `[DONE]`). `call_llm_streaming` in `agent_loop.rs` receives the event and converts it to `Err(anyhow!(...))`, causing the existing fallback/retry logic in `run()` to apply unchanged.

**Rationale:** Adding a variant to `StreamEvent` is additive and exhaustively handled at the two existing `match` sites (`call_llm_streaming` and `call_llm_streaming` in the Anthropic client path if applicable). No changes to `run()` or `classify_llm_error_typed` — returning `Err(...)` from `call_llm_streaming` is sufficient for the existing machinery to classify and act.

**Error string format:** `"Streaming chat completion failed (SSE error): {body}"` where `body` is the raw JSON string of the error chunk. This does NOT embed an HTTP status code (since there is none), so `extract_http_status` returns `None`. `is_transport_failure` also returns `false`. The error falls through to the pattern-matching fallbacks in `classify_llm_error_typed`, landing on `Unknown` → `(should_retry=true, should_fallback=false)`.

This means D-03 is required.

### D-03: Error string must encode the provider error code from the SSE body

Extract the `code` field from the SSE error JSON and embed it in the error string as `(NNN Reason)` if present, so `extract_http_status` in `classify_llm_error_typed` can classify it correctly:

```rust
// If error JSON has a numeric "code" field, format as:
// "Streaming chat completion failed (400 Bad Request): {body}"
// Otherwise:
// "Streaming chat completion failed (SSE error): {body}"
```

**Rationale:** Without this, all SSE errors land as `ProviderError::Unknown` → `(retry=true, fallback=false)` — the fallback still never fires. With it, a `"code": 400` from OpenRouter's error payload becomes a `400` in the error string, `extract_http_status` returns `Some(400)`, `classify_400_subcases` maps it to `SchemaInvalid` → `should_fallback=true`. This closes the gap completely.

The `code`-to-reason mapping needs only to be best-effort — if the code is not recognized or missing, fall back to `"SSE error"` as the reason text. This is correct behaviour because `Unknown` → no fallback is the safe default for unclassifiable errors.

Known code mappings to include: 400 → `"Bad Request"`, 401 → `"Unauthorized"`, 403 → `"Forbidden"`, 404 → `"Not Found"`, 429 → `"Too Many Requests"`, 500 → `"Internal Server Error"`, 502 → `"Bad Gateway"`, 503 → `"Service Unavailable"`.

### D-04: Scope — `LlmClient` (ChatCompletions path) only

`AnthropicClient` has its own streaming path and its own error handling. The Anthropic API never returns HTTP 200 with an error in the SSE body — Anthropic uses proper HTTP status codes. No changes to `anthropic_client.rs`.

**Note:** If a third-party provider using the `AnthropicMessages` `AnyClient` arm surfaces this behaviour in the future, the fix there would mirror this one. Not in scope for this phase.

### D-05: Non-fatal debug log preserved

Keep the existing `debug!("Failed to parse stream chunk: {} — data: {}", e, data)` for chunks that fail both parses (i.e. not a `ChatStreamChunk` and not a recognized error object). These are malformed or unexpected SSE lines that should remain visible in debug logs but not trigger an error. The new `ProviderError` path handles the error-object case; everything else stays as-is.

### D-06: Static-invariant test locks the new StreamEvent variant and error-propagation pattern

New file `crates/ironhermes-agent/tests/invariants_36_14.rs` asserting:
1. `client.rs` contains `StreamEvent::ProviderError` (variant exists)
2. `agent_loop.rs` contains the `StreamEvent::ProviderError` match arm (handler exists)
3. `client.rs` contains `"SSE error"` or `SSE error` (the error string token that distinguishes SSE-originated errors in logs)

### Claude's Discretion

- Exact name for the status-code-to-reason mapping fn (e.g. `sse_code_to_reason`, `http_code_to_reason_str`, or inlined as a `match`).
- Whether the second serde parse for error detection uses `serde_json::from_str::<serde_json::Value>` or a purpose-built `#[derive(Deserialize)] struct SseErrorEnvelope { error: SseError }` — the structured approach is slightly more explicit but the `Value`-based approach is more resilient to provider-specific envelope variations.
- Whether `StreamEvent::ProviderError(String)` carries the raw JSON string or a structured type. Raw string is simpler and sufficient — the classifier only needs the formatted error string.
- Exact names for new unit tests.
</decisions>

<deferred>
## Deferred Ideas

- **Non-LlmClient paths** — If `AnthropicClient` or future OpenAI-native paths ever exhibit this behaviour (HTTP 200 + SSE error body), the same fix pattern applies. Not in scope; D-04 explicitly excludes them.
- **Structured SSE error type** — A `#[derive(Deserialize)] struct SseErrorEnvelope { error: SseErrorBody }` would give compile-time confidence about the shape. Deferred in favour of the simpler `serde_json::Value`-based approach (more resilient to provider variations).
- **Emit the SSE error body as a usage_events `error_kind` row** — The fallback path currently calls `write_usage_failure(&provider_error)` which records the variant name. Richer SSE-origin forensics (actual error message) would require extending the `usage_events` schema. Follow-on.
- **Extend `AnthropicClient` streaming** — AnthropicClient has its own SSE loop and error handling. Audit and harden in a dedicated phase if needed.
</deferred>
