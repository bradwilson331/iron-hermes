# Cross-AI Plan Review — Phase 36.14

## Codex Review

## Summary

The plan is directionally sound and should close the PROV-07 SSE-body fallback gap for the OpenRouter-style `HTTP 200 + data: {"error": ...}` case. The minimal stream-event approach fits the existing architecture: detect provider errors inside `client.rs`, propagate them through `call_llm_streaming`, and let the existing fallback classifier/run loop do the rest. The biggest issue is execution ordering: adding `StreamEvent::ProviderError` in Task 1 will break the existing exhaustive match in `call_llm_streaming`, so the Task 1 build verification cannot pass until Task 2's match arm is also added.

## Strengths

- Keeps the blast radius small by only doing the second `serde_json::Value` parse after `ChatStreamChunk` deserialization fails.
- Reuses the existing fallback/retry path instead of modifying the `run()` fallback block.
- Correctly recognizes that the error string must include a parseable status like `(400 Bad Request)` for the current classifier to route fallback.
- `StreamEvent::ProviderError(String)` is a clean propagation mechanism for the current channel-based streaming design.
- Anthropic exclusion is reasonable if its observed failure mode is proper HTTP status handling.
- Preserving the debug log for non-error malformed chunks avoids hiding unrelated stream parsing issues.

## Concerns

- **HIGH: Task ordering/build verification is wrong.**
  `StreamEvent` is exhaustively matched in `agent_loop.rs`; adding a new enum variant before adding the `StreamEvent::ProviderError` arm will make `cargo build -p ironhermes-agent` fail. Task 1 and the `call_llm_streaming` match-arm change need to be one compile unit before build verification.

- **MEDIUM: Numeric code extraction may miss real provider shapes.**
  The plan says extract `val["error"]["code"]` or `val["code"]` as `Option<u16>`, but provider `code` fields may be strings, e.g. `"400"`, or provider-specific text, e.g. `"invalid_model"`. If OpenRouter or another provider returns a numeric string, the fallback gap remains.

- **MEDIUM: Raw error JSON in the propagated error may leak or bloat logs.**
  The fallback warning logs `{err}`. Existing HTTP body errors already have this risk, but this change extends it to SSE payloads. Provider error objects can contain metadata, request IDs, or echoed details. Consider truncating or extracting only `message`, `code`, and maybe `type`.

- **MEDIUM: Partial streaming output before ProviderError can cause mixed UI output.**
  If a provider emits content deltas and later emits an SSE error, `call_llm_streaming` will return `Err`, but the stream callback may already have printed partial primary-provider output before fallback starts. This is probably rare for invalid-model errors, but it is worth explicitly accepting or guarding.

- **LOW: Static-grep invariants are too weak.**
  Checking for `"StreamEvent::ProviderError"` in `agent_loop.rs` does not prove `call_llm_streaming` returns `Err`; the token could appear in a comment or unrelated code.

- **LOW: `(NNN Reason)` formatting is brittle but consistent with current architecture.**
  It depends on `extract_http_status` parsing exactly three digits followed by a space inside parentheses. This is acceptable as a minimal fix, but it should be treated as a compatibility bridge, not a long-term classifier API.

- **LOW: Unknown-code behavior is conservative but may preserve the original failure for some providers.**
  Missing/unknown code maps to `Unknown`, so no fallback. That is safe, but it means body-level errors without numeric codes still return to retry behavior rather than trying fallback.

## Suggestions

- Move the `call_llm_streaming` `StreamEvent::ProviderError(body) => return Err(anyhow::anyhow!(body))` arm into Task 1, before any build check.

- Make code extraction tolerant:
  ```rust
  fn extract_sse_error_code(val: &serde_json::Value) -> Option<u16> {
      let code = val.pointer("/error/code").or_else(|| val.get("code"))?;
      code.as_u64()
          .and_then(|n| u16::try_from(n).ok())
          .or_else(|| code.as_str()?.parse::<u16>().ok())
  }
  ```

- Prefer formatting from extracted fields instead of raw JSON where possible:
  `Streaming chat completion failed (400 Bad Request): <message>`

- Add at least one real stream-path test, not only classifier tests: mock an HTTP 200 SSE response containing `data: {"error":{"message":"bad model","code":400}}` and assert `chat_completion_stream` emits `StreamEvent::ProviderError`.

- Add a helper-level test for string code:
  `{"error":{"message":"bad model","code":"400"}}` should classify as fallback.

- Strengthen invariants to look for the behavior, not only tokens. For example, assert `agent_loop.rs` contains both `StreamEvent::ProviderError` and `return Err(anyhow::anyhow!`.

- Consider adding `500`, `502`, `503`, and `429` SSE tests because those are central to PROV-07 and exercise retry/fallback differences.

## Risk Assessment

**Overall risk: MEDIUM.** The design is small and well aligned with the current fallback system, so implementation risk is not high. The main risks are execution-order breakage, provider payload shape variance, and over-reliance on string formatting for classification. With tolerant code extraction plus one actual SSE stream test, the plan becomes low-risk and should achieve the intended fallback behavior.

## Consensus Summary

Only one reviewer (Codex) ran to completion this round, so the "consensus" section reflects a single perspective rather than cross-AI agreement. Highlights from that single reviewer:

### Agreed Strengths

- Minimal blast radius — second JSON parse only on the cold path (after `ChatStreamChunk` deserialization fails).
- Architecturally clean propagation via a new `StreamEvent::ProviderError(String)` variant; no changes to `run()` or the classifier.
- Correctly threads the `(NNN Reason)` status token through `extract_http_status` to reuse the existing fallback machinery.
- AnthropicClient scope exclusion (D-04) and debug-log preservation (D-05) are reasonable.

### Agreed Concerns

- **HIGH — Task ordering breaks the Task 1 build verify.** Adding `StreamEvent::ProviderError` in Task 1 will fail the exhaustive match in `agent_loop.rs::call_llm_streaming`. The plan currently acknowledges this in passing ("if the build fails, add a temporary `_ => {}` arm"), but should be restructured so Task 1 either also adds the match arm or includes a documented temporary catch-all to be removed in Task 2.
- **MEDIUM — Numeric code extraction is type-fragile.** OpenRouter/upstreams may emit `"code": "400"` (string) — current `.as_u64()` extraction misses those cases and the fallback gap stays open. Suggested fix: tolerant extractor that handles both `as_u64()` and `as_str()?.parse::<u16>()`.
- **MEDIUM — Raw JSON in `anyhow!` may bloat logs and leak metadata.** Consider formatting from extracted `message`/`code` fields rather than echoing the entire SSE chunk into `warn!`-level logs.
- **MEDIUM — Partial content deltas before the SSE error are not addressed.** If the provider streams a few content tokens and then emits the error envelope, the UI may have already printed primary-provider output before fallback fires. Worth at minimum a comment in the plan acknowledging the trade-off.
- **LOW — Static-grep invariants are too weak.** `StreamEvent::ProviderError` token could appear in a comment. Strengthen by asserting co-occurrence with `return Err(anyhow!` near the match arm.
- **LOW — `(NNN Reason)` string-bridge is a compatibility hack.** Acceptable here, but the long-term fix would be a structured classifier API.

### Divergent Views

None — only one reviewer completed. Rerun with `--gemini`/`--opencode`/`--codex --all` once additional CLIs are installed or available to surface divergent perspectives.

## Recommended Plan Edits (for `/gsd:plan-phase --reviews` consumption)

1. **Restructure task boundaries** so the new variant and its match arm land atomically:
   - Option A: combine Task 1 + Task 2 step 1 into a single "wire the variant + handler end-to-end" task; defer tests + invariants to Task 2.
   - Option B: keep two tasks but make Task 1's verify step `cargo check --no-default-features` + an explicit `_ => unreachable!("Task 2 adds the arm")` placeholder that Task 2 removes.
2. **Tolerant code extraction**: add the `extract_sse_error_code` helper covering numeric AND string `code` shapes; add a unit test for `"code": "400"`.
3. **Log hygiene**: format the propagated error string from extracted `message` + `code` fields rather than the raw JSON; cap raw-JSON inclusion at a length budget (e.g. 512 chars) for debug-only context.
4. **Add a real stream-path integration test**: mock an HTTP 200 SSE body with the error envelope and assert `chat_completion_stream` emits `StreamEvent::ProviderError(...)` with the expected `(400 Bad Request)` token.
5. **Strengthen `invariants_36_14.rs`**: assert `agent_loop.rs` contains BOTH `StreamEvent::ProviderError` AND `return Err(anyhow::anyhow!` (or equivalent) within a bounded window — protects against drive-by deletion of the Err return.
6. **Optional belt-and-suspenders tests**: add 429/500/502/503 SSE error fixtures to lock the retry vs. fallback semantics across the full PROV-07 surface.
7. **Document the partial-content-then-error case** in `<deferred>` or in plan notes — at minimum, explicit acknowledgement that the operator may see truncated primary-provider output before fallback engages.
