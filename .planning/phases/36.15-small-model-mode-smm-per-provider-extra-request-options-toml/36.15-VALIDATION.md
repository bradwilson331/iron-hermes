## Security Domain

> `security_enforcement` not explicitly disabled in `.planning/config.json` — section included per workflow §5.55.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | No | Extras are not credentials |
| V3 Session Management | No | Extras are per-provider config, not session state |
| V4 Access Control | No | Operator-only config; no user-controlled input path |
| V5 Input Validation | Yes (limited) | Typed structs provide implicit serde-level validation at deserialization time |
| V6 Cryptography | No | Extras contain no secrets |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Operator injects arbitrary HTTP headers via extras | Tampering | Not possible — extras only affect the JSON body; `reqwest` controls headers; `ChatRequest.extra` is serialized into the body via `#[serde(flatten)]` only |
| Extra fields conflict with reserved LLM API fields (e.g., `model`, `messages`) | Tampering | `ChatRequest` has explicit named fields; named fields win over flattened extras in serde serialization order. Add unit test asserting reserved-key collision behavior. |
| `provider.order` pointing to untrusted provider routes | Elevation of Privilege | Out of scope for 36.15 — operator controls their own config; treat as operator self-trust |
