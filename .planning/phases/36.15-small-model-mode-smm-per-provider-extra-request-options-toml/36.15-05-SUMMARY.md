## Invariant Test Results

### Test 4 — `extra_caller_wins_per_key_d09` (D-09 caller-wins)
**Result: PASS**

Caller passes `extra = {"num_ctx": 100}` directly to `chat_completion`. Wire body captures `num_ctx: 100`. Confirms the direct-boundary semantics of D-09: whatever arrives in the `extra` parameter is flattened verbatim into the ChatRequest body.

### Test 5 — `extra_stream_options_floor_preserved_when_config_silent` (D-09 stream floor)
**Result: PASS**

Called `chat_completion_stream` with `extra = None`. Wire body captured `stream_options.include_usage: true`. Confirms the `or_insert_with` floor at `client.rs:236` still fires when neither caller nor config supplies `stream_options`. Threat T-36.15-12 is mitigated — the floor is regression-protected.

### Test 6 — `extra_reserved_key_collision_named_field_wins` (T-36.15-09 audit)
**Result: PASS (but documents insecure behavior — see Threat Flags)**

RESEARCH §Security Domain assumed serde named fields would win over `#[serde(flatten)]` HashMap keys. The test reveals the OPPOSITE is true: when `extra` contains `"model" → "attacker-supplied-model"`, the wire body's top-level `model` is `"attacker-supplied-model"`, not the ChatRequest's intended model string.

The test is left in the file asserting the current insecure behavior so that:
1. The behavior cannot silently regress undetected.
2. When a future fix (reserved-key blocklist) is applied, this assertion flips and CI catches the fix.

T-36.15-09 is **NOT mitigated**. See Threat Flags below.

### Test 7 — `extra_model_switch_picks_per_model_override_d10` (D-10 model-switch)
**Result: PASS**

Pure synchronous unit test. Same `providers` HashMap, two sequential `resolve_extras` calls with different model names:
- `"llama3.1:8b"` → `num_ctx = 32768` (per-model override wins over provider default 8192)
- `"llama3.1:70b"` → `num_ctx = 4096` (different per-model override)

Confirms `resolve_extras` is stateless with respect to model identity: switching model means calling with a new model name on the next turn — no shared mutable resolver state needed.

**Setup approach:** Programmatic struct-literal construction. `serde_yaml` is not a dev-dependency in `ironhermes-agent`; struct literals are unambiguous and sidestep the D-01 serde_yaml untagged enum pitfall documented in `config_extras.rs`.

## Deviations from Plan

### Auto-discovered Security Finding (Rule 2 — security)

**1. [Rule 1 - Bug] T-36.15-09 ASSUMPTION FALSE: serde flatten defeats named fields**
- **Found during:** Task 1, Test 6 execution
- **Issue:** The plan's `<interfaces>` section stated: "Serde serializes named fields first; for a HashMap key collision via flatten, the named field's value wins." Test 6 proves this is wrong. The flattened HashMap key `"model"` overwrites the named `model` field on the wire.
- **Fix applied:** Test assertion updated to document the actual insecure behavior (asserts `"attacker-supplied-model"` wins). No production code changed — fix requires a reserved-key filter in the config_extras ingestion path or ChatRequest serialization layer.
- **Files modified:** `crates/ironhermes-agent/tests/extra_request_options.rs` (test comment updated)
- **Commit:** c737b1a4
