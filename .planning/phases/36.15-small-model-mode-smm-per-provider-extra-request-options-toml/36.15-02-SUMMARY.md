## ADR: D-01 Deviation — HashMap at Deserialization Boundary

**Decision made:** `ProviderConfig.extra_request_options` and `ProviderModelConfig.extra_request_options` use `HashMap<String, serde_json::Value>` instead of `Option<ProviderExtraOptions>`.

**Why the untagged enum failed (Pitfall 1 confirmed):**

The plan's primary approach (`#[serde(untagged)] enum ProviderExtraOptions`) was implemented and tested via the Wave 0 canary. The canary test `extras_canary_openrouter_provider_order_nested` FAILED immediately:

```
thread 'config::extras_canary::extras_canary_openrouter_provider_order_nested' panicked:
expected ProviderExtraOptions::OpenRouter variant for openrouter provider
```

Root cause: `serde_yaml` with `#[serde(untagged)]` tries variants in declaration order. Because every field in every variant is `Option<T>`, serde accepts an empty (all-None) Ollama struct as a match for any YAML mapping — including one with a `provider:` key that belongs to OpenRouter. The `provider:` key was silently discarded, and the value deserialized as a wrong-variant success (`Ollama` with all-None fields). This is exactly PATTERNS.md Pitfall 1.

**Chosen fallback:** Raw `HashMap<String, serde_json::Value>` — serde_yaml correctly deserializes any mapping into this type regardless of key names, including nested objects like `provider: { order: [...] }`.

**What is retained:** The typed structs (`OllamaExtraOptions`, `VllmExtraOptions`, `OpenRouterExtraOptions`, `ProviderRouting`, `ProviderExtraOptions`) are kept in `config_extras.rs` as documentation types for Plan 03 (`config_schema.rs` schema key generation). They are not used in the deserialization path.

**resolve_extras impact:** The function is simpler — no `serde_json::to_value` step. Both `extra_request_options` fields are already `HashMap<String, serde_json::Value>`, so the merge is a direct clone + insert loop.

#[serde(default, skip_serializing_if = "HashMap::is_empty")]

## Deviations from Plan

### D-01 Deviation — Untagged Enum Replaced by Raw HashMap

**1. [Rule 1 - Bug] Untagged ProviderExtraOptions enum fails for OpenRouter variant**
- **Found during:** Task 1/2 integration (Wave 0 canary test execution)
- **Issue:** `serde_yaml` with `#[serde(untagged)]` and all-Optional struct fields always matches the first variant, silently discarding keys that belong to later variants. OpenRouter's `provider:` key was absorbed by the all-None Ollama variant. This is PATTERNS.md Pitfall 1 confirmed at runtime.
- **Fix:** `extra_request_options` field uses `HashMap<String, serde_json::Value>` at the deserialization boundary. Typed structs retained as documentation types for Plan 03.
- **Files modified:** config_extras.rs (ProviderModelConfig field type, resolve_extras impl), config.rs (ProviderConfig field type, import, canary test bodies updated from enum matching to HashMap access)
- **Commits:** 53b12d1d, 5bce0b27

### Auto-fix: custom_providers migration block

**2. [Rule 3 - Blocking] Existing ProviderConfig struct initializer lacked new fields**
- **Found during:** First cargo build attempt

- **Fix:** Added `extra_request_options: HashMap::new()` and `models: HashMap::new()` to that initializer.
