## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Strongly-typed per-provider extras structs: `OllamaExtraOptions`, `OpenRouterExtraOptions { provider: ProviderRouting { order, ignore, ... } }`, `VllmExtraOptions`. Each struct lives next to/inside `ProviderConfig` in `crates/ironhermes-core/src/config.rs`. Adding a new tunable field requires a struct-field addition; changing a value is pure TOML.
- **D-02:** Extend `ProviderConfig` (config.rs:196) with `extra_request_options: Option<ProviderExtraOptions>` and `models: HashMap<String, ProviderModelConfig>` where `ProviderModelConfig` holds its own optional `extra_request_options`.
- **D-03:** Per-provider + per-model with per-key merge. Per-model keys win; missing per-model keys fall through to provider default.
- **D-04:** Serialization: typed structs serialize to `HashMap<String, serde_json::Value>` at the AgentRuntime layer, immediately before the call into `LlmClient`. Nested values (e.g., `provider: { order: [...] }`) survive via `serde_json::to_value`.
- **D-05:** In scope — OpenAI-compatible path only: `LlmClient::chat_completion(extra)` (client.rs:151) and `chat_completion_stream(extra)` (client.rs:215) via the two AgentRuntime call sites `call_llm` (agent_loop.rs:1757) and `call_llm_streaming` (agent_loop.rs:1790), which currently pass `None`.
- **D-06:** Out of scope (deferred) — `build_openrouter_chat_request_full` (any_client.rs:546) and native `AnthropicClient` (anthropic_client.rs:877 `_extra` currently ignored). Not modified in 36.15.
- **D-07:** Coverage: Ollama, vLLM, OpenRouter non-Claude routes, any other OpenAI-compat provider. OpenRouter Claude WITH `prompt_caching.enabled = true` is intentionally NOT covered.
- **D-08:** Static knob only — no dynamic retry / num_ctx doubling. Operator sets num_ctx; PROV-07 fallback chain handles the exceed_context_size_error if it still fires.
- **D-09:** Caller wins per-key (`caller » config`). Existing `stream_options.include_usage: true` floor at client.rs:236 is preserved. Shallow merge only.
- **D-10:** Per-call resolution in `AgentRuntime`. On every turn, resolve `(provider, current_model) → merged_extra` and pass into `call_llm` / `call_llm_streaming`. Mid-session `/model` switch picks up new per-model override on the very next turn.

- How `ProviderExtraOptions` is enum'd or trait-objected (untagged enum vs `Option<serde_json::Value>` + dispatch).
- Exact merge implementation (build caller map first, then `.entry().or_insert()` each config key, or inverse).
- How `AgentRuntime` reaches the resolved `ProviderConfig` (same `self.config` accessor it already holds).

### Deferred Ideas (OUT OF SCOPE)

- OpenRouter Claude cache path wiring (`build_openrouter_chat_request_full`).
- Native AnthropicClient wiring (`_extra`).
- Dynamic `num_ctx` retry on `exceed_context_size_error`.
- Deep merge of nested objects.

- Full SMM architecture port (governor, router, escalation, plan tracker, etc.) — that is Phase 36.16.

## Summary

Phase 36.15 adds a thin but precisely-placed configuration knob that makes IronHermes provider-portable without code changes. The target data path is already complete at both ends: `ChatRequest.extra` (ironhermes-core/src/types.rs:149) already has `#[serde(flatten)]` and accepts arbitrary JSON fields, and `LlmClient::chat_completion` / `chat_completion_stream` already accept `extra: Option<HashMap<String, serde_json::Value>>` at their signatures (client.rs:151, :215). The work is entirely in the middle: (1) defining the typed config structs that sit in TOML, (2) serializing them to the `HashMap<String, Value>` shape at the AgentRuntime layer, and (3) threading that map through the two `call_llm` / `call_llm_streaming` call sites in `agent_loop.rs` that currently pass `None`.

The most important landmine confirmed by codebase inspection is **the `is_openrouter_claude` branch** in `chat_completion_stream`. When `prompt_caching.enabled = true` AND the model is OpenRouter Claude, the stream takes the `build_openrouter_chat_request_full` path, which already has its own `extra` HashMap parameter but is NOT wired by this phase (D-06). The OpenAI-compatible `else` branch at client.rs:279 — which covers Ollama, vLLM, non-Claude OpenRouter, and all custom providers — IS the target. D-07 is confirmed correct: non-Claude OpenRouter routes DO go through the `else` branch; only OpenRouter Claude with prompt_caching on goes through the full-builder path.

The `AgentRuntime` owns both `self.config: Arc<Config>` and `self.resolver: Arc<ProviderResolver>`. The resolver's `main_provider()` returns the active provider name string, and `resolve_for_main()` gives the `ResolvedEndpoint` (which contains `default_model`). The **D-10 invariant** is confirmed safe: the `/model` slash command does NOT rebuild the AnyClient mid-session — it calls `resolver.validate_model(target)` and returns a confirmation string, leaving actual client state unchanged. The `call_llm` / `call_llm_streaming` methods pass `None` for the model parameter to the client, which then falls through to `self.default_model` on the inner `LlmClient`. This means the per-model key for extras resolution at the `AgentRuntime` layer should use `self.resolver.resolve_for_main().default_model` (the same value the client uses as the wire model) — no special mid-session model-swap logic is required.

**Primary recommendation:** Implement `ProviderExtraOptions` as an untagged serde enum with provider-specific variant structs. Use `serde_json::to_value` → `as_object()` unwrap to convert to the HashMap at the resolution site. Thread a new `extras: HashMap<String, serde_json::Value>` parameter into `call_llm` / `call_llm_streaming` in `agent_loop.rs`; AgentRuntime resolves and passes it each turn.

### Pattern 1: ProviderExtraOptions Enum (Researcher Recommendation)

**What:** Untagged enum per-provider; serde deserializes based on field presence.
**When to use:** When providers have non-overlapping field names (Ollama `num_ctx` vs OpenRouter `provider`).

```rust
// Source: [VERIFIED: config.rs serde patterns in codebase — same pattern as CacheTtl enum]

/// Per-provider typed extras. Deserialized from the `extra_request_options:` TOML block.
/// Serialized to `HashMap<String, serde_json::Value>` at the AgentRuntime layer via
/// `serde_json::to_value(opts).as_object().cloned()`.
///
/// Untagged enum: serde picks the variant by trying each in order.
/// Field names must be non-overlapping to avoid ambiguity (they are).
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(untagged)]
pub enum ProviderExtraOptions {
    Ollama(OllamaExtraOptions),
    OpenRouter(OpenRouterExtraOptions),
    Vllm(VllmExtraOptions),
}

#[derive(Debug, Clone, Default, Serialize, Deserialize)]
#[serde(default)]
pub struct OllamaExtraOptions {
    #[serde(skip_serializing_if = "Option::is_none")]
    pub num_ctx: Option<u32>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub num_predict: Option<i32>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub top_k: Option<u32>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub top_p: Option<f64>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub num_batch: Option<u32>,
}

#[derive(Debug, Clone, Default, Serialize, Deserialize)]
#[serde(default)]
pub struct VllmExtraOptions {
    #[serde(skip_serializing_if = "Option::is_none")]
    pub top_k: Option<i32>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub top_p: Option<f64>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub repetition_penalty: Option<f64>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub min_p: Option<f64>,
}

#[derive(Debug, Clone, Default, Serialize, Deserialize)]
#[serde(default)]
pub struct OpenRouterExtraOptions {
    #[serde(skip_serializing_if = "Option::is_none")]
    pub provider: Option<ProviderRouting>,
}

#[derive(Debug, Clone, Default, Serialize, Deserialize)]
#[serde(default)]
pub struct ProviderRouting {
    #[serde(skip_serializing_if = "Option::is_none")]
    pub order: Option<Vec<String>>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub ignore: Option<Vec<String>>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub quantizations: Option<Vec<String>>,
}
```

**TOML untagged enum caution:** `serde_json` and `serde` untagged enum deserialization with TOML (via `serde_yaml` / `toml` crate) can be brittle when all fields are optional. **The project uses `serde_yaml` for `config.yaml`** (not TOML for the main config — the name `config.yaml` is the canonical config file). The TOML syntax in the CONTEXT.md is illustrative of the *field shape*, not the actual serialization format. Per codebase inspection, `Config` is deserialized from YAML via `serde_yaml`. The TOML `[table.key]` syntax maps to YAML block structures. The untagged enum deserialization in `serde_yaml` may succeed if field sets are non-overlapping, but **the safer alternative** is a single `HashMap<String, serde_json::Value>` on `ProviderConfig` with typed helper functions — see Pattern 2.

### Pattern 2: Alternative — `serde_json::Value` with typed accessors (Researcher Recommendation)

**What:** Store extras as `Option<serde_json::Value>` (a raw JSON map) in the config struct, with a typed conversion helper that validates known fields at resolver-build time.
**When to use:** When the config is YAML-deserialized (as IronHermes uses) and you need nested table support without untagged enum deserialization ambiguity.

### Pattern 4: Extras Resolution Helper (D-10)

```rust
// Source: [ASSUMED — based on existing config accessor patterns in agent_runtime.rs]

/// Resolve the merged extras HashMap for a given (provider_name, model_name) pair.
/// Per-model keys win; provider-level keys fill gaps.
/// Returns an empty HashMap if no extras are configured.
pub fn resolve_extras(
    config: &Config,
    provider_name: &str,
    model_name: &str,
) -> HashMap<String, serde_json::Value> {
    let provider_cfg = config.providers.get(provider_name);

    // Get provider-level extras as a HashMap<String, Value>
    let provider_extras: HashMap<String, serde_json::Value> = provider_cfg
        .and_then(|p| p.extra_request_options.as_ref())
        .and_then(|e| serde_json::to_value(e).ok())
        .and_then(|v| v.as_object().cloned())
        .map(|m| m.into_iter().collect())
        .unwrap_or_default();

    // Get per-model extras (per-model wins)
    let model_extras: HashMap<String, serde_json::Value> = provider_cfg
        .and_then(|p| p.models.get(model_name))
        .and_then(|m| m.extra_request_options.as_ref())
        .and_then(|e| serde_json::to_value(e).ok())
        .and_then(|v| v.as_object().cloned())
        .map(|m| m.into_iter().collect())
        .unwrap_or_default();

    // Merge: start with provider extras, override with model extras (D-03)
    let mut merged = provider_extras;
    for (k, v) in model_extras {
        merged.insert(k, v);
    }
    merged
}
```

This function lives in `ironhermes-core/src/config.rs` or a new `config_extras.rs` module so it can be unit-tested without agent dependencies.

### Pattern 8: TOML/YAML quoted keys for model names with dots

The CONTEXT.md uses TOML syntax for illustration but the actual config is YAML. In YAML, a key with a dot requires quoting:

```yaml
# config.yaml — correct YAML for per-model extras
providers:
  ollama:
    extra_request_options:
      num_ctx: 8192
    models:
      "llama3.1:8b":        # YAML quoted key — colon in model name
        extra_request_options:
          num_ctx: 32768
```

The colon in `llama3.1:8b` is the character that requires quoting in YAML (colons introduce mappings). The dot is fine unquoted in YAML keys — only TOML requires quoting for dots. `serde_yaml` deserializes quoted keys into `HashMap<String, ProviderModelConfig>` correctly; no special handling needed. ### Anti-Patterns to Avoid

- **Mutating `ChatRequest` extras before the `or_insert_with` floor:** The floor in `chat_completion_stream` must remain the last writer for `stream_options`. Config extras are set before the floor fires (they arrive as the `extra` parameter), so the floor can still override a config-set `stream_options.include_usage: false`. This is documented behavior per D-09 — do not change the floor position.
- **Putting `resolve_extras` inside `LlmClient`:** The config is not accessible from `LlmClient`. Resolution must happen at `AgentRuntime` or `AgentLoop` level where `self.config` is in scope.
- **Rebuilding the resolver per call:** `resolve_for_main()` returns `&ResolvedEndpoint` from a pre-built HashMap. It is O(1) and safe to call per-turn without caching.
- **Deep-merging nested objects:** D-09 explicitly defers deep merge. The OpenRouter `provider.order` value is a `serde_json::Value` (an array); the caller's `provider.order` fully replaces the config's `provider.order` if both are set (shallow key replace). This is correct for the in-scope use cases.

## Common Pitfalls

### Pitfall 1: Untagged enum deserialization ambiguity in serde_yaml

**What goes wrong:** `#[serde(untagged)]` enums require serde to try each variant in declaration order. If all fields in all structs are `Option<...>` (which they are, since all extras fields have `skip_serializing_if = "Option::is_none"`), serde may match the wrong variant or always match the first.

**Why it happens:** With `#[serde(untagged)]`, serde deserializes by trying each variant; the first variant whose fields parse without error wins. When all fields are optional, every variant matches an empty YAML block, and `OllamaExtraOptions {}` may match before `OpenRouterExtraOptions {}` even when `provider:` is present.

**How to avoid:** Two options:
1. Use `#[serde(deny_unknown_fields)]` on each struct so serde fails fast on wrong variant — but this is stricter than desired.
2. **Preferred:** Use a flat approach — store `extra_request_options` as `Option<HashMap<String, serde_json::Value>>` on `ProviderConfig` directly (deviating from D-01 typed structs) OR use provider-type dispatch: resolve extras by looking at the provider's `api_mode` or by using per-provider sub-structs in separate fields (`ollama_extra`, `openrouter_extra`). **The planner should document which approach is chosen and why.**

**Alternative shape that avoids the issue** (researcher recommendation):
```yaml
providers:
  ollama:
    extra_request_options:
      num_ctx: 8192        # arbitrary YAML map — deserialized as HashMap<String, Value>
```

```rust
// In ProviderConfig:
pub extra_request_options: Option<HashMap<String, serde_json::Value>>,
pub models: HashMap<String, ProviderModelConfig>,
```

This approach satisfies D-04 (serialization at the AgentRuntime layer) and D-03 (per-key merge), while avoiding untagged enum ambiguity. D-01 (typed structs) would be partially softened: types are validated at test time rather than at deserialization time. The acceptance criteria (Ollama `num_ctx`, vLLM `top_k`, OpenRouter `provider.order` observable on wire) are still met. **Flag this for planner decision.**

**Warning signs:** Compile warning about unreachable match arms; test that sets `num_ctx` gets `provider.order` struct instead.

### Pitfall 2: `provider_name` in AgentLoop is not the config map key

**What goes wrong:** `AgentLoop.provider_name` (set via `with_provider_name`) is used for usage tracking and rate-limit key derivation. It may differ from the `config.providers` HashMap key in edge cases (e.g., if a provider is configured under a custom name but `main_provider()` returns a canonical name).

**Why it happens:** `self.resolver.main_provider()` returns the canonical provider name from the resolver's internal main_provider field, which is set from `config.model.provider`. This IS the key used in `config.providers` — they are the same value. [VERIFIED: provider.rs build() logic confirmed they are identical]

**How to avoid:** Always use `self.resolver.main_provider()` to look up `self.config.providers`. Do not use `self.client.model()` or `AgentLoop.provider_name`.

**Warning signs:** Extras always empty despite config being set; wrong provider's extras applied.

### Pitfall 3: YAML model key with colon not quoted

**What goes wrong:** A model named `llama3.1:8b` in YAML without quotes causes a parse error: YAML interprets the colon as a key-value separator.

**Why it happens:** YAML colons are special characters in key position. `llama3.1:8b` without quotes is a parse error in strict YAML.

**How to avoid:** Document in the operator guide that model names containing `:` must be quoted in YAML: `"llama3.1:8b"`. The serde_yaml deserializer accepts quoted YAML string keys as HashMap keys without special configuration. Test this explicitly with a model name containing a colon.

**Warning signs:** serde_yaml deserialization error on config load: `found unexpected ':' at line N`.

### Pitfall 4: config_schema.rs test `schema_contains_all_cache_breaking_fields` fails if new keys are wrongly marked cache-breaking

**What goes wrong:** The test at config_schema.rs:290 asserts a hard-coded list of expected cache-breaking keys. Adding a new key with `cache_breaking: true` does NOT break the test — but if a future test adds `extra_request_options.*` to the expected list and the field is absent, it will fail.

**Why it happens:** The schema() function is a static Vec; tests enumerate expectations.

**How to avoid:** `extra_request_options.*` fields should be `cache_breaking: false` and `secret: false`. Changing `num_ctx` does not change the prompt structure; it only affects Ollama's processing. [ASSUMED — no official IronHermes guideline, but consistent with other non-secret operational config]

### Pitfall 5: OpenRouter `provider.order` nested structure via serde_json::to_value

**What goes wrong:** If `OpenRouterExtraOptions.provider` is `Option<ProviderRouting>` and `ProviderRouting.order` is `Option<Vec<String>>`, then `serde_json::to_value(&opts)` produces:
```json
{"provider": {"order": ["anthropic", "openai"]}}
```
The outer key is `"provider"` and the value is a nested object. When this is merged into `ChatRequest.extra` via `#[serde(flatten)]`, the wire body gets `"provider": {"order": [...]}` — which is exactly what OpenRouter expects. This works correctly. The only risk is if the flatten interacts with an existing `provider` field on `ChatRequest` — but `ChatRequest` has no `provider` field; the flatten is onto `extra: HashMap<String, Value>`.

**How to avoid:** No action required. Document this as confirmed correct in the plan.

**Warning signs:** Would only fail if `ChatRequest` gained a `provider` field (it won't in this phase).

### Pitfall 6: The `call_llm` / `call_llm_streaming` signature change cascades

**What goes wrong:** `call_llm` and `call_llm_streaming` are private methods on `AgentLoop`. They are called from multiple sites within `agent_loop.rs` (lines 1563, 1584, 1587 in the main `run()` loop, and potentially from the fallback block). A signature change requires updating all call sites.

**Why it happens:** Rust requires all call sites to match the new signature at compile time.

**How to avoid:** Count all call sites before changing the signature. From grep output: `call_llm_streaming` is called at 1563, 1584; `call_llm` at 1587 (and also in the streaming fallback at 1565). The extras parameter could alternatively be stored on `AgentLoop` as a field set by `AgentRuntime` before calling `run()`, which avoids signature changes to the private methods. **Planner should choose: (a) thread as parameter, (b) store as field on AgentLoop.** Option (b) avoids cascading call-site changes.

## Open Questions

1. **Untagged enum vs raw HashMap for `ProviderExtraOptions` (D-01 vs pragmatism)**
   - What we know: D-01 requires strongly-typed structs; untagged enum deserialization with all-optional fields is fragile in serde.
   - What's unclear: Whether `serde_yaml` untagged enum deserialization works reliably with all-optional-field variants, or whether `deny_unknown_fields` causes operability issues.
   - Recommendation: Write the Wave 0 config roundtrip test FIRST (before any other tasks) to validate the chosen deserialization approach. If the untagged enum fails, fall back to `HashMap<String, serde_json::Value>` on `ProviderConfig` and note the D-01 deviation in the plan.

2. **AgentLoop extras delivery: parameter threading vs field on AgentLoop**
   - What we know: `call_llm` / `call_llm_streaming` are private; there are 4 call sites in `run()`; AgentLoop is already built with many builder fields.
   - What's unclear: Which approach the planner prefers for minimizing diff scope.
   - Recommendation: Store extras as a field on `AgentLoop` set by `AgentRuntime` before calling `run()` (via a builder method `with_resolved_extras`). This minimizes call-site changes inside `run()`. The field is `Option<HashMap<String, serde_json::Value>>`; `call_llm` reads `self.resolved_extras.clone()` internally.

3. **config_schema.rs — enumerate all extras keys vs wildcard**
   - What we know: The schema is a static Vec; `hermes config set` uses exact key matching.
   - What's unclear: Whether a wildcard pattern (e.g., `providers.*.extra_request_options.*`) would be cleaner, or whether static entries for each known key are required.
   - Recommendation: Static entries for the canonical acceptance set (Ollama num_ctx/num_predict/top_k, vLLM top_k/top_p, OpenRouter provider.order). Unknown keys set directly in YAML still work at runtime — schema entries only affect `hermes config set` validation and `hermes config show` output.
