# Phase 36.3.7: Kanban / multi-agent board — kanban_* tools - Context

**Gathered:** 2026-05-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Deliver IronHermes Kanban v1 kernel — a durable, profile-aware work-queue that coordinates heterogeneous IronHermes profiles across research, scheduled-ops, digital-twin, and engineering workloads without in-process subagent swarms.

The scope is the **kernel**: the `~/.ironhermes/kanban.db` SQLite board (4 + 1 tables: `tasks`, `task_links`, `task_comments`, `task_events`, `task_runs`), a gateway-embedded dispatcher with atomic-claim + live-PID detection + circuit-breaker, a 6-tool LLM surface (`kanban_show`/`list`/`complete`/`block`/`comment`/`create`) gated by `HERMES_KANBAN_TASK` env, the `KANBAN_GUIDANCE` system-prompt block injected into worker prompts, two bundled skills (`kanban-worker` v2.0.0 + `kanban-orchestrator` v3.0.0) synced into every profile, the `/kanban` slash command + full CLI verb surface, and all three workspace kinds (`scratch`/`dir:<abs>`/`worktree`) — all enforcing the lane contract from `docs/kanban/worker-lanes.md`.

Out of scope: multi-board, the triage/auto-decompose/specify flow, the dashboard plugin, gateway notify-subscribe + notifier, `kanban swarm` topology helper, three deferred LLM tools (`heartbeat`/`link`/`unblock`), portable profile artifacts (`profile export`/`install`), starter-roster bundle, external CLI worker lanes (Codex/Claude Code/OpenCode), @mention delegation parser.

</domain>

<decisions>
## Implementation Decisions

### Scope cut
- **D-01:** Kernel v1 only. Reference (`docs/kanban/reference.md`) lists ~20 user-facing surfaces; v1 ships the subset that proves the worker protocol end-to-end and lets a human drive the board via CLI + `/kanban`. Dashboard plugin, triage/decompose/specify, multi-board, swarm helper, gateway notifier, and 3 of 9 LLM tools all defer to follow-up phases (see `<deferred>` below).
- **D-02:** 6-of-9 LLM tools in v1 — `kanban_show`, `kanban_list`, `kanban_complete`, `kanban_block`, `kanban_comment`, `kanban_create`. Deferred: `kanban_heartbeat` (advisory; orchestrator-skill protocol doesn't mandate), `kanban_link` (orchestrator uses `parents=[...]` on `kanban_create` instead), `kanban_unblock` (operator verb, CLI-only is sufficient).

### Data model
- **D-03:** Separate `~/.ironhermes/kanban.db` SQLite file. Distinct WAL from `ironhermes-state` (which owns sessions+FTS5). PDF §3.1 verbatim; clean isolation, no cross-locking. Multi-board layout `~/.ironhermes/kanban/boards/<slug>/kanban.db` is reserved but not exercised in v1 — board resolution returns `default` for all calls.
- **D-04:** New crate `ironhermes-kanban` owns the schema, CAS helpers, dispatcher, and worker-side DB API. Mirrors `ironhermes-cron`/`ironhermes-state` separation (one crate per durable subsystem). Consumed by `ironhermes-cli`, `ironhermes-gateway`, `iron_hermes_ui`.
- **D-05:** Five tables — `tasks`, `task_links`, `task_comments`, `task_events`, `task_runs` (reference adds `task_runs` vs PDF's 4-table schema). `task.current_run_id` points at the active run or NULL; `task_runs` rows hold per-attempt `outcome`, `summary`, `metadata`, `error`, `log_path`, `started_at`, `ended_at`. Synthetic zero-duration runs cover never-claimed completions so attempt history stays complete.
- **D-06:** Status enum is the reference's 7-state machine: `triage | todo | ready | running | blocked | done | archived`. v1 honors `triage` as a parking column (no auto-decompose); transitions out of `triage` are operator-only (deferred features add the LLM decomposer).
- **D-07:** Task columns include `idempotency_key` (nullable, unique-when-set), `scheduled_at` (nullable timestamp; dispatcher skips ready tasks whose scheduled_at is in the future), `max_runtime_seconds`, `max_retries`, `tenant` (nullable), `priority` (default 0), `skills` (JSON array; dispatcher emits `--skills <n>` for each on spawn), plus v2-reserve nullable `workflow_template_id` and `current_step_key` (kernel ignores; clients may write).
- **D-08:** `claim_lock` format is `<host>:<pid>:<uuid>` (lanes-doc contract, richer than PDF's `<host>:<pid>` — UUID disambiguates rapid reclaim-then-reclaim races).

### Dispatcher
- **D-09:** Gateway-embedded by default (`kanban.dispatch_in_gateway: true`). Lives as a tokio task on `ironhermes-gateway`'s runtime; ticks every 60s (`kanban.dispatch_interval_seconds`); `HERMES_KANBAN_DISPATCH_IN_GATEWAY=0` env override for debugging. Standalone `ironhermes kanban daemon --force` kept as deprecated single-release escape hatch.
- **D-10:** Dispatcher operations per tick (the "dumb" loop): (1) `detect_crashed_workers` — `kill -0` on host-local PIDs from `task_runs.claim_pid`, reap dead → `crashed`; (2) live-PID claim extension — alive PID at TTL expiry emits `claim_extended` event instead of reclaim (covers slow LLM calls > 15 min); (3) stale-claim reclaim — claim TTL expired AND PID dead → reset to `ready`, emit `reclaimed`; (4) max-runtime enforcement — wall-clock exceeds `max_runtime_seconds` → SIGTERM, 5s grace, SIGKILL, emit `timed_out`; (5) ready promotion — `todo` tasks with all parents `done` → `ready`, emit `promoted`; (6) atomic claim — BEGIN IMMEDIATE + CAS UPDATE WHERE status='ready' AND claim_lock IS NULL AND (scheduled_at IS NULL OR scheduled_at <= now), respecting `max_in_progress`; (7) respawn-guard check — refuse respawn for `blocker_auth` (last failure was 429/quota/auth), `recent_success` (completed run in last hour), `active_pr` (GitHub PR URL in recent comment); emit `respawn_guarded`; (8) spawn worker subprocess.
- **D-11:** Concurrency cap via `kanban.max_in_progress` config, default 8. When `SELECT COUNT(*) FROM tasks WHERE status='running'` ≥ cap, dispatcher stops claiming this tick. Invalid/below-1 values log warn + behave as unlimited.
- **D-12:** Failure circuit breaker via `kanban.failure_limit` (default 2). After N consecutive non-successful attempts (spawn_failed / crashed / timed_out / protocol_violation), emit `gave_up` event with `{failures, effective_limit, limit_source, error}` and auto-block the task with the last error as reason. Per-task `max_retries` overrides global; both fall through to built-in default.
- **D-13:** `DEFAULT_CLAIM_TTL_SECONDS = 900` (15 min, matches PDF + lanes doc).
- **D-14:** Stranded-task diagnostic — `ready` tasks whose assignee never produces a claim within `kanban.stranded_threshold_seconds` (default 1800 = 30 min) surface as `stranded_in_ready` in `ironhermes kanban diagnostics`; severity escalates to `error` at 2x, `critical` at 6x. Identity-agnostic — no per-board allowlist.

### Worker spawn
- **D-15:** Spawn command is `ironhermes --profile <P> chat -q "work kanban task <id>"`. New flag: add `-q/--query <PROMPT>` to the existing `Chat` subcommand (parity with upstream `hermes -p <P> chat -q`). The top-level `-e/--execute` flag is preserved and remains the recommended path for scripted single-shot calls; `chat -q` is the worker-spawn shape.
- **D-16:** Workers are full OS processes (lanes-doc §"The hierarchy" + NanoClaw lesson from PDF §3.3). No in-process AgentLoop reuse. Dispatcher spawn writes the 9-env-var contract before exec; worker reads task_id from `HERMES_KANBAN_TASK` and queries `kanban.db` directly via the 6 LLM tools, never shells `ironhermes kanban …`.
- **D-17:** 9 env vars set on spawn (lanes-doc contract verbatim): `HERMES_KANBAN_TASK`, `HERMES_KANBAN_DB`, `HERMES_KANBAN_BOARD` (always `default` in v1), `HERMES_KANBAN_WORKSPACES_ROOT`, `HERMES_KANBAN_WORKSPACE`, `HERMES_KANBAN_RUN_ID`, `HERMES_KANBAN_CLAIM_LOCK`, `HERMES_PROFILE`, `HERMES_TENANT` (only when task has tenant).
- **D-18:** Env scrub policy reuses `build_safe_env()` allowlist from `ironhermes-exec` (Phase 22 pattern): PATH, HOME, USER, LANG, TERM, RUST_LOG, IRONHERMES_HOME, plus the 9 kanban env vars above. Forward-compatible with new vars per [[project_arch_embedded_agent]] precedent.
- **D-19:** Per-task stdout/stderr captured to `~/.ironhermes/logs/kanban/<task_id>.{stdout,stderr}.log` (lanes-doc `<board-root>/logs/<task_id>.log` adapted to IronHermes home layout). Log path written to `task_runs.log_path` for `kanban_show` + `hermes kanban log <id>` retrieval. GC'd on `archive` and by `kanban gc --log-retention-days N`.

### LLM tool surface
- **D-20:** Tool registration follows IronHermes `Tool` trait pattern in `ironhermes-tools`. Each of the 6 tools is its own struct (not a verb-dispatcher on a single `kanban_tool` — granular surface per reference). Tools gate visibility on `HERMES_KANBAN_TASK` env presence (worker mode) or explicit toolset enable (orchestrator mode). Zero schema footprint on a chat session that never touches kanban.
- **D-21:** `kanban_show` defaults `task_id` to `$HERMES_KANBAN_TASK` env when called with no args. Returns pre-formatted `worker_context` envelope: title + body + parent handoffs (most recent completed run's summary+metadata per parent) + prior attempts on self (per-run outcome/summary/error) + full chronological comment thread + workspace path + tenant.
- **D-22:** `kanban_complete(summary, metadata, result?, expected_run_id?, created_cards?)` is the protocol terminator. Server-side gates: (a) `expected_run_id` mismatch → reject (worker's run was superseded); (b) `created_cards=[...]` validation — assert each id exists AND `tasks.created_by = current worker's HERMES_PROFILE` — phantom ids reject with structured error, emit permanent `completion_rejected` event; (c) free-form prose scan for `t_<hex>` references in summary that don't resolve → advisory `hallucinated_ref` event (non-blocking).
- **D-23:** `kanban_block(reason, expected_run_id?)` — same `expected_run_id` gate. `reason` strings starting with `review-required:` (lanes-doc convention) are doc-flagged in v1; dashboard treatment lands when the dashboard plugin ships in a follow-up.
- **D-24:** `kanban_create(title, assignee, parents?, tenant?, body?, workspace?, skills?, priority?, idempotency_key?, scheduled_at?, max_runtime?, max_retries?)` — returns `{task_id, status}`. `parents=[...]` is the canonical gating path (orchestrator skill explicitly avoids after-the-fact linking). `idempotency_key` short-circuits: if key already exists, return existing `task_id` instead of duplicating.
- **D-25:** `kanban_list(assignee?, status?, tenant?, archived?, limit?)` and `kanban_comment(task_id?, body)` — straightforward queries; `kanban_comment` defaults `task_id` to env when worker-scope.

### Worker protocol
- **D-26:** `KANBAN_GUIDANCE` system-prompt block injected into worker prompts via the existing 10-layer prompt builder (Phase 15). New layer-aware hook: when `HERMES_KANBAN_TASK` env is set at process start, the prompt assembler prepends the canonical KANBAN_GUIDANCE block (6-step lifecycle: orient → work → heartbeat → block/complete). Block text is bundled as a static asset, sourced from upstream `agent/prompt_builder.py` KANBAN_GUIDANCE constant.
- **D-27:** Protocol-violation detection — worker subprocess exits with status 0 while task is still `running` → emit `protocol_violation` event AND auto-block immediately (not retried). Distinct from `crashed` (non-zero exit / signal). Matches lanes doc §"A lifecycle terminator".
- **D-28:** Worker is auto-passed `--skills kanban-worker` on spawn (reference §"The worker skill") even if profile config doesn't include it. Profile-pinned task-level extra skills (`task.skills` JSON array) emit additional `--skills <n>` flags on the same exec; dispatcher concatenates.

### Bundled skills
- **D-29:** Ship `skills/kanban-worker/SKILL.md` (v2.0.0) and `skills/kanban-orchestrator/SKILL.md` (v3.0.0) as bundled assets in the IronHermes repo. Both are byte-for-byte translations of the upstream Hermes SKILL.md files saved at `.planning/phases/36.3.7-.../kanban-{worker,orchestrator}-skill-upstream.md`, adjusted only to swap `hermes -p` → `ironhermes --profile` CLI references and `~/.hermes/` → `~/.ironhermes/` path references.
- **D-30:** Skills sync into each profile dir during `ensure_home_dirs()` first-run scaffolding AND during `ironhermes skills update` (new behavior — current update flow is hub-only). `ironhermes -p <P> skills reset kanban-worker --restore` is the user-facing recovery path. Profile-local edits are preserved on subsequent syncs (no force-overwrite of user mods).

### Workspaces
- **D-31:** Three workspace kinds in v1 (reference §"Core concepts" + lanes-doc):
  - `scratch` (default): fresh tmp dir at `~/.ironhermes/kanban/workspaces/<task_id>/`. Wiped on `kanban_complete`/`hermes kanban complete`. First scratch workspace per install emits `tip_scratch_workspace` event for discoverability.
  - `dir:<absolute path>`: existing shared path. **Relative paths rejected at dispatch** (`dir:../foo` is a confused-deputy escape vector). Preserved on completion. Trusted-local-user threat model (kanban is single-host by design).
  - `worktree` / `worktree:<path>`: git worktree at `.worktrees/<task_id>/` or pinned path. Worker creates via `git worktree add` using `HERMES_KANBAN_BRANCH` env (set when task has `--branch <name>`). Preserved on completion.
- **D-32:** `kanban.default_workdir` config knob — board-level default applied when neither `--workspace` nor task itself overrides. Per-task `workspace:` still wins.

### CLI surface
- **D-33:** Full CLI verb surface (reference §"CLI command reference"): `init`, `create`, `list`, `show`, `assign`, `link`, `unlink`, `claim`, `comment`, `complete`, `block`, `unblock`, `archive`, `tail`, `watch`, `runs`, `assignees`, `dispatch` (one-shot pass for `/kanban dispatch` and ops), `stats`, `log`, `context`, `gc`. Plus the four operator-recovery verbs explicitly locked: `reclaim <id>`, `reassign <id> <new-profile> --reclaim`, `diagnostics` (surfaces `stranded_in_ready`), `daemon --force` (deprecated standalone dispatcher escape hatch).
- **D-34:** Bulk verbs accept multiple ids: `complete`, `archive`, `unblock`, `block` (per-id partial failures reported, batch continues). Bulk close with `--summary/--metadata` is **refused** — handoff is per-run, copy-pasting the same summary across N tasks is almost always wrong (reference §"Bulk close caveat").
- **D-35:** New `Kanban { #[command(subcommand)] command: kanban::KanbanCommands }` subcommand on the top-level `Commands` enum in `ironhermes-cli/src/main.rs`. Subcommand registration matches `Cron`/`Skills`/`Memory` pattern. Argparse tree shared with `/kanban` slash command via existing `CommandRouter` (Phase 21.1) — adding the kanban command propagates to TG/Discord/Slack automatically.

### Gateway / slash command
- **D-36:** `/kanban <verb>` slash command **bypasses the running-agent guard** for all subcommands (reference §"Mid-run usage"). Rationale: kanban state lives in DB, not in the running agent's context — reads and writes are safe mid-turn. Existing guard whitelist in `ironhermes-gateway` extended; the same policy applies to `iron_hermes_ui` server's command dispatch.
- **D-37:** `notification_sources` config key (`~/.ironhermes/config.yaml`) — controls cross-profile gateway subscription allowance. Values: `['*']` (accept all), explicit list (e.g. `['default', 'zilor-ppt']`), or omitted (profile isolation per Phase 24 D-22). Default matches Phase 24 stance — profile isolation. No subscriber tables in v1 (notifier is deferred), but the config key is reserved so the deferred phase doesn't need a config migration.

### Multi-tenant
- **D-38:** `task.tenant` nullable column; `--tenant <name>` flag on `create`; `--tenant` filter on `list`. Worker receives `HERMES_TENANT` env. Per-tenant workspace path convention `~/tenants/<name>/...` is operator-managed (no code path generation in v1). Tenant value propagates from parent task to children when orchestrator passes `tenant=os.environ.get("HERMES_TENANT")` per the orchestrator skill (no automatic kernel propagation — explicit-is-better-than-implicit matches reference §"What is deliberately not here").
- **D-39:** Cross-tenant `task_links` rejected at link time (per reference §"What is deliberately not here"). Use a tenant-less parent if cross-tenant fanout is needed.

### Concurrency correctness
- **D-40:** Atomic claim CAS pattern (PDF §12.1):
  ```sql
  BEGIN IMMEDIATE;
  UPDATE tasks
    SET status='running', claim_lock=?, claim_expires=?, started_at=?, current_run_id=?
    WHERE id=? AND status='ready' AND claim_lock IS NULL
      AND (scheduled_at IS NULL OR scheduled_at <= ?);
  -- examine changes(): 1 = won, 0 = lost the race
  COMMIT;
  ```
  Dispatcher inserts the `task_runs` row in the same transaction; pointer + run row are coherent by construction.
- **D-41:** Worker writes (comment, complete, block) are gated by `WHERE claim_lock=?` — mismatched lock causes the write to no-op and emit a `claim_expired` advisory event. Composes with `expected_run_id` gate on terminating tools. Reclaim of a stale worker is therefore safe; the displaced worker's late writes fall on the floor cleanly.

- Schema migration mechanism (reuse `ironhermes-state`'s `SCHEMA_VERSION` pattern in a fresh module vs. brand-new approach) — Claude decides during planning.
- Exact event-payload JSON shapes — match upstream where the reference table specifies them (`claimed`, `completed`, etc.); Claude chooses field names for advisory events (`tip_scratch_workspace`, `hallucinated_ref`).
- Tracing instrumentation strategy — Claude decides which spans to emit; recommendation: `tracing::info_span!("kanban.dispatch.tick")`, `kanban.spawn{task_id, profile}`, `kanban.claim{task_id, lock}`.

- Whether to emit a Phase 36.3.7 INV ledger (matches Phase 22.4.2.2 / 27.1.4.x precedent) — Claude decides; recommended yes given the protocol-correctness invariants (atomic claim, expected_run_id, created_cards gate).

## Specific Ideas

- **The reference doc IS the spec.** When the PDF and the reference disagree, the reference wins (D-01..D-39 all trace to reference). The PDF stays as design rationale (`docs/hermes-kanban-v1-spec.pdf`).
- **Skill versions are pinned to upstream.** `kanban-worker` ships as v2.0.0 and `kanban-orchestrator` as v3.0.0 — these are the versions in the Nous Research repo at sync time (2026-05-29). Bumping them later is its own change.
- **Worker subprocess shape matches Hermes verbatim.** `ironhermes --profile <P> chat -q "work kanban task <id>"` — the lanes-doc spawn shape with `ironhermes` substituted for `hermes`. The `chat -q` flag is added specifically to honor this contract (D-15).
- **`created_cards` gate is non-optional.** Without it, an orchestrator can hallucinate task ids in `kanban_complete.created_cards` and the kernel would have no audit trail. Skill explicitly says "permanently recorded on the task's event log" — implement as `completion_rejected` event, never deletable (D-22).
- **`expected_run_id` is the run-level fencing primitive.** Composes with `claim_lock`-asserted writes (D-41). A reclaimed-then-respawned worker's late writes from the prior run are rejected by *both* gates — defense in depth.
- **No "smart routing" or "auto-assignment" in the kernel.** Reference §"Scope boundary" is explicit. Operator manages profile-to-assignee mapping; orchestrator profiles route at decomposition time. Future router-profile pattern is user-space.
- **Single-host design.** Reference §"Out of scope" — no cross-host kanban. PID checks assume host-local; do not implement remote-PID detection.

</specifics>

## Deferred Ideas

These were discussed and are part of the long-term canonical surface but explicitly fall outside Phase 36.3.7. Capture as candidate follow-up phases under 36.3.7.x or peer 36.3.x phases.

### Tool surface follow-up (likely 36.3.7.1)
- `kanban_heartbeat` LLM tool + `kanban.dispatch_stale_timeout_seconds` (default 4h) + 1-hour heartbeat cadence guidance.
- `kanban_link` LLM tool (after-the-fact dependency editing, currently absent — operators must use CLI `link`).
- `kanban_unblock` LLM tool (currently CLI/operator-only).

### Triage + decomposer flow (likely 36.3.7.2)
- Auto-decompose loop: dispatcher runs LLM decomposer on `triage` tasks (`kanban.auto_decompose: true`, `auto_decompose_per_tick: 3`).
- `kanban specify` and `kanban decompose` CLI/slash verbs.
- `auxiliary.kanban_decomposer` and `auxiliary.profile_describer` config slots.
- Profile-description field + `ironhermes profile describe <name> {--text|--auto}` CLI verbs.
- `kanban.default_assignee` and `kanban.orchestrator_profile` config keys.

### Multi-board (likely 36.3.7.3)
- `ironhermes kanban boards {list,create,switch,show,rename,rm}` CLI surface.
- `~/.ironhermes/kanban/boards/<slug>/kanban.db` per-board layout.
- `--board <slug>` flag + `~/.ironhermes/kanban/current` slug pointer.
- `HERMES_KANBAN_BOARD` env propagation (already in v1 contract D-17; multi-board makes it meaningful).

### Dashboard plugin (likely 36.3.7.4 — large)
- **Hosting decision (locked for the follow-up phase):** The dashboard SPA + REST + WS surface lives **inside `iron_hermes_ui`** (the UI server) and is reached from the Agents page via a "KANBAN" button — not as a separate web server on `ironhermes-gateway`. Rationale: matches [[project_arch_embedded_agent]] / [[project_arch_gateway_vs_ui]] precedent (agent + user-facing surfaces live in the UI server; gateway is the agent runtime + dispatcher host). The kanban DB is read-through + write-through `ironhermes-kanban` from both sides — no separate domain logic in the UI plugin.
- React-or-equivalent SPA at `plugins/kanban/` mounted in `iron_hermes_ui`.
- REST surface (`/board`, `/tasks/*`, `/tasks/bulk`, `/links`, `/dispatch`, `/workers/active`, `/runs/{id}`, `/inspect`, `/profiles`, `/orchestration`, `/config`) served from `iron_hermes_ui`'s axum router under `/api/plugins/kanban/...`.
- WebSocket `/events?since=<event_id>` tailing `task_events` — also served from `iron_hermes_ui`.
- Drag-drop columns, multi-select bulk actions, inline create, side drawer with editable title/assignee/priority/body/dependencies/result + comment thread + run history.
- Trash drop-zone (`DELETE /api/plugins/kanban/tasks`).
- Recovery actions (Reclaim / Reassign / Change profile model) tied to `⚠ stuck worker` badge.

### Gateway notifier (likely 36.3.7.5)
- `notify-subscribe`/`notify-list`/`notify-unsubscribe` CLI verbs.
- Auto-subscribe on `/kanban create` from a chat (gateway-only, skipped on `--json`).
- Subscription table in `kanban.db` + background poll of `task_events` for terminal events.
- Terminal-event delivery shape (`completed` with first-line summary, `blocked`/`gave_up`/`crashed`/`timed_out` with reason).
- Auto-cleanup on `done`/`archived`.
- `notification_sources` config enforcement (the config key itself is reserved in v1 per D-37).

### Topology helpers (likely 36.3.7.6)
- `ironhermes kanban swarm "<goal>" --workers a,b,c --verifier d --synthesizer e` topology builder (root + parallel workers + verifier + synthesizer in one command).
- Optional: blackboard structured-comment helpers.

### @mention parser (P6) (likely 36.3.7.7 or peer)
- Gateway-side parser for `@profile-name` patterns in user messages and comment bodies.
- Auto-create with surrounding text as task body.
- Profile-name resolution + denial path for unknown profiles.

### Portable profile artifacts (likely 36.3.7.8 or peer)
- `ironhermes profile export <name>` produces YAML/Markdown artifact.
- `ironhermes profile install <path>` imports.
- Closes the Gemini-CLI-subagent-as-file parity gap (PDF §1.3 Table 1).

### External CLI worker lanes (much later, likely v3.1+)
- Plugin `spawn_fn` registration API (currently rejected per [[project_plugin_loader_rejected]]).
- Codex / Claude Code / OpenCode wrapper lanes.
- Generic CLI-runner shape parameterised by config.
