### UAT-09-A — Live worker subprocess spawn

**Goal:** prove `dispatcher → spawn_worker → real ironhermes subprocess → KanbanStore` round-trip works end-to-end on a real machine.

**Preconditions:**
- (a) `cargo build --workspace` exits 0.
- (b) At least one configured profile in `~/.ironhermes/profiles/`.
- (c) Ability to make real LLM calls (network + valid API key for the profile's provider).

**Procedure:**

1. `cargo build --workspace` — confirm success.
2. Isolated home: `IRONHERMES_HOME=$(mktemp -d) && export IRONHERMES_HOME && echo "Using IRONHERMES_HOME=$IRONHERMES_HOME"`.
3. Init kanban: `./target/debug/ironhermes kanban init` — then verify `ls $IRONHERMES_HOME/kanban.db` and `ls $IRONHERMES_HOME/skills/kanban-worker/SKILL.md` both succeed (proves plan 07 first-run sync ran).
4. Create a task (substitute `YOUR_PROFILE` with an existing profile name):
   ```bash
   ./target/debug/ironhermes kanban create \
     "smoke-test task — say hello and call kanban_complete with a one-line summary" \
     --assignee YOUR_PROFILE --json
   ```
   Capture the returned `task_id`.
5. Confirm it's ready: `./target/debug/ironhermes kanban list` — task must appear with `status=ready`.
6. **Env-scrub probe (D-18 / INV-36.3.7-07 runtime check):** before dispatching, set a sentinel:
   ```bash
   export OPENAI_API_KEY="marker_${RANDOM}_${RANDOM}"
   echo "Sentinel value: $OPENAI_API_KEY"
   ```
   (Stash the real key elsewhere first.) The sentinel must NOT appear in the worker's logs after step 9 — this verifies D-18 env scrub at runtime.
7. One-shot dispatch: `RUST_LOG=ironhermes_kanban=info ./target/debug/ironhermes kanban dispatch --max 1` — watch tracing output. Expect spans named `kanban.dispatch.tick` and `kanban.dispatch.step` (with `step=claim_and_spawn`), and `claimed` then `spawned` events with a non-zero PID.
8. (Optional) `ps -p <PID>` should show a running `ironhermes --profile YOUR_PROFILE --skills kanban-worker chat -q "work kanban task <id>"` process.
9. Wait for the worker process to exit (or `kill -TERM <PID>` if it hangs).
10. Verify outcome:
    - `./target/debug/ironhermes kanban show <task_id>` → expect `status: done` (golden path) or `status: blocked` (acceptable PARTIAL).
    - `./target/debug/ironhermes kanban runs <task_id>` → expect ≥1 row with `outcome: completed` or `outcome: blocked`.
    - `cat $IRONHERMES_HOME/logs/kanban/<task_id>.stdout.log` — confirm worker stdout captured at the canonical path from `paths::kanban_log_stdout()`.
    - `grep "marker_" $IRONHERMES_HOME/logs/kanban/<task_id>.stdout.log` — must return ZERO matches (proves D-18 env scrub).

**PASS criteria (all must hold):**
1. `kanban dispatch --max 1` tracing emits a `claimed` event followed by a `spawned` event with a non-zero PID.
2. After the worker process exits, `kanban show <task_id>` returns `status: done` (golden path) OR `status: blocked` (acceptable PARTIAL).
3. `kanban runs <task_id>` returns ≥1 row with `outcome: completed` or `outcome: blocked`.
4. `$IRONHERMES_HOME/logs/kanban/<task_id>.stdout.log` exists and is non-empty.
5. No stranded claim_lock — `kanban list` after worker exit does not show the task as `running`.
6. The sentinel `marker_*` value injected in step 6 does NOT appear in the worker's stdout log (D-18 env scrub).

**FAIL signals (any of):**
- Worker never spawns (no PID in tracing output for the `claim_and_spawn` step).
- Task stays `ready` indefinitely (>60s after dispatch returns).
- Worker crashes with sqlite "database is locked" (would indicate WAL pragma drift in plan 02 schema setup).
- Sentinel `marker_*` value appears in worker stdout log (D-18 env scrub regression — would violate INV-36.3.7-07).
- `kanban list` shows the task as `running` 60+ seconds after the worker process exited (stranded claim_lock — would violate D-10 step 1 detect_crashed).

**Evidence to capture:** PID, task_id, run_id, full tracing output of `kanban dispatch` (with `RUST_LOG=ironhermes_kanban=info`), the stdout/stderr log file contents, output of `kanban show` and `kanban runs`, output of the `grep "marker_"` sentinel check.

**Escalation path on fail:** open Phase 36.3.7.0 (fix-forward sub-phase) for the specific failure mode; attach the evidence above as the bug report; cross-reference the violated INV ID from `INV-36.3.7.md`. INV-36.3.7-05/07/10 are the most likely violators for runtime smoke failures.

### UAT-09-B — Live `/kanban` slash command from gateway

**Goal:** prove the D-36 mid-run bypass works — typing `/kanban list` during a real gateway-routed chat session executes the verb without polluting the agent's context and without blocking the dispatcher.

**Preconditions:**
- (a) UAT-09-A passed (proves the kernel + worker spawn pipeline is wired correctly).
- (b) Gateway can start (`./target/debug/ironhermes gateway start` returns no error within 5 seconds and remains running).
- (c) At least one gateway-attached chat platform configured (Telegram is preferred; local chat REPL via `ironhermes chat` is sufficient — Discord/Slack not required).

**Procedure:**

1. Fresh home: `IRONHERMES_HOME=$(mktemp -d) && export IRONHERMES_HOME && ./target/debug/ironhermes kanban init`.
2. Seed a task: `./target/debug/ironhermes kanban create "bypass-smoke task" --assignee YOUR_PROFILE --json` → capture `task_id`.
3. **Terminal A** — start the gateway (dispatch_in_gateway defaults to `true` per D-09):
   ```bash
   RUST_LOG=ironhermes_gateway=info,ironhermes_kanban=info \
     ./target/debug/ironhermes gateway start
   ```
   Wait for the kanban dispatcher span `kanban.dispatch.tick` to appear in the gateway log (proves D-09 embed).
4. **Terminal B** — start an interactive chat session: `./target/debug/ironhermes chat`.
5. After the prompt appears, type `/kanban list` and hit Enter.
6. (Optional) follow up with `/kanban show <task_id>`.
7. Then type a regular non-slash message (e.g. `what's the weather`) and let the LLM respond.
8. Exit chat (Ctrl-D or Ctrl-C).
9. Inspect the transcript: `find $IRONHERMES_HOME -name '*.jsonl' -newer $IRONHERMES_HOME/kanban.db -print` to locate the session transcript; `grep '/kanban' <transcript>` — the slash command must NOT appear (D-36 bypass means the command is handled out-of-band, never enters agent context).
10. Stop the gateway (Ctrl-C in Terminal A).
11. Verify no orphan processes: `ps -A | grep -E 'ironhermes (gateway|chat|--skills kanban-worker)' | grep -v grep` — must return empty after both terminals exit.

**PASS criteria (all must hold):**
1. `/kanban list` prints the task table directly to the terminal (not via an LLM round-trip — verifies the slash command was handled by the CommandRouter bypass, not forwarded as a user message).
2. Latency is sub-second (no LLM round-trip — bypass means direct CLI dispatch).
3. The session transcript file (under `$IRONHERMES_HOME/`) contains the regular non-slash message but NOT `/kanban list` (D-36 mid-run bypass, INV-36.3.7-SG-05 runtime path).
4. The gateway log shows the kanban dispatcher tick (`kanban.dispatch.tick` span) continued running uninterrupted during the slash command (D-09 — bypass must not block the embedded dispatcher).
5. After gateway shutdown, no orphan `ironhermes` processes remain (`ps -A | grep ironhermes` returns empty for non-current-shell entries).

**FAIL signals (any of):**
- `/kanban list` is sent to the LLM (visible in agent token usage spike or in the agent's reply mentioning "I'll run that command").
- Gateway crashes or returns an error when slash command is received.
- Transcript JSONL contains the `/kanban list` string as a user message (would violate D-36).
- Kanban dispatcher tick spans stop appearing in the gateway log during/after the slash command (would violate D-09 embedded dispatcher independence).
- Orphan kanban-worker processes remain after gateway shutdown.

**Evidence to capture:** full gateway log (with `RUST_LOG=ironhermes_gateway=info,ironhermes_kanban=info`), chat transcript JSONL file, full terminal output of both terminals, output of `ps -A | grep ironhermes` after shutdown.

**Escalation path on fail:** open Phase 36.3.7.0 (fix-forward sub-phase); attach evidence; cite the violated INV (most likely INV-36.3.7-SG-05 if the slash command leaks into the transcript, or D-09 if the dispatcher pauses).

### UAT-09-B — Live `/kanban list` slash command — **FAILED at step 4**

Tested first via `chat -q "/kanban list"` (run_single path), then by static-trace through the interactive `chat` path (run_chat).

**`chat -q` path (run_single):** As designed, `run_single` does NOT intercept slash commands — line 875 comment: "no user can trigger a slash command mid-batch. Dropping it is intentional." Resulting behavior: the literal string `/kanban list` was sent to the LLM, which called `delegate_task` 3 times and produced its own markdown synthesis. 4 turns, 43,340 tokens, 5m47s wall time. Not a bypass, but correct-by-design for `run_single`.

**Interactive `chat` path (run_chat):** Static trace confirms:
- `input.starts_with('/')` at `main.rs:1601` correctly enters slash dispatch ✓
- `dispatch_command(...)` → `router.resolve("/kanban list")` matches `CommandDef::new("kanban", ...)` at `registry.rs:215` ✓
- `handlers::dispatch(def, args, ctx, router)` at `handlers.rs:12` enters the giant `match cmd.name` ✗

**Root cause — Bug #2: `/kanban` slash command has no handler.**
- `handlers.rs` has no `"kanban" =>` arm in the dispatch match.
- `name => todo_stub(name)` (handlers.rs:89) catches it and returns `CommandResult::Output("/kanban is not yet available. (Not implemented)")`.

### Bug #3 (lower severity): Failure circuit-breaker off-by-one

During UAT-09-A re-dispatch attempts, `consecutive_failures` reached **3** before the circuit breaker (`failure_limit` default 2) blocked further spawns. The semantics implied by "failure limit = 2" should be "block at 2 failures" (`>=`) but the implementation uses `>` (block after exceeding 2). Result: every task gets one extra spawn attempt before the breaker fires. One-character fix in `dispatcher.rs` (`>` → `>=`). Confirm the intended semantics with D-12 before fixing.
