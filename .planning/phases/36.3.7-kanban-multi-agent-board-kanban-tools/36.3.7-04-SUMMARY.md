# Phase 36.3.7 Plan 04: Kanban LLM Tool Surface Summary

6 LLM Tool impls for the kanban worker protocol — direct KanbanStore calls (no CLI shelling per D-20 backend portability).

## What Was Built

### 6 Tool Implementations

All tools live in `crates/ironhermes-kanban/src/tools/`, share a `Arc<TokioMutex<KanbanStore>>`,
and gate visibility on `HERMES_KANBAN_TASK` env (worker mode) or `explicit_enable` flag (orchestrator mode) per D-20.

| Tool | File | Store Method | Key Contract |
|------|------|--------------|-------------|
| `kanban_show` | show.rs | `get_task` + SQL queries | Returns `worker_context` envelope: title, body, status, assignee, tenant, workspace, parent_handoffs, prior_attempts, comments |
| `kanban_list` | list.rs | `list_tasks` | Compact summaries only (no body/comments per D-25); filters: assignee, status, tenant, archived, limit |
| `kanban_comment` | comment.rs | `add_comment` / inline SQL | D-41: `worker_write_gated` when `HERMES_KANBAN_CLAIM_LOCK` is set; returns `{"status":"no-op","reason":"claim_expired"}` on gate miss |
| `kanban_complete` | complete.rs | `complete_task` | D-22: `expected_run_id` + `created_cards` dual-gate; structured rejection JSON as `Ok` |
| `kanban_block` | block.rs | `block_task` | D-23: `expected_run_id` gate; `review-required:` prefix → advisory tracing log |
| `kanban_create` | create.rs | `create_task` | D-24: idempotency_key dedup; parents → todo; dir: relative rejected (D-31); human max_runtime parsing |

### register_kanban_tools

```rust
pub fn register_kanban_tools(
    registry: &mut ironhermes_tools::ToolRegistry,
    store: Arc<TokioMutex<KanbanStore>>,
    explicit_enable: bool,
)
```

Registers all 6 tools under `toolset = "kanban"`. Plan 05 calls this at session construction
when `HERMES_KANBAN_TASK` env is present (worker mode) or when the kanban toolset is explicitly
enabled (orchestrator mode).

```json
  ]

```

### Structured Rejection JSON Convention

Protocol terminators return `Ok(String)` with structured JSON for protocol-level rejections so
the LLM can read and handle them without the tool call failing entirely:

```json
// stale_run_id rejection:
{"status": "rejected", "reason": "stale_run_id", "task_id": "...", "expected": "r_old", "actual": "r_new"}

// created_cards rejection (+ permanent completion_rejected event in task_events):
{"status": "rejected", "reason": "created_cards", "task_id": "...", "phantom_ids": [...], "wrong_profile_ids": [...]}

// claim_expired no-op (kanban_comment in worker mode with stale claim):
{"status": "no-op", "reason": "claim_expired"}
```

Genuine errors (bad SQL, task not found) propagate as `Err` per the `anyhow::Result<String>` contract.

## Proposal: ToolOutcome enum (for future phase consideration)

The plan requested documenting whether structured rejection JSON should be lifted to the
`ironhermes-tools` Tool trait as `enum ToolOutcome { Ok(String), Rejected(serde_json::Value) }`.

**Recommendation: Defer to v2, do not implement in v1.**

Rationale:
- All 25 existing `impl Tool` blocks return `anyhow::Result<String>` — changing the return type
  would be a breaking change across the entire tool ecosystem.
- The convention of returning `Ok(structured_rejection_json)` is well-established at the call
  sites in AgentLoop (the caller just forwards the string to the LLM).
- If added, `ToolOutcome` would be an additive enum with `#[non_exhaustive]` — the AgentLoop
  would match `ToolOutcome::Rejected(v)` to add a `[REJECTED]` prefix to the LLM message,
  enabling trajectory recording to distinguish protocol rejections from successful outputs.
- Consider pairing with Phase 36.3.7.1's `kanban_heartbeat` work when the tool surface expands.
