## What Was Built

### Config Wiring Decision

**Choice made: `serde_yaml::Value` raw field in `ironhermes-core::Config`.**

`ironhermes-kanban` already depends on `ironhermes-core`, so `ironhermes-core` cannot depend on `ironhermes-kanban` (circular dep). The same pattern used for `mcp_servers` applies here: store raw `serde_yaml::Value` in `Config`, deserialize to `KanbanConfig` at the use site in runner.rs.

```rust
// ironhermes-core/src/config.rs
#[serde(default)]
pub kanban: serde_yaml::Value,
```

At the spawn site in runner.rs:
```rust
let kanban_config: ironhermes_kanban::KanbanConfig =
    if self.config.kanban.is_null() {
        ironhermes_kanban::KanbanConfig::default()
    } else {
        match serde_yaml::from_value::<ironhermes_kanban::KanbanConfig>(self.config.kanban.clone()) {
            Ok(cfg) => cfg,
            Err(e) => { warn!(...); KanbanConfig::default() }
        }
    };
```

Pre-36.3.7 configs (absent `kanban:` key) parse cleanly with `Value::Null` → all-defaults.

### Step 11 Insertion in runner.rs

Inserted immediately after the closing `}` of the Step 10 cron tick `if let Some(ref job_store)` block (line 1240), before the `tokio::select!` dispatch loop. The block:

1. Deserializes `self.config.kanban` to `KanbanConfig` (defaults on null/parse error)
2. Checks `HERMES_KANBAN_DISPATCH_IN_GATEWAY` env override (`!= "0"` = enabled, absent = enabled)
3. If both `config.dispatch_in_gateway && env_ok`:
   - Opens `KanbanStore::open_default()` — logs warn + skips on error (non-fatal)
   - Creates `DispatcherContext::new(store, config)`
   - Spawns `run_dispatch_loop(ctx, kanban_cancel)` into `join_set`
   - Logs `"Kanban dispatch task started ({}s interval)"`
4. If env override active: logs `"Kanban dispatcher disabled via HERMES_KANBAN_DISPATCH_IN_GATEWAY=0"`
5. If config disabled: debug log only

The `kanban_cancel = self.cancel.clone()` ensures the dispatcher task receives the same CancellationToken as all other gateway tasks — clean shutdown on Ctrl-C or programmatic cancel.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `run_dispatch_loop` was `!Send` — could not be spawned into tokio JoinSet**

- **Found during:** Task 1 build (`cargo build -p ironhermes-gateway`)
- **Issue:** `crates/ironhermes-kanban/src/dispatcher.rs` used `tracing::info_span!(...).entered()` to create `EnteredSpan` values inside `run_dispatch_tick` (both in the outer loop and in each of the 6 step blocks). `EnteredSpan` is `!Send` (it holds `PhantomNotSend`). Because the future `.await`s inside those same blocks, rustc considers the `EnteredSpan` potentially alive across the await point, making the entire `run_dispatch_loop` future `!Send`. `JoinSet::spawn` requires `Send`.
- **Fix:** Replaced all `.entered()` patterns with `.instrument(span)` on the inner async block wrapping each step's `.await`. `Instrument` is `Send`-safe. Applied to both `run_dispatch_loop` (outer span) and all 6 steps in `run_dispatch_tick`. Added `use tracing::Instrument as _;` import.
- **Files modified:** `crates/ironhermes-kanban/src/dispatcher.rs`
- **Commit:** fdba05eb

**2. [Rule 3 - Blocking] `serde_yaml` not a direct dep of `ironhermes-gateway`**

- **Found during:** First build attempt after adding config deserialization code
- **Issue:** `serde_yaml::from_value` was unresolved — `ironhermes-gateway` did not have `serde_yaml` as a direct Cargo dependency.
- **Fix:** Added `serde_yaml = { workspace = true }` to `crates/ironhermes-gateway/Cargo.toml`.
- **Files modified:** `crates/ironhermes-gateway/Cargo.toml`
- **Commit:** fdba05eb
