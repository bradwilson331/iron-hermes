## Task 0 Decision: PID-liveness primitive

**User selected:** `nix` with the Errno-discriminating implementation.

```rust
#[cfg(unix)]
pub fn is_pid_alive(pid: u32) -> bool {
    use nix::sys::signal::kill;
    use nix::unistd::Pid;
    use nix::errno::Errno;
    match kill(Pid::from_raw(pid as i32), None) {
        Ok(()) => true,                  // process exists
        Err(Errno::ESRCH) => false,      // no such process
        Err(Errno::EPERM) => true,       // exists but owned by another uid
        Err(_) => false,
    }
}
```

**Rationale:** The naive `kill(pid, 0).is_ok()` form drops the EPERM signal (process exists but owned by another uid) into the "dead" bucket. For a dispatcher that may spawn workers under a different uid than the gateway runtime (e.g. cron-launched setups), this would cause the dispatcher to incorrectly reclaim live foreign-uid workers. The Errno discrimination prevents that class of bug.

**Reachable as:**
- `ironhermes_kanban::is_pid_alive` (crate-root re-export — plan 03 will use this)
- `ironhermes_kanban::pid::is_pid_alive` (module-qualified)

**Supply-chain risk T-36.3.7-01-SC is moot** — `nix = { version = "0.29", features = ["process"] }` is a pre-existing workspace dependency (Cargo.toml line 126) already in use by `ironhermes-gateway`. No new package install was performed. The `[ASSUMED]` tag in RESEARCH.md was about verification before adding; the package was already vetted in a prior phase. `ironhermes-kanban/Cargo.toml` opts into the `signal` feature in addition (kill + Errno).

**An invariant test (`pid_liveness_handles_eperm`) locks the `Errno::EPERM` branch** in `pid.rs` against accidental simplification in future refactors.

### Cross-crate boundary

Every cross-crate type uses plain `String` for enumerable fields per CONTEXT.md D-17 (precedent: `OriginDecision` in `ironhermes-core`). `KanbanStatus` and `KanbanEventKind` exist for internal type safety within `ironhermes-kanban` only; `Task::status` and `KanbanEvent::kind` are plain `String` so `ironhermes-cli`, `ironhermes-gateway`, and `iron_hermes_ui` don't need a dep on this crate just to handle the enum.

### CLI flag wiring (D-15)

`chat -q "<prompt>"` short-circuits through `run_single` (the same path top-level `-e/--execute` uses) instead of entering the interactive REPL. The dispatcher's spawn command in plan 03 will be:
```
ironhermes --profile <P> chat -q "work kanban task <id>"
```
which matches the upstream `hermes -p P chat -q` contract verbatim. Top-level `-e` is preserved per D-15 ("remains the recommended path for scripted single-shot calls").
