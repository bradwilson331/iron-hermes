## Summary

Phase 36.3.7 ships the IronHermes Kanban v1 kernel as a new `ironhermes-kanban` crate that mirrors the `ironhermes-state` / `ironhermes-cron` separation pattern: one crate owns a durable SQLite subsystem, consumed by gateway, CLI, and UI. The crate delivers a 5-table SQLite schema with WAL and the `SCHEMA_VERSION` migration ladder, an atomic-claim dispatcher embedded as a tokio task in `ironhermes-gateway`, a 6-tool LLM surface gated by `HERMES_KANBAN_TASK` env, `KANBAN_GUIDANCE` injection into the 10-layer `PromptBuilder`, two bundled skills synced via `ensure_home_dirs()`, and a full CLI verb surface registered on the `Commands` enum.

The codebase has every required building block already in place and proven: `ironhermes-state` provides the exact schema/migration/WAL idioms to mirror; `ironhermes-gateway/src/runner.rs` shows exactly where to spawn the dispatcher tokio task (step 10 of the `start()` join set, after the cron tick task); `ironhermes-exec/src/sandbox.rs` provides the env-allowlist pattern; `ironhermes-cron-runner` provides the `CronRunnerContext` / `run_tick_loop` analog; `ironhermes-agent/src/prompt_builder.rs` has a `BTreeMap<PromptSlot, String>` slot system where a new pre-slot 0 block is the natural injection point for `KANBAN_GUIDANCE`; and the `CommandRouter` / `is_bypass()` function in `ironhermes-core/src/commands/running_agent.rs` is the exact mechanism to add `kanban` to the bypass list.

**Primary recommendation:** Mirror `ironhermes-state`'s schema/migration/WAL pattern verbatim in a fresh `KanbanStore` struct inside `ironhermes-kanban`. Use `TransactionBehavior::Immediate` (rusqlite) for the atomic CAS claim. Spawn the dispatcher as step 11 in `GatewayRunner::start()` join set, parallel to the cron tick task (step 10). Use `sysinfo` crate for cross-platform PID liveness (already a common dep in the ecosystem; no `nix` / libc unsafe required). Inject `KANBAN_GUIDANCE` by adding a pre-build hook in `PromptBuilder::build()` that prepends the static block when `HERMES_KANBAN_TASK` env is set.

```rust
const SCHEMA_SQL: &str = "
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;

CREATE TABLE IF NOT EXISTS schema_version (version INTEGER NOT NULL);

CREATE TABLE IF NOT EXISTS tasks (
    id                  TEXT PRIMARY KEY,
    title               TEXT NOT NULL,
    body                TEXT,
    assignee            TEXT NOT NULL,
    status              TEXT NOT NULL DEFAULT 'ready',
    priority            INTEGER NOT NULL DEFAULT 0,
    tenant              TEXT,
    workspace           TEXT,
    skills              TEXT,           -- JSON array
    idempotency_key     TEXT UNIQUE,
    claim_lock          TEXT,
    claim_expires       REAL,
    current_run_id      TEXT REFERENCES task_runs(id),
    consecutive_failures INTEGER NOT NULL DEFAULT 0,
    max_retries         INTEGER,
    max_runtime_seconds INTEGER,
    scheduled_at        REAL,
    workflow_template_id TEXT,
    current_step_key    TEXT,
    created_by          TEXT,
    created_at          REAL NOT NULL,
    started_at          REAL,
    ended_at            REAL
);
-- ... task_links, task_comments, task_events, task_runs tables
";
```

Key details from `ironhermes-state` (lines 46-116, 383-429): [VERIFIED: codebase]

1. `PRAGMA journal_mode=WAL` is the FIRST line in `SCHEMA_SQL`, set inside `execute_batch(SCHEMA_SQL)` at open time.
2. `schema_version` table holds a single row. On `None` → insert `SCHEMA_VERSION`. On `Some(v)` → call `run_migrations(v)`.
3. Migrations use `if current < N { ALTER TABLE ...; UPDATE schema_version SET version = N; }` — idempotent chain, never skipped.
4. `let _ = conn.execute("ALTER TABLE ... ADD COLUMN ...", [])` — the `let _ =` suppresses "duplicate column" errors on re-run (Phase 36.2 v9 precedent).
5. `conn.busy_timeout(Duration::from_millis(5000))` set immediately after open.

**Recommendation for Claude's Discretion:** Use the `SCHEMA_VERSION` / `run_migrations()` pattern verbatim. Start at `SCHEMA_VERSION = 1`. Keep the migration ladder in `schema.rs` separate from the store struct.

### Q2: Atomic Claim CAS Correctness [VERIFIED: codebase + D-40]

The project uses `rusqlite` (sync). The CAS pattern from D-40:

```sql
BEGIN IMMEDIATE;
UPDATE tasks
  SET status='running', claim_lock=?, claim_expires=?, started_at=?, current_run_id=?
  WHERE id=? AND status='ready' AND claim_lock IS NULL
    AND (scheduled_at IS NULL OR scheduled_at <= ?);
-- examine changes(): 1 = won, 0 = lost the race
COMMIT;
```

**LANDMINE:** rusqlite's `transaction()` defaults to `TransactionBehavior::Deferred`. `BEGIN IMMEDIATE` requires:

```rust
use rusqlite::TransactionBehavior;

let tx = conn.transaction_with_behavior(TransactionBehavior::Immediate)?;
tx.execute(
    "UPDATE tasks SET status='running', claim_lock=?, claim_expires=?, \
     started_at=?, current_run_id=? \
     WHERE id=? AND status='ready' AND claim_lock IS NULL \
     AND (scheduled_at IS NULL OR scheduled_at <= ?)",
    params![claim_lock, claim_expires, now, run_id, task_id, now],
)?;
let won = tx.changes() == 1;  // changes() on the Connection, not on a statement
tx.commit()?;
```

`rusqlite::Connection::changes()` returns the number of rows changed by the last INSERT/UPDATE/DELETE. After the CAS UPDATE: `1 = won`, `0 = lost` (another dispatcher claimed it first). [VERIFIED: codebase pattern + rusqlite API - ASSUMED for `changes()` method location]

The `task_runs` row MUST be inserted in the same transaction (D-40): "Dispatcher inserts the `task_runs` row in the same transaction; pointer + run row are coherent by construction."

**Existing example:** `ironhermes-state` uses `execute_batch` + sequential UPDATE for migrations — not a direct CAS example, but the rusqlite connection and transaction patterns are established. No existing `BEGIN IMMEDIATE` in the codebase was found; this is the first use. The rusqlite `transaction_with_behavior(TransactionBehavior::Immediate)` API is the correct approach. [ASSUMED]

### Q3: Live-PID Detection (D-10 step 1+2) [VERIFIED: codebase search]

No existing PID liveness check was found anywhere in `crates/`. The codebase does NOT currently use `nix`, `libc`, or `sysinfo` for PID checks.

**Recommendation:** Use `sysinfo`:

```rust
// crates/ironhermes-kanban/src/pid.rs
use sysinfo::{System, ProcessesToUpdate};

/// Returns true if a process with the given PID is currently running on this host.
/// This is the equivalent of POSIX `kill -0 <pid>`.
pub fn is_pid_alive(pid: u32) -> bool {
    let mut sys = System::new();
    sys.refresh_processes(ProcessesToUpdate::Some(&[sysinfo::Pid::from_u32(pid)]), false);
    sys.process(sysinfo::Pid::from_u32(pid)).is_some()
}
```

**Alternative (Unix-only, no external dep):** Parse `/proc/<pid>` on Linux, or use `libc::kill(pid, 0)` on macOS/Linux with `#[cfg(unix)]`. Since the system targets macOS/Linux (darwin + linux, per OS version in env), a `#[cfg(unix)]` approach is viable, but `sysinfo` avoids `unsafe` and is more idiomatic.

**Dispatcher logic for live-PID extension (D-10 step 2):** On TTL expiry, before reclaiming: if `is_pid_alive(run.claim_pid)` → emit `claim_extended` event and reset `claim_expires = now + DEFAULT_CLAIM_TTL_SECONDS`. Only if PID is dead → reset task to `ready`, emit `reclaimed`.

```rust
fn build_kanban_worker_env(task: &Task, run: &TaskRun, workspace: &str) -> Vec<(String, String)> {
    let mut env = Vec::new();
    // Safe system vars
    for var in &["PATH", "HOME", "USER", "LANG", "TERM", "RUST_LOG", "IRONHERMES_HOME"] {
        if let Ok(v) = std::env::var(var) { env.push((var.to_string(), v)); }
    }
    // 9 kanban env vars (D-17)
    env.push(("HERMES_KANBAN_TASK".into(), task.id.clone()));
    env.push(("HERMES_KANBAN_DB".into(), kanban_db_path().to_string_lossy().into()));
    env.push(("HERMES_KANBAN_BOARD".into(), "default".into()));
    env.push(("HERMES_KANBAN_WORKSPACES_ROOT".into(), workspaces_root().to_string_lossy().into()));
    env.push(("HERMES_KANBAN_WORKSPACE".into(), workspace.into()));
    env.push(("HERMES_KANBAN_RUN_ID".into(), run.id.clone()));
    env.push(("HERMES_KANBAN_CLAIM_LOCK".into(), run.claim_lock.clone()));
    env.push(("HERMES_PROFILE".into(), task.assignee.clone()));
    if let Some(tenant) = &task.tenant {
        env.push(("HERMES_TENANT".into(), tenant.clone()));
    }
    env
}
```

### Q6: KANBAN_GUIDANCE Prompt Injection (D-26) [VERIFIED: codebase]

**PromptSlot enum** (verified at `crates/ironhermes-agent/src/prompt_builder.rs:65-75`):

```rust
pub enum PromptSlot {
    Identity = 1,
    SystemMessage = 2,
    ToolGuidance = 3,
    Memory = 4,
    Skills = 5,
    ContextFiles = 6,
    Timestamp = 7,      // ephemeral (breaks cache)
    PlatformHints = 8,
    UserMessage = 10,
}
```

**KANBAN_GUIDANCE injection approach:** The `PromptBuilder` uses `BTreeMap<PromptSlot, String>` with `set_slot()`. There is no "slot 0" for a pre-identity block. The correct approach is:

**Option A (recommended):** Add a new `pub fn with_kanban_guidance(mut self) -> Self` builder method that prepends the `KANBAN_GUIDANCE` static block to the `Identity` slot (slot 1). This stays in the cached prefix (slots 1-6) since `KANBAN_GUIDANCE` is static. The `PromptBuilder` is constructed fresh per session; the kanban worker's `AgentLoop` setup checks `std::env::var("HERMES_KANBAN_TASK")` before calling `.with_kanban_guidance()`.

**Option B:** Add the guidance as a `SkillOverlay` (Phase 21.8.2 pattern already exists via `skill_overlays: Vec<(String, String)>`). Each overlay is prepended to the system slot in `build_system_message()`. Call `builder.add_skill_overlay("KANBAN_GUIDANCE", KANBAN_GUIDANCE_TEXT)` when `HERMES_KANBAN_TASK` is set.

**LANDMINE:** `KANBAN_GUIDANCE` must NOT go into slots 7+ (Timestamp/PlatformHints) — those are ephemeral and would break the Anthropic prompt cache every turn (Phase 36.2 D-CACHE-04 invariant). The `cached_layers_must_be_stable()` check panics in debug builds if dynamic content leaks into slots 1-6. Since `KANBAN_GUIDANCE` is a static string with no timestamps or session IDs, it is safe in slots 1-6.

**Where to hook:** The agent loop's `AgentLoop::new()` or the CLI's `run_single()` / `run_chat_turn()` constructs the `PromptBuilder`. Add the `HERMES_KANBAN_TASK` check there:

```rust
// In the PromptBuilder construction site (CLI chat entry point, ~main.rs or agent module)
let mut builder = PromptBuilder::new(model, platform);
if std::env::var("HERMES_KANBAN_TASK").is_ok() {
    builder = builder.add_skill_overlay("KANBAN_GUIDANCE", ironhermes_kanban::KANBAN_GUIDANCE);
}
```

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic claim serialization | Custom lock/mutex | `BEGIN IMMEDIATE` SQLite transaction | SQLite WAL provides full cross-process serialization; in-process mutex doesn't protect against multiple gateway restarts |
| PID liveness check | Parsing `/proc`, `unsafe libc::kill` | `sysinfo` crate | Cross-platform, no unsafe, already common |
| Env scrub for subprocess | Custom secret-pattern matching | Mirror `ironhermes-exec/src/sandbox.rs` pattern | Established allowlist already tested |
| Event log immutability | Soft-delete flags, UPDATE | Append-only INSERT into `task_events` | Events are the audit trail; once written they must not change |
| Task ID generation | Sequential integers | `uuid::Uuid::new_v4()` with `t_` prefix | Prefix makes IDs recognizable in prose; UUID prevents collision across boards |

**Key insight:** The most dangerous custom-solution trap in this phase is implementing the CAS claim with an in-process `Mutex` instead of `BEGIN IMMEDIATE`. Multiple gateway processes (restart scenario, standalone daemon) would then race without serialization. SQLite's `BEGIN IMMEDIATE` is the correct cross-process lock.

## Common Pitfalls

### Pitfall 1: DEFERRED vs IMMEDIATE Transaction
**What goes wrong:** Using `conn.transaction()` (default = DEFERRED) for the CAS claim allows two dispatcher instances to both read `status='ready'` before either locks, then both succeed the UPDATE.
**Why it happens:** `rusqlite::Connection::transaction()` documentation doesn't prominently highlight the `TransactionBehavior` enum.
**How to avoid:** ALWAYS use `conn.transaction_with_behavior(TransactionBehavior::Immediate)` for the claim UPDATE. Write an invariant test that asserts the source contains `"Immediate"`.
**Warning signs:** Integration tests show double-claims under concurrent test harnesses.

### Pitfall 2: changes() Location
**What goes wrong:** Calling `tx.changes()` on the `Transaction` wrapper instead of the `Connection`. rusqlite's `changes()` is on `Connection`, not `Transaction`.
**Why it happens:** It's a natural API confusion.
**How to avoid:** After `tx.execute(CAS_UPDATE, ...)`, use `conn.changes()` where `conn` is the `Connection` underlying the transaction, OR use `tx.changes()` if rusqlite exposes it on `Transaction` (verify API). [ASSUMED — needs verification at implementation time]

### Pitfall 3: Protocol Violation vs Crash Detection
**What goes wrong:** Treating worker exit-0 with task still `running` as a `crashed` event instead of `protocol_violation`.
**Why it happens:** Easy to conflate "process exited" with "something went wrong."
**How to avoid:** After child process exits: check exit code. If `Some(0)` AND task still `running` → emit `protocol_violation` + auto-block. If non-zero / signal → emit `crashed`. These have different retry semantics (D-27: protocol_violation is NOT retried).

### Pitfall 4: is_bypass() Test Invariant
**What goes wrong:** Adding `"kanban"` to `is_bypass()` without updating the invariant test in `running_agent.rs`.
**Why it happens:** The test asserts both members AND non-members; adding a member without updating the test causes test failure.
**How to avoid:** Update both `is_bypass()` and the test in the same commit. The test is an intentional regression gate per the Phase 36 design.

### Pitfall 5: Cache Stability with KANBAN_GUIDANCE
**What goes wrong:** `KANBAN_GUIDANCE` accidentally includes a dynamic value (session ID, timestamp) → `cached_layers_must_be_stable()` panics in debug builds.
**Why it happens:** The block might be tempting to include `$HERMES_KANBAN_TASK` as a runtime-expanded value.
**How to avoid:** Keep `KANBAN_GUIDANCE` as a static string (`const`). The worker reads `$HERMES_KANBAN_TASK` at runtime via `kanban_show()`, not from the injected text.

### Pitfall 6: dir: Workspace Path Validation
**What goes wrong:** Accepting relative paths like `dir:../tenants/foo/` → confused-deputy filesystem escape.
**Why it happens:** Path validation missed at create time.
**How to avoid:** At `kanban_create` time (and at dispatch time for defense-in-depth): reject any `workspace` value starting with `dir:` unless the path after `dir:` is absolute (`path.is_absolute()`).

### Pitfall 7: created_cards Phantom IDs
**What goes wrong:** Orchestrator LLM hallucinates task IDs in `kanban_complete(created_cards=[...])`.
**Why it happens:** LLM may fabricate IDs it saw in prior tool results or invented in prose.
**How to avoid:** `kanban_complete` MUST verify each `created_cards` entry: (1) exists in `tasks` table, (2) `tasks.created_by = HERMES_PROFILE`. Rejection is a permanent `completion_rejected` event — not a soft error.

### Pitfall 8: Missing Workspace Scaffolding
**What goes wrong:** `scratch` workspace dir doesn't exist when the worker starts → worker can't write files.
**Why it happens:** Workspace dir creation is a dispatcher responsibility, not the worker's.
**How to avoid:** Dispatcher creates `kanban_workspace_for(task_id)` before spawning the worker (and emits `tip_scratch_workspace` event on first-ever scratch creation per D-31).
