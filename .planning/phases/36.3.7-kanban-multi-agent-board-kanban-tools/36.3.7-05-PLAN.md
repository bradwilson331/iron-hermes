<objective>
Wire the worker prompt injection (D-26) and the tool registration (D-20) into the CLI chat entry point. When a process starts with `HERMES_KANBAN_TASK` env set (i.e., the dispatcher spawned this process as a worker), two things happen at session-construction time: (1) the `KANBAN_GUIDANCE` system-prompt block is prepended to the agent's identity layer via the existing `add_skill_overlay` API, and (2) the 6 `kanban_*` tools are registered on the session's `ToolRegistry`.

Purpose: Without this wiring, a worker process spawned by plan 03's dispatcher has no idea what protocol to follow — it sees `--skills kanban-worker` loaded (giving it the deeper pitfalls/examples skill) but lacks the lifecycle preamble that tells it to call `kanban_show` first. The injection happens at the prompt-assembly layer (existing 10-layer builder from Phase 15) — no new prompt slot; reuse the `skill_overlays` field that Phase 21.8.2 already added (PATTERNS.md confirms `skill_overlays: Vec<(String, String)>` at prompt_builder.rs:109; plan 01 SUMMARY confirms `add_skill_overlay` method exists).

CRITICAL invariant (RESEARCH.md Pitfall 5 + Phase 36.2 D-CACHE-04): `KANBAN_GUIDANCE` MUST be a `pub const &str` with NO runtime interpolation. The worker reads `$HERMES_KANBAN_TASK` at runtime via `kanban_show()`, NOT from the injected text. If the static text contained dynamic content, `cached_layers_must_be_stable()` would panic in debug builds.

Output: A static `KANBAN_GUIDANCE` constant in `ironhermes-kanban`, the CLI's chat handler wired to inject it + register the 6 tools when env-gated.
</objective>
