# Phase 36.3.7.2: Tool-schema compatibility — drop top-level oneOf from delegate_task — Context

**Gathered:** 2026-05-29
**Status:** Ready for planning
**Source:** Phase 36.3.7.0 UAT-09-A re-run #5 (see `.planning/phases/36.3.7.0-kanban-v1-uat-discovered-fixes-inserted/36.3.7.0-04-UAT-EVIDENCE.md` — "Discovered: Bug #5")

<domain>
## Phase Boundary

This is a single-file source fix + a single-file test fix + a system-level regression test that locks the rule for every future tool. Discovered during Phase 36.3.7.0 UAT when a kanban worker subprocess routed through Anthropic-via-OpenRouter hit:

```
400: tools.1.custom.input_schema: input_schema does not support oneOf, allOf, or anyOf at the top level
```

`crates/ironhermes-tools/src/delegate_task.rs:735` is the lone offender in `ironhermes-tools` (confirmed via `grep -rnE '"oneOf"|"allOf"|"anyOf"' crates/ironhermes-tools/src/`). The schema-level `oneOf` was added to enforce mutual exclusion of `task` (single mode) vs `tasks` (batch mode) at tool-definition parse time. The runtime path in `execute()` at line 763 already enforces this same constraint as a defence-in-depth fallback (`if args.get("tasks").is_none() && args.get("task").is_none() { bail!("Either 'task' (single mode) or 'tasks' (batch mode) is required"); }`). Dropping the schema-level `oneOf` preserves runtime correctness; only the parse-time signal to the LLM is lost (it can still be communicated in the property descriptions).

In scope:
- BUG-IRONHERMES-TOOLS-SCHEMA-COMPAT-01 — drop top-level `oneOf` at delegate_task.rs:735; rewrite the descriptions of `task` and `tasks` properties so the LLM still understands they are mutually exclusive (description-only signal, not schema-level enforcement)
- BUG-IRONHERMES-TOOLS-SCHEMA-COMPAT-02 — audit all other tools in `crates/ironhermes-tools/src/` for top-level `oneOf` / `allOf` / `anyOf`; cite findings in SUMMARY; expand fix surface only if grep returns more hits beyond the delegate_task line
- BUG-IRONHERMES-TOOLS-SCHEMA-COMPAT-03 — system-level receiver-end test that synthesizes the tool registry, renders each tool's `input_schema`, asserts no top-level `oneOf` / `allOf` / `anyOf`; runs against EVERY tool in the registry to lock the regression for future additions
- Update the existing `delegate_task` schema unit test at lines 1230-1239 that asserts on the `oneOf` shape (it now asserts the opposite: NO top-level `oneOf`)

Out of scope:
- Per-provider schema rendering (Anthropic vs OpenAI different shapes) — too large a lift; runtime-validation fallback already covers correctness
- Any change to the runtime validation path in `execute()` — that's the load-bearing correctness layer, leave it alone
- Touching ANY tool's `execute()` logic
- Anything in the kanban crate or 36.3.7.x scope
- Renaming or restructuring `delegate_task` beyond the schema change
- The OpenRouter "deprecated env var OPENROUTER_API_KEY" warning (separate config issue)
- The profile `.env` propagation question (separate operational decision)

</domain>

<locked_decisions>
## Locked Decisions

### Drop top-level `oneOf` from delegate_task input_schema

**Decision:** Modify `crates/ironhermes-tools/src/delegate_task.rs` around line 735 to remove the entire `oneOf` block:
```rust
// REMOVE this block:
"oneOf": [
    { "required": ["task"] },
    { "required": ["tasks"] }
]
```

Replace it with NOTHING at the schema top level — no alternative encoding (no nested `oneOf` inside a property, no anyOf inside properties, no required hack). The schema becomes a flat `"type": "object"` with `"properties": {...}` and an explicit `"required": []` (or no required field at all). The mutual-exclusion constraint moves entirely to:
- The runtime `execute()` validation at line 763 (already in place — verified)
- The `task` and `tasks` property descriptions, which must call out the mutual exclusion in plain English so the LLM honors it at tool-call time

**Rejected alternatives:**
- (a) Nest the `oneOf` inside a wrapper property like `"_mutex": { "oneOf": [...] }` — moves the violation one level deep but Anthropic's validator may still reject (untested, risky)
- (b) Render different schemas per provider (Anthropic vs OpenAI) — too large a code change; touches the tool-registration path and the LLM adapter layer
- (c) Convert `oneOf` to `anyOf` — Anthropic rejects this at the top level too (per the error message)
- (d) Use `"required": ["task"]` AND `"required": ["tasks"]` separately — schema-invalid (can't have two required arrays)

**Rationale:** The runtime validation is already the load-bearing correctness layer (per the comment at line 1221-1224 in the existing test: "Runtime validation in `execute()` still enforces mutual exclusion as defence-in-depth fallback"). The schema-level `oneOf` was redundant safety. Removing it loses the parse-time signal to the LLM but the property descriptions can carry that signal in prose. Net effect: tool works through every provider, runtime correctness preserved.

**Receiver verification (mandatory):** the fix MUST include:
- A unit test that asserts the rendered schema does NOT contain a top-level `"oneOf"` key
- An update of the existing test at delegate_task.rs:1230-1239 (which CURRENTLY asserts `"oneOf"` is present) — it must now assert the opposite
- The property descriptions for `task` and `tasks` must each mention the other and the mutual-exclusion rule, so the LLM sees the constraint at tool-call time

### Audit other tools in `ironhermes-tools`

**Decision:** A static-grep pass over `crates/ironhermes-tools/src/` for `"oneOf"`, `"allOf"`, `"anyOf"` (in JSON-literal context — `"oneOf":` exactly). Cite ALL findings in SUMMARY.md. Expand the fix surface ONLY IF the grep returns hits beyond:
- delegate_task.rs:735 (the producer — being fixed)
- delegate_task.rs:1231 (the existing test — being updated)

Pre-audit run from this CONTEXT confirmed those are the only two hits. If a re-grep during planning finds more, halt and surface them as additional named bugs (BUG-IRONHERMES-TOOLS-SCHEMA-COMPAT-04+); do not silently expand scope.

**Out of scope for grep audit:** test files outside `delegate_task.rs` — the test at line 1231 is the only one that asserts on the `oneOf` shape; other tools' tests don't reference the keyword.

### System-level receiver-end test

**Decision:** Add a new test (location: `crates/ironhermes-tools/tests/no_top_level_schema_combinators.rs` or similar) that:
1. Instantiates the full tool registry (or at least every concrete tool in `ironhermes-tools`).
2. For each tool, calls `tool.schema()` (or `tool.input_schema()` — whatever the trait method is).
3. Asserts the rendered `Value` does NOT have a top-level `oneOf`, `allOf`, or `anyOf` key.
4. Fails with the tool name in the message so future regressions are immediately greppable.

This is the LOCK for every future tool addition — anyone who adds a new tool with a top-level boolean combinator will get a CI-time fail with the offending tool named. It directly encodes the bilateral-tracing meta-rule for this surface.

**Test must run against EVERY tool registered in `ironhermes-tools`, not just `delegate_task`.** If the tool registry's iteration API is awkward, hardcode the list — better to need a one-line update when a new tool is added than to have the regression test silently miss tools.

</locked_decisions>

- **No changes to `execute()` logic in any tool.** The runtime validation in delegate_task::execute() at line 763 is the load-bearing correctness layer; leave it alone.
- **No per-provider schema rendering.** Don't introduce conditional schema generation based on the active LLM provider — too large; runtime fallback covers correctness.
- **No changes to the kanban crate or any 36.3.7.x source.** This phase is `ironhermes-tools` only.
- **No changes to the tool trait / registration interface.** The `Tool::schema()` method signature stays as-is.
- **No rename or restructure of `delegate_task` beyond the schema change.** The struct, the tool name, the file location, all stay.
- **No fix expansion if the audit grep finds zero additional hits.** Stop at delegate_task. If the audit finds more, surface them as named bugs and halt; do NOT silently expand.
- **No new tools.** This phase fixes existing tools' schemas; it does not add capabilities.
- **No documentation overhaul of `ironhermes-tools`.** Comments in delegate_task.rs around the removed `oneOf` should be updated to point at the runtime validation as the correctness layer + property descriptions as the LLM signal; nothing broader.

</scope_fences>
