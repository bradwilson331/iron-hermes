# Phase 36.3.7.5 — Gateway Notifier — VERIFICATION Report

**Phase Goal:** Ship the v1-NOTE-deferred gateway notifier per `docs/kanban/reference.md` §703 + §759-773. When `/kanban create "…"` runs from the gateway (Telegram / Discord / Slack), the originating chat auto-subscribes to the new task. A background polling loop in the gateway runner reads `task_events` every few seconds and delivers ONE plain-text message per terminal event (`completed`, `blocked`, `gave_up`, `crashed`, `timed_out`) to each subscribed chat. Subscriptions live in a new `kanban_subscriptions` table (6th table in the existing `kanban.db`) and auto-remove after the first terminal-event delivery attempt. Explicit operator CLI (`hermes kanban notify-{subscribe,list,unsubscribe}`) covers cron / script callers. `--json` callers of `/kanban create` skip auto-subscribe per reference.md:718. The notifier loop spawn is GATED on `kanban.notification_sources = Some(non_empty)` AND at least one platform in that list being enabled in `gateway.platforms` (default-off preserved).

**Verdict:** **PASS** — all 12 phase-level gates from `36.3.7.5-PLAN.md` + the implicit crate-isolation gate are materially observable in the codebase; all bilateral-tracing producer/consumer pairs cite both ends in their respective SUMMARIES; all 8 locked CONTEXT decisions are observable at the file:line level; all 12 scope-fences upheld; keystone lifecycle e2e test passes end-to-end.

## 6. Forward Notes (load-bearing for downstream phases)

These items are NOT verification failures — they are intentional forward-compatibility notes surfaced for future phases.

1. **Discord/Slack adapter coverage gap in send_fn closure (documented forward-compat).** Per Plan 03 SUMMARY decision row 4 + the runner's `build_adapter_snapshot`, only the Telegram adapter `Arc` is retained as a runner-scope `Arc`. Discord and Slack adapters are constructed inside their own spawned tasks (Serenity Context for Discord; socket-mode runner for Slack) and are not retained. As a result, subscriptions naming `discord` or `slack` will hit the `"platform {} not enabled in gateway"` arm of `build_notifier_send_fn` and the notifier will log+drop per D-log-and-drop-on-fail.
