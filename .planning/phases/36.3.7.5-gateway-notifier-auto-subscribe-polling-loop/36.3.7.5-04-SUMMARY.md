## Scope-Expansion Audit

CONTEXT.md narrative assumed `cmd_kanban` already had a Create arm AND
`CommandContext` already carried `chat_id` / `thread_id`. Neither existed. Plan
04 absorbed the scope expansion gracefully:

1. **CommandContext extension** (~30 LOC): 3 new optional fields + 2 new
   builders + 1 new trait + 1 new boundary type. Purely additive; no existing
   field or builder churn. Forward-compatible — future `/kanban comment`,
   `/kanban complete`, etc. arms can land on the same `KanbanStoreWriter` trait
   without churn.

2. **cmd_kanban Create arm** (~80 LOC): new `Some("create")` arm + `"create"`
   removed from `DEFERRED_KANBAN_SUBVERBS`. Parses `title` + `--assignee` +
   `--json` from the slash-arg slice; calls `writer.create_task_simple`;
   on success, conditionally calls `writer.append_subscription` per the
   D-json-skips-auto-subscribe locked decision. Auto-subscribe failures
   log+drop (per the dispatcher/notifier failure-handling parallel) so the
   task is never lost to a flaky kanban DB.

3. **Architectural delta from CONTEXT.md plan:** `KanbanStoreWriterImpl` lives
   in **`ironhermes-kanban`**, NOT `ironhermes-cli` as the original plan
   envisioned. Reason: `ironhermes-cli` already depends on `ironhermes-gateway`
   (the gateway is a build target the cli can launch), so a gateway → cli dep
   would be circular. Moving the impl to `ironhermes-kanban` (already a gateway
   dep) breaks the cycle while keeping the trait in `ironhermes-core`. The cli
   crate still re-exports the impl from `kanban/mod.rs` for ergonomic
   discoverability — zero behavior change for any third-party importer.

## Threat-Model Audit

The Plan 04 threat model (1 mitigate + 4 accept rows in PLAN.md `<threat_model>`)
is honored at the code+test level:

- **T-36.3.7.5-04-01 (Spoofing / forged chat_id on `notify-subscribe`):** `accept`.
  Same trust model as existing `hermes kanban` verbs — operator authenticated
  by OS user / shell session. CLI verbs are operator-only.
- **T-36.3.7.5-04-02 (Tampering / `--json` flag bypass):** `accept`. `--json`
  is a hint, not a security boundary. Explicit `notify-subscribe` works after
  the fact.
- **T-36.3.7.5-04-03 (Info Disclosure / cross-tenant subscription leak):**
  `accept`. v1 has no tenant scoping on subscriptions per CONTEXT.md scope-fence.
- **T-36.3.7.5-04-04 (EoP / gateway gets write access where v1 only had read):**
  **mitigated.** New write path is gated on `ctx.kanban_store_writer.is_some()`.
  CLI-only path (no gateway) doesn't attach the writer, so `/kanban create` from
  a non-gateway session returns "writer not configured". Asserted by the absence
  of writer-wiring in non-gateway CommandContext build sites (TUI / classic
  shell / batch CLI).
- **T-36.3.7.5-04-05 (Repudiation / auto-subscribe lacks user-id linkage):**
  `accept`. Originating chat IS the user identifier in the gateway context.
