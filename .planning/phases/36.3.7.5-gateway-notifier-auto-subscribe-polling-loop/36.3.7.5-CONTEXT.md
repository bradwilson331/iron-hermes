<domain>
## Phase Boundary

This is the v1-deferred gateway notifier — the closure of the "I created a task from the gateway, tell me when it's done" loop. Three integration points exist already and bound the scope:

1. **`notification_sources` config key reserved** at `crates/ironhermes-kanban/src/config.rs:14, 63, 76, 123`. `Option<Vec<String>>` of platform identifiers (e.g., `["telegram", "discord"]`). Currently always `None`; default left as None to preserve "off unless explicitly opted in" semantics. This phase populates the key's behavior, NOT the schema.
2. **Gateway send paths exist on every platform.** `PlatformAdapter::send_message(chat_id, content, thread_id)` is implemented by `TelegramAdapter`, `DiscordAdapter`, `SlackAdapter` (the 3 platforms shipped from Phase 34). The notifier consumes the adapter trait; it does NOT touch platform-specific code.
3. **Gateway runner's `join_set` is the established spawn point.** `crates/ironhermes-gateway/src/runner.rs:1278` shows the canonical pattern: `join_set.spawn(async move { ironhermes_kanban::run_dispatch_loop(dispatcher_ctx, kanban_cancel).await; });`. The notifier spawn mirrors this exactly, alongside the dispatcher.

**Subscription persistence.** A new SQLite table `kanban_subscriptions` lives in the same database as `tasks` / `task_events` (no new DB file; just a 6th table joining the existing 5). Auto-removed on terminal events. Indexed for the two query patterns: "all subscriptions for a task" (notifier delivery path) and "all subscriptions for a (platform, chat_id)" (CLI `notify-list --chat` / unsubscribe).

**Terminal-event set** (per `docs/kanban/reference.md:705`): `completed`, `blocked`, `gave_up`, `crashed`, `timed_out`. The notifier delivers ONE message per terminal event per subscription, then deletes the subscription (the auto-remove on terminal events). Per-message format includes the first line of `summary` on `completed` (per reference.md:714).

**Reclaimed events are NOT in the terminal set** — they signal a runtime hiccup but the task continues. The notifier ignores them (does not send a message). This makes 36.3.7.4 a recommended-but-not-required dependency; if 36.3.7.4 hasn't shipped yet, the notifier still works because reclaim isn't a delivery event.

**Auto-subscribe scope** (per reference.md:701-718, §763):
- Triggered ONLY when `/kanban create "…"` runs through the gateway (not from terminal `ironhermes kanban create`, since there's no chat to subscribe).
- Source of the subscription: the originating chat's `(platform, chat_id, thread_id)` tuple, available in the `CommandContext` that `cmd_kanban` already receives (per Phase 36.3.7.0-02 wiring).
- Skipped if `--json` flag is present on `kanban create` (machine-output callers manage subscriptions explicitly per reference.md:718).

**Explicit CLI surface** (per reference.md:597-600 + §765-773):
```
kanban notify-subscribe <task-id> --platform <P> --chat-id <C> [--thread-id <T>]
kanban notify-list [<task-id>] [--json]
kanban notify-unsubscribe <task-id> [--platform <P>] [--chat-id <C>]
```
- `notify-subscribe` adds a row with `source='explicit'` (vs. `'auto'` from auto-subscribe).
- `notify-list` without a task_id lists all subscriptions; with a task_id filters to that task. `--json` for scripting.
- `notify-unsubscribe` without platform/chat-id removes ALL subscriptions for the task (operator emergency); with filters scopes down.

  1. Query `task_events` for terminal events (kind IN ('completed','blocked','gave_up','crashed','timed_out')) NEWER than the last-poll watermark.
  2. For each event, look up subscriptions for the task.
  3. Format message per reference.md:707-716 (e.g., `"✓ t_<id> completed by <assignee>\n<summary-first-line>"` for completed; `"⚠ t_<id> blocked: <reason>"` for blocked; etc.).

  5. After all subscriptions for a task have been delivered (any non-retry failure → log + drop, OR retry per a fixed back-off — locked decision in planning), remove the subscriptions for that task (auto-remove on terminal).
  6. Advance the watermark to the latest event_id processed.

<locked_decisions>
## Locked Decisions

### Table name + schema

**Decision:** Single new SQLite table `kanban_subscriptions` in the existing `kanban.db`. Columns:
```sql
CREATE TABLE kanban_subscriptions (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id     TEXT NOT NULL,
    platform    TEXT NOT NULL,           -- 'telegram' | 'discord' | 'slack' (string for forward-compat with future platforms)
    chat_id     TEXT NOT NULL,
    thread_id   TEXT NOT NULL DEFAULT '', -- '' = no thread; canonical empty-string substitution for the UNIQUE constraint
    source      TEXT NOT NULL CHECK (source IN ('auto', 'explicit')),
    created_at  REAL NOT NULL,
    UNIQUE (task_id, platform, chat_id, thread_id)
);
CREATE INDEX idx_subs_task_id ON kanban_subscriptions (task_id);
CREATE INDEX idx_subs_chat ON kanban_subscriptions (platform, chat_id, thread_id);
```

Empty-string `thread_id` (not NULL) chosen to keep the UNIQUE constraint simple — SQLite UNIQUE treats NULL as distinct. Forward-compat: all 4 existing platforms in scope use `thread_id` only on Telegram super-groups; Discord/Slack pass `""`.

**Rejected alternative:** Separate `chats` + `subscriptions` tables with a foreign key. Rejected — premature normalization for v1; the duplication is bounded (few users × few platforms × few tasks).

### Send-closure injection pattern

**Decision:** `run_notifier_loop(ctx, send_fn, cancel_token)` takes a `Arc<dyn Fn(platform, chat_id, thread_id, message) -> BoxFuture<Result<()>> + Send + Sync>` (or equivalent — exact bounds at planning). The gateway injects a closure that fans out to the right `PlatformAdapter::send_message` based on the `platform` argument.

**Rationale:** Keeps the `ironhermes-kanban` crate FREE of any dependency on `ironhermes-gateway`. The kanban crate publishes the notifier; the gateway crate wires it up. Same pattern as the existing dispatcher's `spawn_fn` injection.

**Rejected alternative:** Put the notifier in the gateway crate. Rejected — the polling logic needs `KanbanStore` + event-kind enums; pulling those into the gateway would invert the dependency.

### Watermark — in-memory for v1

**Decision:** The notifier loop maintains an in-memory `last_event_id: i64` watermark. On startup, it initializes to `MAX(event_id) FROM task_events` (i.e., "everything before this moment was already delivered or doesn't matter"). This means tasks completed during a gateway downtime are NOT notified.

**Rationale:** v1 cost/benefit — persistent watermark would require schema + concurrency reasoning (what if two notifier loops run? what if a tick crashes mid-delivery?). Skip for v1; add if delivery-loss is observed.

**Rejected alternatives:**
- Persistent watermark in a `kanban_meta` table. Rejected — more surface area for v1.
- Watermark = `created_at` of the most recent subscription. Rejected — doesn't handle the "subscription created BEFORE the terminal event" lifecycle correctly.

### Failed-delivery handling — log + drop (no retry)

**Decision:** If `send_fn` returns `Err(_)`, the notifier logs one warning line (`event="notification_failed" task_id=... platform=... chat_id=..."`) and proceeds. The subscription is STILL removed (auto-remove on terminal delivery attempt, even if the attempt failed). This avoids unbounded retry loops + stuck subscriptions.

**Rationale:** v1 simplicity. The gateway's send_message already has per-platform retry/backoff (Telegram explicitly). At the notifier layer, retries would compound.

**Rejected alternatives:**
- Persistent retry queue. Rejected — too much state for v1.
- Idempotent re-poll on the same event. Rejected — would require watermark roll-back logic.

### `--json` flag skips auto-subscribe

**Decision:** `cmd_kanban` Create branch checks the `--json` boolean. If true, the auto-subscribe hook is SKIPPED. Matches reference.md:718 verbatim contract. Explicit operators (`notify-subscribe`) still work after the fact.

**Rationale:** The reference doc is explicit: scripted callers manage subscriptions explicitly. This avoids surprising a cron job with notification spam.

### Gateway-gating of the notifier loop

**Decision:** Notifier loop is spawned IFF:
1. `kanban.notification_sources` is `Some(non_empty_vec)`, AND
2. At least one platform in that list is enabled in the gateway's platform config (the existing `gateway.platforms` machinery)

If both true, spawn. If either false, log a single one-line "notifier disabled (reason: …)" at gateway startup and don't spawn. Operator can flip the gate by editing config.

**Rationale:** Default-off matches the v1-NOTE semantics + minimizes risk of unexpected DM spam to operators who haven't opted in. The reservation comment in `config.rs:14` aligns with this default-off behavior.

### Single-DB, no new file

**Decision:** Subscriptions live in the existing `kanban.db` next to `tasks` / `task_events` (6th table). No separate DB file, no new connection pool.

**Rejected alternatives:**
- Separate `kanban_subscriptions.db`. Rejected — same lifecycle as kanban.db; separation buys nothing and complicates the migration story.

### Auto-remove timing — after terminal-event delivery attempt

**Decision:** Subscription is removed AFTER the notifier attempts to send the terminal-event message (success OR fail per the locked decision above). Specifically: the notifier loops `for sub in list_subscriptions_for_task(task_id): send_fn(...).await; then remove_all_subscriptions_for_task(task_id)`. No race window where a second poll re-delivers because removal is in the same tick as send.

**Rationale:** "Auto-remove themselves on terminal events" is the reference.md contract. Removal AFTER attempt (not before) ensures we don't lose the subscription on a transient panic between "list" and "send".

</locked_decisions>

<scope_fences>
## Scope Fences

- **No platform-specific message formatting.** All deliveries use plain-text `send_message` regardless of platform's rich-UI capabilities.
- **No subscription filtering by event kind.** v1 is all-or-nothing per subscription.
- **No multi-tenant access control on subscriptions.** Inherited from `cmd_kanban`'s existing tenant filter; no new tenant logic here.
- **No web push / email / SMS / non-gateway channels.** v1 ships gateway-only.
- **No persistent watermark.** In-memory; gateway downtime can lose notifications. Acceptable for v1.
- **No retry on send_fn failure.** Log + drop subscription.
- **No backfill of pre-existing tasks.** Subscriptions are forward-only from this phase's deployment.
- **No expansion of `notification_sources` schema beyond `Vec<String>`.** Per-source filters / per-source quiet-hours / etc. all deferred.
- **No new `KanbanEventKind` variants.** Reuse the existing terminal set.
- **No change to the dispatcher's existing event-append shape.** The notifier reads `task_events`; it does NOT mutate the dispatcher's emission patterns.
- **No `kanban_heartbeat` / `kanban_link` / `kanban_unblock` LLM tools.** Separate phases.
- **No worktree branches.** Develop-direct, inline orchestrator (per cwd-drift lesson from Phase 36.3.7.1).

</scope_fences>
