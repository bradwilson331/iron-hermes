# Phase 36.3.7.5 — Gateway notifier: auto-subscribe + polling loop + notify-{subscribe,list,unsubscribe} verbs

## Phase Goal

Ship the v1-NOTE-deferred gateway notifier per `docs/kanban/reference.md` §703 + §759-773.
When `/kanban create "..."` runs from the gateway (Telegram / Discord / Slack), the originating
chat auto-subscribes to the new task. A background polling loop in the gateway runner reads
`task_events` every few seconds and delivers ONE plain-text message per terminal event
(`completed`, `blocked`, `gave_up`, `crashed`, `timed_out`) to each subscribed chat. Subscriptions
live in a new `kanban_subscriptions` table (6th table in the existing `kanban.db`) and
auto-remove after the first terminal-event delivery attempt. Explicit operator CLI
(`hermes kanban notify-{subscribe,list,unsubscribe}`) covers cron / script callers. `--json`
callers of `/kanban create` skip auto-subscribe per reference.md:718. The notifier loop spawn
is GATED on `kanban.notification_sources = Some(non_empty)` AND at least one platform in that
list being enabled in `gateway.platforms` (default-off preserved).

This phase is **bilateral-tracing-by-construction**: every BUG ships its producer (the
write / spawn / handler arm) AND its consumer (the test that drives it) in the SAME plan.
No producer-only plans; no test-only plans. Per LEARNINGS 2026-05-29.

## Critical scope-fence: kanban crate MUST NOT depend on gateway crate

Locked in CONTEXT.md. The notifier loop accepts an injectable closure
`send_fn: Arc<dyn Fn(platform: &str, chat_id: &str, thread_id: Option<&str>, message: &str)
-> BoxFuture<Result<()>> + Send + Sync>`. The gateway runner constructs this closure at spawn
time by capturing its `Arc<dyn PlatformAdapter>` set and routing on the `platform` arg. The
kanban crate publishes the notifier signature; the gateway crate wires it to the adapter
trait. Same pattern as the existing dispatcher's `spawn_fn` injection at
`crates/ironhermes-kanban/src/dispatcher.rs:99-112`.

## Architectural decision the planner had to resolve

**Auto-subscribe attach point (BUG-06) requires extending two structures that the CONTEXT.md
author assumed were already in place:**

1. `ironhermes_core::commands::context::CommandContext` does NOT carry `chat_id` /
   `thread_id` fields — only `platform`, `session_id`, `agent_running`. **Plan 04 extends
   it** with `chat_id: Option<String>` + `thread_id: Option<String>` + a builder method
   `with_chat_origin(chat_id, thread_id)`. The gateway's `handle_slash_command` at
   `crates/ironhermes-gateway/src/handler.rs:430` is the construction site that gets
   updated to call `.with_chat_origin(event.chat_id.clone(), event.thread_id.clone())`
   (verify field names against MessageEvent at planning time; both exist on the gateway
   event struct).

2. `cmd_kanban` in `crates/ironhermes-core/src/commands/handlers.rs:1150` currently only
   handles `list/show/tip`. `create` is in `DEFERRED_KANBAN_SUBVERBS` (line 1145) and
   routes to `deferred_subverb_message`. **Plan 04 ALSO** removes `"create"` from the
   deferred list, adds a `Some("create")` arm in `cmd_kanban` that takes `[title, ...flags]`,
   calls a NEW write-capable trait `KanbanStoreWriter` (sibling of the existing
   `KanbanStoreReader`), and on success invokes the auto-subscribe hook iff CommandContext
   has `chat_id` AND `--json` was NOT passed.

3. **Scope decision (planner's authority — missing information, legitimate split reason):**
   The CONTEXT.md narrative refers to "`cmd_kanban`'s `Create` branch" as if it already
   exists. It doesn't. The cleanest closure of this phase is to BUILD that branch as part
   of BUG-06 work, since BUG-06 explicitly owns the auto-subscribe hook and the hook is
   meaningless without a `/kanban create` path. Plan 04 absorbs this gracefully (one extra
   handler arm + one new trait + builder field), avoiding a phase split. The trait extension
   is forward-compatible: future `/kanban comment`, `/kanban complete`, etc. arms can land
   on the same `KanbanStoreWriter` trait without churn.

## Worktree / parallelization strategy

**Decision: develop-direct, inline orchestrator. NO worktrees.** Per CONTEXT.md scope-fence
("No worktree branches. Develop-direct, inline orchestrator (per cwd-drift lesson from
Phase 36.3.7.1)").

Wave 1 plans (01 + 02) are file-disjoint and can be executed back-to-back in the same
session without conflict. Plan 01 touches `schema.rs`, `store.rs`, `types.rs`, `lib.rs`
(re-export block). Plan 02 touches new `notifier.rs`, `config.rs`, `lib.rs` (different
re-export block). The only file overlap is `lib.rs`, where the inserts go in DIFFERENT
re-export sections — sequential execution avoids a merge entirely. Convention: Plan 01
first, Plan 02 second (subscription store must exist before the notifier reads it).

Wave 2 plans (03 + 04) are independent of each other but both depend on Wave 1 outputs.
Run 03 first (gateway spawn — narrower), then 04 (CLI + slash + auto-subscribe — broader).

## Scope fences (binding on all 4 plans)

- **No `ironhermes-kanban` → `ironhermes-gateway` dep.** The notifier accepts an injected
  closure; the gateway constructs the closure at spawn time.
- **No new DB file.** Subscriptions land in the existing `~/.ironhermes/kanban.db` as a 6th
  table next to `tasks` / `task_events` / `task_runs` / `task_links` / `task_comments`.
- **No persistent watermark.** In-memory `last_event_id: i64` initialized at spawn from
  `SELECT MAX(id) FROM task_events` (locked CONTEXT decision; gateway-downtime loss accepted
  for v1).
- **No retry on `send_fn` failure.** Log + drop subscription per the locked
  "failed-delivery handling — log + drop (no retry)" CONTEXT decision.
- **No new `KanbanEventKind` variants.** Reuse the existing terminal set:
  `Completed`, `Blocked`, `GaveUp`, `Crashed`, `TimedOut` (cited by `as_str()` in
  `events.rs:84-101`).
- **No subscription filtering by event kind.** v1 is all-or-nothing per subscription.
- **No platform-specific rich formatting.** All deliveries use plain-text
  `PlatformAdapter::send_message(chat_id, content, thread_id)` at `adapter.rs:27-32`.
- **No reclaim-as-terminal-event delivery.** `Reclaimed` is a runtime hiccup; notifier
  ignores it. Phase 36.3.7.4's `Reclaimed` event append is still load-bearing for the
  event audit trail; just not for v1 notifier delivery.
- **No change to the dispatcher's existing event-append shape.** Notifier READS
  `task_events`; it does NOT mutate dispatcher emission.
- **No `kanban_heartbeat` / `kanban_link` / `kanban_unblock` LLM tools.** Out of scope per
  CONTEXT.md "Out of scope" bullet.
- **No backfill of subscriptions for pre-existing tasks.** Forward-only from this phase's
  deployment.
- **No expansion of `notification_sources` schema beyond `Vec<String>`.**
- **No worktrees, no separate branches.** Develop-direct inline.
