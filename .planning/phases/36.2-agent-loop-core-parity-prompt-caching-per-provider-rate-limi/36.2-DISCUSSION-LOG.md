## Per-provider rate-limit tracker

### Q1 — Telemetry source: where does the tracker get its rate-limit signal?

| Option | Description | Selected |
|--------|-------------|----------|
| Response headers when available, 429 fallback otherwise (Recommended) | Parse `x-ratelimit-*` from Anthropic + OpenRouter. Fall back to reactive 429 counting where headers absent. | ✓ |
| Headers only — ignore providers that don't expose them | Simpler, no reactive logic. Visible coverage gaps for Ollama/custom. | |
| Reactive 429-counting only | Provider-agnostic; loses real remaining-budget info. Cheapest. | |

**User's choice:** Headers when available, 429 fallback otherwise.
**Notes:** Captured as D-RL-01. Closest to hermes-agent's nous_rate_guard.py pattern.

### Q2 — Tracking key granularity: what's the per-key/per-provider unit?

| Option | Description | Selected |
|--------|-------------|----------|
| (provider, api_key_hash) (Recommended) | Matches Anthropic's per-key buckets. Covers v2.2 AUTH-01 credential pool case. | |
| (provider, model) | Some providers bucket by model class. Per-model accuracy; misses per-key reality. | |
| (provider, api_key_hash, model) | Both axes. Most accurate; biggest map; closest to Anthropic's actual quota model. | ✓ |

**User's choice:** (provider, api_key_hash, model).
**Notes:** Captured as D-RL-02. The user picked the three-axis option over the recommendation. Anthropic separates Opus/Sonnet/Haiku into independent quota buckets, so per-model resolution matters.

### Q3 — Action on near-limit: what does the tracker DO?

| Option | Description | Selected |
|--------|-------------|----------|
| Log + emit structured event; AgentLoop decides (Recommended) | Tracker emits `RateLimitEvent`; AgentLoop consumes (90% → hint, post-429 → fallback). Separation of concerns. | ✓ |
| Tracker triggers fallback directly | Tightest coupling; smallest LOC; least observable from outside. | |
| Tracker just logs; no action | Pure observability. Existing 429 → classify_llm_error → fallback keeps working. | |

**User's choice:** Log + structured event channel.
**Notes:** Captured as D-RL-03. Tracker measures; AgentLoop reacts.

### Q4 — Crate home: where does the tracker module live?

| Option | Description | Selected |
|--------|-------------|----------|
| New module in `ironhermes-agent` (Recommended) | Lives next to agent_loop.rs. Avoids a new crate. In-memory (Tokio Mutex<HashMap>). | ✓ |
| New `ironhermes-providers` crate | Cleaner separation but new crate for one phase. | |
| `ironhermes-core::rate_limit` | Risk: muddles with gateway user-rate-limiter RateLimitConfig already in core/config.rs. | |

**User's choice:** New module in `ironhermes-agent`.
**Notes:** Captured as D-RL-04.

## Usage & cost accounting ledger

### Q1 — Pricing source: where do USD prices come from?

| Option | Description | Selected |
|--------|-------------|----------|
| Static table mirroring ModelRegistry, refreshable via CLI (Recommended) | Static `pricing.toml` + `hermes pricing refresh` (models.dev / OpenRouter). Disk cache at `$HERMES_HOME/pricing-cache.json`. Offline by default. | ✓ |
| Live API fetch on first use, then disk cache (TTL 24h) | No static table. First-call latency; fails open on offline. | |
| Token counts only — no USD pricing this phase | Defer USD entirely. Closes the ledger gap without pricing maintenance. | |

**User's choice:** Static table + refresh CLI.
**Notes:** Captured as D-USAGE-01. Direct port of Phase 21.3's ModelRegistry precedence pattern (disk cache > static > fallback).

### Q2 — Ledger storage: where do usage records live?

| Option | Description | Selected |
|--------|-------------|----------|
| Extend existing sessions columns + new `usage_events` table (Recommended) | Keep session aggregates; add per-turn rows for forensics. Best of both. | ✓ |
| Sessions columns only (extend in place) | Cheapest schema change; loses forensics. | |
| New `usage_events` table only (drop session aggregates) | Cleaner normalization; every `/usage` query is a GROUP BY. | |

**User's choice:** Both — extend sessions cols AND add `usage_events`.
**Notes:** Captured as D-USAGE-02. Per-turn `usage_events` insert + `sessions` increment land in the same transaction.

### Q3 — Surfacing: how does the user see usage? (multi-select)

| Option | Description | Selected |
|--------|-------------|----------|
| `/usage` slash command (Recommended) | On-demand via CommandRouter. Multi-platform: CLI, TUI, gateway, web UI. | ✓ |
| Status-bar live counter (TUI + web UI) | Persistent display. Adds tick subscription. | ✓ |
| Per-turn debug log line | `tracing::info!` at turn end. Power-user forensics. | ✓ |

**User's choice:** All three.
**Notes:** Captured as D-USAGE-03. Three independent surfaces all ship in this phase.

### Q4 — Aggregation grain: what's the smallest tracked unit?

| Option | Description | Selected |
|--------|-------------|----------|
| Per-turn (with rollups for session/day/provider) (Recommended) | Each LLM call writes one row. Rollups via SQL. Most flexibility. | ✓ |
| Per-session only | Cheapest; loses per-turn detail. | |
| Per-call AND per-(subagent path) | Per-turn rows + parent_call_id linkage. Best fidelity for subagent-heavy workloads. | |

**User's choice:** Per-turn with rollups.
**Notes:** Captured as D-USAGE-04.

## Error classification taxonomy depth

### Q1 — Taxonomy shape: how much depth do we add to the existing classifier?

| Option | Description | Selected |
|--------|-------------|----------|
| Typed `ProviderError` enum, keep tuple as facade (Recommended) | New enum with payloads; existing `(bool, bool)` becomes a `From` impl. Zero churn for 12+ existing tests. | ✓ |
| Typed enum, replace tuple entirely | Cleaner; touches every call site (~5). | |
| Keep tuple, add a thin `ProviderErrorKind` label only | Cheapest evolution; loses `retry_after` and per-variant context. | |

**User's choice:** Typed enum, tuple as facade.
**Notes:** Captured as D-ERR-01.

### Q2 — Cross-system integration: does the new taxonomy feed Rate-limit tracker (#2) and Usage ledger (#3)?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — ProviderError is the canonical classification source (Recommended) | Single source of truth across the 3 sub-systems shipped this phase. | ✓ |
| No — taxonomy is local to classify_llm_error | Less coupling; some duplication. | |
| Partial — Rate-limit tracker yes, ledger no | Couples where it pays off; keeps ledger schema clean. | |

**User's choice:** Yes — canonical source.
**Notes:** Captured as D-ERR-02. RateLimitTracker destructures `RateLimited{retry_after}`; `usage_events.error_kind` records the variant name on failures.

### Q3 — Refactor scope: how invasive is the change?

| Option | Description | Selected |
|--------|-------------|----------|
| Additive — wrap existing helper, keep old tests verbatim (Recommended) | Add `classify_llm_error_typed`; old `classify_llm_error` delegates via `.into()`. Zero test churn. | ✓ |
| Replace in place — update existing call sites + tests | Single classifier; bigger PR. | |
| Greenfield module — deprecate the old fn | Most flexibility; risks two paths coexisting indefinitely. | |

**User's choice:** Additive.
**Notes:** Captured as D-ERR-03. Lowest blast radius; preserves the 12+ existing tests in agent_loop.rs and the invariants_27_1_4_1_1.rs grep gate.

### Q4 — Test coverage strategy: how do we prove the taxonomy is complete?

| Option | Description | Selected |
|--------|-------------|----------|
| Port hermes-agent's error_classifier.py test cases (Recommended) | Read `/Users/twilson/code/hermes-agent/agent/error_classifier.py` + tests; mirror in Rust. Best parity guarantee. | ✓ |
| Variant-coverage table only — one test per enum variant | Smaller test set; faster to write; lower fidelity. | |
| Property-based fuzzing of error strings | Most paranoid; biggest infra cost. | |

**User's choice:** Port hermes-agent's test cases.
**Notes:** Captured as D-ERR-04. Property-based fuzzing deferred.
