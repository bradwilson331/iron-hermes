## Summary

Phase 36.2 closes four parity gaps in IronHermes's agent loop against hermes-agent v0.14.0. All five upstream Python source files exist and were read in full. All Rust call sites cited in CONTEXT.md were grep-verified — the line numbers are accurate within a few lines (see corrections below).

The four sub-systems are well-understood and additive. The most important discoveries are: (1) Anthropic's rate-limit response headers use the `anthropic-ratelimit-*` prefix, **not** the `x-ratelimit-*` prefix that the Python `rate_limit_tracker.py` tracks — the Python tracker targets Nous/OpenRouter, not Anthropic natively; this must be addressed in the Rust implementation; (2) the `AnthropicUsage` struct in `anthropic_client.rs` currently only has `input_tokens` and `output_tokens` — the `cache_read_input_tokens` and `cache_creation_input_tokens` that appear as `None` in the `Usage` wrapper are in the outer OpenAI-compat `Usage` struct, not in `AnthropicUsage`; populating them requires extending `AnthropicUsage` first; (3) the `/usage` command already exists in the dispatch table as a `todo_stub` returning "No token cost tracking" — wire-up is straightforward; (4) blake3 is NOT in the Cargo.lock; sha2 0.10.9 IS present across multiple crates — the planner should use sha2/SHA-256 truncated for `api_key_hash`.

**Primary recommendation:** Build in wave order — D-ERR first (pure additive, no deps), then D-RL + D-CACHE in parallel (both need ProviderError), then D-USAGE last (needs schema migration and the other three). Validate each wave before merging.

### Anti-Patterns to Avoid

- **Storing api_key_hash as a `String` in logs:** BLAKE3/SHA-256 hash bytes are for HashMap keys only. Never serialize cleartext key or even hash to tracing logs.
- **Creating a new `ironhermes-providers` crate:** D-RL-04 explicitly prohibits this. Tracker lives in `ironhermes-agent`.
- **Touching `crates/ironhermes-core/src/config.rs` `RateLimitConfig`:** This is the gateway user rate-limiter at lines 812-829. DO NOT TOUCH. The per-provider tracker is a wholly separate concept in `ironhermes-agent`.
- **Using `f64` for cost amounts:** Float drift. Use `i64` microdollars (1 USD = 1_000_000) in SQLite and in Rust structs.
- **Writing the `usage_events` INSERT outside the session UPDATE transaction:** Must be atomic — both writes in a single SQLite transaction per D-USAGE-02.
- **Adding `cache_control` to both AnthropicMessages and ChatCompletions arms of AnyClient:** Only the `AnthropicMessages` arm gets cache_control in wave 1/2. ChatCompletions arm is wave-3 OpenRouter stretch only.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTTP header parsing | Custom header string parser | `reqwest::Response::headers()` + existing `lowered` pattern from Python | Headers are case-insensitive per RFC 7230; the Python tracker already handles this correctly |
| Currency arithmetic | `f64` cost calculation | `i64` microdollar integers (1 USD = 1_000_000) | Float drift accumulates; SQLite stores INTEGER cleanly |
| API key hashing | Custom hash | `sha2::Sha256` (already in Cargo.lock 0.10.9) | Cryptographically safe truncation; already available |
| Disk cache I/O | Custom file format | Mirror `models_cache.rs` (serde_json pretty-print + `get_hermes_home()`) | Established pattern, tested, handles concurrent readers correctly |

| Broadcast channel for rate-limit events | Custom MPMC queue | `tokio::sync::broadcast::channel` | Already in tokio dep; fits the fan-out to AgentLoop + future subscribers |

### 2. `rate_limit_tracker.py` (~247 lines)

**Key types:**
- `RateLimitBucket` — `limit, remaining, reset_seconds, captured_at`; computed props `used`, `usage_pct`, `remaining_seconds_now`
- `RateLimitState` — four buckets (requests_min, requests_hour, tokens_min, tokens_hour) + `captured_at` + `provider`
- `parse_rate_limit_headers(headers, provider)` → `Optional[RateLimitState]`
- `format_rate_limit_display(state)` / `format_rate_limit_compact(state)` — output formatters

**Header names tracked by Python tracker (Nous/OpenRouter format — `x-ratelimit-*`):**

| Header | Meaning |
|--------|---------|
| `x-ratelimit-limit-requests` | RPM cap |
| `x-ratelimit-limit-requests-1h` | RPH cap |
| `x-ratelimit-limit-tokens` | TPM cap |
| `x-ratelimit-limit-tokens-1h` | TPH cap |
| `x-ratelimit-remaining-requests` | requests left in minute window |
| `x-ratelimit-remaining-requests-1h` | requests left in hour window |
| `x-ratelimit-remaining-tokens` | tokens left in minute window |
| `x-ratelimit-remaining-tokens-1h` | tokens left in hour window |
| `x-ratelimit-reset-requests` | seconds until minute request window resets |
| `x-ratelimit-reset-requests-1h` | seconds until hour request window resets |
| `x-ratelimit-reset-tokens` | seconds until minute token window resets |
| `x-ratelimit-reset-tokens-1h` | seconds until hour token window resets |

**Window-decay algorithm:** `remaining_seconds_now = max(0, reset_seconds - (now - captured_at))` — a simple linear decay from the captured value. No server re-sync between requests; stale after a new response arrives and replaces the state.

**Threshold for warning:** `usage_pct >= 80%` triggers display warning. CONTEXT.md uses `remaining < 10%` for `Warning` severity — effectively the same threshold (90% used = 10% remaining = 80%+ used_pct maps to `Warning`).

**Exhausted bucket definition (from `nous_rate_guard.py`):** `remaining == 0` AND `reset_window >= 60s`. Values with reset < 60s are treated as transient upstream jitter, not genuine quota exhaustion. This is the breaker-trip condition for the cross-session guard — not needed in Phase 36.2 (in-memory only), but important for the `is_genuine_nous_rate_limit` logic the Rust tracker should mirror for the `Critical` severity level.

### 3. `nous_rate_guard.py` (~326 lines)

**The Python `rate_limit_tracker.py` uses `x-ratelimit-*` headers** (Nous Portal / OpenRouter / OpenAI-compat format).

**Anthropic's actual response headers use `anthropic-ratelimit-*` prefix**, NOT `x-ratelimit-*`. [VERIFIED: Anthropic docs fetched 2026-05-25]

### Anthropic Native Headers

| Header | Value | Units |
|--------|-------|-------|
| `anthropic-ratelimit-requests-limit` | integer | max requests per rate period |
| `anthropic-ratelimit-requests-remaining` | integer | requests left before rate limited |
| `anthropic-ratelimit-requests-reset` | RFC 3339 datetime | when request limit fully replenished |
| `anthropic-ratelimit-tokens-limit` | integer | max tokens per rate period |
| `anthropic-ratelimit-tokens-remaining` | integer (rounded to nearest 1K) | tokens left |
| `anthropic-ratelimit-tokens-reset` | RFC 3339 datetime | when token limit fully replenished |

| `anthropic-ratelimit-output-tokens-remaining` | integer (rounded to nearest 1K) | output tokens left |
| `anthropic-ratelimit-output-tokens-reset` | RFC 3339 datetime | when output token limit replenished |
| `retry-after` | seconds (float) | wait before retry on 429 |

**Important:** Anthropic reset values are RFC 3339 timestamps (absolute), not seconds-from-now (relative). The Python tracker uses seconds-from-now (`reset_seconds`). The Rust tracker must parse RFC 3339 strings and compute `reset_at: Option<SystemTime>`.

| `x-ratelimit-remaining-requests-1h` | integer | requests left in hour window |
| `x-ratelimit-remaining-tokens` | integer | tokens left in minute window |
| `x-ratelimit-remaining-tokens-1h` | integer | tokens left in hour window |

### Provider Comparison Table

| Provider | Header Prefix | Reset Format | Two-window? |
|----------|--------------|--------------|-------------|
| Anthropic | `anthropic-ratelimit-*` | RFC 3339 datetime | No (one window, replenishes continuously via token bucket) |
| OpenRouter | `x-ratelimit-*` | seconds (float) | Yes (per-minute + per-hour) |

## Prompt Caching — Anthropic API Details

[VERIFIED: Anthropic docs fetched 2026-05-25 from platform.claude.com]

### cache_control Envelope

```json
{
  "type": "ephemeral",
  "ttl": "1h"
}
```

Valid `ttl` values: `"5m"` (default, standard pricing) and `"1h"` (2x base input price for cache writes). Only `type: "ephemeral"` is supported.

### Maximum Breakpoints

**4 breakpoints per request maximum.** Hierarchy: tools → system → messages.

### Minimum Cacheable Tokens (per model)

| Model family | Min tokens |
|-------------|------------|
| Claude Opus 4.7 / 4.6 / 4.5, Haiku 4.5 | 4,096 |
| Claude Opus 4.1, Sonnet 4.6 / 4.5 | 1,024 |
| Claude Haiku 3.5 | 2,048 |

**Important:** If the cached prefix is shorter than the minimum, Anthropic silently ignores the `cache_control` marker — no error, no cache. The `cached_layers_must_be_stable` assertion (D-CACHE-04) guards against accidental cache breaks but cannot detect this case.

### system_and_3 Strategy Implementation

CONTEXT.md calls for "system + last 3 non-system messages." Anthropic's limit is 4 total breakpoints. This maps as:

- Breakpoint 1: on the last system block (after SOUL/tool-guidance/provider/system message/MEMORY/USER snapshot/skills/context files — layers 1-8)
- Breakpoints 2-4: on the 3rd, 2nd, and 1st most-recent non-system messages in reverse order

In practice for a growing conversation, the rolling window means: attach `cache_control` on message[N-3], message[N-2], message[N-1], and the system block. Anthropic caches the prefix up to each breakpoint. The last 3 assistant-user pairs are included.

**Lookback window:** 20 blocks maximum per breakpoint. The system checks at most 20 positions backward from the breakpoint marker.

### When mixing 1h and 5m TTLs

1h entries must come BEFORE 5m entries in the request. For the system_and_3 strategy with single TTL (D-CACHE-02), this is not a concern — all markers use the same TTL.

### cache_read vs cache_creation in ITPM

For most Claude models, `cache_read_input_tokens` do NOT count toward ITPM rate limits (only uncached + cache_creation count). Exception: Claude Haiku 3.5 counts cache reads toward ITPM. This affects the rate-limit tracker's token-bucket logic: when computing tokens consumed for rate limiting, use `input_tokens + cache_creation_input_tokens`, not total prompt tokens.

## Common Pitfalls

### Pitfall 1: Anthropic Header Prefix Mismatch
**What goes wrong:** Code reads `x-ratelimit-remaining-requests` for Anthropic responses and always gets `None`.
**Why it happens:** Python tracker was written for Nous/OpenRouter. Anthropic uses `anthropic-ratelimit-*`.
**How to avoid:** Parse both prefixes based on provider; detect presence of either prefix family before concluding "no rate limit data."
**Warning signs:** RateLimitTracker always returns `RateLimitSource::Reactive429` even after successful Anthropic calls.

### Pitfall 2: Anthropic Reset as RFC 3339 (not seconds)
**What goes wrong:** `x-ratelimit-reset-*` is float seconds; `anthropic-ratelimit-*-reset` is an RFC 3339 datetime string. Parsing both as floats will panic/silently yield 0.
**Why it happens:** Different API conventions.
**How to avoid:** Branch on provider in the header parser. For Anthropic: `DateTime::parse_from_rfc3339(&val)?.timestamp()` to get a `SystemTime`.
**Warning signs:** Reset time is always epoch or panics in tests.

### Pitfall 3: AnthropicUsage Missing Cache Fields
**What goes wrong:** `cache_read_input_tokens` / `cache_creation_input_tokens` remain None in the outer `Usage` struct even after adding `cache_control` markers.
**Why it happens:** The `AnthropicUsage` inner struct only has `input_tokens` and `output_tokens`. Cache fields are never deserialized from the Anthropic response body.
**How to avoid:** Extend `AnthropicUsage` with `#[serde(default)]` cache fields BEFORE writing the cache-control request code.
**Warning signs:** Cost accounting shows $0 for cache operations; `cache_read_input_tokens` is always 0.

### Pitfall 4: Migration Version Collision
**What goes wrong:** Two separate migration blocks both check `if current < 9` — one silently clobbers the other.
**Why it happens:** PRs merged out of order, or planner writes two separate migration tasks.
**How to avoid:** The schema migration must be a single atomic block (v9). The planner should put all three `ALTER TABLE sessions ADD COLUMN` statements AND the `CREATE TABLE usage_events` in one `if current < 9` block.
**Warning signs:** `usage_events` table missing at runtime despite migration running.

### Pitfall 5: Float Cost Drift
**What goes wrong:** `0.1 + 0.2 != 0.3` accumulates across thousands of turns.
**Why it happens:** `f64` arithmetic is inexact.
**How to avoid:** Store and compute all costs as `i64` microdollars. The Python source uses `Decimal` — use `i64` in Rust as specified in D-USAGE-01/02.
**Warning signs:** Session total cost drifts from sum of per-turn costs.

### Pitfall 6: Transaction Atomicity for usage_events + sessions Update
**What goes wrong:** AgentLoop crashes after writing `usage_events` but before updating `sessions` aggregate (or vice versa).
**Why it happens:** Two separate SQL statements without an explicit transaction.
**How to avoid:** Wrap the INSERT into `usage_events` and the UPDATE on `sessions` in a single `conn.execute_batch("BEGIN; ...; COMMIT;")` or `conn.unchecked_transaction()`.
**Warning signs:** Session totals diverge from the sum of `usage_events` rows.

### Pitfall 7: input_tokens Semantics After Caching
**What goes wrong:** Cost calculation uses `response.input_tokens` as total prompt tokens and undercounts by the number of cached tokens.
**Why it happens:** Anthropic's `input_tokens` in the response = tokens AFTER the last cache breakpoint only. Total = `cache_read + cache_creation + input_tokens`.
**How to avoid:** Use `CanonicalUsage.prompt_tokens` (Python's derived property) logic: total_input = `in_tok + cache_read + cache_create`.
**Warning signs:** Cost is near-zero on cache-hit turns; cost spikes anomalously on cache-miss turns.

### Pitfall 8: Touching gateway RateLimitConfig
**What goes wrong:** Developer edits `crates/ironhermes-core/src/config.rs:812-829` thinking it's the rate-limit tracker.
**Why it happens:** Both are "rate limit" related.
**How to avoid:** The gateway `RateLimitConfig` (messages_per_minute, burst_size) is for protecting the gateway from user message floods. The per-provider tracker lives only in `ironhermes-agent`. MUST NOT TOUCH `config.rs`.
**Warning signs:** Gateway message throttling changes unexpectedly.

// Source: synthesized from D-ERR-01 + Python FailoverReason taxonomy

#[derive(Debug, Clone, PartialEq)]
pub enum ProviderError {
    RateLimited { retry_after: Option<Duration> },
    Auth,                               // 401/403 — rotate credential, fallback
    Billing,                            // 402/credit exhaustion — rotate, fallback
    ContextLength,                      // context too large — compress
    Server { status: u16 },             // 5xx
    Transport,                          // connection refused / DNS / timeout
    SchemaInvalid,                      // 400 bad request, thinking sig, grammar, etc.
    ToolError,                          // tool execution failed in-provider
    ModelNotFound,                      // 404 with model-not-found pattern
    PayloadTooLarge,                    // 413 — compress payload
    Unknown,
}

impl ProviderError {
    pub fn should_retry(&self) -> bool {
        matches!(self,
            Self::RateLimited { .. } | Self::Server { .. } | Self::Transport | Self::Unknown
        )
    }
    pub fn should_fallback(&self) -> bool {
        matches!(self,
            Self::RateLimited { .. } | Self::Auth | Self::Billing |
            Self::ContextLength | Self::Server { .. } | Self::Transport |
            Self::ModelNotFound | Self::PayloadTooLarge
        )
    }
    pub fn should_compress(&self) -> bool {
        matches!(self, Self::ContextLength | Self::PayloadTooLarge)
    }
    /// Variant name for recording in usage_events.error_kind
    pub fn variant_name(&self) -> &'static str {
        match self {
            Self::RateLimited { .. } => "RateLimited",
            Self::Auth => "Auth",
            Self::Billing => "Billing",
            Self::ContextLength => "ContextLength",
            Self::Server { .. } => "Server",
            Self::Transport => "Transport",
            Self::SchemaInvalid => "SchemaInvalid",
            Self::ToolError => "ToolError",
            Self::ModelNotFound => "ModelNotFound",
            Self::PayloadTooLarge => "PayloadTooLarge",
            Self::Unknown => "Unknown",
        }
    }
}

impl From<ProviderError> for (bool, bool) {
    fn from(e: ProviderError) -> Self {
        (e.should_retry(), e.should_fallback())
    }
}

### Sub-system A: Prompt Caching (D-CACHE-01..04)

**Critical invariants:**
1. `cached_layers_must_be_stable()` fires `panic!` (debug) / `tracing::warn!` (release) if any of layers 1-8 contain timestamps, session IDs, or per-turn data. This invariant must be verifiable via a static-grep test (mirrors `invariants_27_1_4_1_1.rs`).
