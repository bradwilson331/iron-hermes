### CR-01: Anthropic SSE event parser corrupts/panics on `data:` payloads that aren't JSON objects with at least 2 bytes

**File:** `crates/ironhermes-agent/src/anthropic_client.rs:1019`
**Issue:** The streaming SSE parser builds a tagged JSON envelope via:
```rust
let tagged = format!(r#"{{"type":"{etype}",{}}}"#, &data[1..data.len() - 1]);
```
This assumes `data` is a JSON object string whose first byte is `{` and last byte is `}`. It strips both ends and splices the interior into a new envelope. Two failure modes:

1. **Panic on short payloads.** If `data.len() < 2`, `data[1..data.len()-1]` panics with arithmetic underflow on `data.len()-1 == 0` or slices out-of-range. Anthropic's spec allows `event: ping\ndata: {}\n\n` — with `data = "{}"`, `data.len()-1 == 1`, the slice `[1..1]` is empty, but if upstream ever sends `data: ` (one space, len=1) or a transport hiccup truncates to a single brace, this panics inside the spawned task. The whole streaming task aborts silently with no surface error.
2. **Corruption / interpolation when `data` does not start with `{`.** No guard validates the shape. If a future Anthropic event includes `data: "literal-string"` or `data: 42`, the code strips the quote/digit boundary bytes and emits malformed JSON that the catch-all `_ => {}` arm silently swallows after `from_str` errors. More dangerously, if `etype` itself is attacker-controllable (it isn't today — comes from `event:` line — but worth noting), the `{etype}` interpolation has zero quoting and could allow JSON injection. Even with trusted upstreams, an event line like `event: foo"bar` (RFC for SSE allows any non-newline byte) crashes the parser.

**Fix:** Replace the format-splice with a struct-based parse — deserialize `data` to `serde_json::Value`, then build the envelope:
```rust
let inner: serde_json::Value = match serde_json::from_str(&data) {
    Ok(v) => v,
    Err(e) => { debug!("Failed to parse SSE data: {e}"); continue; }
};
let mut tagged = match inner {
    serde_json::Value::Object(mut m) => {
        m.insert("type".to_string(), serde_json::Value::String(etype.clone()));
        serde_json::Value::Object(m)
    }
    _ => { debug!("SSE data is not an object: {data}"); continue; }
};
let parsed: AnthropicSseEvent = match serde_json::from_value(tagged) { ... };
```
Or use `#[serde(tag = "type")]` with an outer envelope struct that holds both `event:` and `data:` after collecting both — never string-splice JSON.

**Issue:** `AgentLoop::new` initializes `provider_name: String::new()` and `api_key_for_usage_tracking: String::new()`. agent = agent

### CR-03: `compute_cost_micros` integer truncation silently zeroes small-token costs

**File:** `crates/ironhermes-core/src/pricing.rs:155-167`
**Issue:** The cost formula uses `(tokens * micros_per_1m) / 1_000_000` with integer i64 arithmetic:
```rust
let input_cost = (in_tok * entry.input_per_1m_micros) / 1_000_000;
```
For Anthropic Sonnet at $3/M (`input_per_1m_micros = 3_000_000`), a turn that uses 333 input tokens computes `(333 * 3_000_000) / 1_000_000 = 999` micro-USD = $0.000999, which is correct.

But for Claude Haiku at $0.25/M (`input_per_1m_micros = 250_000`), a turn that uses 3 input tokens computes `(3 * 250_000) / 1_000_000 = 0` (750_000 / 1_000_000 truncates to 0). For OpenAI gpt-4o cache_creation at `cache_creation_per_1m_micros = 0`, multi-thousand-token operations still cost zero (intentional for OpenAI). Combined, every small-volume Haiku turn or any per-byte-pricing edge silently undercounts cost to $0, then aggregates a $0 column in `sessions.cost_usd_micros`. The aggregator at `SUM(cost_usd_micros)` looks correct, but the underlying rows are wrong.

The integer-micro-USD discipline is otherwise sound; the bug is order-of-operations. Multiplying first then dividing minimizes drift, but the divisor of 1_000_000 is bigger than the per-token sub-unit for cheap models.

Worst-case demonstration: an entire 1-million-token-input conversation on Haiku at 1-token-per-row resolution would log 1M rows of 0-micros and aggregate to $0 instead of $0.25. In practice tokens-per-turn are 10²-10⁵ so the per-row loss is small, but the bug is real and stamps zero costs onto every short turn for cheap models.

**Fix:** Use rounding-aware integer arithmetic, e.g. add `500_000` (half a million-micros = half a cent) before dividing:
```rust
let input_cost = (in_tok * entry.input_per_1m_micros + 500_000) / 1_000_000;
```
Or scale up by another factor so the displayed unit isn't lost. The cleanest fix is to track in nano-USD (1 USD = 1_000_000_000) for storage and convert to micros at the display boundary; this gives 3 decimal places of slack and preserves the integer discipline.

### CR-05: `attach_cache_control_markers` silently no-ops when `system` is `Blocks(_)` — multi-turn cache attaches skipped after first call

**File:** `crates/ironhermes-agent/src/anthropic_client.rs:632-654`
**Issue:** The function early-returns on the `AnthropicSystem::Blocks(_)` branch:
```rust
AnthropicSystem::Blocks(_) => {
    // ... comment about "future call site"
    return;
}
```
The early `return` exits the ENTIRE function — not just the system-block path. Both the system marker AND the last-3-messages markers are skipped. The comment claims "This branch is not exercised by current call sites — adapt_messages always returns Text" which is true today, but the function is `pub(crate)` and used inside the request builder. The dead-branch defense becomes a footgun if anyone refactors `adapt_messages` to preempt-attach markers (which is exactly the natural place to attach them when iterating messages).

Additionally, the function takes `&mut Option<AnthropicSystem>` and unconditionally converts `Text → Blocks` with the marker, mutating the caller's data even when the function later fails. Idempotency is broken: calling it twice on the same system produces `Blocks` on the first call, then no-ops on the second (no marker attached because the early return).

**Fix:** Split the early-return into a `continue` on just the system path:
```rust
if let Some(s) = system.as_mut() {
    match s {
        AnthropicSystem::Text(t) => {
            let text = std::mem::take(t);
            let mut block = SystemBlock::text(text);
            block.cache_control = Some(CacheControl::ephemeral(ttl));
            *s = AnthropicSystem::Blocks(vec![block]);
        }
        AnthropicSystem::Blocks(blocks) => {
            // attach marker to last existing block instead of returning
            if let Some(last) = blocks.last_mut() {
                last.cache_control = Some(CacheControl::ephemeral(ttl));
            }
        }
    }
}
// Fall through to message-level markers regardless of system shape.
```

### CR-06: Web `list_sessions` / `get_session_messages` panic on poisoned mutex (no graceful path)

**File:** `crates/iron_hermes_ui/src/server/api.rs:136, 157, 491`
**Issue:** Three call sites unwrap the state store mutex:
```rust
let store = state.state_store.lock().unwrap();      // L136
let store = state.state_store.lock().unwrap();      // L157 (inside per-session map closure)
.lock().unwrap()                                     // L491 — get_session_messages
```

If any other thread panics while holding the lock (e.g., a single SQLite error path inside `add_message`), the mutex becomes poisoned and these calls panic the request handler. ### CR-07: `Anthropic::chat_completion_stream` SSE buffer grows unbounded on malformed-stream attack

**File:** `crates/ironhermes-agent/src/anthropic_client.rs:973-998`
**Issue:** The stream loop buffers bytes into `String` (line 991) and only consumes when `find("\n\n")` succeeds. ### CR-08: `cost_field_to_micros` silently truncates fractional cents — overflow undetected

**File:** `crates/ironhermes-core/src/pricing_cache.rs:203-210`
**Issue:** Two correctness gaps:

1. **Truncation, not rounding.** `(v.as_f64().unwrap_or(0.0) * 1_000_000.0) as i64` truncates toward zero. A models.dev price of `$2.999999` becomes `2_999_999` micros (fine); `$2.9999999` becomes `2_999_999` micros (cent-precision lost). For models priced at $0.0001 per 1M, the float `0.0001 * 1_000_000.0 = 100.0` rounds in IEEE 754 to `99.9999...` and truncates to `99`. This is a 1% accuracy loss on cheap-model pricing.

2. **Silent overflow on huge prices.** `(v.as_u64().unwrap_or(0) as i64) * 1_000_000` overflows when `v > i64::MAX / 1_000_000 ≈ 9.2e12`. A malicious refresh payload with `"input": 10000000000` would multiply to `1e16` micros (still fits), but `"input": 100_000_000_000` (1e11) would multiply to `1e17` micros (still fits), and the comment in pricing.rs:154 says i64 max is ~9.2e18 so realistic prices never overflow. However, `as i64` from a `u64` larger than `i64::MAX` silently produces a negative value, which then multiplies by 1_000_000 with wrap-on-overflow behavior in release builds. T-36.2-09-PARSE claims "graceful" handling but `as i64` on huge u64s is undefined-behavior-adjacent.

**Fix:** Use checked arithmetic and `.round()` for floats:
```rust
Some(v) if v.is_f64() => {
    let scaled = v.as_f64().unwrap_or(0.0) * 1_000_000.0;
    if scaled.is_finite() { scaled.round() as i64 } else { 0 }
}
Some(v) if v.is_u64() => {
    let n = v.as_u64().unwrap_or(0);
    if n <= (i64::MAX / 1_000_000) as u64 {
        (n as i64) * 1_000_000
    } else {
        tracing::warn!("price field overflows i64 micros; skipping");
        0
    }
}
```

### CR-10: `parse_retry_after` confuses byte vs char offsets after `to_lowercase`

**File:** `crates/ironhermes-agent/src/error_classifier.rs:210-228`
**Issue:** The comment claims "ASCII so byte == char alignment is preserved." This is true for the needles (`"retry-after:"` etc.) but not for the surrounding error string. If a 429 error chain contains non-ASCII bytes (e.g., a Unicode response body translated through `format!("{err:#}")`), `to_lowercase()` on the full chain can change the byte length of some characters (`İ.to_lowercase() == "i\u{307}"`, a 2-byte combining diacritic). `lower.find(needle)` returns a byte index into the LOWERCASED string, but `lower[idx + needle.len()..]` then walks past non-ASCII multi-byte sequences treating bytes as chars via `.chars()`. This works because `chars()` re-decodes, but the offset arithmetic is technically incorrect on multi-byte characters at byte boundaries before the needle — a `find` returning byte 7 of a string where byte 7 is in the middle of a UTF-8 sequence is impossible because `to_lowercase` produces valid UTF-8 and `find` always returns code-point-aligned positions. So this is correct-by-construction, but the safety reasoning in the comment is wrong.

The real bug is the LACK of an upper bound on the parsed integer: `let n: u64 = secs_str.parse().ok()?;` can return `u64::MAX`. `Duration::from_secs(u64::MAX)` then floods downstream sleep/sleep-until paths with a 584-billion-year duration. A malicious server returning `Retry-After: 99999999999999999999999` is dropped by `parse` (overflow), but `9223372036854775000` parses fine and creates a Duration that exceeds reasonable bounds. Anywhere this Duration is then ADDED to `SystemTime::now()`, the result silently saturates or wraps.

**Fix:** Cap the parsed seconds at a sane upper bound (e.g. 1 hour = 3600s, or 1 day):
```rust
if let Ok(n) = secs_str.parse::<u64>() {
    let capped = n.min(86_400); // cap at 24h
    return Some(Duration::from_secs(capped));
}
```

### WR-02: `write_usage_success`/`write_usage_failure` issue unbounded SQLite writes on the agent path

**File:** `crates/ironhermes-agent/src/agent_loop.rs:1018-1112, 1147-1182`

SQLite has WAL journal mode (line 49 of state lib.rs) so writers don't block readers, but the synchronous `tx.execute` calls plus `tx.commit()` can take 5-50ms each on slow disks (mobile / network drives / WSL2). On a multi-turn long session, this stalls the agent worker for hundreds of ms cumulatively.

The agent path uses `if let Ok(c) = compressor_mutex.try_lock()` at line 1102 (correctly non-blocking), but the SQLite path at line 1024 uses `store.lock()` (blocking, no timeout). **Fix:** Either move the write to `tokio::task::spawn_blocking` (matches the session_search intercept pattern), or use `tokio::sync::Mutex` for the state store. The current pattern works but stalls the agent task on the call path.

### WR-09: `parse_since` panics on multi-byte unit characters

**File:** `crates/ironhermes-core/src/commands/handlers.rs:731-748`
**Issue:** `s.split_at(s.len() - 1)` panics on `s.len() == 0` (caught by the `is_empty` guard) but ALSO produces wrong behavior on multi-byte unit characters. Inputs like `"1月"` (1-month in Japanese, 4-byte string) → `split_at(s.len() - 1) = split_at(3)`, which is in the middle of the `月` codepoint → byte-index-not-on-char-boundary panic. ### WR-11: `SCHEMA_SQL` re-runs PRAGMA journal_mode=WAL on every open — silent failure on read-only mount

**File:** `crates/ironhermes-state/src/lib.rs:48-49`
**Issue:** `PRAGMA journal_mode=WAL` inside `execute_batch` is non-transactional and silently fails on a read-only filesystem (e.g., NFS export with no-locking) without an error path. The subsequent `CREATE TABLE IF NOT EXISTS` proceeds with the default rollback journal, which has lock-contention semantics incompatible with the WAL-assumed write path. **Fix:** Check the pragma return value explicitly:
```rust
let mode: String = self.conn.query_row(

)?;
if mode != "wal" {
    warn!("PRAGMA journal_mode=WAL ignored; got: {mode}");
}
```
