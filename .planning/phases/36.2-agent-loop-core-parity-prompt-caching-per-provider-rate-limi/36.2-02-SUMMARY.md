# Phase 36.2 Plan 02: Migration v9 — usage_events table + cache-token columns Summary

Land the SQLite storage layer that unblocks every downstream Phase 36.2 plan that writes a per-turn usage row.

## What Shipped

- **Schema v9 migration block** (idempotent, `let _ =` ALTER pattern) at `crates/ironhermes-state/src/lib.rs:425`. Adds three columns to `sessions` (`cache_read_tokens`, `cache_creation_tokens`, `cost_usd_micros` — all `INTEGER DEFAULT 0`) and creates the `usage_events` table (10 cols) plus `usage_events_session_idx` and `usage_events_ts_idx`.
- **`SCHEMA_VERSION` bumped 8 → 9** at `lib.rs:46`. Fresh DBs receive the new columns and `usage_events` table directly from `SCHEMA_SQL` (mirrors v8 `workspace_root` precedent — fresh DBs skip `run_migrations` entirely, so DDL must live in both places).
- **`pub struct UsageEvent`** at `lib.rs:144-181` — 10 fields, `Debug + Clone + Serialize + Deserialize`, all numerics `i64` (no `u64`, no `usize`, no `f64`). `cost_usd_micros` is micro-USD per `D-USAGE-01` (avoids float drift). `error_kind: Option<String>` is doc-restricted to `ProviderError::variant_name()` strings only — raw Debug payloads are explicitly forbidden to mitigate T-36.2-02-PII.
- **`StateStore::insert_usage_event(&UsageEvent) -> Result<()>`** at `lib.rs:836`. All SQL uses `params!` bindings (T-36.2-02-INJ mitigation locked structurally).
- **Extended `StateStore::update_session_stats`** at `lib.rs:809` — signature grew from 4 to 7 numeric args (`input_tokens, output_tokens, tool_call_count, cache_read_tokens, cache_creation_tokens, cost_usd_micros`). All six numeric columns use additive `+= ?N` semantics. `#[allow(clippy::too_many_arguments)]` is intentional and documented.
- **`StateStore::conn_for_test()`** accessor at `lib.rs:860` returns `&Connection` so integration tests (this plan) and the per-turn write site (downstream Plan 07) can wrap `insert_usage_event + update_session_stats` in a single caller-owned `unchecked_transaction()` (Pitfall 6 atomicity).
- **10 integration tests** in `crates/ironhermes-state/tests/usage_events_schema.rs` proving migration round-trip (b1, b2, b3), idempotency on partial-migration replay (b4), single-row insert (b5), additive `update_session_stats` aggregation (b6), atomic commit + rollback (b7×2), `error_kind` round-trip (b8), and 9_999_999_999_i64 micro-USD lossless round-trip (b9).
- **Updated v8 invariant tests** at `lib.rs:1143-1228` — `schema_version_constant_is_8` → `schema_version_constant_is_9`; `v7_db_upgrades_to_v8_preserving_rows` → `v7_db_upgrades_to_latest_preserving_rows` with extended assertions for v9 columns + `usage_events` table existence.

## Deviations from Plan

### Spec text vs. v8 precedent — acceptance grep counts for `CREATE TABLE` / `CREATE INDEX`

The plan's `<acceptance_criteria>` block specifies `grep -c 'CREATE TABLE IF NOT EXISTS usage_events' = 1`, `grep -c 'CREATE INDEX IF NOT EXISTS usage_events_session_idx' = 1`, and `grep -c 'CREATE INDEX IF NOT EXISTS usage_events_ts_idx' = 1`. **Actual counts: 2 / 2 / 2.**

**Reason:** This plan mirrors the Phase 25.3 v8 `workspace_root` pattern as instructed by the plan's `<interfaces>` and `read_first` references. That precedent places new DDL in **both** `SCHEMA_SQL` (for fresh installs — `init_schema` never calls `run_migrations` on a brand-new DB; it INSERTs `SCHEMA_VERSION` directly per `lib.rs:333-339`) **and** the migration block (for in-place upgrades). For `workspace_root` the migration uses `ALTER TABLE ADD COLUMN`, but for `usage_events` the equivalent is `CREATE TABLE IF NOT EXISTS`. The semantic intent the plan was guarding (no duplicate v9 migration block) is preserved: `grep -c 'if current < 9' = 1`. The literal-text grep criteria appear to have overlooked the fresh-DB path that v8 already established as the project convention.

**Alternative considered + rejected:** Move all v9 DDL into the migration block only and change the fresh-DB init path to `run_migrations(0)` so every fresh install replays the full migration chain. Rejected because (a) it diverges from the v8 precedent without a planning decision; (b) it is a cross-cutting refactor of the SCHEMA_SQL contract; (c) it would also have to retroactively redefine the v8 fresh-install path to run the workspace_root migration on fresh installs — out of scope for this plan.

Logged in `deferred-items.md` as "Acceptance grep 'exactly 1' criterion mismatch" so a future planner who wants to tighten the criterion can do so as a deliberate architectural change.

### [Rule 3 — Blocking] Pre-existing clippy warnings became gate blockers

Three pre-existing warnings in `ironhermes-state` (`with_busy_retry` and `is_busy` are `dead_code`; `session_export.rs:69` triggers `clippy::collapsible_if`) predated this plan but became blockers because the plan introduced a `cargo clippy -- -D warnings` acceptance gate. Suppressed each with a localized `#[allow]` attribute and a comment that names the deferred decision. None of the suppressed code paths were behaviorally modified — purely a noise-gate workaround. All three are documented in `deferred-items.md` with rationale and pointers for the future phase that should re-enable them.

### [Rule 1 — Bug] v8 invariant tests would have FAILed after SCHEMA_VERSION bump

`schema_migration_v8_tests::schema_version_constant_is_8` and `schema_migration_v8_tests::v7_db_upgrades_to_v8_preserving_rows` were hard-coded to assert `SCHEMA_VERSION == 8` and `version == 8` post-upgrade. Both became false after the version bump. Updated to:
- `schema_version_constant_is_9` asserts the new value.
- `v7_db_upgrades_to_latest_preserving_rows` asserts `version == SCHEMA_VERSION` (future-proof) AND extends the post-upgrade checks with Phase 36.2 invariants: cache/cost columns default to 0 on pre-v9 rows, `usage_events` table exists.

The substance of the original Phase 25.3 tests (legacy rows survive migration with NULL `workspace_root`) is preserved verbatim.

## Threat Surface Scan

No new threat surface beyond what is already in the plan's `<threat_model>`. All mitigations are in place:

- T-36.2-02-MIG (partial-migration tampering) — `let _ =` idempotent ALTER + `IF NOT EXISTS` guards + version-gate `if current < 9`. Verified by b4_migration_idempotent_on_reopen.
- T-36.2-02-INJ (`/usage` SQL injection) — all writes use `params!` only. Cross-plan invariant recorded for downstream Plan 10's reader.
- T-36.2-02-PII (PII in error_kind) — doc comment on `UsageEvent.error_kind` explicitly forbids raw Debug payloads; only `ProviderError::variant_name()` strings are permitted.
- T-36.2-02-ATOM (write divergence) — caller owns the transaction (via `conn_for_test()` / future Plan 07's analog accessor); b7×2 tests prove commit + rollback both leave both rows in their post-write-or-pre-write state respectively.
- T-36.2-02-DOS (unbounded `usage_events` growth) — accepted per plan; pruning policy deferred.
- T-36.2-02-SC (supply chain — no new deps) — confirmed; `cargo tree -p ironhermes-state` unchanged.

## Notes for Downstream Plans

- **Plan 07 (AgentLoop post-turn write site):** wrap `insert_usage_event` + `update_session_stats` in a single `conn.unchecked_transaction()` block (see b7 test as the canonical pattern). The `StateStore` methods themselves DO NOT start a transaction — that ownership is intentionally pushed to the caller.
- **Plan 10 (`/usage` reader):** ALL filter values (`--provider`, `--since`, `--model`, `--today`) MUST be passed via `rusqlite::params!` bindings. Never `format!`-interpolate user input into the SQL string. This is a hard invariant of the T-36.2-02-INJ mitigation contract.
- **Future `Session` struct extension:** plan-deferred (Step 7 in this plan). Read paths at `lib.rs:490, 547, 731, 903` continue to work because new columns have `DEFAULT 0`. When a future plan extends `Session` to carry the cost fields, those four SELECT statements must be updated in lockstep.
