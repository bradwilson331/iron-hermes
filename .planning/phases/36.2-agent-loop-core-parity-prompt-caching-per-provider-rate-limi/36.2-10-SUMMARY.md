# Phase 36.2 Plan 10: /usage slash command + TUI cost+token pills Summary

The Phase 36.2 substrate (Plans 01-07 + 09 + 11) is now user-visible end-to-end: every LLM call writes a per-turn `usage_events` row with correct cost (Plan 07), and this plan adds the four user-facing surfaces:

1. **`/usage` slash command** (multi-platform via CommandRouter): bare invocation, `--today`, `--provider X`, `--model X`, `--since Nd|Nh|Nm`.
2. **TUI status-bar cost pill** (`$X.YYY`) and **token pill** (`N.NK tok`) in tui_rata.
3. **Web UI sidebar cost surface** — DEFERRED with a documented TODO; `/usage` text rendering still works on web today via CommandRouter dispatch.
4. **Manual UAT checkpoint** — Task 3, pending operator sign-off (5 verifications listed below).

Wire user-visible reporting onto the Plan 02 storage + Plan 07 write site so users can finally inspect what each session cost. ## Deviations from Plan

### 1. [Rule 1 — Blocking compile dep] Tests moved from `ironhermes-core/tests/` to `ironhermes-cli/tests/`

- **Found during:** RED build of the initial test file at `crates/ironhermes-core/tests/usage_command.rs`.
- **Issue:** The plan's `<files>` block listed `crates/ironhermes-core/tests/usage_command.rs` as the test home. Adding it required importing `ironhermes_state::{StateStore, UsageEvent, UsageFilter}` as a dev-dep on `ironhermes-core`. But `ironhermes-state`'s `Cargo.toml` declares `ironhermes-core = { path = "../ironhermes-core" }` — adding state as a dev-dep of core would create a **circular Cargo dependency** (`core --(dev)--> state --(prod)--> core`), which Cargo rejects at resolve time.
- **Fix:** Moved the test to `crates/ironhermes-cli/tests/usage_command.rs`. The cli crate already depends on both `ironhermes-core` and `ironhermes-state` (prod deps), so it's the correct home for any test that exercises both. This precedent is established at `crates/ironhermes-cli/tests/handlers_state_store.rs:6-9` ("Per RESEARCH OQ-7: placed in `ironhermes-cli/tests/` ... because `ironhermes-state` imports `ironhermes-core` — adding it as a dev-dep of core would create a circular dependency").
- **Files modified:** `crates/ironhermes-cli/tests/usage_command.rs` (created) — `crates/ironhermes-core/tests/usage_command.rs` (created then deleted before commit).
- **Justification:** The plan-author appears to have missed the circular-dep constraint. The cli home is the project-established convention.

### 2. [Rule 2 — Critical correctness add] `StateStoreHandle::usage_text` takes primitives, not `&UsageFilter`

- **Found during:** Task 1 design.
- **Issue:** The plan's `<interfaces>` block showed `cmd_usage` constructing a `UsageFilter` and calling `store.query_usage_events(&filter)` directly. But `StateStoreHandle` is a trait in `ironhermes-core`; `UsageFilter` is a struct in `ironhermes-state`. Adding `&UsageFilter` to the trait signature requires `ironhermes-core` to back-depend on `ironhermes-state`, breaking the leaf-crate invariant. The PLAN's `<key_links>` block also implied `cmd_usage` calls `query_usage_events` directly, which would require the same back-dep.
- **Fix:** Redesigned the trait method to take 5 primitives (`Option<&str>` × 3, `bool`, `Option<i64>`) — same shape as the existing `list_sessions_text_filtered(limit: usize, workspace_root: Option<&str>)`. Implementations build `UsageFilter` and call `query_usage_events` inside the method body where both crates are in scope. The test fixture and the production `StateStoreAdapter` both do this.
- **Files modified:** `crates/ironhermes-core/src/commands/context.rs`, `crates/ironhermes-cli/src/tui_rata/commands.rs`, `crates/ironhermes-cli/tests/usage_command.rs`, `crates/ironhermes-core/src/commands/handlers.rs::cmd_usage`.
- **Justification:** Preserves the leaf-crate property of `ironhermes-core` — a strict precedent across this codebase (see Phase 22.4.2 D-04, Phase 21.3 D-04, Phase 17 MemoryManagerHandle, etc.).

### 3. [Rule 1 — Bug] `dispatch_all_todo_stubs_return_not_yet_available` test pinned `"usage"` to the stub set

- **Found during:** First `cargo test -p ironhermes-core --lib` after wiring cmd_usage.
- **Issue:** The pre-existing test at `handlers.rs:1937` iterates over a hard-coded list of `todo_commands` and asserts each dispatches to a "is not yet available" output. The list included `"usage"`. Once `cmd_usage` was wired, dispatch no longer routes /usage to todo_stub → the test fails.
- **Fix:** Removed `"usage"` from the list and replaced with a comment line `// "usage" removed — now has real handler (Phase 36.2 Plan 10)` matching the existing convention used by every other graduated stub (background, retry, undo, etc. — all marked the same way).
- **Files modified:** `crates/ironhermes-core/src/commands/handlers.rs:1944`.

### 4. [Plan calibration] `as f64` count in `status_line.rs` exceeds plan's "<=3" guard

- **Found during:** Acceptance grep sweep at end of Task 2.
- **Issue:** Plan acceptance specifies `grep -c 'as f64' crates/ironhermes-cli/src/tui_rata/status_line.rs` returns <= 3. Actual count post-Task 2: **6**.
- **Breakdown:**
  - Line 45 — doc comment (no code)
  - Lines 83, 86 — pre-existing `format_token_count` (Phase 22.4 baseline)
  - Line 104 — pre-existing percentage calc (Phase 22.4 baseline)
  - Lines 137, 143 — **NEW for Plan 10** (display-layer cost + token pill conversions)
- **Justification:** Only 2 of 6 are new; both are display-only per Pitfall 5 (`as f64 / 1_000_000.0` and `as f64 / 1_000.0` at format-string boundaries). Upstream arithmetic stays i64 / usize. The plan's "<=3" target wasn't calibrated against the pre-existing 4-baseline.
- **Action:** Logged as a deviation; **NO refactor** of pre-existing code (out-of-scope per SCOPE BOUNDARY). The intent of the guard (no upstream f64 arithmetic) is preserved.

### 5. [Rule 2 — UX choice] Web UI sidebar surface deferred with documented TODO

- **Found during:** Task 2 implementation, reading the web UI status bar source.
- **Issue:** The plan's `<action>` Step 4 says "Add `cost_usd_micros` and `session_total_tokens` to the broadcast payload struct". But the web UI status bar at `crates/iron_hermes_ui/src/components/shell_legacy/status_bar.rs` uses Dioxus `ReadSignal<TokenBudget>` — a reactive signal pattern. Adding cost+token pills requires (a) extending `TokenBudget` to carry cost, (b) extending `ConfigSummary` or adding a `UsageSummary` payload, (c) extending the websocket broadcast in `state.rs`, (d) extending the Dioxus component props. That's a cross-cutting Dioxus refactor — exactly what Phase 26.7 (web wiring) is scoped to handle.
- **Fix:** Added a documented `TODO Phase 36.2 Plan 10 (D-USAGE-03)` comment block on `ConfigSummary` in `crates/iron_hermes_ui/src/server/api.rs` (~line 50-78) spelling out:
  - WHY deferred (Dioxus signal-based status bar requires a cross-cutting refactor)
  - WHO closes it (Phase 26.7 web-wiring scope)
  - WHAT shape to add (`cost_usd_micros: i64` + `session_total_tokens: usize`)
  - WHERE the canonical formatting contract lives (`tui_rata/status_line.rs::build_pills` — `${:.3}` + `{:.1}K tok`).
- **Justification:** Per the plan's explicit allowance ("If the web UI is not currently functional or has no parallel status surface, defer with a `// TODO Phase 36.2 web UI cost surface — depends on web UI build status` comment and document the deferral in the SUMMARY"). The `/usage` slash command itself still works on the web UI via CommandRouter dispatch — only the pill surface deferred.

## Cross-Plan Invariants (for any future plan extending /usage)

For future plans adding new `--flag X` subcommands to `/usage` or wiring the web UI sidebar surface:

1. **ALL user-supplied filter values MUST flow through `rusqlite::params!` bindings.** Never `format!(...)`-interpolate into the SQL string. The b12 static-grep guard locks this at the source-file level — adding a `format!(...SELECT ...)` line will break the test.
2. **The display layer is the ONLY place i64 micro-USD becomes f64.** Upstream `cost_usd_micros` arithmetic stays i64; only `as f64 / 1_000_000.0` at format-string boundaries is permitted.
3. **`format_usage_rollups` is the single canonical text renderer.** Any new surface (alternate platform, custom view) should call it (or fork it with `cfg!`-style separation), not re-implement formatting.
4. **`StateStoreHandle::usage_text` is primitive-typed.** Future filter additions should add primitive parameters (Option<&str> / bool / Option<i64>) — never `&UsageFilter` or `&UsageRollup` (those types live in ironhermes-state and would back-dep ironhermes-core).
5. **Web UI surface MUST extend `ConfigSummary` (or a sibling `UsageSummary`) with `cost_usd_micros: i64` + `session_total_tokens: usize` fields** and wire them through the websocket — see the TODO at `crates/iron_hermes_ui/src/server/api.rs::ConfigSummary` for the canonical shape and rationale.
