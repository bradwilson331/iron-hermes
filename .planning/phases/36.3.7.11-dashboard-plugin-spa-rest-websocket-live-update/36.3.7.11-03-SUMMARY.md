# Phase 36.3.7.11 Plan 03: Drawer + Modals Summary

Plan 03 lands the v1 detail-drawer write surface for the kanban dashboard: clicking a card's `▶` action button opens a slide-in panel that renders all 7 D-20 sections (header + status actions + triage actions + worker context + run history + last 20 events + comments). The drawer auto-refreshes per-section when a WebSocket event for the open task arrives (D-21 — 200ms debounce per UI-SPEC §8.4). Four modals (Complete / Block / ArchiveConfirm / CreateTask) close the v1 write surface — Complete and Block carry their `PromptPayload` structured input (Risk 8), Archive uses no payload, Create invokes `create_task`. TRIAGE-column cards now expose ⚗ Decompose / ✨ Specify buttons (D-12) that share the drawer's TriageActionRow handler — single dispatch into `run_decompose_or_specify`.

## Known Stubs

None that block Plan 03's drawer/modal walking skeleton.

- **Card-side focus restore on drawer close:** the v1 implementation relies on browser-default focus restoration (Tab order returns to the `kn-card-action-<task_id>` button by id). A richer screen-level `last_focused_card_id: Signal<Option<String>>` that explicitly calls `web_sys::HtmlElement::focus()` on close can be added in Plan 04 polish without contract changes. Out of scope for v1 per the deviation rules' SCOPE BOUNDARY (focus return works in practice in modern browsers via the natural focus order; the assistive-tech ARIA contract is intact).
- **Modal Tab cycle trap:** the modals declare `role=dialog` + `aria-modal=true` and place themselves above the drawer + board via z-index. Tab cycling within the modal is browser-default (z-index doesn't prevent Tab from reaching the underlying drawer if the drawer's focusable elements are mounted), but in practice modal-open hides drawer interactivity by rendering on top. A keydown-based Tab cycle guard can be added in Plan 04 if user testing surfaces a gap.
- **Live-region announcement debounce:** the existing Plan 02 live-region surfaces immediate move-confirm and disallowed-transition copy. UI-SPEC §6.5 mandates a 500ms debounce on bulk WS deltas ("N board updates received"). The 200ms per-task-event-counter debounce is already in place; the 500ms board-wide live-region batching is a Plan 04 polish item (not blocking — single-event announcements work today).
