# Phase 36.3.7.11: Dashboard plugin — SPA + REST + WebSocket live-update for hermes dashboard Kanban tab - Context

**Gathered:** 2026-05-31
**Status:** Ready for planning

<domain>
## Phase Boundary

Ship a **Kanban tab inside `iron_hermes_ui`'s HermesApp** that visualizes the existing kanban board (tasks + events from `ironhermes-kanban`) and exposes structured write actions back to the same `kanban_db` code path the LLM `kanban_*` tools and `hermes kanban` CLI already use. The dashboard is a third surface on top of the existing shared store — never a parallel implementation.

**In scope (v1):**
- Kanban tab mounted in HermesApp's wheel navigation as a new `KANBAN` module.
- Discovery affordance: a `KANBAN BOARD →` button in the **Agents** page top-right toolbar, immediately right of `PRUNE ENDED`. Primary navigation path is `Agents → Kanban` (operators land on Agents when supervising swarm work).
- 6-column board: `TRIAGE / TODO / READY / IN PROGRESS / BLOCKED / DONE`. `ARCHIVED` revealed by a toolbar toggle (becomes a 7th column when on).
- Card visual style matches the **Models** page from the reference screenshot (cyan-glow border, monospace heading, thin separator, footer row of meta chips + action). On Kanban cards: chips render `STATUS · PRIORITY · ASSIGNEE · AGE` plus per-card checkbox slot reserved for a future multi-select.
- HTML5 native drag-and-drop with allowed-transition validation (see D-09 below).
- Detail drawer (mid-tier): worker_context block + status action row + comment thread + last 20 task_events + run history.
- Live updates via dashboard-specific `task_events` tail consumer pushed over WebSocket.
- Read endpoints (Dioxus `#[server]` fns): `fetch_board`, `fetch_task`, `fetch_task_events`, `fetch_task_runs`, `fetch_comments`.
- Write endpoints (Dioxus `#[server]` fns): `patch_task_status`, `post_comment`, `create_task`, `run_decompose_or_specify`.
- Default board only (current/default board per `~/.hermes/kanban/current`). Every `#[server]` signature takes `board: Option<String>` so a future switcher is a UI-only addition.

**Out of scope (v1):**
- Explicit `/api/plugins/kanban/*` REST mount. Dashboard surface is Dioxus `#[server]` fns only; no parallel HTTP API.
- Inline edits of title / body / assignee / priority in the drawer.
- Dependency editor (no `add_link` / `remove_link` writes from UI).
- Bulk operations / multi-select bulk actions / drag-to-trash / bulk delete.
- Board switcher UI / `+ New board` / archive-board flow.
- Multi-tenant filter dropdowns beyond the current tenant.
- Profile-description editor / orchestration settings `PUT` endpoint.
- Worker visibility endpoints (`/workers/active`, `/runs/{id}`, `/inspect`).
- Plugin extensibility surface (Python ref "extending the dashboard" patterns).
- PR-link rendering / GitHub integration in the drawer.
- "Nudge dispatcher" button / `POST /dispatch` endpoint.
- The Flat view (Kanban-Flat-view.png is reference for a future enhancement, not v1).
- Refactoring the 36.3.7.5 notifier — dashboard tail is independent.
- Mutations to `RUNNING` status from UI (dispatcher-owned).

</domain>

<decisions>
## Implementation Decisions

### Visual contract & discoverability

- **D-01: Card style mirrors the Models page reference image.** Dark surface, cyan-glow border, monospace heading, thin internal separator, footer row of meta chips with a trailing action button. Status / priority / assignee / age render as chips on the footer; `EDIT`-style action button slot reserved for the drawer-open affordance.
- **D-02: Wheel-nav addition — `KANBAN` module.** Sits alongside existing modules (CHAT / AGENTS / MODELS / TOOLS / SKILLS / MEMORY / SESSIONS / PROVIDER / GATEWAY / SYSTEM).
- **D-03: Agents-page toolbar button — `KANBAN BOARD →` lives immediately right of `PRUNE ENDED` in the top-right action area.** Same button style as `+ NEW AGENT` / `PRUNE ENDED`. Operators supervising swarm work land on Agents; this is the primary entry path.
- **D-04: Themes inherit from existing HermesApp design tokens.** No theme fork. ANSI palette, Ioskeley Mono, 0px radius on base elements, Warp-style 6px on cards — all unchanged.

### HTTP surface

- **D-05: Dioxus `#[server]` functions only. NO explicit `/api/plugins/kanban/*` REST mount.** Reads via `use_resource` calling `#[server] fetch_*`. Writes via `spawn(async move { ... })` calling `#[server] patch_/post_/run_*`. The board state lives in a `Signal<Vec<Task>>` (or richer per-column signal) with optimistic updates *before* the await fires.
- **D-06: HTML5 native drag-and-drop API only.** No JS drag-and-drop library. Drag source: `draggable: "true"` on each card + `ondragstart`/`ondragend` updating a `dragged_task_id: Signal<Option<TaskId>>`. Drop zone: `ondragover` MUST call `event.prevent_default()` (or `ondrop` never fires). `ondrop` validates the transition against D-09 then fires the `#[server]` mutation. The blueprint code the user pasted during discussion is the literal implementation contract.
- **D-07: Optimistic UI + asynchronous persistence.** Local signal updates immediately on `move_task(task_id, new_status)`; the `#[server]` mutation runs in a `spawn` block. On error, revert the signal and surface a toast — exact revert pattern decided at planning.
- **D-08: WebSocket on the embedded server pushes raw `task_events` rows.** Client maintains `last_event_id` cursor; on receive, applies delta to the appropriate column signal. WebSocket connection lifecycle mirrors `crates/iron_hermes_ui/src/server/ws.rs` patterns exactly (5s app-level Ping, close-frame handshake, `TypedWebsocket<String, String>` envelope, RAII slot guards).

### Columns & lifecycle

- **D-09: Six visible columns + archived toggle.**
  - Visible: `TRIAGE / TODO / READY / IN PROGRESS / BLOCKED / DONE`.
  - Toolbar toggle reveals `ARCHIVED` as a 7th column.
  - Status taxonomy matches `ironhermes-kanban` `Status` enum exactly — the UI labels are display strings; the wire-level value is the canonical lowercase enum.
- **D-10: Drag-allowed transitions (validated client-side AND server-side):**
  - `triage → todo` (manual promote, equivalent to `specify` outcome)
  - `todo → ready` (manual promote when `auto_promote_children = false`)
  - `blocked → ready` (= unblock)
  - any column → `archived` (with confirm modal)
- **D-11: Drag-BLOCKED transitions (UI rejects with hint; surface dedicated action instead):**
  - → `done` — needs `summary` per `kanban_complete` contract → drawer **Complete…** button opens summary + metadata modal.
  - → `blocked` — needs `reason` per `kanban_block` contract → drawer **Block…** button opens reason modal.
  - → `running` — dispatcher-owned per worker-lanes contract; UI writes would race claim transactions.
  - Cross-skipping transitions (e.g. `triage → ready`) — skips lifecycle invariants; force-promote stays a CLI-only escape hatch.
- **D-12: Triage column hosts the 36.3.7.10 action affordances.** ⚗ Decompose / ✨ Specify buttons appear on triage cards (and in the triage drawer). They call the same `run_decompose_or_specify` `#[server]` fn.

### Write surface (v1)

- **D-13: Four `#[server]` write fns:**
  - `patch_task_status(task_id, board: Option<String>, new_status, prompt_payload: Option<PromptPayload>) -> Result<TaskRow, ServerFnError>` — `prompt_payload` carries `summary+metadata` for Complete or `reason` for Block; None for unblock / archive / drag-allowed promotes.
  - `post_comment(task_id, board: Option<String>, body) -> Result<CommentRow, ServerFnError>`.
  - `create_task(board: Option<String>, payload: CreateTaskPayload) -> Result<TaskRow, ServerFnError>` — payload includes title, assignee, optional parents, priority, tenant, triage flag.
  - `run_decompose_or_specify(task_id, board: Option<String>, action: DecomposeOrSpecify) -> Result<DecomposeResult, ServerFnError>` — `DecomposeOrSpecify::Decompose` or `::Specify`.
- **D-14: Server-side validation enforces the same transitions as client-side D-10/D-11.** Defense-in-depth: the client validates for UX (no error round-trip on disallowed drags); the server validates for correctness.

### Live updates

- **D-15: Dashboard-specific tail consumer in `iron_hermes_ui`'s `server` feature.** Polls `task_events` with `since=<last_event_id>` cursor at ~250ms interval. Maintains per-WS-client `last_seen_event_id`; pushes new rows as JSON deltas. **Independent of the 36.3.7.5 notifier — no shared primitive, no notifier refactor.**
- **D-16: Cross-process awareness.** The kanban dispatcher + 36.3.7.5 notifier live in the gateway process; the dashboard lives in `iron_hermes_ui`'s server process. Both read the same `~/.hermes/kanban.db` (WAL mode). A future swap to `tokio::sync::broadcast` (when iron_hermes_ui embeds the dispatcher) is API-compatible — WS contract stays identical.
- **D-17: Tail-poll interval is configurable.** Default 250ms (sub-second perceived latency). New config key: `dashboard.kanban.tail_interval_ms` (default 250). Decided at planning whether this lives under `dashboard.kanban.*` or a new sibling.

### Multi-board

- **D-18: Default-board-only UI for v1.** No switcher, no `+ New board` modal, no archive-board flow. Resolves the active board via `~/.hermes/kanban/current` (the same precedence chain the CLI uses, minus the `--board` flag and `HERMES_KANBAN_BOARD` env var which are inapplicable to the UI).
- **D-19: Every `#[server]` fn signature takes `board: Option<String>`.** `None` means "resolve current/default". Switcher UI is a future addition with zero `#[server]` signature churn.

### Detail drawer

- **D-20: Mid-tier drawer scope:**
  - Header: title (read-only), assignee chip, priority chip, status chip, tenant chip.
  - `worker_context` block — the exact shape `kanban_show` returns (canonical contract from ROADMAP).
  - Status action row: **Complete…** (opens summary + metadata modal → `kanban_complete` via `patch_task_status` with `PromptPayload::Complete`), **Block…** (opens reason modal → `kanban_block` via `patch_task_status` with `PromptPayload::Block`), **Unblock** (one-click → `patch_task_status` `new_status=ready`), **Archive** (confirm → `patch_task_status` `new_status=archived`).
  - Triage-only action row: **⚗ Decompose**, **✨ Specify** (both call `run_decompose_or_specify`).
  - Comment thread: read existing + post-new (calls `post_comment`).
  - Last 20 `task_events` for this task (read-only stream view).
  - Run history: `task_runs` rows with outcome + elapsed (matches Kanban-completed-task-schema-view.png reference).
- **D-21: Drawer refresh-on-event.** The dashboard tail consumer pushes every event for the open task; the drawer's `useEffect`-equivalent dependency includes a per-task event counter that triggers a re-fetch of the affected sub-section (comments / events / runs) — matches the Python ref live-drawer-refresh behavior.

### Auth

- **D-22: Reuse iron_hermes_ui's existing session model.** Kanban `#[server]` fns inherit whatever auth the chat-side `#[server]` fns already enforce. WS uses the same `TypedWebsocket` pattern as `server/ws.rs` (5s keepalive Ping, close-frame handshake, RAII teardown). **No kanban-specific tokens, middleware, or split read/write auth.**
- **D-23: Localhost-bind is the deployment-level threat model.** Matches Python ref. Operator override (`--host 0.0.0.0`) carries the same "don't do this on a shared host" caveat that already exists for the chat surface.

### Claude's Discretion

- Plan slicing — the ROADMAP entry flags "likely a multi-plan phase". Recommended cut (planner to confirm): Plan 01 = read-side `#[server]` fns + board fetch + WS tail consumer. Plan 02 = drag-and-drop + write-side `#[server]` fns + transition validator. Plan 03 = detail drawer + comment thread + action modals. Plan 04 = Agents-page button + wheel-nav module wiring + visual polish to Models-card parity. Plan 05 = end-to-end UAT + tests. Exact wave structure is planner's call.
- WS reconnect strategy on session close (re-establish from `last_event_id` cursor) — concrete behavior at planning.
- Optimistic-update revert UX on `#[server]` failure (toast + signal rewind vs page-level error banner) — planner's choice.
- Card-action button glyph for the drawer-open affordance ("EDIT" placeholder from Models page, or a kanban-specific glyph) — designer's choice within the existing icon set.

</decisions>

## Existing Code Insights

### Reusable Assets

- **`crates/iron_hermes_ui/src/server/ws.rs`** — Complete WebSocket lifecycle with keepalive, close-frame, RAII teardown. New kanban WS handler is a near-clone with `KanbanEvent` envelope instead of `ChatStreamEvent`.
- **`crates/iron_hermes_ui/src/server/api.rs`** — `#[cfg(feature = "server")] use ironhermes_core::types::Platform;` pattern: server-only imports gated by feature flag so the WASM client build stays unaffected. New kanban `#[server]` fns use the same gate for `ironhermes_kanban::*` imports.
- **`crates/iron_hermes_ui/src/protocol.rs`** — Wire-protocol enum colocation (request/response/stream-event types in one module). `KanbanEvent` envelope lives here.
- **`crates/ironhermes-kanban/src/tools/`** — Each tool exposes a function-call entry point that internally does store mutation + event append + side-effects. `#[server]` writes call these directly (don't re-implement validation).

### Established Patterns

- **`#[component]` + PascalCase for all components** (Dioxus 0.7.1; `cx`/`Scope`/`use_state` are forbidden). KanbanBoard, KanbanColumn, TaskCard, TaskDrawer all follow this.
- **`Signal<T>` for local mutable state, `ReadOnlySignal<T>` for read-only props, `use_resource` for async fetch.** Per `crates/iron_hermes_ui/CLAUDE.md` conventions.
- **Clippy enforces "no signal borrow across `.await`".** Optimistic updates must release the write guard *before* `spawn`ing the `#[server]` call. Pattern: clone task_id + new_status, drop write guard, then `spawn(async move { ... })`.
- **Asset constants at module top: `const NAME: Asset = asset!("/assets/...")`.** Kanban-specific assets (column icons if any) follow this pattern.
- **Conditional rendering in RSX uses `if condition { ... }`, conditional attributes use `attr: if condition { "value" }`** — informs the "drag-disallowed" visual styling on cards mid-drag.

### Integration Points

- **`iron_hermes_ui::AppState` (in `server/state.rs`)** — The dashboard tail consumer's state (broadcast sender, last-event-id watermark, per-client cursors) attaches here. Initialized in `AppState::init` alongside the existing chat-side state.
- **Wheel nav module list** — adding `KANBAN` requires touching the wheel-nav component registration site. Mirror the existing module-add pattern (CHAT / AGENTS / MODELS / etc all already register the same way).
- **Agents page top-right toolbar** — current buttons: `+ NEW AGENT`, `PRUNE ENDED`. New button: `KANBAN BOARD →` injected immediately right of `PRUNE ENDED`. Single-component change.
- **`ironhermes-kanban` re-exports needed by `iron_hermes_ui`** — currently the UI crate depends on `ironhermes-kanban` for nothing; this phase adds the dep behind `#[cfg(not(target_arch = "wasm32"))]` (matches the existing pattern for `ironhermes-state` / `ironhermes-tools`).
