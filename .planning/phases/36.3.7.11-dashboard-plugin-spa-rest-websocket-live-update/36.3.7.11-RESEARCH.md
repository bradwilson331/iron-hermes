## Summary

Phase 36.3.7.11 ships a Kanban tab inside the existing `iron_hermes_ui` HermesApp — the third surface on top of the shared `~/.hermes/kanban.db` (alongside LLM `kanban_*` tools and `hermes kanban` CLI). The implementation path is clear: mirror the existing `server/ws.rs` WS lifecycle for the tail consumer, mirror `server/api.rs` `#[server]` fn patterns for reads/writes, and add a new `Screen::Kanban` / `WheelWedge::Kanban` variant into the existing 10-wedge state machine.

The biggest coordination risks are: (1) the wheel navigation is a hardcoded 10-wedge `match` that wraps by modulo-10 — adding an 11th wedge requires updating `WheelWedge`, `Screen`, and all downstream `match` arms simultaneously; (2) drag-and-drop requires `DragEvent` in `web-sys` features (not currently listed in `Cargo.toml`, though it IS in the compiled WASM fingerprint); (3) rusqlite is `!Send` — the dashboard tail consumer must open its own `KanbanStore` (sync) inside a `tokio::task::spawn_blocking` or use `Arc<TokioMutex<KanbanStore>>` with `.await` discipline; (4) the `#[server]` write fns call directly into existing `KanbanStore` methods, which are sync and must be wrapped correctly.

**Primary recommendation:** Follow the 5-plan slice. Start with Plan 01 (walking skeleton: tab visible + real data from `fetch_board` + WS tail pushing delta events to client). Plans 02-04 build on a working board. Plan 05 is UAT.

## Key Technical Decisions (Planner Questions Answered)

### Q1 — Tail consumer attachment in AppState

**Where:** Add two fields to `AppState` in `crates/iron_hermes_ui/src/server/state.rs`:

```rust
// Dashboard kanban tail consumer state
pub kanban_tail_broadcast: tokio::sync::broadcast::Sender<String>,  // JSON-serialized KanbanWsEvent
pub kanban_tail_cancel: tokio_util::sync::CancellationToken,
```

**Lifecycle:** Spawn at `AppState::init` (alongside existing initialization), NOT lazy-on-first-client. The tail loop runs unconditionally — it polls SQLite every 250ms and sends to a `broadcast::channel`. The broadcast sender keeps events buffered; if no WS clients are subscribed the receiver count is 0 and `send()` returns `Err(SendError)`, which is silently discarded. This matches the notifier pattern exactly and requires NO guard against the loop running with no subscribers — the cost is one SQLite query every 250ms, which is negligible.

**Pattern to mirror:**
```rust
// notifier.rs: Arc<TokioMutex<KanbanStore>> + AtomicI64 watermark
// Dashboard tail: same pattern but sends to broadcast::Sender<String>
//   instead of calling send_fn.
```

**RAII guard for WS clients:** Each WS client handler subscribes via `kanban_tail_broadcast.subscribe()` (returns `Receiver`). The `Receiver` is dropped when the WS handler exits — no explicit unsubscribe needed.

**Guard against zero-client polling overhead:** None needed. 250ms poll costs ~50µs on local SSD SQLite. Accept the overhead per D-15.

### Q2 — KanbanEvent WS envelope

The `KanbanEvent` struct in `ironhermes-kanban/src/events.rs` is the DB row shape. The WS envelope wraps it. Mirror `ChatStreamEvent` pattern from `protocol.rs` — external Serde tagging, unconditional on both client and server:

```rust
// In: crates/iron_hermes_ui/src/protocol.rs  (ADD alongside ChatStreamEvent)
#[derive(Serialize, Deserialize, Debug, Clone)]
pub enum KanbanWsEvent {
    /// One or more new task_events rows since the client's last_event_id.
    /// Client applies deltas to its per-column Signal<Vec<Task>>.
    TaskEventBatch {
        events: Vec<KanbanEventRow>,
        last_event_id: i64,
    },
    /// Server-side error (DB read failure etc.)
    Error { message: String },
    /// Keepalive acknowledgement (mirrors chat WS: no payload)
    Ping {},
}

#[derive(Serialize, Deserialize, Debug, Clone)]
pub struct KanbanEventRow {
    pub id: i64,
    pub task_id: String,
    pub kind: String,           // matches KanbanEventKind::as_str()
    pub payload: Option<String>, // JSON dict
    pub created_at: f64,
}
```

The client maintains `last_event_id: Signal<i64>` initialized from `max_event_id` at board-fetch time. On reconnect, sends `{"last_event_id": N}` in the WS handshake (or re-fetches board and resets the cursor).

Wire shape (external tagging): `{"TaskEventBatch":{"events":[...],"last_event_id":42}}`.

### Q4 — Optimistic-Update Clone-and-Drop Pattern

**Clippy rule:** `clippy.toml` enforces no `GenerationalRef`, `GenerationalRefMut`, or `WriteLock` across `.await` points. The canonical pattern:

```rust
// CORRECT: drop write guard before spawn
{
    let mut w = tasks.write();           // write lock acquired
    if let Some(t) = w.iter_mut().find(|t| t.id == tid) {
        t.status = new_status.clone();
    }
}                                         // WriteLock drops HERE — before any .await

// Clone owned values needed inside the async block
let tid_owned = tid.clone();
let new_status_owned = new_status.clone();
let prev_status = /* captured before write */ prev_status.clone();

spawn(async move {
    match patch_task_status(tid_owned.clone(), None, new_status_owned, None).await {
        Ok(_) => { /* committed — nothing to do */ }
        Err(e) => {
            // Revert: acquire new write lock (no borrow outstanding)
            let mut w = tasks.write();
            if let Some(t) = w.iter_mut().find(|t| t.id == tid_owned) {
                t.status = prev_status;  // rewind
            }
            // surface toast (separate Signal<Option<String>>)
            *toast_msg.write() = Some(format!("Failed: {e}"));
        }
    }
});
```

**Existing example in codebase:** `agents.rs` lines 354-357 — `spawn(async move { let _ = api_agents_prune(None).await; agents_resource.restart(); })` shows the `spawn` without signal borrows crossing `.await`. The pattern is established.

### Q8 — Cross-process WAL visibility (D-16)

**Architecture:** The gateway process (dispatcher + 36.3.7.5 notifier) and `iron_hermes_ui` server process both open `~/.hermes/kanban.db` with `PRAGMA journal_mode=WAL`. In WAL mode:

- **Readers see a consistent snapshot** at the start of each read transaction. Each `KanbanStore.conn.query_row(...)` call implicitly begins a read transaction that sees all WAL frames committed before it started.
- **WAL checkpointing:** SQLite auto-checkpoints the WAL at 1000 pages (default `wal_autocheckpoint`). Both processes benefit from this without coordination.
- **Read-snapshot freshness:** The dashboard tail consumer's 250ms poll means each query sees events committed up to the start of that query. Events written by the gateway dispatcher are visible to the next poll cycle — maximum latency is 250ms + WAL flush time (< 1ms on SSD).
- **No read-snapshot "stuck" risk:** WAL readers do NOT block writers and vice versa. The tail consumer cannot prevent the dispatcher from writing, and the dispatcher cannot prevent the tail consumer from reading.
- **Practical concern:** `KanbanStore` opens a new connection per operation (`open_for_board` is called per-query in `show.rs`). The dashboard tail consumer should instead hold a persistent `KanbanStore` connection (opened at startup in `AppState::init`) and reuse it across ticks — avoids per-tick file-open overhead.

**WAL checkpoint cadence:** Default SQLite auto-checkpoint at 1000 WAL frames. The dashboard does not need to trigger manual checkpoints.

[VERIFIED: `store.rs` `busy_timeout(5000ms)` + `journal_mode=WAL` in `new_inner`; `notifier.rs` cross-process pattern]

### Q9 — run_decompose_or_specify entry point

**From Phase 36.3.7.10:** `KanbanDecomposeTool` and `KanbanSpecifyTool` exist in `crates/ironhermes-kanban/src/tools/decompose.rs` and `specify.rs`. However — critical finding — in v1 both tools return a `no_aux_client` rejection envelope. The actual decompose/specify kernel logic lives in `crates/ironhermes-kanban/src/decomposer.rs` (Phase 36.3.7.10's `decompose_triage_task` function) and `specifier.rs`, but the LLM tool runtime wiring is deferred.

**For the dashboard `run_decompose_or_specify` `#[server]` fn:** The `#[server]` fn should call the kernel functions directly (NOT through the tool's `execute()` method, which returns the rejection). The correct call path:

```rust
// In the #[server] fn (server-only, not WASM):
#[cfg(feature = "server")]
use ironhermes_kanban::decomposer::decompose_triage_task;
#[cfg(feature = "server")]
use ironhermes_kanban::specifier::specify_triage_task;

// Then:
match action {
    DecomposeOrSpecify::Decompose => {
        // Need to construct an AuxClient — this is the same blocker
        // the LLM tool has. If the aux_client is not available in
        // iron_hermes_ui's AppState, the #[server] fn returns the
        // same rejection the LLM tool returns.
    }
    DecomposeOrSpecify::Specify => { /* same */ }
}
```

**Policy concern:** The 36.3.7.10 decomposer requires an `AuxClient` (LLM inference client) to run. The `iron_hermes_ui` AppState has a `runtime` (AgentRuntime) which has a provider resolver. The `#[server]` fn CAN call the decomposer if it constructs an `AuxClient` from `app_state.resolver`. This is different from the LLM tool's no-client situation. **The planner should verify whether `decompose_triage_task` accepts the `AppState.resolver` as its aux client.** If yes, the dashboard's `run_decompose_or_specify` is the first surface to actually wire the decomposer. If no, return a structured "decompose_not_wired" response and tell the operator to use CLI.

## Risks and Landmines

### Risk 1: WheelWedge modulo-10 wrap is hardcoded

**What goes wrong:** `WheelWedge::from_index` wraps modulo 10 (`rem_euclid(10)`) and the match arm is exhaustive over 10 variants. Adding an 11th wedge (`Kanban`) without updating `from_index` to modulo 11 causes index 10 to silently map to index 0 (`Chat`), making the Kanban wedge unreachable by keyboard nav.

**Prevention:** Update `WheelWedge` enum, `from_index` (change 10 → 11, add match arm), `index()` (add `Kanban => 10`), `label()`, `sub()`, `glyph()`, `to_screen()` — all 6 methods together in a single commit. `Screen` enum also gains `Kanban` variant.

**Warning signs:** Navigating to index 10 selects Chat instead of Kanban.

[VERIFIED: `state.rs` lines 632-724]

---

### Risk 2: rusqlite is !Send — tail consumer thread discipline

**What goes wrong:** `KanbanStore.conn` is `rusqlite::Connection` which is `!Send`. It cannot be shared across async tasks without `Arc<TokioMutex<KanbanStore>>` and awaiting the lock. The tail consumer must NOT hold the Mutex across the broadcast send.

**Pattern (from notifier.rs):**
```rust
// CORRECT — lock scope ends before broadcast
let events = {
    let store = kanban_store.lock().await;
    store.list_events_after(watermark)?  // returns Vec, releases lock
};
// broadcast is called AFTER lock is released
tx.send(serde_json::to_string(&batch)?).ok();
```

**The dashboard tail consumer needs a NEW store method** `list_events_after(watermark: i64) -> Result<Vec<KanbanEvent>>` (not the `list_terminal_events_after` which filters to 5 terminal kinds — the dashboard shows ALL event kinds for the drawer's event stream). This method does NOT exist yet. The planner must create it in `store.rs`.

[VERIFIED: `store.rs` — `list_terminal_events_after` only returns 5 kinds; `get_events` returns all but requires `task_id`; a new `list_all_events_after(watermark)` is needed]

---

### Risk 3: DragEvent not in Cargo.toml web-sys features

**What goes wrong:** If `DragEvent` and `DataTransfer` are not explicitly listed in `Cargo.toml`'s `web-sys.features`, they may be dropped in a clean build or when the transitive dep that currently pulls them in changes. The drag-and-drop code compiles in dev but fails in CI/release.

**Prevention:** Add `"DragEvent"`, `"DataTransfer"` to the `web-sys` features array in `Cargo.toml` explicitly.

[VERIFIED: `Cargo.toml` lines 24-38 — these features are absent]

---

### Risk 4: ondrop never fires without ondragover prevent_default

**What goes wrong:** Standard HTML5 behavior — the browser's default `ondragover` handler rejects the drop, preventing `ondrop` from firing. In Dioxus 0.7.1, `event.prevent_default()` must be called inside `ondragover` (not `ondragenter`, not `ondragstart`).

**Specific Dioxus gotcha:** Dioxus 0.7.1 event objects are `Event<DragData>`. The `prevent_default()` method is on the outer `Event` wrapper, not on `DragData`. Pattern: `|event: Event<DragData>| { event.prevent_default(); }`.

**Warning signs:** Cards can be dragged but dropped items silently fail with no ondrop callback.

[ASSUMED — standard HTML5 + Dioxus event model; verify against Dioxus 0.7.1 docs if needed]

---

### Risk 5: Signal borrow across .await in optimistic updates

**What goes wrong:** Clippy panics at runtime (not compile time for some signal types) when a `WriteLock` or `GenerationalRefMut` is held across an `.await` point.

**Prevention:** Always follow the clone-and-drop pattern (Q4 above). Never:
```rust
// WRONG
let mut w = tasks.write();
w.iter_mut()...;
let _ = patch_task_status(...).await;  // WriteLock still held — panic!
```

[VERIFIED: `clippy.toml` enforces this; `CLAUDE.md` documents the rule]

---

### Risk 6: Tail consumer runs when no list_all_events_after method exists

**What goes wrong:** The dashboard needs `store.list_all_events_after(watermark)` returning ALL event kinds (for the WS delta push). Only `list_terminal_events_after` (5 kinds) and `get_events` (by task_id) exist. Without the new method, the tail can only push terminal events — missing `promoted`, `claimed`, `heartbeat`, `edited`, etc. that the drawer's event stream needs.

**Prevention:** Plan 01 Wave 0 must add `pub fn list_all_events_after(&self, watermark: i64) -> Result<Vec<KanbanEvent>>` to `store.rs` (mirrors `list_terminal_events_after` without the `kind IN (...)` filter).

[VERIFIED: `store.rs` — method survey confirms gap]

---

### Risk 7: WS reconnect cursor reset

**What goes wrong:** On WS reconnect after disconnect, the client's `last_event_id` cursor may be stale if the signal was reset. Events during the disconnect window are missed.

**Prevention:** On WS `onopen` (reconnect), the client sends its current `last_event_id` in a handshake message. The server uses that value as the starting watermark for this client's subscription, backfilling any missed events as a `TaskEventBatch`. Alternatively (simpler): on reconnect, re-fetch the full board via `fetch_board` and reset the cursor to `max_event_id`. The planner should pick one; the simpler full-refetch is recommended for v1.

[ASSUMED — WS reconnect strategy is Claude's Discretion per CONTEXT.md; full-refetch is simplest]

---

### Risk 8: Complete/Block require structured input — drawer modals are mandatory

**What goes wrong:** Attempting to route `→done` or `→blocked` through drag-and-drop (bypassing the drawer modal) would call `patch_task_status` with `prompt_payload = None`, causing the server to reject (or silently create a task with empty summary/reason, breaking the audit trail).

**Prevention:** D-10/D-11 are enforced at both client and server. The client transition validator MUST reject `→done` and `→blocked` drags immediately (show disallowed-transition hint), never reaching the `#[server]` fn. The `#[server]` fn additionally validates server-side (D-14).

[VERIFIED: `complete.rs` + `block.rs` require non-empty summary/reason per their tool schemas]

## Open Questions

1. **Decompose/Specify wiring (Q9 follow-up)**
   - What we know: `KanbanDecomposeTool.execute()` returns `no_aux_client` in v1. The kernel function `decompose_triage_task` exists but needs an `AuxClient`.
   - What's unclear: Does `iron_hermes_ui`'s `AgentRuntime` / `ProviderResolver` satisfy the `AuxClient` interface expected by `decompose_triage_task`? If so, the dashboard `run_decompose_or_specify` `#[server]` fn is the first surface to wire this correctly.
   - Recommendation: The planner should check `crates/ironhermes-kanban/src/decomposer.rs` function signature. If it matches, wire it. If not, `run_decompose_or_specify` returns `{"status":"not_wired","message":"Use hermes kanban decompose <id>"}` in v1 and this becomes a follow-up.

2. **Wheel visual spec for 11th wedge**
   - What we know: The wheel SVG is generated from `wheel-v2.js` `DEFAULT_SECTIONS` (10 entries). The prototype is React. Adding an 11th wedge may require updating CSS arc math.
   - What's unclear: Is the wheel SVG dynamically generated from the wedge count, or is it hardcoded for exactly 10 wedges? If hardcoded, adding KANBAN requires CSS changes to arc angles (360/11 instead of 360/10).
   - Recommendation: Planner should read the wheel component render logic before committing to the geometry approach.

3. **`list_all_events_after` scope**
   - What we know: The dashboard WS needs all event kinds for the board-level feed, but the drawer only shows the last 20 for a specific task.
   - What's unclear: Should the tail consumer push board-level ALL events (and the drawer subscribes to the same feed, filtering client-side by task_id)? Or should the drawer use a separate `#[server]` fn poll on open-task-changed?
   - Recommendation: Push all events via the WS tail. Client filters by `task_id` for the drawer's event list. This uses one WS connection per client rather than two.

4. **Config struct location for `DashboardConfig`**
   - What we know: `ironhermes-core/src/config.rs` already has `pub kanban: serde_yaml::Value`. Adding `pub dashboard: DashboardConfig` there is clean.
   - What's unclear: Does any existing code serialize the full `Config` struct in a way that would be broken by adding a new field with `#[serde(default)]`? Almost certainly not (default derivation handles missing YAML keys), but the planner should confirm.
   - Recommendation: Add with `#[serde(default)]` on `DashboardConfig`. No existing callers break.
