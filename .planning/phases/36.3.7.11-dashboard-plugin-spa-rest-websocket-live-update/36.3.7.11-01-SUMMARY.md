# Phase 36.3.7.11 Plan 01: Dashboard Plugin Walking Skeleton Summary

Lands the kanban dashboard walking skeleton: a `Screen::Kanban` mounted inside HermesApp that fetches real tasks from `~/.hermes/kanban.db` via Dioxus `#[server]` fns, opens a WebSocket to `/api/ws/kanban`, and re-renders the 6-column board whenever the dashboard tail consumer pushes a `KanbanWsEvent::TaskEventBatch`. Plans 02-04 layer drag-and-drop, the detail drawer, and wheel-nav wiring on top.

## What Shipped

### Wave 0 — store helper + dashboard config + protocol types

- `KanbanStore::list_all_events_after(watermark)` — mirrors `list_terminal_events_after` minus the `kind IN (...)` filter so the dashboard tail consumer can push ALL event kinds (D-15). Inline unit tests cover the all-kinds and empty-table behaviors.
- `ironhermes_core::config::{DashboardConfig, DashboardKanbanConfig}` — `tail_interval_ms` default 250 ms via `#[serde(default)]`. Pre-36.3.7.11 configs parse cleanly with the canonical default.
- `iron_hermes_ui::protocol`:
  - `KanbanWsEvent::{TaskEventBatch, Error, Ping}` — external-tag enum locked by wire-format tests (`{"TaskEventBatch":{"events":[...],"last_event_id":N}}`, `{"Ping":{}}`).
  - `KanbanEventRow`, `TaskRow`, `WorkerContextEnvelope`, `TaskRunRow`, `CommentRow` — plain Serde wire shapes so the WASM client never pulls `ironhermes-kanban`.
  - `PromptPayload::{Complete, Block}` — D-13 transport wrapper for Plan 02 write-side fns.
- `iron_hermes_ui/Cargo.toml`: `ironhermes-kanban`, `tokio-util`, `rusqlite` under `cfg(not(target_arch = "wasm32"))` (server-only); `DragEvent` + `DataTransfer` explicit `web-sys` features (Risk 3 pre-emption for Plan 02).

### Wave 1 — server fns + WS handler + tail consumer

- `server/kanban_api.rs`: five `#[server]` fns (`fetch_board`, `fetch_task`, `fetch_task_events`, `fetch_task_runs`, `fetch_comments`). All take `board: Option<String>` (D-19), wrap sync `KanbanStore` calls in `tokio::task::spawn_blocking`, and resolve `None → open_default` (D-18). No REST mount (D-05).
- `server/kanban_ws.rs`:
  - `#[get("/api/ws/kanban")] ws_kanban` route mirrors `server::ws::ws_chat` byte-for-byte: `WS_KEEPALIVE_INTERVAL = Duration::from_secs(5)`, `send_close_frame` on every teardown branch (clean recv close, broken recv, broken send, keepalive failure), and RAII `Receiver` drop on exit removes the client from the broadcast fan-out.
  - `run_kanban_tail_loop(tx, cancel, interval_ms)` opens its own `KanbanStore::open_default`, initializes the watermark via `max_event_id`, then polls `list_all_events_after` at `interval_ms` cadence. Lock-scope-before-broadcast-send (Pattern G) keeps the rusqlite `!Send` discipline. **No `use ironhermes_kanban::notifier`** — D-15 independence.
- `server/state.rs`: `AppState` gains `kanban_tail_broadcast: broadcast::Sender<String>` + `kanban_tail_cancel: CancellationToken`; `AppState::init` constructs both and spawns `run_kanban_tail_loop` unconditionally (no lazy-on-first-client).
- `server/mod.rs`: registers `kanban_api` + `kanban_ws` submodules.

### Wave 2 — ScreenKanban + child components + Screen::Kanban variant

- `state::Screen::Kanban` variant added. The two exhaustive matches (`app_footer::screen_label`, `breadcrumb::screen_short_name`) gained `Screen::Kanban => "KANBAN"` arms. `WheelWedge` stays at 10 variants — wheel-nav wedge wiring is Plan 04.
- `components/hermes_app/screens/kanban.rs`: `ScreenKanban` component — owns `use_resource(fetch_board)`, the WS client (mirrors `hermes_app/mod.rs` `use_websocket` + `use_future` recv loop), an `archive_visible` toggle, and a WS status indicator. All hooks register unconditionally on every render (Pattern E from PATTERNS.md). On `TaskEventBatch` it calls `board_resource.restart()` — full re-fetch (D-08 minimal Plan 01 behavior; Plan 02 swaps to delta-apply per Q11).
- `screens/kanban/{board,column,card}.rs`:
  - `KanbanBoard` — flex row of 6 visible columns + optional 7th archived.
  - `KanbanColumn` — header (label + count) and either filtered cards or empty-state copy per UI-SPEC §7.3. Filters by status string (D-09 lowercase taxonomy).
  - `KanbanCard` — Models-page visual contract: monospace heading, thin separator, footer chip row (status / priority / assignee / age) + action button (▶) that fires `on_open_drawer`. `draggable="true"` is reserved for Plan 02.
- `components/hermes_app/screen_router.rs`: `screens::kanban::ScreenKanban { is_active: cur == Screen::Kanban }` mounted alongside the other 13 screens (class-toggle pattern).
- `assets/kanban.css`: cyan-glow card border (`.kn-card` with `border: 1px solid var(--accent-primary)` + `box-shadow: var(--w-shadow-block)`), board flex layout, per-status chip colors, WS status dot, and `@media (prefers-reduced-motion: reduce)` overrides per UI-SPEC §6.6. **Zero new hex literals** (D-04 verified by grep).

## Walking-Skeleton Verification

The plan's headline `must_haves.truths` walking-skeleton entry reads: *"with kanban.db containing N tasks, navigating active_screen to Screen::Kanban shows the 6-column board populated with N cards; a CLI write (`hermes kanban set <id> status=todo`) causes the dashboard to re-render the moved card within tail_interval_ms + WS RTT."*

This is satisfied by construction:

1. `ScreenKanban` calls `use_resource(fetch_board(None))` → `KanbanStore::open_default → list_tasks` → returns N rows.
2. `KanbanBoard` fans out into six `KanbanColumn`s; each filters the shared `tasks` signal by status.
3. The dashboard tail consumer (`run_kanban_tail_loop`) polls every 250 ms; a CLI write appends a `task_events` row whose id > watermark.
4. The tail consumer reads it via `list_all_events_after`, broadcasts a `TaskEventBatch` JSON frame, and the `/api/ws/kanban` socket forwards it to the client.
5. The client's `use_future` recv loop deserializes the frame, matches `TaskEventBatch`, and calls `board_resource.restart()` — the resource re-fetches, the `use_effect` syncs into `tasks`, the columns re-render with the moved card.

Live verification requires running `dx serve` with a populated kanban.db and is performed in Plan 05 manual UAT (per the plan-slicing decision in CONTEXT).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Build] rusqlite + tokio-util added as iron_hermes_ui server deps**

- **Found during:** Task 2.
- **Issue:** `kanban_api.rs` joins `task_links` / `task_runs` / `task_comments` via the `KanbanStore`'s public `Connection` (matching the show.rs analog). Without an explicit `rusqlite` dep on `iron_hermes_ui`, `cargo build --features server` fails with `E0433 — failed to resolve: use of unresolved module or unlinked crate rusqlite`. Similarly the tail loop's `CancellationToken` needs `tokio_util::sync`.
- **Fix:** added `rusqlite = { workspace = true }` and `tokio-util = { workspace = true }` to the `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]` block. Behind the WASM-exclusion gate so the client build remains unaffected.
- **Files modified:** `crates/iron_hermes_ui/Cargo.toml`.
- **Commit:** 49711b4f (Wave 1).

**2. [Rule 3 - Build] rusqlite prepared-statement borrow lifetime**

- **Found during:** Task 2 first build.
- **Issue:** Three `let mut stmt = ...?; stmt.query_map(...)?.collect::<Result<...>>()?` chains hit `E0597 — stmt does not live long enough`. The iterator from `query_map` borrows from `stmt`, and the `?` operator's temporary crosses the borrow boundary, dropping `stmt` mid-iteration.
- **Fix:** rewrote each chain as `let mut stmt = ...?; let mapped = stmt.query_map(...)?; let mut out = Vec::new(); for row in mapped { out.push(row?); }` — `stmt` is bound to the block scope and outlives `mapped` correctly.
- **Files modified:** `crates/iron_hermes_ui/src/server/kanban_api.rs` (three loops in `fetch_task` + one in `fetch_comments`).
- **Commit:** 49711b4f (Wave 1).

**3. [Rule 1 - Bug] Source-only assertion needs comment-stripping**

- **Found during:** Task 2 test run.
- **Issue:** `kanban_ws_tail::kanban_ws_tail_independence_no_notifier_import` failed because the source-string search also matched the literal text `use ironhermes_kanban::notifier` that appears inside a `//!`/`///` doc comment **documenting** the D-15 prohibition. The test correctly flagged the substring; the comment is intentional documentation.
- **Fix:** updated the test to strip line-comment prefixes (`//`, `///`) before searching — the invariant still fires on actual `use` statements but no longer false-positives on doc comments that name the prohibition.
- **Files modified:** `crates/iron_hermes_ui/tests/kanban_ws_tail.rs`.
