### 2.2 Cyan-Glow Border Specification

The card border is the primary design signature (D-01). It is defined in terms of the existing warp-ih Warp block shadow pattern, extended with a cyan outer glow:

```css
/* Kanban card cyan-glow border — new in kanban.css */
.kn-card {
  border: 1px solid var(--accent-primary);          /* solid 1px cyan */
  box-shadow:
    0 0 0 1px color-mix(in srgb, var(--accent-primary) 40%, transparent),  /* soft halo */
    0 0 8px  color-mix(in srgb, var(--accent-primary) 20%, transparent),   /* diffuse glow */
    var(--w-shadow-block);                            /* Warp base shadow */
  border-radius: var(--w-radius-block);              /* 6px — Warp-style */
}

/* Hover: glow intensifies */
.kn-card:hover {
  border-color: var(--accent-primary-hi);
  box-shadow:
    0 0 0 1px color-mix(in srgb, var(--accent-primary-hi) 60%, transparent),
    0 0 12px color-mix(in srgb, var(--accent-primary-hi) 30%, transparent),
    var(--w-shadow-block);
}

/* Drag source: glow suppressed, card opacity reduces */
.kn-card[data-dragging="true"] {
  opacity: 0.55;
  box-shadow: var(--w-shadow-block);
}

/* Optimistic-pending pulse */
.kn-card[data-pending="true"] {
  animation: kn-pending-pulse 1.4s ease-in-out infinite;
}
@keyframes kn-pending-pulse {
  0%, 100% { border-color: var(--accent-primary); }
  50%       { border-color: var(--ansi-yellow); box-shadow: 0 0 8px color-mix(in srgb, var(--ansi-yellow) 25%, transparent), var(--w-shadow-block); }
}
```

Screen-reader note: the glow border is decorative. Status meaning is always conveyed by the status chip text label, not by border color alone.

### 2.3 Spacing Scale

Uses the existing 4-point grid from `tokens.css` (`--sp-N` variables). Only standard-set values {4, 8, 16, 24, 32, 48, 64} are used. Kanban-specific applications:

| Token | Value | Kanban Usage |
|-------|-------|--------------|
| `--sp-1` | 4px | Chip internal padding (vertical), checkbox slot gap |
| `--sp-2` | 8px | Card inner padding (compact + standard), chip gap, icon-text gap, column header padding |
| `--sp-4` | 16px | Column gap, drawer section gap, modal padding, column header padding (preferred — see note) |
| `--sp-6` | 24px | Toolbar height padding, drawer header padding |
| `--sp-7` | 32px | Board outer padding (horizontal) |
| `--sp-9` | 48px | — |
| `--sp-10` | 64px | — |

Card padding note: compact card inner padding uses `--sp-2` (8px). Column header padding uses `--sp-4` (16px) — this produces a closer visual match to `Kanban-main-view.png` than 8px would.

Exceptions:
- Touch targets for action buttons: minimum 44px height (WCAG 2.5.5 AAA / 2.5.8 AA). Applied via `min-height: 44px` on `.kn-action-btn`. This 44px value is a WCAG-mandated minimum and is not part of the spacing scale.
- Drag handle / card drag zone: minimum 44px height on mobile viewports (≤768px). Same WCAG justification.

### 2.7 Motion

| Interaction | Animation | Duration | Easing | Reduced-motion fallback |
|------------|-----------|----------|--------|------------------------|
| Drawer open/close | `transform: translateX(0/100%)` | 200ms | `--ease-out` | Instant (no transition) |
| Modal appear | `opacity 0→1, scale 0.96→1` | 150ms | `--ease-out` | Instant |
| Toast appear/dismiss | `opacity 0→1` slide up 8px | 180ms | `--ease-out` | Instant |
| Drag preview | Card follows pointer natively (HTML5 DnD ghost) | native | native | Native (no JS animation) |
| Optimistic pulse | `kn-pending-pulse` keyframe (border color oscillates) | 1.4s infinite | ease-in-out | `animation: none` |
| Card snap-back (revert) | Signal resets status → card returns to original column on next render | ~16ms (next frame) | n/a | Same (no CSS transition on column position) |
| Column drop-target highlight | `transition: box-shadow 80ms` | 80ms | linear | Instant |

`@media (prefers-reduced-motion: reduce)` block in `kanban.css` sets all kanban animations to `none` and all transitions to `0ms`.

### 6.3 Keyboard Alternative to Drag-and-Drop

Per WAI-ARIA Authoring Practices for drag-and-drop, a keyboard alternative MUST be provided. Implementation:

When a card has focus, `Ctrl+Right` / `Ctrl+Left` (Mac: `Cmd+Right` / `Cmd+Left`) trigger the same logic as a drag-and-drop:

1. Client-side transition validator runs (`is_drag_allowed(current_status, target_status)`).
2. If allowed: optimistic update fires, `#[server]` call spawned, live-region announces move.
3. If disallowed: no state change; live-region announces the rejection copy (see §6.5 below).

Transitions to DONE and BLOCKED via keyboard are disallowed by the same validator as drag — those require the action buttons in the drawer (Complete… / Block…).

## 8. Interaction Contracts

### 8.1 Drag-and-Drop

Full spec based on D-06 blueprint:

1. **Drag start**: `ondragstart` sets `dragged_task_id = Some(task_id)`. Card receives `data-dragging="true"` (opacity 0.55, glow suppressed). `cursor: grabbing` on `body` during drag.
2. **Drag over column**: `ondragover` MUST call `event.prevent_default()` (otherwise `ondrop` never fires — Risk 4 in RESEARCH.md). Column validates `is_drag_allowed(current_status, target_status)` and sets visual state (valid/invalid target highlight) using CSS attribute or class.
3. **Drop on valid column**: `ondrop` fires:
   a. Clone `task_id` and `new_status` as owned values.
   b. Add `task_id` to `pending_task_ids`.
   c. Write optimistic update to `tasks` signal (mutate in-place, change `.status`). Write guard MUST be dropped before `spawn`.
   d. `spawn(async move { patch_task_status(...).await })`.
   e. On success: remove from `pending_task_ids`.
   f. On error: revert signal (write guard re-acquired in spawn body), remove from `pending_task_ids`, show toast.
4. **Drop on invalid column**: `ondrop` fires, `is_drag_allowed` returns false, no signal mutation, no `#[server]` call. Column disallowed-hint copy appears as a tooltip/overlay. Live-region announces hint.
5. **Drag end** (cancelled or completed): `ondragend` sets `dragged_task_id = None`. All column highlights reset.
6. **Drag to ARCHIVED**: always allowed per D-10 but triggers `ArchiveConfirmModal` on drop — the actual `#[server]` call only fires if the user confirms. If cancelled, `dragged_task_id = None`, no state change.

Cursor states:
- Card at rest: `cursor: default`
- Card on hover: `cursor: grab`
- During drag: `cursor: grabbing` (applied to `body`)
- Over invalid drop target: `cursor: not-allowed`

### 8.2 Drawer Open / Close

- **Open trigger**: click on card action button (`▶`). Sets `open_drawer_task_id = Some(task_id)`. Drawer slides in from right (200ms, `translateX` from `+480px` to `0`).
- **Close triggers**:
  - Click the `✕` close button in drawer header.
  - Press `Escape` key (when focus is in drawer or no modal is open over it).
  - Do NOT close on backdrop click (clicking the board behind the drawer does not dismiss — avoids accidental dismissal during swarm supervision per design intent).
- **Backdrop**: no visual backdrop on the board. The board remains visible and partially interactive.
- **Multiple opens**: opening a different card while drawer is open replaces content without closing/reopening animation (slide content swap, no re-animation).

### 8.3 Modal Stacking Rules

- Only one modal can be open at a time.
- Drawer can be open simultaneously with one modal. Focus is in the modal when modal is open; closing the modal returns focus to the drawer.
- Modal opens on top of drawer (z-index 300 > drawer z-index 200).
- Modal overlay covers the drawer.
- Escape closes the frontmost modal. A second Escape then closes the drawer.

### 8.4 Live-Region Update Cadence

- WS `TaskEventBatch` events are applied to signals on receipt.
- Live-region announcements are debounced: max one announcement per 500ms. During a burst, a summary "N board updates" is announced after the debounce window.
- Drawer refresh: when a `TaskEventBatch` contains events for the currently-open task, the drawer sub-section (comments / events / runs) re-fetches via `use_resource` restart after a 200ms debounce. This prevents flickering during rapid event bursts.
- Board re-render: signal mutations cause Dioxus to re-render only the affected column(s). Not a full board refresh.

### 8.5 WS Reconnect Strategy (v1)

On WS disconnect detected (recv error or keepalive Ping failure):
1. Client transitions `ws_state` to `Reconnecting`.
2. Toast: "Live updates paused — reconnecting…"
3. Client attempts reconnect after 1s, then 2s, then 5s (exponential backoff cap 5s).
4. On successful reconnect: client calls `fetch_board` (full re-fetch, resets cursor to `max_event_id`). This is the simpler v1 strategy per RESEARCH.md Risk 7.
5. Toast: "Live updates resumed."
6. `ws_state` → `Connected`.
