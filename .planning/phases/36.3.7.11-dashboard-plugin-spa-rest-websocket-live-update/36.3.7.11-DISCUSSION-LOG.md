## HTTP surface shape

| Option | Description | Selected |
|--------|-------------|----------|
| Axum REST + thin client wrappers | Mount axum router at `/api/plugins/kanban/*`. Dioxus client calls via `fetch`. Matches Python ref + ROADMAP literal scope. External CLI/scripts reachable. | |
| Dioxus #[server] functions only | Skip explicit REST. `#[server] fn fetch_board()` etc. Tighter Dioxus coupling, type-safe, no external HTTP clients. | ✓ |
| Both — REST + #[server] wrappers | Explicit REST as canonical surface; #[server] fns wrap them server-side. Redundant indirection. | |

**User's choice:** Dioxus #[server] functions only.
**Notes:** User followed up with a detailed code blueprint locking in: `use_resource` for reads, `spawn(async move { ... })` for mutations, optimistic `Signal<Vec<Task>>` updates before await, HTML5 native drag-and-drop (`draggable: "true"`, `ondragstart`/`ondragend` updating `dragged_task_id: Signal<Option<TaskId>>`, `ondragover` MUST call `event.prevent_default()`, `ondrop` reads signal and fires #[server] mutation). The blueprint code is the literal implementation contract for downstream agents.
**Deviation note:** Deliberately supersedes the ROADMAP's literal "REST API" wording. Phase intent ("expose the kanban surface to the dashboard") is preserved; explicit REST is rejected to avoid double surface area and keep type-safety end-to-end.

## Write surface & drag rules

| Option | Description | Selected |
|--------|-------------|----------|
| Allowed-transition subset + 4 write fns | Drag only: triage→todo, todo→ready, blocked→ready, any→archived (with confirm). DONE/BLOCKED via drawer buttons. v1 writes: patch_task_status, post_comment, create_task, run_decompose_or_specify. | ✓ |
| Free drag with confirms + auto-prompts | Any column-to-column drag. Modal prompts for summary/reason mid-drag. More freedom, more modal interrupts. | |
| Read-only board for v1 | No writes. Pure visualization. Decompose/Specify/Complete/Block stay CLI + LLM tools. | |
| Full write parity with Python ref | Bulk actions, inline create, multi-select, drag-to-trash, editable drawer fields, dependency editor. ~2x plans. | |

**User's choice:** Allowed-transition subset + 4 write fns.
**Notes:** Rationale: kanban_complete and kanban_block require structured input (summary / reason) — letting drag silently bypass those would either drop the handoff or insert empty rows, both of which break attempt-history audits. RUNNING is dispatcher-owned per the worker-lanes contract; UI writes to it would race claim transactions. Drawer hosts dedicated buttons for the constrained-input transitions.

## WebSocket source pattern

| Option | Description | Selected |
|--------|-------------|----------|
| Dashboard-specific tail consumer | iron_hermes_ui server tails task_events at ~250ms with since=event_id. WS pushes deltas. Independent of 36.3.7.5 notifier. Future swap to in-process broadcast is API-compatible. | ✓ |
| Extract shared task_events_tail primitive | Refactor 36.3.7.5 notifier to consume a shared `task_events_tail(since, kinds_filter)` primitive. DRY but touches just-shipped notifier code; risks regressions. | |
| Fanout hook on existing notifier | Add `Vec<EventSink>` to 36.3.7.5 notifier loop. Dashboard registers a sink. Single poll for both consumers. Tight coupling. | |
| Defer to research | Let gsd-phase-researcher investigate dispatcher/notifier process model before locking. | |

**User's choice:** Dashboard-specific tail consumer.
**Notes:** Cross-process boundary (dispatcher + 36.3.7.5 notifier in gateway process; dashboard in iron_hermes_ui server process) rules out in-process broadcast for v1. 250ms tail gives <300ms perceived latency = "feels live". WS contract stays identical if iron_hermes_ui later embeds the dispatcher and we swap the tail for an in-process broadcast::Receiver.

## Auth model

| Option | Description | Selected |
|--------|-------------|----------|
| Reuse existing session model | Kanban #[server] fns inherit iron_hermes_ui's current auth. WS mirrors server/ws.rs TypedWebsocket pattern. Localhost-bind = deployment-level threat model. | ✓ |
| Explicit dashboard-plugin auth middleware | New middleware gating only /api/plugins/kanban/* style fns. Useful for external CLI scripts with separate tokens. Adds surface area. | |
| Read-only without auth + writes require token | GET-shaped fns unauthenticated; PATCH/POST require token. Complicates the #[server] split. | |

**User's choice:** Reuse existing session model.
**Notes:** Localhost-bind matches Python ref threat model. Avoids two divergent auth surfaces in one app. Future retrofit (per-user tokens, remote dashboards) is a localized change to #[server] fn signatures.
