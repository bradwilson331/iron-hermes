## Wiring Gap (the reason Tasks 3-5 are BLOCKED)

Operator verification at the Task 3 checkpoint produced:

```
$ IRONHERMES_HOME=/tmp/uat-36.17.5-home target/release/ironhermes toolset list
TOOLSET    STATUS     TOOLS   AVAILABLE
memory     enabled    1       1/1 (memory ✓)

browser    disabled   11      11/11 ...

$ ironhermes toolset show voice
Error: unknown toolset 'voice' — known toolsets: agent, browser, code, learning, memory, session, skills, web
```

`voice` toolset is absent from CLI inspection output despite `ALL_TOOLSETS` containing it.

### Root Cause (two missing wires)

1. **`cmd_toolset_list` does NOT call `register_tts_tools`.**
   `crates/ironhermes-cli/src/toolset_cmd.rs::cmd_toolset_list` builds a fresh
   `ToolRegistry::new()` and calls only `register_defaults()`. PLAN 03's
   `register_tts_tools(session_key, dispatcher, config)` is invoked only inside
   `build_app_runtime_bundle` — a code path the toolset commands never enter.
   Even if PLAN 03's `session_key=Some(...)` wiring were threaded through the
   agent CLI startup, the **toolset inspection commands have a SEPARATE registry
   construction path** that bypasses it entirely.

2. **`toolset_members_map()` has no `"voice"` entry.**
   The static map in `toolset_cmd.rs` (keyed by toolset name → tool list) is the
   data source for `toolset list` and `toolset show <name>`. `"voice"` is
   missing from this map, so even if the registry were populated, the CLI
   would print `unknown toolset 'voice'`. Adding it to `ALL_TOOLSETS`
   (Plan 01) updated the constants module but did NOT update the CLI's
   parallel lookup table.

### Why Rule 4 (architectural) and not Rules 1-3 (auto-fix)

Closing this gap requires:
- Threading a synthetic `SessionKey::new(Platform::Local, "cli-inspection")` (or `None`-with-fallback) through the `cmd_toolset_list` code path, OR
- Refactoring `cmd_toolset_list` to call `build_app_runtime_bundle` (which carries downstream consequences — agent-runtime startup side-effects, config dependency, async-ness in a sync command path), OR
- Adding a separate "registry-for-inspection" factory that calls `register_defaults() + register_tts_tools()` without the agent-runtime baggage, AND
- Adding `"voice" → ["text_to_speech", "send_audio"]` to `toolset_members_map()` (or refactoring it to derive from registry state instead of a hardcoded table).

Each option has trade-offs that warrant planning (Rule 4: ask), not inline auto-fix (Rules 1-3). The gap was not visible from PLAN 03's invariant test suite because that test exercises `register_tts_tools` against a freshly-constructed `ToolRegistry::new()` directly — it does NOT exercise the CLI startup paths that bypass `build_app_runtime_bundle`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] rustls CryptoProvider not installed before Edge TTS WebSocket TLS handshake**
- **Found during:** Task 2 verification (`cargo run -p ironhermes-cli -- tts test` panicked with `Could not automatically determine the process-level CryptoProvider from Rustls crate features`)
- **Issue:** `msedge-tts 0.4` tokio-runtime feature pulls in `rustls 0.23` + `tokio-rustls` but NOT a `rustls` crypto-provider feature. The default-provider auto-detection only works when exactly one of `aws-lc-rs` / `ring` is enabled directly by the consuming crate. Transitive enabling via reqwest's `rustls-tls` feature does NOT satisfy this constraint.
- **Fix:** Added `rustls = "0.23"` as a direct dep of `ironhermes-cli` (Cargo.toml) and dev-dep of `ironhermes-tools`. Call `rustls::crypto::aws_lc_rs::default_provider().install_default().ok()` at the top of `cmd_tts_test` and at the top of `test_edge_synth_writes_file`. `.ok()` is intentional — the call is idempotent across tests in the same binary.
- **Files modified:** `crates/ironhermes-cli/src/main.rs`, `crates/ironhermes-cli/Cargo.toml`, `crates/ironhermes-tools/tests/tts_tools.rs`, `crates/ironhermes-tools/Cargo.toml`
