## Summary

This phase ports Python hermes-agent's `TTSProvider` ABC and two built-in providers (Edge TTS and ElevenLabs) into IronHermes (Rust). The architecture is a faithful concept-level port: a `TtsProvider` trait + `TtsRegistry` in `ironhermes-core`, provider impls + two LLM-callable tools in `ironhermes-tools`, and Telegram delivery wiring in `ironhermes-gateway`.

The most important research outcome is the **Edge TTS crate selection**: the crate named `edge-tts-rust` referenced in `tts-idea.txt` does not exist on crates.io. The actual crate to use is `msedge-tts` (GitHub: `hs-CN/msedge-tts`, version 0.3.0, published ~3 months before research date). A second viable option is `edge-tts-rs`. Both expose a `synthesize()` method returning raw audio bytes. This decision is Claude's Discretion per CONTEXT.md.

The `SendAudioTool` presents the only non-trivial architectural question: `Tool::execute()` takes only `args: serde_json::Value` — no per-turn context. Platform + chat_id must be **constructor-injected** (same pattern as `CronjobTool` carries `Arc<Mutex<JobStore>>`). The existing `TelegramAdapter::send_audio()` method (added in Phase 36.17.2.2) already implements the Telegram audio-attachment path. A new `register_tts_tools()` method on `ToolRegistry` follows the `register_cronjob_tool()` / `register_browser_tools()` pattern.

**Primary recommendation:** Use `msedge-tts` for Edge TTS synthesis (most downloads, actively maintained). Inject `Arc<TelegramAdapter>` + `SessionKey` into `SendAudioTool` at construction time through `app_runtime_factory.rs`. Use `std::process::Command` (not the `which` crate) to probe ffmpeg at startup and cache the boolean in a `std::sync::OnceLock<bool>` (already the project-preferred lazy-init pattern).

### Pattern 1: TtsProvider Trait (ironhermes-core)

```rust
// Source: ported from tts_provider.py D-09 trait surface
use async_trait::async_trait;
use std::path::PathBuf;

#[async_trait]
pub trait TtsProvider: Send + Sync {
    fn name(&self) -> &str;
    fn display_name(&self) -> &str { self.name() }
    fn is_available(&self) -> bool;
    fn voice_compatible(&self) -> bool { false }
    async fn synthesize(&self, text: &str, output_path: &PathBuf) -> anyhow::Result<PathBuf>;
}
```

**Object safety note:** `async fn` in traits requires `async-trait` (already a workspace dep) OR Rust 2024 RPITIT. The project uses `async-trait` throughout (`web_search.rs` line 31). Use `#[async_trait]` on both the trait and every impl — this is the established project pattern. `Arc<dyn TtsProvider + Send + Sync>` is object-safe with `async-trait` because the macro desugars to `Pin<Box<dyn Future>>`. ### Pattern 2: TtsRegistry (ironhermes-core)

```rust
// Source: ported from tts_registry.py D-10 built-ins-always-win invariant
use std::collections::HashMap;
use std::sync::Arc;

pub const BUILTIN_TTS_NAMES: &[&str] = &["edge", "elevenlabs"];

pub struct TtsRegistry {
    providers: HashMap<String, Arc<dyn TtsProvider>>,
}

impl TtsRegistry {
    pub fn new() -> Self { Self { providers: HashMap::new() } }

    pub fn register(&mut self, provider: Arc<dyn TtsProvider>) {
        let key = provider.name().to_lowercase();
        if BUILTIN_TTS_NAMES.contains(&key.as_str()) {
            // Built-ins are inserted unconditionally at startup
            self.providers.insert(key, provider);
            return;
        }
        // Future non-built-in registrations: warn-and-ignore (D-10)
        tracing::warn!("TtsRegistry::register: '{}' is not in BUILTIN_TTS_NAMES; ignored", key);
    }

    pub fn get(&self, name: &str) -> Option<Arc<dyn TtsProvider>> {
        self.providers.get(&name.to_lowercase()).cloned()
    }
}
```

**Note:** Phase v1 ONLY registers two built-ins at `register_defaults()` time. The "reject non-built-ins" logic is future-proofing for the point when external providers are introduced. For v1, `register()` is called only by `register_tts_tools()` with the two built-in instances. [CITED: tts_registry.py — `_BUILTIN_NAMES = frozenset({...})` pattern]

### Pattern 4: ElevenLabs Provider (mirrors web_search.rs)

```rust
// Source: web_search.rs pattern — per-call reqwest::Client::new(), env-var key check
use async_trait::async_trait;
use ironhermes_core::tts::TtsProvider;

pub struct ElevenLabsProvider {
    config: ElevenLabsConfig,
}

#[async_trait]
impl TtsProvider for ElevenLabsProvider {
    fn name(&self) -> &str { "elevenlabs" }
    fn is_available(&self) -> bool {
        std::env::var("ELEVENLABS_API_KEY").is_ok()
    }
    fn voice_compatible(&self) -> bool { true }   // Opus output = inline voice bubble

    async fn synthesize(&self, text: &str, output_path: &PathBuf) -> anyhow::Result<PathBuf> {
        let api_key = std::env::var("ELEVENLABS_API_KEY")
            .map_err(|_| anyhow::anyhow!("ELEVENLABS_API_KEY not set"))?;

        // Truncate to ElevenLabs cap: eleven_multilingual_v2 = 10000 chars
        let text = if text.len() > 10000 { &text[..10000] } else { text };

        let client = reqwest::Client::new();  // per-call, matches web_search.rs line 92
        let url = format!(
            "https://api.elevenlabs.io/v1/text-to-speech/{}",
            self.config.voice_id
        );
        let response = client
            .post(&url)
            .header("xi-api-key", &api_key)
            .json(&serde_json::json!({
                "text": text,
                "model_id": self.config.model_id,
                "output_format": "mp3_44100_128"  // or "opus_48000_128" when output_path ends in .opus
            }))
            .send()
            .await
            .map_err(|e| anyhow::anyhow!("ElevenLabs HTTP request failed: {}", e))?;

        let status = response.status();
        if !status.is_success() {
            // ElevenLabs error shape: {"detail": {"type": "...", "code": "...", "message": "..."}}
            let body = response.text().await.unwrap_or_default();
            return Err(anyhow::anyhow!("ElevenLabs API {} error: {}", status, body));
        }

        let bytes = response.bytes().await
            .map_err(|e| anyhow::anyhow!("Failed to read ElevenLabs response: {}", e))?;
        tokio::fs::write(output_path, &bytes).await
            .map_err(|e| anyhow::anyhow!("Failed to write audio file: {}", e))?;
        Ok(output_path.clone())
    }
}
```

[VERIFIED: web_search.rs — `std::env::var("FIRECRAWL_API_KEY")` in both `is_available()` and `execute()`; `reqwest::Client::new()` per call at line 92]
[CITED: elevenlabs.io/docs/api-reference/text-to-speech/convert — endpoint, xi-api-key header, output_format field]

### Pattern 7: ffmpeg MP3 → Opus Conversion for Telegram Voice Bubbles

```bash
# Verified format per voice-mode.md + tts.md "Telegram Voice Bubbles & ffmpeg" section
ffmpeg -i input.mp3 -c:a libopus -b:a 64k -ar 48000 -ac 1 output.ogg
```

The output **must** be:
- Container: OGG (`.ogg` extension — Telegram Bot API `sendVoice` requires OGG container)
- Codec: libopus (`-c:a libopus`)
- Sample rate: 48000 Hz (`-ar 48000`)  
- Channels: mono (`-ac 1`) — voice messages are mono
- Bitrate: 64k (`-b:a 64k`) — sufficient for voice; Telegram accepts 32–192 kbps

The `-application voip` flag is valid but redundant for a file conversion; libopus defaults to `audio` application mode. For voice bubbles, mono + 48kHz + libopus is what matters.

[CITED: tts.md §"Telegram Voice Bubbles & ffmpeg" — "ffmpeg converts MP3 → Opus"; voice-mode.md §"Platform Delivery" table — "Opus/OGG" required for Telegram voice bubble]
[CITED: shashwatv.com/parse-audio-to-ogg-opus-telegram/ — confirms libopus + OGG container]

**Rust invocation:**
```rust
tokio::process::Command::new("ffmpeg")
    .args(["-i", input.to_str().unwrap(), "-c:a", "libopus",
           "-b:a", "64k", "-ar", "48000", "-ac", "1",
           "-y", output.to_str().unwrap()])
    .output()
    .await
    .map_err(|e| anyhow::anyhow!("ffmpeg conversion failed: {}", e))?;
```

### Pattern 8: TextToSpeechTool execute()

```rust
// Source: tts-idea.txt "Tool Logic Example" (Path B prototype, adapted)
async fn execute(&self, args: serde_json::Value) -> anyhow::Result<String> {
    let text = args["text"].as_str()
        .ok_or_else(|| anyhow::anyhow!("Missing required parameter: text"))?;

    // Determine output path
    let output_path = if let Some(p) = args["output_path"].as_str() {
        PathBuf::from(p)
    } else {
        let audio_dir = get_hermes_home().join("audio_cache");
        std::fs::create_dir_all(&audio_dir)
            .map_err(|e| anyhow::anyhow!("Failed to create audio_cache dir: {}", e))?;
        let ext = if provider_name == "elevenlabs" && use_opus { "opus" } else { "mp3" };
        audio_dir.join(format!("{}.{}", uuid::Uuid::new_v4(), ext))
    };

    let provider = self.registry.get(&self.config.tts.provider)
        .ok_or_else(|| anyhow::anyhow!(
            "TTS provider '{}' not available or not registered",
            self.config.tts.provider
        ))?;

    // Truncate text (Edge: 5000 chars, ElevenLabs: 10000 chars for eleven_multilingual_v2)
    let provider_result = provider.synthesize(text, &output_path).await?;
    Ok(provider_result.to_string_lossy().to_string())
}
```

## Common Pitfalls

### Pitfall 1: Telegram sendVoice Codec/Container Confusion

**What goes wrong:** Uploading an MP3 file to `sendVoice` instead of `sendAudio`. The file uploads without error but Telegram silently renders a broken voice bubble (no spectrogram, duration = 0, or rejects the upload).

**Why it happens:** `sendVoice` REQUIRES OGG container + Opus codec. Any other format is rejected or rendered as a broken bubble. `sendAudio` accepts MP3 and renders as a rectangular music player.

**How to avoid:** The dispatch logic in `SendAudioTool`:
- File extension `.ogg` or `.opus` → `send_voice()` (Bot API: `sendVoice`)
- File extension `.mp3` + ffmpeg present → convert to `.ogg` → `send_voice()`
- File extension `.mp3` + ffmpeg absent → `send_audio()` (Bot API: `sendAudio`, rectangular player)

**Warning signs:** Voice bubble renders with no playback controls or Telegram returns error code 400 `"Bad Request: VOICE_MESSAGES_FORBIDDEN"` (wrong format for sendVoice).

[CITED: tts.md §"Telegram Voice Bubbles & ffmpeg" — "Without ffmpeg, Edge TTS...sent as regular audio files (playable, but shown as a rectangular player)"]

### Pitfall 2: ElevenLabs 429 vs Quota vs Voice-Not-Found

**What goes wrong:** `anyhow::bail!("HTTP 429")` lumps rate-limit and quota exhaustion together, making debugging harder. Voice-not-found may return 400, not 404.

**Why it happens:** ElevenLabs error structure:
```json
{
  "detail": {
    "type": "rate_limit_error",        // or "authentication_error", "validation_error"
    "code": "rate_limit_exceeded",     // or "concurrent_limit_exceeded", "invalid_voice_id"
    "message": "Too many requests",
    "request_id": "..."
  }
}
```

**How to avoid:** Surface the full JSON body in the `anyhow` error message (already done in Pattern 4 above — `body` is logged). The `code` field distinguishes quota (`quota_exceeded`) from rate-limit (`rate_limit_exceeded`) from bad voice ID (`invalid_voice_id`). Since D-11 locks us to `anyhow`, include both `status` and `body` in the error string.

[CITED: elevenlabs.io/docs/eleven-api/resources/errors — error JSON shape]

### Pitfall 3: `Arc<dyn TtsProvider>` Object Safety

**What goes wrong:** Adding a non-object-safe method to `TtsProvider` (e.g., a generic `fn synthesize<P: AsRef<Path>>(...)`) causes `Arc<dyn TtsProvider>` to fail to compile.

**Why it happens:** Rust's object safety rules prohibit generics on trait methods when using `dyn Trait`.

**How to avoid:** Keep all trait methods concrete. Use `&PathBuf` (not generic). The `async-trait` crate desugars `async fn` to `Pin<Box<dyn Future + Send>>` which IS object-safe. [VERIFIED: async-trait is already used with `Tool: Send + Sync` throughout the codebase]

### Pitfall 4: `SendAudioTool` Receiving Wrong `SessionKey`

**What goes wrong:** `register_tts_tools()` is called once at bundle construction with the session key of the *first* message. For the gateway (which handles multiple simultaneous chats), every session's `SendAudioTool` would deliver to the same chat_id.

**Why it happens:** `Tool::execute()` has no per-turn context parameter. Constructor injection locks in the session key at registration time.

**How to avoid:** `register_tts_tools()` must be called **per-session** (per `MessageEvent`), not once at process startup. This is the same pattern as `register_browser_tools()` — the `browser_session` Arc is per-AgentLoop instance. The `AppRuntimeBundle` pattern (one bundle per gateway session) already handles this correctly. The planner must verify that `build_app_runtime_bundle()` is called per session in the gateway handler, not once at startup. [VERIFIED: app_runtime_factory.rs — bundle is constructed per invocation, not as a singleton]

### Pitfall 5: msedge-tts Audio Format Is Not MP3 by Default

**What goes wrong:** `msedge-tts` defaults to a different audio format (e.g., WAV or WebM). Writing the raw bytes to `<uuid>.mp3` produces a file with incorrect extension and format mismatch that rodio or Telegram may reject.

**Why it happens:** Edge TTS API is a WebSocket-based streaming protocol; the format must be set in `SpeechConfig`. The crate's docs confirm: "Make sure you know the right voice name and audio format."

**How to avoid:** Explicitly set `output_format` in `SpeechConfig` to `audio-24khz-48kbitrate-mono-mp3` (or equivalent MP3 constant from the crate) before calling `synthesize()`. Verify the exact constant name from `msedge-tts` docs at implementation time. [ASSUMED — msedge-tts SpeechConfig format constants need implementation-time verification]

### Pitfall 6: `create_dir_all` Race on First Synth

**What goes wrong:** Two simultaneous TTS tool calls both check that `audio_cache/` doesn't exist and both call `create_dir_all`. One races to a `EEXIST` error.

**Why it happens:** `create_dir_all` on a path that already exists returns `Ok(())` (it is idempotent), so this is NOT actually a problem. The pitfall is calling `fs::create_dir` (singular) instead, which does error on existing dir.

**How to avoid:** Always use `std::fs::create_dir_all` (or `tokio::fs::create_dir_all`), never `create_dir`. [CITED: D-16 — "audio cache dir created on first synth, not at startup"]

> `security_enforcement` is not explicitly disabled in `.planning/config.json` — section included.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | No | — (no new auth surface; ElevenLabs key via env var, same as all other API keys) |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| LLM prompt injection via `text` arg → excessive API cost | Elevation of Privilege | Truncate to provider cap; `is_available()` env-var gate so ElevenLabs is opt-in |
| Audio cache disk exhaustion | Denial of Service | Deferred to future phase (D-16 — no cleanup this phase); acceptable risk for v1 |
| `output_path` arg traversal (LLM passes `../../etc/passwd`) | Tampering | Clamp `output_path` to be under `$IRONHERMES_HOME/audio_cache/` when provided by LLM; reject paths that escape the audio cache dir |
| ElevenLabs API key leakage via `redact_args()` | Information Disclosure | `TextToSpeechTool::redact_args()` must NOT echo API key; tool args (`text`, `output_path`) contain no secrets — default `redact_args` (no-op) is safe |

**`output_path` traversal is a real risk:** If the LLM passes `output_path: "/etc/passwd"` the tool would overwrite system files. Mitigation: when `output_path` is provided by the LLM, validate that `canonicalize(output_path).starts_with(get_hermes_home())`. The planner must include this validation as a task.
