# Phase 36.17: iron_hermes_ui web logging in $IRONHERMES_HOME/logs - Context

**Gathered:** 2026-05-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Add daily-rolling file-based tracing logs for the `iron_hermes_ui` server binary, mirroring the TUI's logging pattern from commit `eedb49e1` (`feat(tui): daily-rolling file logging to $IRONHERMES_HOME/logs/tui.log`).

Two log streams under `$IRONHERMES_HOME/logs/`:

1. `web.log.YYYY-MM-DD` — app/agent tracing emitted by the `ironhermes` and `iron_hermes_ui` crates.
2. `web-access.log.YYYY-MM-DD` — HTTP request access log emitted by `tower_http::trace::TraceLayer`.

Both layers are added inside the `#[cfg(feature = "server")]` `main()` in `crates/iron_hermes_ui/src/main.rs`. The existing stdout `tracing_subscriber::fmt()` console layer is preserved unchanged. WASM/client builds are unaffected.

**In scope:** file-appender wiring, two daily-rolling streams, ANSI-stripped file output, non-blocking writers with WorkerGuards held for the server lifetime, per-layer EnvFilter wiring for the two streams, mounting `TraceLayer` on the Axum `Router`, ensuring `$IRONHERMES_HOME/logs/` is created at startup.

**Out of scope:** restructuring the existing console subscriber install (it stays as-is), changing any application log levels beyond the file-layer defaults, log forwarding to external services, log retention/rotation policy beyond daily-rolling, adding new tracing instrumentation inside app code, structured JSON log format, log aggregation across multiple server instances, agent-side logging changes (the embedded agent already logs through the same global subscriber).

</domain>

<decisions>
## Implementation Decisions

### Log Streams + File Layout
- **D-01:** Two log streams, both daily-rolling, both under `$IRONHERMES_HOME/logs/` (the same directory the TUI uses):
  - `web.log.YYYY-MM-DD` — app/agent tracing
  - `web-access.log.YYYY-MM-DD` — HTTP access log
- **D-02:** Each stream uses its own `tracing_appender::rolling::daily(&log_dir, "<name>")` appender wrapped in `tracing_appender::non_blocking(...)`. Both `WorkerGuard`s are returned from the install function and held in `main()` for the lifetime of `axum::serve(...).await` — dropping them shuts down the writer threads and loses buffered output (same constraint as the TUI's `_file_log_guard`).
- **D-03:** Both file layers set `.with_ansi(false)` so log files never contain escape sequences (matches `tui.log` behavior). The console layer keeps default ANSI.

### Default EnvFilter Levels (when `RUST_LOG` is unset)
- **D-04:** `web.log` (app stream) default filter when `RUST_LOG` is unset: `ironhermes=info,iron_hermes_ui=info`. Same parity-with-TUI spirit as eedb49e1 (TUI uses `ironhermes=info`), extended with `iron_hermes_ui=info` so the server/api/ws modules in this crate are captured.
- **D-05:** `web-access.log` (HTTP access stream) uses a per-layer filter `tower_http::trace=info`, independent of `RUST_LOG`. This pins HTTP request lines to the access log file and prevents them from polluting either the app log or the console.
- **D-06:** Standard `RUST_LOG=...` overrides still apply to the app log filter (via `EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("ironhermes=info,iron_hermes_ui=info"))`). The access-log filter is intentionally not driven by `RUST_LOG` — it's a fixed per-layer filter so the access stream stays predictable.

### Console (stdout) Output
- **D-07:** The existing stdout layer (`tracing_subscriber::fmt().with_env_filter(...)`) stays installed. Adding the file layers does not change current console behavior — `cargo run --features server` and `dx serve` look the same as today, plus the two files now exist.
- **D-08:** Console keeps default ANSI (colored output). Only the file layers strip ANSI (D-03).
- **D-09:** The console layer uses the same EnvFilter as the `web.log` layer (D-04). HTTP access lines do NOT print to stdout — they go only to `web-access.log`.

### HTTP Access Logging
- **D-10:** Mount `tower_http::trace::TraceLayer::new_for_http()` on the Axum router with default `on_request`/`on_response` callbacks at `INFO`. One line per request — method, path, status, latency.
- **D-11:** No detailed request body / header capture. No request-id propagation in this phase. (Both can be added later if needed; not in scope.)
- **D-12:** TraceLayer is mounted via `.layer(TraceLayer::new_for_http())` on the router, alongside the existing `.layer(axum::Extension(app_state))` in `crates/iron_hermes_ui/src/main.rs`.

### Dependencies
- **D-13:** Add `tracing-appender = { workspace = true }` to `crates/iron_hermes_ui/Cargo.toml` under the existing `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]` block. (`tracing-appender = "0.2"` is already declared in `Cargo.toml` workspace deps line 73 — added by commit eedb49e1.)
- **D-14:** Add `tower-http` with the `trace` feature to the same non-wasm32 block. Not currently in workspace deps — needs adding to root `Cargo.toml` `[workspace.dependencies]` as well. Pin to a version compatible with `axum = "=0.8.4"` (likely `tower-http = "0.5"` or `"0.6"`; planner/researcher confirms exact version against the lockfile).

### Filesystem Setup
- **D-15:** Use `ironhermes_core::constants::get_hermes_home()` (already imported in main.rs's neighborhood — `iron_hermes_ui` depends on `ironhermes-core` under the non-wasm32 block) to resolve the home dir.
- **D-16:** Call `std::fs::create_dir_all(home.join("logs"))` at startup before installing the file layers. If creation fails (e.g. read-only home in tests), the install function falls back to file-layer-disabled (matches TUI pattern in `event_loop.rs:88-100`) and the console layer continues to work.

### Code Structure
- **D-17:** Extract the subscriber-install logic into a helper function (e.g. `install_web_logger_subscriber()`) that returns `(Option<WorkerGuard>, Option<WorkerGuard>)` for the two file appenders. Pattern mirrors `install_tui_logger_subscriber()` in `crates/ironhermes-cli/src/tui_rata/event_loop.rs:85-117`.
- **D-18:** Use `tracing_subscriber::registry().with(console).with(web_file_layer).with(access_file_layer).init()` to compose the layers. Each layer carries its own `.with_filter(...)` so the global registry stays a single source of truth.

### Claude's Discretion
- Whether to extract the install helper into a new module (e.g. `crates/iron_hermes_ui/src/server/logging.rs`) or keep it inline in `main.rs`. Either is acceptable; the helper is the only file-logging surface in the crate so a dedicated module is reasonable but not required.
- Exact `tower-http` minor version (D-14) — pick the highest version compatible with `axum = "=0.8.4"` from the current lockfile context.
- Whether to use `try_init()` (silent no-op on double-install) or `init()` (panic). TUI uses `try_init()` for test-friendliness; web UI may not have the same double-install concern but should match for consistency.
- The exact `EnvFilter` parse path — direct `EnvFilter::new(...)` vs `EnvFilter::builder().with_default_directive(...).parse_lossy(...)`. Either works; match the TUI install function for consistency.
- Test approach for D-16's fallback path (read-only home) — the TUI has no regression test for this; web UI plan may or may not add one.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `install_tui_logger_subscriber()` in `crates/ironhermes-cli/src/tui_rata/event_loop.rs:85-117` — direct template for the web UI's install helper. Difference: TUI installs `tui_logger::TuiTracingSubscriberLayer` as one of its registry layers (in-TUI panel); the web UI registers the existing console fmt layer instead. Otherwise the pattern is identical.
- `ironhermes_core::constants::get_hermes_home()` — already used by the TUI install function (line 88); reuse directly. No new dependency needed.
- `tracing_appender::rolling::daily` + `tracing_appender::non_blocking` — already proven in production (eedb49e1).

### Established Patterns
- **WorkerGuard lifetime:** Returned from the install function and held in the outer scope (`run_chat_ratatui` for TUI; `main()` for web UI). Dropping the guard shuts down the writer thread → log loss. Plans MUST capture both guards in `main()` after install, before `axum::serve(...).await`.
- **Fallback on dir-creation failure:** TUI returns `None` from the install function when `create_dir_all` fails; the in-TUI panel still works. Web UI mirrors this: return `(None, None)` for the two guards; console layer still installs.
- **`.with_ansi(false)` on file layers:** Locks the file output free of escape sequences (`tui.log` parity).
- **`try_init()` over `init()`:** TUI uses `try_init` for test-friendliness; web UI should match for consistency even though it's less likely to double-install.

### Integration Points
- `crates/iron_hermes_ui/src/main.rs:18-23` — the current `tracing_subscriber::fmt().with_env_filter(...).init()` call replaces with the new composed `registry().with(console).with(web_file).with(access_file).try_init()`.
- `crates/iron_hermes_ui/src/main.rs:41-44` — `Router::new().serve_dioxus_application(...).layer(Extension(app_state))` — append `.layer(TraceLayer::new_for_http())` here.
- `crates/iron_hermes_ui/Cargo.toml` non-wasm32 block (lines around `tracing-subscriber = { workspace = true }`) — add `tracing-appender = { workspace = true }` and `tower-http = { workspace = true, features = ["trace"] }`.
- Root `Cargo.toml` `[workspace.dependencies]` — add `tower-http` entry pinned to a version compatible with `axum = "=0.8.4"`.

<specifics>
## Specific Ideas

- **Pattern parity is the primary goal.** The TUI commit eedb49e1 is the reference — every choice that has a "match the TUI" option should take it unless explicitly diverged in <decisions>.
- **Same `logs/` directory.** Both surfaces (TUI and web UI) write to the same `$IRONHERMES_HOME/logs/` directory; users get one place to look for application logs across surfaces. `tui.log.YYYY-MM-DD` and `web.log.YYYY-MM-DD` sit side by side.
- **No new tracing instrumentation in this phase.** Only the appender/layer wiring + the access log layer. Anything that needs `tracing::info!(...)` calls added to existing handlers belongs in a follow-up phase.

</specifics>

<deferred>
## Deferred Ideas

- **Detailed access log fields** (request_id, remote_addr, user-agent, content-length, request-span timing). Considered for `web-access.log` but the user picked Basic. Add later if the access log proves insufficient for debugging WebSocket/agent SSE flows.
- **Custom http_access target** (drop `tower_http::trace` in favor of a hand-rolled middleware that emits `tracing::info!(target = "http_access", ...)` lines). Skipped — tower-http's `TraceLayer` is good enough.
- **Dev-vs-prod console gating** (e.g. `IRONHERMES_LOG_CONSOLE=1` or `isatty` detection to silence stdout under systemd/docker). Skipped — keep console behavior unchanged.
- **Log forwarding** (push logs to a remote collector like Loki, OTLP exporter, etc.) — separate phase if/when needed.
- **Structured JSON log format** for machine ingestion — separate phase.
- **Log retention beyond daily-rolling** (gzip + N-day cleanup). `tracing-appender` doesn't do this; would need a separate housekeeping job. Out of scope.
