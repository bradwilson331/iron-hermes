## Q2 — TraceLayer integration details for axum 0.8

**Question:** Exact import path (`tower_http::trace::TraceLayer`), `new_for_http()` signature, default `on_request` / `on_response` log level (INFO confirmed?), default target (is it `tower_http::trace::on_request` etc., or a single `tower_http::trace` target?). Confirm the per-layer filter `tower_http::trace=info` actually matches what TraceLayer emits — verify against tower-http docs.

**Answer:**

- **Import path:** `use tower_http::trace::TraceLayer;` (verified at docs.rs/tower-http/0.6.8/tower_http/trace/index.html).
- **Constructor signature:** `TraceLayer::new_for_http()` returns a `TraceLayer` configured with the HTTP status-code classifier. No arguments.
- **Default `on_request` level:** **`Level::DEBUG`**, not `Level::INFO` — confirmed at docs.rs/tower-http/0.6.8/tower_http/trace/struct.DefaultOnRequest.html ("Defaults to `Level::DEBUG`"). Same applies to `DefaultOnResponse`.
- **Default targets:** `tower_http::trace::on_request` for request events and `tower_http::trace::on_response` for response events (also `tower_http::trace::on_failure` for the failure handler). These are distinct target strings, NOT a single `tower_http::trace` target. The targets are nested under the parent module path, so the `EnvFilter` directive `tower_http::trace=info` is a **module-prefix match** that captures all three target strings (per `tracing_subscriber::EnvFilter` semantics — directives match the target as a prefix at module boundaries).

**Per-layer filter sanity check:**

If TraceLayer is mounted with pure defaults (`.layer(TraceLayer::new_for_http())`), the request/response log events emit at `DEBUG`. The locked filter `tower_http::trace=info` will **filter them out**. This contradicts D-10 ("default `on_request`/`on_response` callbacks at INFO") — D-10 describes the *desired* level but does not match the *default* behavior.

**Required fix (planner must include in plan):**

```rust
use tower_http::trace::{TraceLayer, DefaultOnRequest, DefaultOnResponse};
use tracing::Level;

let trace_layer = TraceLayer::new_for_http()
    .on_request(DefaultOnRequest::new().level(Level::INFO))
    .on_response(DefaultOnResponse::new().level(Level::INFO));

let router = axum::Router::new()
    .serve_dioxus_application(ServeConfig::new(), App)
    .layer(axum::Extension(app_state))
    .layer(trace_layer)
    .into_make_service();
```

This makes the access-log filter `tower_http::trace=info` actually match the emitted events.

**Risk / open question:** Yes — this is the only material divergence from CONTEXT.md's locked decisions and it requires an explicit code-level adjustment. The planner MUST include a task that explicitly sets request/response levels to INFO. Without this, both files will exist but `web-access.log` will be empty.

**Confidence:** HIGH — docs.rs is authoritative; verified the default-level claim against the explicit `DefaultOnRequest::level` documentation.

## Q3 — Per-layer EnvFilter wiring

**Question:** tracing-subscriber registry composition with three layers (console, web file, access file), each with its own `.with_filter(EnvFilter::...)`. Confirm the exact builder pattern. Identify any gotchas with per-layer EnvFilter clones — does each layer need its own filter instance, or can `EnvFilter` be cloned cheaply?

**Answer:**

**Composition pattern (verified against docs.rs/tracing-subscriber/0.3/tracing_subscriber/layer/index.html):**

```rust
use tracing_subscriber::prelude::*;
use tracing_subscriber::{fmt, registry, EnvFilter};

let app_filter = || {
    EnvFilter::try_from_default_env()
        .unwrap_or_else(|_| EnvFilter::new("ironhermes=info,iron_hermes_ui=info"))
};

let console_layer = fmt::layer()
    .with_writer(std::io::stdout)
    .with_filter(app_filter());

let web_file_layer = fmt::layer()
    .with_writer(web_non_blocking)
    .with_ansi(false)
    .with_target(true)
    .with_filter(app_filter());

let access_file_layer = fmt::layer()
    .with_writer(access_non_blocking)
    .with_ansi(false)
    .with_target(true)
    .with_filter(EnvFilter::new("tower_http::trace=info"));

let _ = registry()
    .with(console_layer)
    .with(web_file_layer)
    .with(access_file_layer)
    .try_init();
```

**Per-layer filter requirements (from docs):**
- Per-layer filtering requires the `"registry"` feature flag — already enabled via the workspace `tracing-subscriber = { version = "0.3", features = ["env-filter"] }` (the registry root type is unconditionally available; the `env-filter` feature gates the `EnvFilter` type).
- "A span or event will be recorded if it is enabled by _any_ per-layer filter, but it will be skipped by the layers whose filters did not enable it." → Each file layer independently decides whether to write.
- **Each layer needs its own filter instance.** `EnvFilter::with_filter(self, ...)` consumes the filter; sharing one filter across layers requires `.and_then(other_layer)` combinator.

**`EnvFilter` cloning:**
- Docs do not explicitly call out `Clone`, but the canonical idiom (used in `tracing-subscriber` examples) is to **build the filter inside a closure or call site** rather than clone — see the `app_filter()` closure above. Each call to `EnvFilter::try_from_default_env()` re-parses `RUST_LOG`, which is fine at startup (parsed twice, no runtime cost during operation).
- If a clone is truly needed, `EnvFilter` does implement `Clone` (verified by inspection of the public API — `tracing-subscriber/src/filter/env/mod.rs`). Cloning is "cheap-ish" (clones the internal `Vec<Directive>`); fine for one-time startup use.

**Filter target match semantics:**
- `tower_http::trace=info` matches any target whose path starts with `tower_http::trace` at module boundaries — so it captures `tower_http::trace::on_request`, `tower_http::trace::on_response`, `tower_http::trace::on_failure`, etc.

**Risk / open question:** None. Pattern is standard.

**Confidence:** HIGH — pattern is the documented idiom and the workspace already uses `with_filter` in `crates/ironhermes-cli/src/tui_rata/event_loop.rs:98`.

## Q5 — WorkerGuard lifetime semantics

**Question:** Two guards now (instead of one as TUI has). Confirm: Are they `Send`? What happens if one is dropped before the other? Is there a clean shutdown idiom that waits for the queue to drain, or does dropping the guards at end of `main()` already do that?

**Answer:**

- **`Send`:** Yes. `tracing_appender::non_blocking::WorkerGuard` is `Send` (verified by inspection — the type wraps a `JoinHandle` and a shutdown channel, both of which are `Send`). Holding two guards as locals in `async fn main()` across `axum::serve(...).await` is sound.
- **Independent drop:** Each `WorkerGuard` is tied to its own appender's background thread via a 1:1 relationship. Dropping one guard:
  1. Sends a shutdown signal to that single writer thread.
  2. Blocks the dropper until that thread drains its queue and exits.
  3. Does NOT affect the other guard's writer thread.
  So dropping `web_guard` before `access_guard` simply means the `web.log` writer flushes and shuts down while the access-log writer keeps running. Both file layers' tracing events that arrive after their respective guard drops are silently discarded (the channel send fails; the layer's writer is gone).
- **Clean shutdown idiom:** Drop the guards at the natural end of `main()`. The `WorkerGuard::drop` impl synchronously waits for the queue to drain (see `tracing-appender` source — the guard's `Drop` impl calls `shutdown_signal.notify_one()` then `handle.join()`). No `await` is needed.

**Correct pattern for `main()`:**

```rust
let (web_guard, access_guard) = install_web_logger_subscriber();
// ... build router with TraceLayer ...
axum::serve(listener, router).await.unwrap();
// Guards drop here at scope end — both writer threads flush + join.
drop(web_guard);
drop(access_guard);
```

The explicit `drop` calls at the end are stylistic — Rust will drop them anyway when `main()` returns. Make them explicit (mirroring TUI `event_loop.rs:68`) to communicate intent and discourage future refactors from binding the guards as `_` (which drops immediately and loses the buffered output).

**Order of drop:** Insignificant — each guard is independent. Either order produces the same outcome.

**Risk / open question:** None for the steady-state case. One edge case worth noting in the plan: if `axum::serve(...).await` panics, the guards will still drop (Rust runs destructors on unwind), so logs from before the panic will be flushed. If the binary is killed with `SIGKILL`, the guards never drop and unflushed buffered lines are lost — but that's true for any non-fsync-per-line log strategy and is accepted in the TUI today.

**Confidence:** HIGH — verified against `tracing-appender 0.2.5` source and TUI reference behavior.

## Q6 — Dir-creation fallback semantics

**Question:** TUI returns `Option<WorkerGuard>` when `create_dir_all` fails (event_loop.rs:88-100). For two streams, what's the cleanest signature? `(Option<WorkerGuard>, Option<WorkerGuard>)` is in D-17, but consider whether a single `Option<(WorkerGuard, WorkerGuard)>` (both-or-none) is simpler. Recommend one based on the TUI pattern's actual behavior.

**Answer:**

**Recommendation: `Option<(WorkerGuard, WorkerGuard)>` (both-or-none).**

**Rationale:**
- The two streams share the same fail mode — they both require `$IRONHERMES_HOME/logs/` to exist. There is no realistic scenario where `web.log` can be created but `web-access.log` cannot (both go to the same directory, both use the same appender API). The split tuple `(Option, Option)` admits an impossible state.
- The TUI's `Option<WorkerGuard>` shape is single-stream; it doesn't establish precedent for the multi-stream case. Using `Option<(WorkerGuard, WorkerGuard)>` makes the both-or-none invariant explicit and lets the caller destructure once:
  ```rust
  let _guards = install_web_logger_subscriber();
  ```
  (The variable holds the option-pair guard; both file layers are present or neither is.)
- The control flow inside the install fn becomes:
  ```rust
  let file_layers_and_guards = std::fs::create_dir_all(&log_dir).ok().map(|_| {
      let web_appender = tracing_appender::rolling::daily(&log_dir, "web.log");
      let (web_nb, web_guard) = tracing_appender::non_blocking(web_appender);
      let access_appender = tracing_appender::rolling::daily(&log_dir, "web-access.log");
      let (access_nb, access_guard) = tracing_appender::non_blocking(access_appender);
      let web_layer = /* ... */;
      let access_layer = /* ... */;
      ((web_layer, access_layer), (web_guard, access_guard))
  });
  ```
  Cleaner than two separate `Option` branches.

**However — D-17 is locked.** The CONTEXT.md text says `(Option<WorkerGuard>, Option<WorkerGuard>)` explicitly. Two options for the planner:

**Option A (respect D-17 as locked):** Return `(Option<WorkerGuard>, Option<WorkerGuard>)`. Both `Option`s are filled together or both `None` — semantic equivalence to the recommended shape, just a less ergonomic signature.

**Option B (flag D-17 as a discretionary refinement):** Surface this to the user in the plan-check phase and ask whether the cleaner `Option<(WorkerGuard, WorkerGuard)>` is acceptable. CONTEXT.md `<discretion>` doesn't list signature shape — so D-17 reads as locked.

**My recommendation to the planner:** **Implement D-17 verbatim as `(Option<WorkerGuard>, Option<WorkerGuard>)`** to honor the lock, and note in the plan that the two `Option`s are always in the same state. The ergonomic gain of consolidating doesn't justify diverging from a locked decision.

**Risk / open question:** Low — purely cosmetic.

**Confidence:** HIGH — both shapes work; recommendation is to honor D-17.

## Q7 — Test approach for the install function

**Question:** What's the cheapest way to assert the function compiles and at least the in-memory layer composition is sound? `cargo build -p iron_hermes_ui --features server` is the floor; any `#[cfg(test)]` smoke test possible? (TUI has none, per CONTEXT.md.)

## Q9 — Verification: does `dx serve` still work after these changes?

**Question:** `dx serve` proxies WebSocket through a separate dev process (per project memory). Does the TraceLayer mounted via `.layer(...)` interfere with the dev proxy in any documented way? Pull from `.planning/codebase/ARCH.md` and the multiplatform gateway scope memory if relevant.

**Answer:**

**No documented interference.** `TraceLayer` is a tower middleware that wraps the service inside-the-server — it intercepts the request before the Axum handler dispatch and intercepts the response after. It does NOT modify request/response payloads, HTTP headers, or status codes. Its only observable side effect is emitting `tracing` events.

**`dx serve` architecture (from project memory `project_arch_gateway_vs_ui.md`):** the dioxus dev CLI proxies WebSocket connections through a separate process that forwards to the embedded server. The proxy is external to the Axum `Router` — it sits in front of the binary. Any middleware added to the inner `Router` (including TraceLayer) executes after the proxy has already done its work for HTTP requests and is bypassed entirely for the WebSocket-upgrade path once it's been hijacked.

**Specific check — WebSocket upgrade requests:**
`TraceLayer::new_for_http()` uses HTTP status-code classification. WebSocket upgrade is a normal HTTP request with `Connection: Upgrade, Upgrade: websocket` headers that returns `101 Switching Protocols`. TraceLayer will log the upgrade request and the `101` response, then the connection switches protocols and the middleware is no longer involved. This is the standard tower-http behavior and is widely deployed (e.g., axum's own examples use TraceLayer + WebSocket together).

**Other `dx serve` consideration — duplicate subscriber install:** `dx serve` runs `iron_hermes_ui` as a child process. There is no risk of `try_init()` failing because it's a fresh process each run. `try_init()`'s safety value is for **test** binaries where multiple tests in the same process attempt to install — not for `dx serve`.

**Stdout behavior under `dx serve`:** The console layer's output goes to the child process's stdout, which `dx serve` forwards to the dev console. No change from current behavior (D-07).

**Risk / open question:** None directly from middleware composition. **Indirect:** if the user has unusual environment overrides (e.g., redirected stdout under `dx serve`), the console layer's writes might appear in a different stream than expected. This is not a regression — same as today's behavior. Not in scope.

**Confidence:** MEDIUM-HIGH — middleware non-interference is a property of tower's Service composition (HIGH), but `dx serve`'s exact dev-proxy implementation hasn't been read line-by-line for this research (MEDIUM). However, no plausible interaction mode causes a regression.

### Pattern 1: Layered subscriber with per-layer filters
**What:** `tracing_subscriber::registry()` as the root, composed with multiple `Layer`s each carrying its own `.with_filter(...)`.
**When to use:** Whenever the same process needs to fan out logs to multiple sinks with different scopes (e.g., one stream for app, one for HTTP access).
**Example:** See Q3 above.

### Pattern 2: Non-blocking file appender with WorkerGuard
**What:** Wrap a `rolling::daily(...)` appender in `non_blocking(...)`; hold the returned `WorkerGuard` for the writer's intended lifetime.
**When to use:** Any time async/multi-threaded code emits log events that would otherwise block on disk I/O.
**Example:**
```rust
let appender = tracing_appender::rolling::daily(&log_dir, "web.log");
let (non_blocking, guard) = tracing_appender::non_blocking(appender);
let layer = fmt::layer().with_writer(non_blocking).with_ansi(false).with_filter(env_filter);
// hold `guard` for the lifetime of the writer
```

### Anti-Patterns to Avoid

- **Binding `WorkerGuard` to `_`:** `let _ = tracing_appender::non_blocking(...)` immediately drops the guard, shutting down the writer thread before any logs are written. Always bind to a real local that lives for the writer's intended lifetime.
- **Hand-rolling daily rotation:** `tracing-appender` already does this correctly with date suffix in the filename. Don't write a custom `chrono::Local::now().format(...)` filename + manual `File::create`.
- **Single global EnvFilter for multiple layers:** Per CONTEXT.md, the access log filter is independent of `RUST_LOG`. Sharing one filter means RUST_LOG silencing would also silence access logs. The per-layer pattern (D-18) avoids this.
- **Mounting TraceLayer after `.into_make_service()`:** `.layer(...)` must be called on the `Router`, before `.into_make_service()`. The current code at `main.rs:41-44` already gets this right with `.layer(axum::Extension(app_state))`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Daily file rotation | Custom `chrono`-based rotation | `tracing_appender::rolling::daily` | Atomic file-creation, timezone handling, well-tested edge cases |

## Common Pitfalls

### Pitfall 1: TraceLayer default level is DEBUG, not INFO
**What goes wrong:** Mount `.layer(TraceLayer::new_for_http())` with no `.on_request(...)` / `.on_response(...)` customization; pair it with the locked filter `tower_http::trace=info`; result: `web-access.log` exists but is empty.
**Why it happens:** `DefaultOnRequest` and `DefaultOnResponse` both default to `Level::DEBUG` per docs.rs. CONTEXT.md D-10 describes the intended *level*, not the default behavior.
**How to avoid:** Always set `.on_request(DefaultOnRequest::new().level(Level::INFO))` and `.on_response(DefaultOnResponse::new().level(Level::INFO))`. See Q2 fix code.
**Warning signs:** `web-access.log.YYYY-MM-DD` file exists but `wc -l` shows 0 lines after exercising the server with curl.

### Pitfall 2: `WorkerGuard` dropped at end of expression
**What goes wrong:** `let _ = install_web_logger_subscriber();` — destructures the tuple but binds both `Option<WorkerGuard>`s to `_`, dropping them at the end of the statement. Writer threads shut down before `axum::serve(...).await` even starts. All log lines are lost (or written to a file the test never sees).
**Why it happens:** Easy to write `_` instead of a real local in Rust. The compiler does NOT warn for `WorkerGuard` because it has no `#[must_use]` attribute on `Drop`.
**How to avoid:** Bind to named locals: `let (_web_guard, _access_guard) = install_web_logger_subscriber();`. The underscore prefix silences "unused variable" warnings while still extending the lifetime to the end of the function.
**Warning signs:** Files exist but only contain the first one or two log lines (whatever flushed before the guards dropped) — or are entirely empty.

### Pitfall 3: `try_init` Err return silently ignored
**What goes wrong:** A previous subscriber (e.g., from `tracing_subscriber::fmt().init()`) is already installed; `try_init` returns `Err`, swallowed by `let _ = ...`. The new file layers never receive events.
**Why it happens:** Subscriber install is global per process. The existing `tracing_subscriber::fmt()...init()` at main.rs:18-23 MUST be removed when the new install fn replaces it.
**How to avoid:** Delete lines 18–23 of `crates/iron_hermes_ui/src/main.rs` as part of this phase. Replace with the call to `install_web_logger_subscriber()`. The plan should explicitly call this out.
**Warning signs:** Console output continues to work (because the old fmt subscriber is still installed), but neither log file gets any content.

### Pitfall 4: `EnvFilter::new(...)` parsing panic
**What goes wrong:** `EnvFilter::new("ironhermes=info,iron_hermes_ui=info")` panics on malformed directives. Typo introduced during a refactor → panic at startup.
**Why it happens:** `EnvFilter::new` calls `from_str(...).expect(...)`. The TUI uses the same fallback pattern (`event_loop.rs:93`).
**How to avoid:** Acceptable risk — the string is a const literal, not user input. If paranoid, use `EnvFilter::builder().with_default_directive(...).parse_lossy(...)` which never panics.
**Warning signs:** Server fails to start; panic message mentions `EnvFilter` directive parse error.

### Pitfall 5: `dx serve` doesn't pick up new behavior
**What goes wrong:** Engineer runs `dx serve` after the change; sees console output as expected; assumes everything works. But `$IRONHERMES_HOME/logs/` is still empty because `dx serve` spawned the server with a different `IRONHERMES_HOME` (or none).
**Why it happens:** `dx serve` may not inherit shell env vars in all configurations.
**How to avoid:** During UAT, set `IRONHERMES_HOME` explicitly: `IRONHERMES_HOME=/tmp/test-home dx serve`. Verify with `ls $IRONHERMES_HOME/logs/`.
**Warning signs:** Logs appear when running `cargo run --features server` directly but not under `dx serve` — almost certainly an env var inheritance issue, not a code bug.

## Code Examples

### The complete install function (recommended shape)

```rust
// crates/iron_hermes_ui/src/server/logging.rs

use tracing::Level;
use tracing_appender::non_blocking::WorkerGuard;
use tracing_subscriber::{fmt, prelude::*, registry, EnvFilter};

/// Install the global tracing subscriber for the `iron_hermes_ui` server.
///
/// Composes three layers:
/// 1. Console (stdout, ANSI) — same filter as web.log layer.
/// 2. Web file — daily-rolling `$IRONHERMES_HOME/logs/web.log.YYYY-MM-DD`,
///    ANSI stripped, filter `ironhermes=info,iron_hermes_ui=info`
///    (honors RUST_LOG override via `EnvFilter::try_from_default_env`).
/// 3. Access file — daily-rolling `$IRONHERMES_HOME/logs/web-access.log.YYYY-MM-DD`,
///    ANSI stripped, fixed per-layer filter `tower_http::trace=info`
///    (independent of RUST_LOG).
///
/// Returns the two `WorkerGuard`s for the file appenders. Both MUST be held
/// in `main()` for the lifetime of `axum::serve(...).await` — dropping them
/// shuts down the writer threads and loses buffered output.
///
/// If `$IRONHERMES_HOME/logs/` can't be created, returns `(None, None)` and
/// only the console layer is installed (matches the TUI fallback at
/// `crates/ironhermes-cli/src/tui_rata/event_loop.rs:88-100`).
pub fn install_web_logger_subscriber() -> (Option<WorkerGuard>, Option<WorkerGuard>) {
    let log_dir = ironhermes_core::constants::get_hermes_home().join("logs");

    let app_filter = || {
        EnvFilter::try_from_default_env()
            .unwrap_or_else(|_| EnvFilter::new("ironhermes=info,iron_hermes_ui=info"))
    };

    let console_layer = fmt::layer()
        .with_writer(std::io::stdout)
        .with_target(true)
        .with_filter(app_filter());

    match std::fs::create_dir_all(&log_dir) {
        Ok(_) => {
            let web_appender = tracing_appender::rolling::daily(&log_dir, "web.log");
            let (web_nb, web_guard) = tracing_appender::non_blocking(web_appender);
            let access_appender = tracing_appender::rolling::daily(&log_dir, "web-access.log");
            let (access_nb, access_guard) = tracing_appender::non_blocking(access_appender);

            let web_file_layer = fmt::layer()
                .with_writer(web_nb)
                .with_ansi(false)
                .with_target(true)
                .with_filter(app_filter());

            let access_file_layer = fmt::layer()
                .with_writer(access_nb)
                .with_ansi(false)
                .with_target(true)
                .with_filter(EnvFilter::new("tower_http::trace=info"));

            let _ = registry()
                .with(console_layer)
                .with(web_file_layer)
                .with(access_file_layer)
                .try_init();

            (Some(web_guard), Some(access_guard))
        }
        Err(_) => {
            let _ = registry().with(console_layer).try_init();
            (None, None)
        }
    }
}
```

## Open Questions

1. **Should the plan add an explicit `#[cfg(test)]` smoke test for the install fn?**
   - What we know: TUI doesn't have one (per CONTEXT.md). Adding one is optional.
   - What's unclear: Whether the marginal value of an isolated test is worth the risk of conflicting with future test-binary subscriber installs.
   - Recommendation: Skip in v1; rely on the UAT script. Add later if the install fn is touched by multiple later phases.

2. **Is there a server-side test binary in `iron_hermes_ui` that already installs a subscriber?**
   - What we know: `cargo test --package iron_hermes_ui` exists and the crate has `[dev-dependencies]` for tokio (Cargo.toml line 60).
   - What's unclear: Whether any existing test installs a global subscriber that would interfere with the smoke test if added.
   - Recommendation: If the planner opts to add a test (Q7 Option), use `try_init` (already locked) and run the test in isolation with `cargo test ... -- --test-threads=1`.

3. **Will the access log capture WebSocket upgrade responses (HTTP 101) usefully?**
   - What we know: `TraceLayer` logs the HTTP-level upgrade request and 101 response; after that, the connection has switched protocols and middleware no longer sees frames.
   - What's unclear: Whether the engineer wants per-frame logging (out of scope per D-11).
   - Recommendation: Note in `web-access.log` documentation/release notes that WebSocket activity beyond the upgrade is invisible to this log. If frame logging is wanted, that's a future phase.
