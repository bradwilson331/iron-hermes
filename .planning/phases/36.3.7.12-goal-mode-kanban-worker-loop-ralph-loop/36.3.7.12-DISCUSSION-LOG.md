> Here's a comprehensive breakdown of **Goal Mode**, how it fits into the
> Kanban system, and how agents interact with the board in Hermes Agent:
>
> ---
>
> ## The Kanban Board — Overview
>
> Hermes Kanban is a durable, multi-agent task board backed by a local
> SQLite database (`~/.hermes/kanban.db`). It's shared across all your
> Hermes profiles, allowing multiple named AI agents (profiles) to
> collaborate on work that crosses session boundaries, survives restarts,
> or requires human-in-the-loop steps.
>
> **Core concepts:**
> - **Task** — a row with a title, optional body, one assignee (a profile
>   name), and a status: `triage → todo → ready → running → blocked →
>   done → archived`.
> - **Link** — a parent→child dependency. The dispatcher auto-promotes a
>   child task from `todo` to `ready` once all its parents are `done`.
> - **Comment** — the inter-agent communication protocol. Agents and
>   humans both append comments; when a worker is spawned (or
>   re-spawned), it reads the full comment thread as part of its context.
> - **Workspace** — the directory the worker operates in (either a fresh
>   scratch directory, a git worktree, or a persistent shared dir).
> - **Dispatcher** — a loop that every N seconds reclaims stale tasks,
>   promotes tasks whose dependencies are met, and spawns workers.
>
> ---
>
> ## How Workers Interact with the Kanban Board
>
> When the dispatcher spawns a worker, it sets `HERMES_KANBAN_TASK=t_abcd`
> in the child environment. This env var activates a dedicated **kanban
> toolset** — the worker never shells out to `hermes kanban` CLI
> commands; it uses structured tool calls instead. This matters because
> workers may run on remote backends (Docker, Modal, SSH), and tool args
> are structured JSON rather than fragile CLI strings.
>
> **The worker lifecycle (via the `kanban-worker` skill) looks like
> this:**
>
> 1. **On spawn**, call `kanban_show()` to read the task's title, body,
>    parent handoffs, prior run attempts, and the full comment thread.
> 2. **Change directory** into `$HERMES_KANBAN_WORKSPACE` (via the
>    terminal tool) and do the actual work there.
> 3. **Call `kanban_heartbeat(note="...")`** every few minutes during
>    long operations. The dispatcher reclaims tasks that have been
>    `running` for over 4 hours with no heartbeat in the last hour
>    (treated as a crashed worker — benign, sends the task back to
>    `ready`).
> 4. **Complete** with `kanban_complete(summary="...", metadata={...})`
>    when done, or `kanban_block(reason="...")` if stuck.
>
> If a worker exits with status 0 while the task is still `running`
> without calling one of those two, it's logged as a
> `protocol_violation`.
>
> The `kanban-worker` skill is bundled and synced into every profile on
> install/update — no separate install step.
>
> ---
>
> ## Goal Mode (`--goal`)
>
> By default, every worker gets **one shot** at its card: do the work,
> call `kanban_complete` or `kanban_block`, and exit. This is the
> standard single-attempt model.
>
> **Goal mode changes this fundamentally.** You activate it with
> `--goal` on the CLI or `goal_mode=True` in the `kanban_create` tool
> (or the dashboard). Instead of a one-shot run, the worker enters a
> **goal loop** — the same Ralph-style engine that powers the `/goal`
> slash command.
>
> **How the goal loop works:**
> - After every turn, an **auxiliary judge** checks the worker's output
>   against the card's title + body, treating that content as the
>   **acceptance criteria**.
> - If the work is not yet done *and* the turn budget remains, the
>   **worker keeps going in the same session** — it doesn't exit and
>   wait to be re-dispatched.
> - The loop ends when one of three things happens:
>   1. The judge agrees the goal has been met.
>   2. The worker terminates the task itself (calls
>      `kanban_complete`/`kanban_block`).
>   3. The turn budget runs out — at which point the card is **blocked**
>      for human review rather than exiting silently.
>
> **When to use it:** Goal mode is for open-ended, multi-step, or "keep
> going until X is true" tasks — things like "translate the entire docs
> site to French" with the acceptance criteria written in the card body.
> You should **skip it for cheap one-shot work** because the per-turn
> judge overhead isn't worth it, and the dispatcher's existing
> retry/circuit-breaker already handles transient failures.
>
> **Important:** The quality of goal mode depends entirely on how
> well-written your card body is — it becomes the literal acceptance
> criteria the judge evaluates against. Write it as explicit, verifiable
> conditions.
>
> Example CLI invocation:
> ```
> hermes kanban create "Translate the docs site to French" \
>     --body "Acceptance: every page translated, no English left, links intact." \
>     --assignee linguist \
>     --goal \
>     --goal-max-turns 15    # optional; default 20
> ```
>
> ---
>
> ## The Orchestrator Skill
>
> A well-behaved orchestrator **does not do the work itself**. Its job
> is to decompose a high-level goal into tasks, link them (establishing
> dependencies), assign each to the right profile, and step back. The
> `kanban-orchestrator` skill encodes this as tool-call patterns with
> anti-temptation rules and a decomposition playbook keyed on
> `kanban_create` / `kanban_link` / `kanban_comment`.
>
> A canonical orchestrator turn (two parallel researchers handing off to
> a writer) would look like: create a research task for profile A,
> create a second research task for profile B, create a writing task
> linked as a child of both research tasks (so it won't start until both
> are done), then exit. The dispatcher handles all promotion and
> spawning automatically.
>
> For best results, the orchestrator profile's toolset should be
> **restricted to board operations** (`kanban`, `gateway`, `memory`) so
> it literally cannot execute implementation tasks even if it tries.
>
> ---
>
> ## The Two Surfaces
>
> The board has two front doors:
> - **Tool surface** (`kanban_*` tools) — how agents interact. Available
>   only inside spawned worker/orchestrator sessions.
> - **CLI / Slash command / Dashboard** — how humans interact. `hermes
>   kanban <verb>` or `/kanban <verb>` from any gateway platform
>   (Telegram, Discord, Slack, etc.), plus the visual dashboard at
>   `hermes dashboard`.
>
> Both surfaces route through the same `kanban_db` layer, so reads are
> always consistent and writes can't drift. The `/kanban` slash command
> is explicitly exempted from the gateway's "don't interrupt a running
> agent" guard — meaning you can send `/kanban comment <id> "..."` from
> your phone while a worker is mid-run, and the comment will land in the
> thread for the worker's next context read.

## Judge model config

| Option | Description | Selected |
|--------|-------------|----------|
| Mirror decomposer_model | Add `judge_model: String` to KanbanConfig (sibling of `decomposer_model`). Empty = use `auxiliary.kanban_judge` config then fall back to main provider. Same precedence pattern as auto_decompose's model resolution. | ✓ |
| Hard-fixed to decomposer_model | Reuse `decomposer_model` for both decomposer and judge. Cheaper config surface but cannot dial independently. | |
| Per-card override only | No config field — judge model always inferred from a `--goal-judge-model` CLI flag at create-time, defaults to provider's default. | |

**User's choice:** Mirror decomposer_model.
**Notes:** Matches the established Phase 36.3.7.10 idiom. Per-card
override deferred to a future phase if usage shows need.

## DEFCON gating for goal_mode card creation

| Option | Description | Selected |
|--------|-------------|----------|
| Always-allowed; budget tightens with DEFCON | goal_mode always settable. DEFCON tier dials `--goal-max-turns` ceiling. Aligns with security memory: stricter levels RESTRICT, don't REMOVE. | |
| Gated at DEFCON ≤ 3 | Refuse to create goal_mode cards at DEFCON 1-3. Conservative — autonomy treated as inherently risky. | |
| No DEFCON coupling for this phase | Skip DEFCON integration; ship goal_mode with budget cap only. Defer DEFCON gating to the future DEFCON-tiered phase. Smaller scope this phase. | ✓ |

**User's choice:** No DEFCON coupling for this phase.
**Notes:** Folds into the same future DEFCON-tiered phase that already
owns the CR-01 symlink-bypass deferral. Keeps Phase 36.3.7.12 focused
on the loop mechanics + budget primitive.

## Dispatcher integration topology

| Option | Description | Selected |
|--------|-------------|----------|
| Same dispatcher, in-process goal loop | Existing dispatcher tick picks up goal_mode cards via normal `ready → running` claim. Worker reads `goal_mode` on spawn, enters in-session loop. No separate worker pool. Matches hermes-agent spec. | ✓ |
| Dedicated /goal worker spawn path | Dispatcher detects goal_mode and dispatches via separate code path with own concurrency cap. More observability but doubles spawn-fn surface. | |
| Standalone `kanban-goal-loop` daemon | Goal loop runs in separate long-lived process. Maximum isolation but biggest new infrastructure. | |

**User's choice:** Same dispatcher, in-process goal loop.
**Notes:** Matches the hermes-agent design ("worker keeps going in the
same session — it doesn't exit and wait to be re-dispatched"). Crate
isolation fence holds (`ironhermes-kanban` continues to have zero
`ironhermes-gateway` dep).
