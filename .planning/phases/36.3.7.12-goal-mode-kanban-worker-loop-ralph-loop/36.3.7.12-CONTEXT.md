# Phase 36.3.7.12: Goal mode - kanban worker loop (Ralph loop) - Context

**Gathered:** 2026-06-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Extends the kanban auto-decompose infrastructure (Phase 36.3.7.10's per-tick
TRIAGE→TODO LLM rewriter via `DecomposeFn`) into a full in-session autonomous
worker loop on the same dispatcher. A card opts in via a per-card `goal_mode`
flag set at create-time. After the existing dispatcher promotes the card to
RUNNING and spawns a worker the normal way, the worker reads `goal_mode` from
its env and enters a Ralph-style in-session loop: after every turn an
auxiliary judge LLM evaluates the worker's output against the card's
`title + body` (treated as literal acceptance criteria). The loop terminates
on one of three conditions:

1. Judge agrees the goal has been met (worker proceeds to call `kanban_complete`).
2. Worker self-terminates (`kanban_complete` or `kanban_block`).
3. Per-card turn budget (`--goal-max-turns N`, default 20) is exhausted →
   card moves to **BLOCKED** for human review, not silent exit.

Companion to Phase 36.3.7.11's manual-review dashboard — goal_mode is the
OPT-IN inverse of the manual flow, not its replacement. Phase 36.3.7.10's
`auto_decompose` remains unchanged and continues to drive TRIAGE→TODO
LLM rewrites independently of this loop.

**Scope anchor:** per-card `goal_mode` flag + CLI/tool surface to set it +
in-session worker goal loop with auxiliary judge + per-card turn budget +
BLOCKED-on-budget-exhaustion semantics. NOT DEFCON gating (deferred to the
existing DEFCON-tiered phase), NOT a separate dispatcher pool, NOT a
dashboard UI for goal_mode toggle (CLI + tool surface only this phase —
dashboard toggle is a follow-on UI phase).

</domain>

<decisions>
## Implementation Decisions

### D-01: goal_mode opt-in mechanism — per-card flag
A new `goal_mode BOOLEAN NOT NULL DEFAULT 0` column lands on the `tasks`
table. Three create-time surfaces set it:

- **CLI:** `ironhermes kanban create --goal [--goal-max-turns N] "Title" --body "Acceptance: ..."`
- **LLM tool:** `kanban_create` accepts a `goal_mode: bool` arg (and
  `goal_max_turns: u32`).
- **Dashboard:** out-of-scope this phase; follow-on UI phase adds the toggle
  to the CreateTaskModal.

Not per-board, not per-tenant, not per-profile. Per-card only. The card's
`body` is the literal acceptance criteria the auxiliary judge evaluates
against — body content is load-bearing, not advisory.

### D-02: Auto-advance scope — in-session goal loop, not cross-state autonomy
The /goal worker does **not** auto-advance cards across multiple statuses
(no TRIAGE→TODO→IN_PROGRESS→DONE pipeline this phase — `auto_decompose`
already covers TRIAGE→TODO). Instead, after the existing dispatcher claims
a `goal_mode=true` READY card and promotes to RUNNING, the spawned worker
detects the flag from its env and enters an in-session loop. Each turn:

1. Worker produces output (tool calls + textual response).
2. Auxiliary judge LLM evaluates output against `title + body`.
3. If judge says goal not met AND budget remains → worker continues the
   SAME session (no re-dispatch, no re-spawn, no DB write between turns
   beyond a heartbeat).
4. If judge says met OR worker calls `kanban_complete`/`kanban_block` OR
   budget exhausted → loop ends.

Loop end is the same as the existing manual flow: `kanban_complete` →
DONE; `kanban_block` → BLOCKED; budget exhaustion is a synthetic
`kanban_block(reason="goal_max_turns exhausted; needs human review")`
emitted by the worker shell BEFORE process exit.

### D-03: Budget + kill-switch primitives — per-card budget only
- **Per-card turn budget:** `--goal-max-turns N` flag at create, defaults
  to 20. Stored on the task row as `goal_max_turns INTEGER`. NOT
  workspace-wide concurrency cap. NOT global kill-switch beyond the
  existing dispatcher kill paths.
- **Heartbeat reclaim:** the existing 4h-no-heartbeat → READY mechanism
  (Phase 36.3.7.6 `KanbanHeartbeatTool`) applies unchanged. The judge
  evaluation runs between turns inside the worker process — workers must
  still heartbeat during long single-turn operations.
- **Budget exhaustion is BLOCKED, not silent.** A goal_mode worker that
  burns its turn budget without satisfying the judge MUST emit
  `kanban_block(reason="goal_max_turns exhausted; needs human review")`
  before exiting. Worker-shell-side enforcement: when the per-turn
  counter hits `goal_max_turns`, the worker harness intercepts and forces
  the block call so a hung judge cannot escape with a `protocol_violation`.

### D-04: Failure handling — budget exhaustion → BLOCKED
- Judge says not-met + budget exhausted → `kanban_block` (D-03 above).
- Judge fails (network error, rate limit, malformed response) → log as
  `judge_error` event payload subkind on an `Edited` event row (reuses
  the nd7 producer pattern — events.rs frozen surface preserved). Worker
  treats failed judge call as "judge says not met" and increments the
  turn counter. Two consecutive judge errors → escalate to
  `kanban_block(reason="judge unavailable")`.
- No auto-retry beyond what the dispatcher already does for `reclaim` of
  heartbeat-failed runs (Phase 36.3.7.5/6 idiom). A `goal_mode` card that
  was reclaimed once and is back in READY is picked up the normal way and
  the loop restarts from turn 0.

### D-05: Judge model config — mirror decomposer_model
Add `judge_model: String` to `KanbanConfig` (sibling of `decomposer_model`
at `config.rs:92-95`). Empty string = use `auxiliary.kanban_judge` config
then fall back to main provider. Same precedence pattern as
`decomposer_model`. NO per-card `--goal-judge-model` override surface this
phase (open question deferred — see Deferred Ideas).

### D-06: Dispatcher integration — same dispatcher, in-process loop
The existing dispatcher tick is unchanged. No `/goal`-specific spawn path,
no separate concurrency cap, no standalone daemon. The dispatcher claims
`goal_mode=true` cards via the normal `ready → running` claim and spawns a
worker the normal way. The worker shell detects `goal_mode` on spawn (via
the existing `HERMES_KANBAN_TASK` env-var pattern from Phase 36.3.7.6 —
the worker can `kanban_show` and read `goal_mode` from the result, or the
dispatcher can additionally set `HERMES_KANBAN_GOAL_MODE=1` /
`HERMES_KANBAN_GOAL_MAX_TURNS=N` for cheap env-read). The worker is
responsible for entering the in-session loop. Outside the worker process,
the rest of ironhermes sees a normal long-running task that calls
`kanban_complete`/`kanban_block` at the end. **Crate-isolation fence holds**
— `ironhermes-kanban` continues to have zero `ironhermes-gateway` dep.

### D-07: DEFCON gating — NOT in scope this phase
`goal_mode` cards can be created at all DEFCON tiers in this phase's
shipping config. DEFCON-tiered budget caps (e.g., DEFCON 5 ceiling 50,
DEFCON 1 ceiling 5) are explicitly deferred to the same future
DEFCON-tiered phase that already owns the CR-01 symlink-bypass deferral
and the broader DEFCON 5→1 hardening sweep. Tracker: see Deferred Ideas.

### D-08: Worker tool surface — already wired
- `HERMES_KANBAN_TASK` env var pattern: already in use per Phase
  36.3.7.6 commit `ed1aee3c`. Worker tools `kanban_show` /
  `kanban_heartbeat` / `kanban_complete` / `kanban_block` already exist.
- `kanban-worker` skill is already bundled per-profile (Phase 36.4.1+
  skills library work). This phase does NOT create a new worker skill —
  it amends the existing skill's documentation to describe the goal loop
  + new env vars + budget behavior.
- `protocol_violation` event already exists (Phase 36.3.7.10) for exit-0
  while status=running without complete/block. Goal_mode does NOT change
  this contract — the worker shell's budget-exhaustion path explicitly
  calls `kanban_block` before exit so protocol_violation cannot fire on
  a budget hit.

### Claude's Discretion
- Exact spelling of new SQL column name (`goal_mode` vs `goal_loop` —
  prefer `goal_mode` to match hermes-agent's published spec the user
  referenced).
- Whether the auxiliary judge LLM call uses the existing
  `auxiliary.kanban_decomposer` config-resolution helper or gets its own
  helper fn (both work; planner picks the cleanest factoring).
- Exact env var name for the goal-budget signal if D-06's optional env
  enrichment path is used (e.g., `HERMES_KANBAN_GOAL_MAX_TURNS` is one
  reasonable choice but the planner can pick).
- Whether judge invocation reuses the existing decomposer LLM call site
  via a thin wrapper or stands up its own `kanban_judge` tool.
- Event payload subkind tag spelling for judge events ("subkind":"judge_verdict"
  vs "judge_eval" — pick one and pin in PLAN.md).

<code_context>
## Existing Code Insights

### Reusable Assets
- **`DecomposeFn` closure injection point** (`crates/ironhermes-kanban/src/decomposer.rs`):
  Phase 36.3.7.10 established the pattern. A `JudgeFn` closure can be
  added the same way — exported from `lib.rs`, accepted by the
  AgentRuntime constructor or KanbanStore::with_judge(closure), invoked
  inside the worker process per turn.
- **`auto_decompose` config + per-tick limit** (`config.rs:72-95`):
  Goal-loop does NOT need a "per tick" knob because the loop runs
  in-session, but the **config layout** (opt-in boolean + integer cap +
  model string) is the template for `judge_model` (D-05). Existing
  defaults helper fn `default_auto_decompose_per_tick()` shows the
  serde idiom to copy.
- **`KanbanHeartbeatTool`** (Phase 36.3.7.6, `tools/heartbeat.rs`): the
  4h-no-heartbeat reclaim path is the only kill-switch goal-mode workers
  need beyond the per-card turn budget.
- **`HERMES_KANBAN_TASK` env-var pattern** (Phase 36.3.7.6 commit
  `ed1aee3c` + the test serialization in `tools_smoke.rs`): the existing
  env-bridge for worker spawn. Adding `HERMES_KANBAN_GOAL_MODE` /
  `HERMES_KANBAN_GOAL_MAX_TURNS` follows the same convention.
- **`KanbanEventKind::Edited` + JSON subkind payload** (quick task nd7
  precedent + Phase 36.3.7.6 frozen surface): the in-tree pattern for
  emitting new event semantics without growing the enum. Goal-loop events
  (`judge_verdict`, `judge_error`, `goal_turn_advanced`,
  `goal_budget_exhausted`) MUST use this pattern.
- **`cas::assert_run_id_tx`** (`cas.rs:181-199`): the run-id-gated
  transaction helper. Per-turn counter writes must be wrapped so a
  reclaimed worker cannot mutate state against a stale run.

### Established Patterns
- **Opt-in defaults off**: every prior autonomous primitive
  (`auto_decompose`, gateway notifier, `dispatcher_enabled`) ships
  default-disabled. Goal_mode follows the same rule — `goal_mode` column
  defaults to 0; no global "enable goal mode" config knob this phase.
- **Closure injection over plugin loader**: confirmed by
  `project_plugin_loader_rejected`. New runtime primitives ship as
  direct AgentRuntime fields, not via a plugin registry.
- **Frozen event enum + subkind tag**: Phase 36.3.7.6 + quick task nd7
  precedent. Phase 36.3.7.12 MUST NOT add `Goal*` variants to
  `KanbanEventKind`.
- **Bilateral regression test discipline**: every BUG ships producer +
  consumer in same commit set (LEARNINGS 2026-05-30). Goal-loop work
  ships goal-emit producer test + worker-shell-budget-enforcement
  consumer test.
- **Crate-isolation fence**: `ironhermes-kanban` MUST NOT depend on
  `ironhermes-gateway`. The goal-loop work continues to honor this — the
  `JudgeFn` closure (if introduced) is the boundary the same way
  `DecomposeFn` already is.

### Integration Points
- **New `tasks` columns:** `goal_mode BOOLEAN NOT NULL DEFAULT 0` +
  `goal_max_turns INTEGER NOT NULL DEFAULT 20`. SQLite migration via the
  existing `KanbanStore::new` schema-bump path (Phase 36.3.7.5/6
  precedent — `KanbanStore::new` drops legacy tables and re-creates).
  Per-card runtime counter ALSO needs storage — TBD by planner (likely a
  `goal_turn_counter INTEGER NOT NULL DEFAULT 0` column or a
  `goal_turns` join table).
- **CLI surface** (`crates/ironhermes-cli/src/kanban/`): `kanban create`
  arg parser gains `--goal` + `--goal-max-turns`. `kanban show` output
  gains `goal_mode` + `goal_max_turns` + `goal_turns_used` lines when
  applicable.
- **LLM tool surface** (`crates/ironhermes-kanban/src/tools/create.rs`):
  `KanbanCreateTool` JSON schema gains `goal_mode` + `goal_max_turns`
  fields. NO new tool — Phase 36.3.7.6 froze the verb set; goal_mode is
  a flag on existing `create`.
- **Worker harness** (likely `crates/ironhermes-agent/src/worker_loop.rs`
  or wherever the spawned-worker entry point lives — planner to confirm
  during research): adds the in-session loop + judge call + budget
  enforcement. This is the largest new surface in the phase and is the
  natural seat for `JudgeFn` injection.
- **Dispatcher** (`crates/ironhermes-kanban/src/dispatcher.rs`):
  unchanged claim/promote logic. May optionally set
  `HERMES_KANBAN_GOAL_MODE` env var on spawn if the planner chooses the
  env-bridge variant over a `kanban_show`-on-spawn lookup.

## Specific Ideas

- **Authoritative spec source:** the user pasted a complete design
  reference (captured in `36.3.7.12-DISCUSSION-LOG.md`) describing
  hermes-agent's Goal Mode design — CLI shape, in-session loop,
  auxiliary judge, body-as-acceptance-criteria, budget-exhaustion-as-block,

  Phase 36.3.7.12 ports this design to ironhermes. The CLI ergonomics

- **Example canonical usage** (from the spec):
  ```bash
  ironhermes kanban create "Translate the docs site to French" \
    --body "Acceptance: every page translated, no English left, links intact." \
    --assignee linguist \
    --goal \
    --goal-max-turns 15
  ```
- **Inter-agent communication via comments** (already present in
  ironhermes-kanban): goal-loop workers continue to read the full
  comment thread on spawn via `kanban_show`. No change to the comment
  protocol for this phase.

## Deferred Ideas

- **DEFCON-tiered budget caps** — DEFCON 5 ceiling 50 / DEFCON 3 ceiling
  20 / DEFCON 1 ceiling 5 (or whatever the DEFCON-tiered phase decides).
  D-07 explicitly defers. Pair with the existing CR-01 symlink-bypass
  deferral in the same future DEFCON-tiered phase.
- **Dashboard UI for goal_mode toggle** — CreateTaskModal gets a
  "Goal mode" checkbox + max-turns field; ScreenKanban renders a `⚙`
  glyph on goal_mode cards. Follow-on UI phase. Not blocking this phase.
- **Per-tenant or per-board goal_mode policy** — opt-in default per-board,
  or "only assignees in profile group X may set goal_mode". Out of scope;
  v1 is per-card only.
- **Dedicated `/goal` worker pool with separate concurrency cap** —
  rejected per D-06. Would be revisited only if observability shows that
  goal-loop workers are starving manual workers under load. Not
  speculatively scoped.
- **Standalone `kanban-goal-loop` daemon** — rejected per D-06. Too much
  new infra for v1.
- **Per-card `--goal-judge-model` override** — D-05 ships only the
  workspace-level `judge_model` config. Per-card override would let
  expensive cards use a stronger judge; defer until usage shows the
  need.
- **Goal-loop trajectory schema** — specialized trajectory events
  (`goal_advanced`, `goal_decomposed`, `goal_failed`) beyond the
  `KanbanEventKind::Edited` subkind tag pattern. The trajectory ledger
  already exists (`ironhermes-trajectory`); a richer schema there is a
  follow-on observability phase.
- **`kanban-orchestrator` skill anti-temptation rules** — the
  pasted spec describes orchestrator-profile toolset restrictions
  (`kanban`, `gateway`, `memory` only). Goal_mode does not require this
  skill to ship — it operates fine on a normal worker profile. Skill
  authoring is a separate Phase 36.4.* work item.
