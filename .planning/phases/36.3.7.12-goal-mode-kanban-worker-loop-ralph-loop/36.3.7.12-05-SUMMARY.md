### Task 1 — dispatcher passthrough + reclaim reset + handoff coverage + cap enforcement (D-04 / D-06 + Pitfall 4 mitigation)

**4 new integration tests in `crates/ironhermes-kanban/tests/dispatcher_logic.rs`** (+599 lines):

1. **`goal_mode_no_dispatcher_change` (D-06)** — Builds a board with two ready cards (A: goal_mode=false; B: goal_mode=true, goal_max_turns=7), injects a recording spawn_fn that captures each `(task.id, task.goal_mode)` invocation. After `run_dispatch_tick`:
   - Both cards reach `running`.
   - Mock spawn_fn called exactly twice (once per card).
   - Card A reached spawn_fn with `goal_mode=false`; card B with `goal_mode=true` — dispatcher does NOT strip the flag.
   - Per-task event-kind *list* equality: `a_kinds == b_kinds` (same ordering, same counts — stronger than set equality, catches ordering drift).
   - Zero goal-loop subkind events at the dispatcher layer (no `judge_verdict`, `goal_turn_advanced`, `goal_budget_exhausted` in any payload) — those only land from the worker process via Plan 04's wrapper.

2. **`reclaim_resets_goal_counter` (D-04)** — Seeds a goal_mode=true card with `goal_max_turns=10` + `goal_turns_used=3` + expired claim + NULLed `claim_pid` (so Step 1 `detect_crashed_workers` skips it and only Step 3 `reclaim_stale_claims` fires) + `scheduled_at = now + 3600.0` (so Step 6 doesn't re-claim on the same tick). After `run_dispatch_tick`:
   - `task.status == "ready"` (release_claim ran).
   - `task.goal_turns_used == 0` (reset wired into the reclaim path).
   - `task.goal_mode == true` (the flag persists; only the counter resets).

3. **`goal_mode_card_reclaim_preserves_judge_history` (handoff coverage)** — Seeds a goal_mode card with `body="Acceptance: produce a haiku with exactly 5/7/5 syllables."`, claims under run_id_A + claim_lock_A, emits two `judge_verdict` events tied to run_id_A via `KanbanEventKind::Edited` + JSON subkind payloads (frozen-surface contract preserved). After a reclaim tick + a second tick that re-claims via ok_spawn:
   - `current_run_id` is `Some(run_id_B)` with `run_id_B != run_id_A`.
   - `claim_lock_B != claim_lock_A`.
   - `task.body` is byte-identical before vs after reclaim (acceptance criteria byte-stable).
   - The two `judge_verdict` event payloads are byte-identical before vs after reclaim (prior task_events NOT deleted by reclaim).

4. **`goal_mode_card_consecutive_failures_caps_reclaim` (cap enforcement)** — Seeds a goal_mode card with `failure_limit=2` + `consecutive_failures=1` (= cap - 1) + expired claim + NULLed claim_pid. After `run_dispatch_tick`:
   - `task.status == "blocked"` — cap fires.
   - `task.consecutive_failures == 2` — exactly at the limit.
   - `task.goal_mode == true` — flag persists across breaker trip.
   - `gave_up` event emitted.

Mirrors `circuit_breaker_trips_on_reclaim_path`'s shape with goal_mode=true. Locks: goal_mode does NOT bypass the `failure_limit` cap; without this cap, the reclaim reset would create a fresh budget every respawn and produce infinite re-spawn for a card whose worker keeps killing itself mid-loop.

**One-line wiring in `crates/ironhermes-kanban/src/dispatcher.rs` (+11 lines)** — inside `reclaim_stale_claims`, AFTER `release_claim` resets the row to `ready` and BEFORE the `consecutive_failures` bump:

```rust
// Phase 36.3.7.12 D-04: when a goal_mode card is reclaimed, reset its
// per-card turn counter so the next worker starts at goal_turns_used=0
// with a fresh budget. The CAS gate from Plan 02 (bump_goal_turn_counter)
// already prevents the OLD run from corrupting state; this reset is the
// handoff side of the contract so the NEW run sees a clean budget.
// Plan 05 Task 1 wiring (the one-line addition the planner anticipated).
if task.goal_mode {
    let store = ctx.store.lock().await;
    let _ = store.reset_goal_turn_counter(&task.id);
}
```

The `let _ =` swallows errors to match the surrounding reclaim path's tracing-only failure mode — the reclaim itself must always proceed. The reset is un-CAS-gated by design (Plan 02 Task 3 decision): the reclaim path is the only privileged caller; the new claim does not yet exist at the moment of reset, so a run-id check would be vacuous.

## Deferred Follow-ups (seed scope for the next phase)

These five findings emerged from live UAT and become the seed scope for the follow-up phase the orchestrator will insert after closing 36.3.7.12. **Captured verbatim from operator-supplied notes.**

### FINDING-01: `HERMES_KANBAN_DB` is set-but-never-read

`worker_spawn.rs:112-115` sets the env var to bridge dispatcher↔worker DB paths across profile boundaries, but NO consumer reads it. `KanbanStore::open_default()` and `KanbanStore::open_for_board(slug)` both resolve through `paths::kanban_db_path()` which is HERMES_HOME-relative. When dispatcher runs without `--profile` (HERMES_HOME=`~/.ironhermes`) and worker runs with `--profile dev` (HERMES_HOME=`~/.ironhermes/profiles/dev`), they hit DIFFERENT DBs. Operator hit this during UAT — fix is option A (profile-match everywhere) which is brittle. Real fix: add `KanbanStore::open_from_env()` constructor that reads `HERMES_KANBAN_DB` first, falls back to `kanban_db_path()`. Plan 04's `run_single` wrapper at line 935 needs to use that. The 6 LLM kanban tools should also adopt it.

### FINDING-02: `Command::new("ironhermes")` bare PATH lookup is a UAT footgun

`worker_spawn.rs:254` shells out to whatever `ironhermes` is on PATH — typically a `cargo install`ed copy. Operator hit this when their `~/.local/bin/ironhermes` symlink pointed at a release binary from May 31 (predating this entire phase). Worker silently ran pre-Plan-04 code with no goal loop. Fix: honor `IRONHERMES_WORKER_BIN` env var if set, fall back to `"ironhermes"` PATH lookup. Allows `cargo run` in a worktree to pin worker subprocesses to the same code base via one-line export.

### FINDING-03: Goal-mode workers thrash under unrestricted toolsets

Live UAT showed gemini-3.5-flash interpreting impossible/ambiguous acceptance criteria as "use terminal + delegate_task to figure out a workaround." The parent agent loop's 50-iteration budget combined with subagent timeouts (300s default) means a single goal-mode TURN can consume 10+ minutes producing nothing. Fix options: (a) default goal-mode workers to a restricted toolset (no `terminal`, no `delegate_task`); (b) clamp inner agent loop max_iterations when `HERMES_KANBAN_GOAL_MODE=1` is set; (c) document recommended UAT prompt patterns. Recommend (a)+(c).

### FINDING-04: Profile-context documentation gap

The operator's interactive shell, the dispatcher subprocess, and the worker subprocess each resolve HERMES_HOME differently when `--profile` is partially applied. No runbook captures that ALL kanban verbs in a UAT chain must agree on profile. Docs need: (a) the per-process HERMES_HOME table; (b) the kanban CLI cheatsheet with explicit `--profile` examples; (c) the symlink rebuild workflow when iterating on worker code; (d) card-reset SQL recipe for breaker recovery.

Also folds in the Row 1 criterion refinement from this plan's UAT: VALIDATION.md should be amended to "judge_verdict event OR worker-self-complete via kanban_complete" rather than requiring the judge event in every happy-path run.

### FINDING-05: `api_key` literal is the only worker-survivable credential form

Worker `env_clear()` (D-18) drops API-key env vars before spawn. `api_key_env: VAR` in `~/.ironhermes/config.yaml` cannot resolve in workers. `api_key:` literal works but is deprecated and prints a warning at every worker startup. Fix: introduce `api_key_file:` form that reads from a path (with mode 0600 enforcement), OR document that workers MUST use literal `api_key:` until an alternative ships.
