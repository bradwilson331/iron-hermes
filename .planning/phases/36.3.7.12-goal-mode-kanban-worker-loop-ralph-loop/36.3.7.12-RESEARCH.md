# Phase 36.3.7.12: Goal mode - kanban worker loop (Ralph loop) - Research

**Researched:** 2026-06-02
**Domain:** ironhermes-kanban worker loop + ironhermes-agent in-session control
**Confidence:** HIGH (all findings verified by direct codebase grep + file:line citations)

## Summary

The CONTEXT.md already locks every architectural decision; this research's job
was to pin the **exact file:line citations** the planner needs for each
integration touchpoint. Findings below confirm three load-bearing structural
facts:

1. **The "worker" is not a separate harness** — it is the same `ironhermes` CLI
   binary re-invoked with `HERMES_KANBAN_TASK` env set. The "in-session goal
   loop" wraps `AgentLoop::run()` (which itself iterates up to
   `max_iterations` turns). There is no `worker_loop.rs` to amend; the seat
   for the goal-loop wrapper is `crates/ironhermes-cli/src/main.rs` worker-mode
   branch + `crates/ironhermes-agent/src/agent_loop.rs::run`.

2. **The schema migration story is broken-on-purpose for now** —
   `crates/ironhermes-kanban/src/schema.rs:13` pins `SCHEMA_VERSION = 1` and
   `run_migrations` (line 180) is an explicit landing-place for v2. The phase
   MUST bump SCHEMA_VERSION → 2 and add a v2 ALTER branch with idempotent
   `ADD COLUMN` for both new columns. The DDL block uses
   `CREATE TABLE IF NOT EXISTS` so it does NOT add new columns to existing DBs
   — only the migration ladder does that.

3. **The decomposer LLM call site is reusable** —
   `crates/ironhermes-cli/src/kanban/commands.rs:1404-1557` (`build_runtime_decompose_fn`)
   is a ~150-line closure that resolves provider → builds `LlmClient` →
   sends `ChatMessage` pair → parses JSON. The judge wrapper can be a near-clone
   with a different system prompt and a `{verdict: "met"|"not_met", reason: ...}`
   response shape. Same three-tier model cascade applies, gated on a new
   `kanban_judge` role.

**Primary recommendation:** Treat the goal loop as a **CLI-side wrapper around
`AgentLoop::run()`** that lives in `crates/ironhermes-cli/src/main.rs` worker
branch (line 299-323). The wrapper: (1) reads `HERMES_KANBAN_GOAL_MODE`
env, (2) if set, calls `AgentLoop::run()` repeatedly inside a turn budget
loop, (3) injects a synthetic user-turn between iterations carrying the judge
verdict, (4) on budget exhaustion calls `kanban_block` synthetically and
exits. The kanban crate gets the schema + tool-schema changes; the CLI crate
gets the loop wrapper + judge LLM call site.

## Findings

### Finding 1 — Worker entry point is the CLI binary, not a "worker_loop.rs"

**Cited:** `crates/ironhermes-kanban/src/worker_spawn.rs:228-245` —
`spawn_worker_for_board` invokes `Command::new("ironhermes")` with
`--profile <assignee> chat -q "work kanban task <id>"`. No subprocess harness;
the worker IS `ironhermes chat -q`.

**Cited:** `crates/ironhermes-cli/src/main.rs:299-323` —
`register_kanban_tools_if_applicable` detects worker mode via
`std::env::var("HERMES_KANBAN_TASK").is_ok()` and registers the kanban tool
suite. This is the entry-point gate for "we are in worker mode."

**Cited:** `crates/ironhermes-cli/src/main.rs:281-288` —
`inject_kanban_guidance_if_worker` is the **canonical worker-detection
checkpoint** for in-process behavior changes. The goal-mode loop wrapper
belongs in the same neighborhood (called after this function, before/around
the `chat -q` command dispatch).

**Implication for planner:** There is no new worker process to write. The
goal loop is a **CLI-side wrapper** around the existing `chat -q` dispatch
that detects `HERMES_KANBAN_GOAL_MODE=1` and re-invokes `AgentLoop::run()`
in a turn-budget loop. The wrapper lives in `main.rs` near line 303 (worker
mode detection) and calls into a new helper in `ironhermes-cli/src/kanban/`
that owns the budget + judge state.

### Finding 5 — Schema migration: must use the migration ladder, not the IF NOT EXISTS path

**Cited:** `crates/ironhermes-kanban/src/schema.rs:13` —
`pub const SCHEMA_VERSION: i64 = 1;` (must bump to 2).

**Cited:** `crates/ironhermes-kanban/src/schema.rs:31-55` — `CREATE TABLE IF
NOT EXISTS tasks (...)` block. Adding columns to this DDL block has **no
effect on existing DBs** — `IF NOT EXISTS` short-circuits to a no-op when the
table is already present. New columns ONLY land via the migration ladder.

**Cited:** `crates/ironhermes-kanban/src/schema.rs:180-190` —
`run_migrations(conn, current)` is an explicit landing-place for v2. The
docstring shows the exact idiom to copy:

```rust
if current < 2 {
    let _ = conn.execute("ALTER TABLE tasks ADD COLUMN goal_mode INTEGER NOT NULL DEFAULT 0", []);
    let _ = conn.execute("ALTER TABLE tasks ADD COLUMN goal_max_turns INTEGER NOT NULL DEFAULT 20", []);
    // (decide here whether to add goal_turns_used or use a join table)
    conn.execute("UPDATE schema_version SET version = 2", [])?;
}
```

The `let _ =` pattern suppresses "duplicate column" errors on partial re-runs
(mirror of `ironhermes-state` precedent). The atomicity contract in the
docstring (lines 168-179) REQUIRES wrapping in `BEGIN`/`COMMIT` —
`KanbanStore::init_schema` already satisfies this. Phase 36.3.7.12 must NOT
weaken that wrapping.

**Per-turn counter storage:** RECOMMEND `goal_turns_used INTEGER NOT NULL
DEFAULT 0` as a column on `tasks` (single rusqlite write per turn under
`cas::assert_run_id_tx`). A join table is overkill — we never need historical
per-turn counts; the dashboard only needs "current turn / max".

**Correction to CONTEXT.md §code_context line 277-281:** The claim
"`KanbanStore::new` drops legacy tables and re-creates" is overstated. Per
schema.rs:5-6 the schema block uses `CREATE TABLE IF NOT EXISTS` (idempotent),
and the migration ladder at schema.rs:180 is the proper path. The `DROP TABLE
IF EXISTS kanban_notify_subs` at schema.rs:119 is a one-off orphan cleanup,
not a general drop-and-recreate pattern. The planner should use the migration
ladder, not table drops.

### Finding 8 — Worker-shell budget enforcement: wrap `AgentLoop::run()`

**Cited:** `crates/ironhermes-agent/src/agent_loop.rs:1336`
(`pub async fn run(&mut self, mut messages: Vec<ChatMessage>) -> Result<AgentResult>`).
This is the per-turn invocation site. The internal turn counter (line 1457:
`if turns_used >= self.max_iterations { ... }`) is the iteration ceiling for
a **single agent run**, not the goal loop.

**Recommended seat for goal loop:** a new helper in
`crates/ironhermes-cli/src/kanban/` (e.g. `goal_loop.rs`) that:

```rust
pub async fn run_goal_loop_if_enabled(
    agent_loop: &mut AgentLoop,
    initial_messages: Vec<ChatMessage>,
    task_id: &str,
    run_id: &str,
    claim_lock: &str,
    judge_fn: &JudgeFn,
) -> Result<()> {
    let goal_mode = std::env::var("HERMES_KANBAN_GOAL_MODE").is_ok();
    if !goal_mode {
        // normal worker path — single AgentLoop::run() call
        return agent_loop.run(initial_messages).await.map(|_| ());
    }
    let max_turns: u32 = std::env::var("HERMES_KANBAN_GOAL_MAX_TURNS")
        .ok().and_then(|s| s.parse().ok()).unwrap_or(20);
    let mut consecutive_judge_errors = 0u32;
    let mut messages = initial_messages;
    for turn in 0..max_turns {
        // 1. run one agent invocation
        let result = agent_loop.run(messages.clone()).await?;
        // 2. CAS-gated turn counter bump (Finding 9)
        bump_goal_turn(task_id, run_id, claim_lock)?;
        // 3. check for self-termination (kanban_complete / kanban_block called)
        if task_terminated(task_id)? { return Ok(()); }
        // 4. invoke judge
        let verdict = match judge_fn(JudgeRequest { ... }).await {
            Ok(v) => { consecutive_judge_errors = 0; v }
            Err(e) => {
                append_judge_error_event(task_id, run_id, &e)?;
                consecutive_judge_errors += 1;
                if consecutive_judge_errors >= 2 {
                    synthetic_kanban_block(task_id, "judge unavailable")?;
                    return Ok(());
                }
                continue;
            }
        };
        if verdict.met { return Ok(()); } // judge agrees → exit cleanly
        // 5. inject synthetic user-turn carrying verdict + reason
        messages.push(ChatMessage::user(&format!(
            "Judge verdict: not met. Reason: {}\nContinue working toward the acceptance criteria.",
            verdict.reason
        )));
    }
    // budget exhausted → synthetic block before exit
    synthetic_kanban_block(task_id, "goal_max_turns exhausted; needs human review")?;
    Ok(())
}
```

This is the **only seat** that needs to exist outside the existing
infrastructure. Everything else is amendment.

**Crate boundary check:** `goal_loop.rs` lives in `ironhermes-cli` (which
already depends on `ironhermes-kanban` and `ironhermes-agent`). It MUST NOT
move into `ironhermes-kanban` — that crate has zero dep on `ironhermes-agent`
per the locked crate-isolation fence (CONTEXT.md §code_context line 269-272).

### Finding 9 — CAS gating for per-turn counter writes

**Cited:** `crates/ironhermes-kanban/src/cas.rs:181-199`
(`assert_run_id_tx`). This is the existing gate for any worker-side mutation
— if the worker's `run_id` no longer matches the task's `current_run_id` (a
reclaim+respawn happened mid-turn), the write is rejected with
`KanbanError::StaleRunId`.

**Cited:** `crates/ironhermes-kanban/src/cas.rs:241-277` (`worker_write_gated`).
This is a higher-level helper that combines CAS-check + write inside one
`BEGIN IMMEDIATE` tx. Goal-loop per-turn writes (incrementing
`goal_turns_used`) SHOULD use this pattern — pass a closure that does the
`UPDATE tasks SET goal_turns_used = goal_turns_used + 1 WHERE id=?` work.

**Why this matters:** A worker reclaimed mid-loop must NOT bump the counter
against the new run. `assert_run_id_tx` + the `claim_lock` gate ensure the
reclaim+respawn produces a fresh `goal_turns_used = 0` (because the column
default is 0 on reclaim → ready; the new run starts from 0). The planner
should add a dedicated `KanbanStore::bump_goal_turn_counter(task_id, run_id,
claim_lock)` helper inside `store.rs` that wraps `worker_write_gated` for
exactly this purpose.

## Common Pitfalls

### Pitfall 1: Adding columns only to the `CREATE TABLE IF NOT EXISTS` DDL
**What goes wrong:** New columns never land on existing DBs because the
table already exists; only fresh DBs get them.
**Why:** `IF NOT EXISTS` short-circuits. The DDL block is "schema if blank",
the migration ladder is "schema upgrade for existing DBs."
**How to avoid:** Always add both — DDL block for fresh-DB path AND
migration ladder for existing-DB path. Bump `SCHEMA_VERSION`.
**Warning signs:** Tests pass (fresh DB), production breaks (existing DB),
`PRAGMA table_info(tasks)` shows missing columns.

### Pitfall 2: Crate-isolation fence breach
**What goes wrong:** Adding `ironhermes-agent` dep to `ironhermes-kanban`.
**Why:** The kanban crate is depended on by gateway, which must not transitively
pull the agent; the boundary is enforced by closure injection (`DecomposeFn`,
`SpawnFn`). The goal-loop wrapper MUST live in `ironhermes-cli`.
**How to avoid:** `JudgeFn` typedef lives in `ironhermes-kanban/src/judge.rs`
(sibling of decomposer.rs); the production `build_runtime_judge_fn` that
actually calls an LLM client lives in `ironhermes-cli/src/kanban/commands.rs`.
**Warning signs:** `cargo check -p ironhermes-kanban` pulls
`ironhermes-agent` into the build graph.

### Pitfall 3: Holding signal Read/Write across `.await`
**What goes wrong:** Clippy panics at runtime if a `GenerationalRef` or
`WriteLock` is held across an `.await` point (enforced by
`crates/iron_hermes_ui/clippy.toml`).
**Why:** Only relevant if the goal-mode work touches `iron_hermes_ui` Dioxus
components (it should NOT this phase — CONTEXT.md §canonical_refs line 217
confirms no UI work).
**How to avoid:** Goal-loop wrapper lives in `ironhermes-cli`, not `iron_hermes_ui`.
The dashboard UI change is deferred (CONTEXT.md §deferred lines 332-334).
**Warning signs:** Adding any `iron_hermes_ui` code in this phase.

### Pitfall 4: Counter bump without CAS gate
**What goes wrong:** A reclaimed worker continues looping, judge runs, judge
says "not met", wrapper bumps `goal_turns_used`. The new run (already started)
sees `goal_turns_used = 1` and falsely believes one turn was consumed.
**Why:** Reclaim+respawn doesn't reset `goal_turns_used` automatically.
**How to avoid:** Two-pronged defense: (a) the migration sets `goal_turns_used`
DEFAULT 0 AND the reclaim path explicitly `UPDATE tasks SET goal_turns_used=0
WHERE id=?` when releasing the claim; (b) all goal-loop counter writes go
through `worker_write_gated` (cas.rs:241) so a stale-run worker writes a
`claim_expired` advisory event instead of bumping the counter.
**Warning signs:** Worker logs show "judge says not met" but `goal_turns_used`
in the DB exceeds the number of `judge_verdict` events for the current run.

### Pitfall 5: Silent budget exhaustion
**What goes wrong:** Worker hits `goal_max_turns`, exits without calling
`kanban_block`, dispatcher sees orphaned `running` task → eventual
`protocol_violation` event after timeout.
**Why:** D-03 mandates the worker-shell intercepts and forces the block.
**How to avoid:** In the goal-loop wrapper (Finding 8), the loop's `for` body
MUST be wrapped in a structure that guarantees `synthetic_kanban_block(task_id,
"goal_max_turns exhausted; needs human review")` is called when the loop
exits without an earlier `return Ok(())`. RAII pattern: a `Drop` guard, or
explicit fall-through code after the loop body.
**Warning signs:** Tests show `protocol_violation` events on goal_mode cards
that hit the budget; this should NEVER happen — only natural completion,
judge-met exit, self-terminate (complete/block), or budget→block.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| LLM prompt injection via task `body` reaching judge | Tampering | Treat `body` as user message content (untrusted), judge system prompt is static + trusted (mirror commands.rs:1465-1466 pattern). |
| Worker spawning subprocess inheriting OPENAI_API_KEY | Information Disclosure | Already mitigated by `env_clear()` + allowlist at `worker_spawn.rs:234`. Goal_mode env additions ride the same allowlist. |
| Judge LLM cost runaway (model loop never converges) | Denial of Service | `goal_max_turns` budget IS the mitigation (D-03). Default 20 caps judge invocations at 20 per card. |
| Reclaim+respawn double-counting turns | Tampering | `worker_write_gated` (cas.rs:241) is the CAS gate; per-turn writes must use this. See Pitfall 4. |
