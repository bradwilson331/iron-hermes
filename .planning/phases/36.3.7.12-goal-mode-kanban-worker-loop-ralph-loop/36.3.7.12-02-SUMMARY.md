# Phase 36.3.7.12 Plan 02: Kanban-Crate Producer Surface for Goal Mode

Three independent kanban-crate-only additions that unblock Plan 03 (CLI surface, sibling worktree) and Plan 04 (goal loop wrapper, future wave): the `kanban_create` LLM tool's JSON Schema now advertises `goal_mode` + `goal_max_turns`; `build_kanban_worker_env` conditionally appends `HERMES_KANBAN_GOAL_MODE=1` + `HERMES_KANBAN_GOAL_MAX_TURNS=<budget>` only when `task.goal_mode == true`; `KanbanStore` gains `bump_goal_turn_counter` (CAS-gated) and `reset_goal_turn_counter` (un-gated, reclaim-only); and `events.rs` pins four `pub const &str` subkind tags + a compile-time exhaustive-match guard that breaks the build if a new `KanbanEventKind` variant lands.

## What Was Built

## Decisions Made

- **Schema-only delta in Task 1, no execute() edit.** Plan 01 had already wired the JSON args (`args.get("goal_mode")` / `args.get("goal_max_turns")`) into `CreateTaskOptions` so the LLM-caller surface was forward-compat the moment Plan 02's schema delta landed. The plan explicitly anticipated this ("for now accept the args opportunistically"). Task 1 Step 2 in PLAN.md was therefore a no-op — the execute() site was already correct.

- **Defensive 0 → 20 budget coercion repeated at env-build site.** Plan 01's `KanbanStore::create_task` already coerces `opts.goal_max_turns == 0 → 20`. Plan 02 repeats the coercion at `build_kanban_worker_env` so a struct-literal `Task { goal_mode: true, goal_max_turns: 0, .. }` (which can happen in test fixtures or future hand-rolled code paths) still emits "20" to the worker harness. Belt-and-suspenders — neither layer alone is sufficient because the two enter the env path via different code paths.

- **`reset_goal_turn_counter` is intentionally NOT CAS-gated.** T-36.3.7.12-02-E01 disposition in the threat register: `accept`. The reclaim path is the only privileged caller; the new claim does not yet exist at the moment of reset, so a run-id check would be vacuous. Documented in the fn docstring + threat register. Plan 05's integration test will assert no other call site lands.

- **Exhaustive-match frozen-surface guard, no catch-all arm.** `frozen_surface_no_new_variants` enumerates all 29 current `KanbanEventKind` variants explicitly. A new variant lands → match becomes non-exhaustive → COMPILE BREAK. This is the BUILD BREAK contract, not a runtime assertion. The test body also serves as documentation of the frozen surface.

- **`bump_goal_turn_counter` placed adjacent to `append_event`.** Both are public worker-side write helpers; co-locating them in the source mirrors the API expectations of the Plan 04 wrapper which uses both (write-counter then write-event under the same claim_lock guarantee).
