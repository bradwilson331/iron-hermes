<objective>
Add a regression integration test in `tests/uqm_session_queue_unification.rs` that exercises the exact failure mode from the UAT (2026-05-28T15:36-15:38 UTC): a parked per-chat worker MUST wake when `/queue` is invoked via the production handler entry point. Without this test, the regression could recur silently — the entire parent phase's 6-test suite passed under the broken code because none of them dispatched `/queue` through `handler.handle_with_multimodal` against a real parked worker.

**Why the existing tests missed this:** Every existing test in `uqm_session_queue_unification.rs` that exercises the worker pop-loop dispatches messages through `uqm.dispatch(...)` directly (lines 334-380 — `test_5_same_chat_messages_emit_5_eye_reactions_and_fifo_order_through_handler` is the closest pattern). `uqm.dispatch` ALWAYS calls `notify_one()` on success (user_queue.rs:154), so the wake works. The bug only manifests on the fast-path code where `handler.handle_with_multimodal` is invoked DIRECTLY (bypassing the dispatch loop's UQM call), reaches the `CoreCommandResult::Queued` arm, and pre-fix calls `session_queue.try_push` without ever touching UQM. The single existing test that DOES exercise this code path (`test_slash_command_bypasses_per_chat_worker` at line 835) does so against an EMPTY worker state — no `spawn_test_worker` is called, no real Notify-park happens, the bug is silently invisible because there is nothing to wake.

**What this test does that the others don't:**

1. Pre-loads 1 free-text event via `uqm.dispatch` so the worker is registered AND spawned via `spawn_test_worker`.
2. Waits for the worker to drain that initial event and park at `notify.notified().await` (observable: `send_log.len() >= 1` because `RecordingFailingAdapter.send_message` records the placeholder send before returning `Err`).
3. Dispatches 5 `/queue` events via `handler.handle_with_multimodal` DIRECTLY — exactly mimicking the runner.rs fast-path's `tokio::spawn(async move { handler.handle_with_multimodal(...).await })` body shape (runner.rs:943-967), but inline-awaited so the test thread can observe completion.
4. Asserts the worker wakes from each `notify_one()` call, pops the synthesized event, emits 👀, and invokes `handle_with_multimodal` on it. The primary signal is the 👀-reaction count on synthesized message_ids q_1..q_5 (worker emits 👀 inline at pop time per D-08 invariant — if the worker never wakes, the count stays at 0).
5. Asserts FIFO ordering of the 5 new 👀 reactions on the synthesized event message_ids.

**Under the unfixed code (handler.rs:805 direct try_push, no notify_one):** Step 4 times out. The 5 `/queue` synthesized events sit in `SessionQueue` with depth growing 1 → 5, but the worker remains parked at `notify.notified().await`. The 👀-count on q_1..q_5 stays at 0. The diagnostic panic dumps `send_log` + `reactions` + `SessionQueue.len` + an explicit "REGRESSION SIGNAL" note pointing at the wake-protocol re-introduction.

Purpose: lock the fix in CI so this exact regression cannot recur. The test fails closed (timeout panic with diagnostic dump) when the production code path lacks the wake — which is exactly what we need to detect a re-introduction of the bug.

Output: ~120-line test function appended at the bottom of `tests/uqm_session_queue_unification.rs`, after the existing `test_slash_command_bypasses_per_chat_worker` (which ends at line 923).
</objective>
