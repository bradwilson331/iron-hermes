<objective>
Fix the production regression where `/queue` typed during a busy free-text turn pushes the synthesized event onto `SessionQueue` but never wakes the parked per-chat worker. The UAT on 2026-05-28T15:36-15:38 UTC observed 128/129 `/queue` events stranded in the queue with zero 👀 reactions, confirming the worker was parked at `runner.rs:1045 notify_task.notified()` for the full session.

**Root cause** (from RESEARCH.md): `handler.rs:805` calls `self.session_queue.as_ref().try_push(&session_key, queued_event)` directly. `SessionQueue::try_push` has no Notify; it merely deposits the event in a `VecDeque` under an `std::sync::Mutex`. The only `notify_one()` call in the entire gateway is `user_queue.rs:154` inside `UQM::dispatch`. The `/queue` fast-path skips `UQM::dispatch` entirely (runner.rs:935-970 fast-path comment: "Skip the multimodal + UQM.dispatch path for this event"), so the handler-side push is the ONLY route — and it never signals.

**The fix (Option B from RESEARCH §Fix Space, validated against my live source read):** Replace the handler's direct `session_queue.try_push(...)` call with `uqm.dispatch(queued_event, None, None).await`. `UQM::dispatch` already performs push + Notify wake atomically under its own `tokio::sync::Mutex` (user_queue.rs:114-164). It is the single correct site for "event enters the queue lifecycle" because it owns the wake protocol.

**Why Option B (not A or C):**
- **Option A (handler calls notify_one() after its own try_push):** Requires the handler to know about the workers map, which means giving it an `Arc<UserQueueManager>` field AND coordinating with the no-worker case (call `dispatch` as fallback, which double-pushes — corrupting FIFO). Rejected.
- **Option B (handler delegates to UQM::dispatch):** Pushes once via UQM, Notify wake is automatic, sidecar payload pushed in lockstep (`push_multimodal((None, None))` is a no-op for text-only commands — `take_multimodal` returns `Some((None, None))` which `unwrap_or((None, None))` normalizes — verified no FIFO skew). Selected.
- **Option C (runner intercepts /queue before handler):** Splits command-parsing across two layers and breaks the existing test `test_slash_command_bypasses_per_chat_worker` (uqm_session_queue_unification.rs:835) which asserts the handler's intercept does the push. Rejected.

**No-worker case (RESEARCH Q2 / context_lock #2):** If `/queue` is the FIRST message on a fresh chat (no worker registered, no Notify in the workers map), `UQM::dispatch` returns `Ok(DispatchOutcome::WorkerSpawned)` and inserts a Notify but the handler — invoked from the runner's fast-path detached `tokio::spawn` — has no access to `worker_join_set_dispatch` to spawn a worker. The synthesized `/queue` event would then sit until the next free-text message triggers worker spawn via the normal dispatch loop. This is a **latent secondary gap**, NOT the UAT failure. The UAT failure is "wake EXISTING parked worker" (worker existed from prior free-text turns; Notify was already registered). Per `context_lock #2` and `RESEARCH Q2`, this phase fixes only the wake-parked case; the fresh-chat path remains a known scope boundary for a follow-up gap-closure phase. The plan does NOT silently sweep this — Plan 02 documents it explicitly and the handler's debug log makes the case observable in production traces.

**Cap-hit UX deduplication (context_lock #2):** Under the fix, the existing `Err(QueueError::CapacityReached { .. })` arm at handler.rs:823-844 (which fires `❌` + "⏳ Queue is full (128 messages). Wait for the agent to drain before sending more.") becomes **dead code on the fast-path** because `UQM::dispatch` (user_queue.rs:115-138) fires the identical UX before returning `Err`. The handler MUST detect this and return early — it must NOT also send its own cap-hit message (double-reply). The handler-side cap-hit arm is preserved as a **defensive fallback** for the `else`-branch where `user_queue_manager` is `None` (handlers constructed via `::new()` without `set_user_queue_manager` — e.g., the legacy GW-05 tests at `tests/running_agent_guard_tests.rs` and the session_queue_integration.rs harness which is what the parent phase's D-20 contract preserves).

**Depth-aware reply preservation (context_lock #3):** Current behavior at handler.rs:807-812 computes `let depth = queue.len(&session_key)` immediately after `try_push` and emits either `"Queued for the next turn."` (depth ≤ 1) or `"Queued for the next turn. ({depth} queued)"` (depth > 1). Under the fix, the same `queue.len(&session_key)` lookup is moved AFTER the successful UQM::dispatch await. Wording is byte-identical. The `Arc<SessionQueue>` field is still on the handler (D-20 contract preserves `set_session_queue`), so `self.session_queue.as_ref().map(|q| q.len(&session_key))` remains available.

Purpose: close the second production regression from Phase 36.17.2 (the first was the slash-command serialization fixed by Plan 05 of the parent phase). After this plan ships, `/queue` typed during a busy turn produces a 👀 reaction at pop time and is processed as the next free-text turn — restoring the depth-128 buffering capability the user expects.

Output: ~25-line addition to `handler.rs` (struct field + setter), ~20-line rewrite of the `CoreCommandResult::Queued` body, ~5-line reorder in `runner.rs::run_gateway`.
