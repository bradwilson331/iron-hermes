# Phase 36.3.7.9: Multi-board CLI - Context

**Gathered:** 2026-05-31
**Status:** Ready for planning
**Source:** /gsd:discuss-phase (replaces 2026-05-30 stub)

<domain>
## Phase Boundary

Ship the multi-board CLI surface: `hermes kanban boards list/create/switch/show/rename/rm` + a `--board <slug>` flag on existing `kanban` subcommands; a 4-tier `current_board` cursor resolution; the multi-board on-disk layout at `~/.hermes/kanban/boards/<slug>/kanban.db`; per-board `schema_version` rows with auto-migration; LLM-tool surfaces gain optional `board: Option<String>` without renumbering. Default-board single-DB users are NOT migrated — the existing `~/.hermes/kanban.db` stays at its legacy path for back-compat.

**In scope:**
- `hermes kanban boards {list, create, switch, show, rename, rm}` (+ `--delete` on `rm`)
- `--board <slug>` flag on every existing `kanban` subverb
- Board resolution function: `--board` flag > `HERMES_KANBAN_BOARD` env > `~/.hermes/kanban/current` file > `default`
- Multi-board layout: `~/.hermes/kanban/boards/<slug>/{kanban.db, workspaces/, logs/}`
- Per-board `schema_version` row + auto-migrate-with-banner on access
- LLM tool optional `board: Option<String>` param + always-emit `board_resolved` envelope field
- `notifier.toml` config surface with `subscribe_boards = ["*"]` default (scoping inert in v1, codepath exists)
- Slug validation: lowercase alnum + `-` + `_`, 1-64 chars, must start alphanumeric

**Out of scope (deferred):**
- Cross-board task links (docs §71 forbids — schema simplification)
- Migrating the legacy `~/.hermes/kanban.db` into `boards/default/` (back-compat preserved)
- Dashboard board switcher UI (docs §150 describes it but UI lives in a later phase)
- Tenant namespacing (mentioned in docs §75 but orthogonal to board scope)
- Cross-bot/cross-profile notifier scoping enforcement (codepath exists, only `"*"` exercised)
- Per-board RBAC or auth (single-host trust model preserved)

</domain>

<decisions>
## Implementation Decisions

### D-01 — On-disk layout & migration (locked by docs/kanban/reference.md §71-90)
- **Default board stays at** `~/.hermes/kanban.db`. No file move, no symlink, no copy.
- **Named boards live at** `~/.hermes/kanban/boards/<slug>/kanban.db` + sibling `workspaces/` and `logs/` directories.
- **No migration step** on existing installs — they keep working as single-board users with zero filesystem disturbance.
- **Rationale:** Back-compat for single-board users is absolute; `boards/<slug>/` is opt-in by creating a non-default board.

### D-02 — `current_board` cursor resolution (locked by docs §95-100)
- 4-tier precedence, highest first:
  1. Explicit `--board <slug>` CLI flag
  2. `HERMES_KANBAN_BOARD` env var (dispatcher sets this when spawning workers)
  3. `~/.hermes/kanban/current` file (slug-only, single line, written by `boards switch`)
  4. Literal `"default"`
- Resolver returns `(slug, db_path, source)` so downstream callers know provenance.
- **Implementation hint:** Single pure-function `resolve_board_context(cli_flag: Option<&str>) -> BoardContext` reusable from CLI + LLM tools + dispatcher + notifier; uses `Option::or_else` chaining (no nested branches).

### D-03 — Notifier polling scope (decided this session)
- **v1 default: global sweep across all boards.** Mirrors the dispatcher behavior documented in §71 ("one dispatcher sweeps all boards per tick").
- **Scoping surface added day-one** to prevent hermes-agent issue #21877 (multi-profile cross-bot contamination):
  - Add `~/.hermes/kanban/notifier.toml` with `subscribe_boards = ["*"]` as the only default-shipped value.
  - Notifier reads this on each tick → if `["*"]`, glob-expands via `list_boards()`; else honours the explicit slug list.
  - **Only the `["*"]` branch is exercised in v1** — the explicit-list codepath ships inert and is unit-tested but not consumed.
- **Rationale:** IronHermes is single-host (`docs/kanban/reference.md` §71), so global sweep is fine today; but designing the config surface upfront means we never have to migrate a `notifier.toml` schema later when multi-profile use-cases arrive.

### D-04 — Dispatcher scope (locked by docs §71)
- One dispatcher (gateway-embedded by default per `kanban.dispatch_in_gateway: true`) sweeps **all boards** per tick.
- Workers are spawned with `HERMES_KANBAN_BOARD` env-var pinned so they can't see other boards.
- **No code change required for D-04** beyond:
  - Iterating `list_boards()` inside the existing dispatcher tick (currently single-board hard-coded)
  - Setting `HERMES_KANBAN_BOARD` from the per-board sweep iteration (already partially wired in `worker_spawn.rs:117`)
- **Rationale:** Zero architectural surprise — extends the existing tick loop, doesn't restructure it.

### D-05 — Cycle detection scope (locked by docs §71)
- **No code change required.** Cross-board task linking is forbidden by docs; `task_links` rows can only reference task IDs that live in the same DB.
- Existing cycle-detection SQL (`WITH RECURSIVE` ancestor walk introduced in Phase 36.3.7.8) executes against whichever `db_path` the active connection holds. No scope expansion needed.
- **Rationale:** The forbidden-cross-board-links invariant is what keeps cycle detection trivially correct under multi-board.

### D-06 — Schema migration on board access (decided this session)
- **Auto-migrate with stderr banner.** On any access (open via CLI, `--board <slug>`, LLM tool with explicit `board:`, dispatcher per-tick sweep), if `schema_version < CURRENT_VERSION`:
  - Run pending migrations transparently inside `KanbanStore::open(...)`.
  - Emit one-line stderr banner: `[kanban] migrated board '<slug>' from v<old> to v<new>`.
  - Bump the `schema_version` row.
- Single code path for default board AND named boards — both go through the same `open_with_migrate` helper.
- **Rationale:** Silent auto-migrate is too magical for end-users debugging "why did my board change?"; refuse-and-prompt punishes the common case of bumping a `hermes` binary. The banner threads the needle.

### D-07 — `boards rm` semantics (decided this session)
- **Archive path is permissive** (default `boards rm <slug>`):
  - Always moves `~/.hermes/kanban/boards/<slug>/` to `~/.hermes/kanban/boards/_archived/<slug>-<unix_ts>/`.
  - Open tasks are preserved inside the archived dir — fully recoverable by moving the directory back.
  - Prints `archived <slug> -> _archived/<slug>-<ts>` confirmation.
- **Hard-delete path refuses if open tasks exist** (`boards rm <slug> --delete`):
  - Pre-flight `SELECT COUNT(*) FROM tasks WHERE status IN ('todo','ready','in_progress')` on the board's DB.
  - If count > 0: exit with `board '<slug>' has <N> open task(s); refusing hard delete. Archive instead (omit --delete) or close tasks first.`
  - Only after count = 0 does `rm -rf <boards/<slug>/>` execute.
- **Rationale:** Archive is recoverable so we tolerate ambiguity; hard-delete is unrecoverable so we don't.

### D-08 — LLM tool `board: Option<String>` resolution (decided this session)
- `None` flows through the same 4-tier resolver (D-02) — worker context (env set) resolves transparently; orchestrator calls without an env var get the file/default cursor.
- **Every tool response envelope (success AND rejection) includes:**
  ```json
  { "board": "<slug>", "board_source": "flag" | "env" | "file" | "default", ... }
  ```
- **Rationale:** Without `board_source`, debugging cross-board confusion in multi-orchestrator deployments becomes a guessing game. The field is cheap, always-present, and lets dashboards / logs filter by source.

### Claude's Discretion
- Exact migration step format (separate migration files vs inline match on `schema_version`) — planner picks.
- Whether `boards create --switch` mutates the cursor file inside the same atomic transaction as the board-dir creation, or post-hoc — planner picks (just be atomic enough that a crash mid-creation doesn't leave a half-created board "current").
- Internal type names (`BoardContext`, `BoardCursor`, etc.) — planner picks.
- Whether `boards list` shows the active cursor inline (e.g., `* atm10-server`) or via a separate `boards show` call — planner picks, but pick one and be consistent.

</decisions>

## Existing Code Insights

### Reusable Assets
- `KanbanStore::open_default()` (`store.rs:201`) — generalizes to `KanbanStore::open(db_path: &Path)` with `open_default()` becoming a thin wrapper. Migration logic stays inside; the file path becomes a parameter.
- `worker_spawn.rs::HERMES_KANBAN_BOARD` env wiring — already half-done. The literal `"default"` becomes the resolved board slug from the dispatcher's sweep iteration.
- Phase 36.3.7.8 `parse_mentions` + `resolve_mention` are board-naive — they receive a `ResolverCtx` with known assignees, which already comes from a specific DB connection. Multi-board just means the caller passes a different connection.
- The `validate_profile_name` invariant from Phase 36.3.7.6 + the `BEGIN IMMEDIATE` + idempotency replay pattern from 36.3.7.7 transfer directly — no per-board variation needed.

### Established Patterns
- **CLI verb shape** (`kanban/mod.rs` + `kanban/commands.rs`): clap enum variant + dispatch arm + `cmd_*` async fn. `boards` is a sub-noun so it'll need a nested clap structure (`KanbanCommands::Boards(BoardsCommands::List { ... } | BoardsCommands::Create { ... } | ...)`).
- **Deferred-subverb routing**: Phase 36.3.7.8's `DEFERRED_KANBAN_SUBVERBS` precedent (handlers.rs:1149) — `"boards"` must be added there.
- **LLM tool registration**: `register_kanban_tools` count discipline — multi-board does NOT add a new tool; it amends every existing tool's schema. The count stays 11.
- **Pure-function resolver shape**: Phase 36.3.7.8's `resolve_mention` (in-file unit tests, no IO) is the template for the new `resolve_board_context`.

### Integration Points
- Gateway dispatcher tick (`runner.rs:1281`) — change from `open_default()` once-per-tick to `for board in list_boards()` per tick.
- Gateway notifier loop (`ironhermes_kanban::run_notifier_loop`) — change from single-board polling to iterating `subscribe_boards` from `notifier.toml`.
- CLI `main.rs:303` — `--board <slug>` flag plumbing into every `cmd_*` call.
- Worker spawn env (`worker_spawn.rs:117`) — `HERMES_KANBAN_BOARD = "<resolved board slug>"` instead of literal `"default"`.
- Every existing `kanban_*` LLM tool execute() — gain `board: Option<String>` arg parsing + envelope `board_resolved` field.

<specifics>
## Specific Ideas

- **`Option::or_else` chain for 4-tier resolver** — explicit user-recommended pattern; flatter than nested branches and trivially unit-testable.
- **`notifier.toml` config file** — user-specified name and `subscribe_boards = ["*"]` default; explicit scoping codepath should ship inert in v1 with unit-test coverage so future phases that need scoping don't have to retrofit.
- **`board_resolved` + `board_source` envelope fields** — user-specified shape: `{"board": "<slug>", "board_source": "flag|env|file|default", ...}`. Always present on tool success AND rejection.
- **Stderr migration banner format** — user-specified: `[kanban] migrated board '<slug>' from v<old> to v<new>`.
- **Hard-delete pre-flight count query** — `SELECT COUNT(*) FROM tasks WHERE status IN ('todo','ready','in_progress')` (does NOT count `done` or `blocked`).
- **Slug validation regex** — `^[a-z0-9][a-z0-9_-]{0,63}$` (lowercase alnum start, alnum + `_` + `-` body, 1-64 chars). Uppercase input downcased before validation. Anything else (slashes, spaces, dots, `..`) rejected at CLI layer to block path-traversal naming.
- **Archive dir suffix** — `<slug>-<unix_ts>` (10-digit seconds) so multiple archives of the same slug don't collide.

</specifics>

<deferred>
## Deferred Ideas

- **Cross-board task links** — explicitly forbidden by docs §71; would require schema redesign and break the per-board lock isolation invariant. NOT a future phase; permanent boundary.
- **Migration of legacy `~/.hermes/kanban.db` into `boards/default/`** — never. Back-compat is permanent; users who want their default board in the new layout can `boards create new-default` and `boards switch` manually.
- **Dashboard board switcher UI** — described in docs §150-165 but lives in a later phase that touches the dashboard frontend. Slug filter must be supported by the backend API in this phase (so the dashboard can be added later without backend churn).
- **Tenant namespacing** — docs §75 mentions tenants as a soft filter inside a board. Orthogonal to this phase; future phase.
- **`notify_boards` explicit-list scoping** — codepath ships inert in v1 (only `["*"]` exercised). Future phase activates it when a real multi-profile use-case requires per-bot scoping (hermes-agent #21877 analog).
- **Per-board RBAC / auth** — single-host trust model preserved (docs §71). If multi-user comes later it's its own phase.
- **`boards migrate <slug>` manual command** — D-06 chose auto-migrate-with-banner, so the manual command isn't shipped. If users start needing it (rollback scenarios), future phase.

</deferred>
