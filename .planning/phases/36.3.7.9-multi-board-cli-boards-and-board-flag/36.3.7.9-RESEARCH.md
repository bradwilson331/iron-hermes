## Summary

Phase 36.3.7.9 extends IronHermes Kanban from a single-board system to a multi-board
system. The codebase is well-structured for this extension: `KanbanStore::new(path)` already
accepts an arbitrary path, `open_default()` is already a thin wrapper, `HERMES_KANBAN_BOARD`
env-pinning is already wired in `worker_spawn.rs` (hardcoded to `"default"`), and the
dispatcher/notifier share an `Arc<TokioMutex<KanbanStore>>` that can be replicated per board.
The primary work is (1) new `paths.rs` helpers, (2) a `resolve_board_context()` pure function,
(3) a `boards` nested clap subcommand, (4) threading `--board` through every `cmd_*` function,
(5) extending the dispatcher tick and notifier loop to iterate boards, (6) adding `board:
Option<String>` to all 11 LLM tool schemas, and (7) adding `toml` as a new dependency for
`notifier.toml` parsing. No schema DDL changes are required for Phase 36.3.7.9 itself — each
named board gets its own DB with the existing schema.

**Path root disambiguation (CRITICAL):** `docs/kanban/reference.md` uses `~/.hermes/` but the
actual codebase root is `~/.ironhermes/`. `crates/ironhermes-kanban/src/paths.rs:1-5` states
explicitly: "All paths are rooted at `ironhermes_core::get_hermes_home()` which resolves to
`$IRONHERMES_HOME` (when set) or `~/.ironhermes`." The planner MUST use `~/.ironhermes/` in
all code. Docs references to `~/.hermes/` are doc-only inaccuracies (the product was
previously named "hermes"; `get_hermes_home()` is the canonical source of truth).
[VERIFIED: crates/ironhermes-kanban/src/paths.rs:1-5]

**Tool count disambiguation:** `crates/ironhermes-kanban/src/tools/mod.rs:47` contains the
comment "Register all 11 kanban tools" and the code registers exactly 11 tools:
`KanbanShowTool`, `KanbanListTool`, `KanbanCommentTool`, `KanbanCompleteTool`,
`KanbanBlockTool`, `KanbanCreateTool`, `KanbanHeartbeatTool`, `KanbanLinkTool`,
`KanbanUnblockTool`, `KanbanSwarmTool`, `KanbanMentionTool`. Tool count = **11** (CONTEXT.md
is correct; ROADMAP.md value of 9 is stale).
[VERIFIED: crates/ironhermes-kanban/src/tools/mod.rs:47-93]

**Primary recommendation:** Implement in this order: paths.rs → resolver → schema/store open
generalization → `boards` CLI verbs → `--board` flag threading → dispatcher multi-board sweep
→ notifier multi-board → LLM tool amendments → docs/tests.

### 1. `clap` nested subcommand pattern for `boards`

**Existing pattern** (`crates/ironhermes-cli/src/kanban/mod.rs`): The `KanbanCommands` enum
uses `#[derive(Subcommand)]` with `#[command(name = "...")]` on each variant. The
`handle_kanban_command` dispatcher is a plain `match` on the enum.

The nested `boards` variant must follow this shape:
[VERIFIED: crates/ironhermes-cli/src/kanban/mod.rs:35-502]

```rust
// In KanbanCommands:
/// Manage boards (multi-project isolation)
#[command(name = "boards")]
Boards(BoardsCommands),
```

```rust
// New enum in mod.rs or boards.rs:
#[derive(Subcommand)]
pub enum BoardsCommands {
    #[command(name = "list")]
    List {
        #[arg(long)]
        json: bool,
    },
    #[command(name = "create")]
    Create {
        slug: String,
        #[arg(long)]
        name: Option<String>,
        #[arg(long)]
        description: Option<String>,
        /// Make this board current after creation
        #[arg(long = "switch")]
        switch: bool,
        #[arg(long)]
        json: bool,
    },
    #[command(name = "switch")]
    Switch {
        slug: String,
    },
    #[command(name = "show")]
    Show {
        #[arg(long)]
        json: bool,
    },
    #[command(name = "rename")]
    Rename {
        slug: String,
        new_name: String,
    },
    #[command(name = "rm")]
    Rm {
        slug: String,
        /// Hard delete (refuses if open tasks exist)
        #[arg(long)]
        delete: bool,
    },
}
```

Dispatch arm in `handle_kanban_command`:
```rust
KanbanCommands::Boards(boards_cmd) => {
    commands::cmd_boards(boards_cmd).await
}
```

Or dispatch each leaf:
```rust
KanbanCommands::Boards(boards_cmd) => match boards_cmd {
    BoardsCommands::List { json } => commands::cmd_boards_list(json).await,
    BoardsCommands::Create { slug, name, description, switch, json } =>
        commands::cmd_boards_create(slug, name, description, switch, json).await,
    // ...
}
```

The second form (individual arms) matches the precedent set for `Swarm` and `Mention`.

### 3. `KanbanStore::open(db_path)` generalization

**Current `new()` method** (`store.rs:184-199`):
[VERIFIED: crates/ironhermes-kanban/src/store.rs:184-199]

```rust
pub fn new(path: impl AsRef<Path>) -> Result<Self> {
    let path = path.as_ref();
    if let Some(parent) = path.parent() {
        std::fs::create_dir_all(parent)
            .with_context(|| format!("create kanban dir {}", parent.display()))?;
    }
    let conn = Connection::open(path)
        .with_context(|| format!("open kanban DB at {}", path.display()))?;
    conn.busy_timeout(std::time::Duration::from_millis(5000))?;
    let mut store = Self { conn };
    store.init_schema()?;
    Ok(store)
}

pub fn open_default() -> Result<Self> {
    Self::new(crate::paths::kanban_db_path())
}
```

**`init_schema()` detail** (`store.rs:210-234`):
```rust
fn init_schema(&mut self) -> Result<()> {
    self.conn.execute_batch(SCHEMA_SQL)?;
    let current: Option<i64> = self.conn
        .query_row("SELECT version FROM schema_version LIMIT 1", [], |r| r.get(0))
        .optional()?;
    match current {
        None => {
            self.conn.execute(
                "INSERT INTO schema_version (version) VALUES (?1)",
                params![SCHEMA_VERSION],
            )?;
        }
        Some(v) => {
            run_migrations(&mut self.conn, v)?;
        }
    }
    Ok(())
}
```

**Key insight:** `KanbanStore::new(path)` IS the generalized `open(db_path)`. It already
accepts any path. The planner should:
1. Add a pub alias: `pub fn open(path: impl AsRef<Path>) -> Result<Self> { Self::new(path) }`
   OR rename `new` to `open` (but `new` is already used in tests — alias is safer).
2. Keep `open_default()` as the thin wrapper that calls `Self::open(kanban_db_path())`.
3. Add `open_for_board(slug: &str) -> Result<Self>` that calls
   `Self::open(board_db_path(slug))`.

**D-06 migration banner injection point:** Inside `init_schema()`, after `run_migrations()`
returns `Ok(())` and BEFORE the outer `Ok(())`:

```rust
Some(v) if v < SCHEMA_VERSION => {
    run_migrations(&mut self.conn, v)?;
    // D-06: emit banner to stderr
    eprintln!("[kanban] migrated board '{}' from v{} to v{}",
              slug_hint.unwrap_or("default"), v, SCHEMA_VERSION);
    self.conn.execute("UPDATE schema_version SET version = ?1",
                      params![SCHEMA_VERSION])?;
}
```

The `slug_hint` requires `init_schema` to accept an optional slug (or `KanbanStore::new`
accepts `slug_hint: Option<&str>`). The planner should add a private `open_inner(path,
slug_hint)` or thread a `label: &str` through `init_schema`.

### 4. Per-board `schema_version` + auto-migrate-with-banner (D-06)

**Current SCHEMA_VERSION constant:** `SCHEMA_VERSION: i64 = 1` at
`crates/ironhermes-kanban/src/schema.rs:13`.
[VERIFIED: crates/ironhermes-kanban/src/schema.rs:13]

**Current `run_migrations()` shape** (`schema.rs:170-179`):
```rust
pub fn run_migrations(conn: &mut Connection, current: i64) -> Result<()> {
    // v1 is the baseline — no ALTER statements needed.
    let _ = current;
    let _ = conn;
    Ok(())
}
```

**Migration ladder pattern** (from the doc comment at schema.rs:162-168):
```rust
// Example for v2:
//   if current < 2 {
//       let _ = conn.execute("ALTER TABLE tasks ADD COLUMN new_col TEXT", []);
//       conn.execute("UPDATE schema_version SET version = 2", [])?;
//   }
```

**Key insight for D-06:** Since `SCHEMA_VERSION == 1` and no migrations exist yet, the
banner will only fire on fresh boards when somehow the stored version < 1, which is
impossible on first-open (the `None` arm inserts `SCHEMA_VERSION`). The banner infrastructure
must be built correctly for future migration steps. The planner should wire it so the
`Some(v) where v < SCHEMA_VERSION` arm emits the banner — this is a no-op for v1 DBs but
correct for v2+ when someone upgrades.

**`schema_version > CURRENT` handling:** The planner must add a guard:
```rust
Some(v) if v > SCHEMA_VERSION => {
    return Err(KanbanError::Other(format!(
        "board schema version {v} is newer than binary supports ({SCHEMA_VERSION}); upgrade binary"
    )));
}
```

### 5. `resolve_board_context()` pure function (D-02)

**Template: `resolve_mention()`** in `crates/ironhermes-kanban/src/mention/resolver.rs:169-206`.
The pattern is: pure fn, no IO, `Option::or_else` chain, in-file unit tests.
[VERIFIED: crates/ironhermes-kanban/src/mention/resolver.rs:169-206]

**Proposed location:** `crates/ironhermes-kanban/src/board/resolver.rs` (new module) or
inline in `crates/ironhermes-kanban/src/board.rs`.

**Proposed signature:**
```rust
/// Resolve the active board context from 4-tier precedence (D-02).
/// Pure function — reads env vars and a file path but performs NO DB I/O.
pub fn resolve_board_context(cli_flag: Option<&str>) -> Result<BoardContext> {
    let slug = cli_flag
        .map(|s| s.to_string())
        .or_else(|| std::env::var("HERMES_KANBAN_BOARD").ok())
        .or_else(|| read_current_board_file().ok().flatten())
        .unwrap_or_else(|| "default".to_string());

    let slug = validate_board_slug_input(&slug)?;
    let db_path = board_db_path_for_slug(&slug);
    let source = derive_source(cli_flag, &slug);

    Ok(BoardContext { slug, db_path, source })
}

fn read_current_board_file() -> std::io::Result<Option<String>> {
    let path = current_board_file();
    match std::fs::read_to_string(&path) {
        Ok(s) => Ok(Some(s.trim().to_string())),
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => Ok(None),
        Err(e) => Err(e),
    }
}
```

**`BoardContext` struct:**
```rust
#[derive(Debug, Clone)]
pub struct BoardContext {
    pub slug: String,
    pub db_path: PathBuf,
    pub source: BoardSource,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub enum BoardSource {
    Flag,    // --board <slug>
    Env,     // HERMES_KANBAN_BOARD
    File,    // ~/.ironhermes/kanban/current
    Default, // literal "default"
}

impl BoardSource {
    pub fn as_str(&self) -> &'static str {
        match self {
            BoardSource::Flag => "flag",
            BoardSource::Env => "env",
            BoardSource::File => "file",
            BoardSource::Default => "default",
        }
    }
}
```

**Note on `source` derivation:** When `cli_flag` is Some → `Flag`; else if
`HERMES_KANBAN_BOARD` set → `Env`; else if file exists and readable → `File`; else `Default`.
The pure function must re-check each tier to set source correctly. The `Option::or_else`
chain computes the slug; a parallel check determines the source.

**Note on `"default"` slug special-casing:** When `slug == "default"`, `db_path` must return
`kanban_db_path()` (the legacy `~/.ironhermes/kanban.db`), not `board_db_path("default")`.
This is the D-01 back-compat invariant.

**`list_boards()` helper** (needed by dispatcher, notifier, `boards list`):
```rust
/// List all board slugs on disk (named boards only; does NOT include "default").
///
/// Returns slugs by reading directory entries under `boards_root()`.
/// Skips `_archived/` and any non-directory entries.
pub fn list_boards() -> Result<Vec<String>> {
    let root = boards_root();
    if !root.exists() {
        return Ok(vec![]);
    }
    let mut slugs = Vec::new();
    for entry in std::fs::read_dir(&root)? {
        let entry = entry?;
        let name = entry.file_name().to_string_lossy().into_owned();
        if name.starts_with('_') { continue; } // skip _archived
        if entry.file_type()?.is_dir() {
            slugs.push(name);
        }
    }
    slugs.sort();
    Ok(slugs)
}
```

**`board_db_path_for_slug()` (resolver helper):**

/// Returns the correct db_path for a slug, honouring the "default" special case.

pub fn board_db_path_for_slug(slug: &str) -> PathBuf {

}

### 7. Gateway dispatcher tick multi-board sweep (runner.rs:1281-1284)

**Current code** (`crates/ironhermes-gateway/src/runner.rs:1281-1284`):
[VERIFIED: crates/ironhermes-gateway/src/runner.rs:1281-1297]

```rust
match ironhermes_kanban::KanbanStore::open_default() {
    Ok(store) => {
        let kanban_store_arc =
            std::sync::Arc::new(tokio::sync::Mutex::new(store));
        // dispatcher spawn ...
        // notifier spawn ...
    }
```

**Proposed multi-board sweep:** The `Arc<TokioMutex<KanbanStore>>` pattern must be
preserved per-board (INV-36.3.7-08-05: failing board logs + skips, others continue).

The planner should change from opening ONE store before both spawns to opening stores
INSIDE the dispatch tick. The cleanest approach is to keep the gateway-side code minimal
and push the multi-board sweep into `ironhermes-kanban`'s `run_dispatch_loop`:

Option A (preferred — minimal gateway change): Keep gateway code as-is but open a
"default" store for the Arc. Let `run_dispatch_loop` internally call `list_boards()` and
open per-board stores per tick (not Arc-cached — opened and dropped each tick). This avoids
Arc proliferation at the gateway spawn site.

Option B (Arc-per-board cache): Gateway opens one Arc per board, stores in a
`HashMap<String, Arc<...>>` before spawning. Harder to manage dynamically.

**Recommendation:** Option A. The dispatch tick already holds a `TokioMutex<KanbanStore>`
inside `DispatcherContext`. Extend `DispatcherContext` to hold either a per-board store
factory or let `run_dispatch_tick` open a per-board store internally. The key constraint
(INV-36.3.7-08-05) is: per-board `open()` failure must log + skip, not abort the tick.

**Worker env wiring:** `worker_spawn.rs:117` currently has:
[VERIFIED: crates/ironhermes-kanban/src/worker_spawn.rs:116-117]
```rust
// HERMES_KANBAN_BOARD — always "default" in v1 (D-03).
env.push(("HERMES_KANBAN_BOARD".into(), "default".into()));
```

This becomes:
```rust
// HERMES_KANBAN_BOARD — the resolved board slug for this task's board.
env.push(("HERMES_KANBAN_BOARD".into(), board_slug.to_string()));
```

`build_kanban_worker_env` must gain a `board_slug: &str` parameter. The dispatch tick
passes the slug from its per-board iteration.

**Test at worker_spawn.rs:400-412** asserts `board == "default"` — this test becomes
parameterized or a new `board_slug_propagates` test is added.

### 8. Notifier loop multi-board scope (D-03)

### 12. Slug validation regex

**`validate_profile_name` rules** (`crates/ironhermes-core/src/profile.rs:63-88`):
[VERIFIED: crates/ironhermes-core/src/profile.rs:63-88]

- Non-empty
- Length <= 64 chars
- Must NOT start with `_`
- Must NOT be a reserved word: `"default"`, `"current"`, `"none"`
- Chars: `[a-z0-9][a-z0-9-]*` (dash allowed, underscore NOT allowed, no uppercase)

**Board slug requirements differ from profile name:**
- `^[a-z0-9][a-z0-9_-]{0,63}$` — underscore IS allowed (CONTEXT.md, docs §121)
- Must NOT be `"_archived"` (reserved directory name)
- Path-traversal blockers: `/`, `..`, leading whitespace, control chars, dots

**`validate_board_slug` must be a NEW function** (NOT reuse `validate_profile_name`) because:
1. Underscore is allowed in slugs but not in profile names.
2. Reserved words differ (`_archived` is reserved for slugs; `current`/`none` are not slug-reserved).

**Proposed implementation:**
```rust
#[derive(Debug, thiserror::Error)]
pub enum BoardSlugError {
    #[error("board slug must not be empty")]
    Empty,
    #[error("board slug exceeds 64 characters")]
    TooLong,
    #[error("board slug must start with alphanumeric character")]
    BadStart,
    #[error("board slug contains invalid characters (allowed: a-z 0-9 - _)")]
    InvalidChars,
    #[error("board slug '{0}' is reserved")]
    Reserved(String),
    #[error("board slug must not contain path separators or '..'")]
    PathTraversal,
}

const RESERVED_BOARD_SLUGS: &[&str] = &["_archived"];

pub fn validate_board_slug(input: &str) -> Result<String, BoardSlugError> {
    let s = input.trim();
    // Path traversal blockers (before downcasing)
    if s.contains('/') || s.contains('\\') || s.contains("..") || s != input.trim() {
        return Err(BoardSlugError::PathTraversal);
    }
    // Downcase
    let s = s.to_lowercase();
    if s.is_empty() { return Err(BoardSlugError::Empty); }
    if s.len() > 64 { return Err(BoardSlugError::TooLong); }
    // Must start with alnum
    let first = s.chars().next().unwrap();
    if !first.is_ascii_alphanumeric() { return Err(BoardSlugError::BadStart); }
    // Body: alnum + '-' + '_' only
    if !s.chars().all(|c| c.is_ascii_alphanumeric() || c == '-' || c == '_') {
        return Err(BoardSlugError::InvalidChars);
    }
    if RESERVED_BOARD_SLUGS.contains(&s.as_str()) {
        return Err(BoardSlugError::Reserved(s));
    }
    Ok(s)
}
```

**Note on `"default"`:** `"default"` is NOT rejected by `validate_board_slug` — it is a
valid slug that maps to the legacy DB path via `board_db_path_for_slug`. The resolver uses it
as the 4th-tier fallback. The `boards create default` command should be rejected separately
with a user-friendly error ("'default' board is the built-in board; use a different slug").

### 14. `boards create --switch` atomicity

**Available fs primitives in the codebase:** `std::fs::create_dir_all` (used in
`KanbanStore::new()`), `std::fs::rename` (standard atomic rename pattern for file writes).

**Recommended pattern (Option B from CONTEXT.md):**
1. `validate_board_slug(slug)` — early reject.
2. `create_dir_all(board_dir(slug))` — create directory.
3. `KanbanStore::open(board_db_path(slug))` — init DB (calls `init_schema()` which runs DDL).
4. If `--switch`: write slug to `current_board_file()` using atomic rename:
   ```rust
   let tmp = current_board_file().with_extension("tmp");
   std::fs::write(&tmp, slug)?;
   std::fs::rename(&tmp, current_board_file())?;
   ```

**Crash semantics:** If the process crashes between steps 2-3 and before 4, the board dir
exists but is not current — harmless (the board is accessible via `--board <slug>` and
`boards switch`). If the process crashes between 3 and 4, the DB is initialized but current
file was not written — again harmless. The only unrecoverable state is a half-written
`current` file, which the atomic rename prevents.

### Anti-Patterns to Avoid

- **Hard-coding `"default"` anywhere after this phase.** Always use

## Common Pitfalls

### Pitfall 1: `"default"` slug must map to legacy DB path

**What goes wrong:** `board_db_path("default")` returns
`~/.ironhermes/kanban/boards/default/kanban.db` — this path does not exist on any
existing install. The actual default board is at `~/.ironhermes/kanban.db`.

**Why it happens:** The multi-board layout uses `boards/<slug>/` for named boards, but the
default board predates this layout.

**How to avoid:** `board_db_path_for_slug("default")` must return `kanban_db_path()` not
`board_db_path("default")`. Add an explicit special-case in the resolver and in any code that
constructs a DB path from a slug.

**Warning signs:** Tests that create `boards/default/kanban.db` and check that the default
board data is there — these would silently pass in isolation but break on real installs.

### Pitfall 2: `list_boards()` must include `"default"` for dispatcher sweep

**What goes wrong:** If `list_boards()` only returns directories under `boards_root()`, the
default board at `kanban_db_path()` is never swept by the dispatcher.

**Why it happens:** The default board has no directory under `boards/`.

**How to avoid:** The dispatcher sweep iterator must explicitly prepend `"default"` before
the `list_boards()` results. OR `list_boards()` itself can synthesize `"default"` as the
first entry. Be consistent: pick one approach and document it.

**Recommendation:** Have the dispatcher build: `let all_boards = std::iter::once("default".to_string()).chain(list_boards()?)`

### Pitfall 3: `validate_board_slug` rejects `"default"` — but shouldn't

**What goes wrong:** If `"default"` is added to `RESERVED_BOARD_SLUGS`, `boards switch
default` fails.

**Why it happens:** `"default"` is a valid board slug (the built-in one). It should not be
creatable via `boards create` but should be switchable and showable.

**How to avoid:** Keep `"default"` out of `RESERVED_BOARD_SLUGS`. Instead, reject `boards
create default` explicitly at the `cmd_boards_create` layer with a friendly message.

### Pitfall 4: `_archived` directory appears in `list_boards()` output

**What goes wrong:** `list_boards()` iterates `boards_root()` entries and returns
`"_archived"` as a board slug.

**Why it happens:** `_archived/` is a sibling directory under `boards/`.

**How to avoid:** Skip entries starting with `_` in `list_boards()` (already shown in the
proposed impl above).

### Pitfall 5: `notifier.toml` absent on existing installs

**What goes wrong:** Notifier loop errors on `read_to_string` if file is missing.

**Why it happens:** The file is not created on upgrade, only on fresh install.

**How to avoid:** Always use `unwrap_or_default()` fallback when the file is absent (ENOENT
is the expected state for any install that hasn't opted into explicit board scoping). The
`NotFound` error code should be silently treated as "use default config."

### Pitfall 6: D-06 banner fires on every open of a `SCHEMA_VERSION == 1` DB opened by a v1 binary

**What goes wrong:** The banner `[kanban] migrated board 'X' from v1 to v1` fires on every
access if the version-update logic is wrong.

**Why it happens:** The `Some(v)` arm runs `run_migrations` which in v1 is a no-op, but the
UPDATE to bump the stored version might also be missing.

**How to avoid:** Only emit the banner when `v < SCHEMA_VERSION`. The `Some(v) if v ==
SCHEMA_VERSION` case is the happy path — no banner, no update.

### Pitfall 7: `boards rename` vs slug immutability

**What goes wrong:** User expects `boards rename atm10-server new-slug` to change the slug
(and thus the directory name and DB path). The docs say slugs are immutable.

**Why it happens:** The `rename` verb in the reference doc (`reference.md:104`) renames the
display name, not the slug. The slug IS the directory name and is immutable.

**How to avoid:** `boards rename <slug> <new_display_name>` should store the display name
somewhere (either a `board.toml` metadata file inside the board dir, or a global
`boards.toml` registry). The planner must decide where display name is persisted — a
per-board `board.toml` file is the simplest.

### Pitfall 8: `boards create --switch` leaves board current if DB init fails

**What goes wrong:** Directory created, `--switch` writes `current` file, then DB open fails
(e.g., filesystem full). Now `current` points to a board with no DB.

**Why it happens:** Writing the `current` file before the DB is initialized.

**How to avoid:** Write `current` AFTER `KanbanStore::open(board_db_path(slug))` succeeds
(Option B from the atomicity section above).

// Source: pattern from crates/ironhermes-kanban/src/mention/resolver.rs:169-206
pub fn resolve_board_context(cli_flag: Option<&str>) -> Result<BoardContext, BoardSlugError> {
    let (raw_slug, source) = if let Some(f) = cli_flag {
        (f.to_string(), BoardSource::Flag)
    } else if let Ok(v) = std::env::var("HERMES_KANBAN_BOARD") {
        (v, BoardSource::Env)
    } else if let Some(v) = read_current_board_file_opt() {
        (v, BoardSource::File)
    } else {
        ("default".to_string(), BoardSource::Default)
    };

impl KanbanStore {
    /// Open (or create) a database at `path` with optional board label for migration banner.
    pub fn open(path: impl AsRef<Path>) -> Result<Self> {
        Self::new_inner(path.as_ref(), None)
    }

    /// Open with a board slug label for migration banners.
    pub fn open_labeled(path: impl AsRef<Path>, slug: &str) -> Result<Self> {
        Self::new_inner(path.as_ref(), Some(slug))
    }

    pub fn open_default() -> Result<Self> {
        Self::open(crate::paths::kanban_db_path())
    }

    pub fn open_for_board(slug: &str) -> Result<Self> {
        let path = crate::paths::board_db_path_for_slug(slug);
        Self::open_labeled(path, slug)
    }

    fn new_inner(path: &Path, slug_hint: Option<&str>) -> Result<Self> {
        if let Some(parent) = path.parent() {
            std::fs::create_dir_all(parent)?;
        }
        let conn = Connection::open(path)?;
        conn.busy_timeout(std::time::Duration::from_millis(5000))?;
        let mut store = Self { conn };
        store.init_schema(slug_hint)?;
        Ok(store)
    }
}

// Source: derived from crates/ironhermes-kanban/src/store.rs:210-234
fn init_schema(&mut self, slug_hint: Option<&str>) -> Result<()> {
    self.conn.execute_batch(SCHEMA_SQL)?;
    let current: Option<i64> = self.conn
        .query_row("SELECT version FROM schema_version LIMIT 1", [], |r| r.get(0))
        .optional()?;

    match current {
        None => {
            self.conn.execute(
                "INSERT INTO schema_version (version) VALUES (?1)",
                params![SCHEMA_VERSION],
            )?;
        }
        Some(v) if v < SCHEMA_VERSION => {
            run_migrations(&mut self.conn, v)?;
            // D-06: emit banner
            let label = slug_hint.unwrap_or("default");
            eprintln!("[kanban] migrated board '{}' from v{} to v{}", label, v, SCHEMA_VERSION);
            self.conn.execute("UPDATE schema_version SET version = ?1", params![SCHEMA_VERSION])?;
        }
        Some(v) if v > SCHEMA_VERSION => {
            return Err(KanbanError::Other(format!(
                "board schema version {} is newer than binary supports ({}); upgrade binary",
                v, SCHEMA_VERSION
            )));
        }
        Some(_) => {} // v == SCHEMA_VERSION: happy path, no-op
    }
    Ok(())
}

## Open Questions

1. **`boards rename` display name storage**
   - What we know: `boards rename atm10-server "ATM10 (Prod)"` renames the display name (slug is immutable per docs §104).
   - What's unclear: Where is the display name persisted? No `board.toml` or metadata file exists yet.
   - Recommendation: Create a `board.toml` file inside each named board's directory (`board_dir(slug)/board.toml`) with `name`, `description`, `icon` fields. For the `"default"` board, the display name is always `"default"` (no metadata file). This is a one-file addition per named board.

2. **Dispatcher Arc-per-board vs per-tick open**
   - What we know: The gateway currently hoists a single `Arc<TokioMutex<KanbanStore>>` before spawning both the dispatcher AND notifier. Multi-board needs multiple stores.
   - What's unclear: Whether the existing `DispatcherContext` struct should be refactored to hold a board-store factory, or whether the gateway-side code should iterate boards before spawning.
   - Recommendation: Keep the gateway change minimal — let the dispatcher internally handle multi-board iteration. This avoids touching `runner.rs` beyond the existing `open_default()` call.

3. **Per-board watermark for notifier**
   - What we know: `NotifierContext` holds a single `Arc<AtomicI64>` watermark. Multi-board requires per-board watermarks.
   - What's unclear: Whether to change `NotifierContext` to hold a `HashMap<String, Arc<AtomicI64>>` or to instantiate one `NotifierContext` per board.
   - Recommendation: One `NotifierContext` with a `HashMap<String, Arc<AtomicI64>>` indexed by slug. Simpler than spawning N notifier tasks.
