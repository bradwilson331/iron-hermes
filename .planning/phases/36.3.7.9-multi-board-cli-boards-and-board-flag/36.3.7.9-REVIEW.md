# Phase 36.3.7.9: Code Review Report

**Reviewed:** 2026-05-31
**Depth:** standard
**Files Reviewed:** 46
**Status:** issues_found

## Summary

Phase 36.3.7.9 introduces the multi-board CLI surface (`hermes kanban boards <verb>`), the parent-level `--board <slug>` flag, multi-board notifier/dispatcher iteration, and D-08 board-envelope injection into all 11 LLM tools. The overall architecture is solid — the 4-tier resolver, slug validator, path helpers, and `open_for_board` chain are coherently designed and well-tested.

Four critical defects were found:

1. **T-1 bypass via the `--board` flag** — the raw slug from `--board <slug>` is passed directly to `KanbanStore::open_for_board` without calling `validate_board_slug` first. `open_for_board` calls `board_db_path_for_slug` which calls `board_dir` which calls `boards_root().join(slug)` — `PathBuf::join` with an attacker-controlled segment containing `..` or `/` can escape the boards root. The resolver's slug validation fires correctly when the resolver is invoked (tier-2/3/4 paths), but the `open_store_for_board(Some(slug))` fast path in `commands.rs` skips the resolver entirely and calls `open_for_board(slug)` directly.

2. **Hand-rolled TOML parser silently mis-reads values** — `read_board_display_name` and `read_board_description` use `line.strip_prefix("name")` / `line.strip_prefix("description")`. This substring prefix matches lines like `name_field = "x"` or `description_long = "y"` and returns the wrong value. It also does not unescape the `\"` and `\\` sequences that `write_board_toml` writes, so a name containing a backslash or double-quote is stored correctly but read back corrupted.

3. **Lock file not cleaned up on `remove_dir_all` failure** — in `cmd_boards_rm`, the `kanban.db.rm-lock` file is manually cleaned up only in the `count > 0` early-return branch. If `remove_dir_all` fails (I/O error, permission denied) the lock file is NOT removed, leaving a stale lock that permanently blocks all future `--delete` attempts on that board until an operator manually removes it.

4. **`init_schema` uses raw `BEGIN`/`COMMIT`/`ROLLBACK` strings instead of rusqlite transactions** — `store.rs::init_schema` calls `self.conn.execute("BEGIN", [])` rather than `self.conn.transaction()`. If `execute_batch(SCHEMA_SQL)` or a prior statement leaves an implicit transaction open (e.g., WAL-mode autocommit boundary), the explicit `BEGIN` will silently succeed but commit scope is ambiguous. Idiomatic rusqlite wraps mutations with `conn.transaction()` which is RAII-safe and cannot be left dangling.

## Critical Issues

### CR-01: T-1 Path-Traversal via Raw `--board` Slug (CLI Fast Path Skips Validator)

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:38-45`

**Issue:** `open_store_for_board(board: Option<&str>)` branches on `Some(slug)` by calling `KanbanStore::open_for_board(slug)` directly. `open_for_board` resolves the path via `board_db_path_for_slug(slug)` → `board_dir(slug)` → `boards_root().join(slug)`. Rust's `PathBuf::join` does NOT prevent path traversal: `join("../other")` escapes the boards root. A user who passes `hermes kanban --board ../etc/passwd list` would attempt to open `/home/user/.ironhermes/kanban/boards/../etc/passwd` as a SQLite database. While SQLite will reject non-SQLite bytes and return an error, it still causes an unexpected open-attempt on an arbitrary filesystem path.

The T-1 mitigation (`validate_board_slug`) is correctly applied in `boards.rs` for every `boards <verb>` command, and in `resolver.rs` for the env/file tier. But the `--board` CLI flag value is never validated before being forwarded to `open_for_board`.

**Fix:**
```rust
// commands.rs open_store_for_board — validate before open
pub fn open_store_for_board(board: Option<&str>) -> Result<KanbanStore> {
    match board {
        Some(raw_slug) => {
            // T-1: validate slug at CLI boundary before constructing any path.
            let slug = ironhermes_kanban::board::validate_board_slug(raw_slug)
                .map_err(|e| anyhow::anyhow!("invalid --board slug: {}", e))?;
            KanbanStore::open_for_board(&slug).context("Failed to open board DB")
        }
        None => {
            let ctx = ironhermes_kanban::board::resolve_board_context(None)
                .context("Failed to resolve board context")?;
            KanbanStore::open(&ctx.db_path).context("Failed to open kanban DB")
        }
    }
}
```

### CR-02: Hand-Rolled TOML Parser Matches Wrong Keys and Misreads Escaped Values

**File:** `crates/ironhermes-cli/src/kanban/boards.rs:424-429` and `boards.rs:439-443`

**Issue (a) — prefix false-match:** `line.strip_prefix("name")` returns `Some(rest)` for any line whose key starts with the string `"name"`, including `name_alt = "x"`, `names = "y"`, `namespace = "z"`. The function then reads the value from these unrelated keys and returns it as the board's display name.

**Issue (b) — missing unescape:** `write_board_toml` escapes `\"` as `\\\"` and `\\` as `\\\\` before writing. `read_board_display_name` calls `rest.trim_matches('"')` which strips only the outer quote characters but does NOT unescape `\\\"` → `"` or `\\\\` → `\\`. A board named `My "Project"` is written as `name = "My \"Project\""` and read back as `My \"Project\"`.

**Issue (c) — wrong key matching order:** The parser scans for `name` before scanning for `description`. A TOML file with `description = "x"\nname = "y"` is handled correctly. But a file with `name = "y"\ndescription = "x"` is also handled correctly because each function only looks for its own key — however, since both parsers scan the same file line-by-line, a file with `named = "misleading"` would match `name` and return `"d = "misleading"` (after stripping the prefix `"name"` and then stripping quotes) which is garbage.

**Fix:** Replace the hand-rolled parser with the `toml` crate already present in `Cargo.toml` (added in Phase 36.3.7.9 Plan 05 for `notifier_config.rs`):

```rust
#[derive(serde::Deserialize)]
struct BoardToml {
    name: Option<String>,
    description: Option<String>,
}

fn read_board_toml(path: &std::path::Path) -> Option<BoardToml> {
    let s = std::fs::read_to_string(path).ok()?;
    toml::from_str(&s).ok()
}

fn read_board_display_name(slug: &str) -> Option<String> {
    if slug == "default" { return None; }
    let path = paths::board_dir(slug).join("board.toml");
    read_board_toml(&path)?.name
}

fn read_board_description(dir: &std::path::Path) -> Option<String> {
    read_board_toml(&dir.join("board.toml"))?.description
}
```

`write_board_toml` should also be updated to use `toml::to_string` rather than manual format strings, or at minimum use `serde_json::to_string` for the value portion to guarantee correct escaping.

### CR-03: Lock File Not Cleaned Up After `remove_dir_all` Failure

**File:** `crates/ironhermes-cli/src/kanban/boards.rs:306-350`

**Issue:** The `kanban.db.rm-lock` file is cleaned up in the `count > 0` early-exit branch (line 338-339). However, if `std::fs::remove_dir_all(&board_path)` on line 348 returns an `Err`, the function returns early via the `with_context` chain and the lock file inside `board_path` is left on disk. The `_lock_file` binding is dropped (file handle closed) but `remove_file(&lock_path)` is never called. The lock file exists at `<board_path>/kanban.db.rm-lock` — since `board_path` still exists (the `remove_dir_all` failed), the stale lock will block every subsequent `--delete` attempt with "another rm in progress".

```
boards/
  alpha/
    kanban.db
    kanban.db.rm-lock   ← stale after remove_dir_all failure; never cleaned up
```

**Fix:** Use a RAII guard or wrap the removal in a closure that cleans up the lock file unconditionally:

```rust
// After the lock is acquired, ensure cleanup on all exit paths:
struct LockGuard { path: std::path::PathBuf }
impl Drop for LockGuard {
    fn drop(&mut self) { let _ = std::fs::remove_file(&self.path); }
}
let _lock_guard = LockGuard { path: lock_path.clone() };
let _lock_file = /* ... open the file ... */;

// Now remove_dir_all: even if it fails, _lock_guard.drop() removes the lock.
std::fs::remove_dir_all(&board_path)
    .with_context(|| format!("delete board dir {}", board_path.display()))?;
```

### CR-04: `init_schema` Uses Raw SQL Strings for Transaction Control Instead of rusqlite RAII Transactions

**File:** `crates/ironhermes-kanban/src/store.rs:281-300`

**Issue:** The migration path calls `self.conn.execute("BEGIN", [])` followed by `self.conn.execute("COMMIT", [])` or `self.conn.execute("ROLLBACK", [])`. This is brittle for two reasons:

1. In WAL mode with `PRAGMA journal_mode=WAL`, SQLite autocommit is active by default. If `execute_batch(SCHEMA_SQL)` (which runs on line 260, *before* the `BEGIN`) has already committed DDL statements, the `BEGIN` starts a new transaction that wraps only the `run_migrations` + `UPDATE` steps. This is actually the intended behavior, but the code comment says "Wrap run_migrations + UPDATE in BEGIN/COMMIT" (T-4) without acknowledging that the DDL above runs outside this transaction boundary.

2. If `self.conn.execute("COMMIT", [])` panics or the process is killed between `run_migrations` completing and `COMMIT` executing, the ROLLBACK path is never reached. rusqlite's `Connection::transaction()` handles this correctly via RAII: the transaction is automatically rolled back when the `Transaction` object is dropped without an explicit `commit()`.

**Fix:** Replace the explicit `BEGIN`/`COMMIT`/`ROLLBACK` strings with a rusqlite `savepoint` or `transaction`:

```rust
let tx = self.conn.transaction()?;
run_migrations(tx.deref_mut(), v)?;
let banner = Self::format_migration_banner(slug_hint, v, SCHEMA_VERSION);
eprintln!("{}", banner);
tx.execute("UPDATE schema_version SET version = ?1", params![SCHEMA_VERSION])?;
tx.commit()?;
```

### WR-01: `cmd_boards_rm` Archive Path Susceptible to TOCTOU — Symlink Check Does Not Cover Archive Destination

**File:** `crates/ironhermes-cli/src/kanban/boards.rs:283-366`

**Issue:** The T-6 symlink check at line 283 calls `symlink_metadata(&board_path)` and refuses to operate if the *source* is a symlink. However, `archive_dir()` (the destination parent) and the archive destination path `dest` are not checked for symlinks. If an attacker can create `~/.ironhermes/kanban/boards/_archived` as a symlink to `/etc/`, then `std::fs::rename(&board_path, &dest)` would place the archived board directory into `/etc/`. This is lower severity since it requires pre-existing write access to the kanban directory, but it violates the stated T-6 intent.

**Fix:** Check `archive_dir()` for symlink components before performing the rename:
```rust
let archive = paths::archive_dir();
// T-6 extension: refuse if archive_dir itself is a symlink
if let Ok(m) = std::fs::symlink_metadata(&archive) {
    if m.file_type().is_symlink() {
        eprintln!("refusing: archive directory is a symlink");
        return Ok(1);
    }
}
```

### WR-02: `read_board_display_name` Called with Unvalidated Slugs from `list_boards()`

**File:** `crates/ironhermes-cli/src/kanban/boards.rs:88-119`

**Issue:** `cmd_boards_list` calls `paths::list_boards()` which returns raw directory names from disk without calling `validate_board_slug`. The returned slugs are then passed to `read_board_display_name(slug)` which calls `paths::board_dir(slug).join("board.toml")` → `boards_root().join(slug)`. If a directory name on disk somehow contains `..` or `/` (e.g., placed there by a concurrent process or external tool), path traversal can occur inside `read_board_display_name`.

`list_boards()` does filter for entries starting with `_`, but it does not run `validate_board_slug` on each name. This is a defense-in-depth gap.

**Fix:** Validate slugs from `list_boards()` before using them as path components, or add validation inside `list_boards()` itself:
```rust
// In list_boards() after collecting the name:
if validate_board_slug(&name).is_err() {
    tracing::warn!("boards: skipping directory with invalid slug name: {:?}", name);
    continue;
}
slugs.push(name);
```

### WR-03: `cmd_boards_switch` Accepts a Directory That Exists But Is Not a Board (No DB Existence Check)

**File:** `crates/ironhermes-cli/src/kanban/boards.rs:189-209`

**Issue:** `cmd_boards_switch` checks `dir.exists()` (line 195-202) to verify the board exists before writing the `current` file. However, `dir.exists()` only checks that the directory path exists — it does NOT verify that a valid `kanban.db` exists inside it. An operator could create a bare directory `~/.ironhermes/kanban/boards/broken/` without a database file, then `boards switch broken` would succeed and all subsequent kanban operations would fail to open the board with a confusing error.

**Fix:** Check that the DB file also exists:
```rust
let db_path = paths::board_db_path(&validated_slug);
if !dir.exists() || !db_path.exists() {
    eprintln!(
        "board '{}' does not exist or has no database; create it with `boards create`",
        validated_slug
    );
    return Ok(1);
}
```

### WR-04: `reject_with_board` Manual JSON Construction Is Fragile — `reason` Field Not Sanitized

**File:** `crates/ironhermes-kanban/src/tools/common.rs:100-112`

**Issue:** `reject_with_board` sanitizes only the `detail` parameter (backslash + quote escaping), but the `reason` parameter is interpolated directly into the format string without any sanitization. While `reason` is caller-controlled (never directly from user input), future callers could pass a dynamically-built reason string that contains double-quotes or backslashes, producing malformed JSON. The test at line 208 uses `r#"path\to\"file""#` only for `detail`, not `reason`.

The broader concern is that the entire `reject_with_board` function builds JSON via `format!()` rather than via `serde_json::json!()`. The `detail` escaping is correct but incomplete — it does not handle newlines (`\n`), carriage returns (`\r`), tab characters (`\t`), or Unicode control characters, all of which produce invalid JSON.

**Fix:** Use `serde_json::json!()` and serialize properly:
```rust
pub fn reject_with_board(reason: &str, detail: &str, ctx: Option<&BoardContext>) -> String {
    let mut obj = serde_json::json!({
        "status": "rejected",
        "reason": reason,
        "detail": detail,
    });
    if let (Some(c), Some(map)) = (ctx, obj.as_object_mut()) {
        map.insert("board".into(), json!(c.slug));
        map.insert("board_source".into(), json!(c.source.as_str()));
    }
    serde_json::to_string(&obj).unwrap_or_else(|_| r#"{"status":"rejected","reason":"serialization_error"}"#.into())
}
```

### WR-05: `resolver.rs::read_current_board_file_opt` Silently Swallows All IO Errors Including Permission Denied

**File:** `crates/ironhermes-kanban/src/board/resolver.rs:62-68`

**Issue:** `read_current_board_file_opt` catches all `Err(_)` variants with a single wildcard arm and falls through to the next tier. The comment says "NotFound silenced; other IO errors also fall through". This means a `PermissionDenied` error on the `current` file (e.g., accidentally `chmod 000` by a user) is silently ignored and the resolver falls through to the `default` tier. The user would be confused when `hermes kanban list` shows the default board's tasks despite having configured a different board via the `current` file.

**Fix:** Distinguish `NotFound` from other errors and log a warning for unexpected IO errors:
```rust
fn read_current_board_file_opt() -> Option<String> {
    match std::fs::read_to_string(crate::paths::current_board_file()) {
        Ok(s) => {
            let t = s.trim().to_string();
            if t.is_empty() { None } else { Some(t) }
        }
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => None,
        Err(e) => {
            tracing::warn!("kanban: failed to read current-board file: {e}; falling through to default");
            None
        }
    }
}
```

### IN-01: `std::mem::forget(dir)` in Test Helpers Causes Tempdir Leak in Every Tool Test

**Files:** `crates/ironhermes-kanban/src/tools/list.rs:164`, `show.rs:263`, `complete.rs:217`, and 9 other tool test `make_store()` helpers

**Issue:** The `make_store()` helper in each tool's `#[cfg(test)]` block calls `std::mem::forget(dir)` to prevent the `TempDir` from being deleted after the store is opened. This is intentional because the store holds an open file handle to the database file. However, this means the temp directory is never cleaned up — on each test run it leaves orphaned directories under the OS temp directory. Over many CI runs these accumulate.

**Fix:** Either pass the `TempDir` as a return value alongside the store (so the test body holds it alive for the duration of the test and it is cleaned up on test completion), or use a `Arc<TempDir>` in the store struct. The pattern used in `boards_lifecycle.rs`'s `ScopedHome` is the idiomatic approach.

### IN-02: `sql_no_slug_literals.rs` Grep Heuristic Has a Known False-Negative Window

**File:** `crates/ironhermes-kanban/tests/sql_no_slug_literals.rs:56-66`

**Issue:** The test searches for the pattern `format!\([^)]*WHERE` — a regex that matches `format!(` and `WHERE` within the same argument span. The limitation comment in the test correctly notes that multi-line `format!(...)` calls are not caught. More concretely, the regex `[^)]*` is greedy and stops at the first `)` character — a `format!(` call whose SQL contains `()` (e.g., `format!("WHERE id IN (?) AND slug = {slug}")`) would not be matched because the `[^)]*` stops at the `(` match character. The audit would silently pass for this injection pattern.

**Fix:** Document the false-negative in the test or upgrade the heuristic to use `ripgrep`'s multiline mode or a more robust pattern that handles parentheses inside the format argument.

### IN-03: `cmd_boards_list` Synthesizes `"default"` Without Verifying Its DB Exists

**File:** `crates/ironhermes-cli/src/kanban/boards.rs:91`

**Issue:** `all` is unconditionally initialized with `vec!["default".to_string()]` before listing named boards. The default board is always shown as present regardless of whether `~/.ironhermes/kanban.db` exists. On a fresh install where only named boards have been used, `boards list` shows `"default"` as if it were an active board even though no tasks have ever been written to it and the DB file does not exist. This is cosmetically misleading and could confuse operators who check the list output to determine which boards are initialized.

This is an intentional design choice (D-01 back-compat), but the discrepancy between "listed" and "initialized" is worth documenting in the list output or the command help text. No code change required if this is intentional, but a note in the output (e.g., `  default (not yet initialized)`) would improve UX.
