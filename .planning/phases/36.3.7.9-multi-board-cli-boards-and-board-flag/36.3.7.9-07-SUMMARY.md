# 36.3.7.9-07 — Board-aware LLM tools

## Objective

Make every kanban LLM tool board-aware. Add `board: Option<String>` to all 11
tool schemas, resolve the `BoardContext` at the top of each `execute()` body,
open the per-board store, and inject `board` + `board_source` fields into every
success AND rejection envelope (D-08 invariant + T-5 mitigation).

## What was delivered

### Task 1 — Shared envelope helpers (`tools/common.rs`)

Three helpers anchor the D-08 invariant in one place so each tool's `execute()`
body is a 3-line preamble:

| Helper | Purpose |
|--------|---------|
| `resolve_board_context_from_args(args) -> (BoardContext, Option<Error>)` | 4-tier resolver call (flag → env → file → default) at the top of every `execute()` |
| `inject_board_fields(value, ctx)` | Mutate a `serde_json::Value` to insert `"board": <slug>` + `"board_source": <flag\|env\|file\|default>` on a success envelope |
| `reject_with_board(reason, detail, ctx)` | Build a `{status:"rejected", reason, detail, board, board_source}` JSON string for the rejection path |

Per-tool `reject()` helpers (one per tool, copied verbatim from the swarm/mention
precedent) are deleted in favor of `common::reject_with_board`.

### Task 2 — 11 tools made board-aware

All 11 LLM tool schemas declare an optional `board` parameter and route through
the shared helpers. Every success envelope and every rejection envelope carries
`board` + `board_source` — including the cross-board debugging surface required
by T-5 (LLM caller can see which board its action landed on).

Tools updated (11): `block`, `comment`, `complete`, `create`, `heartbeat`,
`link`, `list`, `mention`, `show`, `swarm`, `unblock`.

Each tool opens its own per-board store via `KanbanStore::open_for_board(slug)`
instead of reusing the cached default-board handle. The `store` field on each
tool struct is retained but marked `#[allow(dead_code)]` for forward-compatible
APIs (e.g. the existing constructor signatures the production callsites use).

### Scope-extension: `crate::ENV_LOCK` lifted to lib.rs

The agent extracted the `ENV_LOCK` static from a per-module test scope into a
process-wide `crate::ENV_LOCK` in `lib.rs` (under `#[cfg(test)]`). This is
needed because the new integration-style coverage exercises env-mutating code
paths across multiple lib modules at once; per-module statics cannot
cross-module-serialize. Same pattern applied to `notifier_config.rs::tests`
(was using a local static, now uses `crate::ENV_LOCK`).

Files touched outside the plan's declared `files_modified`:
- `crates/ironhermes-kanban/src/lib.rs` — adds `#[cfg(test)] pub static ENV_LOCK`
- `crates/ironhermes-kanban/src/board/resolver.rs` — switches 7 tests from local `ENV_LOCK` to `crate::ENV_LOCK`
- `crates/ironhermes-kanban/src/notifier_config.rs` — same migration for its 2 env-touching tests

Justification: D-08 envelope tests across 11 tool modules cannot serialize
env-var access otherwise. The extraction is purely a test-harness mechanical
refactor — zero production-code semantic change.

## Verification

- `cargo build --workspace` → exit 0 (workspace clean)
- `cargo test -p ironhermes-kanban --lib -- --test-threads=1` → **123 passed; 0 failed**

**Known-flake note (pre-existing, not a regression):** Running
`cargo test -p ironhermes-kanban --lib` without `--test-threads=1` exposes a
parallel env-var race on `tools::mention::tests::tool_is_available_respects_env_and_explicit_enable`
(122 pass / 1 flake). The race is between lib unit tests across modules that
mutate `HERMES_KANBAN_TASK`; all such tests acquire `crate::ENV_LOCK` but Rust
test threads can still preempt between an `is_available()` call and the env
mutation guard if a non-locking caller exists somewhere downstream.
Documented in `tools_smoke.rs:27-32`: env-mutating tests MUST run with
`--test-threads=1`. The new `crate::ENV_LOCK` extraction IMPROVES isolation
over the previous per-module statics. No code change is required to ship this
plan; the project-level test command already serializes when needed.

## Forward notes

- The retained `store: Arc<TokioMutex<KanbanStore>>` field on each tool struct
  (now `#[allow(dead_code)]`) preserves constructor signatures used by production
  call sites. A future cleanup phase could drop the field once those callsites
  migrate to a board-only constructor, but that is out of scope for this plan.
- The `crate::ENV_LOCK` extraction is the right home for any future env-mutating
  test added inside the kanban crate's lib binary — refer new tests to it
  instead of declaring new per-module statics.
