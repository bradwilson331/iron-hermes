# Phase 36.17.1: in-mem FIFO queuing parity of python deque for chat sessions - Context

**Gathered:** 2026-05-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Port hermes-agent's per-session `/queue` FIFO mechanism (`gateway/run.py` §2304-2415) into IronHermes so that messages arriving while a per-session agent is busy are queued in arrival order and replayed one full agent turn per queued item, with **no merging**. Ships end-to-end on Telegram only: the queue data structure, gateway wiring on `GatewayRunner`, the user-facing `/queue` slash command, busy-agent interrupt detection, `/new` + `/reset` clearing hooks, and queue-during-drain preservation across gateway restart.

Despite the phase title's "python deque" wording, the canonical Python source uses `dict[session_key, list[MessageEvent]]` plus a single-slot `adapter._pending_messages` dict — not `collections.deque`. Behavior parity is the strict FIFO contract; implementation parity (split slot + overflow) is reproduced only as a `#[cfg(test)]`-scoped reference implementation for property-based equivalence verification.

</domain>

<decisions>
## Implementation Decisions

### Phase Scope

- **D-01:** Full `/queue` feature parity, not just a data structure. Phase ships: (a) the queue type, (b) `GatewayRunner` integration, (c) `/queue` slash command, (d) busy-agent interrupt/queue detection, (e) `/new` and `/reset` clearing hooks, (f) queue-during-drain mode.
- **D-02:** Telegram is the only wired platform in this phase. Discord, Slack, and `iron_hermes_ui` web wiring are **deferred to separate follow-up phases** (one per platform).
- **D-03:** Queue-during-drain mode is IN — when the gateway is restarting (`_busy_input_mode ∈ {"queue", "steer"}`), incoming events are preserved in the per-session queue so the newly-spawned gateway process can pick them up.
- **D-04:** Goal-continuation distinction is OUT. Porting `_is_goal_continuation_event` + `_clear_goal_pending_continuations` requires `/goal` to exist; `/goal` is **not yet in IronHermes** (only one match in `crates/ironhermes-agent/src/subagent_runner.rs`, unrelated; parity-planning §line 320 lists `/goal` as future). The selective-clear predicate ships with the future `/goal` phase.
- **D-05:** Photo-burst slot-collision logic is OUT. The Python design's slot-sharing was forced by `adapter._pending_messages` doing double-duty for photo-burst follow-ups; IronHermes has no photo-burst flow yet, so the Rust port does not need to mirror this constraint.

### Queue Shape

- **D-06:** Production data structure is a single contiguous FIFO per session:
  ```rust
  pub struct SessionQueue {
      queues: Mutex<HashMap<SessionKey, VecDeque<MessageEvent>>>,
  }
  ```
  Lives on `GatewayRunner`. O(1) `push_back` / `pop_front`.
- **D-07:** Parity is **provable, not load-bearing**. A `#[cfg(test)]`-only module defines a `SessionFifoQueue` trait and a `SplitSlotQueue` reference implementation that mirrors Python's `pending_slot` + `overflow_list` layout byte-for-byte. A `proptest` suite verifies that `SessionQueue` and `SplitSlotQueue` produce identical observable behavior under arbitrary `push`/`pop`/`retain`/`clear` sequences. The trait, the mirror impl, and the proptest suite are **strictly excluded from release builds** via `#[cfg(test)]` — zero runtime cost.
- **D-08:** Public API uses idiomatic Rust verbs, not Python-mirror names. The `SessionQueue` surface is:
  - `try_push(&self, session_key: &SessionKey, event: MessageEvent) -> Result<(), QueueError>`
  - `pop(&self, session_key: &SessionKey) -> Option<MessageEvent>`
  - `len(&self, session_key: &SessionKey) -> usize`
  - `clear(&self, session_key: &SessionKey)`
  - `retain(&self, session_key: &SessionKey, predicate: impl Fn(&MessageEvent) -> bool)`

  Rustdoc on each method cites the Python equivalent (`# Python parity: _enqueue_fifo (gateway/run.py:2315)`).

### Bounding + Eviction

- **D-09:** Bounded **per-session**, not global. `const MAX_QUEUE_DEPTH: usize = 128;`. Global-cap rejected: a single shared `AtomicUsize`/`Mutex` would force every per-session push to contend on global state, killing the per-session isolation that's the whole point of `Mutex<HashMap<…>>`.
- **D-10:** Overflow policy is **drop-newest + reject**, NOT drop-oldest. Rationale: the oldest queued message is what the agent is about to act on next; dropping it breaks causal order. Dropping the newest is also what HTTP backpressure expects — the producer keeps retrying with fresh attempts.
- **D-11:** Soft warning at **75% capacity** (96 messages) via `tracing::warn!` with session key and depth. Hard cap at 128 → `try_push` returns `Err(QueueError::CapacityReached)`.
- **D-12:** HTTP-arrival platforms (future webhook adapter from 36.7.1, future Discord/Slack /queue phases) respond to `Err(QueueError::CapacityReached)` with **HTTP 429 + `Retry-After: 5`** at the network edge. The dropped payload never enters core domain logic — backpressure becomes the caller's problem (well-behaved clients like Stripe and Discord honor `Retry-After` automatically). Telegram long-poll has no HTTP caller to respond to; see D-13.
- **D-13:** Telegram cap-hit UX: emit `❌` reaction on the dropped message via the existing `PlatformAdapter::add_reaction`, then send a short chat reply: `⏳ Queue is full (128 messages). Wait for the agent to drain before sending more.` After UX feedback, ack the Telegram `getUpdates` offset (we cannot skip the offset advance) and emit a structured `tracing::warn!`.

### Concurrency + Ownership

- **D-14:** `SessionQueue` lives as a private field on `GatewayRunner`. Lifecycle is bound to the runner. Mirrors Python's `self._queued_events` placement on `GatewayRunner`.
- **D-15:** Adapters access the queue via a **thin public API on `GatewayRunner`** — `runner.try_enqueue(session_key, event)`, `runner.dequeue(session_key)`, `runner.queue_len(session_key)`, etc. The raw `SessionQueue` type is **not** publicly exported. Shared access is via `Arc<GatewayRunner>` (existing pattern).
- **D-16:** Locking strategy is a single `Mutex<HashMap<SessionKey, VecDeque<MessageEvent>>>` (use `parking_lot::Mutex` if the rest of `ironhermes-gateway` already does — otherwise `std::sync::Mutex`). Critical sections are O(1) and microseconds; chat-message arrival rates (handful per second at most) do not warrant `DashMap` or `RwLock` complexity.
- **D-17:** All `SessionQueue` methods are **synchronous**. No `.await` inside critical sections. Therefore `std::sync::Mutex` (or `parking_lot::Mutex`) is sufficient — `tokio::sync::Mutex` is NOT required.

### Claude's Discretion

- `std::sync::Mutex` vs `parking_lot::Mutex` — pick whichever the rest of `ironhermes-gateway` already uses; performance parity at this scale.
- Exact `QueueError` enum variants beyond `CapacityReached`.
- Exact wording of the Telegram "queue full" chat reply (the version in D-13 is a suggested string).
- Whether to expose queue depth via the existing `/status` slash command — useful but not required to satisfy this phase's scope.
- Test-fixture shape for proptest (`Arbitrary` impl on `MessageEvent`, or a custom strategy).
- Whether `try_push` accepts `&SessionKey` or `SessionKey` (clone vs move) — pick the ergonomics that match existing `GatewayRunner` methods.
- Internal organization: one file (`session_queue.rs`) vs split (`session_queue/mod.rs` + `session_queue/parity_tests.rs`) — pick whatever matches existing crate style.

</decisions>

- `MessageEvent` derives `Clone` (verify during planning) — required for the queue to own a copy without taking the original out of the adapter pipeline.

<specifics>
## Specific Ideas

- **128-message hard cap** (D-09) — the user explicitly picked 128 over 256 to compartmentalize blast radius without over-provisioning. Lockable via a future config knob, not in this phase.
- **75% soft-warning threshold** (D-11) — the user explicitly named the threshold as visible-but-not-yet-rejecting territory.
- **Drop-newest, never drop-oldest** (D-10) — the user's reasoning was *causal preservation*: the oldest messages are the immediate sequential context the agent is about to act on; dropping them would break the agent's expected next-turn input.
- **HTTP 429 + Retry-After: 5** (D-12) — the user's reasoning was *shifting state-management burden to the caller*. Stripe and Discord webhooks both respect `Retry-After`; relying on this avoids the gateway buffering unbounded state.
- **`#[cfg(test)]`-isolated parity mirror** (D-07) — the user's reasoning was *zero-cost provable parity*: get the proptest assurance without runtime trait dispatch or dynamic indirection in the production binary.
- **Python source uses `dict[str, list]`, not `collections.deque`** — the phase title's "python deque" framing is loose. Behavior parity (FIFO) is the contract; implementation parity is verified-but-not-shipped.

</specifics>
