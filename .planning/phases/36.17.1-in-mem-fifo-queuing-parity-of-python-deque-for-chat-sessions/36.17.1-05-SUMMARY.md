# Phase 36.17.1 Plan 05: Telegram end-to-end verification + UAT runbook

## One-liner

Three new end-to-end integration tests prove the Telegram-specific paths
(busy enqueue silent, cap-hit ❌ + chat-reply UX, post-turn drain via the
real `runner.drain_pending` in FIFO arrival order). A new manual UAT
runbook documents 4 live-Telegram scenarios — including Plan 04's
`is_draining` drain-mode flag — with an explicit cross-process out-of-scope
marker.

## Objective

Lock the Telegram-only ship requirement (D-02) end-to-end. Plans 02-04
shipped the SessionQueue + handler wiring + /queue intercept + /new
clearing + drain-mode flag with their own targeted tests; this plan
verifies they compose correctly on the only platform wired in this phase
and produces the runbook the user must execute on a live Telegram bot
before sign-off.

## Tasks completed

### Task 1 — Three new end-to-end Telegram-flow integration tests

**File modified:**

- `crates/ironhermes-gateway/tests/session_queue_integration.rs` (+362
  lines). The new tests are appended at the bottom of the file under a
  `Plan 05 Task 1 — Telegram end-to-end flow tests` section header.

**Tests added (and what each asserts):**

| Test | Asserts |
| --- | --- |
| `test_telegram_busy_path_enqueues` | Telegram `MessageEvent` (platform=Telegram, chat_id="test_chat", sender_id="test_user") arriving via `MessageHandler::handle` while `agent_running=true` enqueues onto SessionQueue (depth 1). The handler's busy-branch records **zero** `send_message` and **zero** `add_reaction` calls (D-13: free-text enqueue is silent; UserQueueManager's transport-layer 👁 is a separate layer not exercised at handler scope). |
| `test_telegram_cap_hit_full_ux` | Pre-fill SessionQueue to MAX_QUEUE_DEPTH (128) with `msg_001..msg_128`. Dispatch a 129th Telegram event with `message_id="msg_id_129"`. Asserts: queue depth still 128 (T-36.17.1-01 cap held); exactly one `add_reaction` with emoji `❌`, chat_id `test_chat`, message_id `msg_id_129` (drop-newest, D-13); exactly one chat reply containing the D-13 literal `"Queue is full (128 messages)"`. Includes a Pitfall 6 documentation comment block referencing `runner.rs:723-736` and the UAT runbook for the offset-advance live check. |
| `test_telegram_post_turn_drain_in_arrival_order` | Build a `GatewayRunner`, enqueue 3 Telegram events with content `"A","B","C"` via `runner.try_enqueue`, release the busy flag, invoke `runner.drain_pending(&key, &handler, adapter_dyn, cancel)` **directly** (NOT a hand-rolled pop loop — the planner is explicit). Asserts queue depth went 3→0 and the recording adapter saw exactly 3 placeholder `█` send_message calls (one per drained `run_agent` invocation, no merging — D-01 explicit: one full agent turn per queued item). FIFO arrival order is a property of `SessionQueue::pop` (VecDeque::pop_front), proven exhaustively by the 1024-case proptest in `session_queue.rs::parity` shipped in Plan 01. |

**Fixture reuse:** All three tests reuse the existing `RecordingPlatformAdapter`
(for `test_telegram_busy_path_enqueues` and `test_telegram_cap_hit_full_ux`)
and `FailingPlatformAdapter` (for `test_telegram_post_turn_drain_in_arrival_order`)
from Plan 02 Task 3. Test fixtures and helpers (`build_test_session_store`,
`build_test_handler_with_queue`, `test_session_key`) are reused — no new
helper types were introduced.

**Pitfall 6 (offset-advance ordering):** documented as a comment block at
the top of both Telegram tests that exercise the dispatch path. The
runner-loop offset advance at `runner.rs:723-736` runs BEFORE the
`msg_tx` send, so handler-level tests cannot observe the offset state;
the live UAT runbook's Scenario 3 step 4 covers the user-visible
"no re-delivery" assertion.

| 1 | Rule 3 — scope clarification (not a fix) | The two Telegram dispatch-path tests include a Pitfall 6 documentation comment that points readers at `runner.rs:723-736` for the actual offset-advance code. The plan's `<action>` step 3 spec says `runner.rs:513-519`. | The line range was stale relative to the current `runner.rs` HEAD. The actual offset-advance code (`if let Some(new_offset) = offset { … offset = Some(update.update_id + 1); }` followed by the unconditional `offset = Some(update.update_id + 1);` fallback) lives at lines 731-736. The Pitfall 6 invariant is unchanged — offset advance precedes `msg_tx.send` — but the line citation was updated to the live source. No code change; comment-only correction. |
| 2 | Rule 3 — scope clarification | `test_telegram_post_turn_drain_in_arrival_order` uses `FailingPlatformAdapter` (not `RecordingPlatformAdapter`) for the drain test. | Identical reasoning to Plan 02 Task 3's `test_drain_after_turn`: under `Config::default()` without a real AgentRuntime, `run_agent` proceeds past the placeholder send into `PromptBuilder` / `StreamConsumer` / runtime setup with uncontrolled side effects that hang the test. `FailingPlatformAdapter` makes `run_agent` fail-fast at its first awaited adapter call so the drain loop's Rule-2 log+continue path actually drives the queue to empty — which is exactly what this test is designed to verify. The 3 placeholder sends recorded by the adapter prove the drain loop iterated 3 times. |
