# Plan 36.17.1-02 — SessionQueue wiring + per-turn drain helper

**Phase:** 36.17.1 — in-mem-fifo-queuing-parity-of-python-deque-for-chat-sessions
**Wave:** 2
**Status:** complete

## Objective

Thread the `SessionQueue` built in Plan 01 onto `GatewayRunner` and
`GatewayMessageHandler`. Replace the busy-agent reject branch in
`handle_with_multimodal` with a queue-or-cap-hit flow, and add a post-turn
drain helper that re-invokes `run_agent` for each queued event in arrival
order until the queue is empty for the session.

The drain helper is a phase deliverable per locked decision D-01(b) — it is
**unconditional**, not best-effort, with no feature gate.

## What changed

### `crates/ironhermes-gateway/src/runner.rs` (+123 lines)

- `GatewayRunner` gains a `session_queue: Arc<SessionQueue>` field, constructed
  with `SessionQueue::new()` in `GatewayRunner::new`.
- Five new public API methods: `session_queue()`, `try_enqueue`, `queue_len`,
  `clear_queue`, and `is_queue_full_for`. The accessor is `pub(crate)`; the
  rest are `pub` so the integration test binary and (eventually) other
  ironhermes-* crates can drive the queue without leaking the internal Arc
  outside the runner.
- `pub async fn start(self: Arc<Self>) -> Result<()>` — the signature widens
  from `&self` to `self: Arc<Self>` so the per-chat worker spawn loop can
  capture an `Arc<GatewayRunner>` and call `runner.drain_pending(...)` after
  each handler turn. The single call site in `ironhermes-cli`'s `run_gateway`
  is updated to `Arc::new(runner).start().await` accordingly.
- `pub async fn drain_pending(key, handler, adapter, cancel)` — pops from
  `self.session_queue` for the given `SessionKey` and re-invokes
  `handler.run_agent` per event in arrival order. **Logs and continues** on
  individual `run_agent` Err per the Rule 2 deviation: a single bad event
  must not poison the rest of the queue. Cancellation short-circuits the
  drain via the `cancel` token between iterations.
- Per-chat worker loop in `GatewayRunner::start` calls
  `self_for_worker.drain_pending(...)` after every `handle_with_multimodal`
  turn for the session_key, completing the Pitfall 4 post-turn drain wiring.

### `crates/ironhermes-gateway/src/handler.rs` (+47 / -7 lines)

- `GatewayMessageHandler` gains an optional `session_queue` plumbing slot via
  `set_session_queue(Arc<SessionQueue>)`, threaded by the runner at
  handler-construction time.
- Replaces the busy-agent reject branch in `handle_with_multimodal`: when
  `agent_running == true` and the chat is free-text (not a command), the
  event is `try_push`'d onto the session queue. Free-text enqueue is **silent**
  per locked decision D-13 — UserQueueManager's transport 👁 reaction is the
  visible signal at the platform layer; the gateway does not emit a chat reply.
- On cap-hit (`SessionQueue::try_push` returns `Err(QueueFull)`), the handler
  records a ❌ reaction on the inbound message and posts the
  D-13 cap-hit chat reply (`"⏳ Queue is full (128 messages)..."`) before
  returning. Telegram's `getUpdates` offset advance happens unconditionally
  in `runner.rs:513-519` before dispatch (Pitfall 6) so cap-hit does not cause
  the offset to be re-served.

### `crates/ironhermes-cli/src/main.rs` (+4 / -1 lines)

- Rule 3 (Blocking) — same-PR call-site fix: `run_gateway` now constructs
  `std::sync::Arc::new(runner).start().await` to match the new `start()`
  signature on `GatewayRunner`. Without this the workspace would not compile,
  so it ships in the same plan even though `cli/` was outside the plan's
  declared `files_modified` list.

### `crates/ironhermes-gateway/tests/session_queue_integration.rs` (+535 lines, new)

Three integration tests covering the Task 3 `<behavior>` block:

| Test | Asserts |
|------|---------|
| `test_busy_agent_enqueues_event` | Free-text arrival under `agent_running == true` enqueues onto SessionQueue and records **zero** `send_message` calls (D-13 silent enqueue). |
| `test_cap_hit_emits_reaction` | Pre-fill the queue to `MAX_QUEUE_DEPTH (128)`, push a 129th; assert ❌ reaction + ⏳ chat reply are recorded and cap holds at 128 (T-36.17.1-01 mitigation evidence). |
| `test_drain_after_turn` | Pre-load 3 events; call `runner.drain_pending(...)` directly; assert queue is empty afterwards and `run_agent` ran 3 times (one placeholder send per drained event). |

The drain test uses a separate `FailingPlatformAdapter` that records every
`send_message` call and then returns Err — without that, `run_agent` proceeds
past the placeholder send into `PromptBuilder` / `StreamConsumer` / runtime
setup that has uncontrolled side effects under `Config::default()` and hangs
the test. The Rule-2 log+continue path is what actually drains the queue to
empty when every `run_agent` errors, which is precisely what this test is
designed to verify.
