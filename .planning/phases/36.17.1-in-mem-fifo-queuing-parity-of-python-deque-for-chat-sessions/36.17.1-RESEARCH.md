## Summary

Phase 36.17.1 ports the Python `hermes-agent` per-session `/queue` FIFO mechanism to IronHermes. The Python source uses a two-part structure — `adapter._pending_messages` (single slot) + `self._queued_events` (overflow list) — but the Rust port replaces both with one contiguous `VecDeque<MessageEvent>` per session, hiding the split in a `#[cfg(test)]`-only mirror for proptest equivalence verification.

The **critical finding** from code investigation is that IronHermes already ships a `UserQueueManager` (`user_queue.rs`) that provides per-chat `mpsc::channel`-based queuing. This existing mechanism queues at the *transport/dispatch* level (between the Telegram poll loop and per-chat worker tasks) and is not aware of the agent-busy state from the per-session `AtomicBool`. Phase 36.17.1's `SessionQueue` operates at the *agent/session* level, keyed by `SessionKey` (platform + chat_id + user_id triple), and uses the existing `AtomicBool`-based running guard from Phase 36 to decide push-vs-dequeue. The two mechanisms serve different layers; this phase does NOT replace `UserQueueManager`.

The gateway already has all the integration scaffolding this phase needs: `SessionKey` (hash + eq + clone), `MessageEvent: Clone + Debug + Serialize + Deserialize`, `PlatformAdapter::add_reaction`, the `RunningAgentGuard` RAII pattern from Phase 36, and a working slash-command dispatch path. The plan is therefore largely additive — new file + wiring on existing structs.

**Primary recommendation:** Implement `SessionQueue` as `crates/ironhermes-gateway/src/session_queue.rs`, wire it onto `GatewayRunner` as a private field, expose the thin public API on `GatewayRunner`, patch `handle_with_multimodal` at the busy-check branch, patch the `/new` NewSession arm in `handler.rs`, and implement `/queue` in `handlers.rs` replacing the current placeholder stub.

## Decision Lock-Ins (Closing CONTEXT.md "Claude's Discretion" Items)

### Mutex Flavor — LOCKED: `std::sync::Mutex`

**Evidence:** `crates/ironhermes-gateway/Cargo.toml` has NO direct `parking_lot` dependency [VERIFIED: `Cargo.toml` lines 1-44]. `runner.rs:14` imports `use std::sync::{Arc, Mutex}` — that is the mutex used for `session_store` wrapping and every other gateway-crate lock. `parking_lot` appears only as a transitive dep in `Cargo.lock` (via other crates), never imported directly in any `src/*.rs` file in `ironhermes-gateway`.

**Decision:** Use `std::sync::Mutex<HashMap<SessionKey, VecDeque<MessageEvent>>>` for `SessionQueue`. [VERIFIED: runner.rs:14, Cargo.toml:1-44]

### `try_push` Signature — LOCKED: `&SessionKey`

**Evidence:** Every existing method on `GatewayRunner` that names a session does so by reference (e.g., `session_store.get(&session_key)`, `session_store.get_running_flag(&session_key)`). `SessionKey: Clone` so the method can clone internally when inserting a new entry into the map. Passing `&SessionKey` avoids forcing callers to give up ownership for a lookup-and-conditional-insert.

**Decision:** `try_push(&self, key: &SessionKey, event: MessageEvent) -> Result<(), QueueError>` — key by ref, event by value (the queue owns it). [VERIFIED: session.rs:244, handler.rs:377]

### File Layout — LOCKED: Single file `session_queue.rs`

**Evidence:** The gateway crate's existing pattern is one file per concern (`user_queue.rs`, `rate_limiter.rs`, `backoff.rs` — all self-contained). No file currently uses a `mod.rs` split within `src/`. D-07's `#[cfg(test)]` modules in this codebase are consistently inlined at the bottom of the owning file (e.g., `user_queue.rs:119`, `rate_limiter.rs:66`, `backoff.rs:66`).

**Decision:** `crates/ironhermes-gateway/src/session_queue.rs` — production struct + public API in the top half; `#[cfg(test)]` module at the bottom containing `SessionFifoQueue` trait, `SplitSlotQueue` mirror, and proptest suite. [VERIFIED: user_queue.rs:119, rate_limiter.rs:66]

### `QueueError` Variants — RECOMMENDED

```rust
#[derive(Debug, thiserror::Error)]
pub enum QueueError {
    #[error("Queue capacity reached (max {max}) for session {session_key}")]
    CapacityReached { session_key: String, max: usize },
```

A single variant suffices for this phase — `CapacityReached` is the only error path. Future phases (e.g., drain-mode errors, webhook 429 handling) can add variants without breaking the existing match. [ASSUMED — single variant is sufficient per D-11/D-12 scope]

## Python Source Verification

### §2298-2302 — `_queue_during_drain_enabled` [VERIFIED: run.py:2298-2302]

```python
def _queue_during_drain_enabled(self) -> bool:
    return self._restart_requested and self._busy_input_mode in {"queue", "steer"}
```

**IronHermes mapping:** `_restart_requested` has no direct equivalent yet — the gateway shuts down cleanly via `CancellationToken`. D-03 requires a new `is_draining: AtomicBool` flag on `GatewayRunner` that is set to `true` before `self.cancel.cancel()` fires in the shutdown sequence (runner.rs:902). When `is_draining` is true, incoming `MessageEvent`s that would normally be dropped (channel closed) are instead pushed to the per-session queue so they survive restart. NOTE: the gateway restart mechanism in IronHermes currently terminates the process (the caller re-runs `ironhermes gateway`); queue contents are in-memory and will be lost on process exit. D-03's "preservation" means: *within the same process lifetime until cancel fires*, late-arriving events are queued rather than discarded. Cross-process queue persistence is explicitly out of scope (phase title: "in-mem").

### §1479 — `self._queued_events` declaration [VERIFIED: run.py:1479]

```python
self._queued_events: Dict[str, List[MessageEvent]] = {}
```

The overflow list is a plain dict of lists, not `collections.deque`. The "python deque" in the phase title is misleading — the canonical Python uses `list.append` / `list.pop(0)`. The Rust `VecDeque` (O(1) both ends) is strictly better and accurate.

### §1007 — `_dequeue_pending_event` [VERIFIED: run.py:1007-1014]

```python
def _dequeue_pending_event(adapter, session_key: str) -> MessageEvent | None:
    return adapter.get_pending_message(session_key)
```

This is the single-slot dequeue: it pops from `adapter._pending_messages`. In the Rust port the slot does not exist — `pop(&self, key: &SessionKey) -> Option<MessageEvent>` calls `VecDeque::pop_front()` directly. No adapter indirection needed.

### §2304-2415 — FIFO helpers [VERIFIED: run.py:2304-2415]

**`_enqueue_fifo` (run.py:2315-2329):**
- If `session_key` is already in `adapter._pending_messages` (slot occupied): append to `self._queued_events[session_key]` overflow.
- If slot is free: set `adapter._pending_messages[session_key] = queued_event`.

**`_promote_queued_event` (run.py:2331-2364):**
- Called after each drain (after the pending slot is consumed).
- If overflow has items: pop the head (`overflow.pop(0)`).
  - If `pending_event is None` (slot was empty): return the popped item as the new pending event.
  - If `pending_event` is not None (slot still occupied, e.g., by an interrupt follow-up): re-stage the popped item back into the slot for the NEXT recursion.

**`_queue_depth` (run.py:2366-2372):**
- `depth = len(overflow) + (1 if session_key in pending_slot else 0)` — counts both layers.

**Rust translation:** `VecDeque` replaces both layers. `try_push` → `push_back`. `pop` → `pop_front`. `len` → `VecDeque::len`. The two-layer bookkeeping in `_enqueue_fifo`/`_promote_queued_event` vanishes. The `SplitSlotQueue` mirror in `#[cfg(test)]` must reproduce the exact two-layer Python semantics so proptest can verify behavioral equivalence.

**`_is_goal_continuation_event` / `_clear_goal_pending_continuations` (run.py:2374-2414):**
Both check `str(text).startswith("[Continuing toward your standing goal]\nGoal:")`. D-04 confirms these are OUT — no call-site in IronHermes uses them. The only way they'd be triggered is if `/goal` exists, which it does not. No action required. [VERIFIED: CONTEXT.md D-04; grepped `ironhermes-agent/src/subagent_runner.rs` — single unrelated `/goal` mention]

### §6785-7029 — `/queue` and `/new` call-sites [VERIFIED: run.py:6785-6867, 6800-6821]

**`/new` clearing (run.py:6788-6798):**
```python
await self._interrupt_and_clear_session(...)
return await self._handle_reset_command(event)
```
`_interrupt_and_clear_session` clears the adapter's pending queue. In IronHermes, the `NewSession` arm in `handler.rs:549-592` already calls `store.remove(&session_key)` which discards `GatewaySession`. The hook point for `clear_queue(session_key)` is immediately before (or inside) that `store.remove()` call.

**`/queue` dispatch (run.py:6800-6821):**
```python
if event.get_command() in {"queue", "q"}:
    queued_text = event.get_command_args().strip()
    if not queued_text:
        return "Usage: /queue <prompt>"
    queued_event = MessageEvent(text=queued_text, ...)
    self._enqueue_fifo(_quick_key, queued_event, adapter)
    depth = self._queue_depth(...)
    if depth <= 1:
        return "Queued for the next turn."
    return f"Queued for the next turn. ({depth} queued)"
```

The `/queue` command calls `try_push` **unconditionally** — regardless of whether an agent is running. This is semantically different from a free-text message (which the running-agent guard rejects). The IronHermes `cmd_queue` stub at `handlers.rs:1607` currently returns a fake `CommandResult::Output` with no actual queuing logic.

### Graceful-Shutdown Primitives (`runner.rs:870-943`) [VERIFIED]

Phase 36.17 shipped web-server graceful shutdown (not gateway-level drain mode). The gateway shutdown sequence is:

1. `tokio::select!` fires on ctrl+c / cancel token (runner.rs:874)
2. MCP servers shut down (runner.rs:895-898)
3. `self.cancel.cancel()` fires (runner.rs:902)
4. Per-chat workers drained with 5s timeout (runner.rs:904-933)
5. `drop(msg_tx)` (runner.rs:937)
6. `join_set` drained (runner.rs:940)

**D-03 drain-mode requirement:** No `is_draining` flag exists yet. The plan must add:
- `is_draining: Arc<AtomicBool>` field on `GatewayRunner`, initialized to `false`.
- Set to `true` at step 2 (before `self.cancel.cancel()`).
- In the dispatch loop (runner.rs:658-776): after `update = msg_rx.recv()` yields `None` (channel closed during drain), do NOT discard — instead push to `session_queue` if `is_draining.load()` is true.

In practice: once `msg_tx` is dropped (step 5) the dispatch loop exits via `None => break`. Messages arriving between step 3 (cancel fired) and step 5 (channel closed) may still be in the `msg_rx` buffer. The drain-preservation window is this ~0ms-to-5s window. This is the IronHermes analog of Python's `_queue_during_drain_enabled` check. [VERIFIED: runner.rs:870-943]

### Pattern: `SessionQueue` — interior mutability, sync only

```rust
// session_queue.rs
use std::collections::{HashMap, VecDeque};
use std::sync::Mutex;
use crate::session::SessionKey;
use ironhermes_core::MessageEvent;

pub const MAX_QUEUE_DEPTH: usize = 128;
pub const WARN_QUEUE_DEPTH: usize = 96;  // 75%

#[derive(Debug, thiserror::Error)]
pub enum QueueError {
    #[error("Queue at capacity ({max}) for session {session_key}")]
    CapacityReached { session_key: String, max: usize },
}

pub struct SessionQueue {
    queues: Mutex<HashMap<SessionKey, VecDeque<MessageEvent>>>,
}

impl SessionQueue {
    pub fn new() -> Self { Self { queues: Mutex::new(HashMap::new()) } }

    // Python parity: _enqueue_fifo (gateway/run.py:2315)
    pub fn try_push(&self, key: &SessionKey, event: MessageEvent) -> Result<(), QueueError> {
        let mut map = self.queues.lock().unwrap();
        let q = map.entry(key.clone()).or_default();
        if q.len() >= MAX_QUEUE_DEPTH {
            return Err(QueueError::CapacityReached { session_key: key.to_string_key(), max: MAX_QUEUE_DEPTH });
        }
        if q.len() >= WARN_QUEUE_DEPTH {
            // tracing::warn! here — inside lock is fine (microsecond, no await)
        }
        q.push_back(event);
        Ok(())
    }

    // Python parity: _dequeue_pending_event (gateway/run.py:1007)
    pub fn pop(&self, key: &SessionKey) -> Option<MessageEvent> {
        let mut map = self.queues.lock().unwrap();
        let q = map.get_mut(key)?;
        let item = q.pop_front();
        if q.is_empty() { map.remove(key); }
        item
    }

    // Python parity: _queue_depth (gateway/run.py:2366)
    pub fn len(&self, key: &SessionKey) -> usize {
        self.queues.lock().unwrap().get(key).map(|q| q.len()).unwrap_or(0)
    }

    // Python parity: /new + /reset clearing
    pub fn clear(&self, key: &SessionKey) {
        self.queues.lock().unwrap().remove(key);
    }

    // Python parity: _clear_goal_pending_continuations structure (gateway/run.py:2385)
    // (goal predicate deferred per D-04; retain is the general mechanism)
    pub fn retain(&self, key: &SessionKey, predicate: impl Fn(&MessageEvent) -> bool) {
        let mut map = self.queues.lock().unwrap();
        if let Some(q) = map.get_mut(key) {
            q.retain(|e| predicate(e));
            if q.is_empty() { map.remove(key); }
        }
    }
}
```

### Anti-Patterns to Avoid

- **`tokio::sync::Mutex` for `SessionQueue`:** D-17 explicitly forbids it. All `SessionQueue` methods are sync; no `.await` inside critical sections.
- **`DashMap` or `RwLock<HashMap>`:** D-16 explicitly forbids it. O(1) operations at chat-message arrival rates need no concurrent sharding.
- **Holding the `Mutex` across an `await`:** The lock guard MUST be dropped before any `.await`. Rust's borrow checker will enforce this for `std::sync::MutexGuard` (which is `!Send`), but be explicit — unlock before calling `adapter.send_message(...)`.
- **Calling `clear_queue` after `session_store.remove`:** The order must be `clear_queue` first, then `store.remove`. If reversed, a new session created in the window between remove+clear could have its first message silently dropped.

## Common Pitfalls

### Pitfall 1: `UserQueueManager` Confusion

**What goes wrong:** Treating the existing `UserQueueManager` (`user_queue.rs`) as the "queue this phase ports." It is not. `UserQueueManager` queues at the *transport layer* (one `mpsc::channel` per `chat_id`, buffers messages while a per-chat worker task is executing). It does not check `agent_running` (the AtomicBool). It uses `tokio::sync::Mutex` (async). `SessionQueue` operates at the *agent layer* (one `VecDeque` per `SessionKey` = platform+chat_id+user_id triple, driven by the existing running guard).

**How to avoid:** Both mechanisms co-exist. `UserQueueManager` ensures per-chat serial delivery to the handler. `SessionQueue` queues messages *inside the handler* when the per-session agent is actively running a turn.

**Warning signs:** A plan that says "replace `UserQueueManager`" or "modify `user_queue.rs`" is wrong.

### Pitfall 2: Mutex Guard Held Across `await`

**What goes wrong:** Code like:
```rust
let mut map = self.queues.lock().unwrap();
adapter.send_message(...).await?;  // COMPILE ERROR: MutexGuard is !Send
```

**Why it happens:** `std::sync::MutexGuard` is `!Send`. Holding it across an `.await` point will fail to compile (the future must be `Send` for tokio's multi-thread executor). This is actually a safety feature — it prevents the bug.

**How to avoid:** Clone or extract the data needed, drop the guard, then perform the async call. All `SessionQueue` methods are sync and must not call any async code internally.

### Pitfall 3: `cmd_queue` Accesses `ctx.agent_loop` (Broken Gate)

**What goes wrong:** The current stub returns early if `ctx.agent_loop.is_none()` — but `agent_loop` is never set in the gateway `CommandContext`, so `/queue` always returns "Agent loop not configured."

**How to avoid:** Remove the `agent_loop` gate. The real gate is "does the session queue accept this event?" — handled by `try_push`'s result, not by whether an agent loop is wired.

### Pitfall 4: Re-Entering `run_agent` After Dequeue — Double Guard

**What goes wrong:** After `run_agent` completes (RAII guard drops, AtomicBool → false), the code calls `session_queue.pop()` to find the next queued event, then calls `run_agent` again. If the new `run_agent` call goes through `handle_with_multimodal`, it will hit the running guard check again (which is now false — correct). But if the re-entry path skips `handle_with_multimodal` and calls `run_agent` directly, it creates the guard again without the busy-check guard — this is fine and intentional, but must be explicit.

**How to avoid:** The post-agent-turn dequeue loop should call `run_agent` directly (bypassing `handle_with_multimodal`), not re-enter the message handler. The `RunningAgentGuard` is set inside `run_agent` at line 875 regardless.

### Pitfall 5: `clear_queue` Order Relative to `session_store.remove`

**What goes wrong:** If `session_store.remove(&session_key)` fires first, the `GatewaySession` (including the `running: Arc<AtomicBool>`) is dropped. A racing `run_agent` turn sees the flag is now gone and creates a new session. The `clear_queue` then fires and clears the NEW session's queue (which should be empty anyway but the race is not obviously safe).

**How to avoid:** Call `session_queue.clear(&session_key)` BEFORE `session_store.remove(&session_key)` in the `/new` handler arm.

### Pitfall 6: Telegram Offset Advance on Cap-Hit (D-13)

**What goes wrong:** Dropping the Telegram update without advancing the offset means Telegram will re-deliver the same message on the next `getUpdates` call, creating an infinite retry loop from Telegram's perspective.

**How to avoid:** D-13 explicitly states "ack the Telegram `getUpdates` offset" — the offset advance already happens unconditionally in the poll loop (runner.rs:515-519) before the message is dispatched. The cap-hit UX fires AFTER offset advance, so this is safe by construction. No special handling needed. [VERIFIED: runner.rs:513-519]

### Pitfall 7: `SessionKey` Partial Construction

**What goes wrong:** `SessionKey::new(platform, chat_id)` without `.with_user(sender_id)` produces a key that matches a different bucket than the one the handler creates. The handler always calls `.with_user(&event.sender_id)` (handler.rs:377).

**How to avoid:** All queue operations must use the same key-construction pattern as the handler: `SessionKey::new(event.platform.clone(), &event.chat_id).with_user(&event.sender_id)`.

## Security Domain

This phase introduces no authentication, authorization, or cryptographic operations. The queue is in-process only, keyed by `SessionKey` derived from the already-authenticated Telegram `sender_id`. The whitelist check (runner.rs:681-689) fires before any queue interaction.

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | — |
| V3 Session Management | no | queue lifetime = process lifetime |
| V4 Access Control | no | per-session key isolation |
| V5 Input Validation | yes | `content: String` in `MessageEvent` already sanitized upstream; queue does not re-validate |
| V6 Cryptography | no | — |

**One security note:** The 128-message hard cap (D-09/D-11) is itself the primary DoS mitigation. Without it a single Telegram user could fill the gateway's heap by sending many `/queue` commands. The drop-newest policy (D-10) ensures the guard works correctly.

## Open Questions (RESOLVED)

All three open questions below have been resolved inline during research and the recommendations are adopted by the plans. Citations name the specific plan + task where each recommendation was implemented.

1. **`CommandResult::Queued` vs side-effect in `cmd_queue`** — RESOLVED
   - What we know: `cmd_queue` is a sync function with no access to `Arc<SessionQueue>`.
   - What was unclear: Should the handler dispatch (gateway) intercept `CommandResult::Queued` and call `try_enqueue`, or should `CommandContext` carry an `Arc<SessionQueue>` so `cmd_queue` can call `try_enqueue` directly?
   - **Resolution:** Add `CommandResult::Queued { message: String }` — keeps `handlers.rs` side-effect free (the existing pattern). The gateway handler intercepts `Queued` and calls `session_queue.try_push(...)`. This is consistent with how `NewSession` is intercepted.
   - **Adopted by:** Plan 03 (`36.17.1-03-PLAN.md`) Task 1 adds the `CommandResult::Queued { message: String }` variant and rewrites `cmd_queue` to return it; Plan 03 Task 2 wires the gateway-side intercept that calls `session_queue.try_push(...)`.

2. **Post-turn dequeue loop placement** — RESOLVED
   - What we know: After `run_agent` completes and `RunningAgentGuard` drops (AtomicBool → false), the code should check `session_queue.pop()` and re-enter.
   - What was unclear: Does the re-entry loop live in `run_agent` itself (tail recursion) or in the worker task in `runner.rs`?
   - **Resolution:** Place the dequeue loop at the caller of `run_agent` in the per-chat worker (runner.rs:734-772), not inside `run_agent`. This keeps `run_agent` single-purpose and avoids deep recursion for long queues. The loop is exposed as `pub(crate) async fn drain_pending(...)` on `GatewayRunner` for direct test coverage.
   - **Adopted by:** Plan 02 (`36.17.1-02-PLAN.md`) Task 3 implements the per-chat worker drain loop and exposes it as `pub(crate) async fn drain_pending(...)`.

3. **`Arc<SessionQueue>` vs `Arc<GatewayRunner>` on `GatewayMessageHandler`** — RESOLVED
   - What we know: `GatewayMessageHandler` is built from `GatewayRunner::build_gateway_handler(&self)`.
   - What was unclear: `Arc<GatewayRunner>` would be circular (runner owns handler, handler needs runner).
   - **Resolution:** Thread `Arc<SessionQueue>` (not `Arc<GatewayRunner>`) into the handler, following the exact same pattern as `Arc<RwLock<SessionStore>>`. No circular reference.
   - **Adopted by:** Plan 02 (`36.17.1-02-PLAN.md`) Task 1 adds `session_queue: Arc<SessionQueue>` to `GatewayRunner` plus a `pub(crate) fn session_queue(&self) -> Arc<SessionQueue>` accessor; Plan 02 Task 2 adds `session_queue: Option<Arc<SessionQueue>>` to `GatewayMessageHandler` with `set_session_queue(...)`, and `build_gateway_handler` threads the Arc in (NOT `Arc<GatewayRunner>`).
