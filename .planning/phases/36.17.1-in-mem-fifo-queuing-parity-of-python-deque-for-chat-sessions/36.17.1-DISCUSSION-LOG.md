## Bounding + eviction

### Q1 — Bounded or unbounded

| Option | Description | Selected |
|--------|-------------|----------|
| Unbounded (parity) | Match Python `list` exactly. | |
| **Bounded per-session `maxlen`** | Hard cap per session. | ✓ |
| Bounded with global cap | Cap total events across all sessions. | |
| Soft warning, hard unbound | Log warning at threshold, never drop. | (folded as 75% warn) |

**User's choice:** Bounded per-session. **Notes (verbatim user reasoning):**
- 128 (or 256) maxlen per session compartmentalizes blast radius.
- Global cap rejected: shared `AtomicUsize`/`Mutex` kills lock-free per-session isolation.
- Overflow policy: **Drop Newest + Warn**. Soft warn at 75% (96 messages) via `tracing::warn!`; hard cap at 128 → reject incoming. Drop-newest preserves the oldest (which holds immediate sequential context the agent is about to act on).
- **Backpressure**: HTTP 429 + `Retry-After: 5` at the network edge for HTTP-arrival platforms. Well-behaved clients (Stripe, Discord) honor `Retry-After` automatically. Stop the overflow at HTTP layer; never enters core domain logic.

### Q2 — Telegram cap-hit UX (no HTTP caller to 429)

| Option | Description | Selected |
|--------|-------------|----------|
| Silent drop + log only | Drop, warn, no chat reply. | |
| Reject with chat reply | Send "Queue is full" Telegram reply. | |
| **Reject with chat reply + reaction** | `❌` reaction via `add_reaction` + short rejection chat reply. | ✓ |
| Telegram-specific: never drop, hard-clamp the producer | Slow `getUpdates` offset advancement. | |

**User's choice:** Reject with chat reply + reaction.
