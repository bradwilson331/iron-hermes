# Phase 36.17.2.2 Plan 04: TelegramAdapter MediaSender + edit_message_markdown_v2 Summary

Land the four structural reconciliations that everything else in Phase 36.17.2.2 rides on: refactor `send_file_multipart` to return `Result<MessageResponse>`, add `send_audio` for D-13's fifth type, replace the legacy `parse_mode: Markdown` `edit_message_markdown` trait method with `edit_message_markdown_v2` (with D-02 parse-error fallback) and ripple to every adapter impl in the crate, and implement `MediaSender` on `TelegramAdapter` with the full D-12/D-13/D-14/D-15/D-17 dispatch plus the phase threat model's three input gates.

## What Shipped

### Task 1 — `send_file_multipart` widened + `send_audio` helper (commit `7a65f348`)

`send_file_multipart` previously deserialized the Telegram response as `TelegramResponse<serde_json::Value>` and discarded the body, returning `Result<()>`. It now deserializes as `TelegramResponse<TgMessage>` and projects to `MessageResponse` via the exact same shape used by `send_message` (telegram.rs:218-236) — `message_id: result.message_id.to_string()`, `chat_id: chat_id.to_string()`, `platform: Platform::Telegram`. The 4 in-crate `TgSendApi` callers (`send_voice`, `send_image_file`, `send_video`, `send_document`) append `.map(|_| ())` to keep their existing `Result<()>` contract — `ironhermes-cron`'s `TgSendApi` trait stayed untouched.

Added `pub async fn send_audio(&self, chat_id, path, thread_id) -> Result<MessageResponse>` as an inherent method on `TelegramAdapter` (not on `TgSendApi` — cron has no audio caller). Single-line wrapper around `send_file_multipart("sendAudio", "audio", ...)` matching the four existing helpers' shape. This is the fifth method `MediaSender::send_audio` needs in task 4 for D-13's audio/voice split (D-14: `.mp3 .m4a .flac .wav` go to `sendAudio`, `.ogg .opus` go to `sendVoice`).

The D-02 single-retry-as-plain-text fallback lives only in `TelegramAdapter::edit_message_markdown_v2` (test fixtures don't talk to Telegram so they don't need it). The first `api_call` is wrapped in `match`; on `Err`, the error description is substring-matched against `"can't parse"`, `"parse entities"`, `"parse_mode"`. On match: `warn!` logs the failing chat/message/error and the call is re-issued ONCE with `parse_mode` OMITTED. On retry-Ok return `Ok(())`; on retry-Err `error!` logs both errors and the retry `Err` is returned. The retry happens AT MOST ONCE — the T-36.17.2.2-D02-INFINITE-RETRY mitigation. Non-parse-mode errors propagate unchanged.

Added `use tracing::{error, warn};` import.

This commit intentionally leaves `stream_consumer.rs:100` calling the legacy name — task 3 fixes it. The split keeps the trait/impl rename atomic and reviewable separately from the call-site rename.

### Task 3 — `stream_consumer.rs:100` call-site rename (commit `64754747`)

Mechanical rename of `.edit_message_markdown(...)` → `.edit_message_markdown_v2(...)` at the only production caller. Per the plan's task split, the `&remaining` body is passed through WITHOUT `escape_outside_code_blocks` — that escape-application is plan 05's job. ### Task 4 — `impl MediaSender for TelegramAdapter` (commit `8e75c641`)

`#[async_trait] impl MediaSender for TelegramAdapter` lives at telegram.rs:452, after the existing `impl PlatformAdapter for TelegramAdapter` block. All five per-type methods implemented; `send_media` inherits the trait's default dispatch.

Each per-type method matches on `&MediaSource`:

- **`MediaSource::Path(p)`** — runs three gates in sequence:
  1. `check_size_cap(p, cap)` — `tokio::fs::metadata` against `SIZE_CAP_20_MB` (photo/voice/audio/video) or `SIZE_CAP_50_MB` (document). On exceed, returns a typed `Err` whose message starts with `"media exceeds size cap: ..."` so the D-19 dispatch loop in plan 06 can substring-detect it.
  2. `canonicalize_under_allowed_roots(p)` — T-INPUT-MEDIA-PATH gate. Canonicalizes the path (resolves symlinks + `..`), then checks the canonical form is contained under one of the allowed roots: `$HERMES_HOME` (if env var is set and canonicalizes) AND `/tmp`. On rejection logs `warn!(filename = %p.file_name())` — FILENAME ONLY per T-LOG-LEAK — and returns `Err("media path outside allowed roots: ...")`.
  3. `send_file_multipart(method, field, chat_id, &validated, thread_id)` — forwards to the helper that returns `Result<MessageResponse>` (refactored in task 1).
- **`MediaSource::Url(u)`** — D-12 passthrough:
  1. `validate_url_scheme(u)` — accepts only `http://` and `https://` (rejects `file://`, `gopher://`, `ftp://`, etc.) per T-INPUT-MEDIA-URL.
  2. `send_url_form(adapter, method, field, chat_id, u, thread_id)` — builds `{ chat_id, <field>: u, [message_thread_id] }`, calls `adapter.api_call`, projects `TgMessage` → `MessageResponse`. No multipart, no local fetch.

D-13 dispatch table (method / multipart field):

| `MediaKind` | Method | Field | Cap |
|---|---|---|---|
| `Photo` | `sendPhoto` | `photo` | 20 MiB |
| `Voice` | `sendVoice` | `voice` | 20 MiB |
| `Audio` | `sendAudio` | `audio` | 20 MiB |
| `Video` | `sendVideo` | `video` | 20 MiB |
| `Document` | `sendDocument` | `document` | 50 MiB |

D-14 audio-format split is enforced upstream by `MediaTagExtractor::infer_kind` (plan 02 telegram.rs:495-513) — `.ogg`/`.opus` → `Voice`, `.mp3`/`.m4a`/`.flac`/`.wav` → `Audio`. The `MediaSender` trait's default `send_media` impl matches on `MediaKind` and dispatches to the right method.

D-17 honored — no `caption` parameter on any of the five methods.

**FLAGGED RISK D-05 honored.** `MediaSender::send_photo` is INTENTIONALLY a sibling, NOT a rename, of the existing `TgSendApi::send_image_file` method on the same struct. `send_image_file` has `ironhermes-cron` callers (verified by `rg send_image_file crates/ironhermes-cron/src/` — referenced in adapter.rs doc-comment and trait method at line 33). The two methods share `send_file_multipart` under the hood, so behavior for the Path arm is identical; the new name exists so the `MediaSender` trait surface reads naturally. The impl block's doc-comment records the divergence.
