# Phase 36.17.2.2: IronHermes Telegram client delivers streaming final media messages - Context

**Gathered:** 2026-06-03
**Status:** Ready for planning
**Trigger:** Bring IronHermes's Telegram delivery surface to parity with the hermes-agent contract captured in `docs/telegram-features.txt` — finalized text rendered as MarkdownV2, streaming intermediate edits as plain text (already done via 36.17.2 D-03), and `<MEDIA: ...>` outputs routed as **native Telegram attachments** instead of raw text paths.

<domain>
## Phase Boundary

After this phase, the IronHermes Telegram client delivers AI-generated turns over Telegram with the same user-visible contract as hermes-agent:

1. **Final text edit** uses `parse_mode: MarkdownV2` with a smart escape function (literal reserved chars outside fenced code / inline code / link URLs get backslash-escaped; real markdown syntax — `*bold*`, `_italic_`, `` `code` ``, ` ```fence``` `, `[label](url)` — survives).
2. **Intermediate streaming edits** continue to send plain text (no `parse_mode`) per locked decision 36.17.2 D-03. The cursor block `█` strip on final edit (`stream_consumer.rs:159-175`) is preserved.
3. **`<MEDIA: path|url>` inline tags** in the agent's output are extracted by a new `MediaTagExtractor` (sibling of `StreamingContextScrubber` at `handler.rs:1334`) and routed as native Telegram attachments via `sendPhoto / sendVoice / sendAudio / sendVideo / sendDocument`. The text is edited first; attachments are sent as separate follow-up messages.

**Out of scope:**

- Discord/Slack/web/webhook media routing — strictly Telegram client in this phase (multi-platform comes via the new `MediaSender` trait shape in D-18, but only `TelegramAdapter` implements it now).
- Inbound media handling (`tg_message_to_event` at `telegram.rs:379-419` already extracts `photo` + `document` attachment metadata; no changes here). Adding inbound `voice` / `video` extraction is a separate phase.
- TTS generation itself (this phase only delivers an already-produced `.ogg/.opus/.mp3` file via the MEDIA tag protocol — wiring of an actual TTS tool is unrelated).
- `sendMediaGroup` / album batching for multi-photo turns — sequential single-message delivery per D-11.
- `sendSticker` / `sendAnimation` — not in the multipart helper set today; deferred.
- Caption-on-attachment behavior (D-17 diverges from hermes-agent §Audio Captions intentionally — see decisions).
- The 36.17.2 queue/worker architecture is unchanged. The new media-routing code runs **inside** `handle_with_multimodal` after the existing `stream_consumer.flush(true)` returns (D-19), so the per-chat worker still pops one event at a time and the cap-hit UX / 👀 reaction / slash-command fast-path all stay verbatim.

</domain>

<decisions>
## Implementation Decisions (LOCKED by user 2026-06-03)

### Final-text parse mode

- **D-01:** **Final flush sends `parse_mode: MarkdownV2`** with a smart escape function. The 18 reserved chars Telegram requires escaped — `_ * [ ] ( ) ~ ` ` > # + - = | { } . !` — are backslash-escaped ONLY outside fenced code blocks, inline code spans, and link URLs. Real markdown syntax authored by the model (bold, italic, inline code, fenced code, links) survives untouched. The existing `edit_message_markdown` method at `telegram.rs:250-265` (which sends legacy `parse_mode: Markdown`) is **replaced** by a new `edit_message_markdown_v2` method; the call site in `stream_consumer.rs:99-105` switches over.
- **D-02:** **Parse-error fallback: single retry as plain text.** When `editMessageText` returns `400 Bad Request: can't parse entities` (or any other parse-mode-related 400), the gateway re-issues the same `editMessageText` call **once** with `parse_mode` omitted. Logged at `warn!` with the body that failed. On second failure, log `error!` and leave the streamed plain-text in place (D-03 means intermediate edits already deposited a plain-text version into the placeholder, so the user sees the streamed body without final formatting).
- **D-03:** **Streaming intermediate edits stay plain text.** `stream_consumer.rs::flush(final_edit=false)` continues to call `edit_message` (no `parse_mode`) at `stream_consumer.rs:114, 161`. Cursor `█` strip on final edit (`stream_consumer.rs:159-175`) is preserved verbatim. Matches docs/telegram-features.txt §Streaming Intermediate Edits.
- **D-04:** **Escape logic lives in a new module: `crates/ironhermes-gateway/src/markdown_v2.rs`.** Exports two public functions:
  - `pub fn escape_markdown_v2(text: &str) -> String` — unconditional escape of all 18 reserved chars (used when callers know the body is plain literal text).
  - `pub fn escape_outside_code_blocks(text: &str) -> String` — the smart escape used by `edit_message_markdown_v2` and the `send_message` overflow-chunking path (`stream_consumer.rs:121-128`). Tracks `` ``` `` fence state, ` ` ` inline-code state, and `[label](url)` URL state; reserved chars inside any of those contexts pass through unescaped.
  - Module is golden-tested with cases matching hermes-agent's reference escape table (see canonical_refs §Test fixtures).

### Media routing protocol

- **D-05:** **Media routing uses `<MEDIA: path|url>` inline tags in the agent's output**, extracted by a new `MediaTagExtractor` struct (sibling of `StreamingContextScrubber` at `handler.rs:1334`). Wire shape:
  - `extractor.feed(delta: &str) -> String` strips matched tags from the visible stream and accumulates them internally; returned string is what reaches `stream_tx` (and thus `StreamConsumer`).
  - `extractor.flush_tail() -> String` (paired with the existing scrubber tail flush at `handler.rs:1432`) handles any trailing partial tag at stream end.
  - `extractor.take_attachments() -> Vec<MediaRef>` drains the accumulated tags after the stream ends.
  - `MediaRef { source: MediaSource, kind: MediaKind }` where `MediaSource = Path(PathBuf) | Url(String)` and `MediaKind = Photo | Voice | Audio | Video | Document`.
- **D-06:** **Tag grammar: `<MEDIA:\s*([^>]+)>`** — single regex, single capture group. The captured token is trimmed and inspected:
  - If it parses as a URL (`http://` or `https://` prefix), `MediaSource::Url`.
  - Otherwise `MediaSource::Path` (relative paths resolved against the gateway's cwd / `HERMES_HOME` per existing convention).
  - `MediaKind` inferred by extension on the last path/URL segment (case-insensitive):
    - `.png .jpg .jpeg .webp .gif (non-animated)` → `Photo`
    - `.ogg .opus` → `Voice`
    - `.mp3 .m4a .flac .wav` → `Audio` (note: `Audio` is a new variant; today only `send_voice` exists)
    - `.mp4 .mov .webm` → `Video`
    - anything else → `Document`
- **D-07:** **Text-first, attachment-second; no caption on attachments.** Delivery sequence inside `run_agent`:
  1. `stream_consumer.flush(true).await?` — runs the MarkdownV2 final edit per D-01/D-02.
  2. `let attachments = extractor.take_attachments();`
  3. For each `MediaRef` in stream order: `media_sender.send_media(chat_id, media_ref, thread_id).await` (see D-18). No `caption` parameter is passed; the surrounding text was already rendered by step 1.
- **D-08:** **Extraction happens during streaming (scrubber-style).** Tags never reach the user's screen as visible text under the happy path. Implementation mirrors `StreamingContextScrubber` exactly: a small state machine that buffers possible partial tag prefixes across delta boundaries (`<`, `<M`, `<ME`, …, `<MEDIA:…` until matching `>`) and only emits to the visible stream once the prefix is disambiguated.
- **D-09:** **Tags inside fenced code blocks AND inline code pass through verbatim** to the visible stream (no extraction). The extractor tracks two pieces of state alongside the partial-prefix machine: an `in_fenced_code` boolean toggled by ` ``` ` runs, and an `in_inline_code` boolean toggled by ` ` ` runs that are NOT inside a fence. When either is true, `<MEDIA: …>` text streams to the user unchanged. This lets the model document the convention (e.g. "Use ` ``` ` `<MEDIA: path>` ` ``` ` to send media") without false-positive attachments.
- **D-10:** **Missing / unreadable / oversized media → log `warn!` + reinsert tag as visible text.** When `send_media` fails (file open error, Telegram API error including size rejection, URL fetch failure on Telegram's side), the gateway logs at `warn!` level with the source path/URL and the underlying error, then re-edits the placeholder message via `editMessageText` to append the original `<MEDIA: ...>` tag text to the final body. The user sees the tag literal, knows something tried to attach, and can ask the model to retry. **Never silent.**
- **D-11:** **Multiple media tags in one turn = sequential `send_media` calls in stream order.** No `sendMediaGroup` album batching in this phase. Three tags → one text edit + three attachment messages = four Telegram messages total. Each attachment is awaited before the next is dispatched (consistent with the 36.17.2 D-06 per-chat serial worker).
- **D-12:** **URL form passes through to Telegram unchanged.** `sendPhoto` / `sendVoice` / etc. accept either a multipart upload OR a URL string in the `photo` / `voice` / etc. parameter. The gateway uses the URL form (Telegram's servers fetch). No local download. Failure mode is Telegram returning a 400 from its own fetch attempt — handled identically to D-10's log+reinsert. **Local paths uploaded multipart** via the existing `send_file_multipart` helper at `telegram.rs:155-200`.

### Native attachment scope

- **D-13:** **Ship all five attachment types: photo, voice, audio, video, document.** Existing multipart helpers cover four (`send_voice` @ `telegram.rs:25-32`, `send_photo` @ `:34-41`, `send_video` @ `:43-50`, `send_document` @ `:52-59`). The phase adds a fifth: `async fn send_audio(&self, chat_id, path, thread_id) -> Result<MessageResponse>` calling `self.send_file_multipart("sendAudio", "audio", chat_id, path, thread_id).await` — same shape as the existing four. The new helper is needed for the `.mp3` / `.m4a` / `.flac` / `.wav` branch of D-06.
- **D-14:** **Audio-format dispatch: `.ogg / .opus → sendVoice` (round inline bubble); `.mp3 / .m4a / .flac / .wav → sendAudio` (music-player UI).** Matches Telegram Bot API requirements (sendVoice rejects non-opus payloads). TTS pipelines that produce opus get the inline bubble matching the hermes-agent UX; arbitrary audio files get the music player.
- **D-15:** **File size pre-check before multipart upload.** Before calling `send_*` for a `MediaSource::Path`, `tokio::fs::metadata(path).await?.len()` against the per-type cap:
  - `sendPhoto` / `sendVideo` / `sendVoice` / `sendAudio`: 20 MB (public Bot API limit)
  - `sendDocument`: 50 MB
  - URL form: no pre-check (Telegram fetches; D-10 handles their rejection)
  - On oversize, **do not even try the upload**: log `warn!('media exceeds size cap: {path} {size} > {cap}')` and reinsert the tag per D-10's unified path. Saves a wasted multipart attempt.
- **D-16:** **Strictly outbound-only.** No changes to `tg_message_to_event` at `telegram.rs:362-420`. Existing inbound `Attachment` extraction for `photo` and `document` fields (`:381-396`) stays as-is; adding inbound `voice` / `video` extraction is a separate phase.

### Audio caption + adapter-trait surface

- **D-17:** **Uniform no-caption policy across all attachment types.** Even for `sendVoice`, no `caption` parameter is set. This diverges intentionally from hermes-agent §Audio Captions (which attaches plain-text captions on voice bubbles) — the unified `<MEDIA: ...>` extractor produces a cleaner protocol: surrounding text was already streamed/edited into the placeholder message via D-01, the attachment is the next message. One pattern, no per-type carve-out. Document the divergence; users who notice can ask in a follow-up phase.
- **D-18:** **New `pub trait MediaSender` in `crates/ironhermes-gateway/src/adapter.rs`** with these methods (all `async`, all returning `Result<MessageResponse>`):
  - `async fn send_photo(&self, chat_id: &str, source: &MediaSource, thread_id: Option<&str>) -> Result<MessageResponse>`
  - `async fn send_voice(&self, chat_id: &str, source: &MediaSource, thread_id: Option<&str>) -> Result<MessageResponse>`
  - `async fn send_audio(&self, chat_id: &str, source: &MediaSource, thread_id: Option<&str>) -> Result<MessageResponse>`
  - `async fn send_video(&self, chat_id: &str, source: &MediaSource, thread_id: Option<&str>) -> Result<MessageResponse>`
  - `async fn send_document(&self, chat_id: &str, source: &MediaSource, thread_id: Option<&str>) -> Result<MessageResponse>`
  - `async fn send_media(&self, chat_id: &str, media_ref: &MediaRef, thread_id: Option<&str>) -> Result<MessageResponse>` — dispatches to the correct `send_*` based on `media_ref.kind`. Default impl provided in the trait body; concrete adapters implement only the per-type methods.

  **`TelegramAdapter` implements both `PlatformAdapter` and `MediaSender`.** No other adapter implements `MediaSender` today (Discord/Slack/web do not). The media-routing code in `handler.rs` holds `Option<Arc<dyn MediaSender>>` — present when running on Telegram, `None` on other platforms (the latter skip media extraction entirely with a `warn!` log if any tag is found).
- **D-19:** **Dispatch inline in `run_agent`, sequential awaits, after final flush.** No `tokio::spawn`-and-forget, no new `TurnOutput` struct, no refactor of the 36.17.2 D-06 worker loop. The handler.rs code addition is approximately:

  ```rust
  // After stream_consumer.flush(true).await? (existing call ~line 1437)
  let media_refs = media_extractor.take_attachments();
  if !media_refs.is_empty() {
      if let Some(media_sender) = self.media_sender.as_ref() {
          for media_ref in media_refs {
              if let Err(e) = media_sender.send_media(&chat_id, &media_ref, thread_id).await {
                  warn!("attachment failed, reinserting tag: {:?} {}", media_ref, e);
                  let _ = adapter.edit_message(&chat_id, &placeholder_id, &reinsert_body).await;
              }
          }
      } else {
          warn!("media tags emitted on platform without MediaSender: {} refs dropped", media_refs.len());
      }
  }
  ```

  The full implementation handles the reinsert-body accumulation correctly (collect all failed tags, re-edit the placeholder once with the appended tag text rather than once per failure).
- **D-20:** **Three-layer test plan:**

Test cases sourced from hermes-agent's Python reference test table where applicable.

Drives `handle_with_multimodal` end-to-end with synthetic LLM responses emitting `<MEDIA: ...>` tags. Assertions:

    - `send_*` calls fire in stream order with correct `MediaKind` per extension (D-06, D-11, D-14).
    - Missing path → reinsert via `editMessageText` re-call (D-10).
    - Oversize path → reinsert without attempting `send_*` (D-15).
    - Tags inside ` ``` ` fences pass through verbatim (D-09).

  - **Live UAT runbook (`crates/ironhermes-gateway/tests/telegram_media_uat.md` — NEW file, blocking-human checkpoint):** mirrors the `tests/session_queue_telegram_uat.md` shape from 36.17.2 D-22. Scenarios:

### Claude's Discretion

- **Exact location of the `MediaTagExtractor` struct.** Either `crates/ironhermes-gateway/src/media_tag.rs` (new module, symmetric with `markdown_v2.rs` in D-04) or as a sibling type inside the existing `crates/ironhermes-agent/src/streaming_scrubber.rs` file. Recommendation: new module in the gateway crate so it has access to gateway types (`MediaRef`, `MediaSource`, `MediaKind`) without forcing those types into the agent crate.
- **Whether `MediaSource` / `MediaKind` / `MediaRef` live in `ironhermes-gateway` or `ironhermes-core`.** Gateway-only is simpler; promoting to core enables future CLI display of attachments. Recommendation: gateway-only until a second consumer materializes.
- **Whether `send_media` and the per-type methods on `MediaSender` are `async fn` (requires `async_trait`) or return `Pin<Box<dyn Future>>` directly.** The codebase already uses `#[async_trait]` on `PlatformAdapter` per `crates/ironhermes-gateway/src/adapter.rs`. Match that style.
- **Concrete name of the `send_message`-overflow-chunking MarkdownV2 path** (`stream_consumer.rs:121-128`'s "Send additional overflow chunks as new plain-text messages" branch). Today it sends plain text; D-01 implies the chunks should also render as MarkdownV2 since they're part of the final message. Open question for the planner: should every overflow chunk go MarkdownV2, or only the last (which is the natural "final" chunk)? Recommendation: every overflow chunk uses `send_message_markdown_v2` so the entire response renders consistently. Implementation requires a new `async fn send_message_markdown_v2` on `TelegramAdapter` (parallel to the existing plain `send_message` at `telegram.rs:218-236`).
- **Whether the reinsert-on-failure pattern (D-10) appends to the placeholder or sends a fresh follow-up message.** Recommendation: edit the placeholder via `editMessageText` to append the tag text (so the user's "final answer" message in their chat history is canonical and self-contained), but the planner may choose follow-up if it simplifies the reinsert-body accumulation.
