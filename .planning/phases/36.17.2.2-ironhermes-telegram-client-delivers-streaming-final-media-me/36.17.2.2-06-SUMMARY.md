**Verified anchor ordering (strict awk):**

**Dispatch block landed at handler.rs:1521-1588 with:**
1. `extractor_gw.lock().unwrap().take_attachments()` drains the accumulator.
2. If non-empty AND `self.media_sender.is_some()`:
   - Iterate refs in stream order.
   - Call `media_sender.send_media(&event.chat_id, &media_ref, None).await`. On Err: `tracing::warn!` with chat_id + kind + error, push `media_ref.original_tag_text.clone()` into `failed_tags`.
   - After the loop, if `failed_tags` non-empty: await `body_rx` (the oneshot receiver — see below), build `format!("{final_body}\n\n{appended}")`, run through `escape_outside_code_blocks`, ONE combined `adapter.edit_message_markdown_v2(...)` call. On its Err: `tracing::error!` (no recursion — single retry is plan 04's responsibility inside the adapter impl).
3. If `media_sender.is_none()`: `tracing::warn!` with chat_id + ref_count, drop refs silently per D-18.

**Reinsert-body resolution (oneshot channel chosen):**

The plan asked the executor to pick between (a) `StreamConsumer.final_body()` accessor on the consumer or (b) `tokio::sync::oneshot::channel<String>` from the consumer task to the parent. Inspection of handler.rs:1307-1356 showed:

- `let mut consumer = StreamConsumer::new(...)` at handler.rs:1310 is **moved into** `tokio::spawn(async move { ... })` at handler.rs:1311. The parent task never owns the consumer after spawn, so a direct accessor on the consumer is not reachable from the parent.
- Choice: **oneshot channel**.
  - Added `pub fn final_body(&self) -> &str { &self.buffer }` accessor on StreamConsumer (stream_consumer.rs:60-71). Cheap reader; doc-comment cites D-10.
  - Wired `let (body_tx, body_rx) = tokio::sync::oneshot::channel::<String>()` BEFORE the consumer spawn at handler.rs:1308. `body_tx` is captured by the spawn via an `Option<Sender>` wrapper.
  - On both `flush(true)` exit branches (the dual-channel branch at handler.rs:1352 and the tool-rx-closed branch at handler.rs:1368), the consumer takes the sender, calls `consumer.final_body().to_string()`, and sends. The Option-wrap prevents double-send.
  - The parent task awaits `body_rx` ONLY inside the `failed_tags` non-empty branch (zero overhead on the happy path).

### 2. Synthetic-LLM-stream injection mechanism

**Chosen mechanism: drive the production composition directly via a test-side helper that reproduces the D-19 block.**

Considered and rejected approaches:

1. **Use existing chat-completion Provider mock.** None exists. `MockProvider` at `crates/ironhermes-agent/src/memory_flush_handler.rs:52` is a `MemoryProvider`, not a chat-completion `Provider` — RESEARCH Open Q2 / Assumption A5 was confirmed by `rg -n 'impl.*Provider.*for' crates/`.
2. **Use `AgentRuntime::for_tests()`.** Exists at `crates/ironhermes-agent/src/agent_runtime.rs:583` but is gated by `#[cfg(any(test, feature = "test-support"))]` AND uses a `localhost:0` LLM client — usable from inside the `ironhermes-agent` crate's `#[cfg(test)]` blocks, but **not** from a gateway integration-test binary without enabling the `test-support` feature on `ironhermes-agent`. Even with the feature flag, `localhost:0` cannot produce streaming deltas; the test would have to mock the entire LLM round-trip.
3. **Build a `FakeStreamingProvider`.** Would require adding a `Fake` variant to `AnyClient` (`crates/ironhermes-agent/src/any_client.rs:27`) plus a closure-driven delta-stream injection seam on `AgentRuntime`. Invasive across crate boundaries.

**Pragmatic chosen mechanism:** the test feeds chunks through `scrubber → extractor` directly (the exact composition wired in `run_agent` at handler.rs:1372-1383) and then invokes a `dispatch_media_d19` helper that reproduces the production D-19 dispatch block verbatim. Tests every D-07/D-09/D-10/D-11/D-15 contract on the same code paths `run_agent` exercises, without forcing AgentRuntime surgery. The threat model accepts this trade-off (T-TEST-FAKE-PROVIDER-LEAK row).

### 3. Reinsert-body propagation: oneshot channel chosen (not StreamConsumer accessor alone)

The plan offered two valid resolutions for sourcing the post-flush body that the D-19 reinsert path needs:

| Option | Description | Verdict |
|--------|-------------|---------|
| (a) `pub fn final_body(&self) -> &str { &self.buffer }` accessor on StreamConsumer, called directly from `run_agent` after `consumer_handle.await.ok()` | The consumer is moved into the spawn at handler.rs:1311 via `async move`. After spawn, `run_agent` no longer owns it — `consumer_handle.await.ok()` returns `()`, not the consumer. So a direct accessor on the parent task's side is unreachable. | Not viable alone |
| (b) Wire `tokio::sync::oneshot::channel<String>` from the consumer task to the parent | The consumer task takes the sender (via `Option::take`) and sends `consumer.final_body().to_string()` on each `flush(true)` exit branch. Parent awaits the receiver only in the `failed_tags` non-empty branch (zero overhead on the happy path). | **Chosen** |

The accessor was still added (for clarity + so the consumer task can call `consumer.final_body().to_string()` without exposing the private buffer field). The oneshot channel is the actual propagation mechanism.
