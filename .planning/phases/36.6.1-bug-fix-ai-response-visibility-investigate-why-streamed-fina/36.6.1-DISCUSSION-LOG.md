## Area 1: Root cause scope

**Evidence provided:** Three screenshots from the live TUI:
- Screenshot 1: `/help` output visible, but "hi" agent response entirely not visible after submit.
- Screenshot 2: `/usage` command output partially visible; title shows "Chat [live]" (auto_follow=true); last 2–3 rows of the usage table cut off below viewport.
- Screenshot 3: After manual scroll down to position 253/310, full `/usage` content visible.

**Analysis:**

Code paths checked:
- `scroll_to_bottom()` (app.rs:397): sets `auto_follow = true, transcript_scroll = 0`. Correct.
- `reconcile_scroll(area)` (app.rs:419): when `auto_follow`, sets `transcript_scroll = max`. Correct.
- `transcript_max_scroll(area)` (app.rs:430): `max = total - visible`. Correct.
- `compute_transcript_area(size)` (event_loop.rs:688): mirrors 4-chunk layout from `ui.rs`. Appears correct.
- `handle_stream_event(Finished)` (app.rs:731): calls `commit_assistant_buffer()` then `scroll_to_bottom()`. Correct flow.
- i==0 prefix formula in `transcript_line_count` (app.rs:463): `(prefix_len + body_chars + width - 1) / width`. Correct — this is the Phase 21.8.3 fix.

**Decision reached:** The structural scroll logic is correct. The defect is `wrapped_line_count` and the i>0 path in `transcript_line_count` using `chars().count()` for character width. Ratatui's `Paragraph { wrap: Wrap { trim: false } }` uses word-wrap — when a word straddles a column boundary, the whole word moves to the next row. This produces ≥ rows than our character-count ceiling divide. Over a long transcript (multi-paragraph /help output, table rows), the discrepancy accumulates to 5–15+ rows, causing `max` to be too small. In the extreme case (screenshot 1), `total_computed ≤ visible_rows` → `max = 0` → viewport stuck at row 0, hiding new responses.

**Locked decision:** Fix target is `wrapped_line_count` (app.rs:956). Secondary check: confirm `compute_transcript_area` area exactly matches `frame.area()` split in `ui.rs`.
