<domain>
## Phase Boundary

Fix a bug where the ratatui TUI auto-scroll mechanism undershoots the true visual bottom after AI responses, leaving the last lines (or in severe cases the entire response) below the visible viewport. User evidence: three screenshots showing (a) a full "Hi!" response invisible after submit, (b) the last two rows of a `/usage` table cut off while the title bar shows "Chat [live]", and (c) the full content visible after manually scrolling to scroll position 253/310.

**Requirements:** No pre-existing requirement number — phase-local bug fix.

**In scope:**
- Investigate the exact discrepancy between `transcript_line_count` (character-based ceiling-divide) and ratatui's actual wrapped-row count (word-wrap)
- Fix `transcript_line_count` / `wrapped_line_count` so the computed total matches ratatui's actual render
- Verify `compute_transcript_area` in `event_loop.rs` mirrors `ui.rs` layout correctly (confirming this is not the root cause)
- Regression test — two forms (see D-02 and D-03)

**Out of scope:**
- Any TUI feature changes (overlays, pickers, skins)
- Changes to `scroll_to_bottom()` / `reconcile_scroll()` control flow — the logic is correct; only the input (line count) is suspected wrong
- Scrollbar rendering changes (formulas already landed in prior phase)

<decisions>
## Implementation Decisions

### Root cause hypothesis

- **D-01:** The auto-scroll undershoot is caused by `transcript_line_count` (in `app.rs`) returning a value lower than ratatui's actual rendered row count for the same content. The scroll machinery is structurally correct — `reconcile_scroll` with `auto_follow = true` faithfully sets `transcript_scroll = transcript_max_scroll(area)`, and `transcript_max_scroll` computes `total - visible`. The defect is that `total` (from `transcript_line_count`) is too small.

  Root cause of the undercount: **word-wrap vs character-wrap divergence.** `transcript_line_count` uses `(chars + width - 1) / width` (strict character-count ceiling division). Ratatui's `Paragraph` with `Wrap { trim: false }` performs word-wrap — when a word straddles a width boundary, the whole word is pushed to the next row, leaving the previous row short. This produces the same or more rows than character-wrap. For long natural-language output (e.g., `/help` listing many commands, `/usage` table rows), the per-line divergence accumulates: 1–2 extra ratatui rows per wrapped line × many lines = enough deficit in `transcript_max_scroll` to leave the tail of a response below the viewport. In the extreme case (screenshot 1, `total_computed ≤ visible`) `max = 0` and the viewport stays pinned to row 0, hiding the new response entirely.

  Secondary check: researcher should verify `compute_transcript_area(size)` in `event_loop.rs` (lines 688–706) produces a Rect identical to what ratatui uses in `ui.rs::render_transcript`. If the heights diverge (e.g., off by one due to rounding in the layout engine), the `visible` term in `transcript_max_scroll` would also be wrong. Current reading suggests they match, but confirmation is required.

  **Fix target:** `wrapped_line_count` (used for i > 0 lines) and the i == 0 ceiling-divide in `transcript_line_count`. The fix must align with ratatui's actual word-break semantics. Options: (a) use `unicode-width::UnicodeWidthStr` for column widths and simulate word-break logic, (b) add a per-line or per-message padding constant to over-estimate slightly (simpler but fragile), (c) use a ratatui `TestBackend` render to derive the true line count at runtime (accurate but heavy). Researcher picks the cleanest approach with evidence.

### Regression tests

- **D-02:** Unit test on `transcript_line_count` (fast, targeted): feed known multi-line text — a mix of short lines, lines that wrap, lines with prefixes that wrap — to `transcript_line_count(width)` and assert the result equals the row count ratatui actually renders for the same content via a `TestBackend` render. This test lives in `app.rs` under `#[cfg(test)]` (or the `test-support` feature gate used by existing scroll tests). It pins the formula's correctness independently of the full UI stack.

- **D-03:** TestBackend integration test on end-to-end auto-scroll (behavioral): seed `App` with a transcript long enough that `max > 0`, simulate a `StreamEvent::Finished` via `handle_stream_event`, call `reconcile_scroll(transcript_area)` where `transcript_area` is from `compute_transcript_area`, and assert `app.transcript_scroll == expected_max`. This test catches regressions in the scroll control flow (not just the count formula) and lives alongside the existing `ui.rs` snapshot tests. Both tests must pass before the phase ships.

### Claude's Discretion

- The exact fix for `wrapped_line_count` — whether to adopt `unicode-width`, simulate word-break, or another approach — is left to the researcher and planner. D-01 names the hypothesis; the researcher confirms it and selects the minimal correct fix.
- Whether the D-02 and D-03 tests are both in `app.rs` or split across `app.rs` and `ui.rs` — planner picks the cleanest location.

</decisions>

<code_context>
## Existing Code Insights

### Confirmed-correct machinery (do not change)

- `scroll_to_bottom()`, `reconcile_scroll()`, `transcript_max_scroll()` — logic is correct; only the input (`transcript_line_count`) is suspected wrong.
- `compute_transcript_area(size)` — appears to correctly mirror `ui.rs` 4-chunk layout; researcher must confirm.
- Role-prefix formula for i==0 in `transcript_line_count`: `(prefix_len + body_chars + width - 1) / width` — correctly accounts for shared first row; prior phase fixed this.

### Suspected defect site

- `wrapped_line_count(line, width)` at `app.rs:956`: `(line.chars().count() + width - 1) / width`. Uses character count, not grapheme display width, and does not account for word-break semantics. This is the primary fix target.

### Word-wrap vs char-wrap divergence (why it accumulates)

ratatui `Paragraph { wrap: Wrap { trim: false } }` uses word-wrap: if a word straddles the `width` column boundary, the entire word moves to the next row. Character-wrap fills each row to exactly `width` chars, splitting words at column boundaries. Word-wrap produces ≥ rows as character-wrap. For long-form text (multi-sentence /help output, table rows), a 1–2 row/paragraph discrepancy accumulates to 5–15 rows across a full transcript, which is enough to push `max` to 0 on a short transcript (screenshot 1) or leave several lines below the viewport on a medium transcript (screenshot 2).

### Test infrastructure already in place

- `#[cfg(feature = "test-support")]` gate used by `new_test_empty` and `new_test_with_messages`.
- `App::new_test_with_messages(vec![("assistant", "…long body…")])` constructs a seeded App.
- `TestBackend::new(80, 24)` + `terminal.draw(|f| ui(f, &app))` pattern from `ui.rs` tests.

<specifics>
## Specific Ideas

- For the D-02 unit test, a minimal reproducer: `transcript_line_count("A very long sentence that wraps at 80 chars blah blah blah blah blah blah blah blah blah", 78)` should equal the row count ratatui renders for the same span. Build a single-message App, render to TestBackend, count non-blank rows in the transcript area.

- For D-03, the structure:
  ```rust
  let mut app = App::new_test_with_messages(vec![("assistant", long_body)]);
  let area = compute_transcript_area(ratatui::layout::Size { width: 80, height: 24 });
  app.handle_stream_event(StreamEvent::Finished { total_tokens: 0 });
  app.reconcile_scroll(area);
  let max = app.transcript_max_scroll(area);
  assert_eq!(app.transcript_scroll, max, "auto-scroll must land at max");
  // Then render and verify last line visible
  ```

- The fix for `wrapped_line_count` should use `unicode_width::UnicodeWidthStr::width(line)` for the column count instead of `line.chars().count()`. Ratatui uses this internally. This closes the grapheme-width gap. For the word-wrap gap, the simplest correct approach is to use ratatui's own `LineComposer` logic — but since that's internal, a pragmatic alternative is: simulate word-wrap by iterating words and summing widths, counting a new row when a word doesn't fit. The researcher should decide between (a) using unicode-width only (fixes wide chars, doesn't fix word-wrap discrepancy), (b) full word-wrap simulation, or (c) just measuring the actual ratatui render count per message in `transcript_line_count` using a hidden TestBackend call — the last option is accurate but heavyweight for a hot path.

</specifics>
