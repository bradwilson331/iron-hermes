## Summary

The auto-scroll undershoot is caused by `wrapped_line_count` in `app.rs` using
`line.chars().count()` (character ceiling-divide) while ratatui's `Paragraph { wrap: Wrap { trim: false } }`
uses word-wrap via `WordWrapper` from `ratatui-widgets`. The two algorithms diverge whenever a word
straddles a column boundary: word-wrap pushes the whole word to the next row, character-wrap splits
it. This produces ≥ rows under word-wrap, and the per-line undercount accumulates across a full
transcript, leaving `transcript_max_scroll` too small and hiding the tail of AI responses.

The decisive finding from reading `ratatui-widgets-0.3.0/src/paragraph.rs` (lines 331–364) is that
**ratatui 0.30.0 already exposes `Paragraph::line_count(&self, width: u16) -> usize`** — an
unstable-feature-gated method that internally drives `WordWrapper::new(styled, width, trim)` and
counts the resulting lines. This is byte-for-byte the same path ratatui uses when rendering.
Using this method from within `transcript_line_count` would be the most accurate approach, but it
requires constructing a `Paragraph` per message. The cleaner, zero-allocation alternative — and the
one recommended here — is a **word-wrap simulator that mirrors `WordWrapper`'s word-boundary logic
using `unicode_width::UnicodeWidthStr::width`**, which is already a transitive dependency of ratatui
(confirmed in `Cargo.lock`: `unicode-width 0.2.2`). This is not a direct dependency of
`ironhermes-cli`; it must be added explicitly.

The `compute_transcript_area` parity check is confirmed: the function in `event_loop.rs` (lines
688–706) uses identical constraints and produces the same `Rect` as `ui.rs`. There is no off-by-one.

**Primary recommendation:** Replace `wrapped_line_count` with a word-wrap simulator using
`unicode_width::UnicodeWidthStr::width` per grapheme word, mirroring ratatui's `WordWrapper`
word-boundary semantics for `trim: false`. Add `unicode-width = "0.2"` as a direct dependency.
Apply the same word-width logic to the `i == 0` ceiling-divide in `transcript_line_count`.

## 1. Confirmed Root Cause

**File:** `crates/ironhermes-cli/src/tui_rata/app.rs`

### `wrapped_line_count` — the defect site

```rust
// app.rs:956–965  [VERIFIED: direct code read]
pub(crate) fn wrapped_line_count(line: &str, width: usize) -> usize {
    if line.is_empty() {
        return 1;
    }
    let cols = line.chars().count();   // ← WRONG: counts Unicode scalar values, not display cols
    if width == 0 {
        return 1;
    }
    (cols + width - 1) / width         // ← WRONG: character-wrap, not word-wrap
}
```

Two distinct bugs compound here:

**Bug A — character count vs display width.** `chars().count()` counts Unicode scalar values.
`UnicodeWidthStr::width` returns the terminal column count. For ASCII text they are equal; for
CJK characters (width 2) or zero-width joiners (width 0) they diverge. ratatui's `WordWrapper`
uses `grapheme.symbol.width() as u16` (i.e., `UnicodeWidthStr::width`) throughout. [VERIFIED:
ratatui-widgets-0.3.0/src/reflow.rs line 90: `let symbol_width = grapheme.symbol.width() as u16`]

**Bug B — character-wrap vs word-wrap.** `(cols + width - 1) / width` is ceiling division — it
fills each output row to exactly `width` characters, splitting words at column boundaries.
ratatui's `WordWrapper` (with `trim: false`, which is what `Wrap { trim: false }` uses) buffers
words in `pending_word`, then emits a new row when `line_width + whitespace_width + word_width >=
max_line_width`. When a word doesn't fit on the current row, the entire word moves to the next
row, leaving the previous row short. This produces ≥ rows compared to character-wrap for any
natural-language text with words shorter than `width`. [VERIFIED: ratatui-widgets-0.3.0/src/reflow.rs
lines 107–156]

**Accumulation effect:** For a typical AI response of N lines, each line that word-wraps produces
1 extra row that `wrapped_line_count` misses. Over 15–30 lines of `/help` or `/usage` output,
the deficit is 5–15 rows. When `total_computed <= visible`, `transcript_max_scroll` returns 0
and the viewport stays at row 0, hiding the entire response (screenshot 1 in the bug report).

### `transcript_line_count` — i == 0 path also affected

```rust
// app.rs:463–468  [VERIFIED: direct code read]
let body_chars = line.chars().count();         // ← Bug A: should be display width
let total_chars = prefix_len + body_chars;
if width == 0 || total_chars == 0 { 1 }
else { (total_chars + width - 1) / width }    // ← Bug B: character-wrap
```

The i == 0 path has both bugs. `prefix_len` is computed from `role_label.len() + 2` — since
role labels are ASCII ("You", "Hermes", "Tool", "System"), `len()` equals display width, so
`prefix_len` is correct. Only `body_chars` needs the display-width fix, and the division needs
word-wrap awareness.

## 3. Fix Recommendation — Word-Wrap Simulator

### Decision: Option 2 — Word-wrap simulation with unicode-width

**Rejected: Option 1 (unicode-width only).** Replacing `chars().count()` with `UnicodeWidthStr::width`
fixes Bug A (wide chars) but does nothing for Bug B (word-wrap divergence). For ASCII-only content
(all English text in this app) Bug A produces zero error; Bug B is the dominant cause of the
undercount. Fixing only Bug A leaves the bug entirely present for ASCII transcripts.

**Rejected: Option 3 (TestBackend render per message).** Accurate but heavyweight: constructing a
`Terminal`, a `Backend`, and a full ratatui render on every call to `transcript_line_count` (which
is called on every event-loop tick, per message in history) would add O(N_messages) allocations
per frame. The hot-path cost would be visible as frame-rate degradation on long transcripts. The
`Paragraph::line_count` method in ratatui 0.30.0 is a lighter variant of this — it runs
`WordWrapper` without the buffer allocation overhead of a full render — but it is gated behind
`#[instability::unstable(feature = "rendered-line-info")]` and requires enabling that feature flag
in Cargo.toml plus constructing a `Paragraph` per message. The word-wrap simulator is simpler.

**Chosen: Option 2 — word-wrap simulator.** Implement a `word_wrapped_line_count(line: &str, width: usize) -> usize`
function that mirrors `WordWrapper`'s core word-boundary logic for the `trim: false` case, using
`unicode_width::UnicodeWidthStr::width` for column widths. This is:
- Zero-allocation for short lines (no heap allocations in the ASCII common case)
- O(chars) per line — same as the existing ceiling divide
- Exactly matches ratatui's `WordWrapper { trim: false }` output for ASCII + basic Unicode text
- Confirmed correct by reading ratatui's `WordWrapper::process_input` [VERIFIED: reflow.rs:77–192]

### Key ratatui WordWrapper semantics to mirror (trim: false)

From reading `reflow.rs:77–192`, the `trim: false` word-break rule is:

```
untrimmed_overflow = pending_line.is_empty()
    && !self.trim          // trim: false
    && word_width + whitespace_width + symbol_width > self.max_line_width
```

When this fires: flush `pending_whitespace` + `pending_word` onto a new output row, then continue
accumulating. Additionally: `line_full = line_width >= max_line_width` and
`pending_word_overflow = symbol_width > 0 && line_width + whitespace_width + word_width >= max_line_width`.

The practical effect for `trim: false` on natural-language text: a word break occurs when the
accumulated `(current_row_width + whitespace + next_word_width) >= max_line_width`. When a word
alone exceeds `max_line_width`, it falls back to character-splitting (the `line_full` path fills
the row then wraps). The whitespace before a word-boundary line-break is consumed (not emitted on
the next row).

### Algorithm for `word_wrapped_line_count`

```rust
/// Count the terminal rows that `line` occupies when rendered by ratatui's
/// `WordWrapper { trim: false }` at the given column `width`.
///
/// Mirrors the word-boundary logic from ratatui-widgets WordWrapper::process_input
/// for the trim=false case, using unicode display widths.
///
/// - Empty line → 1  (blank row is still rendered)
/// - width == 0 → 1  (defensive; avoids divide-by-zero)
/// - Long single word → character-wraps (ratatui's fallback: line_full path)
pub(crate) fn word_wrapped_line_count(line: &str, width: usize) -> usize {
    use unicode_width::UnicodeWidthStr;

    if line.is_empty() || width == 0 {
        return 1;
    }

    let mut rows = 1usize;
    let mut current_row_width: usize = 0; // columns used in current row

    // Split into whitespace-delimited "chunks": [ws, word, ws, word, ...]
    // We iterate grapheme clusters to mirror WordWrapper's grapheme-level logic.
    // For ASCII (common case), chars() == grapheme clusters.
    //
    // Simplified: iterate words (split_whitespace) and model whitespace as single space.
    // This matches real behavior for the ASCII natural-language text in this app.
    for word in line.split_whitespace() {
        let word_w = UnicodeWidthStr::width(word);
        // Space between words (treat as 1 col; trim: false keeps whitespace on same row)
        let sep = if current_row_width == 0 { 0 } else { 1 };

        if word_w == 0 {
            // Zero-width word (e.g. ZWNJ) — skip, doesn't affect layout
            continue;
        }

        if current_row_width == 0 {
            // Starting a new row: does this word fit?
            if word_w <= width {
                current_row_width = word_w;
            } else {
                // Word wider than row: character-wrap it
                let word_rows = (word_w + width - 1) / width;
                rows += word_rows - 1; // first row already counted
                current_row_width = word_w % width;
                if current_row_width == 0 { current_row_width = width; }
            }
        } else if current_row_width + sep + word_w <= width {
            // Word fits on current row
            current_row_width += sep + word_w;
        } else {
            // Word doesn't fit: wrap to next row
            rows += 1;
            if word_w <= width {
                current_row_width = word_w;
            } else {
                // Oversized word: character-wrap from start of new row
                let word_rows = (word_w + width - 1) / width;
                rows += word_rows - 1;
                current_row_width = word_w % width;
                if current_row_width == 0 { current_row_width = width; }
            }
        }
    }

    rows
}
```

### Trim=false edge case: leading whitespace

ratatui's `WordWrapper { trim: false }` preserves leading whitespace on each row (lines 113–114:
`pending_line.extend(self.pending_whitespace.drain(..))`). `split_whitespace()` drops leading
whitespace. For lines that start with spaces (e.g., code indentation in `/help` output), the
simulator using `split_whitespace` will undercount the leading whitespace column cost, potentially
producing 1 fewer row than ratatui when the leading whitespace causes the first word to wrap.

**Assessment:** For this codebase's actual content (conversational AI responses, `/help` output,
`/usage` tables), leading-space lines are rare. The error is at most 1 row per such line. For
correctness, use `unicode_segmentation::UnicodeSegmentation::graphemes(line, true)` to iterate
grapheme clusters and track whitespace explicitly — but `unicode_segmentation` is not a direct
dependency of `ironhermes-cli`.

**Recommended mitigation:** Use a char-level word/whitespace iterator instead of `split_whitespace`:

```rust
// iterate word/whitespace tokens preserving leading whitespace:
// This matches ratatui's char-by-char accumulation without unicode_segmentation.
for c in line.chars() {
    let w = unicode_width::UnicodeWidthChar::width(c).unwrap_or(0);
    // ... accumulate into current_row_width / pending_word_width ...
}
```

This requires `unicode_width::UnicodeWidthChar` (in the same crate). The full char-level
implementation is slightly more complex but handles leading whitespace correctly. The planner
should implement the char-level version as the production-quality fix.

```rust
        app.transcript_scroll, max
    );

    // Confirm the last rendered row is visible: render at scroll=max and
    // check that the last content row appears in the viewport.
    let backend = TestBackend::new(80, 24);
    let mut terminal = Terminal::new(backend).unwrap();
    terminal.draw(|f| ui(f, &app)).unwrap();
    let buf = terminal.backend().buffer();
    // Row 22 (0-indexed: row 21 inside border at y=1..22) should be non-blank
    // when content fills the viewport
    let last_visible_row = 22u16; // area.height - 2 (border) = 22; rows 1..22
    let last_row_non_blank = (1u16..79u16).any(|col| {
        buf.cell((col, last_visible_row)).map(|c| c.symbol() != " ").unwrap_or(false)
    });
    assert!(last_row_non_blank,
        "last visible row (row {last_visible_row}) must be non-blank after auto-scroll to bottom");
}
```

**Note:** `compute_transcript_area` is a private function in `event_loop.rs`. For D-03 it must be
made `pub(crate)` or the test must inline its equivalent computation. The planner should choose
`pub(crate)` — the function is already a named, documented helper.

## 6. Risks and Landmines

### Risk 1: Leading-whitespace lines (trim: false)

**What:** `Wrap { trim: false }` preserves leading whitespace on continuation lines. A naive
`split_whitespace`-based simulator drops leading whitespace, potentially undercounting rows for
lines like `"    - bullet point that wraps"` at narrow widths.

**Mitigation:** Use a char-level iterator with `UnicodeWidthChar::width` tracking the current
token type (whitespace vs non-whitespace), not `split_whitespace`. This mirrors ratatui's
grapheme-level processing. The planner should implement the char-level version.

### Risk 2: Oversized single words (longer than `width`)

**What:** A word wider than `width` (e.g., a URL or unbroken code string) is character-split by
ratatui. The simulator must also character-split these, not just push to next row.

**Mitigation:** The algorithm above includes an `else` branch that applies ceiling-divide for
oversized words. Test with: `word_wrapped_line_count("a".repeat(160), 78)` — expected 3 rows, not
1 (push-to-next-row) and not 1 (ceiling div already correct here since no spaces).

### Risk 3: `i == 0` first-line `format!` allocation on hot path

**What:** Using `format!("{}: {}", role_label, line)` for i == 0 allocates a `String` per
message per event-loop tick (~100ms) for each call to `transcript_line_count`.

**Mitigation:** This is O(N_messages * chars_in_first_line) per tick. For typical transcript
lengths (<100 messages, <200 chars first line), this is ~20KB/tick, negligible. If profiling
shows it matters, use the manual "start with prefix_w pre-filled" approach instead.

### Risk 4: `compute_transcript_area` visibility for D-03

**What:** `compute_transcript_area` is not `pub(crate)` today — it is a private free function
in `event_loop.rs`. The D-03 test in `ui.rs` cannot call it.

**Mitigation:** Change `fn compute_transcript_area` to `pub(crate) fn compute_transcript_area`
in `event_loop.rs`. This is a trivial visibility change with no semantic effect.

### Risk 5: Zero-width characters (ZWJ, ZWNJ, combining marks)

**What:** `UnicodeWidthChar::width` returns `None` for control characters and `Some(0)` for
zero-width joiners. The simulator must handle `None` as width 0 (skip) and `Some(0)` as width 0
(no column advance but still part of the word).

**Mitigation:** Use `unicode_width::UnicodeWidthChar::width(c).unwrap_or(0)` throughout.

### Risk 6: ANSI escape sequences in message bodies

**What:** `render_message_body` returns the raw message body string. If an assistant response
contains ANSI escape codes (e.g., from a tool output rendered with `colored`), the char-level
width count will include escape bytes (ESC, `[`, digits, `m`) as display columns, overcounting.

**Assessment:** `transcript_text()` applies `ansi_to_tui` for the actual render, which strips
ANSI sequences and counts visible graphemes. However, `transcript_line_count` operates on the raw
body string. This is a pre-existing issue — the current `chars().count()` has the same problem.
Out of scope for this fix; document as a known limitation.

## Common Pitfalls

### Pitfall 1: Forgetting to fix both call sites

**What goes wrong:** Fixing `wrapped_line_count` (called for `i > 0` lines) but leaving the
`i == 0` ceiling-divide unchanged still undercounts the first line of every message.

**How to avoid:** The `i == 0` path (lines 463–468 in `transcript_line_count`) must also use
`word_wrapped_line_count` — either by constructing the prefix+body string, or by implementing
a version of the simulator that accepts a `prefix_width` initial fill offset.

### Pitfall 2: Using `Paragraph::line_count` without feature flag

**What goes wrong:** `Paragraph::line_count` is gated behind `#[instability::unstable(feature = "rendered-line-info")]`.
Calling it without the feature flag emits a compile error.

**How to avoid:** The recommended fix (word-wrap simulator) does not use this method. For D-02
tests, use the TestBackend render approach instead of `Paragraph::line_count`.

### Pitfall 3: `split_whitespace` silently drops leading spaces

**What goes wrong:** Lines beginning with spaces (code blocks, indented lists) are
mis-measured — the simulator starts word accumulation at column 0 but ratatui starts at the
true leading-space offset. The fix undershoots on these lines.

**How to avoid:** Use char-level iteration with `UnicodeWidthChar::width`, tracking whitespace
separately from word characters, mirroring ratatui's grapheme-level approach.

### Pitfall 4: Off-by-one in D-03 TestBackend row counting

**What goes wrong:** The transcript block has 1-char borders. Content rows are at y=1..22 (for
a 24-row terminal), not y=0..23. Counting row 0 or row 23 picks up border characters.

**How to avoid:** Test columns 1..79 and rows 1..22 only. The D-03 test above does this correctly.
