# Phase 36.17.2: unify session queue — replace UserQueueManager mpsc buffer with SessionQueue - Context

**Gathered:** 2026-05-27
**Status:** Ready for planning
**Trigger:** Live Telegram UAT of 36.17.1-05 confirmed the busy-branch enqueue + post-turn `drain_pending` are dead code on the Telegram path. See `36.17.1-05-SUMMARY.md` and the conversation log immediately preceding this phase's creation.

<domain>
## Phase Boundary

Make 36.17.1's `SessionQueue` reachable in production Telegram by collapsing `UserQueueManager`'s per-chat `mpsc` buffer into `SessionQueue`. After 36.17.2, `SessionQueue` is the single source of truth for buffered messages on every chat across every gateway-routed platform (Telegram now; Discord/Slack/webhook on whatever flows through `UserQueueManager::dispatch` already).

Out of scope:
- The `/queue` slash command (lands in 36.17.1-03, untouched).
- The `is_draining` flag + `drain_for_restart` (lands in 36.17.1-04, untouched).
- The cap-hit ❌ + chat-reply UX in the gateway handler (lands in 36.17.1-02; preserved unchanged).
- `/new` + `/reset` queue-clear ordering (lands in 36.17.1-03 — `SessionQueue::clear` BEFORE `session_store.remove`).
- Discord/Slack/web/REST platform parity — phases per the original 36.17.1 D-02 deferral list. They auto-inherit the unified path through `UserQueueManager::dispatch`.
- Photo-burst slot-collision logic (was OUT in 36.17.1 D-05; still OUT).

The phase ships a behavior-equivalent replacement of UQM's internal queueing with no observable user-facing change *except*:
1. The 👁 transport reaction now fires **when the worker pops the message and begins its turn**, not when `dispatch` lands it on the queue. This is the user-visible improvement that justifies the architectural churn — 👁 reflects actual processing, never buffer occupancy.
2. Cap-hit on `dispatch` (queue full) bubbles a 429-class signal to the transport layer instead of silently replacing the worker (current UQM behavior at `user_queue.rs:80-93`).

</domain>

<root_cause>
## Root Cause Surfaced in 36.17.1 UAT

The 36.17.1 implementation added a busy-branch enqueue inside `handle_with_multimodal` (handler.rs:980-983, 1516-1517) and a post-turn `drain_pending` call inside the per-chat worker (runner.rs:999-1013). Both code paths are correct in isolation — proven by 9/9 passing integration tests in `tests/session_queue_integration.rs`. But they are **unreachable in the production Telegram dispatch architecture**:

```
TG long-poll → dispatch_future → user_queue_dispatch.dispatch(event)
                                          ↓
                                  per-chat chat_rx (mpsc, UQM-owned)
                                          ↓
                                  worker_task.spawn → loop:
                                          ↓
                                  chat_rx.recv()  ← messages 2..N wait here
                                          ↓
                                  handler.handle_with_multimodal(event)
                                          ↓ (agent_running = false at entry)
                                  run_agent (RAII guard flips agent_running)
                                          ↓
                                  drain_pending(session_key, …) — queue is empty
```

The per-chat worker is **strictly serial**. While the worker is in `handle_with_multimodal`, messages 2..N for the same chat sit in `chat_rx` (UQM's `mpsc::Receiver`). They never see `agent_running == true` at `handle_with_multimodal` entry because by the time the worker pops them, the previous turn's `RunningAgentGuard` has dropped (`run_agent` returned), so `agent_running` is back to `false`. The busy-branch enqueue logic in `handler.rs:980` is therefore unreachable from the Telegram path. `drain_pending` is called after every turn but always finds an empty queue.

The integration tests pass because they synthesize parallel `handle_with_multimodal` calls directly against the handler — production never does that.

</root_cause>

<decisions>
## Implementation Decisions (LOCKED by user 2026-05-27)

### Architecture

- **D-01:** Target architecture is **option (C) — Unified Queueing**. `SessionQueue` is the single source of truth for per-chat buffered messages. `UserQueueManager`'s internal `mpsc::Sender`/`Receiver` per chat is removed entirely.
- **D-02:** `UserQueueManager` keeps its **public surface** (`new`, `dispatch`, `remove`) and ownership relationship (one instance per `GatewayRunner`, owns `Arc<dyn PlatformAdapter>`). Only its **internals** change. Callers in `runner.rs` continue to call `user_queue_dispatch.dispatch(event, text_prefix, image_data_uri)` and `queue_task.remove(&chat_id_task)` with identical signatures. Phase is a pure refactor at the call-site level.
- **D-03:** `UserQueueManager::dispatch` rewrites internally to push directly into the runner's `SessionQueue` via `runner.try_enqueue(&session_key, queued_event)`. UQM holds an `Arc<SessionQueue>` clone at construction time (passed in via `new`) — it does NOT hold an `Arc<GatewayRunner>` to avoid the circular ownership shape (runner owns UQM owns runner). The thin API `try_enqueue` from 36.17.1-02 is sufficient.

### Worker Loop

- **D-04:** The per-chat worker loop (`runner.rs:958-1024`) rewrites to **poll `SessionQueue::pop` directly**. The current `while let Some(queued_msg) = chat_rx.recv().await` pattern becomes a `SessionQueue::pop`-driven loop with explicit signaling for "queue is empty, sleep / exit" (see D-05).
- **D-05:** Worker shutdown signal: the worker exits its loop when (a) `cancel_token.is_cancelled()` returns true, OR (b) `SessionQueue::pop(&session_key)` returns `None` AND a separate per-chat **idle signal** indicates no further pushes are expected. The simplest correct mechanism is a **per-chat `tokio::sync::Notify`** owned by `UserQueueManager`, signaled by `dispatch` on every successful push. The worker waits via `Notify::notified()` when the queue is empty, then re-polls. When `remove(&chat_id)` is called (worker is exiting), the Notify is dropped so any pending `notified()` future cancels via channel-close semantics.
- **D-06:** The worker's per-iteration sequence is:
  1. `event = session_queue.pop(&session_key)` (sync, releases the mutex immediately)
  2. If `None`: `notify.notified().await` with `tokio::select!` on `cancel_token.cancelled()` — exit if cancelled, else loop back to step 1.
  3. If `Some(event)`: emit the 👁 transport reaction (`add_reaction(chat_id, message_id, "👁")` via `Arc<dyn PlatformAdapter>`), then call `handler.handle_with_multimodal(event, adapter, cancel_token.child_token(), processed_attachments)`.
  4. After `handle_with_multimodal` returns: log Err if any, then loop back to step 1 (do **not** drop the worker — the next pop attempts to drain anything that arrived during the turn).
- **D-07:** The post-turn `drain_pending` helper from 36.17.1-02 becomes **redundant** under D-06 — the worker's natural pop loop already drains every event that arrived during the turn, one full turn at a time, in FIFO order. The `drain_pending` call at runner.rs:999-1013 is **removed** in this phase. `GatewayRunner::drain_pending` itself is retained as a pub-crate API for the integration test (it is harmless when the queue is empty, and other code paths may still want it).

### Reaction Accuracy

- **D-08:** The 👁 transport reaction emission **moves from `dispatch` to the worker** (D-06 step 3). At `dispatch` time the message is unprocessed; emitting 👁 there would falsely signal "agent is looking at this" while the message is still in the buffer behind earlier events. The worker emits 👁 immediately before calling `handle_with_multimodal`, which means the user sees the reaction exactly when the agent begins its turn on that specific message.
- **D-09:** 👁 emission failure is logged at `warn` level and ignored (matches current UQM behavior at `user_queue.rs:70-72`). It must not block the turn — a transient Telegram API error on the reaction call must not poison the user's actual message.

### Strict Backpressure

- **D-10:** `UserQueueManager::dispatch` returns a **`Result<DispatchOutcome, QueueError>`** signature (or equivalent — Claude's discretion on exact shape). The outcome variants are:
  - `Ok(DispatchOutcome::Accepted)` — message landed on the queue, worker will pick it up.
  - `Ok(DispatchOutcome::WorkerSpawned)` — message landed on the queue AND a new worker must be spawned (first message for this chat, or after `remove`). Caller spawns the worker.
  - `Err(QueueError::CapacityReached { … })` — `SessionQueue::try_push` returned cap-hit. Caller (the Telegram dispatch loop in `runner.rs`) is responsible for the 429-class user-facing UX. **NOTE:** the existing 36.17.1-02 cap-hit UX is already implemented inside `handle_with_multimodal` (handler.rs:980 path). That path will no longer be reachable from dispatch under D-04 (messages never reach `handle_with_multimodal` until the worker pops them), so the cap-hit UX **must migrate to the dispatch path** — either inside `UserQueueManager::dispatch` itself (so all transports get it for free) or in the per-platform dispatch loop. D-11 chooses.
- **D-11:** Cap-hit UX **lives in `UserQueueManager::dispatch`**. When `try_push` returns `CapacityReached`, UQM fires the ❌ reaction + "⏳ Queue is full (128 messages). Wait for the agent to drain before sending more." chat reply via its owned `Arc<dyn PlatformAdapter>`, then returns `Err(QueueError::CapacityReached)`. The per-platform dispatch loop in `runner.rs` does NOT need to handle the reply — UQM has the adapter and the message metadata already. Telegram offset advance happens unconditionally in `runner.rs:513-519` (Pitfall 6) before dispatch — cap-hit cannot cause re-delivery.
- **D-12:** HTTP-arrival platforms (future webhook/REST adapter, Discord/Slack when they flow through `UserQueueManager`) inherit the same `Err(QueueError::CapacityReached)` signal at the dispatch boundary and respond with **HTTP 429 + `Retry-After: 5`** at the network edge. The dropped payload never enters core domain logic.

### SessionKey Construction

- **D-13:** `UserQueueManager` keys its internal state by **full `SessionKey` (platform + chat_id + user_id)**, not by `chat_id`-string alone (current shape at `user_queue.rs:24`). This matches `SessionQueue`'s keying (Pitfall 7) and prevents cross-user collision when two users DM the same bot from the same `chat_id`-namespace (e.g., group chats). `UQM::new`, `dispatch`, and `remove` rewrite to take/return `SessionKey` where the current shape uses `String`. The `chat_id_task` variable at `runner.rs:950` becomes `session_key_task`.
- **D-14:** `SessionKey` is constructed at `dispatch` entry using `SessionKey::new(event.platform.clone(), &event.chat_id).with_user(&event.sender_id)`. This matches the existing construction at `runner.rs:994-998` (which builds the drain-pending key) and at `handler.rs:946-948` (which builds the RAII running-agent guard key). One pattern, three call sites — all use the full triple.

### Lifecycle

- **D-15:** Worker spawn is **still triggered by `dispatch`** returning `DispatchOutcome::WorkerSpawned`. The dispatch loop in `runner.rs:943-1025` rewrites to spawn the worker on the new outcome variant. The worker continues to live in `worker_join_set` for shutdown tracking (Plan 03 from 22.4.2.1).
- **D-16:** Worker exit conditions remain the same: cancellation token fired OR queue is empty AND no further pushes expected (D-05 Notify-based wait). On exit, the worker calls `user_queue_manager.remove(&session_key)` to clear UQM's internal state. The post-`remove` next-dispatch for the same SessionKey re-creates everything (worker + notify + state) idempotently.
- **D-17:** **Queue persistence across worker exits is undefined behavior in this phase.** If the worker exits because the queue is empty, and then a new message arrives, UQM creates a fresh worker. If the worker exits because the cancellation token fired (shutdown), the queue is preserved by `drain_for_restart`'s `is_draining=true` semantics (locked in 36.17.1-04 D-03) — but the worker is gone, so nobody drains. Phase 36.17.2 does NOT change this; the in-process drain window from 36.17.1-04 already covers "messages preserved during the cancel-but-before-process-exit gap" and the gateway-restart-recovery story stays the same. **If post-restart drain becomes desirable, that's a separate future phase.**

### Concurrency + Mutex Hygiene

- **D-18:** `UserQueueManager` retains a `tokio::sync::Mutex` (it crosses `.await` for the `dispatch` map lookup). `SessionQueue` retains its `std::sync::Mutex` (no await crossings inside critical sections — D-17 from 36.17.1). The `MutexGuard` from `SessionQueue::try_push` MUST drop before any `.await` call in UQM (Pitfall 2 from 36.17.1) — the compiler enforces this since `std::sync::MutexGuard` is `!Send`.
- **D-19:** The per-chat `tokio::sync::Notify` instances live in UQM's internal map keyed by `SessionKey`. Cloning the `Arc<Notify>` out of the locked map before signaling is required so the signal happens after the mutex is dropped (avoid notifying under lock).

### Test Strategy

- **D-20:** All 9 existing integration tests in `tests/session_queue_integration.rs` MUST continue to pass unchanged. They directly exercise `handler.handle_with_multimodal` and `runner.drain_pending`; both stay callable in this phase. The handle_with_multimodal busy-branch code path (handler.rs:980, 1516) is **kept** as a defensive fallback for any caller that doesn't go through UQM (e.g., test drivers, future direct-handler invocations) — it's no longer the production hot path but it's not actively wrong.
- **D-21:** A new integration test `tests/uqm_session_queue_unification.rs` exercises the production path end-to-end: synthesize 5 Telegram updates for the same chat in tight succession against a `UserQueueManager` wired to a test `RecordingPlatformAdapter`; assert that exactly one 👁 reaction fires per message and that the 5 messages are processed in FIFO arrival order through `handle_with_multimodal`. This is the test that would have caught the 36.17.1 unreachability bug.
- **D-22:** A live Telegram UAT runbook MUST be produced and gated as a `checkpoint:human-verify` task — same shape as `tests/session_queue_telegram_uat.md` from 36.17.1-05, but for the unified path. Scenarios: (a) burst 5 messages while busy → all 5 process in FIFO with 👁 firing on each at the moment of pop, not on dispatch; (b) cap-hit at 128 → ❌ + chat reply from `dispatch`; (c) `/new` clears queue mid-burst — remaining un-popped events are dropped, no replay; (d) shutdown + restart → in-process drain window from 36.17.1-04 still preserves queue (no new behavior, sanity check).

### Slash-Command Fast-Path (added 2026-05-27 after UAT bug surface)

A second UAT finding (`/queue` typed during a busy turn was held for ~90s by the per-chat worker before its agent loop even started) confirmed that the unification done in D-01..D-22 fixes free-text burst handling but does NOT fix slash-command latency. Commands still serialize behind queued free-text events because the worker pops one entry at a time and runs each through `handle_with_multimodal` — including commands. Per the user, slash commands MUST short-circuit without entering the SessionQueue + worker pipeline at all.

- **D-23:** **Slash commands bypass UserQueueManager entirely.** When the dispatch loop (`runner.rs:874-1028`) sees `event.content.starts_with("/")`, the event is **not** routed through `UserQueueManager::dispatch`. It is dispatched on a separate fast-path that invokes `handler.handle_with_multimodal(event, adapter, cancel.child_token(), empty_attachments).await` **inline from the dispatch task itself**, OR spawned into a dedicated short-lived `tokio::spawn` if the inline-await would block the dispatch loop from accepting the next platform update (recommended: `tokio::spawn` so the dispatch loop never blocks). The fast-path target is the same `GatewayMessageHandler` shared with the queue+worker path; only the routing differs.
- **D-24:** **Command-content detection is `event.content.starts_with("/")`.** Strict prefix match, no whitespace trimming (matches existing command parser behavior at `handler.rs:411`). Anything that isn't a slash command falls through to UQM.dispatch. Group chats already require `@mention` matching at `runner.rs:914-921` BEFORE dispatch is called, so the fast-path inherits that filter.
- **D-25:** **Ordering semantics — commands are observably out-of-band relative to queued free-text events.** A `/queue` typed between free-text msg1 (in-flight) and msg2 (queued) may execute concurrently with msg1's agent turn. The user-visible contract: commands respond promptly (sub-second after dispatch); free-text events queue in arrival order. This matches the hermes-agent Python reference where command-bypass and `_queued_events` are separate code paths (`gateway/run.py` §2304-2415 vs the command dispatcher at §1850+).
- **D-26:** **State-mutation safety of concurrent commands is already covered** by the existing thread-safe primitives: `SessionQueue` uses `std::sync::Mutex` (D-16 from 36.17.1); `SessionStore` uses `tokio::sync::RwLock`; `running_agent` flag is `Arc<AtomicBool>`. The fast-path adds no new shared-state hazards. The single subtle interaction is `/new` clearing the SessionQueue mid-burst: the worker may be mid-pop on a freshly-cleared queue, in which case `pop` returns `None` and the worker loops back to `notify.notified().await` — correct by inspection. Plan 03 adds a regression test for "`/new` clears queue mid-burst, worker idles without panicking, subsequent dispatch resumes normally."
- **D-27:** **Plan 05 scope (new):** Add the command fast-path. Modify the dispatch loop in `runner.rs` to branch on `event.content.starts_with("/")` BEFORE the `UQM.dispatch(...)` call, routing slash commands into a `tokio::spawn(async move { handler.handle_with_multimodal(...).await })` on the dispatch thread. The spawned task is detached (no `worker_join_set` membership — commands are short-lived; the existing graceful-shutdown drain at `runner.rs:1159-1170` handles the in-flight-when-cancelled case by setting `is_draining=true` which the command's handler eventually observes via `cancel.is_cancelled()`). Add an integration test in `tests/uqm_session_queue_unification.rs` that dispatches `/queue interrupt this` while a free-text turn is in flight on the same chat, asserts the `/queue` response is observable before the in-flight turn completes, and asserts the synthesized event is pushed into SessionQueue. Add live UAT Scenario 7 to `tests/session_queue_telegram_uat.md` for cap-hit-with-/queue-mid-burst.

### Threat Model Addendum

- **T-36.17.2-05 (command-vs-queue race):** A `/new` slash command racing with a queued free-text event could lose track of which events were intended to survive the clear. **Mitigation:** SessionQueue's mutex serializes `try_push` and `clear` against the worker's `pop`. `/new`'s clear-BEFORE-store.remove ordering (Pitfall 5 from 36.17.1) is preserved. Plan 03 + Plan 05 test cases cover the race.
- **T-36.17.2-06 (command storm bypass-amplifies):** A user typing 100 slash commands in 1 second would spawn 100 detached tasks each calling `handle_with_multimodal`. **Mitigation:** Existing per-chat semaphore (`semaphore_dispatch`, `runner.rs:947`) was applied in the worker spawn but NOT in the fast-path. Plan 05 must wire the same `Arc<Semaphore>` permit into the spawned task before calling `handle_with_multimodal` — preserves the bounded-concurrency invariant from Phase 22.4.2.1 TG-06.

### Claude's Discretion

- Exact name of the `DispatchOutcome` enum and variant casing.
- Exact placement of UQM's internal notify map — separate `HashMap<SessionKey, Arc<Notify>>` vs. consolidating with the worker-presence tracking.
- Whether to expose `UserQueueManager::queue_len(&session_key)` as a debugging hook (the runner already has `runner.queue_len(&key)` from 36.17.1-02; UQM wrapper is optional sugar).
- Internal organization: keep `user_queue.rs` single-file vs. split into `user_queue/mod.rs` + `user_queue/notify.rs`.
- Whether the 👁 reaction emission is `tokio::spawn`'d (fire-and-forget, matches current line 69) or awaited inline before `handle_with_multimodal`. Inline is more correct for "👁 = agent has begun"; fire-and-forget is what UQM does today. **Recommendation:** await inline; the user sees 👁 at exactly the moment of processing start, and a transient reaction-API stall delays the placeholder `█` send by the same amount (which is fine — it's the same network).

<threats>
## Threat Model

Inherited from 36.17.1:
- T-36.17.1-01 (CapacityReached invariant) — preserved by D-11. Cap-hit UX migrates from handler to dispatch but the 128-cap on SessionQueue is unchanged.
- T-36.17.1-02 (cross-session collision via partial SessionKey) — preserved by D-13/D-14 (UQM keys by full SessionKey).
- T-36.17.1-03 (lost-update during drain mode) — unchanged. 36.17.1-04's `is_draining`+`drain_for_restart` are not touched.

New in 36.17.2:
- **T-36.17.2-01 (worker-exit/dispatch race):** A message arrives at `dispatch` just as the previous turn's worker is mid-exit (queue was empty, worker is calling `remove(&session_key)`). If `dispatch`'s `try_push` succeeds AFTER the worker has already exited but BEFORE `remove` completes, the new message lands on a queue with no consumer. **Mitigation:** UQM's internal mutex serializes `dispatch` and `remove` against each other. `dispatch` re-checks the senders/notify map after acquiring the lock and spawns a fresh worker if needed. The `senders.lock().await` pattern at `user_queue.rs:51` is the existing template.
- **T-36.17.2-02 (Notify lost-wakeup):** If `dispatch` signals `notify_one()` before the worker reaches `notify.notified().await`, the worker's next `notified()` call still receives the wake (`Notify` semantics: a permit is retained when no one is waiting). Verified by tokio docs. No mitigation needed; documented for awareness.
- **T-36.17.2-03 (👁 reaction spurious during cancellation):** Worker pops an event, emits 👁, then the cancellation token fires before `handle_with_multimodal`. The user sees 👁 for a message that never gets processed. **Mitigation:** Acceptable. The window is microseconds; the user-visible artifact is identical to the existing "agent crashed mid-turn" case. No code change.

</threats>
