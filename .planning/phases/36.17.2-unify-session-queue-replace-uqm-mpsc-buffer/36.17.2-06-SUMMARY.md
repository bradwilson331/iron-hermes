# Phase 36.17.2 Plan 06: Fix Transport Reaction Emoji 👁 → 👀 Summary

Surgical gap-closure fix: replace the in-flight transport reaction literal at `runner.rs:1066` from `"👁"` (U+1F441 EYE — not on Telegram's `setMessageReaction` allow-list, rejected with `REACTION_INVALID` HTTP 400) to `"👀"` (U+1F440 EYES — allow-listed, same "agent is looking at this" intent). Propagate the corrected glyph through doc comments, the UQM session-queue unification test (30 occurrences), the live UAT runbook (31 occurrences across Scenarios 1/5/6/7), and record the decision as D-28 in CONTEXT.md with a forward-pointer from D-09's warn-and-continue fallback. Pre-existing latent bug — not a 36.17.2 regression; the same `👁` literal was emitted at dispatch-time under 36.17.1 and failed silently the same way.

## Root Cause

UAT (2026-05-28) of plans 36.17.2-01..05 against a live Telegram bot surfaced this on every popped message:

```
WARN Worker: 👁 reaction emission failed; continuing (Phase 36.17.2 D-09)
  error=Telegram API error (400): Bad Request: REACTION_INVALID
```

Telegram's `setMessageReaction` Bot API maintains a hardcoded allow-list of accepted emoji. `👁` (U+1F441 EYE — single eye) is not on that list. `👀` (U+1F440 EYES — pair of eyes) is. The two glyphs carry equivalent user-intent ("I see you / agent is working on this"), so the fix is a one-codepoint literal substitution at the emission site.

The D-09 fallback (warn + continue) had been masking the failure since 36.17.1 — the agent itself kept functioning, but the user-visible reaction never rendered. This is therefore a pre-existing latent bug surfaced by 36.17.2's UAT, not a 36.17.2 regression. The same `👁` literal existed in the dispatch-time emission code path before plans 01-02 moved it to the worker; it failed silently the same way under 36.17.1 because no one ran a live Telegram UAT against the dispatch-time path.
