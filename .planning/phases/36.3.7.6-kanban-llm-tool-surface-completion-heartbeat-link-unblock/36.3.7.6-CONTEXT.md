## Locked Decisions

### D-heartbeat-impl — Append event row, NOT column update

**Decision:** `kanban_heartbeat` appends one `KanbanEventKind::Heartbeat` row to `task_events` via `store.append_event(task_id, run_id, KanbanEventKind::Heartbeat, payload)`. Payload shape `{"note": "..."}` when `note` arg present, `null` otherwise. Returns `{"status":"ok","task_id":"...","event_id":N}`.

**Rationale:**
1. `KanbanEventKind::Heartbeat` ALREADY EXISTS at events.rs:47 (snake_case `"heartbeat"` at events.rs:93). Zero-new-API impl.
2. The dispatcher staleness detection at `docs/kanban/reference.md:869` ALREADY reads `task_events` rows of kind=`heartbeat` to compute `heartbeat_age_seconds`. A column-based alternative would create two sources of truth.
3. Heartbeat-event volume is bounded at ~1/hour/worker per reference.md:291 guidance — no query-perf concern.

**Trade-off:** `task_events` table growth rate increases by ~1 row/hour/active-worker. Acceptable vs. schema-stability win.

**Rejected:** Add `tasks.last_heartbeat_at REAL` column. Rejected — would split the source-of-truth across two locations and require dispatcher staleness logic to be rewritten.

### D-link-cycle-detection — WITH RECURSIVE descendant walk + BEGIN IMMEDIATE

**Decision:** `store.insert_link_checked(parent_id, child_id)` (NEW sibling method) opens a `BEGIN IMMEDIATE` transaction, runs:
```sql
WITH RECURSIVE descendants(id) AS (
    SELECT child_id FROM task_links WHERE parent_id = ?1
    UNION
    SELECT tl.child_id FROM task_links tl JOIN descendants d ON tl.parent_id = d.id
)
SELECT 1 FROM descendants WHERE id = ?2 LIMIT 1
```
with params `(child, parent)`. Non-empty result → return `KanbanError::LinkCycle { parent_id, child_id }`. Empty result → run the existing tenant check + `INSERT OR IGNORE INTO task_links`. Commit.

**Rationale:**
1. The semantic invariant is "no `parent_id` should also appear as a transitive descendant of its `child_id`." The descendant walk asks exactly that.
2. The PRIMARY KEY `(parent_id, child_id)` on `task_links` (schema.rs:60-67) is a covering btree on `parent_id`, so the recursive CTE runs against an existing index.
3. `BEGIN IMMEDIATE` matches the existing concurrency pattern in `block_task` (store.rs:817-821) — prevents TOCTOU under concurrent writers in WAL mode.
4. SQLite supports `WITH RECURSIVE` since 3.8.3 (2014); rusqlite passes the SQL through unchanged.

**Existing `store.insert_link` is unchanged.** The `kanban_create::parents` path still calls it. Cycles are impossible by construction at create time (at most one new node in the DAG).

**Rejected:** (a) Extend `store.insert_link` with a `check_cycle: bool` flag — rejected, mixes two semantics into one method. (b) Walk ancestors of proposed `parent` instead of descendants of `child` — algorithmically equivalent but no ancestor-side index exists (would force a full scan).

### D-link-fk-enforcement — Rely on FK + map to KanbanError::TaskNotFound

**Decision:** `task_links` has `FOREIGN KEY (parent_id) REFERENCES tasks(id)` + `FOREIGN KEY (child_id) REFERENCES tasks(id)` (schema.rs:60-67), and `PRAGMA foreign_keys=ON` is set at open (schema.rs:21). A write with a phantom `parent_id` OR `child_id` errors at the SQL layer. `KanbanLinkTool::execute` catches the FK-violation error variant and returns structured rejection `{"status":"rejected","reason":"task_not_found","id":"<the missing id>"}`. The handler may pre-check via `store.get_task(parent_id)` / `store.get_task(child_id)` to produce a friendlier rejection with the specific missing id; the executor picks the more ergonomic of the two patterns at impl time.

**Rationale:** FK + the existing `KanbanError::TaskNotFound` variant (error.rs:22) provide automatic phantom-id detection without new error types.

### D-unblock-status-precondition — Fail-closed in LLM-tool handler

**Decision:** `KanbanUnblockTool::execute` runs a precondition gate BEFORE calling `store.unblock_task(task_id)`:
1. Resolve `task_id` (arg OR `$HERMES_KANBAN_TASK` env). Return `{"status":"rejected","reason":"missing_task_id"}` if neither present.
2. Call `store.get_task(task_id)`. If `Err(KanbanError::TaskNotFound)` → return `{"status":"rejected","reason":"task_not_found","task_id":"..."}`.
3. If `task.status != "blocked"` → return `{"status":"rejected","reason":"invalid_status","task_id":"...","current":"<actual>","expected":"blocked"}`.
4. Otherwise call `store.unblock_task(task_id)` (UNCHANGED — uses the existing unconditional UPDATE + `Unblocked` event append at store.rs:881-890).
5. Return `{"status":"ok","task_id":"..."}`.

**Rationale:**
- The existing `store.unblock_task` is operator-trusted (called from `cmd_unblock` at `crates/ironhermes-cli/src/kanban/commands.rs:367`). Operators can intentionally rescue a stuck `done`/`archived` task. The LLM tool surface is NOT operator-trusted — workers should never silently move a `done` task back to `ready`.
- Gating in the HANDLER (not the store) keeps the store API minimal and stable; CLI parity is preserved (the existing CLI behavior does not change).

**Trade-off vs. RESEARCH-recommended Option:** RESEARCH §2c suggested adding `store.unblock_task_strict` as a sibling method. Locked decision instead places the gate in the tool handler. This minimizes store-API surface area (one fewer public fn) and keeps the precondition policy adjacent to the LLM-tool prompt/contract. If a future operator-CLI case needs the strict variant, it can be promoted to the store layer without breaking the LLM tool's contract.

**Status assertion is exactly `task.status == "blocked"`.** No fuzzy match; no allow-list. Per `crates/ironhermes-kanban/src/types.rs` boundary convention D-17, `status` is plain `String` at the boundary; the CHECK / runtime invariant constrains it to a known set.
