## Summary

Phase 36.3.7.6 closes the 3 LLM tools (`kanban_heartbeat`, `kanban_link`, `kanban_unblock`) promised in `docs/kanban/reference.md:14` + `:204-208`. The phase is structurally light because (a) **every required `KanbanStore` primitive already exists**, (b) **`KanbanEventKind::Heartbeat` AND `KanbanEventKind::Unblocked` are ALREADY defined** (`events.rs:36, 47, 93, 102`) — no enum extension needed, (c) **the 6-tool registration pattern in `crates/ironhermes-kanban/src/tools/mod.rs:45-62` is a near-mechanical extension point** (add 3 more `registry.register(...)` calls + 3 sibling files), and (d) **the `tools_smoke.rs` integration-test file already follows a per-tool-section layout** that the new tests slot into without restructuring.

The only material design tension is **cycle detection on `kanban_link`** — `task_links` (schema.rs:60-67) has a `PRIMARY KEY (parent_id, child_id)` + FK constraints, BUT NO cycle prevention. `store.insert_link` (store.rs:378) checks tenant mismatch only. A cycle introduced via `kanban_link` would break the dispatcher's parent-completion gate (dispatcher pre-orders parent→child without cycle awareness). The planner must specify a write-time DFS check.

Secondary: **`heartbeat` is NOT currently in `DEFERRED_KANBAN_SUBVERBS`** (handlers.rs:1143-1148), but `link` and `unblock` ARE — meaning the planner needs to (1) add a NEW `Heartbeat` variant + `cmd_heartbeat` to the CLI parity (the docs `reference.md:583` claim it ships but it does not), and (2) remove `"link"` and `"unblock"` from `DEFERRED_KANBAN_SUBVERBS` only if Phase 36.3.7.6 also wires gateway-side `/kanban link` and `/kanban unblock` arms (recommended OUT of scope to keep phase tight).

**Primary recommendation:** Single multi-plan phase, 1-2 plans depending on cycle-detection ambition. Plan 01 ships all 3 LLM tools + tests + docs reconciliation as a contiguous unit since file overlap is high (single `tools/mod.rs` registration, single `tools_smoke.rs` test file, single docs file). The phase is approximately ~400-500 LOC source + ~200-300 LOC tests + ~10 LOC docs reconciliation. CLI parity for `kanban heartbeat` is recommended IN scope (the docs already claim it exists; closing the gap is cheap and gives the LLM handler a CLI to delegate to if the planner prefers).

### 2b. `kanban_link`

**Existing `task_links` table DDL** (schema.rs:60-67):
```sql
CREATE TABLE IF NOT EXISTS task_links (
    parent_id   TEXT NOT NULL,
    child_id    TEXT NOT NULL,
    created_at  REAL NOT NULL,
    PRIMARY KEY (parent_id, child_id),
    FOREIGN KEY (parent_id) REFERENCES tasks(id) ON DELETE CASCADE,
    FOREIGN KEY (child_id)  REFERENCES tasks(id) ON DELETE CASCADE
);
```

FK constraint + `PRAGMA foreign_keys=ON` (schema.rs:21) means a write with a phantom `parent_id` OR `child_id` errors at the SQL layer — phantom-id rejection is **automatic**.

**Existing method:** `store.insert_link(&mut self, parent_id: &str, child_id: &str) -> Result<()>` (store.rs:378). Already:
- Loads both tasks to fetch tenants (store.rs:~395 area; verified via grep).
- Rejects with `KanbanError::TenantMismatch { parent, child }` when both tasks have non-NULL tenants that differ (store.rs:400-407).
- INSERTs with `OR IGNORE` (store.rs:411) — duplicate link is a silent no-op, not an error.

**Cycle detection is NOT present.** The planner must specify it.

**Recommended cycle-detection algorithm:** DFS walking the **descendant chain of the proposed child** — i.e., before writing `(parent, child)`, walk `SELECT child_id FROM task_links WHERE parent_id = ?` recursively starting from `child`, and reject if the walk visits `parent`. Rationale:

1. The semantic invariant is "no `parent_id` should also appear as a transitive descendant of its `child_id`."
2. `idx_tasks_status_assignee` exists (schema.rs:130) but there is no dedicated `(parent_id)` index on `task_links` — however PRIMARY KEY `(parent_id, child_id)` IS a covering index on `parent_id`, so the recursive walk uses the existing PK btree.
3. SQLite supports `WITH RECURSIVE` CTEs (default since 3.8.3, all currently shipped rusqlite versions support it). The single-query form is:
   ```sql
   WITH RECURSIVE descendants(id) AS (
       SELECT child_id FROM task_links WHERE parent_id = ?1
       UNION
       SELECT tl.child_id FROM task_links tl JOIN descendants d ON tl.parent_id = d.id
   )
   SELECT 1 FROM descendants WHERE id = ?2 LIMIT 1
   ```
   With params (`child`, `parent`). A returned row means the proposed `parent` is already a descendant of `child` → reject as cycle. Empty result → safe to write.
4. The check + insert must happen in a single `BEGIN IMMEDIATE` transaction to prevent TOCTOU under concurrent writers (kanban uses WAL mode, and `BEGIN IMMEDIATE` is the existing concurrency pattern — see `block_task` at store.rs:817-821).

**New API surface required:** Either (a) extend `store.insert_link` to take an additional `check_cycle: bool` flag (back-compat: existing callers in `kanban_create::parents` get false to preserve current behavior at create time), OR (b) add a sibling method `store.insert_link_checked(parent_id, child_id) -> Result<()>` that the new `KanbanLinkTool` calls. **Recommendation: (b)** — the existing `kanban_create::parents` path is at create-time when at most one new node exists in the DAG, so cycles are impossible by construction; only post-hoc `kanban_link` calls need the check. Keeps the existing method unchanged.

**New error variant:** Add `KanbanError::LinkCycle { parent_id: String, child_id: String }` to `crates/ironhermes-kanban/src/error.rs`. Plan return-as-structured-JSON-rejection (matches the `KanbanError::StaleRunId` / `KanbanError::CreatedCardsRejected` pattern used in `complete.rs:157-180` and `block.rs:123-130`). LLM gets `{"status":"rejected","reason":"link_cycle","parent_id":"...","child_id":"..."}`.

**Schema layout:**
```json
{
  "type": "object",
  "properties": {
    "parent_id": { "type": "string", "description": "Parent task ID — must exist." },
    "child_id":  { "type": "string", "description": "Child task ID — must exist. Must not already be an ancestor of parent (cycle detection)." }
  },
  "required": ["parent_id", "child_id"]
}
```

**Failure paths that must be tested (BUG-04 ≥2 tests):**
- Happy: insert valid link, assert `task_links` row exists.
- Phantom IDs: FK rejection surfaces as DB error → recommend wrapping in a friendlier `KanbanError::TaskNotFound` rejection.
- Cycle: pre-seed `A→B`, attempt `B→A`, assert `link_cycle` rejection AND no row written.
- Tenant mismatch: pre-existing behavior — recommend ONE test to lock the existing tenant-gate behavior (regression lock; the existing `tools_smoke.rs` doesn't test it from a tool entry point).

### 2c. `kanban_unblock`

**Existing method:** `store.unblock_task(&mut self, task_id: &str) -> Result<()>` (store.rs:881-890). Current behavior:
1. `UPDATE tasks SET status='ready', claim_lock=NULL, current_run_id=NULL, claim_expires=NULL WHERE id=?1` (store.rs:883-887). **Note: this updates UNCONDITIONALLY — it does NOT check the current status.**
2. Appends `KanbanEventKind::Unblocked` event row with no payload (store.rs:888).

`KanbanEventKind::Unblocked` already exists (`events.rs:36`, snake_case `"unblocked"` at `events.rs:86`). **NO new variant needed.**

**The existing impl has a latent bug for the LLM-tool use case:** unblocking a task that is currently `done` / `archived` / `running` would silently move it to `ready`, blowing through the lifecycle invariants. The CLI `cmd_unblock` (commands.rs:367-378) inherits this — but CLI is an operator-trusted surface. The LLM tool is NOT. **The planner MUST add a status precondition check** before the `UPDATE` — fail closed if current status ≠ `blocked`.

**Recommended approach:**
- Add a new sibling method `store.unblock_task_strict(task_id) -> Result<()>` that wraps the UPDATE in `BEGIN IMMEDIATE`, loads the current status, returns `KanbanError::InvalidStatus { current, expected: "blocked" }` (new variant) if not `blocked`, then performs the existing update + event append.
- Existing `unblock_task` (called from CLI `cmd_unblock` at commands.rs:370) remains unchanged for operator compatibility. The LLM tool calls `unblock_task_strict`.

**Should the tool ALSO verify the task is currently `blocked`?** **YES — fail-closed if `ready`/`running`/`done`/`archived`.** Per the locked CONTEXT pattern from Phase 36.3.7.5 (structured-JSON rejection that the LLM can read and decide on), return:
```json
{"status":"rejected","reason":"invalid_status","task_id":"t_...","current":"done","expected":"blocked"}
```

**Schema layout:**
```json
{
  "type": "object",
  "properties": {
    "task_id": { "type": "string", "description": "Task ID to unblock. Omit to use $HERMES_KANBAN_TASK." }
  },
  "required": []
}
```

Defaults `task_id` to `$HERMES_KANBAN_TASK` (matches the pattern in all 6 existing tools).

**Failure paths that must be tested (BUG-04 ≥2 tests):**
- Happy: pre-seed task in `blocked` status (use `store.block_task`), call tool, assert status=`ready` AND `unblocked` event row appended.
- Wrong-status rejection: pre-seed task in `done` (or `ready`), call tool, assert structured rejection AND no UPDATE happened AND no event written.

## 5. Pattern derived from Phase 36.3.7.5 Plan 04

Phase 36.3.7.5 Plan 04 wired 3 new CLI verbs (`notify-subscribe / -list / -unsubscribe`) + an auto-subscribe hook + 9 receiver-end dispatch tests, shipped across 7 commits. The reusable shape for Phase 36.3.7.6:

### 5a. `KanbanStoreWriter` trait pattern — **NOT directly applicable here**

`KanbanStoreWriter` (defined at `crates/ironhermes-core/src/commands/context.rs:264`) exists to abstract the writer surface for the **gateway-side slash command dispatch** (i.e., `cmd_kanban` at handlers.rs:1159 calling into a writer that lives elsewhere without a circular crate dep). ### 5b. `handlers_kanban_notify.rs` receiver-test shape

**Use this shape for `link` and `unblock` ONLY if** the planner decides to wire them through `CommandContext` for gateway-side dispatch — which is OUT of scope per Section 4. **For the 3 LLM tools themselves**, use the simpler `tools_smoke.rs` shape (see 5c below).

### 5c. `tools_smoke.rs` receiver-test shape (RECOMMENDED for this phase)

## 7. Scope-fence recommendations

Items the planner should NOT touch:

- **The existing 6 tools' shapes** (no schema breaks). All edits ADD; nothing existing is renamed or reordered.
- **The 36.3.7.5 notifier.** Heartbeat is NOT a terminal event (`docs/kanban/reference.md:865` documents it as a worker telemetry event, not lifecycle). The notifier delivers only `Completed/Blocked/GaveUp/Crashed/TimedOut` per the locked CONTEXT.md decision at `36.3.7.5-CONTEXT.md:18-20`. Subscribing-to-heartbeats is a different feature (out of scope).
- **The `cmd_kanban` dispatch shape in handlers.rs.** The 3 new LLM tools are NOT slash commands. `DEFERRED_KANBAN_SUBVERBS` is untouched (per Section 4).
- **The `KanbanStoreReader` / `KanbanStoreWriter` trait shapes** (context.rs:215, 264). They're stable. The 3 new LLM tools call `KanbanStore` directly via their owned `Arc<TokioMutex<...>>`, not through the trait abstractions.
- **The `task_links` table DDL.** The existing PRIMARY KEY + FK constraints suffice; cycle detection lives in the new `store.insert_link_checked` method, not in DDL.
- **The dispatcher's stale-detection logic** (`reference.md:869`). The dispatcher already reads `heartbeat` events from `task_events`; the new tool writes the same kind via the same `append_event` path. No dispatcher change.
- **The existing `store.insert_link` / `store.unblock_task` methods.** Keep them unchanged for operator-CLI parity. Add SIBLING methods for the strict-mode LLM tool paths.
- **The `tasks` table.** No `last_heartbeat_at` column add (rejected per Section 2a rationale — would create two sources of truth).
- **`KanbanEventKind` enum.** Both required variants (`Heartbeat`, `Unblocked`) already exist. **Do not add new variants.**

## 8. Open questions for the planner / user

The 3 BUGs in the ROADMAP stub do leave one design choice each open. Research can settle two; one needs user/planner input.

### Q1 — BUG-01 (heartbeat impl): event row vs column?

**Research-settled.** Recommend **event row** (option a) per Section 2a rationale: (1) `KanbanEventKind::Heartbeat` already exists, (2) the existing dispatcher staleness detection reads from `task_events` rows (per reference.md:869), (3) option (b) creates two sources of truth. **No user input needed unless the planner wants to override the recommendation** (e.g., for query-perf reasons — but workload analysis says heartbeat-event volume is bounded at ~1/hour/worker per reference.md:291 guidance, so query perf is a non-issue).

### Q2 — BUG-02 (link cycle detection): walk-parents vs walk-children?

**Research-settled.** Recommend **walk descendants of proposed `child` via WITH RECURSIVE CTE** (per Section 2b). Algorithmically equivalent to walking ancestors of proposed `parent`, but the descendant walk uses the existing PRIMARY KEY `(parent_id, child_id)` btree directly (no ancestor index exists). **No user input needed.**

### Q3 — BUG-03 (Unblocked variant): NEW variant or reuse existing?

**Research-settled — reuse existing `KanbanEventKind::Unblocked` at events.rs:36.** **No user input needed.**

### Q4 — Should `kanban heartbeat` CLI verb ship alongside the LLM tool?

**Needs planner decision.** The docs (`reference.md:583`) already claim it exists. Two options:
- (a) Ship the CLI verb in this phase — closes the doc gap, gives the LLM handler a CLI to delegate to if the planner prefers, minor ~30 LOC additional scope.
- (b) Mark the doc claim as stale and remove the false `reference.md:583` line.

Recommendation: **(a)** — minor extra scope, closes doc gap, matches operator expectations.

### Q5 — Should the LLM tool's structured rejection for `kanban_link` cycle include the offending path?

E.g., `{"status":"rejected","reason":"link_cycle","cycle_path":["t_a","t_b","t_a"]}`. The recursive CTE can be extended to return the path that closed the cycle. Trade-off: ~10 LOC + a `path TEXT NOT NULL` column carrier in the CTE — improves LLM-side debugging. **Recommend yes; needs planner sign-off.** Out of LLM-debuggability spirit per LEARNINGS 2026-05-29 (structured rejections > opaque errors), but extra scope.

### Q6 — Should `kanban_unblock` be orchestrator-gated (similar to `kanban_create`'s exclusive `explicit_enable`)?

The existing pattern (Section 1 + the `KanbanCreateTool` rationale at create.rs comments) implies certain tools are orchestrator-only via the `explicit_enable=true` registration parameter. **Workers should not unblock themselves.** Recommendation: gate `kanban_unblock` to orchestrator-mode only — but the existing 6-tool pattern at `register_kanban_tools` (mod.rs:45-62) does NOT distinguish per-tool — `explicit_enable` is passed uniformly. Either (a) extend `register_kanban_tools` signature to take a per-tool gate, OR (b) accept that worker-mode unblocking is technically allowed (with structured-rejection on wrong-status preventing footguns). **Recommendation (b)** — keeps the registration shape uniform; the wrong-status rejection is the structural safeguard. **Needs planner sign-off.**
