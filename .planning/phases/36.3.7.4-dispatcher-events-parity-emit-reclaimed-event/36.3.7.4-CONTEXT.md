## Phase Boundary

This is a single 1-line producer fix + a single receiver-end test. The doc-comment at `crates/ironhermes-kanban/src/dispatcher.rs:19` says:

```rust
//! 3. **reclaim_stale_claims** — expired claim with dead or null PID →
//!    reset to `ready`, append `reclaimed` event.
```

But the implementation at `reclaim_stale_claims` (lines 399-473) only emits `tracing::info!(event = "reclaimed", task_id = %task.id, ...)` at line 437-441 — it never calls `store.append_event(&task.id, ..., KanbanEventKind::Reclaimed, ...)` to write a row to the `task_events` table.

**Why this matters now** (not just abstractly):
1. **Bilateral consumer downstream.** Phase 36.3.7.5 (gateway notifier) polls `task_events` to deliver terminal-event messages to subscribed chats. If `reclaim_stale_claims` doesn't write its event, the notifier cannot relay a reclaim signal.
2. **Bilateral consumer adjacent.** `crates/ironhermes-kanban/src/store.rs::block_task_with_reclaim` at lines 697-720 already emits a `Reclaimed` event when reclaiming on its own path — so the variant is wired through `as_str()`, serialization, and DB write-path; just the dispatcher's runtime call site is missing.
3. **Live UAT runtime evidence** (Phase 36.3.7.0 Run #5 + Run #6 UAT-EVIDENCE): the `kanban show` event log DOES show a `reclaimed` event for the TTL-expiry path — meaning the bug is intermittent / depends on which code path closed the run. (Investigation: the events shown in Run #6 came from `store.rs::block_task_with_reclaim`, which fires when the breaker trips OR when `release_claim` is called with a "reclaimed" reason. The dispatcher's `reclaim_stale_claims` path calls `release_claim(..., "ttl_expired")` at line 459 — different reason string, so different code path may emit different event. Need to verify which path the Run #6 event came from when reading the canonical implementation.)
4. **Bilateral-tracing meta-rule reaffirmation** (LEARNINGS 2026-05-29). The doc/impl gap is the simplest possible producer/consumer mismatch — fix it once, document the rule reapplication, move on.

In scope:
- **BUG-36.3.7.4-01** — insert exactly one `store.append_event(...)` call into `reclaim_stale_claims` AFTER the `tracing::info!(event = "reclaimed", ...)` block ends at dispatcher.rs:441 and BEFORE the "Close the run if there is one" block at line 443. The call must:
  - Use `KanbanEventKind::Reclaimed`
  - Pass `Some(&run.id)` if `run` is `Some(_)`, OR `None` if no run exists (the `let run = match … { Some(...) => ..., None => None }` at lines 418-425 already gives us `Option<Run>`)
  - Payload JSON: `{"pid": pid_or_null, "reason": "ttl_expired", "stale_lock": claim_lock_or_null}` — match the fields already in the `tracing::info!` log line plus the lock string the next-block uses
  - Use the canonical `let mut store = ctx.store.lock().await; … store.append_event(...)?` pattern (see dispatcher.rs:286-298 for the shape — the `Crashed` event append in `detect_crashed_workers`)
- **BUG-36.3.7.4-02** — 1 receiver-end test in `crates/ironhermes-kanban/tests/dispatcher_logic.rs` tail-appended after the 36.3.7.1 tests. The test must:
  - Seed a stale-claim task with dead PID (mirror the 36.3.7.1 Plan 01 test setup at dispatcher_logic.rs:908)
  - Drive one tick of `reclaim_stale_claims` (or `run_dispatch_tick` and trust the step-1 / step-3 ordering)
  - Assert via `SELECT COUNT(*) FROM task_events WHERE task_id=? AND kind='reclaimed'` returns ≥ 1
  - Assert the payload contains `"reason":"ttl_expired"` substring
  - Failure message must name BUG-36.3.7.4-02 so future regressions are immediately greppable

Out of scope:

## Locked Decisions

### Insert one `store.append_event` call, no other changes

**Decision:** Add the following block immediately after the `tracing::info!(event = "reclaimed", …)` at dispatcher.rs:437-441:

```rust
// Phase 36.3.7.4 BUG-36.3.7.4-01: append `reclaimed` event row so downstream
// consumers (gateway notifier per 36.3.7.5, event-replay audits) can see the
// TTL-expiry reclaim. Matches the doc-comment at dispatcher.rs:19 ("reset to
// `ready`, append `reclaimed` event").
{
    let pid = run.as_ref().and_then(|r| r.claim_pid);
    let claim_lock = task
        .claim_lock
        .clone()
        .unwrap_or_else(|| "unknown".to_string());
    let payload = serde_json::json!({
        "pid": pid,
        "reason": "ttl_expired",
        "stale_lock": claim_lock,
    });
    let mut store = ctx.store.lock().await;
    store.append_event(
        &task.id,
        run.as_ref().map(|r| r.id.as_str()),
        KanbanEventKind::Reclaimed,
        Some(&payload),
    )?;
}
```

**Rejected alternatives:**
- (a) Reuse the existing `release_claim(..., "ttl_expired")` call's internal event append. **Verify during execution** whether `release_claim` already writes a `reclaimed` event or only updates the task row. If it does write one, this phase becomes a NO-OP and only the receiver test remains (just to lock the invariant). If it does NOT, this insertion is the producer fix.
- (b) Change the reason string at line 459 from "ttl_expired" to "reclaimed" so the existing store.rs event path matches. Rejected — "ttl_expired" is the operational fact (the claim TTL ran out), "reclaimed" is the lifecycle event; they're orthogonal in semantics.
- (c) Move the event append to AFTER the consecutive_failures bump at line 462-469. Rejected — the canonical pattern (see dispatcher.rs:286-298 for `Crashed`) is bump → event → breaker, BUT the breaker call was added in Phase 36.3.7.1-01 at line 481, AFTER the bump. Placing the reclaim event after the tracing::info! and before the bump matches the natural lifecycle order (state change → log → event → bump → breaker check).

**Verification responsibility (the planner / executor must do this at Task 1 read time):** grep `crates/ironhermes-kanban/src/cas.rs` for `release_claim` and confirm whether it appends a `Reclaimed` event. If it DOES, the producer fix is a no-op AND the existing 36.3.7.0/1 UAT evidence that shows the `reclaimed` event row was emitted via that path — and this phase shrinks to just the receiver test BUG-36.3.7.4-02. If it does NOT, proceed with both bugs.

### Receiver-end test mirrors Phase 36.3.7.1 Plan 01's seed pattern

**Decision:** The new test in `dispatcher_logic.rs` MUST mirror the seed-stale-claim pattern from `circuit_breaker_trips_on_reclaim_path` (dispatcher_logic.rs:908) but assert on `task_events` rather than task status. Test name: `reclaim_stale_claims_appends_reclaimed_event` or similar.

Body shape:
```rust
#[tokio::test]
async fn reclaim_stale_claims_appends_reclaimed_event() {
    let (ctx, task_id, _run_id) = seed_stale_claim_dead_pid(/* failure_limit = 5, headroom */).await;
    // Failure_limit headroom — DON'T let the breaker trip; we're asserting
    // the reclaim event, not the gave_up event.
    reclaim_stale_claims(&ctx, /* now = */ 1_000_000.0).await.unwrap();
    let store = ctx.store.lock().await;
    let count: i64 = store
        .conn
        .query_row(
            "SELECT COUNT(*) FROM task_events WHERE task_id=?1 AND kind='reclaimed'",
            params![task_id],
            |r| r.get(0),
        )
        .unwrap();
    assert!(
        count >= 1,
        "BUG-36.3.7.4-02: reclaim_stale_claims must append a `reclaimed` row to task_events. \
         Found {count} rows."
    );
    // Optionally also assert payload contains "ttl_expired" — depending on
    // whether release_claim emits its own event with a different reason.
}
```

If `release_claim` already emits the event (per the Rejected-alternative-a verification), the assertion `count >= 1` will still pass because the event IS written — just from a different code site. The test stays valuable as a regression lock.
