# Phase 36.3.7.8: @mention delegation parser — inline routing from prose — Research

**Researched:** 2026-05-30
**Domain:** Markdown text parsing + Kanban task graph mutation + dispatcher-tick integration (Rust workspace, ironhermes-kanban crate)
**Confidence:** HIGH

## Summary

This phase adds inline `@<assignee>` delegation parsing to the Kanban v1 kernel. A worker or orchestrator writes `@reviewer take a look` inside a task body or comment, and the system materializes a fresh child task assigned to `reviewer`, linked back to the originating task as its parent.

The phase is structurally light because the heavy infrastructure (atomic transaction primitives, `KanbanStore::create_task`, parent-link insertion via `insert_link`, the 10-tool LLM surface registration pattern, `KanbanWorkerSpec`/`SwarmGraphSpec` idempotency suffix scheme, `DEFERRED_KANBAN_SUBVERBS` deferred-slash routing, the receiver-end test layout in `tools_smoke.rs`, the docs-reconciliation gate shape) is already shipped by Phases 36.3.7 + 36.3.7.0..7. The new content is: (1) a pure-function Markdown scanner that emits `@handle` spans with fence-skipping semantics, (2) a resolver that maps a handle to a validated assignee with graceful fallback, (3) an LLM tool `kanban_mention` that calls the parser + resolver + spawns child cards in one transaction, (4) a CLI verb `hermes kanban mention <task_id>` with the same path, and (5) a one-line addition to `DEFERRED_KANBAN_SUBVERBS` so the gateway `/kanban mention` routes to the deferred-CLI message.

**Primary recommendation:** Ship `@mention` as a **dedicated LLM tool + CLI verb**, NOT as a dispatcher-tick scanner. Build the parser as a **pure regex-based function** with explicit fence/inline-code/HTML-comment skip rules — do **not** pull in `pulldown-cmark` or `comrak`. Use an **explicit `kanban_mention(task_id)` invocation** model (orchestrator/worker calls the tool when they want delegation to fire) rather than implicit "every body is scanned every tick" — explicit calls are testable, predictable, idempotent-friendly, and don't blow up the dispatcher tick latency budget. The 11th LLM tool slots in cleanly behind 36.3.7.7's swarm-completion (10 → 11).

## Recommended Decisions (with rationale & evidence)

### Decision 1 — Where does @mention extraction run?

**Recommendation:** **LLM tool + CLI verb only.** NOT a dispatcher-tick scanner. NOT a hybrid.

**Evidence:**
- The dispatcher tick is a hot path. Per `crates/ironhermes-kanban/src/dispatcher.rs:122-220`, every tick runs 8 ordered steps: detect_crashed_workers, extend_live_pid_claims, reclaim_stale_claims, enforce_max_runtime, promote_ready, claim_and_spawn, plus instrumentation overhead. Default interval is `config.dispatch_interval_seconds` (min 1s). Scanning every task body + every comment for `@handle` regex matches on every tick would add O(N × body_chars) work per tick, scaling poorly as the board grows.
- Side-effects from implicit scans are surprising. A worker writes `the @reviewer said this isn't ready` as a parenthetical note in a comment, and the system spontaneously spawns a `reviewer` child task — the worker didn't intend to delegate. Explicit invocation (`kanban_mention(task_id)`) makes the act of delegation a deliberate ceremony. This matches how 36.3.7.7's swarm fan-out works — explicit `kanban_swarm` call, never an implicit "we noticed you mentioned multiple things in your body" scan.
- Idempotency becomes trivial. If extraction only runs when the LLM calls the tool, the natural anchor for the idempotency key is the tool invocation. Implicit dispatcher scans force a more painful "did we already process this body version" tracking layer.
- The CONTEXT-stub line "Stretches the LLM-tool surface or the dispatcher-side handler (planner decides)" indicates this is genuinely planner's discretion — no inherited constraint forces dispatcher placement.

**Counter-argument (and why it doesn't bind):** Prose written by humans via the CLI (`hermes kanban comment t_abcd --body "@reviewer pls look"`) won't auto-delegate under the tool-only model. **Resolution:** the same `cmd_mention` CLI verb is available — humans run `hermes kanban mention t_abcd` to fire delegation explicitly. This is consistent with how human operators already drive batch operations (no implicit auto-decompose on every `triage` body in v1, etc.).

**Locked default in this research:** TOOL-ONLY. Planner overrides only if a use case emerges where the LLM never explicitly calls the tool (no such case identified in the 36.3.7.x phase chain).

### Decision 2 — Parser strategy: pure function or streaming Markdown walker?

**Recommendation:** **Pure function**, regex-based, with explicit fence-state machine. Do NOT pull in `pulldown-cmark` or `comrak`.

**Evidence:**
- `crates/ironhermes-kanban/Cargo.toml:27` already has `regex = { workspace = true }`. Zero new dependencies needed for the regex approach.
- A grep of the entire `crates/` tree (excluding `iron_hermes_ui/.planning/`) shows **no current use** of `pulldown-cmark` or `comrak` in any compiled crate. The only references are inside `iron_hermes_ui/.planning/phases/03-*/04-*` discussion logs where the desktop UI team **deferred** the markdown crate decision to a later phase. Adding such a crate to `ironhermes-kanban` would be the first ironhermes-side dependency on a Markdown parser — a meaningful build-graph cost (`pulldown-cmark` is ~5K LOC, ships its own ICU-style char tables; `comrak` is ~25K LOC).
- Task bodies are short. Per the Kanban v1 design, `tasks.body` is free-form prose, typically 1-2 paragraphs. There is no "streaming" need — load the body into memory (already in memory from the `tasks` table read), run the regex pass, done.
- The fence-skip logic is well-bounded:
  1. Skip everything between matching ``` ... ``` or ~~~ ... ~~~ fences (CommonMark §6.6).
  2. Skip everything between matching `` ` ``...`` ` `` inline code spans (CommonMark §6.5) — single-backtick form is the dominant case in task bodies.
  3. Skip everything between `<!--` and `-->` (CommonMark §6.4 HTML blocks subset).
  4. Skip indented (4-space) code blocks? **DEFER** — rare in task bodies; documented limitation in v1.
  
  Implementing this as a pure ~80 LOC state machine over `body.char_indices()` is straightforward.

- The "streaming Markdown walker" alternative would couple us to whatever AST the chosen crate exposes (`pulldown-cmark::Event` enum, `comrak::nodes::NodeValue` enum) — overkill for a single-pattern extractor.

**Counter-argument:** A regex-based scanner is technically more fragile than a real CommonMark parser for adversarial inputs. **Resolution:** task bodies are not adversarial — they're authored by workers/orchestrators inside our own trust boundary. A handful of receiver tests covering the fence-skip rules give us enough coverage. If we ever need full CommonMark fidelity (e.g., for prompt-injection scrubbing across all incoming bodies), that's a future-phase concern.

**Locked default in this research:** PURE-FUNCTION REGEX with fence-state machine. Concrete shape proposed in `## Code Examples` below.

### Decision 3 — Assignee resolver: how does `@<word>` become a real assignee?

**Recommendation:** Three-stage pipeline. (1) **Lexical normalization** — lowercase the handle, strip trailing punctuation. (2) **Validation gate** — run `validate_profile_name` (already in `ironhermes-core::profile::validate_profile_name`). (3) **Existence gate** — check whether the normalized handle has any tasks in the board (via the existing `cmd_assignees` aggregation at `commands.rs:694`); if not, apply the configured fallback policy.

**Evidence:**
- `validate_profile_name` (`crates/ironhermes-core/src/profile.rs:63-88`) **is already strict**: lowercase alphanumeric + dashes, no leading underscore, no reserved tokens (`default`, `current`, `none`), max 64 chars, must start with letter or digit. This is exactly the right validator for a handle in v1.
- Profile names in natural-language prose almost never appear capitalized (`@reviewer`, not `@Reviewer`) — but `@Reviewer` would otherwise hit `ProfileNameError::InvalidChars`. Lowercase-normalize before validation.
- Trailing punctuation: in prose, `@reviewer,` or `@reviewer.` or `@reviewer?` is common. The regex should NOT capture trailing punctuation as part of the handle; `[A-Za-z0-9][A-Za-z0-9-]*` greedy-match handles this correctly (dash is allowed, but a comma/period/question mark ends the match).
- The "known assignees" registry that the resolver consults for the existence gate is already implemented as a SQL aggregation. `cmd_assignees` at `commands.rs:694-714` shells out to a store API that returns `(assignee, task_count)` rows. This is the canonical source of "real" assignees on the board. Adding a parallel `store.list_known_assignees() -> HashSet<String>` (or reusing what `cmd_assignees` already calls) is one short SQL: `SELECT DISTINCT assignee FROM tasks WHERE assignee IS NOT NULL`.

**Three policies (REQ-36.3.7.8-05):**
| Policy | Behavior on unknown `@handle` | Use case |
|---|---|---|
| `skip` (default) | Drop silently; return a counter in `skipped[]` with reason `unknown_handle`. | LLM-driven calls where unknown handles are noise (prose mentions a tool name, not a person). |
| `pending` | Materialize the child anyway with the literal handle as assignee. Validation still applies — if the handle fails `validate_profile_name`, downgrade to `skip` for that handle. | Operator workflows where unknown handles indicate "register this person later, but capture the work now." |
| `error` | Return `{"status":"rejected","reason":"unknown_handle","detail":"..."}` for the whole call. No partial state — atomic-transaction rollback. | Strict CI/automation contexts where unknown handles indicate a typo and the worker should retry with corrected text. |

**Counter-argument:** Why not always require known-assignee?  **Resolution:** prose often contains `@<word>` patterns that aren't intended as delegations — `@noreply`, `@channel` (Slack convention), `@everyone` (Discord convention), file paths starting with `@`, etc. Defaulting to `skip` for unknowns avoids false-positive delegations.

**Locked default in this research:** CONFIGURABLE per call, default `skip`. The LLM tool exposes the policy via the `fallback_policy` param; the CLI verb via `--fallback-policy`.

### Decision 4 — Cycle detection: what if a child @mentions back to the parent?

**Recommendation:** **Two-layer defense.** (1) **Self-mention rejection** at resolver (constant-time): a handle that resolves to the same assignee as the parent task's assignee is `Skipped(SelfReference)`. (2) **Ancestor-chain check** at store layer (O(chain-depth) SQL): walk the parent's ancestor chain via `task_links` up to `MAX_MENTION_CHAIN_DEPTH = 4` hops; if the resolved assignee appears within the chain, skip with `Cycle`. NO general DAG cycle detection — link insertion already uses the proven 36.3.7.6 `insert_link_checked` `WITH RECURSIVE` pattern for cross-link cycles, which catches the topological case.

**Evidence:**
- The fundamental loop pathology: task A (assignee = worker-a) writes `@worker-b please review` → creates child B (assignee = worker-b). B writes `@worker-a oh you should look at this` → creates child C (assignee = worker-a). Without bounds, A→B→A→B→... fan-out is unbounded.
- Depth-limit constant `MAX_MENTION_CHAIN_DEPTH = 4` is chosen because:
  - Legitimate chains in the patterns table at `docs/kanban/reference.md` §740 (P2 Pipeline: scout → editor → writer = 3 hops) need at least 3.
  - Adding 1 for safety margin gives 4.
  - Beyond 4 hops, the path likely indicates a flow that should have been a designed swarm (Phase 36.3.7.7) rather than spontaneous fan-out.
- The walk is cheap. SQLite's `WITH RECURSIVE` on `task_links` against the existing PK `(parent_id, child_id)` index is sub-millisecond for chains of 4 hops. Same cost regime as the 36.3.7.6 cycle check at `store.rs:497-509`.
- Self-mention is the cheapest possible check: comparing two strings. Doing it at the resolver layer avoids needing a DB roundtrip for the most common cycle case.

**Counter-argument:** Why not just rely on the existing `insert_link_checked` WITH RECURSIVE detector?  **Resolution:** `insert_link_checked` only catches cycles that would form in the `task_links` DAG itself — but the mention-chain isn't always a true cycle in `task_links` (each child has a single fresh `parent_id`, so the DAG is technically a tree, not a cycle). The cycle is at the **assignee identity** level (same worker bouncing tasks), not the **node identity** level. Hence a separate assignee-chain check.

**Locked default in this research:** TWO-LAYER (self-reference quick reject + 4-hop ancestor-chain check). Constant exposed as `pub const MAX_MENTION_CHAIN_DEPTH: usize = 4;` in `mention/resolver.rs` for test access.

### Pattern 1: Pure-function parser inside the kanban crate

**What:** A `pub fn parse_mentions(body: &str) -> Vec<MentionSpan>` lives in `src/mention/parser.rs`. No IO. No async. No mutable state across calls. Trivially testable from `#[cfg(test)]` modules and from `tests/tools_smoke.rs` alike.

**When to use:** Whenever a caller has a body string and wants the literal list of `@handle` spans, fence-aware.

**Example:**
```rust
// Source: proposed src/mention/parser.rs (NEW)
//
// fence-state machine: walks the body char-by-char, maintaining a small enum
// of "what scope am I in right now" (Prose / FencedCode / InlineCode /
// HtmlComment) and only emits handle spans when state == Prose.

use regex::Regex;

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct MentionSpan {
    pub handle: String,   // raw handle as-found, NOT lowercased (resolver does that)
    pub byte_offset: usize,
}

pub fn parse_mentions(body: &str) -> Vec<MentionSpan> {
    // Strategy: do ONE pass that strips fence/inline-code/html-comment regions
    // into a "redacted" string of the same length, then run the @handle regex
    // against the redacted view. Byte offsets line up by construction.
    let redacted = redact_non_prose(body);
    static HANDLE_RE: once_cell::sync::Lazy<Regex> = once_cell::sync::Lazy::new(|| {
        // `@` followed by [a-z0-9-] (case-insensitive); first char must be alnum
        Regex::new(r"@([A-Za-z0-9][A-Za-z0-9-]*)").unwrap()
    });
    HANDLE_RE
        .captures_iter(&redacted)
        .filter_map(|cap| {
            let m = cap.get(1)?;
            Some(MentionSpan {
                handle: m.as_str().to_string(),
                byte_offset: m.start(),
            })
        })
        .collect()
}
```

### Pattern 2: Sibling-method on KanbanStore for the transaction

**What:** `KanbanStore::create_mention_children(parent_id, plan, idempotency_key)` is a new pub fn alongside `create_task` and `create_swarm`. Wraps N inserts + N links + N event-rows in one `BEGIN IMMEDIATE` transaction.

**When to use:** Only the `kanban_mention` LLM tool and the `cmd_mention` CLI verb call it. Never re-entered from inside `create_task` (same constraint as 36.3.7.7 `create_swarm` per D-no-create-task-reuse).

**Example:**
```rust
// Source: proposed addition to crates/ironhermes-kanban/src/store.rs
//
// Mirrors the create_swarm shape at store.rs:540-1000. The key difference is
// that mention-children have N parents (always exactly 1 each: the
// originating task) rather than the variable-parents shape of swarm cards.

pub struct MentionPlan {
    pub parent_id: String,
    pub children: Vec<MentionChildSpec>,
    pub idempotency_key: Option<String>,
    pub workspace: Option<String>,
    pub skills: Option<Vec<String>>,
    pub tenant: Option<String>,
}

pub struct MentionChildSpec {
    pub handle: String,            // original-cased handle from prose
    pub assignee: String,          // normalized + validated profile name
    pub mention_index: usize,      // 0-indexed within the original parsed list
    pub title: String,             // auto-generated, e.g. "@reviewer mention from t_abcd"
    pub body: Option<String>,      // optional override; defaults to a snippet
}

pub struct MentionResult {
    pub children: Vec<MentionChildIds>,
}

pub struct MentionChildIds {
    pub child_id: String,
    pub assignee: String,
    pub handle: String,
}

impl KanbanStore {
    pub fn create_mention_children(
        &mut self,
        plan: MentionPlan,
    ) -> Result<MentionResult, KanbanError> {
        // Idempotency short-circuit
        if let Some(ref base) = plan.idempotency_key {
            let first_key = format!("{base}:mention:0");
            if let Some(_existing) = self.find_by_idempotency_key(&first_key)? {
                // Walk task_links to reconstruct children; return existing
                // MentionResult. Same shape as create_swarm replay path.
                return self.replay_mention_children(&plan.parent_id, base);
            }
        }

        let tx = self.conn.transaction_with_behavior(rusqlite::TransactionBehavior::Immediate)?;
        let mut children = Vec::with_capacity(plan.children.len());

        for spec in &plan.children {
            // INSERT INTO tasks (one child)
            // INSERT INTO task_links (parent → child)
            // INSERT INTO task_events (Created)
            // … all via tx.execute(...) using the INSERT shapes already at
            //   store.rs:243-281 (create_task) and store.rs:412-417 (insert_link)
            children.push(MentionChildIds {
                child_id: /* computed */ String::new(),
                assignee: spec.assignee.clone(),
                handle: spec.handle.clone(),
            });
        }

        tx.commit()?;
        Ok(MentionResult { children })
    }
}
```

### Anti-Patterns to Avoid

- **Implicit dispatcher-tick scanning.** Don't add a "step 9" to the 8-step dispatcher tick that walks every task body for @mentions. Adds latency, surprises authors, and complicates idempotency. Decision 1 rationale above.
- **Pulling in `pulldown-cmark`/`comrak`.** New crate-level dep for an ~80 LOC state machine is overkill and rebuilds the docs team's deferred decision the wrong way. Decision 2 rationale above.
- **Re-entering `KanbanStore::create_task` from inside `create_mention_children`'s transaction.** Same anti-pattern documented at 36.3.7.7 D-no-create-task-reuse — `create_task` takes `&mut self` and runs its own autocommit, deadlocks or breaks atomicity if called inside an outer tx. Inline the INSERT shapes.
- **Extending the `KanbanStoreWriter` trait.** That trait (from Phase 36.3.7.5) only exists for the gateway slash arm path. This phase defers the slash surface (REQ-08) so the trait does NOT need an `append_mention_children` method.
- **Adding a new `KanbanEventKind` variant** like `MentionFanOut`. Each child's creation already emits the existing `KanbanEventKind::Created` row from inside the transaction (same as `create_task`/`create_swarm`). No new event variant.
- **Spawn-env contract change.** Don't introduce a `HERMES_KANBAN_MENTION_PARENT` env var; the LLM tool already takes an explicit `task_id` (or defaults to `$HERMES_KANBAN_TASK` in worker mode). The 9-env-var spawn contract is invariant per INV-36.3.7.
- **Stripping handles inside multi-line raw strings.** A worker writing a body containing `\n@reviewer\n` should have that mention extracted. Do not collapse the body to a single line before parsing — the fence-state machine handles newlines correctly.
- **Forgetting `@@` escapes.** A literal `@@reviewer` should NOT match — the first `@` is the at-sign character, the second `@` starts a handle. Our `@[A-Za-z0-9]` regex naturally handles this because the second `@` is not in the character class — but the FIRST `@` would still match the empty-suffix case if we weren't requiring a starting alnum. We do require it. **Tested explicitly in REQ-13's edge cases.**

## Common Pitfalls

### Pitfall 1: Fence-marker line discipline (CommonMark §6.6 nuance)
**What goes wrong:** A naive regex `\`\`\`.*?\`\`\`` matches greedy across paragraphs but fails on the standard "fence must be at start of line with up to 3 leading spaces" rule. Real-world example: a body containing `let s = "\`\`\`oops\`\`\`";` has fence markers mid-line, which CommonMark does NOT treat as a fenced code block.
**Why it happens:** Mid-line backtick triplets are inline code spans, not fenced blocks. The author writes a regex that doesn't know the difference.
**How to avoid:** The fence-state machine MUST require the fence opener (` ``` ` or `~~~`) to start at column 0 (or after up to 3 spaces of indentation) per CommonMark §6.6. Mid-line backticks fall under the inline-code rule (CommonMark §6.5) which has its own matched-count semantics. Receiver test: `mention_inside_inline_triple_backticks_is_not_a_fence` (a body like `prefix \`\`\`foo @reviewer bar\`\`\` suffix` — verify the `@reviewer` IS extracted because it's inside an inline span that doesn't span lines, and CommonMark treats `\`\`\`...\`\`\`` mid-line as an inline-code span of length 3).
**Warning signs:** Tests pass for simple cases but a real worker writes a code example mid-paragraph and the mention IS or ISN'T extracted contrary to expectation.

### Pitfall 2: Trailing punctuation in handles
**What goes wrong:** `@reviewer.` produces handle `reviewer.` (including the period), which fails `validate_profile_name` (the regex `[a-z0-9-]` doesn't allow `.`).
**Why it happens:** The handle regex character class wasn't constrained tightly.
**How to avoid:** Use `@([A-Za-z0-9][A-Za-z0-9-]*)` (greedy alphanumeric+dash, not greedy "everything until whitespace"). Receiver test: `mention_handle_strips_trailing_punctuation` — body `"@reviewer, take a look."` extracts handle `reviewer`.
**Warning signs:** Unknown-handle counter ticks up in prose containing perfectly valid `@reviewer.` references because of period inclusion.

### Pitfall 3: Case folding before validation, or after?
**What goes wrong:** Resolver receives `@Reviewer`, runs `validate_profile_name` first → `ProfileNameError::InvalidChars`. User gets an unknown-handle reason, but the handle was actually valid post-normalization.
**Why it happens:** Validation happens before case-normalization.
**How to avoid:** Pipeline order MUST be: (1) lowercase the handle, (2) `validate_profile_name`. If validation still fails, it's a real malformed handle. Receiver test: `mention_handle_case_insensitive` — body `"@Reviewer needs to see this"` resolves to assignee `reviewer`.
**Warning signs:** Prose with capitalized handles produces zero delegations even though the handle name exists on the board.

### Pitfall 4: Mention-chain depth check uses wrong starting node
**What goes wrong:** The depth check walks the WRONG direction in `task_links` (children-of-parent instead of parents-of-parent), or starts at the child being created instead of the parent triggering the mention.
**Why it happens:** `task_links` edges are `(parent_id, child_id)` and either direction is a one-liner SQL flip — easy to write the wrong one.
**How to avoid:** The walk starts at the **parent task** (the one whose body is being parsed) and walks UP via `WHERE child_id = ?` (find parents of parent of parent of …). Code review checklist: confirm the recursive CTE selects `parent_id` rows, not `child_id` rows. Receiver test: `mention_cycle_A_B_A_4_hops_blocked` — set up a chain A→B→A→B and verify the 4th hop is `Skipped(Cycle)`.
**Warning signs:** A→B→A→B chains never get blocked, or legitimate 2-hop chains erroneously get blocked.

### Pitfall 5: `validate_profile_name` rejects `pending`
**What goes wrong:** REQ-05's `pending` fallback policy materializes children with assignee `pending`, which gets validated by `validate_profile_name`. The current ruleset (`profile.rs:63-88`) accepts `pending` (it's lowercase, alphanumeric, not reserved, ≤64 chars) — so this works in practice. But if a future phase adds `pending` to `RESERVED_NAMES`, the `pending` policy would silently break.
**Why it happens:** Reserved-name lists evolve.
**How to avoid:** Locked test `mention_pending_policy_uses_literal_assignee_pending` exercises the full `pending`-policy path end to end. If `RESERVED_NAMES` ever changes, this test surfaces the regression.
**Warning signs:** The `pending` policy receiver test starts failing after an unrelated profile-validation change.

### Pitfall 6: Idempotency-key suffix conflicts with body re-edits
**What goes wrong:** Worker calls `kanban_mention` with `idempotency_key="abc"` and body `"@reviewer please"`. One child created with key `abc:mention:0`. Worker edits the body to `"@reviewer please @writer too"` and re-invokes with same key. Replay-path returns the OLD single child even though the NEW parse would produce two.
**Why it happens:** Idempotency keys are about "did this *call* already happen" — they're invariant to body changes by design.
**How to avoid:** Document the convention. Callers who want re-parsing after a body edit MUST use a different idempotency key (or none). Receiver test: `mention_idempotency_replay_returns_stale_children_for_changed_body` — explicitly verifies the stale-replay semantics so it doesn't surprise users.
**Warning signs:** Workers report "I added a mention but no child appeared" — usually because they reused an old idempotency key.

### Pitfall 7: Worker-mode `is_available()` gating vs the explicit-orchestrator path
**What goes wrong:** The tool's `is_available()` returns `std::env::var("HERMES_KANBAN_TASK").is_ok() || self.explicit_enable` — same as the other 10 tools. But a CLI invocation from an unparented human-driven `hermes kanban mention t_abcd` won't have `HERMES_KANBAN_TASK` set, only `explicit_enable=true` from the CLI side. The tool layer is fine here; the CLI's `cmd_mention` doesn't go through the tool registry at all — it calls `store.create_mention_children` directly. **No bug if planner uses the same shape as `cmd_create`/`cmd_swarm`.** But it's easy to confuse the two paths.
**Why it happens:** Two code paths (tool + CLI) calling the same store method — easy to wire one path through the tool registry mistakenly.
**How to avoid:** `cmd_mention` constructs a `MentionPlan` directly and calls `store.create_mention_children` — no tool-registry indirection. Code review checklist: `cmd_mention` does NOT instantiate `KanbanMentionTool`.
**Warning signs:** CLI-only invocations fail with "tool unavailable" errors.

### Pitfall 8: Cross-tenant mention link inserts
**What goes wrong:** Parent task has `tenant='business-a'`, parsed `@reviewer-b` happens to be a reviewer normally serving `business-b`. The link insert hits `KanbanError::TenantMismatch` from D-39 inside the transaction, rolling back the whole batch.
**Why it happens:** `task_links` has a tenant-consistency check at `store.rs:474-481`.
**How to avoid:** This is **correct behavior** — cross-tenant delegations should fail closed. Document it; receiver test `mention_cross_tenant_assignee_rejected` confirms the rollback.
**Warning signs:** Multi-tenant deployments report mention failures that look mysterious; the fix is for orchestrators to scope their mentions to their tenant's profile set.

```text
- HTML comments: <!-- ... --> — content between markers is literal.
```

### Proposed: redact_non_prose() state machine (reference, ~80 LOC)
```rust
// Source: NEW crates/ironhermes-kanban/src/mention/parser.rs
//
// The "redact" approach: walk the body once, and for any region that should
// not yield mentions, replace each byte with a space (preserving byte offsets
// so the subsequent regex pass yields correct offsets). Returns a String of
// equal length to `body`.

#[derive(Debug, Clone, Copy)]
enum ScanState {
    Prose,
    FencedCode { fence_char: char, fence_len: usize },
    InlineCode { backtick_run: usize },
    HtmlComment,
}

fn redact_non_prose(body: &str) -> String {
    let mut out = String::with_capacity(body.len());
    let mut state = ScanState::Prose;
    let bytes = body.as_bytes();
    let mut i = 0;
    while i < bytes.len() {
        match state {
            ScanState::Prose => {
                // Detect: fenced opener at line start, HTML comment open, inline backtick run
                if is_line_start(bytes, i)
                    && let Some((fence_char, fence_len, new_i)) = try_consume_fence_open(bytes, i)
                {
                    pad_space(&mut out, new_i - i);
                    i = new_i;
                    state = ScanState::FencedCode { fence_char, fence_len };
                    continue;
                }
                if bytes[i..].starts_with(b"<!--") {
                    pad_space(&mut out, 4);
                    i += 4;
                    state = ScanState::HtmlComment;
                    continue;
                }
                if bytes[i] == b'`' {
                    let n = count_run(bytes, i, b'`');
                    pad_space(&mut out, n);
                    i += n;
                    state = ScanState::InlineCode { backtick_run: n };
                    continue;
                }
                // Default: copy byte to output
                out.push(bytes[i] as char);
                i += 1;
            }
            ScanState::FencedCode { fence_char, fence_len } => {
                if is_line_start(bytes, i)
                    && try_consume_fence_close(bytes, i, fence_char, fence_len).is_some()
                {
                    // Close fence — pad and return to Prose
                    let close_len = count_run(bytes, /* skip indent */ skip_indent(bytes, i), fence_char as u8);
                    pad_space(&mut out, close_len + (skip_indent(bytes, i) - i));
                    i += close_len + (skip_indent(bytes, i) - i);
                    state = ScanState::Prose;
                    continue;
                }
                pad_space(&mut out, 1);
                i += 1;
            }
            ScanState::InlineCode { backtick_run } => {
                if bytes[i] == b'`' {
                    let n = count_run(bytes, i, b'`');
                    if n == backtick_run {
                        pad_space(&mut out, n);
                        i += n;
                        state = ScanState::Prose;
                        continue;
                    }
                }
                pad_space(&mut out, 1);
                i += 1;
            }
            ScanState::HtmlComment => {
                if bytes[i..].starts_with(b"-->") {
                    pad_space(&mut out, 3);
                    i += 3;
                    state = ScanState::Prose;
                    continue;
                }
                pad_space(&mut out, 1);
                i += 1;
            }
        }
    }
    out
}
```

## Open Questions

1. **Should the child task's `body` field be populated, and if so, with what?**
   - What we know: 36.3.7.7's `kanban_swarm` per-card body is either explicitly set (rich form) or `None` (flat form).
   - What's unclear: For a mention-generated child, the body could be (a) `None` (let the worker figure it out from the parent), (b) a snippet of the surrounding mention prose ("@reviewer look at this — `<one sentence after the handle>`"), (c) a `kanban_show <parent_id>` reference.
   - Recommendation: ship (a) `None` by default; planner can layer (b) as a low-risk enhancement if research shows worker-mode value. The mention's surrounding prose IS readable via `kanban_show <parent_id>` anyway.

2. **Does the LLM-tool surface need a `dry_run` mode?**
   - What we know: `kanban_create` doesn't have one; `kanban_swarm` doesn't have one.
   - What's unclear: A `dry_run: true` flag that runs parse + resolve + skip-checks but skips the transaction would help LLM agents preview "what would this create" before committing.
   - Recommendation: skip in v1. The `body_override` param already covers the "test against an alternate body" case; full dry-run is a forward-phase polish item.

3. **Per-child `priority` inheritance from parent — or all default?**
   - What we know: The parent's `priority` is in the loaded `Task` struct.
   - What's unclear: Should mention-generated children inherit the parent's priority, default to 0, or be configurable?
   - Recommendation: **inherit from parent** by default. Justification: the mention is a direct delegation off the parent's work, so the priority semantics flow naturally. If a worker wants a different priority for the child, they can call `kanban_create` directly with explicit `parents=[parent_id]` instead. Document in LEARNINGS.

4. **What if `task_links` already contains a `(parent, child)` row from a prior tool call?**
   - What we know: `INSERT OR IGNORE INTO task_links` swallows duplicate rows silently (per `store.rs:414-418`).
   - What's unclear: If a worker happens to already have a manually-created child with the same assignee, the mention-flow would create a SECOND child (with a new id), not silently dedupe to the existing one.
   - Recommendation: this is **correct** — children are identified by id, not by `(parent, assignee)`. Document it. Receiver test `mention_with_existing_manual_child_creates_second_child` confirms.

5. **What's the right user-visible name for the LLM tool — `kanban_mention` or `kanban_delegate`?**
   - What we know: The phase name is "@mention delegation parser". Existing tools use action verbs (`create`, `complete`, `block`).
   - What's unclear: `kanban_mention` is shorter and aligns with `docs/kanban/reference.md` §741 ("P6 @mention"). `kanban_delegate` is more verb-shaped.
   - Recommendation: **`kanban_mention`** for consistency with the spec reference and the §741 vocabulary. Planner decides.

|---|---|---|

| Markdown smuggling (`@reviewer` hidden inside HTML-escaped content) | Tampering | We parse the raw body, not HTML-decoded; smuggled handles would need to literally appear as `@<word>` in source text. ## Sequencing vs Phase 36.3.7.7

- The mention-flow creates 1 parent → 1 child per resolved mention. There is no batch-of-N topology that requires `create_swarm`. The atomic-transaction primitive is a sibling method on `KanbanStore` — not a re-entrant call to `create_swarm`.
- The four locked structural patterns (tool-mounts-store-directly, BEGIN IMMEDIATE transactions, sibling-method shape, DEFERRED_KANBAN_SUBVERBS slash deferral) are inherited from 36.3.7.6 (CLOSED), NOT from 36.3.7.7.
