# Phase 36.3.7.8: Code Review Report

**Reviewed:** 2026-05-31T00:00:00Z
**Depth:** standard
**Files Reviewed:** 13
**Status:** issues_found

## Summary

The phase implements the `@mention` delegation parser as planned: a pure-function
Markdown fence-state-machine parser (`mention/parser.rs`), a three-stage resolver
with `FallbackPolicy` and self-reference detection (`mention/resolver.rs`), a
new store primitive `create_mention_children` with WITH RECURSIVE
ancestor-walk cycle detection and idempotency replay inside a `BEGIN IMMEDIATE`
transaction, an LLM tool `KanbanMentionTool` registered as the 11th kanban tool,
a CLI `kanban mention` verb, and 17 integration tests + 4 CLI parity tests.

Most of the priority-signal landmines flagged in PATTERNS.md are correctly
handled: SQL uses `params![]` end-to-end (no string interpolation), the
WR-01 fix from 36.3.7.7 is preserved (idempotency replay lookup happens
INSIDE `BEGIN IMMEDIATE`), the tool docstring + count was updated to 11,
mention is appended to `DEFERRED_KANBAN_SUBVERBS`, the CLI test scaffold
sidesteps the missing `Debug` derive on `KanbanCommands`, `cmd_mention` calls
the store directly (NOT the LLM tool registry), and the ancestor cycle SQL is
parameterised.

However, the adversarial pass found **two BLOCKER-class correctness bugs** in the
idempotency replay layer and an **identity-resolution mismatch between the CLI and
tool paths** that breaks the case-insensitive contract documented in REQ-04 for
the CLI surface. There is also a **LIKE-injection vector** in the idempotency
finder (low impact, but real) and a **dead match arm** that suggests the
resolver's responsibility boundary was lost during implementation. One unit test
(`mention_invalid_assignee_rolls_back_whole_batch`) does not exercise the
behaviour it claims to verify.

Recommendation: address CR-01, CR-02, WR-01, WR-02, and WR-03 before close-out;
the remaining warnings and info items can be deferred or addressed inline.

## Critical Findings

### CR-01: Idempotency replay only checks `:mention:0`; skipped index-0 yields phantom replay miss and UNIQUE violation

**File:** `crates/ironhermes-kanban/src/store.rs:1215-1239`

**Issue:** The replay short-circuit inside `create_mention_children` checks for
the existence of a single hard-coded suffix:

```rust
if let Some(ref base) = plan.idempotency_key {
    let first_key = format!("{base}:mention:0");
    let existing: Option<String> = tx
        .query_row(
            "SELECT id FROM tasks WHERE idempotency_key = ?1",
            params![first_key],
            ...
        )
```

`MentionChildSpec.mention_index` is the **0-indexed position in the ORIGINAL
parsed list** (see store.rs lines 105–109 and tools/mention.rs:247 — `for (i,
span) in spans.iter().enumerate()`). The first parsed mention may be skipped by
the resolver (malformed handle, self-reference, unknown-under-Skip-policy,
inside a fence) — in which case the first surviving `MentionChildSpec` has
`mention_index >= 1` and the persisted per-child key is `{base}:mention:1`,
`{base}:mention:2`, etc. — but **never** `{base}:mention:0`.

Concrete reproduction:

1. Body: `"@default ping @reviewer"`. The resolver returns
   `Skipped(Malformed)` for `@default` (reserved name) and `Resolved("reviewer")`
   for `@reviewer`. `children = [{mention_index: 1, assignee: "reviewer"}]`.
2. First call with `idempotency_key = Some("k")` inserts `tasks` row with
   `idempotency_key = "k:mention:1"`. (No `:mention:0` row is ever written.)
3. Second call with the same key: `first_key = "k:mention:0"` lookup misses,
   replay branch is skipped, `mention_insert_loop` runs again and attempts a
   second INSERT with `idempotency_key = "k:mention:1"`. SQLite UNIQUE
   constraint fires → `KanbanError::Db(...)` is propagated up.

The `tasks.idempotency_key` column is declared `UNIQUE`, so the second call
fails. The replay contract documented in REQ-12 ("re-invocation returns existing
children") is violated whenever the original parse contained a skipped mention
at index 0.

The defensive fall-through at line 1232–1237 (`first_key existed but LIKE scan
returned nothing — re-open tx and insert`) is reachable in the opposite direction
too: if some other process inserted a `:mention:0` between the first read and
the shared `find_mentions_by_idempotency_key` borrow re-acquisition, but in
practice this branch is the same hazard inverted.

**Fix:** Use the same LIKE scan that `find_mentions_by_idempotency_key`
already implements, scoped to the base key prefix, to detect *any* persisted
child under this batch. (Note: see WR-03 for the LIKE-escape concern that must
be addressed at the same time.)

```rust
if let Some(ref base) = plan.idempotency_key {
    let pattern = like_escape(base) + ":mention:%";
    let existing: Option<String> = tx
        .query_row(
            "SELECT id FROM tasks WHERE idempotency_key LIKE ?1 ESCAPE '\\' LIMIT 1",
            params![pattern],
            |r| r.get(0),
        )
        .optional()
        .map_err(KanbanError::from)?;
    if existing.is_some() {
        tx.commit()?;
        if let Some(replay) = self.find_mentions_by_idempotency_key(base)? {
            return Ok(replay);
        }
        // Defensive fall-through unchanged.
    }
}
```

### CR-02: CLI `cmd_mention` does not lowercase `parent_assignee` or DB-returned `known_assignees`, breaking case-insensitive resolution contract on the CLI path

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:626-653`

**Issue:** The LLM tool (`tools/mention.rs:213-233`) lowercases both the
DB-returned assignees and the parent assignee before populating `ResolverCtx`:

```rust
for r in rows {
    if let Ok(a) = r {
        set.insert(a.to_lowercase());       // tool path: lowercased
    }
}
let parent_assignee = parent.assignee.to_lowercase();   // tool path: lowercased
```

The CLI path (`commands.rs:634-650`) does neither:

```rust
let mut set = HashSet::new();
for r in rows {
    set.insert(r.context("Failed to read assignee row")?);    // CLI: raw
}
...
let parent_assignee = parent.assignee.clone();   // CLI: raw
```

Resolver step 3 (`resolver.rs:176`) compares the lowercased handle against
`ctx.parent_assignee` for the self-reference check; resolver step 4
(`resolver.rs:181`) compares the lowercased handle against
`ctx.known_assignees`. The resolver doc comment at `resolver.rs:139` requires
`known_assignees` to be "all lowercase, all pre-validated"; the CLI path
violates this precondition.

Today this passes the integration tests because `validate_profile_name` rejects
uppercase at task-creation time, so DB rows are always lowercase. But:

1. The contract is brittle — any future code path that inserts an assignee via
   raw SQL (tests, migrations, repair scripts) bypasses the lowercase guarantee
   and silently changes CLI behaviour vs. tool behaviour.
2. The two code paths produce different `Resolution` outcomes for the same input
   when given a mixed-case `parent.assignee`. REQ-04 (case-insensitive handle
   resolution) is documented as a tool-level guarantee; the CLI must honour it
   too because cmd_mention is the operator-recovery path users will hit when the
   LLM is unavailable.
3. Test `mention_case_insensitive_handle_resolution` (tools_smoke.rs:1995) is a
   resolver-level unit test that calls `resolve_mention` directly with a
   pre-lowercased context — it does NOT exercise the CLI's context construction
   and therefore does not catch this divergence.

**Fix:** Mirror the tool's normalization in `cmd_mention`:

```rust
// known set
for r in rows {
    let a = r.context("Failed to read assignee row")?;
    set.insert(a.to_lowercase());
}

// parent assignee
let parent_assignee = parent.assignee.to_lowercase();
```

### WR-01: `find_mentions_by_idempotency_key` LIKE pattern is unescaped; `_` / `%` in base key allows cross-batch row leakage

**File:** `crates/ironhermes-kanban/src/store.rs:1094-1116`

**Issue:** The replay-finder builds its LIKE pattern by direct interpolation:

```rust
let pattern = format!("{base_key}:mention:%");
let mut stmt = self.conn.prepare(
    "SELECT id, idempotency_key, assignee \
     FROM tasks \
     WHERE idempotency_key LIKE ?1 \
     ORDER BY idempotency_key",
)?;
```

`base_key` is operator/LLM-supplied (it flows from `--idempotency-key` on the
CLI and from the `idempotency_key` arg on the LLM tool). SQLite LIKE treats
`_` as "any single character" and `%` as "any run of characters" with no
default escape. An operator who supplies the key `my_batch_1` for one fan-out
will match rows persisted under `myxbatchY1:mention:0` in a subsequent
`find_mentions_by_idempotency_key("my_batch_1")` call.

Impact:

- A replay can return children that belong to an unrelated batch, producing
  a cross-batch identity confusion in the returned `MentionResult.children`.
- Combined with CR-01's `:mention:0` hard-coded check (which uses `=`, not
  `LIKE`, so is exact), this confusion is silent — no UNIQUE violation, just
  wrong replay output.
- Not a SQL-injection vector in the classical sense (params![] is used), but
  it is a glob-injection vector against the LIKE matcher.

**Fix:** Use a SQLite ESCAPE clause and escape `%`, `_`, and the escape
character itself in `base_key` before composing the pattern:

```rust
fn like_escape(s: &str) -> String {
    let mut out = String::with_capacity(s.len() + 4);
    for ch in s.chars() {
        match ch {
            '\\' | '%' | '_' => { out.push('\\'); out.push(ch); }
            _ => out.push(ch),
        }
    }
    out
}

let pattern = format!("{}:mention:%", like_escape(base_key));
// ... LIKE ?1 ESCAPE '\\'
```

Apply the same fix at every LIKE site that interpolates user-supplied data
(only this site and the CR-01 fix site in this phase).

### WR-02: `mention_invalid_assignee_rolls_back_whole_batch` does not actually test rollback — the failure point is the pre-tx pre-flight, no rows are ever inserted

**File:** `crates/ironhermes-kanban/tests/tools_smoke.rs:2026-2097`

**Issue:** The test claims to verify REQ-11 (atomic rollback of partial-insert
on failure). It injects an invalid assignee `"UPPERCASE_FAIL"` in the *second*
child of a two-child batch. But `create_mention_children` validates every
assignee in a pre-flight loop **before opening the transaction**:

```rust
// store.rs:1186-1190
for spec in &plan.children {
    ironhermes_core::profile::validate_profile_name(&spec.assignee)
        .map_err(|e| KanbanError::Other(anyhow::anyhow!("invalid assignee: {e}")))?;
}
// transaction opens AFTER this loop succeeds
```

When the second spec fails validation, the error is returned **before** any
INSERT is attempted. The "atomic rollback" assertion (`task_before ==
task_after`) holds trivially because no transaction was ever opened. The test
passes, but it would also pass if `mention_insert_loop` were rewritten to
auto-commit per child (i.e., the test is incapable of detecting a regression
that breaks atomicity).

To actually exercise the rollback path, the test needs a failure that fires
*after* the first INSERT lands but *before* the second commits. Candidates:

- Inject a duplicate per-child idempotency_key via a pre-seeded row (UNIQUE
  violation on the 2nd INSERT).
- Use `mention_index` collisions in two children of the same batch (per-child
  key collision inside the loop).
- Trip the WITH RECURSIVE ancestor-cycle check on the 2nd child but not the
  1st (insert the 1st, then the cycle check rejects the 2nd → rollback drops
  the 1st).

**Fix:** Add a separate test that triggers an in-loop failure (the cleanest
shape is a duplicate-per-child-key collision); keep the current test but
rename it to `mention_invalid_assignee_rejected_before_tx` so it reflects what
it actually tests.

### WR-03: Defensive fall-through opens a second `BEGIN IMMEDIATE` tx and re-runs `mention_insert_loop` which will fail with UNIQUE on the existing rows

**File:** `crates/ironhermes-kanban/src/store.rs:1232-1238`

**Issue:** When the replay short-circuit detects `first_key` exists but the
shared-borrow `find_mentions_by_idempotency_key` then returns `None`, the code
opens a second tx and runs `mention_insert_loop`:

```rust
if existing.is_some() {
    tx.commit()?;
    if let Some(replay) = self.find_mentions_by_idempotency_key(base)? {
        return Ok(replay);
    }
    // Defensive fall-through
    let tx = self
        .conn
        .transaction_with_behavior(TransactionBehavior::Immediate)?;
    return Self::mention_insert_loop(tx, plan);
}
```

The doc comment dismisses this as "shouldn't happen under normal use," but
once CR-01 is fixed the surface area for this branch shrinks to a real race:
some other writer deleted the row between the existence check and the LIKE
scan. The re-entry into `mention_insert_loop` will:

1. Walk `plan.children` and attempt to INSERT with `idempotency_key =
   "{base}:mention:{i}"`. If *any* row at that key still exists, UNIQUE fires
   and the whole new tx rolls back.
2. If the rows were truly deleted, the loop succeeds — but the original
   children are gone and the new child IDs differ from the previously-returned
   IDs, breaking the replay-stability contract.

There is also a TOCTOU subtlety: after `tx.commit()` (which committed nothing),
another `BEGIN IMMEDIATE` from a concurrent writer is no longer blocked. The
WR-01 fix from 36.3.7.7 specifically required the lookup to be inside a single
`BEGIN IMMEDIATE` boundary. The "commit-and-re-borrow" workaround introduced
here to satisfy the borrow checker re-opens the same race the WR-01 fix
closed.

**Fix:** Eliminate the &mut/&borrow conflict by inlining the LIKE-scan replay
inside the same tx (no need to call `&self.find_mentions_by_idempotency_key`).
Prepare and execute the LIKE statement directly on `&tx`, then `tx.commit()`
exactly once before returning the result. This collapses the two-phase dance
into a single atomic step and removes the defensive fall-through entirely.

### WR-04: `Resolution::Skipped(SkipReason::Cycle)` arm in `tools/mention.rs` is dead code (resolver never returns it) — masks a real responsibility-boundary bug

**File:** `crates/ironhermes-kanban/src/tools/mention.rs:291-296`

**Issue:** The tool's match block handles a `Cycle` skip reason:

```rust
Resolution::Skipped(SkipReason::Cycle) => {
    skipped.push(json!({
        "handle": span.handle,
        "reason": "cycle"
    }));
}
```

But the resolver (`resolver.rs:161-198`) NEVER returns
`Resolution::Skipped(SkipReason::Cycle)` — cycle detection is delegated to the
store layer (`store.rs:1271-1302`) per Landmine 3 in PATTERNS.md. The store's
cycle detection raises a `KanbanError` and terminates the whole batch — it
does NOT translate into a per-handle skip.

Consequences:

1. Dead match arm — `Cycle` cannot be produced by `resolve_mention`. A reader
   trying to understand "when does a handle get marked as cycle-skipped?" is
   misled.
2. The store's ancestor-cycle outcome (whole-batch error) is structurally
   different from a per-handle skip. If someone added a per-handle cycle pre-check
   to the resolver later (e.g., to avoid the batch-abort cost), they'd expect
   this code path to work — but the resolver context has no DB connection
   (`resolver.rs:132-144`), so layer-2 detection can't move there without an
   API change.

Either:

- Remove the arm and update `SkipReason::Cycle`'s doc comment to clarify it
  is a "reserved-for-future-use" variant the store doesn't produce; OR
- Wire up a Resolver-side ancestor-cycle entrypoint (signature change to
  `ResolverCtx`) so the variant has a producer.

**Fix (minimal):**

```rust
// resolver.rs — remove or annotate:
SkipReason::Cycle,   // RESERVED — currently produced by store layer
                     // only as KanbanError::Other("mention_cycle: ...").

// tools/mention.rs — remove the unreachable arm or annotate it
// `// SAFETY: produced by future resolver-side cycle check; today the store
// // raises mention_cycle as a whole-batch error instead.`
```

### WR-05: `cmd_mention` propagates `--fallback-policy=error` failure as a plain `anyhow!` error, not a structured rejection envelope

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:678-693`

**Issue:** When the CLI encounters an unknown handle under
`FallbackPolicy::Error`, it bails with `Err(anyhow!(...))`:

```rust
if matches!(policy, FallbackPolicy::Error)
    && matches!(reason, SkipReason::UnknownHandle)
{
    return Err(anyhow!(
        "unknown_handle: handle '{}' did not resolve under fallback_policy=error",
        span.handle
    ));
}
```

The LLM tool path (`tools/mention.rs:301-309`) returns a JSON
`{"status":"rejected","reason":"unknown_handle"}` envelope. A user wiring the
CLI into a shell script gets:

- A non-zero exit code (good — `Result::Err` → `?` propagates up to `main`).
- An error message printed to **stderr** by the binary's top-level error
  handler (`hermes` wraps anyhow errors), not a parseable JSON object even
  when `--json` is set.

This is inconsistent with the rest of the CLI's `--json` output contract.
Operators recovering from an LLM-driven failure expect identical envelopes
between LLM-tool output and CLI output for the same logical operation.

**Fix:** When `--json` is set, print the rejected envelope to stdout and
return `Ok(2)` (non-zero exit, but no stderr). Mirror the tool's envelope
shape:

```rust
if matches!(policy, FallbackPolicy::Error)
    && matches!(reason, SkipReason::UnknownHandle)
{
    if json {
        println!(
            "{}",
            serde_json::to_string_pretty(&serde_json::json!({
                "status": "rejected",
                "reason": "unknown_handle",
                "detail": format!("handle '{}' did not resolve", span.handle),
            }))?
        );
        return Ok(2);
    }
    return Err(anyhow!(...));
}
```

### WR-06: `mention_ancestor_cycle_skipped` test accepts BOTH `Err` AND `Ok` outcomes — the test passes regardless of whether layer-2 cycle detection actually fires

**File:** `crates/ironhermes-kanban/tests/tools_smoke.rs:1842-1859`

**Issue:** The test's success arm is permissive to the point of vacuity:

```rust
match result {
    Err(e) => { /* asserts error message contains "cycle" */ }
    Ok(r) => {
        // Layer-2 skipped it — result.children may be 0 or the store allowed it.
        // At minimum the DB must not have a cycle: assert t4's child (if any)
```

The `Ok(r)` arm does *nothing* — it doesn't even assert that

under the supplied fixture (chain `t1(alice) → t2(bob) → t3(alice) → t4(bob)`,

### WR-08: `cmd_mention` JSON output omits the `status` field present in the LLM tool envelope

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:719-731`

**Issue:** The tool's success envelope (`tools/mention.rs:359-364`) is:

```json
{
  "task_id": "...",
  "mentions_parsed": N,
  "children_created": [...],
  "skipped": [...]
}
```

The CLI's `--json` output mirrors this shape, but neither path includes a
`"status": "ok"` field. The rejection envelope from `reject()`
(`tools/mention.rs:84-92`) has `"status":"rejected"`. A consumer parsing both
shapes has to test for the presence of `reason` vs. `children_created` to
disambiguate. A `"status":"ok"` (or `"status":"success"`) in the success path
removes that ambiguity.

This is a minor consistency nit — not a behavioural bug — but it makes
downstream parsers more fragile than necessary.

**Fix:** Add `"status":"ok"` to both the tool and CLI success envelopes, OR
document explicitly in the docstring that the absence of `"status"` means
success.

### IN-01: `mention/parser.rs::handle_re` regex permits trailing hyphen handles (`@foo-`); resolver then rejects them as malformed silently

**File:** `crates/ironhermes-kanban/src/mention/parser.rs:62`

**Issue:** The regex `@([A-Za-z0-9][A-Za-z0-9-]*)` greedily consumes a trailing
hyphen if one appears immediately before whitespace or end-of-string:
`@foo-` extracts `"foo-"`. `validate_profile_name` rejects names ending in
`-` (consequence of the character class plus the leading-character rule),
so the resolver returns `Skipped(Malformed)` and the user sees a "malformed"
skip without an explanation that the hyphen-position rule was the issue.

This is cosmetic — the system behaves safely. Mention the rule in the
parser's doc comment if desired:

```rust
//! Note: `@foo-` extracts "foo-" which fails validate_profile_name
//! (trailing hyphen). The resolver reports this as Skipped(Malformed).
```

### IN-02: `redact_non_prose` invariant assertion is `debug_assert_eq!` — silently degrades in release builds

**File:** `crates/ironhermes-kanban/src/mention/parser.rs:233-237`

**Issue:** The byte-length invariant (`redact_non_prose(body).len() ==
body.len()`) is the linchpin that makes returned byte offsets safe to slice
back into the original `body`. In release builds (which kanban ships as),
`debug_assert_eq!` is a no-op. If a future refactor breaks the invariant,
release callers would silently corrupt offsets.

Given the parser is pure and downstream consumers don't slice `body` by
`byte_offset` today (the consumer uses `span.handle`, not `&body[offset..]`),
the impact is currently nil. But the invariant doc at line 18–21 explicitly
promises offsets that point into `body`, so the invariant should hold in
release.

**Fix:** Promote to `assert_eq!` if performance is acceptable (one length
comparison at the end of the function — trivial cost), or remove the doc
promise.

### IN-03: Resolver doc comment for `FallbackPolicy::Pending` says `"pending"` is a valid profile name "confirmed in RESEARCH.md §Pitfall 5" but no test asserts this against `validate_profile_name`

**File:** `crates/ironhermes-kanban/src/mention/resolver.rs:188-192`

**Issue:** The contract relies on the assertion that
`validate_profile_name("pending")` succeeds. Today it does (lowercase, non-
reserved). But there is no defensive unit test that pins this — if someone
adds `"pending"` to `RESERVED_NAMES` in `ironhermes_core::profile`, the
Pending policy silently produces invalid `MentionPlan.children` entries that
