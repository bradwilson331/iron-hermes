## Summary

Phase 36.3.7.10 ships the LLM-driven decomposer + specifier that transforms one-liner `triage` tasks into structured, actionable work graphs. The phase has two tightly related deliverables: (1) a **specifier** (`hermes kanban specify <id>`) that rewrites a triage card's body in-place with structured fields and promotes it to `todo`; and (2) a **decomposer** (`hermes kanban decompose <id>`) that fans a triage task out into a swarm graph of child tasks and promotes the parent to `todo`. Auto-mode wires the decomposer into the dispatcher's existing 8-step tick loop as a new Step 0 (runs before crash-detection) or Step 5.5 (runs after `promote_ready`). The config knob `kanban.auto_decompose` (bool, default `false` for v1 — see Q7) and `kanban.auto_decompose_per_tick` (u32, default 3) live in the existing `KanbanConfig` struct in `crates/ironhermes-kanban/src/config.rs`.

The decomposer calls an LLM using a config-driven auxiliary model slot — a new `auxiliary.kanban_decomposer` key added to the existing `AuxiliaryConfig`-like pattern in `KanbanConfig`. If no auxiliary model is configured, it falls back to the main provider via the existing `resolve_role` cascade. The decomposer writes its output directly to `tasks.body` (overwriting the one-liner) AND promotes status `triage → todo`. A `decomposed` event row is appended to `task_events`. The specifier follows the same body-update pattern but does not fan out; it just rewrites and promotes. This avoids introducing a new comment-based indirection that LLMs would have to re-read on every `kanban_show`.

**Primary recommendation:** Model the decomposer as a pure Rust async function in `crates/ironhermes-kanban/src/decomposer.rs` that takes a `Task` + `KanbanConfig` + a `ProviderClient` (injected, not hard-coded) and returns a `DecomposerResult` enum. CLI verbs (`hermes kanban decompose`, `hermes kanban specify`) call this function directly. The dispatcher tick injects it as a closure analogous to `spawn_fn` in `DispatcherContext`. No separate skill file is required for v1 — the LLM prompt is a static Rust string in the decomposer module.

### Q2: Dedicated skill vs. `delegate_task`?

**Recommendation: No skill file, no `delegate_task`. Use a direct HTTP call in `decomposer.rs`.**

Rationale:
- `delegate_task` spawns a child agent process and is heavyweight. The decomposer is a single LLM call that returns a structured JSON payload — closer to a tool call than a full agent session.
- The kanban crate (`ironhermes-kanban`) depends on `ironhermes-tools` (which has `DelegateTaskTool`) but `delegate_task` requires a `SubagentRunner` — an abstraction that requires an agent loop. The kanban crate is explicitly kept free of `ironhermes-agent` dependency.
- The `skills_bundle.rs` pattern embeds skill SKILL.md files for the kanban-worker and kanban-orchestrator. Adding a third skill for decompose would work but is over-engineered for what is a single structured prompt call.
- The clean pattern: `decomposer.rs` exposes a `pub type DecomposeFn = Arc<dyn Fn(DecomposeRequest) -> BoxFuture<Result<DecomposeOutput>> + Send + Sync>` injectable closure. Tests substitute a mock. Production implementation calls the configured LLM endpoint via `reqwest` (already a workspace dep) or via a thin wrapper over the existing provider client.

[VERIFIED: `crates/ironhermes-kanban/Cargo.toml` — no `reqwest` direct dep; but `ironhermes-core` has the provider client; the kanban crate can add a `DecomposeFn` injection point and let the caller (CLI/dispatcher) supply the real implementation from `ironhermes-agent` or `ironhermes-core`]

**Revised recommendation:** Define `DecomposeFn` as an injectable trait-object in `decomposer.rs` (same pattern as `SpawnFn` / `SendFn`). The production binding is wired at the CLI `cmd_decompose` / dispatcher startup, not inside the kanban crate itself. This preserves crate-isolation: `ironhermes-kanban` contains the prompt, the output schema, and the store writes; the actual HTTP call lives in the caller that has the provider client.

### Q3: Where does the decomposer write its output?

**Recommendation: Write directly to `tasks.body` AND promote `triage → todo` in one atomic transaction.**

Evidence:
- `tasks` schema at `schema.rs:31–55` has a `body TEXT` column. [VERIFIED: `crates/ironhermes-kanban/src/schema.rs:33`]
- The swarm tool at `store.rs:960` writes multiple rows in a `BEGIN IMMEDIATE` transaction.
- Writing to `tasks.body` means `kanban_show` surfaces the decomposed spec immediately, no extra query.
- Emitting a comment instead would require workers to read comments in addition to `body` — more brittle, wastes tokens.
- The `decomposed` event row in `task_events` provides the audit trail without duplicating the body.

**Atomic transaction contents:**
```sql
BEGIN IMMEDIATE;
UPDATE tasks SET body = ?new_body, status = 'todo' WHERE id = ?task_id AND status = 'triage';
INSERT INTO task_events (task_id, kind, payload, created_at) VALUES (?task_id, 'decomposed', ?payload, ?now);
-- For decompose only: INSERT child tasks + INSERT task_links ...
COMMIT;
```

The `WHERE status = 'triage'` guard prevents a race where two ticks try to decompose the same task simultaneously.

### Q4: When does auto-mode trigger?

**Recommendation: New Step 0 in `run_dispatch_tick_for_board`, before crash-detection.**

The existing 8 steps run in order: detect_crashed → extend_live_pid_claims → reclaim_stale → enforce_max_runtime → promote_ready → claim_and_spawn.

The decomposer should run BEFORE all other steps because:
1. Decomposed tasks transition `triage → todo`, then `promote_ready` (Step 5) can immediately advance them to `ready` if they have no parents. One tick completes the full pipeline.
2. Running after `promote_ready` would require a second tick before decomposed children become `ready`.

Implementation: add `decompose_triage_tasks(ctx)` as a new function called at the top of `run_dispatch_tick_for_board`. Gate on `ctx.config.auto_decompose`. Apply `auto_decompose_per_tick` cap.

[VERIFIED: `crates/ironhermes-kanban/src/dispatcher.rs:216–279` — `run_dispatch_tick_for_board` is the correct injection point; it's already structured as isolated steps]

**Trigger surface for manual mode:** CLI `hermes kanban decompose <id>` calls the same `decompose_triage_task()` store function directly. No dispatcher involvement.

### Q5: How to handle decomposer failures?

**Recommendation: Retain task in `triage`, append `decompose_failed` event, log warning. NO retry/backoff in v1.**

Rationale:
- The circuit breaker in the dispatcher operates on `running` tasks (workers that crash/timeout). Triage tasks are not in the `running` state — they are not claimed. The circuit breaker should NOT be applied to decomposer failures (wrong lifecycle stage).
- Retaining in `triage` is the safest policy: the operator can see the failure, fix the task title, and re-trigger manually.
- A `decompose_failed` event payload contains `{"reason": "llm_error" | "parse_error" | "no_aux_client", "message": "..."}`.
- Per-tick cap (`auto_decompose_per_tick = 3`) acts as a natural rate limiter.
- Backoff: not in v1. The dispatcher's 60s tick interval provides natural backoff. A task that fails decomposition will be retried on the NEXT tick — up to once per minute. If the operator wants to suppress retries, they move the task out of `triage` manually.

### Q8: Decomposer output schema

**Recommendation: Structured Markdown body with TOML frontmatter-style sections.**

The `tasks.body` column is `TEXT`. The decomposer writes a canonical Markdown format:

```markdown
## Goal
<one sentence stating what success looks like>

## Approach
<brief description of the execution strategy>

## Acceptance Criteria
- [ ] <criterion 1>
- [ ] <criterion 2>
- [ ] <criterion 3>

## Work Breakdown
- **<subtask 1 title>** (→ @<assignee>): <one-liner>
- **<subtask 2 title>** (→ @<assignee>): <one-liner>

## Risk Register
| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| <risk> | low/med/high | <mitigation> |

## Suggested Skills
<comma-separated skill names, e.g. `software-development, research`>
```

**Justification:**
- Human-readable in `kanban show` and the dashboard markdown renderer (which already handles headings, bold, lists, tables per reference.md §417).
- LLMs produce this format reliably; no JSON parsing failure modes.
- Workers reading `kanban_show` body get the spec in their system prompt without extra parsing.
- The `## Work Breakdown` section drives child task creation (for `decompose`); the `specify` path only writes this body and promotes to `todo` — no children.

**For `decompose`: the LLM also returns a JSON task graph (separate from body):**

The decomposer LLM call returns a structured JSON object used to create child tasks:
```json
{
  "new_title": "Add Stripe payment integration",
  "new_body": "<markdown body as above>",
  "children": [
    {"title": "...", "assignee": "researcher", "body": "..."},
    {"title": "...", "assignee": "developer", "body": "..."}
  ],
  "skills": ["software-development"]
}
```

This JSON is parsed in Rust (via `serde_json`), then `store.create_swarm` (already existing at `store.rs`) or a new `store.create_decompose_children` is called atomically. **Recommendation: reuse the existing `create_swarm` path** — decompose children map to "workers" in the swarm topology (Shape 1: root → workers). The root task IS the original triage task (promoted to `todo`), not a new card.

[VERIFIED: `crates/ironhermes-kanban/src/store.rs:725–960` — `create_swarm` creates root + workers atomically; the decomposer variation is: existing task becomes the parent, children created as `todo` with parents=[original_task_id]]

```rust
    pub title: String,
    pub body: Option<String>,
    pub assignee: String,
    pub config: KanbanConfig,
}

pub struct DecomposeOutput {
    pub new_title: String,
    pub new_body: String,
    pub children: Vec<ChildSpec>,  // empty for specify-only
}

pub struct ChildSpec {
    pub title: String,
    pub assignee: String,
    pub body: Option<String>,
}

/// Injectable LLM call. Production: calls provider client. Tests: returns fixture.
pub type DecomposeFn =
    Arc<dyn Fn(DecomposeRequest) -> BoxFuture<Result<DecomposeOutput>> + Send + Sync>;
```

### Pattern 3: Store Function `decompose_triage_task`

```rust
// In store.rs (or decomposer.rs calling store methods):
pub fn decompose_triage_task(
    &mut self,
    task_id: &str,
    new_body: &str,
    children: &[ChildSpec],
    config: &KanbanConfig,
) -> Result<DecomposedIds> {
    let tx = self.conn.transaction_with_behavior(TransactionBehavior::Immediate)?;
    // Guard: only act if still triage (prevents double-decompose)
    let status: String = tx.query_row(
        "SELECT status FROM tasks WHERE id=?1", params![task_id], |r| r.get(0)
    ).optional()?.ok_or_else(|| KanbanError::TaskNotFound(task_id.to_string()))?;
    if status != "triage" {
        return Err(KanbanError::WrongStatus { expected: "triage".into(), actual: status });
    }
    // Update parent task body + promote
    tx.execute("UPDATE tasks SET body=?1, status='todo' WHERE id=?2", params![new_body, task_id])?;
    // Append decomposed event
    // ... insert children + links ...
    tx.commit()?;
    Ok(DecomposedIds { child_ids, root_promoted: true })
}
```

### Anti-Patterns to Avoid

- **Storing decomposed output as a comment:** Workers reading `kanban_show` already get `body` in the system prompt. A comment-only approach forces workers to parse comments, wasting tokens and adding complexity.
- **Hardcoding the model in the kanban crate:** The `DecomposeFn` injection point keeps `ironhermes-kanban` free of provider client dependencies. Never import `ironhermes-agent` from `ironhermes-kanban`.
- **Applying the circuit breaker to decomposer failures:** The circuit breaker operates on `running` tasks with worker processes. Triage tasks are not claimed; the circuit breaker model does not apply.
- **Using `delegate_task` for the decomposer:** Spawning a full child agent for a single structured JSON call is heavyweight. A direct LLM HTTP call via the injected `DecomposeFn` is correct.
- **Setting `auto_decompose: true` as the default:** Prior phases established the conservative pattern (notifier defaulting to `None`, boards not auto-switching). Ship `false` for v1.

## Failure Mode Policy

| Failure | Policy | Rationale |
|---------|--------|-----------|
| LLM call returns error (network, rate-limit, 500) | Retain in `triage`; append `decompose_failed` event with `reason="llm_error"`; log warn; continue to next task | Safe default; operator can see the failure; retry on next tick |
| LLM returns unparseable JSON | Retain in `triage`; append `decompose_failed` with `reason="parse_error"`; log warn | Same as above |
| LLM picks unknown assignee for a child | Route child to `config.default_assignee`; if also empty, route to task's own assignee | Mirrors reference.md §436: "decomposer NEVER lands a child task with assignee=None" |
| Task no longer in `triage` at write time (race) | `UPDATE ... WHERE status='triage'` returns 0 rows; log info "already processed"; skip without error | Idempotent; status guard is the only synchronization needed |
| `decompose_fn` is `None` in dispatcher | Skip Step 0 entirely (gate: `ctx.decompose_fn.is_some()`) | Gateway runner may not inject a decompose_fn in v1 if the provider client is not configured |
| `auto_decompose_per_tick` exhausted | Remaining triage tasks silently deferred to next tick | Reference.md §431 documents this cap explicitly |

## Common Pitfalls

### Pitfall 1: Crate-isolation fence violation

**What goes wrong:** Adding a direct dependency on `ironhermes-agent` (which has the provider HTTP client) from `ironhermes-kanban` to make LLM calls inline.
**Why it happens:** The decomposer needs to call an LLM; the HTTP client lives in the agent crate.
**How to avoid:** Use the `DecomposeFn` injection pattern (same as `SpawnFn`, `SendFn`). The kanban crate ONLY defines the type alias and the trait signature. The CLI (`cmd_decompose`) and the gateway runner provide the concrete implementation. The gate: `grep -E '^ironhermes-agent\s*=' crates/ironhermes-kanban/Cargo.toml` must return 0.
**Warning signs:** Build fails with "circular dependency" or `ironhermes-kanban` imports `ironhermes-agent` types.

### Pitfall 2: Tool count regression test

**What goes wrong:** Adding 2 new LLM tools but forgetting to update the `11`-tool count assertion in `tools/mod.rs:58`.
**Why it happens:** The assertion is an integer literal, not derived from the registration list.
**How to avoid:** Update the assertion to `13` in the same commit as the `register_kanban_tools` extension. Gate in verifier: `grep -c 'exactly 13' crates/ironhermes-kanban/src/tools/mod.rs` = 1.

### Pitfall 3: `RESERVED_ROLE_NAMES` count doc-comment drift

**What goes wrong:** Adding `"kanban_decomposer"` to the array but not updating the doc-comment "The seven reserved auxiliary role names" and the count assertion test.
**Why it happens:** The count appears in both the comment and a test assertion.
**How to avoid:** In `config.rs:48`, update the doc-comment from "seven" to "eight". Update the count test at line 2484.

### Pitfall 4: Double-decompose race in dispatcher

**What goes wrong:** Two rapid dispatcher ticks both read the same triage task before either commits the `UPDATE status='todo'`.
**Why it happens:** The dispatcher tick runs every 60s by default but tests may run ticks back-to-back.
**How to avoid:** The `UPDATE tasks SET status='todo' WHERE id=? AND status='triage'` guard ensures only one write succeeds. Check `rows_affected` — if 0, the task was already processed; return `Ok(DecomposedIds::already_processed())` without error.

### Pitfall 5: `DEFERRED_KANBAN_SUBVERBS` omission

**What goes wrong:** Gateway `/kanban decompose` falls through to the deferred-verb error if `"decompose"` is not added to `DEFERRED_KANBAN_SUBVERBS` before a gateway slash arm is wired.
**Why it happens:** The catch-all at `handlers.rs:1288` gives a confusing "not found" error.
**How to avoid:** Add `"decompose"` and `"specify"` to `DEFERRED_KANBAN_SUBVERBS` FIRST (Wave 1), wire the actual gateway slash arms LAST (or in a follow-up phase).

## Open Questions

1. **Does `decompose_fn` need to be injected into the gateway runner at startup?**
   - What we know: The dispatcher runner at `crates/ironhermes-gateway/src/runner.rs` spawns `run_dispatch_loop` with a `DispatcherContext`. If `decompose_fn: None`, auto-decompose is silently a no-op.
   - What's unclear: The gateway runner has access to the main provider client (via the agent runtime it already spawns). Wiring the real `DecomposeFn` into the runner requires importing the provider client — which may or may not be a circular dependency issue.
   - Recommendation: Planner should decide: (a) wire `decompose_fn` in gateway runner (Phase 36.3.7.10), or (b) leave as `None` in v1 and only support CLI-triggered decompose. Option (b) is safer for the first version.

2. **Should `KanbanDecomposeTool` and `KanbanSpecifyTool` appear in the LLM tool count test?**
   - Currently the test asserts `11` tools. If both decompose and specify are added as LLM tools, it becomes `13`. If they are CLI-only in v1 (no LLM tool exposure), the count stays at `11`.
   - Recommendation: Add both as LLM tools (orchestrators should be able to call `kanban_decompose` on a task). Count → `13`.
