# Phase 36.3.7.10: Code Review Report

**Reviewed:** 2026-05-31
**Depth:** standard
**Files Reviewed:** 23 (Phase 36.3.7.10 deltas — LLM-driven decomposer / specifier)
**Status:** issues_found

## Summary

Phase 36.3.7.10 wires an LLM-driven decomposer/specifier kernel (`crates/ironhermes-kanban/src/decomposer.rs`), two CLI verbs (`hermes kanban decompose|specify`), two LLM tool stubs (`kanban_decompose`, `kanban_specify` — observable but quiescent in v1), a dispatcher Step 0 (auto-decompose) gated by `auto_decompose` config, and the production `build_runtime_decompose_fn` LLM bridge in `crates/ironhermes-cli/src/kanban/commands.rs`.

The atomic-transaction primitives in `apply_specify` / `apply_decompose` are solid (status-guarded UPDATE + same-tx event/link INSERTs), the test coverage of the kernel (`tests/decomposer_logic.rs`) is comprehensive (5 happy/sad-path cases with mock injection), and the dispatcher Step 0 gating is correct (both `auto_decompose` and `decompose_fn.is_some()` must pass — graceful no-op otherwise).

However, **the LLM JSON-parsing seam in `build_runtime_decompose_fn` has three serious defects**: (1) a panic-prone `&raw_text[..raw_text.len().min(200)]` slice that does not respect UTF-8 char boundaries (BLOCKER), (2) an empty-string fallback for missing `new_body` that silently overwrites the task body with `""` on a malformed LLM response and STILL promotes triage → todo (BLOCKER — data loss), and (3) an HTTPS-only API-key guard that allows empty-key HTTP endpoints to pass clearance (security gap). Two `cmd_decompose` JSON-output sites also report **wrong `new_title` values** (`task.title` pre-rewrite in `--all` mode, hard-coded `""` in single-id mode), creating an observable contract mismatch with the documented `{ok, task_id, reason, fanout, child_ids, new_title}` envelope. The `apply_decompose` child-INSERT path likewise loses tenant context (parent's `tenant` is not propagated, all children get NULL).

Multiple smaller correctness/quality issues are documented below.

## Critical Issues

### CR-01: UTF-8 boundary panic in error truncation slice

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1506`
**Issue:** When the LLM returns a non-JSON response, the parse-failure error is formatted with `&raw_text[..raw_text.len().min(200)]`. `len()` is the byte length, not the char count — if byte 200 lands mid-codepoint on multi-byte UTF-8 input (common for non-English LLM output, emojis, mathematical symbols), the slice panics with `byte index N is not a char boundary`. The panic propagates out of the `DecomposeFn` future, crashes the entire `cmd_decompose` invocation, and leaves the triage task in an inconsistent state (no `decompose_failed` event is appended because the kernel never receives the `Err`).

**Fix:**
```rust
// Replace the byte-slice with a char-boundary-aware truncate.
let preview: String = raw_text.chars().take(200).collect();
let parsed: serde_json::Value = serde_json::from_str(&raw_text)
    .map_err(|e| ironhermes_kanban::KanbanError::Other(anyhow::anyhow!(
        "parse_error: LLM response is not valid JSON: {} (raw: {})",
        e,
        preview
    )))?;
```

### CR-02: Silent data loss when LLM response is missing `new_body`

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1509-1516`
**Issue:** When the LLM produces a JSON object that is structurally valid but missing one of the required fields, the closure papers over the gap with `.unwrap_or("(untitled)")` for `new_title` and `.unwrap_or("")` for `new_body`. The kernel then commits `apply_specify` / `apply_decompose` with `new_body = ""`, which permanently overwrites the operator's original triage description, promotes the task `triage → todo`, and appends a `specified` / `decomposed` event with no signal that the body was lost. The operator now has a body-less task in `todo` and no way to recover the original triage prose (it was overwritten inside the same `BEGIN IMMEDIATE` transaction).

**Fix:** Reject the LLM output when required fields are missing rather than substituting defaults. Bubble up `Err(...)` so the kernel appends the `decompose_failed` event and the task is retained in `triage`.
```rust
let new_title = parsed["new_title"]
    .as_str()
    .ok_or_else(|| ironhermes_kanban::KanbanError::Other(anyhow::anyhow!(
        "schema_error: LLM response missing required `new_title` field"
    )))?
    .to_string();
let new_body = parsed["new_body"]
    .as_str()
    .ok_or_else(|| ironhermes_kanban::KanbanError::Other(anyhow::anyhow!(
        "schema_error: LLM response missing required `new_body` field"
    )))?
    .to_string();
// (children may legitimately be empty per the prompt — leave the `.unwrap_or(&empty_vec)` path)
```

### CR-03: API-key guard only fires for HTTPS endpoints

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1435-1441`
**Issue:** The startup check that surfaces a clear "decomposer model not configured" error to the operator only runs when the resolved endpoint starts with `https://`:
```rust
let api_key = endpoint.api_key.clone().unwrap_or_default();
if api_key.is_empty() && endpoint.base_url.starts_with("https://") {
    anyhow::bail!("decomposer model not configured — ...");
}
```
Any operator who points `model.default` at a misconfigured HTTP endpoint (proxy typo, copy-paste of `http://` from local-dev docs, accidental downgrade) bypasses the guard. The closure proceeds to construct an `LlmClient` with `api_key = ""`, the LLM call returns an unauthenticated error, the kernel correctly appends a `decompose_failed` event — but the operator now believes the issue is the LLM (the error surface is generic) rather than missing config. Worse, if the HTTP endpoint accepts empty keys (some self-hosted gateways), arbitrary triage tasks may be sent to an unverified endpoint over plaintext.

**Fix:** Drop the protocol filter — empty key → fail closed regardless of scheme.
```rust
if api_key.is_empty() {
    anyhow::bail!(
        "decomposer model not configured — set `kanban.decomposer_model` in \
         config.yaml OR `auxiliary.kanban_decomposer` OR ensure `model.default` \
         is set with a valid API key (endpoint: {})",
        endpoint.base_url
    );
}
```

## Warnings

### WR-01: `cmd_decompose --all` JSON output reports the OLD `new_title`

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1597`
**Issue:** The `--all` sweep path emits `"new_title": task.title` in its JSON output, but `task.title` is the pre-decomposition title read by `list_tasks` BEFORE the kernel rewrote it. The documented JSON envelope (`{ok, task_id, reason, fanout, child_ids, new_title}`) is intended to surface the LLM's rewritten title — operators / downstream consumers get the stale value. The kernel's `DecomposedIds` struct does not expose `new_title` so the CLI cannot easily plumb it; the fix is to re-fetch the task after success, or extend the kernel return type.

**Fix:**
```rust
Ok(ids) => {
    // Re-read so we report the rewritten title rather than the stale pre-rewrite one.
    let new_title = {
        let s = store_arc.lock().await;
        s.get_task(&task_id).map(|t| t.title).unwrap_or_default()
    };
    if json {
        output_rows.push(serde_json::json!({
            "ok": true,
            "task_id": task_id,
            "reason": serde_json::Value::Null,
            "fanout": ids.child_ids.len(),
            "child_ids": ids.child_ids,
            "new_title": new_title,
        }));
    }
    ...
}
```

### WR-02: `cmd_decompose` / `cmd_specify` single-id JSON output hard-codes `new_title: ""`

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1642, 1658, 1774, 1788`
**Issue:** Same defect as WR-01 but the single-id branch is even worse: it ships `"new_title": ""` unconditionally for both success and failure paths. Consumers cannot distinguish "the LLM produced an empty title" from "the CLI didn't bother to populate it" because the field is always empty in this code path.

**Fix:** Re-read the task after success and populate `new_title` from the fresh row. On failure, omit the field or substitute the original title.

### WR-03: `apply_decompose` drops parent's `tenant` when creating child rows

**File:** `crates/ironhermes-kanban/src/store.rs:2298-2305`
**Issue:** The child-INSERT statement hard-codes `tenant = NULL` (the 7th column binding):
```sql
INSERT INTO tasks (id, title, body, assignee, status, priority, tenant, workspace, skills, ...)
VALUES (?1, ?2, ?3, ?4, 'todo', 0, NULL, NULL, NULL, ...)
```
But the parent triage task may have been created with a `tenant` (multi-tenant boards rely on this for routing/isolation). Decomposed children end up tenant-less, which means: (1) tenant-scoped list/dispatch queries miss them, (2) `KanbanError::TenantMismatch` is bypassed if the parent/children later get linked via `insert_link_checked`, and (3) operator scoping (`--tenant engineering` on `kanban list`) won't show the work that just got fanned out. The `parent_assignee` cascade was implemented but the tenant analog was forgotten.

**Fix:** Propagate the parent's tenant to children. Load it before the loop and bind it:
```rust
let parent_tenant: Option<String> = tx.query_row(
    "SELECT tenant FROM tasks WHERE id = ?1",
    params![parent_id],
    |r| r.get(0),
)?;
// ...
tx.execute(
    "INSERT INTO tasks (id, title, body, assignee, status, priority, tenant, ...) \
     VALUES (?1, ?2, ?3, ?4, 'todo', 0, ?5, NULL, NULL, ...)",
    params![child_id, child.title, child.body, assignee, parent_tenant, ...],
)?;
```

### WR-04: Doc/impl drift — `ChildSpec` doc says empty `assignee` "never reaches the DB" but cascade can still produce empty

**File:** `crates/ironhermes-kanban/src/decomposer.rs:101-105`, `crates/ironhermes-kanban/src/store.rs:2289-2296`
**Issue:** The `ChildSpec::assignee` rustdoc states: *"Empty string must never reach the DB; the fallback cascade in [decompose_triage_task] enforces a non-empty value."* The actual cascade is:
```rust
let assignee = if !child.assignee.is_empty() {
    child.assignee.clone()
} else if !config.default_assignee.is_empty() {
    config.default_assignee.clone()
} else {
    parent_assignee.to_string()
};
```
If all three fall through (child empty + config empty + parent empty — possible if the parent task was seeded with `""` assignee, which `create_task` does not currently prevent), the child row is inserted with `assignee = ""`. There is no `if assignee.is_empty() { return Err(...); }` post-cascade guard. The dispatcher won't claim assignee-less tasks (they don't match any worker profile), so they stall silently in `todo`.

**Fix:** Add a post-cascade emptiness guard:
```rust
if assignee.is_empty() {
    return Err(KanbanError::Other(anyhow::anyhow!(
        "decompose: child '{}' has no resolvable assignee (child/config/parent all empty)",
        child.title
    )));
}
```

### WR-05: `cmd_specify` `--all` swallows `_ids.root_promoted` so JSON output cannot distinguish promoted vs. already-processed

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1728-1739`
**Issue:** The `Ok(_ids) => { ... }` arm discards `_ids.root_promoted`. When `specify_triage_task` short-circuits on a non-triage task (idempotent double-call), it returns `Ok(DecomposedIds { root_promoted: false, child_ids: [] })` — the CLI reports `"ok": true` with no signal that nothing happened. Operators looking at the JSON output cannot tell which tasks were actually promoted.

**Fix:** Surface `root_promoted` in the JSON envelope and adjust the human-readable path to print "(already specified — skipped)" when `!ids.root_promoted`.

### WR-06: `Decomposed` event payload omits `new_title`

**File:** `crates/ironhermes-kanban/src/store.rs:2333-2336`
**Issue:** The `decomposed` event payload only carries `child_count` and `child_ids`:
```rust
let decomposed_payload = serde_json::json!({
    "child_count": children.len(),
    "child_ids": child_ids,
});
```
Without `new_title`, downstream consumers (notifier, dashboard, audit log) must perform a second DB read to display "Decomposed task '<new title>' into N children". For high-volume boards this doubles the read load on the events feed. The `Specified` event payload (in `apply_specify`) DOES include `new_title` — the asymmetry between the two events is inconsistent.

**Fix:** Mirror the `apply_specify` payload — add `"new_title": new_title` to the decomposed payload.

### WR-07: Decomposer kernel reads task status outside the lock and again inside the apply transaction, but `DecomposeRequest.body` may be stale

**File:** `crates/ironhermes-kanban/src/decomposer.rs:168-185, 229-253`
**Issue:** The kernel correctly drops the lock before the LLM call to avoid serializing the dispatcher. The status guard inside `apply_specify` / `apply_decompose` catches a concurrent promotion (returns `Ok(already_processed)`). However, the `DecomposeRequest.body` passed to the LLM is captured BEFORE the lock is dropped, then committed verbatim hours later if the LLM is slow. If an operator edits the body in the interim (e.g. `kanban comment` adds context, or a worker writes a `heartbeat` annotation), those edits are silently overwritten by the LLM rewrite that was computed against the older body. The status guard does not catch body edits.

**Fix:** Either (1) lock body-edit operations against `status = triage` (treat the triage state as a soft lock on body edits), or (2) add an `expected_body_hash` field to the apply functions so concurrent body mutations cause a `body_changed` rejection.

### WR-08: `KanbanDecomposeTool` / `KanbanSpecifyTool` schema advertises capability the runtime cannot deliver

**File:** `crates/ironhermes-kanban/src/tools/decompose.rs:58-63`, `crates/ironhermes-kanban/src/tools/specify.rs:59-63`
**Issue:** The tool descriptions claim the tool will "fan the task out into a child-task swarm + promote the parent triage→todo" but `execute()` always returns the `no_aux_client` rejection. The schema-vs-implementation gap is mitigated by the descriptions' final sentence ("v1: returns `no_aux_client` if the decomposer is not wired in this runtime — use `hermes kanban decompose <id>` CLI verb instead"), but LLMs commonly truncate or skim long descriptions. An orchestrator that picks the tool based on the first sentence will invoke it, receive `no_aux_client`, and may not recover gracefully.

**Fix:** Either prepend `"[v1: NOT YET WIRED — use CLI] "` to the description's first sentence, OR omit the tool from registration when no runtime DecomposeFn is wired (controlled by an `explicit_enable` flag that the gateway runner sets to `false` until a runtime wiring lands).

### WR-09: `KanbanDecomposeTool` validates `task_id` but never uses it

**File:** `crates/ironhermes-kanban/src/tools/decompose.rs:101-120`, `crates/ironhermes-kanban/src/tools/specify.rs:101-120`
**Issue:** Both tools extract `_task_id`, bind it with a leading underscore, and immediately return `no_aux_client`. The validation effort is wasted — and worse, it sends mixed signals: a caller who passes a valid `task_id` gets the same rejection as one who passes an empty string, but the validation path adds a hidden DB-less code path the test suite must cover.

**Fix:** In v1, either delete the validation block (since the rejection is unconditional) or surface the validation in a separate `pre_check` method so the eventual wiring can reuse it without re-deriving it.

### WR-10: `Step 0` `decompose_triage_tasks` ignores `auto_decompose_per_tick` capacity drift between LLM calls

**File:** `crates/ironhermes-kanban/src/dispatcher.rs:1262-1271`
**Issue:** The function reads `triage_tasks` once at the start of the tick, then iterates up to `cap`. A long-running LLM call (or operator manually invoking `hermes kanban decompose` on a different shell) can promote tasks out of triage mid-tick. The kernel correctly short-circuits with `Ok(already_processed)`, but the iteration counts that as a "successful decomposition" attempt — the cap is consumed even though no LLM call was made. In high-throughput scenarios with many ad-hoc operator interventions, this prevents the dispatcher from reaching the actually-still-triage tasks lower in the list.

**Fix:** Re-check `task.status == "triage"` inside the loop before invoking the kernel, or distinguish "real work consumed cap" from "short-circuit consumed cap" so the loop can refill from the still-triage tail.

### WR-11: `cmd_specify` `--all` does NOT pass `author` into `DecomposeRequest.config.orchestrator_profile` for per-task attribution

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1687-1693, 1722-1727`
**Issue:** The `author` flag is folded into `kanban_config.orchestrator_profile` once at the top of `cmd_specify` and re-used for every task in `--all`. That is correct for the orchestrator identity but the per-task `specified` event payload (built in `apply_specify` at `store.rs:2219`) only records `new_title` — author attribution is never persisted. Operators sweeping all triage tasks lose the audit trail. The docstring on `cmd_specify` claims author is "threaded via the `author` field in the `HERMES_PROFILE` environment variable override (passed to DecomposeRequest.config.orchestrator_profile for author attribution in the `specified` event)" — the threading happens but the event never reads it.

**Fix:** Either (1) extend `apply_specify` to write the orchestrator profile into the event payload, or (2) update the docstring to remove the unfulfilled "author attribution in the `specified` event" claim. Option 1 is correct: events are the audit trail.

## Info

### IN-01: `_kanban_config_from_store` is read but never used

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1552, 1684`
**Issue:** Both `cmd_decompose` and `cmd_specify` call `store.config()`, bind it to `_kanban_config_from_store`, then ignore it entirely — `load_kanban_config(&main_config)` is the value actually used. The comment ("CR-WARNING-5 sourcing seam") suggests this is a deliberate placeholder, but as it stands the call is dead code. If the intent is to let store-level config override `main_config` per-board, the merge is missing.

**Fix:** Delete the binding (and the `store.config()` call) or implement the merge.

### IN-02: `std::mem::forget(dir)` leaks TempDirs across test binary lifetime

**File:** `crates/ironhermes-kanban/tests/decomposer_logic.rs:59`, `crates/ironhermes-kanban/src/tools/decompose.rs:131`, `crates/ironhermes-kanban/src/tools/specify.rs:131`
**Issue:** `std::mem::forget(dir)` is the established pattern in this repo to keep the tempdir alive past its lexical scope, but it permanently leaks the directory until the test binary exits. Multiplied across the test surface, large local test runs accumulate hundreds of `/tmp/.tmpXXXXXX/test.db` files. Lower-impact patterns: store the tempdir in a static guard, or use `tempdir.into_path()` (which intentionally drops cleanup) with a documented opt-out.

**Fix:** Acceptable as-is given test-suite-wide convention, but worth documenting in a `tests/README.md` so newcomers don't propagate the leak to non-test code.

### IN-03: `Decomposer` rustdoc references `Plan 05's cmd_decompose` for prose schema enforcement, but `build_runtime_decompose_fn` only documents the schema in the system prompt — no validation

**File:** `crates/ironhermes-kanban/src/decomposer.rs:30-43`
**Issue:** The docstring promises "The production implementation in Plan 05's `cmd_decompose` enforces the canonical Markdown schema". The actual enforcement is the system prompt at `commands.rs:1459-1470` — there is no schema validator that confirms the LLM honored the section headers. If the LLM omits "## Acceptance Criteria", the body is persisted as-is. Operators expecting to find the section will see a malformed task.

**Fix:** Either implement a lightweight Markdown validator (check for the 6 required H2 headers) or rewrite the docstring to describe the actual contract ("the prompt requests this schema; downstream consumers should not assume conformance").

### IN-04: `DecomposeRequest` carries `config: KanbanConfig` by clone — large and rarely read

**File:** `crates/ironhermes-kanban/src/decomposer.rs:79-80`
**Issue:** Every `DecomposeRequest` clones the full `KanbanConfig` struct (~13 fields, including the optional `PathBuf` and `Vec<String>`). The closure in `build_runtime_decompose_fn` doesn't read it. Tests don't read it. This is allocation churn for an unused field.

**Fix:** Either remove the field from `DecomposeRequest` (callers that need config can capture it in their closure), or change it to `Arc<KanbanConfig>` so the clone is cheap.

### IN-05: Title-length constraint declared in prompt but not enforced

**File:** `crates/ironhermes-cli/src/kanban/commands.rs:1463`
**Issue:** The system prompt says `"new_title": "<concise rewritten title (≤ 60 chars)>"`. The closure does not enforce it. LLMs routinely ignore length constraints. A 300-character `new_title` is persisted verbatim, breaks rendering in the TUI (`list_text` truncation), and bypasses operator expectations.

**Fix:** Truncate at the closure boundary: `let new_title = new_title.chars().take(60).collect::<String>();` with a tracing::warn when truncation fires.

### IN-06: `DEFERRED_KANBAN_SUBVERBS` adds `decompose` / `specify` but the unknown-subverb typo-suggest candidates don't include them

**File:** `crates/ironhermes-core/src/commands/handlers.rs:1151-1152, 1296`
**Issue:** Adding `decompose` and `specify` to `DEFERRED_KANBAN_SUBVERBS` routes them to the CLI-redirect message, which is correct. But the unknown-subverb typo-suggest list at line 1296 (`["list", "show", "tip", "create"]`) does not include them. A user who types `/kanban decmpose` will get a typo suggestion for a candidate that the slash command can't actually run — confusing UX since the suggestion correctly maps to a known deferred subverb but the user still has to type it into a CLI.

**Fix:** Include the deferred subverbs in the typo-suggestion candidate set so the typo path can suggest the correct CLI subverb (with a "use `hermes kanban decompose`" note in the response).

### IN-07: `KanbanDecomposeTool` / `KanbanSpecifyTool` store fields are `#[allow(dead_code)]` and never used

**File:** `crates/ironhermes-kanban/src/tools/decompose.rs:33-37`, `crates/ironhermes-kanban/src/tools/specify.rs:33-37`
**Issue:** Both tools accept an `Arc<TokioMutex<KanbanStore>>` they never read, suppressed with `#[allow(dead_code)]`. The `register_kanban_tools` callsite (mod.rs:128-131) clones the store Arc for them. This is wasteful (one extra Arc clone per registration) and obscures the contract — the tool's `new(store, explicit_enable)` signature lies about needing a store.

**Fix:** Drop the `store` field in v1; restore it when the runtime wiring lands. Document in the constructor's rustdoc that v1 ignores the store.
