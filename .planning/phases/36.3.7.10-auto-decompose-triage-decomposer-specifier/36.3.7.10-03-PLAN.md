Ship the 12th and 13th LLM tools in the kanban surface: `KanbanDecomposeTool` and `KanbanSpecifyTool`. Both tools follow the exact `#[async_trait] impl Tool` pattern established by the 11 existing tools (canonical analog: `tools/create.rs`), board-context-aware per the D-08 envelope contract from Phase 36.3.7.9, and call the Plan 02 kernel fns (`decompose_triage_task` / `specify_triage_task`) with a DecomposeFn sourced from the runtime env. Purpose: Orchestrator profiles need a programmatic way to invoke decompose/specify on triage tasks during their reasoning loop (e.g., "I see 5 triage tasks; let me kanban_decompose the highest-priority one before moving on"). The LLM tool surface is the orchestrator's interface to the kanban kernel. Plans 04 (dispatcher auto-mode) and 05 (CLI manual mode) are the OTHER two surfaces; this plan ships the LLM-callable surface specifically.

Output: 2 new files (`tools/decompose.rs`, `tools/specify.rs`) + 1 modified file (`tools/mod.rs`). Tool-count assertion changes 11→13. Zero changes to non-kanban crates. The two new tools' `execute` methods are deliberately conservative: they REQUIRE a DecomposeFn-producing env (e.g., `HERMES_DECOMPOSER_PROVIDER` + `HERMES_DECOMPOSER_MODEL`) to be configured; absent that, they return a structured `no_aux_client` rejection envelope rather than failing the orchestrator's reasoning loop.

- `pub async fn decompose_triage_task(store: Arc<TokioMutex<KanbanStore>>, task_id: &str, decompose_fn: &DecomposeFn, config: &KanbanConfig) -> Result<DecomposedIds>`

DecomposeFn sourcing in the tool: per RESEARCH §Q2, the kanban crate has no provider-client dependency. The two new tools resolve the DecomposeFn at execute() time via a NEW pub fn in `decomposer.rs` (added inline by this plan): `pub fn try_build_runtime_decompose_fn(config: &KanbanConfig) -> Option<DecomposeFn>` — returns `None` if no provider env vars are set; returns `Some(fn)` that calls the HTTP API using `reqwest` only when the operator has configured `HERMES_DECOMPOSER_PROVIDER` and `HERMES_DECOMPOSER_MODEL`. **IMPORTANT — REVISED PER PATTERNS.md/RESEARCH:** to honor the crate-isolation fence (zero `reqwest` dep on `ironhermes-kanban/Cargo.toml`), this plan does NOT add `try_build_runtime_decompose_fn` to the kanban crate. Instead, the two tools return a structured `no_aux_client` rejection envelope when invoked WITHOUT a wired DecomposeFn, and the LLM tool surface in v1 is **observable-but-quiescent** — the orchestrator can call `kanban_decompose` and will get a clear "decomposer not wired yet" response. The actual wiring of a production DecomposeFn into the LLM tool surface is **deferred to a future phase** (the CLI verbs in Plan 05 wire it directly via a CLI-only closure; the LLM tool surface needs a runtime-context injection mechanism that is out of scope for v1 of Phase 36.3.7.10).

To anchor that decision: the tool's `execute` method follows this contract: parse args → resolve board context → look up DecomposeFn in a runtime-context slot (NEW per-process `static` cell holding `Option<DecomposeFn>` populated by the CLI or by `register_kanban_tools` if a 3rd arg is supplied) → if None, return `reject_with_board("no_aux_client", "Decomposer not wired in this runtime — use `hermes kanban decompose <id>` CLI verb instead", &board_ctx)`; if Some, call the kernel fn and return ok_with_board.

This plan adds a 3rd arg to `register_kanban_tools` only IF it's backward-compatible — if not, the v1 implementation uses a `OnceCell<Option<DecomposeFn>>` static OR omits the wire entirely (tools return the rejection envelope unconditionally for v1). **PLANNING DECISION (binding for executor):** v1 ships the tools with `execute` returning `reject_with_board("no_aux_client", "...")` unconditionally — the registration is the value, the tool surface is observable in the schema, and the orchestrator gets a useful "use the CLI" response. The runtime-context injection mechanism is QUEUED for a follow-up phase; this keeps Phase 36.3.7.10 scope-fenced and the crate-isolation fence intact.
