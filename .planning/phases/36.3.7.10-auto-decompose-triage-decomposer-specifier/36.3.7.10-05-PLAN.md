<objective>
Ship the operator-facing CLI verbs `hermes kanban decompose [<id>|--all]` and `hermes kanban specify [<id>|--all]`. These are the ONLY production-wired decomposer surfaces in v1 (per Plan 03's deferred wiring of the LLM tool surface and Plan 04's deferred wiring of the gateway runner). The CLI is the right home for the production DecomposeFn because the CLI crate already depends on the ironhermes-core provider client (via the kanban worker spawn path) — no crate-isolation fence breakage.

Purpose: The operator types `hermes kanban decompose t_abc` from a terminal, the CLI loads KanbanConfig + main config, resolves the decomposer model via the three-tier cascade (kanban.decomposer_model > auxiliary.kanban_decomposer > main provider), constructs a DecomposeFn closure that calls the provider's text-completion endpoint with a fixed system prompt (encoded inline), parses the JSON response into a DecomposeOutput, hands it to the Plan 02 kernel which atomically updates tasks.body and creates child rows. Result printed as a table (default) or `{ok, task_id, child_ids, new_title}` JSON (--json).

Production DecomposeFn construction strategy (PLANNING DECISION — binding):

The CLI crate is the production home for the DecomposeFn. The closure construction lives in a NEW private fn `build_runtime_decompose_fn(config: &KanbanConfig, main_config: &Config) -> anyhow::Result<DecomposeFn>` inside `commands.rs`. This fn:
  1. Resolves the decomposer model via the three-tier cascade (RESEARCH §Q1):
     - Tier 1: `config.decomposer_model` if non-empty (kanban-local override).
     - Tier 2: `main_config.model.roles.get("kanban_decomposer")` if present.
     - Tier 3: `main_config.model.default` (main provider, same as the agent's chat model).
  2. Constructs an `Arc<dyn Fn(DecomposeRequest) -> BoxFuture<Result<DecomposeOutput>> + Send + Sync>` that, when called: (a) builds a system prompt encoding the canonical Markdown body schema from RESEARCH §Q8 + a JSON-output instruction; (b) builds a user message containing the task title + body + assignee + the operator's profile roster from main_config; (c) calls the resolved provider client (already exists in ironhermes-core; the CLI crate depends on it transitively via ironhermes-agent which it spawns kanban workers through); (d) parses the response as JSON via `serde_json::from_str::<DecomposeOutput>(...)`; (e) on parse failure returns `Err(anyhow!("parse_error: ..."))` so the kernel can append the right DecomposeFailed payload.
  3. Returns the closure wrapped in `Arc::new(...)`.

If no provider client can be constructed (e.g., no API key set, no config.yaml found), `build_runtime_decompose_fn` returns `Err` with a message naming the config keys the operator must set. The cmd_decompose / cmd_specify fns propagate this Err as `Ok(1)` (or unwrap with a clear stderr line), NOT a panic.

CLI verb argument shape (verbatim from RESEARCH §Q6):

`hermes kanban decompose [<id>] [--all] [--tenant T] [--json] [--board <slug>]`
- `id`: `Option<String>`, mutually exclusive with `all`.
- `all`: `bool`, mutually exclusive with `id`.
- `tenant`: `Option<String>`, only meaningful with `--all`.
- `json`: `bool`, output format flag.
- `board`: `Option<String>` (parsed from the verb-local flag if present, falls back to the global `--board` Phase 36.3.7.9 flag).

`hermes kanban specify [<id>] [--all] [--tenant T] [--author NAME] [--json] [--board <slug>]`
- Same as decompose plus `author: Option<String>` (event author override).

JSON output shape (verbatim from RESEARCH §Q6 + reference.md §490-491):
- decompose: `{ok: bool, task_id: String, reason: Option<String>, fanout: u32, child_ids: Vec<String>, new_title: String}`
- specify: `{ok: bool, task_id: String, reason: Option<String>, new_title: String}`

Table output (default): one-line per task with `[task_id] [new_title] (children: N)` for decompose, `[task_id] [new_title]` for specify. Errors print to stderr with `Ok(1)` exit code.

The DecomposeFn injection into the LLM call uses whichever provider crate the CLI already depends on; this plan does NOT add a new top-level Cargo dep. If `ironhermes-cli` already depends on `ironhermes-agent`, the closure can call `ironhermes_agent::provider::client::call_text_completion(...)` (or whatever the equivalent is in the current codebase — read crates/ironhermes-agent/src/ to confirm). If only `ironhermes-core` is the provider home, the closure goes through `ironhermes_core::provider::resolve_role(...)`. Read the relevant crate at execute time to pick the right import.
