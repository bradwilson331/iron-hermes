## Summary

Phase 36.1 closes a parity gap that Phase 36 explicitly deferred: the gateway's `RunningAgentGuard` RAII pattern and `is_bypass` function exist only in `ironhermes-gateway/src/handler.rs`, while the web UI (`iron_hermes_ui`) and TUI (`ironhermes-cli/tui_rata`) use ad-hoc or non-existent running-state checks. The phase has three coordinated tracks.

**Track A — Extraction (D-01):** `RunningAgentGuard` (lines 79–92) and `is_bypass` (lines 101–103) are currently `pub struct` / `fn` in `handler.rs` and re-exported from `lib.rs` via `pub use handler::RunningAgentGuard`. The existing integration tests in `tests/running_agent_guard_tests.rs` import via `ironhermes_gateway::RunningAgentGuard`. After extraction to `ironhermes-core`, the gateway re-exports from core, the tests update their import path, and web UI + TUI import from core directly. `ironhermes-core` is already a dependency of all three consuming crates.

**Track B — Web UI (D-03 through D-07):** `AppState` at `state.rs:24–60` has seven fields; the `running_agents` map is a new eighth field. The existing `subagent_callback_slot` pattern in `ws.rs` (a `tokio::sync::Mutex`-wrapped slot installed/cleared per-turn) is the structural precedent for the per-session flag map. Slash-command interception in `ws.rs` sits between the `req: ChatRequest` parse (line ~172) and the `tokio::spawn` that calls `run_web_turn` (line ~214). There is already a busy-guard (`if in_flight_turn.is_some()`) at this location that currently blocks any concurrent submission — the new guard supplements it with per-session AtomicBool semantics and adds slash interception before reaching `run_web_turn`.

**Track C — TUI (D-08 through D-10):** The `App` struct (`app.rs:171`) has a `pending_rx: Option<UnboundedReceiver<StreamEvent>>` field whose `.is_some()` is the current (incorrect) proxy for agent running state. This is snapshotted at command-context construction time (`commands.rs:537`) and cannot reflect in-flight turns that began after context construction. Replacing it with a persistent `Arc<AtomicBool>` on `App` and wiring `RunningAgentGuard` at `spawn_turn` (event_loop.rs:722) gives the same RAII discipline as the gateway. The `spawn_turn` function is the single call site for TUI agent turns — binding the guard there is the TUI equivalent of binding it at `run_agent` entry in the gateway.

**Primary recommendation:** Extract first, then implement web UI and TUI tracks in parallel. All three tracks are independent after extraction. The extraction is one new file in `ironhermes-core`, one import update in `handler.rs`, and one re-export update in `lib.rs`. The web UI and TUI tracks do not depend on each other.

### Pattern 1: Guard extraction to ironhermes-core

**What:** Move `RunningAgentGuard` + `is_bypass` + `AGENT_RUNNING_REJECT_MSG` verbatim into `crates/ironhermes-core/src/commands/running_agent.rs` as a new public sub-module.

**Why this module path:** `ironhermes-core::commands` already holds all command-dispatch types (`CommandContext`, `CommandRouter`, `handlers`). The guard and bypass function are tightly coupled to the command dispatch contract — the bypass list is defined in terms of canonical command names from `registry.rs`. Placing it at `commands::running_agent` keeps the namespace coherent and avoids a top-level module for a small focused type.

**Exact code to move (from handler.rs:66–103):**
```rust
// Source: crates/ironhermes-gateway/src/handler.rs:66–103 [VERIFIED: Read]
pub const AGENT_RUNNING_REJECT_MSG: &str =
    "Agent is running. Use /stop to interrupt or /queue to send after this turn.";

pub struct RunningAgentGuard(Arc<AtomicBool>);

impl RunningAgentGuard {
    pub fn new(flag: Arc<AtomicBool>) -> Self {
        flag.store(true, Ordering::SeqCst);
        Self(flag)
    }
}

impl Drop for RunningAgentGuard {
    fn drop(&mut self) {
        self.0.store(false, Ordering::SeqCst);
    }
}

pub fn is_bypass(name: &str) -> bool {
    // TODO(D-01): add "approve" | "deny" when approval queue lands
    matches!(name, "stop" | "new" | "status" | "queue")
}
```

### Pattern 2: Web UI — AppState running_agents field (D-03)

**What:** Add `running_agents: std::sync::Mutex<HashMap<String, Arc<AtomicBool>>>` as a new field on `AppState`.

**Mutex selection (Claude's Discretion):** Use `std::sync::Mutex` (not `tokio::sync::Mutex`). Rationale: The flag lookup and insert operations are brief, non-async, and access the map only to get/insert an `Arc<AtomicBool>`. The map is never accessed across an `.await` boundary — the `Arc<AtomicBool>` is cloned out of the map and then the lock drops before any async work happens. Using `std::sync::Mutex` is consistent with the `nudge_turns` field (also `std::sync::Mutex<HashMap<String, u32>>`) at `state.rs:38`. Using `tokio::sync::Mutex` would require `.lock().await` at the flag-lookup site in `ws.rs`, which is unnecessarily complex for a non-contended brief lookup.

**Add a helper method to AppState:**
```rust
// state.rs — new method on AppState
pub fn get_or_create_running_flag(&self, session_id: &str) -> Arc<AtomicBool> {
    let mut map = self.running_agents.lock().unwrap_or_else(|e| e.into_inner());
    map.entry(session_id.to_string())
        .or_insert_with(|| Arc::new(AtomicBool::new(false)))
        .clone()
}
```

This mirrors `SessionStore::get_running_flag` in the gateway (session.rs:256–261): if the session is new, return a fresh `false` flag.

**AppState::init()** must initialize the field:
```rust
running_agents: Arc::new(std::sync::Mutex::new(HashMap::new())),
// NOTE: running_agents does not need to be Arc — AppState is Clone
// and wraps each field appropriately. Use std::sync::Mutex<HashMap<...>>
// directly, consistent with nudge_turns pattern.
```

Wait — `AppState` is `Clone` (derived at line 24). For Clone to work, `running_agents` must itself be `Clone`. `std::sync::Mutex` is not `Clone`. Therefore the field must be wrapped: `Arc<std::sync::Mutex<HashMap<String, Arc<AtomicBool>>>>` — same as `nudge_turns` which is `Arc<std::sync::Mutex<HashMap<String, u32>>>`. [VERIFIED: state.rs:38]

**Corrected field type:**
```rust
pub running_agents: Arc<std::sync::Mutex<HashMap<String, Arc<AtomicBool>>>>,
```

### Pattern 3: Web UI — ws.rs slash interception and guard check (D-04, D-06)

**Insertion point:** After `req: ChatRequest` parse (line ~172) and after the `in_flight_turn.is_some()` busy-guard check (line ~197), but **before** the `tokio::spawn` at line ~214. Specifically, insert between line 213 (`let message = req.message;`) and line 214 (`let handle = tokio::spawn(async move {`).

**Structure (mirrors gateway's `handle_slash_command` + `handle_with_multimodal` separation):**

```rust
// ws.rs insertion — after `let message = req.message;`
let running_flag = app_state.get_or_create_running_flag(&session_id);

if message.starts_with('/') {
    // Slash interception (D-04): resolve + dispatch before run_web_turn
    let (tx_slash, rx_slash) = mpsc::unbounded_channel::<ChatStreamEvent>();
    let app_state_slash = app_state.clone();
    let session_id_slash = session_id.clone();
    let message_slash = message.clone();
    let running_flag_slash = running_flag.clone();

    tokio::spawn(async move {
        let result = dispatch_web_slash_command(
            &app_state_slash,
            &session_id_slash,
            &message_slash,
            running_flag_slash,
        ).await;
        let text = match result {
            Ok(t) => t,
            Err(e) => format!("Command error: {e}"),
        };
        let _ = tx_slash.send(ChatStreamEvent::Delta { text });
        let _ = tx_slash.send(ChatStreamEvent::Finished { total_tokens: 0 });
    });
    // wire rx_slash into in_flight_turn (same InFlightTurn struct, no handle needed
    // for slash dispatch — or use a no-op JoinHandle that resolves immediately)
    // ... see implementation note below
    continue; // don't fall through to run_web_turn
}

// Plain message guard check (D-06)
if running_flag.load(Ordering::SeqCst) {
    let _ = tx.send(ChatStreamEvent::Delta {
        text: AGENT_RUNNING_REJECT_MSG.to_string(),
    });
    let _ = tx.send(ChatStreamEvent::Finished { total_tokens: 0 });
    continue;
}
// Existing tokio::spawn for run_web_turn follows...
```

**Implementation note on slash dispatch delivery:** The simplest approach is to spawn a task that sends `Delta + Finished` over a fresh channel pair and wire the receiver into an `InFlightTurn`. Alternatively, send directly to the outer `tx` channel without spawning — this avoids the `InFlightTurn` complexity. The direct send approach is simpler: since the guard check happens synchronously before the spawn, there is no need to wrap slash dispatch in `InFlightTurn`. The `in_flight_turn` remains `None` after a slash command, allowing the next message to arrive immediately.

**Recommended approach:** Send slash result directly on the existing `tx` channel. This requires `tx` to be created before the slash interception block. Currently `tx` is created only inside the `tokio::spawn` block — the insertion point must move the channel creation earlier.

**Guard wiring for run_web_turn (D-06):** The `RunningAgentGuard` is constructed inside `run_web_turn` (state.rs), receiving the flag for the session:

```rust
// Inside run_web_turn (or at the top of the spawned task in ws.rs):
let running_flag = app_state.get_or_create_running_flag(session_id);
let _guard = RunningAgentGuard::new(running_flag);
// ... rest of run_web_turn
```

The CONTEXT.md says "RunningAgentGuard is constructed here [in run_web_turn], receiving the Arc<AtomicBool>." So the guard binding goes at the top of `run_web_turn` with the flag passed in — or the flag is retrieved inside `run_web_turn` from `AppState`. Since `run_web_turn` takes `&self` (which is `&AppState`), it can call `self.get_or_create_running_flag(session_id)` directly.

### Pattern 5: TUI — RAII guard at spawn_turn (D-09)

**spawn_turn is at event_loop.rs:722.** It is a synchronous function (`fn spawn_turn(app: &App, tx: ..., cancel: ...)`) that calls `tokio::spawn`. The guard must be bound **inside** the spawned async block so it lives for the duration of the async turn — binding it outside the spawn would drop it immediately (sync function returns, guard drops):

```rust
// event_loop.rs — inside spawn_turn, at the top of the tokio::spawn closure:
fn spawn_turn(app: &App, tx: UnboundedSender<StreamEvent>, cancel: CancellationToken) {
    let runtime = app.agent_runtime.clone();
    let agent_running = app.agent_running.clone(); // clone the Arc
    // ... other clones ...

    tokio::spawn(async move {
        let _agent_guard = RunningAgentGuard::new(agent_running); // sets true; Drop sets false
        let _ = tx.send(StreamEvent::Started);
        // ... streaming callbacks and run_turn call ...
        // _agent_guard drops here on all exit paths: Ok, Err, cancel, panic
    });
}
```

This is the TUI equivalent of `let _agent_guard = RunningAgentGuard::new(_running_flag)` at gateway handler.rs:889 inside `run_agent`.

### Anti-Patterns to Avoid

- **Manual store(true/false) pairs:** Do not use `agent_running.store(true, ...); ... agent_running.store(false, ...);` — this is the CLI `main.rs` anti-pattern that Phase 36 explicitly avoids. RAII only.
- **Binding guard outside tokio::spawn:** For `spawn_turn`, the guard MUST be created inside the async block, not in the sync wrapper function. If created in `fn spawn_turn(...)`, it drops when `spawn_turn` returns (immediately after `tokio::spawn`), before the turn runs.
- **Checking `pending_rx.is_some()` as running proxy:** Remove the `Arc::new(AtomicBool::new(app.pending_rx.is_some()))` snapshot. It creates a fresh Arc on every command invocation, meaning `cmd_stop` reads a disconnected flag that cannot be set by a running guard.
- **Raw user input in bypass check:** Never call `is_bypass(raw_input)` on the string typed by the user (e.g., `is_bypass("/new")` or `is_bypass("new ")`) — always use `def.name` after `CommandRouter::resolve()`. The gateway's Pitfall 4 mitigation: `/reset` resolves to `"new"` and correctly bypasses; if you check the raw string `"reset"` against `is_bypass`, it falls through and gets rejected.
- **Relaxed ordering on AtomicBool:** Do not downgrade from `Ordering::SeqCst`. On ARMv8 and other weakly-ordered architectures, `Relaxed` can allow a store to be visible to a later load on the same thread before it is visible across threads. SeqCst is the correct ordering for a guard-semantics flag. (Phase 36 Pitfall 3)

## Common Pitfalls

### Pitfall 1: Guard bound outside tokio::spawn drops immediately

**What goes wrong:** `fn spawn_turn` is synchronous. If `RunningAgentGuard::new(...)` is called in the body of `spawn_turn` before `tokio::spawn(...)`, the guard is dropped when `spawn_turn` returns — before the spawned async task runs. The flag is set to true then immediately cleared to false, providing zero protection.

**Why it happens:** RAII drop fires at the end of the scope where the binding lives, not at the end of the future's lifecycle.

**How to avoid:** Create the guard inside the `async move` closure passed to `tokio::spawn`. Clone `app.agent_running` before the spawn, move the clone in, and bind the guard at the top of the async block.

**Warning signs:** A test that sets `agent_running.store(true)` before spawning and then checks the flag immediately after `spawn_turn` returns — if the flag is false, the guard dropped too early.

### Pitfall 2: Bypass check on pre-resolution name

**What goes wrong:** Calling `is_bypass(raw_command)` on the user's raw input string (e.g., `"/reset"`, `"reset"`, `"/new "`) instead of `def.name` after `CommandRouter::resolve()`. `/reset` resolves to `"new"` via alias — if you check `is_bypass("reset")`, it returns `false` and `/reset` gets rejected during an active turn.

**Why it happens:** The bypass list contains canonical names (`stop`, `new`, `status`, `queue`). Aliases are resolved only by `CommandRouter::resolve()`. Raw strings bypass the resolver.

**How to avoid:** Always check `is_bypass(&def.name)` where `def` is the `CommandDef` returned by `resolve()`. This is D-10's explicit ordering requirement: bypass check AFTER `CommandRouter::resolve()`.

**Warning signs:** The test `test_alias_bypasses_guard` (GW-05-9 in the gateway suite) would fail if ported to web UI/TUI naively with raw-string checking.

### Pitfall 3: SeqCst downgraded to Relaxed

**What goes wrong:** Using `Ordering::Relaxed` on `AtomicBool::store(true, Relaxed)` inside `RunningAgentGuard::new()` or `store(false, Relaxed)` inside `Drop`. On ARMv8 (e.g., Apple Silicon M-series), a relaxed store can be reordered past a subsequent load on another thread, breaking the happens-before guarantee that makes the guard safe.

**Why it happens:** Relaxed is the "fastest" ordering and looks like a reasonable optimization.

**How to avoid:** Keep `Ordering::SeqCst` on both store sites in `RunningAgentGuard`. The const was locked in Phase 36 specifically for this reason.

### Pitfall 4: Fresh Arc per command-context construction

**What goes wrong:** The current `commands.rs:537` creates `Arc::new(AtomicBool::new(app.pending_rx.is_some()))` — a fresh allocation with a snapshot value. If `cmd_stop` calls `ctx.agent_running.load()`, it reads the snapshot, not the live guard-controlled flag. After D-08, `cmd_stop` will correctly see the live flag value.

**Why it happens:** The snapshot was a reasonable approximation when no RAII guard existed. Now it is a correctness bug for surfaces that have the guard.

**How to avoid:** After adding `agent_running: Arc<AtomicBool>` to `App`, replace the snapshot line with `app.agent_running.clone()`.

### Pitfall 5: AppState.running_agents map entry not cleaned up

**What goes wrong:** The `running_agents` map grows unboundedly as sessions are created. Since `AppState` is a singleton for the web UI (all sessions share one process), old session entries accumulate.

**Why it happens:** The gateway's `SessionStore` tracks `GatewaySession` objects with their own LRU/TTL expiry; the web UI's `AppState` has no equivalent session lifecycle management for running flags.

**How to avoid:** The flag cleanup can happen in one of two ways: (a) remove the flag entry when the turn completes (the guard's Drop could do this, but that requires the guard to hold the map reference — complex), or (b) accept the map growth as a low-cost tradeoff for a single-user web UI where session count is bounded. The `nudge_turns` map on `AppState` (line 38) uses the same unbounded pattern and is accepted as reasonable for this deployment model. Document the tradeoff — do not add cleanup complexity in this phase.

### Pitfall 6: ws.rs slash interception blocks the WebSocket select! loop

**What goes wrong:** If slash command dispatch is slow (e.g., calls a blocking operation), and it runs synchronously in the select! arm before the `tokio::spawn` for the turn, the WebSocket event loop stalls.

**Why it happens:** `ws.rs` uses a `tokio::select!` loop. Code between receiving a frame and dispatching must be non-blocking.

**How to avoid:** Wrap slash command dispatch in a `tokio::spawn` (same as agent turns) so the event loop arm returns immediately. Send the result over the `tx` channel, and wire the receiver into `in_flight_turn` (or handle it as a short-lived spawn that writes directly to the socket, since slash responses are synchronous single-turn outputs). The `ChatStreamEvent::Delta + Finished` sequence is synchronous in nature — the simplest approach is to keep the slash dispatch fast (it is synchronous `CommandRouter::dispatch()`) and not spawn a separate task for it.

### Pitfall 7: in_flight_turn not reset after slash dispatch

**What goes wrong:** After slash interception, if `in_flight_turn` is left as `Some(...)` or not properly set/reset, the next message from the client will be rejected by the existing busy-guard (`if in_flight_turn.is_some()`).

**How to avoid:** Slash command dispatch should NOT set `in_flight_turn`. Send the result directly over the WebSocket socket or over the existing `tx` channel before the `in_flight_turn` is set. The simplest model: detect slash, dispatch synchronously (it's fast — pure command dispatch), send `Delta + Finished` frames immediately, `continue` the select loop. This keeps `in_flight_turn` as `None`.
