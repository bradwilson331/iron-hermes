# Phase 36.17.6 — Discussion Log

This phase was scope-bounded by the diagnosis in
`.planning/phases/36.17.5-integrate-tts-functions/36.17.5-04-SUMMARY.md`,
so the discussion focused on four narrow implementation choices rather
than open-ended vision questions.

## Areas Discussed

### Area 1: Registration site

**Question:** Where should `register_tts_tools(...)` be called so the
CLI's `toolset list` / `toolset show` inspection paths see the TTS tools?

**Options presented:**
- Inline at both CLI call sites — `cmd_toolset_list` + `cmd_toolset_show`
  each call `register_tts_tools` after `register_defaults()` via a shared
  private helper. *(recommended)*
- Fold into `ToolRegistry::register_defaults` unconditionally.
- Add a new `register_defaults_full()` factory wrapping `register_defaults` +
  `register_tts_tools`.

**User selection:** Inline at both CLI call sites.

**Rationale captured:** smallest scope; no API surface change on the
stable `register_defaults`; helper keeps the two CLI call sites in sync.

→ **D-01**

---

### Area 2: Inspection-time `SessionKey`

**Question:** `register_tts_tools(session_key: SessionKey)` requires a
`SessionKey`. CLI inspection has no real session. How should we satisfy
the signature?

**Options presented:**
- Synthetic `SessionKey::new(Platform::Local, "inspect")`. *(recommended)*
- Refactor `register_tts_tools` to take `Option<SessionKey>`.
- Split `register_tts_tools` into metadata + session-bind halves.

**User selection:** Synthetic sentinel.

**Rationale captured:** no signature change to Plan 03's contract; the
literal `"inspect"` value is greppable; runtime session-bound paths never
fire from the inspection call site.

→ **D-02**

---

### Area 3: `toolset_members_map()`

**Question:** How should `toolset_members_map()` learn about `voice`
and its members?

**Options presented:**
- Hardcode `"voice" → ["text_to_speech", "send_audio"]`. *(recommended)*
- Derive from registry inspection at call time.

**User selection:** Hardcode.

**Rationale captured:** matches existing precedent for every other
toolset; smallest diff; auditable at a glance; runtime cost stays zero.

→ **D-03**

---

### Area 4: Verification scope after wiring

**Question:** After the wiring lands, what should the verification cover?

**Options presented:**
- Re-run full UAT script Gates 1-5 end-to-end. *(recommended)*
- Re-run only Gates 4 + 5.
- Re-run Gates 4 + 5 plus a new unit test pinning the members-map entry.

**User selection:** Re-run full Gates 1-5.

**Rationale captured:** Gates 1-3 are automated and fast — running them
again is a cheap regression check against the wiring change; Gates 4
and 5 verify the actual fix; the UAT script is the contract.

→ **D-04**

---

## Deferred (out of scope for 36.17.6)

- Generalising `register_tts_tools` to take `Option<SessionKey>` — only
  worth it once a second inspection-style consumer appears.
- Dynamic `toolset_members_map` derivation — only worth it at 3+
  dynamically-registered toolsets.
- Binding a real `SessionKey` for the local CLI agent at runtime — a
  separate concern about whether the CLI's agent paths should expose TTS
  tools by default. Belongs in a future agent-side phase.
- Centralising `CryptoProvider::install_default()` guards into a single
  init module. Hardening pass for later; not blocking 36.17.6.

## Boundary acknowledged

The scope of 36.17.6 is **exactly** the wiring fix that closes
`phase 36.17.5` Plan 04 Gates 4 + 5. Any TTS-feature work, refactor that
extends beyond `toolset_cmd.rs` + a possible `pub` re-export, or
additional UAT gates are explicitly out of scope and belong in their own
phase if needed.
