```rust
fn load_tools_config(hermes_home: &Path) -> ToolsConfig {
    let cfg_path = hermes_home.join("config.yaml");
    if !cfg_path.exists() {
        return ToolsConfig::default();
    }
    let text = match std::fs::read_to_string(&cfg_path) {
        Ok(t) => t,
        Err(_) => return ToolsConfig::default(),
    };
    let config: ironhermes_core::Config = serde_yaml::from_str(&text).unwrap_or_default();
    config.tools
}
```

**Pattern:** no `pub`, no `async`, doc comment describes *why* the helper exists (phase + gap reference). The new helper follows this exactly:

```rust
/// Phase 36.17.6: register TTS tools into an inspection-only registry.
///
/// Both `cmd_toolset_list` and `cmd_toolset_show` build a fresh `ToolRegistry`
/// via `register_defaults()` and never enter `build_app_runtime_bundle`, so
/// `register_tts_tools` from Plan 03 never fires in the CLI inspection path.
/// This helper bridges the gap using a sentinel `SessionKey` (no real session,
/// no dispatcher — only metadata/availability is surfaced).
///
/// Use `Config::default()` (not disk-loaded config) to keep the inspection path
/// I/O-free and always resolve the default `"edge"` provider as available.
fn register_tts_for_inspection(registry: &mut ToolRegistry) {
    use ironhermes_core::{Platform, SessionKey};
    use std::sync::Arc;
    let session_key = SessionKey::new(Platform::Local, "inspect");
    registry.register_tts_tools(
        session_key,
        None, // No Telegram dispatcher for CLI inspection
        Arc::new(ironhermes_core::Config::default()),
    );
}
```

## Shared Patterns

### `register_defaults()` + extension helper call ordering

**Source:** `crates/ironhermes-cli/src/toolset_cmd.rs` lines 119–120 (list) and lines 140–141 (show)

Both `cmd_toolset_list` and `cmd_toolset_show` follow the identical registry-construction sequence:

```rust
let mut registry = ToolRegistry::new();
registry.register_defaults();
// extension helpers go here, before any use of `registry`
```

The new `register_tts_for_inspection(&mut registry)` call goes on the line immediately after `register_defaults()` in both functions. This matches how `browser_chromium_unavailable()` is invoked only after the registry is fully built.

### Pitfall guard: `KNOWN_TOOLSETS` and `toolset_members_map` must change atomically

Per RESEARCH.md Pitfall 1 and Pitfall 4: `check_known_toolset` runs BEFORE the registry is built in `cmd_toolset_show`. Adding `"voice"` to the map without adding it to `KNOWN_TOOLSETS` makes `toolset list` show a voice row but `toolset show voice` still error. Both changes must land in the same task/commit.

**Apply to:** the single task that adds `"voice"` to both `KNOWN_TOOLSETS` and `toolset_members_map`.

### Test count update is mandatory on `KNOWN_TOOLSETS` change

**Source:** `crates/ironhermes-cli/src/toolset_cmd.rs` line 483

Any change to `KNOWN_TOOLSETS.len()` causes `browser_in_known_set` to fail immediately. The `== 8` → `== 9` assertion update is not optional — it is a compile-time-correct but test-time-failing regression without the update.

**Apply to:** same task that adds `"voice"` to `KNOWN_TOOLSETS`.
