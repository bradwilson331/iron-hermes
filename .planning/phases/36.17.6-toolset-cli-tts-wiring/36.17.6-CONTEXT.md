<decisions>

### D-01 — Registration site: inline at both CLI call sites

`cmd_toolset_list` and `cmd_toolset_show` (both in
`crates/ironhermes-cli/src/toolset_cmd.rs`) each call
`register_tts_tools(...)` AFTER `registry.register_defaults()`. A small
private helper in `toolset_cmd.rs` keeps the two call sites in lock-step.

**Rejected alternatives:**
- Fold into `ToolRegistry::register_defaults` unconditionally — too broad,
  changes a stable public API, surprises non-CLI callers.
- New `register_defaults_full()` factory — adds a parallel API surface
  for a one-off need; YAGNI.

**Why:** smallest scope, no blast radius outside the CLI inspection path,
no public-API change on `ToolRegistry::register_defaults`.

### D-02 — Inspection-time session: synthetic `SessionKey::new(Platform::Local, "inspect")`

`register_tts_tools` takes a `SessionKey` (Plan 03 contract). At CLI
inspection time there is no real session, so the helper builds a literal
sentinel `SessionKey::new(Platform::Local, "inspect")` and passes it.
Tools register and surface metadata (`Tool::name`, `Tool::toolset`,
`Tool::schema`, `Tool::is_available`) — the session-bound parts of
runtime execution never fire from inspection.

**Rejected alternatives:**
- Refactor `register_tts_tools` to take `Option<SessionKey>` — touches
  Plan 03's contract; not needed for this single inspection use case.
- Split `register_tts_tools` into metadata + session-bind halves — biggest
  blast radius, deferred until a second consumer needs it.

**Why:** no signature change, no behavioural drift in the agent-runtime
path. The sentinel `"inspect"` value is greppable so future refactors
can find every inspection site.

### D-03 — Members map: hardcode `"voice" → ["text_to_speech", "send_audio"]`

Add a single entry to `toolset_members_map()` mapping `"voice"` to the
two tool names. Matches the existing precedent for every other toolset
(`memory`, `session`, `agent`, `web`, `code`, `browser`).

**Rejected:** dynamic derivation from registry inspection (adds runtime
cost on every CLI call, changes a stable utility, removes intentional
list of TTS tools that's auditable at a glance).

**Why:** uniformity with the rest of the CLI, smallest diff, audit-friendly.

### D-04 — Verification scope: re-run full UAT script Gates 1-5

`scripts/uat/phase-36.17.5-tts.sh` runs end-to-end on the operator's
machine. Gates 1-3 (automated) double as a regression check against the
wiring change. Gates 4 + 5 (manual) verify the fix.

**Rejected:** only re-run Gates 4 + 5 (skips regression coverage).

**Why:** the UAT is the contract; rerunning it is cheap, catches any
subtle CLI-startup regressions that the wiring change might introduce.

### D-05 — Acceptance gate: 36.17.5 stays open until 36.17.6's UAT passes

Phase 36.17.6 is NOT complete until:
1. Code change committed and merged
2. Operator re-runs `bash scripts/uat/phase-36.17.5-tts.sh` and confirms
   5/5 GREEN
3. `36.17.5-VALIDATION.md` frontmatter flipped to
   `nyquist_compliant: true` and `wave_0_complete: true`
4. ROADMAP.md Plan 04 entry flipped to `[x]`
5. `gsd-verifier` runs cleanly on the combined 36.17.5 + 36.17.6 surface

**Why:** 36.17.6 exists solely to close 36.17.5. Leaving 36.17.5 in
partial state until 36.17.6's UAT passes prevents accidental phase-complete
sign-off before the operator confirms the gates.

</decisions>

- **Generalise `register_tts_tools` to take `Option<SessionKey>`** — only

  have 3+ dynamically-registered toolsets. Until then, hardcoded entries

  expose `text_to_speech` + `send_audio` automatically is a separate
  question scoped to a future agent-side phase (not this CLI-inspection
  fix).

  `CryptoProvider::install_default().ok()` guards; a future hardening pass
  could centralise into a single init module. Not blocking 36.17.6.
