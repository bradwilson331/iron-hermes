## Summary

Phase 36.17.6 closes a two-wire gap in the CLI's toolset inspection path that was discovered during Phase 36.17.5 Plan 04 operator verification. The gap has two independent components: (1) `toolset_members_map()` in `toolset_cmd.rs` has no `"voice"` entry, so the CLI does not know what tools belong to the voice toolset; (2) `cmd_toolset_list` and `cmd_toolset_show` each build a `ToolRegistry::new() + register_defaults()` but never call `register_tts_tools(...)`, so even if the map entry were added, the registry's `list_unavailable()` would never have TTS-tool availability data.

The fix is narrow: add one entry to `toolset_members_map()` and add one helper function (called from both `cmd_toolset_list` and `cmd_toolset_show`) that constructs a sentinel `SessionKey` and calls `registry.register_tts_tools(...)`. No changes to `register_tts_tools`' signature, no changes to `ironhermes-tools/src/tts/mod.rs`, no new crate dependencies.

After the wiring change the UAT script's Gates 1-3 (automated) re-run unchanged as a regression check; Gates 4 and 5 (manual) are the primary acceptance gates that were blocked in Plan 04.

**Primary recommendation:** Add `fn register_tts_for_inspection(registry: &mut ToolRegistry)` private helper in `toolset_cmd.rs`; call it after `register_defaults()` in both `cmd_toolset_list` and `cmd_toolset_show`; add `"voice" → &["text_to_speech", "send_audio"]` to `toolset_members_map()`; add `"voice"` to `KNOWN_TOOLSETS`; update the `browser_in_known_set` length assertion from 8 → 9.

### Pattern 1: Private Helper to Share Registration Between Two Call Sites

**What:** Extract a private `fn register_tts_for_inspection(registry: &mut ToolRegistry)` that builds the sentinel key and calls `registry.register_tts_tools(...)`. Both `cmd_toolset_list` and `cmd_toolset_show` call this helper after `register_defaults()`.

**When to use:** Any time two CLI inspection paths need the same extra-registration step.

**Example (reference shape from `app_runtime_factory.rs:102-108`):**
```rust
// Source: crates/ironhermes-agent/src/app_runtime_factory.rs lines 102-108
if let Some(ref session_key) = input.session_key {
    registry.register_tts_tools(
        session_key.clone(),
        input.telegram_adapter.clone(),
        input.config.clone(),
    );
}
```

**Adapted for CLI inspection:**
```rust
// Source: derived from crates/ironhermes-agent/src/app_runtime_factory.rs pattern
fn register_tts_for_inspection(registry: &mut ToolRegistry) {
    use ironhermes_core::{Platform, SessionKey};
    use std::sync::Arc;
    let session_key = SessionKey::new(Platform::Local, "inspect");
    registry.register_tts_tools(session_key, None, Arc::new(ironhermes_core::Config::default()));
}
```

### Pattern 3: `KNOWN_TOOLSETS` Update

`KNOWN_TOOLSETS` at line 16-18 of `toolset_cmd.rs` controls slug-validation for `toolset enable/disable/show`. `"voice"` must be added or `check_known_toolset` will reject `hermes toolset show voice` with "unknown toolset 'voice'". This is the **second root cause** from the wiring gap — `toolset show voice` errors before even reaching the registry.

```rust
// Source: crates/ironhermes-cli/src/toolset_cmd.rs:16-18
const KNOWN_TOOLSETS: &[&str] = &[
    "web", "code", "memory", "agent", "skills", "session", "browser", "learning",
    "voice",  // Phase 36.17.6: add TTS toolset
];
```

**CRITICAL:** Adding `"voice"` to `KNOWN_TOOLSETS` changes its length from 8 to 9. The `browser_in_known_set` unit test at line 482-485 asserts `KNOWN_TOOLSETS.len() == 8`. This assertion **must be updated to 9** or the test suite will fail.

### Anti-Patterns to Avoid

- **Calling `build_app_runtime_bundle`** from the CLI inspection path — async, heavyweight, creates full agent runtime, not appropriate for a read-only inspection command.
- **Folding `register_tts_tools` into `register_defaults()`** — changes the stable public API; breaks the Plan 03 contract that TTS tools are session-bound.
- **Using `Option<SessionKey>`** — changes `register_tts_tools` signature, touching the Plan 03 invariant test `invariants_36_17_5.rs`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| TTS tool registration | Custom registration logic | `registry.register_tts_tools(session_key, None, config)` | Existing method handles TextToSpeechTool + SendAudioTool construction and registration atomically |
| Sentinel session key | Custom struct/enum | `SessionKey::new(Platform::Local, "inspect")` | `SessionKey::new` already accepts `impl Into<String>` for chat_id; `"inspect"` is a valid string literal |
| Config for inspection | Load from disk | `Arc::new(ironhermes_core::Config::default())` | Inspection only needs provider name and edge/elevenlabs config; defaults suffice; avoids I/O errors in a fast inspection path |

**Key insight:** All three building blocks exist. This phase is purely wiring them together at the CLI inspection boundary.

## Common Pitfalls

### Pitfall 1: Forgetting to add `"voice"` to `KNOWN_TOOLSETS`
**What goes wrong:** `cmd_toolset_show` calls `check_known_toolset` before building the registry. If `"voice"` is not in `KNOWN_TOOLSETS`, `hermes toolset show voice` returns `Error: unknown toolset 'voice'` without ever reaching the registry population step.
**Why it happens:** `toolset_members_map` and `KNOWN_TOOLSETS` are two separate data structures. Adding to the map without adding to the const is a partial fix.
**How to avoid:** Both changes must be in the same task. A unit test asserting `KNOWN_TOOLSETS.contains(&"voice")` locks this.
**Warning signs:** `hermes toolset list` shows a `voice` row but `hermes toolset show voice` returns "unknown toolset" — the first is driven by `build_toolset_rows` (uses the map), the second is gated by `check_known_toolset` (uses the const).

### Pitfall 2: Forgetting to update `browser_in_known_set` length assertion
**What goes wrong:** `cargo test -p ironhermes-cli` fails with "KNOWN_TOOLSETS must have exactly 8 entries after Phase 33 addition of learning toolset."
**Why it happens:** The test was written with a hardcoded count for historical documentation. Adding `"voice"` increments the count to 9.
**How to avoid:** Update the assertion to `== 9` and update the message to reference Phase 36.17.5/36.17.6.
**Warning signs:** `cargo test -p ironhermes-cli` fails immediately after adding `"voice"` to `KNOWN_TOOLSETS`.

### Pitfall 3: Using a `Config` loaded from disk vs. `Config::default()`
**What goes wrong:** Loading config from `hermes_home` in the inspection helper introduces I/O that can fail (file missing, YAML parse error) and may return a different `tts.provider` value than expected.
**Why it happens:** The existing `cmd_toolset_list` already calls `load_tools_config(hermes_home)` for enable/disable state, so it's tempting to reuse that config in the helper.
**How to avoid:** Use `Arc::new(Config::default())` in the inspection helper. Availability check for `text_to_speech` uses the default provider `"edge"`, which is always in the registry. The enable/disable state still comes from the properly-loaded `cfg` variable.
**Warning signs:** `text_to_speech` shows `✗` in environments where `config.yaml` does not specify `tts.provider = "edge"` (because a non-default provider is not in the static registry).

### Pitfall 4: `cmd_toolset_show` ordering — `check_known_toolset` before registry build
**What goes wrong:** The registry is built AFTER `check_known_toolset`. Adding `"voice"` to the registry only (without adding to `KNOWN_TOOLSETS`) means `toolset show voice` exits before the helper ever fires.
**Why it happens:** The code path is: `validate → check_known_toolset → load_config → registry → build_toolset_show_view`. Both the const update AND the helper call are needed.
**How to avoid:** Task ordering in the plan: add `"voice"` to `KNOWN_TOOLSETS` AND the map AND the helper call as a single atomic task (one commit). Do not split across tasks.

### Pitfall 5: `build_toolset_rows` uses `DEFAULT_TOOLSETS` for ordering
**What goes wrong:** `voice` row may not appear in `toolset list` output if the ordering logic excludes it.
**Why it happens:** `build_toolset_rows` (line 286-290) uses `DEFAULT_TOOLSETS` for the initial order, then appends from `KNOWN_TOOLSETS`. Since `"voice"` is NOT in `DEFAULT_TOOLSETS` (which is `&["memory", "session", "agent", "skills", "robotics", "learning"]`), it is appended from `KNOWN_TOOLSETS` after the initial ordering block. This means `voice` WILL appear — just after the other toolsets.
**How to avoid:** No action needed; the existing ordering logic handles it correctly.
