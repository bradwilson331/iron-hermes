# Phase 36.17.6: Code Review Report

**Reviewed:** 2026-06-04T00:00:00Z
**Depth:** standard
**Files Reviewed:** 1
**Status:** issues_found

## Summary

Phase 36.17.6 makes a small, focused change to `crates/ironhermes-cli/src/toolset_cmd.rs`:
adds `"voice"` to `KNOWN_TOOLSETS`, maps it to `["text_to_speech", "send_audio"]` in
`toolset_members_map()`, introduces a new private helper
`register_tts_for_inspection(&mut ToolRegistry)`, calls that helper from both
`cmd_toolset_list` and `cmd_toolset_show` after `register_defaults()`, and adds
a unit test `toolset_members_map_voice_entry`. The change is well-scoped, the
sentinel-`SessionKey` approach (`Platform::Local, "inspect"`) matches established
project idiom (see `crates/ironhermes-core/tests/*.rs`), and the helper is
correctly placed *after* `register_defaults()` in both call sites.

Cross-referenced upstream: `register_defaults_except` (registry.rs:580) does NOT
register `text_to_speech` or `send_audio`, so there is no double-registration
risk. `Config::default()` is in-memory only (no disk I/O). `EdgeProvider::new`
and `ElevenLabsProvider::new` are pure constructors (no network/disk side
effects). The sentinel `SessionKey::new(Platform::Local, "inspect")` matches
many existing call sites in the codebase.

Net assessment: no Critical issues. Two Warning-tier issues relate to
documentation drift / brittle test coupling that will silently mislead future
maintainers, plus three Info-tier nits.

## Warnings

### WR-01: Stale comment in `KNOWN_TOOLSETS` doc — says "nine concrete toolsets" but doc-mention "Phase 25.1" / "Phase 33" did not get refreshed for "voice"

**File:** `crates/ironhermes-cli/src/toolset_cmd.rs:14-20`
**Issue:** The doc-comment header was edited from "eight" to "nine" and a third
sentence ("voice added in Phase 36.17.6...") was appended, but the *original*
sentence "browser added in Phase 25.1, learning added in Phase 33" still reads
as the complete enumeration of post-D-01 additions. A future reader scanning
this comment will see the list of historical additions and assume "voice" is a
later afterthought that may or may not be a real built-in. More importantly,
the function-level doc-comment on `check_known_toolset` (line 64) still says
"the six D-01 built-in toolsets" — that count was already stale before this
phase (browser/learning made it 8) and is now *more* stale (9). This is the
exact kind of comment-drift that erodes trust in inline documentation.
**Fix:**
```rust
/// D-01/D-04: The nine concrete toolsets shipped.
/// History: browser (Phase 25.1), learning (Phase 33), voice (Phase 36.17.6).
const KNOWN_TOOLSETS: &[&str] = &[
    "web", "code", "memory", "agent", "skills", "session", "browser", "learning",
    "voice",
];
```

### WR-02: `register_tts_for_inspection` silently swallows would-be failures via duplicate-insert overwrite (defense-in-depth)

**File:** `crates/ironhermes-cli/src/toolset_cmd.rs:407-416`
**Issue:** `ToolRegistry::register` (registry.rs:130-138) only asserts against
*intercept* name collisions; for normal tool re-registration it silently
overwrites via `self.tools.insert(name, ...)`. Today, `register_defaults_except`
does NOT register `text_to_speech` / `send_audio`, so the inspection helper is
the unique registrar — fine. But this is a fragile invariant: if a future
refactor adds TTS tools to `register_defaults`, `register_tts_for_inspection`
will silently shadow them with sentinel-keyed instances, and the bug will
*only* surface in CLI-inspection availability output (not in any test that
currently exists). The helper has no defensive check, no comment naming the
upstream invariant it depends on, and the new unit test
`toolset_members_map_voice_entry` only checks the static map — it does not
actually construct a registry and call the helper, so this drift would not be
caught at CI.
**Fix:** Either (a) add an assertion in the helper that confirms TTS names are
not already in the registry before re-registering, or (b) explicitly document
the upstream invariant and add a regression test:
```rust
fn register_tts_for_inspection(registry: &mut ToolRegistry) {
    use ironhermes_core::{Platform, SessionKey};
    use std::sync::Arc;
    // Invariant: register_defaults_except does NOT register text_to_speech or
    // send_audio (see ironhermes-tools/src/registry.rs::register_defaults_except).
    // If that ever changes, this helper would silently shadow the production
    // tools with sentinel-keyed inspection instances. Guard with a debug_assert.
    debug_assert!(
        registry.get("text_to_speech").is_none(),
        "register_tts_for_inspection: text_to_speech already registered — \
         register_defaults_except may have started registering TTS tools; \
         remove this helper or update register_defaults contract"
    );
    let session_key = SessionKey::new(Platform::Local, "inspect");
    registry.register_tts_tools(
        session_key,
        None,
        Arc::new(ironhermes_core::Config::default()),
    );
}
```
Plus a new test that builds the same registry shape `cmd_toolset_list` uses
and confirms `text_to_speech` and `send_audio` appear (mirrors the existing
GAP-1 / GAP-6 regression-test pattern for the browser toolset).

## Info

### IN-01: `voice` is missing the docstring marker that documents WHY it differs from `browser`

**File:** `crates/ironhermes-cli/src/toolset_cmd.rs:277-278`
**Issue:** `build_toolset_show_view` (line 181) and `build_toolset_rows` (line
309) both special-case `validated == "browser"` for chromium availability.
There is no equivalent runtime-availability check for `voice` because the
sentinel-registered TTS tools handle that via `is_available()`. A future
maintainer extending the `voice` toolset (e.g. adding a `voice_record` member
that needs a runtime check) will read the existing comment patterns and may
not realise the chromium-special-case is unique to browser. A one-line note
near the voice entry would prevent that.
**Fix:** Add an inline comment near the voice insert:
```rust
// Phase 36.17.6: voice toolset — TTS tools wired for CLI inspection path.
// Note: unlike "browser" (which needs chromium_missing special-case in
// build_toolset_rows/build_toolset_show_view), voice members are registered
// via register_tts_for_inspection() and report availability through the
// normal registry.list_unavailable() pathway.
m.insert("voice", &["text_to_speech", "send_audio"]);
```

### IN-02: `toolset_members_map_voice_entry` test does not exercise the registry-availability path

**File:** `crates/ironhermes-cli/src/toolset_cmd.rs:746-768`
**Issue:** The new test verifies the static map but never builds a
`ToolRegistry`, calls `register_tts_for_inspection`, or asserts that
`text_to_speech` / `send_audio` actually appear in the registry. The
existing `browser_in_known_set` + `browser_row_reports_*` pairing covers
*both* the static map AND the runtime registry view; the voice toolset gets
only half that coverage. WR-02's fix already proposes the missing test —
this Info item just calls out the asymmetry explicitly so it is not lost.
**Fix:** Add a parallel test (per WR-02 fix):
```rust
#[test]
fn voice_row_reports_members_via_inspection_registry() {
    let cfg = ToolsConfig::default();
    let mut registry = ToolRegistry::new();
    registry.register_defaults();
    register_tts_for_inspection(&mut registry);

    let members_map = toolset_members_map();
    let rows = build_toolset_rows(&cfg, &registry, &members_map);
    let row = rows.iter().find(|r| r.name == "voice").expect("voice row");
    assert_eq!(row.member_count, 2);
    // text_to_speech is_available() always returns true (no prereqs);
    // send_audio is_available() likewise — both should be marked ✓.
    assert!(
        row.member_summary.contains("text_to_speech \u{2713}"),
        "got: {}", row.member_summary
    );
}
```

### IN-03: Two near-identical setup lines in `cmd_toolset_list` / `cmd_toolset_show` are good candidates for a single factory

**File:** `crates/ironhermes-cli/src/toolset_cmd.rs:121-123, 143-145`
**Issue:** Both functions now read:
```rust
let mut registry = ToolRegistry::new();
registry.register_defaults();
register_tts_for_inspection(&mut registry); // Phase 36.17.6
```
This is duplicate setup that future toolsets will need to extend (next phase
may add e.g. `register_skills_for_inspection`, `register_memory_for_inspection`).
A `fn build_inspection_registry() -> ToolRegistry` factory would centralise
the pattern, making the maintenance contract obvious: "any new
register-only-for-inspection helper goes here." Not a bug — strictly a
maintainability concern — but worth flagging before the third caller appears.
**Fix:**
```rust
/// Build a fresh ToolRegistry for CLI inspection paths (toolset list / show).
/// Centralises the `register_defaults() + sentinel-session helpers` pattern
/// so future toolsets that need similar sentinel wiring add their helper
/// here rather than in every caller.
fn build_inspection_registry() -> ToolRegistry {
    let mut registry = ToolRegistry::new();
    registry.register_defaults();
    register_tts_for_inspection(&mut registry);
    registry
}
```
Then call sites become `let registry = build_inspection_registry();` (note:
no longer needs `mut` at the call site).
