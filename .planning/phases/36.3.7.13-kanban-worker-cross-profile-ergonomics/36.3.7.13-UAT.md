Profile A = the profile that owns the goal-mode card (the assignee profile, where work logically lives).
Profile B = the profile that runs the dispatcher (typically the gateway profile, which may not match assignee).

```bash
# Edit these two lines for your environment. Defaults below match the canonical

```

### S-0b: pick the ironhermes binary

Two valid forms — pick exactly one. Either works post-this-phase because F-02 (Plan 02) added the `IRONHERMES_WORKER_BIN` env override.

```bash
# Option 1 — installed release binary on PATH (production-like)
export IRONHERMES_BIN="$(command -v ironhermes)"
unset IRONHERMES_WORKER_BIN  # not needed if the same binary is on PATH
```

If you took Option 2, the F-02 verification is implicit — every worker subprocess in §5 and §6 will use `$IRONHERMES_BIN`. If you ever see `worker_spawn` invoke a different binary, F-02 is broken; STOP and re-run `cargo test -p ironhermes-kanban --test worker_bin_resolution`.

## Section 5 — Cross-Profile DB Resolution (LIVE REQUIRED)

Verifies D-A1, D-A2, F-02, D-H1.

A goal-mode card created under `--profile $PROFILE_A` must be found and dispatched by a worker invoked under `--profile $PROFILE_B` when `HERMES_KANBAN_DB` bridges the two profiles.

### §5 Step 1 — create the test card under profile A

```bash
TASK_ID=$(
  "$IRONHERMES_BIN" --profile "$PROFILE_A" kanban create \
    --goal \
    --goal-toolset restricted \
    --goal-max-turns 3 \
    --assignee "$PROFILE_A" \
    --body "Acceptance: produce the word PARITY in uppercase with no other output." \
    "§5 cross-profile DB resolution UAT" \
    --json 2>/dev/null | jq -r '.task_id'
)
test -n "$TASK_ID" || { echo "FAIL: TASK_ID is empty — kanban create did not return JSON"; exit 1; }
echo "Created: $TASK_ID under --profile $PROFILE_A"
```

### §5 Step 2 — confirm the card is visible from profile A

```bash
"$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID" | grep -q "status: ready" \
  || { echo "FAIL: card $TASK_ID is not in status=ready under profile A"; exit 1; }
echo "Card $TASK_ID confirmed ready under profile $PROFILE_A"
```

### §5 Step 3 — confirm the card is INVISIBLE from profile B without the bridge

This is the negative half. Without `HERMES_KANBAN_DB`, profile B's dispatcher looks at profile B's DB, where the card does not exist.

```bash
"$IRONHERMES_BIN" --profile "$PROFILE_B" kanban show "$TASK_ID" 2>&1 | tee /tmp/uat-s5-step3.txt
grep -q -i "not found\|no such task\|error" /tmp/uat-s5-step3.txt \
  || { echo "FAIL: profile B sees the card without HERMES_KANBAN_DB — F-01 regression"; exit 1; }
echo "Confirmed: profile B does not see $TASK_ID without HERMES_KANBAN_DB"
```

### §5 Step 4 — dispatch from profile B WITH the bridge

```bash
export HERMES_KANBAN_DB="$PROFILE_A_DB"

# Run dispatcher and capture full output. Use `script` or tee — do not drop stderr.
"$IRONHERMES_BIN" --profile "$PROFILE_B" kanban dispatch 2>&1 | tee /tmp/dispatch-s5-uatlog.txt &
DISPATCH_PID=$!
```

### §5 Step 5 — assert the override log line landed (D-H1)

```bash
# Wait briefly for the dispatcher to open the store and log.
sleep 5

grep -c "HERMES_KANBAN_DB override" /tmp/dispatch-s5-uatlog.txt | awk '$1 >= 1 { print "PASS D-H1: HERMES_KANBAN_DB override log emitted ("$1" times)"; exit 0 } { print "FAIL D-H1: override log line missing"; exit 1 }'
```

### §5 Step 6 — poll for terminal status (≤2 minutes)

```bash
for i in $(seq 1 24); do
  STATUS=$("$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID" --json 2>/dev/null | jq -r '.status')
  printf '  poll %2d/24 — status=%s\n' "$i" "$STATUS"
  case "$STATUS" in
    done|blocked|failed) break ;;
  esac
  sleep 5
done
```

### §5 Step 7 — assert final status

```bash
FINAL_STATUS=$("$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID" --json | jq -r '.status')
if [ "$FINAL_STATUS" = "done" ]; then
  echo "PASS §5: card $TASK_ID reached status=done under --profile $PROFILE_A"
else
  echo "FAIL §5: expected status=done, got $FINAL_STATUS"
  "$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID"
  exit 1
fi

# Cleanly stop the backgrounded dispatcher.
kill "$DISPATCH_PID" 2>/dev/null || true
wait "$DISPATCH_PID" 2>/dev/null || true
```

### §5 pass criteria

| Gate | Command | Pass condition |
|------|---------|----------------|
| D-A1 / D-A2 | step 7 | `FINAL_STATUS=done` |
| D-H1 | step 5 | `grep -c 'HERMES_KANBAN_DB override' /tmp/dispatch-s5-uatlog.txt ≥ 1` |
| F-01 negative half | step 3 | Profile B cannot see the card without the bridge |
| F-02 implicit | S-0b Option 2 | Worker subprocess actually executed `$IRONHERMES_BIN` (verify via `ps` if uncertain) |

### §5 recovery (if FAIL)

If §5 stalls and the card sticks in `running`, reset it before retry:

```bash
sqlite3 "$PROFILE_A_DB" <<SQL
UPDATE tasks SET status='ready', claim_pid=NULL, scheduled_at=NULL WHERE id='$TASK_ID';
INSERT INTO task_events(task_id, kind, payload, ts)
  VALUES ('$TASK_ID', 'reclaimed', '{"reason":"uat_manual_reset"}', strftime('%s','now'));
SQL
```

If the override log line is missing, the candidate root causes are:
1. Plan 01 not merged — `git log develop --grep "open_from_env_or_board" -1` must return at least one commit
2. Tracing filter swallowing the line — re-export `RUST_LOG=ironhermes_kanban=info,kanban.db=info`
3. `HERMES_KANBAN_DB` env not actually inherited — `env | grep HERMES_KANBAN_DB` must show the path

## Section 6 — Restricted-Toolset Smoke (DUAL-RAIL per D-C1)

Verifies D-B1, D-B2, D-F1, D-E2. Pick exactly one rail. Rail A is preferred; Rail B is acceptable if live LLM budget is constrained.

### Rail A — Live smoke

Runs an actual restricted-toolset goal-mode card and asserts the worker did not call any tool outside the restricted preset.

```bash
# Reuse Section 0's exports. PROFILE for §6 can be either A or B — this is a single-profile test.
export PROFILE="$PROFILE_A"

TASK_ID=$(
  "$IRONHERMES_BIN" --profile "$PROFILE" kanban create \
    --goal \
    --goal-toolset restricted \
    --goal-max-turns 2 \
    --assignee "$PROFILE" \
    --body "Acceptance: output the single word RESTRICTED. No other text." \
    "§6 restricted-toolset smoke" \
    --json 2>/dev/null | jq -r '.task_id'
)
echo "Created: $TASK_ID with --goal-toolset restricted"

# Dispatch and capture worker log.
unset HERMES_KANBAN_DB  # single-profile test — do not bridge
"$IRONHERMES_BIN" --profile "$PROFILE" kanban dispatch 2>&1 | tee /tmp/dispatch-s6-uatlog.txt &
DISPATCH_PID=$!

for i in $(seq 1 24); do
  STATUS=$("$IRONHERMES_BIN" --profile "$PROFILE" kanban show "$TASK_ID" --json 2>/dev/null | jq -r '.status')
  case "$STATUS" in
    done|blocked|failed) break ;;
  esac
  sleep 5
done

# Assert no restricted-out tools were called.
FAIL=0
if grep -E -q "Tool:\s*terminal" /tmp/dispatch-s6-uatlog.txt; then
  echo "FAIL §6: 'terminal' tool was called despite restricted preset"; FAIL=1
fi
if grep -E -q "Tool:\s*delegate_task" /tmp/dispatch-s6-uatlog.txt; then
  echo "FAIL §6: 'delegate_task' tool was called despite restricted preset"; FAIL=1
fi
if [ "$FAIL" = "0" ]; then
  echo "PASS §6 Rail A: no terminal or delegate_task in worker log"
fi

# D-E2 producer check — HERMES_KANBAN_GOAL_TOOLSET was emitted to the worker env.
grep -q "HERMES_KANBAN_GOAL_TOOLSET=restricted" /tmp/dispatch-s6-uatlog.txt \
  || echo "WARN §6: HERMES_KANBAN_GOAL_TOOLSET=restricted not visible in dispatch log (may be filtered — confirm via worker.log instead)"

kill "$DISPATCH_PID" 2>/dev/null || true
wait "$DISPATCH_PID" 2>/dev/null || true
exit "$FAIL"
```

### Rail A pass criteria

| Gate | Command | Pass condition |
|------|---------|----------------|
| D-B1 / D-B2 / D-F1 | the two grep blocks | Neither `terminal` nor `delegate_task` appears as a worker tool call |
| D-E2 (advisory) | the third grep | `HERMES_KANBAN_GOAL_TOOLSET=restricted` visible (advisory — Rail B covers it deterministically) |
| Wall clock | `$STATUS` loop | Card reaches `done` or `blocked` within 2 min |
