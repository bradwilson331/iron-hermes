## Domain Background

### Kanban-worker Dispatch Path

The ironhermes kanban worker dispatch path has two host contexts:

1. **CLI one-shot dispatcher** (`ironhermes kanban dispatch`): routes through `run_single` in `crates/ironhermes-cli/src/main.rs`. The `run_single` function opens `KanbanStore::open_default()` at line 935, creates a kanban_store_for_loop, then calls `run_goal_loop_if_enabled` at line 1031. This is the primary swap site for F-01.

2. **Gateway background dispatcher loop** (`runner.rs:1281`): the gateway's `runner.rs` runs a ticker that calls `KanbanStore::open_default()` once per tick to check for pending tasks. This was a **gap from SCOPE.md D-01** that CONTEXT.md adds. The gateway dispatcher spawns workers via `spawn_worker_for_board`.

Both paths call `worker_spawn.rs::spawn_worker_for_board` which calls `build_kanban_worker_env`. The env builder already emits `HERMES_KANBAN_DB` (line 113-115) computed from `board_db_path_for_slug(board_slug)` — **but no consumer reads it**. This is the F-01 root cause.

### HERMES_HOME and Profile Resolution

Kanban DB path resolution flows: `HERMES_HOME` (set by `--profile` flag or env) → `kanban_db_path()` (returns `HERMES_HOME/kanban.db`) → `board_db_path_for_slug(slug)` (returns `HERMES_HOME/kanban/boards/<slug>/kanban.db` for non-default). When dispatcher runs under profile A and worker runs under profile B, they resolve different `HERMES_HOME` values, producing different DB paths. The `HERMES_KANBAN_DB` env var was intended to bridge this but the bridge was one-way.

### Goal Mode v2 Semantics from Phase 36.3.7.12

Goal mode workers are spawned normally by the dispatcher. The worker reads `HERMES_KANBAN_GOAL_MODE=1` and `HERMES_KANBAN_GOAL_MAX_TURNS=N` from env, then enters `run_goal_loop_if_enabled` (in `crates/ironhermes-cli/src/kanban/goal_loop.rs`). The loop calls a `TurnRunner` closure per turn, bumps `goal_turns_used` under a CAS gate, invokes an auxiliary judge LLM, and on budget exhaustion emits a synthetic `kanban_block`. The `BudgetSentinel` RAII guard ensures block happens even on panic.

Phase 36.3.7.12 UAT Row 1 (haiku goal mode) passed live. Rows 2-4 were deferred due to FINDING-03 thrash (LLM spawning `delegate_task` subagents under unrestricted toolset, 10-15 min per turn). This phase closes the thrash by adding a restricted toolset filter and inner-loop clamp.

## Implementation Approach

### 1. `open_from_env()` and `open_from_env_or_board()` Factoring

**Recommended factoring** (D-A2 Claude's Discretion): ship TWO public constructors in `store.rs` next to `open_default` (line 224) and `open_for_board` (line 231):

```rust
/// Phase 36.3.7.13 D-A1: env-bridged constructor. HERMES_KANBAN_DB wins if set;
/// falls back to kanban_db_path(). Used at every dispatcher-bridged open site.
pub fn open_from_env() -> Result<Self> {
    if let Ok(path) = std::env::var("HERMES_KANBAN_DB") {
        tracing::info!(
            target = "kanban.db",
            path = %path,
            "kanban store: using HERMES_KANBAN_DB override"
        );
        Self::open(PathBuf::from(path))
    } else {
        Self::open(crate::paths::kanban_db_path())
    }
}

/// Phase 36.3.7.13 D-A2: env-bridged constructor with slug fallback.
/// HERMES_KANBAN_DB wins; else board slug if Some; else kanban_db_path().
/// Dashboard handlers that currently do Some(slug)=>open_for_board / None=>open_default
/// collapse to a single call_site: open_from_env_or_board(slug_opt.as_deref()).
pub fn open_from_env_or_board(slug: Option<&str>) -> Result<Self> {
    if let Ok(path) = std::env::var("HERMES_KANBAN_DB") {
        tracing::info!(
            target = "kanban.db",
            path = %path,
            slug = ?slug,
            "kanban store: using HERMES_KANBAN_DB override; slug ignored"
        );
        Self::open(PathBuf::from(path))
    } else if let Some(s) = slug {
        Self::open_for_board(s)
    } else {
        Self::open(crate::paths::kanban_db_path())
    }
}
```

**Call-site swap guide:**

### 3. Restricted Toolset Filter — Mechanism Decision

**Recommended mechanism: `retain`-based removal from the live registry.**

The `ToolRegistry` in `ironhermes-tools/src/registry.rs` exposes `tools.retain(...)` indirectly via `unregister_by_prefix`. The registry's `tools` field is a `HashMap<String, Arc<dyn Tool>>`. The cleanest path for D-B2 is to add a public method `remove_by_name(&mut self, name: &str)` OR use the existing `tools.retain(|name, _| allowed.contains(name.as_str()))` pattern inside a new helper.

**Alternative considered: `scope_to(&[toolset_names])`** — this creates a new registry scoped to listed toolsets. However, kanban tools all share the `"kanban"` toolset value; you cannot use `scope_to` to select a subset of kanban tools. The restricted preset needs 11 of 13 kanban tools (excludes nothing kanban-specific, just blocks non-kanban tools). The `scope_to` mechanism works well for keeping only kanban toolset but not for allowing file_read/file_write from a different toolset.

**Recommended implementation:**

```rust
// In main.rs, after register_kanban_tools_if_applicable (line 873 area),
// inside the worker_mode && goal_mode branch:
fn filter_for_goal_mode_if_applicable(
    registry: &Arc<RwLock<ToolRegistry>>,
    preset: &str,  // "restricted" | "extended" | "full"
) {
    if preset == "full" { return; }
    let allowed: HashSet<&str> = match preset {
        "restricted" => ["kanban_show","kanban_list","kanban_comment","kanban_complete",
                         "kanban_block","kanban_create","kanban_heartbeat","kanban_link",
                         "kanban_unblock","kanban_swarm","kanban_mention",
                         "kanban_decompose","kanban_specify",
                         "read_file","write_file"].iter().copied().collect(),
        "extended"   => // restricted + memory_tool + memory_manager_handle + skills_tool
                        [...].iter().copied().collect(),
        _            => return,
    };
    let mut reg = registry.blocking_write();
    reg.tools.retain(|name, _| allowed.contains(name.as_str()));
    // Note: reg.tools is private — this requires either a new pub method
    // `retain_by_name(allowed: &HashSet<&str>)` on ToolRegistry, or the
    // function lives inside the ironhermes-tools crate.
}
```

**The `tools` field is private.** The planner must add a `pub fn retain_by_name(&mut self, allowed: &HashSet<&str>)` method to `ToolRegistry` in `ironhermes-tools/src/registry.rs`, OR use the existing `unregister_by_prefix` approach to remove tool groups. Since tool names are stable strings, a `retain_by_name` method is the cleanest 5-line addition.

**Alternative if `retain_by_name` addition is undesirable:** Use `register_defaults_except(&["terminal", "delegate_task", "web_fetch", ...])` at registration time instead of post-registration removal. This requires knowing the skip list upfront and changing the registration order — more fragile.

**Verdict: Add `pub fn retain_by_name(&mut self, allowed: &[&str])` to ToolRegistry.** This is a 5-line method, stays within the crate, satisfies "LLM never sees blocked schemas" (D-B2), and is testable in isolation.

### 5. Clap Surface for `--goal-toolset`

The existing clap structure in `commands.rs` already handles `--goal` (line 130, `goal_max_turns: u32`). Add `--goal-toolset` as a `String` arg (default `"restricted"`) that is only valid when `--goal` is set.

Clap 4 handles mutual dependency via `requires` on the field:

```rust
/// Toolset preset for goal-mode workers (default: restricted).
/// Invalid without --goal.
#[arg(long, default_value = "restricted", requires = "goal",
      value_parser = ["restricted", "extended", "full"])]
goal_toolset: String,
```

**Risk: `requires` + `default_value` interaction.** Clap 4 does NOT error when a `requires`-gated arg is at its default value without the gating arg being set. If `--goal-toolset` has `default_value = "restricted"`, then invoking `kanban create "title"` without `--goal` will succeed silently (the default value is present, but `--goal` is absent, yet clap won't error because the arg value was "supplied" by the default). 

**Resolution: Do NOT use `default_value` on `--goal-toolset`.** Instead use `Option<String>` and resolve the default at the application layer:

```rust
#[arg(long, requires = "goal", value_parser = ["restricted","extended","full"])]
goal_toolset: Option<String>,
```

Then in the handler: `let preset = goal_toolset.unwrap_or_else(|| "restricted".to_string());`

This way: `kanban create "title"` passes (goal_toolset is None, --goal absent, no conflict). `kanban create "title" --goal-toolset restricted` fails with clap error (goal_toolset requires goal). `kanban create "title" --goal --goal-toolset restricted` passes. `kanban create "title" --goal` passes (goal_toolset defaults to "restricted" in handler).

This is cleaner and safer than a custom validator.

## Risks & Open Questions

### Risk 1: `--goal-toolset` clap `requires` + absence of default

**What goes wrong:** If `--goal-toolset` has `default_value = "restricted"`, clap's `requires = "goal"` check does not fire when the arg is at its default. A user running `kanban create "title" --goal-toolset extended` without `--goal` would succeed silently.

**Mitigation:** Use `Option<String>` (no `default_value`); resolve default in handler. Requires one extra `unwrap_or_else` in the handler but eliminates the footgun.

**Status:** Documented in Implementation Approach §5. LOW risk if the `Option<String>` pattern is followed.

### Risk 2: `store_writer_impl.rs:33` swap assessment

**What goes wrong:** CONTEXT.md does not include `store_writer_impl.rs` in the swap table, but this file calls `KanbanStore::open_default()` for what the comment describes as "dashboard write paths." If this runs in a profile-bridged context, it would miss the F-01 fix.

**Mitigation:** Planner reads `store_writer_impl.rs` fully to determine whether it is called from a dispatcher-bridged path (swap to `open_from_env()`) or only from interactive contexts (keep `open_default()`).

**Status:** OPEN — requires planner investigation. Tentative recommendation: swap.

### Risk 3: Tool names in restricted preset — exact name strings

**What goes wrong:** If tool names in the registry don't exactly match the strings used in the `retain_by_name` filter (e.g., `"read_file"` vs `"ReadFile"` vs `"file_read"`), the filter will silently fail.

**Mitigation:** The test `goal_toolset_filter.rs` must assert the exact tool count (15 for `restricted`) so any naming drift causes a test failure. Planner should grep tool name strings from `register_defaults_except` source. From the registry source, `"terminal"`, `"read_file"`, `"write_file"`, `"patch_file"`, `"search_files"` are the defaults. Kanban tools register as `"kanban_<verb>"`.

**Status:** MEDIUM risk during implementation. Unit test provides the safety net.

### Risk 4: `ToolRegistry.tools` is private — `retain_by_name` needs to be added

**What goes wrong:** The `tools` HashMap is private in both `ironhermes-tools` and `ironagent-tools-api` registry implementations. A post-registration removal requires either a new public method or a different mechanism.

**Mitigation:** Add `pub fn retain_by_name(&mut self, allowed: &[&str])` to `ToolRegistry` in `ironhermes-tools/src/registry.rs`. This is 5 lines and is the correct abstraction (mirrors `unregister_by_prefix` already in the type). Alternatively: move the filter before `register_defaults` and use `register_defaults_except` — but this requires knowing the skip list upfront and breaks the D-B2 contract ("after `register_default_tools`").

**Status:** LOW risk — clean additive API extension. Planner must ensure the method is added in Plan 3.

### Risk 5: `goal_mode_no_dispatcher_change` invariant still holds after swap

**What goes wrong:** The Phase 36.3.7.12 Plan 05 test `goal_mode_no_dispatcher_change` asserts the 8-step event-kind list equality for goal vs non-goal cards. The `open_from_env()` swap in the dispatcher loop (`runner.rs:1281`) and the `run_single` path should not affect dispatcher-layer events. But if the swap somehow breaks the store open in a test that sets a different HERMES_KANBAN_DB env, the test environment could be contaminated.

**Mitigation:** The integration tests for `cross_profile_db_resolution.rs` must use `temp_dir()` for isolation and set `HERMES_KANBAN_DB` only within `std::env::set_var` / `remove_var` guards. Alternatively use a dedicated test-env-isolation helper. The existing dispatcher tests do not set `HERMES_KANBAN_DB`, so contamination risk is LOW as long as new tests clean up after themselves.

### Risk 6: `decompose` and `specify` store injection timing

**What goes wrong:** `decompose.rs` and `specify.rs` receive their store via constructor at `register_kanban_tools` time (not at `execute()` time). If the store is opened before `HERMES_KANBAN_DB` is set in the worker env (which can't happen — env is set by the parent process before the worker boots), OR if the registration call opens the store without `open_from_env()`, the two tools would use the wrong DB.

**Mitigation:** Ensure `register_kanban_tools_if_applicable` (at `main.rs:873` and `main.rs:1629`) opens its store via `open_from_env()` before constructing the store Arc. The store Arc is created once and shared via `Arc::clone` to all 13 tools. If the Arc-wrapped store uses `open_from_env()`, all 13 tools (including decompose/specify) see the correct DB.

**Status:** MEDIUM importance — planner must trace the store-Arc creation site in `register_kanban_tools_if_applicable` and ensure it uses `open_from_env()`.

### Claude's Discretion Recommendations

- **`open_from_env` vs `open_from_env_or_board` naming:** Recommend the two-function factoring from D-A2. The single-function `open_from_env(slug: Option<&str>)` signature also works but the two-function approach is clearer for call sites that only need the no-slug path (dispatcher, WS tailer, gateway runner).
- **`HERMES_KANBAN_GOAL_TOOLSET` env-var name:** Keep as-is. The `HERMES_KANBAN_GOAL_*` prefix is the established convention from Phase 36.3.7.12 (`HERMES_KANBAN_GOAL_MODE`, `HERMES_KANBAN_GOAL_MAX_TURNS`). `HERMES_KANBAN_GOAL_TOOLSET` is the natural extension.
- **Plan slicing:** Keep SCOPE.md's 4-wave structure. Plan 1 (F-01 store swap) is the most valuable for unblocking live UAT. Plan 2 (F-02 binary override) is file-disjoint from Plan 1 and could run in parallel in a worktree. Plan 3 (toolset + schema + clamp) is the largest; keep it in its own wave to preserve bilateral test discipline. Plan 4 (docs) can be worked in parallel with Plan 3 since it touches only Markdown.

### §5 — Cross-Profile DB Resolution (LIVE REQUIRED)

This test verifies that a goal-mode card created under `--profile A` is found and dispatched by a worker running under `--profile B` when `HERMES_KANBAN_DB` bridges the profiles.

```bash
#!/usr/bin/env bash
set -euo pipefail

PROFILE_A="dev"
PROFILE_B="default"  # or whatever the gateway profile is
IRONHERMES_BIN="${IRONHERMES_WORKER_BIN:-$(which ironhermes)}"

# Step 1: Create a goal-mode card under profile A
TASK_ID=$(
  "$IRONHERMES_BIN" --profile "$PROFILE_A" kanban create \
    --goal \
    --goal-toolset restricted \
    --goal-max-turns 3 \
    --assignee "$PROFILE_A" \
    --body "Acceptance: produce the word PARITY in uppercase with no other output." \
    "§5 cross-profile DB resolution UAT" \
    --json 2>/dev/null | jq -r '.task_id'
)
echo "Created: $TASK_ID under --profile $PROFILE_A"

# Verify card is visible from profile A
"$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID" | grep -q "status: ready"
echo "Card confirmed ready under profile $PROFILE_A"

# Step 2: Derive DB path for profile A
PROFILE_A_DB="$HOME/.ironhermes/profiles/$PROFILE_A/kanban.db"
# (adjust path if HERMES_HOME is set differently; use `ironhermes --profile A kanban show` to confirm)

# Step 3: Dispatch from profile B with HERMES_KANBAN_DB bridging
export HERMES_KANBAN_DB="$PROFILE_A_DB"
export IRONHERMES_WORKER_BIN="$IRONHERMES_BIN"

"$IRONHERMES_BIN" --profile "$PROFILE_B" kanban dispatch 2>&1 | tee /tmp/dispatch-$5-uatlog.txt

# Step 4: Assert HERMES_KANBAN_DB override was read
grep -q "HERMES_KANBAN_DB override" /tmp/dispatch-$5-uatlog.txt || \
  (echo "FAIL: override log line not found — store did not read HERMES_KANBAN_DB" && exit 1)
echo "PASS: HERMES_KANBAN_DB override log line present"

# Step 5: Wait for worker to complete (poll up to 120s)
for i in $(seq 1 24); do
  STATUS=$("$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID" --json 2>/dev/null | jq -r '.status')
  echo "  poll $i/24: status=$STATUS"
  if [[ "$STATUS" == "done" || "$STATUS" == "blocked" ]]; then break; fi
  sleep 5
done

# Step 6: Assert final status from PROFILE A's perspective
FINAL_STATUS=$("$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID" --json | jq -r '.status')
if [[ "$FINAL_STATUS" == "done" ]]; then
  echo "PASS §5: card $TASK_ID reached status=done under --profile $PROFILE_A"
else
  echo "FAIL §5: expected status=done, got $FINAL_STATUS"
  "$IRONHERMES_BIN" --profile "$PROFILE_A" kanban show "$TASK_ID"
  exit 1
fi
```

**Expected log grep assertions:**
- `grep -c 'HERMES_KANBAN_DB override' /tmp/dispatch-$5-uatlog.txt` — must be >= 1
- `ironhermes --profile "$PROFILE_A" kanban show "$TASK_ID" --json | jq .status` — must be `"done"`

pub fn retain_by_name(&mut self, allowed: &[&str]) {
