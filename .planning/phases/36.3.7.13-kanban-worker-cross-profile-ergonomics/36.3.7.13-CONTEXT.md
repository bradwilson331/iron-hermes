**Gathered:** 2026-06-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Operational hardening of the kanban-worker dispatch path surfaced by Phase
36.3.7.12 goal-mode UAT. Closes the five FINDING-* items from
`36.3.7.12-05-SUMMARY.md`:

1. **F-01 — Cross-profile DB resolution.** Add `KanbanStore::open_from_env()`
   honoring `HERMES_KANBAN_DB`, and adopt it at every consumer site (CLI
   one-shot dispatcher, gateway background dispatcher loop, dashboard SPA
   read/write handlers, dashboard WS tailer, all 13 LLM kanban tools).
2. **F-02 — Worker bin override.** Add `IRONHERMES_WORKER_BIN` env var to
   `worker_spawn.rs:254` so `cargo run` from a worktree pins worker
   subprocesses to the same code base without the `~/.local/bin/ironhermes`
   symlink dance. Add it to `SAFE_SYSTEM_VARS` for recursive worker spawn.
3. **F-03 — Goal-mode toolset thrash.** Default goal-mode workers to a
   restricted toolset, clamp the inner agent loop to a small ceiling.
4. **F-04 — Profile-context documentation gap.** Ship six documentation
   surfaces covering profile resolution, CLI cheatsheet, profile-discipline
   runbook, goal-mode UAT prompt patterns, skill update, reference update.
5. **F-05 — `api_key_file:` credential form.** OUT OF SCOPE (deferred to a
   future credentials-hardening phase per SCOPE.md).

**Schema bump:** v2 → v3 adds `goal_toolset TEXT NULL` to `tasks`. Migration
ships in the same plan slice as the column, same commit, no separate
phase. Backward compat: NULL on existing goal_mode cards resolves to
`restricted` at worker spawn (D-E1 below).

**Scope anchor:** operational hardening + documentation. No new dispatcher

## Implementation Decisions

### HERMES_KANBAN_DB consumer scope (closes F-01)

- **D-A1 — Central `open_from_env()` helper, called everywhere.** Add a
  single new constructor in `crates/ironhermes-kanban/src/store.rs` next
  to the existing `open_default` / `open_for_board` pair:

  ```rust
  /// Phase 36.3.7.13 D-A1: read HERMES_KANBAN_DB first, fall back to
  /// kanban_db_path(). Single source of truth for env-bridged opens.
  pub fn open_from_env() -> Result<Self> {
      if let Ok(path) = std::env::var("HERMES_KANBAN_DB") {
          tracing::info!(
              target = "kanban.db",
              path = %path,
              "kanban store: using HERMES_KANBAN_DB override"
          );
          Self::open(PathBuf::from(path))
      } else {
          Self::open(crate::paths::kanban_db_path())
      }
  }
  ```

  Every existing `open_default()` call site swaps to `open_from_env()`.
  Touched sites (~25, each a 1-line swap):

  | Site | File | Notes |
  |---|---|---|
  | CLI one-shot dispatcher | `crates/ironhermes-cli/src/main.rs:935` | `run_single` wrapper |
  | Gateway background dispatcher loop | `crates/ironhermes-gateway/src/runner.rs:1281` | Phase 36.3.7.5 Plan 03 spawn site |
  | Dashboard SPA read handlers (8 `#[server]` fns) | `crates/iron_hermes_ui/src/server/kanban_api.rs:55,121,284,341,402,504,707,759` | `fetch_*` + `patch_task_status` + `post_comment` + `create_task` |
  | Dashboard SPA WS tailer | `crates/iron_hermes_ui/src/server/kanban_ws.rs:239` | `run_kanban_tail_loop` (D-15 live-update spine) |
  | All 13 LLM kanban tools | `crates/ironhermes-kanban/src/tools/{show,list,comment,complete,block,create,heartbeat,link,unblock,swarm,mention,decompose,specify}.rs` | each tool's `execute()` body |

  **Other `open_default` sites stay unchanged.** CLI `main.rs:307` and
  `main.rs:1646` operate in user-interactive shell context outside the
  dispatcher→worker bridge; the env override should not affect them.
  Planner to audit per call site during planning.

- **D-A2 — Env wins; slug becomes a hint.** When both `HERMES_KANBAN_DB`
  and a board slug are set (existing dispatcher→worker bridge sets BOTH),
  the env path wins. The slug remains informational (passed through env as
  `HERMES_KANBAN_BOARD` per existing worker_spawn:111-115). Dashboard's
  board-picker becomes inert when env is set — acceptable because
  dashboards are not run with `HERMES_KANBAN_DB` set in real operations
  (the env is for worker subprocesses spawned by dispatcher).

  Implementation implication: a sibling `open_from_env_or_board(slug)` is
  unnecessary. Callers that pass slug today (`open_for_board(slug)`)
  should switch to a single helper whose contract is "env if set; else
  slug if provided; else default":

  ```rust
  pub fn open_from_env_or_board(slug: Option<&str>) -> Result<Self> {
      if let Ok(path) = std::env::var("HERMES_KANBAN_DB") {
          tracing::info!(target = "kanban.db", path = %path,
                         slug = ?slug, "using HERMES_KANBAN_DB override; slug ignored");
          Self::open(PathBuf::from(path))
      } else if let Some(s) = slug {
          Self::open_for_board(s)
      } else {
          Self::open(crate::paths::kanban_db_path())
      }
  }
  ```

  Dashboard handlers that today resolve `Some(slug) => open_for_board(slug)`
  / `None => open_default()` collapse to a single call to this helper.

- **D-H1 — `tracing::info!` every call, no Once gating.** The
  `kanban.db` logger fires on every `open_from_env()` invocation.
  Operators can silence via `RUST_LOG=kanban.db=warn`. Multi-tool worker
  sessions will produce dozens of lines per turn — accepted trade for
  unambiguous foot-gun visibility. No `std::sync::Once`, no per-path
  cache.

### Restricted toolset (closes F-03 thrash)

- **D-B1 — Three-tier named presets.** Add `goal_toolset` column type
  `TEXT NULL` holding one of three preset names. Operator-configurable per
  card at create-time. CLI flag `--goal-toolset` on `kanban create` takes
  the same enum.

  | Preset | Contents | LLM tool count |
  |---|---|---|
  | `restricted` (default) | `kanban_*` (13) + `file_read` + `file_write` | 15 |
  | `extended` | restricted + `memory_*` (`memory_tool` + `memory_manager_handle`) + `skills_tool` | ~18 |
  | `full` | no filtering, current registry intact (SCOPE.md escape hatch) | full registry |

  Names preserve SCOPE.md vocabulary (`restricted`, `full`) and add
  `extended` as middle tier. Default is `restricted` per SCOPE.md D-03.

- **D-B2 — Filter at worker startup, after `register_default_tools`.** In
  `main.rs` worker-mode entry (around the existing
  `register_kanban_tools_if_applicable` call at line 873 / 1629), after the
  full registry is built, run a `filter_for_goal_mode(registry, preset)`
  pass that REMOVES disallowed tools from the registry. The LLM literally
  never sees the schemas for excluded tools — no temptation, no wasted
  turns retrying blocked tools.

  Filter site is **inside the `if worker_mode && goal_mode` branch only**.
  Non-goal workers and non-worker (interactive) sessions retain the full
  registry.

- **D-B3 — CLI surface.** New clap flag on `kanban create`:

  ```text
  ironhermes kanban create [--goal] [--goal-max-turns N]
                           [--goal-toolset restricted|extended|full]
                           [--assignee USER] [--body PROMPT] TITLE
  ```

  When `--goal` is set without `--goal-toolset`, default is `restricted`.
  When `--goal` is NOT set, `--goal-toolset` is invalid (clap error) — the
  preset has no meaning for non-goal cards.

- **D-G1 — LLM `kanban_create` tool surface.** `KanbanCreateTool` JSON
  schema gains an optional `goal_toolset: { type: "string", enum:
  ["restricted","extended","full"] }` field. Symmetric with CLI surface.
  Missing field → NULL column → resolves to `restricted` per D-E1.
  `kanban_swarm` shared-root inheritance NOT in scope this phase
  (deferred — would expand Phase 36.3.7.7 surface).

### Goal-mode storage + env contract

- **D-E1 — NULL semantics: backward-compat default = `restricted`.** When
  a goal_mode=true card has `goal_toolset = NULL` (pre-v3 cards after
  schema migration), the worker uses the `restricted` preset. Honors
  SCOPE.md D-07 literally. **This IS a behavior change for existing
  in-flight goal-mode cards** — pre-v3 they ran with no filter. Mitigation:
  the only such cards are from Phase 36.3.7.12 UAT (operator-known), and
  the FINDING-03 thrash pathology means the unrestricted-on-existing-cards
  behavior was already broken in practice.

- **D-E2 — Env var always carries the resolved preset string.**
  `worker_spawn` resolves NULL → `"restricted"` at spawn time, then emits
  `HERMES_KANBAN_GOAL_TOOLSET=<preset>` env var when `goal_mode=true`. The
  worker reads the env verbatim — no second resolver, no two-sided
  default-agreement requirement. Single source of truth: dispatcher.

  Existing `HERMES_KANBAN_GOAL_MODE=1` / `HERMES_KANBAN_GOAL_MAX_TURNS=N`
  emissions from Phase 36.3.7.12 (worker_spawn:164, 396) are unchanged.

### Inner agent loop clamp (closes F-03 thrash, second axis)

- **D-F1 — `kanban.goal_inner_max_iterations` config knob, default 10.**
  New field on `KanbanConfig` (sibling of `judge_model` /
  `decomposer_model`). Worker-side clamp:

  ```rust
  // In main.rs worker-mode entry, when HERMES_KANBAN_GOAL_MODE=1:
  config.agent.max_iterations = std::cmp::min(
      config.agent.max_iterations,
      kanban_config.goal_inner_max_iterations,
  );
  ```

  Default 10 honors SCOPE.md D-04. Operators can tune up for large-goal
  workspaces (translate-docs-site example) or down for tight-budget
  ones. New config doc-comment + default-roundtrip test + KanbanConfig
  `default()` extension.

### Claude's Discretion

- **Exact wording of the `kanban.db` log line.** D-A1 shows one shape;
  planner can refine the message text + field names as long as the
  `target = "kanban.db"` invariant holds.
- **Whether to ship a sibling `open_from_env_or_board(slug)` or fold
  slug-aware behavior inside a single `open_from_env(slug: Option<&str>)`.**
  D-A2 lays out the slug-aware variant; planner picks the factoring that
  minimizes call-site churn (most existing sites have a binary
  `Some(slug) => open_for_board(slug) / None => open_default()` shape that
  collapses to a single call cleanly).
- **Exact preset filter implementation.** D-B2 specifies the call site
  (worker startup, after `register_default_tools`). The filter mechanism
  (drop-from-registry vs mark-disabled vs build-parallel-registry) is at
  planner discretion. Constraint: the LLM must not see the schemas for
  excluded tools.
- **`HERMES_KANBAN_GOAL_TOOLSET` env-var name spelling.** D-E2 specifies
  the resolved preset string is carried; the env-var name itself is the
  natural extension of the existing `HERMES_KANBAN_GOAL_MODE` /
  `HERMES_KANBAN_GOAL_MAX_TURNS` convention. Planner can rename if a
  stronger convention is established by Phase 36.3.7.12 plan SUMMARY data.
- **Plan slicing.** SCOPE.md proposes 4 plans across 4 waves. Planner can
  refactor (e.g., merge Plan 3 + Plan 4 documentation step if Plan 3
  ships before all 6 docs; split Plan 1 if the dashboard sweep grows too
  large). The schema bump + column adoption (Plan 3) is the most
  invasive slice; preserve its bilateral test discipline.
- **Test coverage depth for the dashboard's 9 swapped sites.** All 9 sites
  collapse to the same helper call; one bilateral test per helper variant
  is sufficient. Planner can add per-handler integration tests if
  warranted by risk analysis.
