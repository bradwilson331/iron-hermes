# Phase 36.3.7.13 — Kanban worker cross-profile ergonomics + goal-mode UAT polish

## Goal

Close the operational gaps surfaced during Phase 36.3.7.12 goal-mode UAT. Specifically:

1. Make kanban workers respect the dispatcher-supplied `HERMES_KANBAN_DB` env var so dispatcher + worker can run under different profiles without losing the card.
2. Let `cargo run` from a worktree pin worker subprocesses to the same code base via `IRONHERMES_WORKER_BIN` env override (no more `~/.local/bin/ironhermes` symlink dance).
3. Prevent goal-mode workers from thrashing on tool-spawned subagents when acceptance criteria are ambiguous — either restrict toolset by default or clamp the inner agent loop.
4. Document the kanban worker operational model end-to-end: config files (global + profile), CLI verbs (per-profile discipline), goal-mode UAT prompt patterns, breaker-recovery recipes.

This phase is **operational hardening + docs** — no new features, no schema bumps. Crate-isolation fence from 36.3.7.x holds: zero new dependencies, zero gateway-side edits.

## Source findings (verbatim from 36.3.7.12-05-SUMMARY.md)

| F-01 | `HERMES_KANBAN_DB` is set-but-never-read | HIGH (UAT-blocking) | Live UAT Row 1 attempt under mixed profile contexts |

## Locked decisions

These will be ratified in the phase's CONTEXT.md after `/gsd-discuss-phase` runs; preliminary positions for the planner:

- **D-01 — `HERMES_KANBAN_DB` consumer.** Add `KanbanStore::open_from_env()` that reads `HERMES_KANBAN_DB` first, falls back to `kanban_db_path()`. Plan-04's `run_single` wrapper at `crates/ironhermes-cli/src/main.rs:935` switches from `open_default()` to `open_from_env()`. All 6 kanban LLM tools (`tools/{create,list,link,unblock,heartbeat,comment,swarm}.rs`) adopt the same constructor inside their `execute()` body. Test gate: `kanban_store_honors_db_env_override` integration test that creates a card under one HERMES_HOME, spawns a worker with `HERMES_KANBAN_DB` pointing at it, and asserts the worker reads the card.
- **D-02 — `IRONHERMES_WORKER_BIN` override.** `worker_spawn.rs:254` checks `std::env::var("IRONHERMES_WORKER_BIN")` first, falls back to `"ironhermes"` (current behavior). Worker_spawn tests assert both paths. Add the env var to the SAFE_SYSTEM_VARS allowlist so workers spawned recursively use the same binary (forward-compat).
- **D-03 — Goal-mode toolset default.** When `HERMES_KANBAN_GOAL_MODE=1` is set in worker env, the agent runtime registers a RESTRICTED toolset: kanban_* tools + file_read + file_write only. Specifically NO `terminal`, NO `delegate_task`, NO `web_fetch`. Operator can override per-card via a new `--goal-toolset full|restricted` flag on `kanban create` (default `restricted`). Stored as `goal_toolset: TEXT` on tasks (schema v3 — separate small migration).
- **D-04 — Inner agent loop clamp.** When `HERMES_KANBAN_GOAL_MODE=1`, the parent agent loop's `max_iterations` is clamped to `min(config.agent.max_iterations, 10)`. This bounds a single goal-turn's wall-clock cost. Subagents (if D-03 allows them) inherit a smaller cap.
- **D-05 — Documentation surfaces.** Six new/updated documents (see Documentation section below).
- **D-06 — No schema-bump cascade.** D-03's `goal_toolset` column triggers SCHEMA_VERSION 2→3, BUT we ship the migration ladder + DDL update in the same plan, same commit, no separate phase.
- **D-07 — Backward compatibility.** Existing goal-mode cards (`goal_toolset` NULL) default to `restricted`. Operator's prior UAT cards are unaffected because they never reach the new env var.
- **D-08 — Crate-isolation fence (carried over from 36.3.7).** Zero new dependencies, zero `ironhermes-gateway` deps in `ironhermes-kanban` Cargo.toml.

## Out of scope (deferred to later phases)

- **F-05 — `api_key_file:` credential form.** Worker env_clear() drops `*_API_KEY` env vars per D-18 security guarantee. The only currently-working credential path is the deprecated `api_key:` literal in profile config.yaml. Fixing this cleanly requires a new credential resolver that reads from a mode-0600 file on disk, which is a discrete piece of work and not blocking goal-mode UAT. Defer to a credentials-hardening phase.
- **DEFCON gating for goal mode.** Phase 36.3.7.12 CONTEXT.md explicitly deferred DEFCON gating; still deferred.
- **Live UAT Rows 2-4 from Phase 36.3.7.12.** Once D-03 + D-04 land, the original UAT timing pathology goes away. Re-run live UAT then OR rely on Plan-04's unit-test coverage (`budget_exhaustion_synthesizes_block`, `judge_invocation_failure_passes_through_to_next_turn`).

### DOC-D — `docs/kanban/goal-mode-uat-prompts.md` (NEW)

Lessons from Phase 36.3.7.12 UAT:
- **Avoid filesystem-temptation prompts.** "Find the string X" → LLM greps filesystem.
- **Prefer logical impossibility over tool-evadability.** "summary='banana' AND summary='apple' simultaneously" forces the judge path.
- **Prefer constrained-output over open-ended.** "reply in exactly 0 tokens" exhausts budget fast without thrashing.
- **Use `--goal-toolset restricted` (default in 36.3.7.13).** No terminal, no delegate_task, no web — LLM can only reason.
- 4-row reference UAT script with new prompts and expected event sequences.

## Risks & threats

- **T-01 (M):** D-01's env-var-first resolution changes the meaning of `KanbanStore::open_default()` callers if they were relying on HERMES_HOME drift. Mitigation: keep `open_default()` byte-identical; only the new `open_from_env()` consults the env var. Audit confirms `open_from_env()` is used only by Plan-04 wrapper + 6 LLM tools — all worker-resident paths.
- **T-02 (L):** D-02's `IRONHERMES_WORKER_BIN` could be set to a malicious binary. Same risk class as PATH lookup itself — out of threat model (operator owns their env). Document the assumption.
- **T-03 (M):** D-03's restricted toolset breaks goal-mode cards that legitimately need terminal/delegate_task. Mitigation: `--goal-toolset full` escape hatch + clear error message ("kanban_block reason='restricted toolset; rerun with --goal-toolset full'").
- **T-04 (L):** D-06's schema v2→v3 migration on an existing DB. Mitigation: same DDL+ladder pattern as 36.3.7.12-01, full bilateral test coverage (fresh / upgrade / idempotent re-run).
