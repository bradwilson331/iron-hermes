# Phase 36.3.7.1 — Kanban dispatcher: extend circuit breaker to remaining failure paths

## Phase Goal

Close the two structurally-identical receiver-end gaps that Phase 36.3.7.0 Plan 03 explicitly
deferred to this sub-phase: `reclaim_stale_claims` and `enforce_max_runtime` in
`crates/ironhermes-kanban/src/dispatcher.rs` both bump `consecutive_failures` but never invoke
`apply_circuit_breaker`. Same pattern as BUG-36.3.7-03 (closed in 36.3.7.0-03) on different
dispatcher steps. Fix is mechanical (call the breaker after the bump, mirroring the canonical
line 305 pattern) plus receiver-end tests covering both new paths × both sides of the
`failure_limit` bound.

This phase is **bilateral-tracing-by-construction**: each plan delivers BOTH the producer
(the new `apply_circuit_breaker` call site) AND the consumer (the receiver-end test that drives
the path and asserts the resulting blocked-task state). The bilateral-tracing meta-rule
(LEARNINGS 2026-05-29) is satisfied at the plan level, not deferred to verification.

## Worktree / Parallelization Strategy

**Decision: 2 plans in 1 wave, separate worktrees, sequential merge (reclaim → enforce).**

Rationale:
- The two edits touch **different functions** in `dispatcher.rs` (lines ~460-470 vs ~580-582).
  The line ranges do NOT overlap; the new code blocks are ~6 LOC each, separated by ~110 lines
  of unrelated function body.
- Both plans also touch the **same test file** (`tests/dispatcher_logic.rs`) by appending
  new `#[tokio::test]` functions at the end of the file. Test functions are independent —
  the only shared surface is the closing of the file, which is append-only.
- Parallel-eligible because the source edits are non-overlapping in their immediate line
  windows. Merge conflicts are possible but localized: if the second worktree's diff context
  shifts due to the first worktree's edit landing first, `git` may report a conflict on the
  test file (append point) or on whitespace/blank-line context in `dispatcher.rs`. Cost is
  bounded: a single rebase + retry on plan 02.
- Merge order is **reclaim first, then enforce** by convention (matches the dispatcher's step
  order: step 3 = reclaim, step 4 = enforce_max_runtime). This is not load-bearing — either
  order works — but it keeps the diff narrative monotone with the file's existing structure.

If the developer running this phase prefers zero coordination cost, they MAY serialize the
two plans (execute Plan 01 fully, then Plan 02 fully) in a single worktree. The wave-1
parallel structure is the **default**; serial execution is a no-cost fallback.

**Not chosen: single-plan collapse.** The two paths are independent BUGs in the ROADMAP
(BUG-36.3.7.1-01 vs BUG-36.3.7.1-02); collapsing them into one plan would hide that
separation in commit history and SUMMARY artifacts. The marginal cost of 2 plans is the
single rebase risk noted above — acceptable.

## Scope Fences (binding on both plans)

- **No changes to `apply_circuit_breaker`'s body or signature** (dispatcher.rs:972-1035).
  Validated as correct by 36.3.7.0-03; the call sites are what's missing.
- **No changes to the bump-blocks themselves.** Add the breaker call AFTER the existing
  `UPDATE tasks SET consecutive_failures = consecutive_failures + 1` block; leave the bump
  untouched.
- **No changes to the `>=` comparison at dispatcher.rs:1000.** D-12 clarifying comment from
  36.3.7.0-03 explicitly forbids it.
- **No changes to the existing 36.3.7.0-03 site at line 305** or the original 36.3.7 site
  at line 899. Those are the canonical references.
- **No silent fix of the missing `KanbanEventKind::Reclaimed` event** in `reclaim_stale_claims`
  (doc comment at dispatcher.rs:19 says "append `reclaimed` event" but only a
  `tracing::info!` exists at lines 437-441). Document the finding in Plan 01 SUMMARY; do
  NOT fix in this phase. `apply_circuit_breaker` does not depend on the event being present.
- **No changes outside `crates/ironhermes-kanban/`.** This phase is dispatcher-only.
- **No helper extraction.** The bump+event+breaker pattern stays duplicated across the (now 4)
  sites.
- **No expansion if the receiver tests find additional gaps.** If a test surfaces a real bug
  in `apply_circuit_breaker` or a sibling path, halt and open a follow-up phase — do NOT
  silently fix in 36.3.7.1.
