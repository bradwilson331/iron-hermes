# Phase 36.3.7.1 Plan 02: Circuit Breaker on `enforce_max_runtime` (BUG-36.3.7.1-02) Summary

Closed BUG-36.3.7.1-02 by wiring `apply_circuit_breaker` into the `enforce_max_runtime`
path of `crates/ironhermes-kanban/src/dispatcher.rs`. The path previously bumped
`consecutive_failures` (lines 570-577) and appended a `TimedOut` event (lines 579-594) but
never invoked the breaker — same structural shape as the BUG-36.3.7-03 gap that 36.3.7.0-03
closed on `detect_crashed_workers`. After this plan, a task whose worker exceeds its
`max_runtime_seconds` budget AND whose `consecutive_failures` reaches `failure_limit` is
blocked on the SAME tick the bump happens — not one tick later via the spawn-failure
breaker.

Also delivers 2 of 4 receiver-end tests for BUG-36.3.7.1-03 (the other 2 land in Plan 01,
which has merged and shipped its tests at lines 908 / 1029 of `tests/dispatcher_logic.rs`).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Plan's dead-PID seed strategy short-circuits `enforce_max_runtime`**

- **Found during:** Task 3 first test run.
- **Issue:** The PLAN.md `<behavior>` section instructed seeding a dead PID (`999_999_995` / `999_999_994`) with `claim_expires = now + 900.0` (future) to suppress reclaim, then driving `run_dispatch_tick` to trigger `enforce_max_runtime`. In practice both tests failed at the FIRST assertion (`timed_out event must be appended`) with a sub-second wall-clock (0.02s) — the function never entered its loop. Root cause: `detect_crashed_workers` (dispatcher step 1) runs BEFORE `enforce_max_runtime` (step 4) and gates on `if is_pid_alive(pid) { continue; }` (line 250) — NOT on `claim_expires`. With a dead PID, step 1 intercepts: closes the run, releases the claim (`status → ready`), bumps `consecutive_failures`, appends a `crashed` event, and invokes the breaker. By the time step 4 runs, the task is no longer `running` and is excluded from `list_tasks(status="running")`.
- **Fix:** Replace the dead PID with a live PID by spawning a real `sleep 120` child process. The child is owned by the test process, so `kill_pid(child_pid, SIGTERM)` from the dispatcher is safe (it does NOT target the test runner — see the existing `pid.rs::tests::kill_pid_self_with_term_fails_gracefully` test which explicitly warns against using `std::process::id()`). With a live PID: step 1 skips (PID alive), step 2 skips (`claim_expires >= now`), step 3 skips (`claim_expires >= now`), step 4 enters the loop because `elapsed = 7200 > 60 = max_runtime`. Each test calls `child.wait()` after the tick to reap.
- **Files modified:** `crates/ironhermes-kanban/tests/dispatcher_logic.rs` (both new tests).
- **Commit:** `ec384297`

**2. [Process - Option B recovery] Task 2 source edit landed on `develop` from the main checkout instead of the spawn-time worktree branch**

- **Found during:** Task 2 commit.
- **Issue:** The harness's CWD reset between Bash calls combined with the use of absolute paths under `/Users/twilson/code/ironhermes/...` routed Edit and Bash operations against the main repo checkout (which was on `develop`), not the spawn-time worktree (`/Users/twilson/code/ironhermes/.claude/worktrees/agent-af0c809d7eb72e0ed`, branch `worktree-agent-af0c809d7eb72e0ed`). The commit landed at `179de393` on `develop` — a protected branch in the deny-list. The mandatory `pre_commit_head_assertion` (#2924) forbids self-recovery via `git update-ref` to rewind a protected branch.
- **Resolution:** Halted before doing anything destructive, surfaced the issue to the orchestrator, and received explicit instruction to accept `179de393` on `develop` as the correct Task 2 deliverable (content, message, location all valid — develop is where the commit would end up after a clean worktree merge-back anyway). Tasks 3-5 then proceeded on `develop` directly with the same guardrails (absolute paths into the main checkout; no `cd` prefixes; trust git-status between commits to detect Plan 01's concurrent commits).
- **Files modified:** None (process-level recovery; no code changed).
- **Commit:** N/A (Task 2's commit `179de393` retroactively serves as the deliverable).
