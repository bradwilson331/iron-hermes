```rust
        // Phase 36.3.7.1 BUG-36.3.7.1-01: circuit breaker on reclaim-stale-claims path.
        // The bump above set consecutive_failures += 1; check the limit on the same
        // tick to match operator semantics (D-12 clarified by 36.3.7.0-03). The run_id
        // sentinel "reclaimed-no-run" is used when no current run is associated.

```

at this point (vs owned `Run` at line 305), and (2) the comment marker reads

## Latent Finding — Missing `KanbanEventKind::Reclaimed` Event (OUT OF SCOPE)

The doc comment at `dispatcher.rs:19` reads (paraphrased): `reclaim_stale_claims`
should "append `reclaimed` event". The implementation at lines 437-441 emits only
a `tracing::info!(event = "reclaimed", ...)` — there is NO
`store.append_event(KanbanEventKind::Reclaimed)` call. The doc and the code disagree.

This is a real **bilateral-tracing finding** (intent vs implementation) but it is
INDEPENDENT of the breaker wiring this plan delivered. Justification for deferring:

1. `apply_circuit_breaker` (lines 996-1056) is state-driven — it re-reads
   `consecutive_failures` from the tasks row and only writes the `gave_up` event +
   blocks the task. It does NOT require the `reclaimed` event to be appended first.
2. Plan 01's no-trip test verifies this independence: the test asserts NO `gave_up`
   event when `consecutive_failures < failure_limit`, and the task transitions
   `running → ready` correctly even though no `reclaimed` event was appended.
3. Adding the event in this plan would expand the diff beyond the locked scope-fence
   (`<scope_fence_reminders>` § "DO NOT add a `KanbanEventKind::Reclaimed` event
   append in `reclaim_stale_claims`") and break the bounded ~6-LOC insertion target.

**Recommended follow-up:** a separate "dispatcher events parity" phase that:
- Adds the missing `Reclaimed` event append in `reclaim_stale_claims` after line 441.
- Audits the other dispatcher steps (`extend_live_pid_claims`, `enforce_max_runtime`,
  `claim_and_spawn`, `promote_ready`) for similarly missing event appends.
- Updates `KanbanEventKind` if a new variant is needed.
- Updates the dispatcher's tracing assertion test (or adds one) to receiver-verify
  every doc-comment-promised event appends correctly.

Cite this SUMMARY § "Latent Finding — Missing `KanbanEventKind::Reclaimed` Event"
as the discovery point.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] First-run test failure — no-trip test exercised wrong producer**

- **Found during:** Task 3 GREEN phase (first full-suite run of the 2 new tests).
- **Issue:** The original test seed (dead non-null PID + expired claim) caused
  `detect_crashed_workers` (Step 1) to catch the task first and trip ITS OWN breaker
  at dispatcher.rs:305 — masking the new line-481 reclaim-path breaker. The trip
  test still passed (because the same outcome was produced) but was producer-misattributed.
  The no-trip test failed outright: a `crashed` event was appended by Step 1, but the
  test's defensive assertion expected NO `crashed` event on the reclaim path. The
  silent mismatch invalidated the trip test's bilateral-tracing for BUG-36.3.7.1-01
  even though it passed.
- **Root cause:** `detect_crashed_workers`'s filter (dispatcher.rs:247) is
  `Some(pid) = run.claim_pid else { continue };` — it skips ONLY when `claim_pid` is
  None. Any task seeded with a dead non-null PID is caught by Step 1 first,
  regardless of whether `claim_expires` is expired.
- **Fix:** After `seed_running`, NULL out `claim_pid` via inline SQL
  `"UPDATE task_runs SET claim_pid = NULL WHERE id = ?1"`. Step 1's filter then
  skips the task, leaving Step 3's `reclaim_stale_claims` as the only path that can
  bump `consecutive_failures` and tip the limit. The reclaim path treats null PID
  as `pid_is_alive == false` (dispatcher.rs:427-431), so the branch fires. The
  plan's `error_msg = "claim TTL expired with dead or null PID"` explicitly names
  this null-PID case, validating the seed change as plan-faithful.
- **Files modified:** `crates/ironhermes-kanban/tests/dispatcher_logic.rs`
- **Commit:** `2ef16004` (Task 3 commit incorporates the fix from the start — no
  separate fixup commit was authored).
- **Why not a helper:** The plan's scope_fence "DO NOT introduce new test helpers"
  precludes a `seed_running_null_pid(...)` helper. The inline SQL adjustment
  mirrors the existing `scheduled_at = now + 3600.0` workaround at
  `circuit_breaker_does_not_trip_below_limit_on_crashed_path` (lines 608-617) and
  introduces no new test surface.
