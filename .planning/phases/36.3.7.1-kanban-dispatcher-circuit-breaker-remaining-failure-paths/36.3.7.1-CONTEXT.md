<domain>
## Phase Boundary

This is a two-site source fix + receiver-end tests covering both new paths. The structural pattern was already established by Phase 36.3.7.0 Plan 03 BUG-36.3.7-03: every dispatcher step that bumps `consecutive_failures` MUST invoke `apply_circuit_breaker` on the same tick — otherwise the breaker fires one tick late (or never, if no subsequent spawn-failure happens).

Phase 36.3.7.0 closed the `detect_crashed_workers` site (line 305 — committed). The two remaining sites identified in `36.3.7.0-03-D12-DETERMINATION.md` §2 are:

- **`reclaim_stale_claims`** at `crates/ironhermes-kanban/src/dispatcher.rs:465` (bump) — currently has NO breaker call. Bug shape identical to BUG-36.3.7-03 on a different path.
- **`enforce_max_runtime`** at `crates/ironhermes-kanban/src/dispatcher.rs:561` (bump) — currently has NO breaker call. Same shape.

The canonical "bump → event → breaker" call pattern is at `dispatcher.rs:276-306` (the line 305 site fixed by 36.3.7.0-03):

```rust
// Increment consecutive_failures.
{
    let store = ctx.store.lock().await;
    store.conn.execute(
        "UPDATE tasks SET consecutive_failures = consecutive_failures + 1 WHERE id=?1",
        params![task.id],
    )?;
}

// Append crashed event.
{ … store.append_event(&task.id, Some(&run.id), KanbanEventKind::Crashed, …)?; }

// Phase 36.3.7.0 BUG-36.3.7-03: circuit breaker on crashed-detection path.
{
    let error_msg = format!("worker process crashed (pid={pid})");
    apply_circuit_breaker(ctx, &task, &run.id, &error_msg, now).await?;
}
```

`apply_circuit_breaker` itself (lines 972-1035) is purely state-driven — it re-reads `consecutive_failures` from the row, computes `effective_limit` (per-task `max_retries` or fallback to `config.failure_limit`), and on `>= effective_limit` blocks the task + appends a `GaveUp` event. It does NOT depend on the bump-site having appended its own event first; the breaker check is independent.

This means both new sites can call the breaker with their existing local context (`task`, `run.id`, an `error_msg` synthesized from the local failure facts) WITHOUT requiring upstream event-append parity.

In scope:
- BUG-36.3.7.1-01 — wire `apply_circuit_breaker` into `reclaim_stale_claims` at dispatcher.rs ~line 469 (immediately after the `consecutive_failures += 1` bump block ends, BEFORE the `for` loop's closing brace), passing `&task`, the `run.id` if a run exists OR a sentinel `"reclaimed-no-run"` string if there is no run (the function tolerates `run: Option<Run>`), `error_msg = format!("claim TTL expired with dead or null PID")`, and `now`.
- BUG-36.3.7.1-02 — wire `apply_circuit_breaker` into `enforce_max_runtime` at dispatcher.rs ~line 581 (immediately AFTER the `TimedOut` event append block closes, BEFORE the `for` loop's closing brace), mirroring the canonical bump → event → breaker order from the line 305 site. Pass `&task`, `&run.id` (always available — `run` is unwrapped earlier in the function), `error_msg = format!("max runtime exceeded ({elapsed}s > {max_runtime}s limit, sigkill={sigkill})")`, and `now`.
- BUG-36.3.7.1-03 — 4 receiver-end tests in `crates/ironhermes-kanban/src/dispatcher_logic.rs` (or a sibling test file mirroring whatever 36.3.7.0-03 chose for its tests): 2 paths (reclaim + enforce_max_runtime) × 2 sides of the `failure_limit` bound (one test where the bump pushes `consecutive_failures` to `failure_limit` and asserts the breaker fires; one test where the bump pushes it to `failure_limit - 1` and asserts it does NOT fire). Failure messages must name the offending path so future regressions are immediately greppable.

Out of scope:
- The missing `KanbanEventKind::Reclaimed` event in `reclaim_stale_claims` (the doc comment at dispatcher.rs:19 says "append `reclaimed` event" but the implementation only emits `tracing::info!(event = "reclaimed", ...)` — there is no `store.append_event(Reclaimed)` call). This is a bilateral-tracing finding (intent vs implementation) but it is INDEPENDENT of the breaker wiring — `apply_circuit_breaker` does not depend on the event being present. Document the finding in SUMMARY; do NOT silently fix it in this phase. If the receiver-end tests turn out to depend on the event being present (e.g., a future eventsource-replay test), that is a separate follow-up.
- Any change to `apply_circuit_breaker`'s signature, body, or `>=` comparison.
- Any change to `detect_crashed_workers` or `claim_and_spawn` — the 36.3.7.0-03 wiring at lines 305 and 899 is the canonical reference and must remain untouched.
- Any change to the `KanbanEventKind` enum, the events table schema, or the events.rs file.
- Any change to the dispatcher tick loop (`dispatch_once`) — the per-step ordering is fine.
- Any new dispatcher steps, new task statuses, new failure causes.
- Any change to `kanban.failure_limit` config defaults or the per-task `max_retries` field.
- Any test outside the receiver-end coverage of the two new paths.

<locked_decisions>
## Locked Decisions

### Mirror the canonical line 305 pattern

**Decision:** Both new breaker call sites MUST use the same call shape as the canonical line 305 site:

```rust
{
    let error_msg = format!("…path-specific cause string…");
    apply_circuit_breaker(ctx, &task, &run.id, &error_msg, now).await?;
}
```

The `&run.id` argument differs by site:
- `reclaim_stale_claims`: `run` is `Option<Run>` at the call point. Use `run.as_ref().map(|r| r.id.as_str()).unwrap_or("reclaimed-no-run")`. Document the sentinel in the inline comment.
- `enforce_max_runtime`: `run` is already unwrapped (line 514: `let Some(run) = run else { continue };`) — use `&run.id` directly.

The `error_msg` strings are NEW prose, not borrowed from existing tracing messages — they will appear in the persisted `gave_up` event's `error` field, so they must be self-contained (no caller-side context required to interpret).

**Rejected alternative:** Centralizing the bump + event + breaker into a single `record_failure_and_check_breaker(...)` helper. This would be cleaner but is OUT OF SCOPE — Phase 36.3.7.0-03 deliberately left the bump+event+breaker call sites duplicated (3 sites at most), and the determination doc explicitly cites "mirror the same breaker call into those two sites" as the intended shape. A helper refactor belongs to a separate cleanup phase, not 36.3.7.1.

### Inline-comment marker for greppable provenance

**Decision:** Each new breaker call MUST be prefixed by a single-line comment of the shape:
```rust
// Phase 36.3.7.1 BUG-36.3.7.1-01: circuit breaker on reclaim-stale-claims path.
```
and
```rust
// Phase 36.3.7.1 BUG-36.3.7.1-02: circuit breaker on max-runtime-exceeded path.
```

This mirrors the comment style used at dispatcher.rs:300 (the 36.3.7.0-03 site). Greppable for future bilateral-tracing audits — anyone looking for "which paths invoke the breaker" can grep `apply_circuit_breaker\(` and see the path provenance in the comment above.

### Receiver-end test placement + shape

**Decision:** Tests live in the same file/module that 36.3.7.0-03 used for its `detect_crashed_workers` breaker test (verify during planning: planner reads the 36.3.7.0-03 SUMMARY + finds the test path, then either co-locates or creates a sibling test file with matching naming convention `breaker_<path>_<boundary>.rs` or `breaker_in_<path>.rs`).

Each test MUST:
1. Build an in-memory `DispatcherContext` with `config.failure_limit = 2` (or whatever the canonical 36.3.7.0-03 test fixture uses — match it exactly).
2. Seed a task with `consecutive_failures` pre-set to `failure_limit - 1` (so one bump tips the breaker) OR `failure_limit - 2` (so one bump leaves headroom).
3. Drive the dispatcher step under test (`reclaim_stale_claims` or `enforce_max_runtime`) one tick.
4. Assert the task's terminal state: `blocked` with reason matching the path-specific `error_msg` substring (for the at-limit case) OR `ready` with `consecutive_failures += 1` and NO `gave_up` event (for the below-limit case).
5. Failure message MUST name the path and the boundary, e.g., `"reclaim_stale_claims path: breaker did not fire at failure_limit (BUG-36.3.7.1-01)"`.

If 36.3.7.0-03's tests live in a non-`tests/` source-module (`dispatcher_logic.rs` or similar), match that placement — do NOT introduce a new test surface convention.

### Scope-fence enforcement

**Decision:** A static-grep at planning time MUST confirm zero unintended changes:
- `git diff crates/ironhermes-kanban/src/dispatcher.rs` after the source edits MUST show ONLY:
  - The two new `apply_circuit_breaker` call blocks (one per site)
  - The two inline-comment markers
- ANY other diff line in `dispatcher.rs` is a deviation — surface immediately, do not silently expand.

<notes>
## Notes

- This phase exists because Phase 36.3.7.0 Plan 03 D-12 determination doc explicitly named these two sites as the deferred follow-up. The fix shape is mechanical; the value is in (a) eliminating the breaker-fires-late behavior on these two paths and (b) locking the bilateral pattern via the receiver-end tests so future dispatcher additions follow the canonical bump → event → breaker order.
- The mechanical surface is small (~2 × 6 LOC source edits + 4 tests). Plans should be tightly scoped — no exploration, no "consider whether to..." language. Same playbook as 36.3.7.0 + 36.3.7.2.
- Bilateral-tracing meta-rule directly applies: the producer is the breaker call, the consumer is the gave_up event landing in the task row's blocked-reason field. Tests assert BOTH ends.
- A latent finding from this scoping pass: `reclaim_stale_claims` claims (in dispatcher.rs:19 doc comment) to "append `reclaimed` event" but only emits `tracing::info!(event = "reclaimed", ...)` — there is no `store.append_event(KanbanEventKind::Reclaimed)` call. The doc and the code disagree. This is a real bug but it is OUT OF SCOPE for 36.3.7.1 because (a) apply_circuit_breaker doesn't depend on it, (b) widening scope dilutes the breaker-wiring focus, and (c) the right fix is a separate "dispatcher events parity" phase. SUMMARY must cite this finding so it doesn't get lost.
- Planner should produce 2 plans (one per path) in a single wave (parallel-eligible, different functions in the same file — handle as separate worktrees to avoid merge conflicts on dispatcher.rs, OR collapse into a single plan if the planner judges the two edits to be too tightly co-located for parallel worktrees). Default recommendation: 2 plans, 1 wave, parallel — same shape as 36.3.7.2.

</notes>
