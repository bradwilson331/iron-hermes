## Web audio transport (D-02)

### Q1: How should the server hand audio bytes to the browser?

| Option | Description | Selected |
|--------|-------------|----------|
| Binary WS frame on ChatStreamEvent | New typed variant `ChatStreamEvent::AudioOut { mime, bytes }`. Server emits a binary frame; wasm UI wraps as Blob → URL.createObjectURL → `<audio>`. Reuses 36.17.4 ws plumbing. No new HTTP route. | ✓ |
| HTTP GET /audio/:id route | Server writes mp3 to audio_cache, returns id in event stream, browser fetches. Adds GC, cleanup, CORS, second auth surface. | |
| Base64 in existing JSON event stream | Encode mp3 bytes as base64 in a text variant. 3× bandwidth, blocks streaming, breaks 36.17.4 typed-event contract. | |
| You decide | Claude picks. | |

**User's choice:** Binary WS frame on ChatStreamEvent.

### Q2: How should the audio actually play in the browser?

| Option | Description | Selected |
|--------|-------------|----------|
| Render a play button per audio, no autoplay | Each audio output gets an inline `<audio controls>` in the transcript. Safe under every browser autoplay policy. | ✓ |
| Attempt autoplay, fall back to play button on rejection | Try `.play()`; on promise reject, show play button. Inconsistent across browsers. | |
| Auto-play after one sticky page-level gesture | First user gesture unlocks autoplay for the rest of the session. Cleaner for podcasts; adds page state. | |
| You decide | Claude picks. | |

**User's choice:** Per-audio inline play button, no autoplay.

### Q3: What's the audio's lifetime in the browser?

| Option | Description | Selected |
|--------|-------------|----------|
| Ephemeral in-memory only | Blob URL only; survives scroll, dies on reload. No server cache, no GC. | |
| Persisted to $IRONHERMES_HOME/audio_cache, replayable after reload | Server writes mp3 to audio_cache; browser keeps reference; on reload, replay endpoint serves the same audio. Adds GC + cleanup. | ✓ |
| Ephemeral + keep-last debug file | In-memory for the browser; server also writes `last.mp3` for operator debugging. | |
| You decide | Claude picks. | |

**User's choice:** Persisted to `$IRONHERMES_HOME/audio_cache/{uuid}.mp3`, replayable after reload.
**Notes:** Implementation reconciliation: server writes the file AND sends the binary WS frame for instant first-play; on page reload the transcript-history returns the uuid and the browser falls back to `<audio src="/audio/:uuid">` served by a new HTTP route inside iron_hermes_ui.

### Q4: How long do persisted audio files live before GC?

| Option | Description | Selected |
|--------|-------------|----------|
| Bounded by total size, LRU-evict | Cap audio_cache at e.g. 500 MB; evict oldest by mtime. Predictable bound. | |
| Time-based: delete files older than N days | Files older than e.g. 7 days pruned on server startup + periodic sweep. | ✓ |
| Never auto-prune | Operator runs `hermes tts cache clean` manually. | |
| You decide | Claude picks. | |

**User's choice:** Time-based, files older than `audio_cache.max_age_days` (default 7) deleted.
**Notes:** Pruned on startup + periodic sweep; sweep cadence is planner discretion.
