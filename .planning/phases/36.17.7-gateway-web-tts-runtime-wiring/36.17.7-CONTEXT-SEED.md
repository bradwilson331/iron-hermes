# Phase 36.17.7 — CONTEXT seed

> **Status:** SEED. This file is the discussion-phase pre-read — convert it to a locked `36.17.7-CONTEXT.md` by running `/gsd:discuss-phase 36.17.7`. Decisions below are starting points, not yet binding.

## Why this phase exists

After Phase 36.17.6 verifier PASSED 9/9, the operator tested the agent live and asked it to summarize Hacker News stories as a podcast hosted by a female voice. The agent **did not** use the IronHermes-native `text_to_speech` / `send_audio` tools — it fell through to the `hyperframes-media` skill (Kokoro Python), then to macOS `say`. The trace was captured in the conversation that closed 36.17.6.

### Root cause (file:line evidence)

**Two facts together explain the silent fallback:**

1. **The guard in `app_runtime_factory.rs:97-103`:**
   ```rust
   if let Some(ref session_key) = input.session_key {
       registry.register_tts_tools(
           session_key.clone(),
           input.telegram_adapter.clone(),
           input.config.clone(),
       );
   }
   ```
   `register_tts_tools` is only called when `input.session_key` is `Some(...)`.

2. **`agent_runtime.rs:215-217` hard-codes `None`:**
   ```rust
   // Phase 36.17.5 D-15: per-turn threading deferred to a follow-up phase.
   // v1 ships the infrastructure; TTS tools activate when session_key is Some.
   session_key: None,
   telegram_adapter: None,
   ```

   `AgentRuntime::from_config` — the constructor used by `run_gateway` (`crates/ironhermes-cli/src/main.rs:3071-3084`) and (by the same pattern) by the iron_hermes_ui web server's runtime construction — therefore never activates TTS for live runtime sessions.

3. **Phase 36.17.6's scope was the CLI inspection path** (`cmd_toolset_list` / `cmd_toolset_show` calling a sentinel-keyed `register_tts_for_inspection` helper). That made the `voice` row visible in `toolset list` (✓ tools, but `disabled` toolset status) but did NOT change `from_config` or any other live-session constructor.

So: the registry exposes the tools to the **inspection** view, but they are absent from the **runtime** registry that the LLM tool-schema list is built from.

### What the agent saw instead

The agent's `toolset list` row shows `voice  disabled  2  2/2 (text_to_speech ✓, send_audio ✓)`. The `✓` is the prereq check (Edge TTS reachable, no API key needed); the `disabled` is the toolset-level enablement state. The LLM never receives a tool schema for `text_to_speech` because the runtime registry doesn't contain it — the tools are registered into the **inspection** registry, which is a separate `ToolRegistry::new()` built inside `cmd_toolset_*` and never read by the agent loop.

## Surfaces in scope

### A) Gateway runtime (Telegram first; Discord/Slack deferred)
- Entry: `crates/ironhermes-cli/src/main.rs::run_gateway` → `AgentRuntime::from_config(...)`.
- The `TelegramAdapter` already implements `ironhermes_tools::AudioDispatcher` (Phase 36.17.5 Plan 03). Wiring it through to `AppRuntimeFactoryInput::telegram_adapter` is the gateway's deliverable.

### B) iron_hermes_ui web runtime (HermesApp / web ws handler)
- Entry: `crates/iron_hermes_ui/src/server/...` — wherever the per-WS-session `AgentRuntime` is constructed (likely `from_config` or a sibling that takes `AppRuntimeFactoryInput`).
- **No existing `WebAudioDispatcher`** — must be built. The simplest correct design is a binary WS frame on the existing `ChatStreamEvent` channel, played in the browser via `new Audio(URL.createObjectURL(blob))`.
- Per memory note `project_warp_vs_hermes_app_active_root`: target HermesApp (active root), NOT WarpHermes (`legacy-shell` opt-in).
- Per memory note `project_arch_embedded_agent`: the agent runs embedded in the UI server — no separate gateway/agent process.
- Per memory note `feedback_css_tokens_unconditional_load`: any UI control surface for audio playback must use the unconditional CSS tokens.

## Decisions sketch (locked at discuss-phase)

### D-01 — Where to thread `session_key`
**Default:** Per-turn `AppRuntimeFactoryInput` bundle built fresh inside the gateway handler / web ws handler before each `run_turn`. Old bundle dropped when turn completes.
**Rationale:** Matches 36.17.5 D-15 comment ("tools are tied to the agent loop, not the runtime"). Avoids mutating the long-lived `AgentRuntime` registry mid-flight.
**Alternative considered:** Add `AgentRuntime::register_tts_for_session(session_key, adapter)` that mutates the shared registry. Rejected because (a) registry is `Arc<RwLock<ToolRegistry>>` and write-locking it per-turn fights ws backpressure, (b) it gives every concurrent session the same tools, which is wrong for the audio-dispatcher injection.

### D-02 — `WebAudioDispatcher` transport
**Default:** New `ChatStreamEvent::AudioOut { mime: String, bytes: Vec<u8> }` typed variant. WS layer encodes as a binary frame (or chunked base64 if forced to JSON). Wasm UI on receipt: `Blob` → `URL.createObjectURL` → `<audio>` element → `.play()` from a user-gestured "Play voice" button (autoplay would be policy-blocked).
**Rationale:** Reuses the existing event channel. Bounded by the existing 128-message queue cap from 36.17.4.
**Alternatives rejected:**
- Writing to `~/.ironhermes/audio_cache/*.mp3` and serving via a new `GET /audio/:id` Axum route — adds cross-origin / cleanup / GC concerns the cache dir has no machinery for today.
- Base64-encoding inside the existing JSON event stream — 3× bandwidth, blocks streaming, and clashes with the 36.17.4 D-03 typed-event contract.

### D-03 — Discord / Slack adapters
**Default:** Out of scope for this phase. Ship Telegram + Web only. Discord voice channels are a large surface (voice gateway, opus encoding, mixer); Slack `files.upload` is small enough to fold in but bundling it dilutes the phase. Queue Discord + Slack as a separate phase, mirroring the 36.17.5 deferral pattern.

### D-04 — Per-session `SessionKey` lifetime
**Default:** Constructed at the start of every `run_turn`, threaded once into `AppRuntimeFactoryInput`, owned by the per-turn bundle, dropped when the turn completes. The same pattern `run_gateway` already uses for `RegistryToolsetSession` (`crates/ironhermes-cli/src/main.rs:3107-3114`).

### D-05 — Invariant test (locking the wiring)
**Default:** Add `crates/ironhermes-agent/tests/invariants_36_17_7.rs` (parallel to `invariants_36_17_5.rs`) with:
1. **Negative-of-deferral test:** `from_config` source no longer contains the literal `session_key: None,` (or the new constructor it's replaced with contains `session_key: Some(`).
2. **Gateway-path test:** integration test or source-grep asserting `run_gateway` builds an `AppRuntimeFactoryInput` with `session_key: Some(...)` and `telegram_adapter: Some(...)` per turn.
3. **Web-path test:** same for the iron_hermes_ui ws handler's runtime constructor.

### D-06 — Toolset enablement-vs-registration semantics
**Open question (decide at discuss-phase):** today `toolset list` shows `voice  disabled` because `disabled` is the slug-level enablement state (config `tools.toolsets.voice = false` or absent), independent of whether `register_tts_tools` ran for the active session. Options:
- **D-06a** — flip default `tools.toolsets.voice = true` in config-loading (changes user-visible defaults).
- **D-06b** — keep slug disabled by default; add a per-session "registered: yes" indicator to inspection output so the operator can distinguish "tool exists in registry" from "toolset enabled in config".
- **D-06c** — auto-enable when the user runs `/toolset enable voice` AND the agent runtime sees `session_key: Some(...)` (config side stays manual).

Recommend D-06b — least surprising, surfaces the runtime/inspection split that 36.17.6 created.

## Wave/plan shape (rough)

- **Wave 1 (parallel):** (a) thread `session_key` + `telegram_adapter` through the gateway handler / `run_gateway`. (b) Build `WebAudioDispatcher` impl in `iron_hermes_ui::server`.
- **Wave 2:** wire the new web dispatcher into iron_hermes_ui's per-session runtime construction.
- **Wave 3:** D-05 invariant test + a Telegram + Web operator UAT (mirrors 36.17.5 / 36.17.6 UAT pattern).
- **Wave 4 (close):** flip enablement-vs-registration per D-06 + ROADMAP completion.
