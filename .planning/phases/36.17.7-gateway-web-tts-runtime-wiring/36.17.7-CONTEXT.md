# Phase 36.17.7: Gateway + web + TUI runtime TTS wiring - Context

**Gathered:** 2026-06-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the runtime-side gap that 36.17.5 deferred (D-15) and 36.17.6 documented: `register_tts_tools` is guarded by `if let Some(ref session_key) = input.session_key` in `crates/ironhermes-agent/src/app_runtime_factory.rs:97-103`, and `AgentRuntime::from_config` — called by `run_gateway` and by the iron_hermes_ui web server and by the ratatui TUI — currently hard-codes `session_key: None, telegram_adapter: None` at `crates/ironhermes-agent/src/agent_runtime.rs:215-217`. Live agent sessions on Telegram, Web, and TUI therefore have `text_to_speech` + `send_audio` REGISTERED in `ironhermes-tools` but NEVER exposed to the LLM tool-schema list, so the agent silently falls through to `hyperframes-media` or `say`.

This phase threads a real per-session `SessionKey` and the platform-appropriate `AudioDispatcher` into the per-turn factory bundle on all three supported surfaces so the two TTS tools actually appear in the agent's tool list for every turn — and builds the missing `WebAudioDispatcher` for iron_hermes_ui.

**Surfaces in scope:** (a) Gateway → Telegram only (reuses existing `impl AudioDispatcher for TelegramAdapter`); (b) iron_hermes_ui web (new `WebAudioDispatcher` impl required); (c) ratatui TUI (`tui_rata`, reuses `Platform::Local` + existing `rodio` dispatcher from 36.17.5 Plan 03).

**Out of scope:** Discord (voice gateway) and Slack (`files.upload` audio) — explicitly deferred per D-03 below; new TTS providers; streaming/chunked synthesis; STT/push-to-talk; voice-mode (auto-speak Path A). The first three were deferred from 36.17.5 and stay deferred.

</domain>

<decisions>
## Implementation Decisions

### Wiring strategy (D-01)
- **D-01:** Per-turn `AppRuntimeFactoryInput` bundle, rebuilt per `run_turn`. Gateway/web/TUI handlers each build a fresh `AppRuntimeFactoryInput { session_key: Some(...), telegram_adapter | web_adapter | local_adapter: Some(...) }` at the start of every `run_turn`, call `build_app_runtime_bundle`, drop when the turn completes. Matches the 36.17.5 D-15 comment ("tools are tied to the agent loop, not the runtime") and mirrors the existing `RegistryToolsetSession` per-session pattern in `run_gateway` (`crates/ironhermes-cli/src/main.rs:3107-3114`).

### Web audio transport (D-02)
- **D-02-a (transport):** New typed variant `ChatStreamEvent::AudioOut { mime: String, uuid: String, bytes: Vec<u8> }`. WS layer encodes as a binary frame on the existing ChatStreamEvent channel (no new ws subprotocol; reuses 36.17.4's typed-event contract). The wasm UI wraps the bytes as a Blob, creates a `URL.createObjectURL`, and attaches it to an `<audio>` element. **Rejected:** HTTP `GET /audio/:id` route as the first-play path (adds cross-origin/cleanup/CORS); base64-in-JSON (3× bandwidth, blocks streaming).
- **D-02-b (playback gesture):** Per-audio inline play button, no programmatic autoplay attempt. Safe under every browser autoplay policy. The play button is a normal HTML `<audio controls>` (or equivalent React control), no "click anywhere to unlock" page-level state.
- **D-02-c (lifetime):** Synthesized audio is persisted to `$IRONHERMES_HOME/audio_cache/{uuid}.mp3` (same dir + naming convention 36.17.5 already uses for CLI playback). The binary WS frame still carries the bytes for instant first-play. On page reload, the transcript-history endpoint returns the uuid in the event payload and the browser falls back to `<audio src="/audio/:uuid">` served by a new authenticated HTTP route inside the iron_hermes_ui server.
- **D-02-d (GC):** Time-based pruning. Files older than `audio_cache.max_age_days` (default 7) are deleted on server startup AND on a periodic sweep (cadence is a planner decision; recommend ≥ daily). New config keys `audio_cache.max_age_days: u32` (default 7) and `audio_cache.sweep_interval_secs: u64` (default 86400) under the existing `tools:` or a new `audio_cache:` section — planner picks the home that fits the existing config schema.
- **D-02-e (format):** Raw mp3 from Edge TTS, no ffmpeg conversion. Modern browsers play mp3 natively in `<audio>`. Skipping ogg/opus re-encode keeps the dispatcher trivial and removes the ffmpeg-required runtime branch. (The Telegram dispatcher still does its existing ogg/opus voice conversion per 36.17.5 D-14 — that's unchanged.)
- **D-02-f (ordering):** One inline `<audio>` control per `send_audio` call, dropped into the chat transcript at the exact stream position of the emit. Multiple emits in a single turn produce multiple inline controls in order, matching the streaming text contract. **Rejected:** end-of-turn coalesced playlist (loses the streaming feel); per-emit + end-of-turn "play all" (overkill for v1).

### Discord & Slack scope (D-03)
- **D-03 (scope):** Defer both. 36.17.7 ships Telegram + Web + TUI only. Discord (voice channel join, opus encoding, mixer) is a large surface; Slack (`files.upload`) is small but bundling dilutes phase focus. Both go to a follow-up phase, mirroring the 36.17.5 deferral pattern.
- **D-03-b (deferred-platform UX):** Tools are STILL registered for Discord/Slack sessions (so the LLM tool-schema list is consistent across platforms), but the platform's `AudioDispatcher` impl returns a clean `Err("audio dispatch not supported on <platform>")` from `send_audio`. The agent reads that and can narrate "I synthesized audio but can't deliver it on this platform." `text_to_speech` itself still synthesizes the file (useful for debugging via the on-disk audio_cache). **Implementation hint:** add a `NotSupportedAudioDispatcher` zero-impl wrapper in `ironhermes-tools` for Discord/Slack to mount; deletion happens when Discord/Slack get real impls.

### Enablement vs registration semantics (D-06)
- **D-06:** Add a per-session "registered" indicator alongside `enabled`/`disabled` in `toolset list` / `toolset show voice`. Concrete column shape and labels are planner territory; the principle is: surface the split between (a) operator-toggled enablement from `config.tools.toolsets.<name>.enabled` and (b) whether `register_tts_tools` actually fired for the current session. **Rejected:** flip default `voice = true` at config-load (commits TTS on by default for everyone — out of scope user-policy change); auto-enable on `/toolset enable` (couples slash command + registration in ways that are harder to reason about). The "inspection" sentinel-key registration that 36.17.6 added stays — the new indicator distinguishes inspection-only from session-live.

### Invariant test (D-05)
- **D-05:** Strict triple source-grep guards in a new `crates/ironhermes-agent/tests/invariants_36_17_7.rs` (mirrors `invariants_36_17_5.rs` style). Three asserts:
  1. `AgentRuntime::from_config` source no longer contains the literal `session_key: None,` (the 36.17.5 D-15 deferral marker).
  2. The gateway handler (per-turn factory build site) source contains `session_key: Some(`.
  3. The iron_hermes_ui ws handler AND TUI handler (`tui_rata/event_loop.rs` or its replacement) source each contain `session_key: Some(`.
- A future-resistant variant: also grep `register_tts_tools(` call count in production source ≥ 4 (factory + 3 handler-level activations) to catch a comment-out regression.

### Claude's Discretion
- Audio-control visual design (button label, styling, accessibility affordances like `aria-label`, transcript layout) is UI design and belongs in `/gsd:ui-phase 36.17.7` (optional) or the executor agent's discretion based on existing iron_hermes_ui patterns.
- Exact GC sweep cadence (the `sweep_interval_secs` default) is planner discretion as long as it's bounded by `max_age_days`.
- Whether to use a single `AudioOut` ChatStreamEvent variant or split into `AudioOutStart { uuid, mime }` + `AudioOutBytes { uuid, bytes }` framing is a planner call — the user-facing contract from D-02 is "one inline control per emit", any framing that delivers that works.
- TUI affordance for triggering / observing playback is executor discretion — the user's TUI is on the same host as the rodio dispatcher, so playback just works; no new TUI widget required unless the executor wants a "🔊 played" indicator next to the relevant transcript line.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `AppRuntimeFactoryInput { session_key: Option<SessionKey>, telegram_adapter: Option<Arc<dyn AudioDispatcher>>, .. }` — fields already exist (Phase 36.17.5 Plan 03). 36.17.7 fills them per turn; does NOT change the struct shape.
- `build_app_runtime_bundle` — entry point that runs the guarded `register_tts_tools` call. Reused as-is.
- `TelegramAdapter::AudioDispatcher` impl — already shipped by 36.17.5 Plan 03. Gateway path needs to clone it into the per-turn factory input; no new dispatcher code for Telegram.
- `Platform::Local` + `rodio` playback — already shipped by 36.17.5 Plan 03 for `hermes tts play`. TUI reuses this directly with `session_key: Some(SessionKey { platform: Local, .. })`.
- `RegistryToolsetSession` per-session pattern in `run_gateway` — the lifetime model 36.17.7's per-turn bundle mirrors.
- `ChatStreamEvent` typed-event channel from 36.17.4 — extended with a new `AudioOut { mime, uuid, bytes }` variant; no new ws subprotocol.

### Established Patterns
- **Per-session lifetime via per-turn factory rebuild** — 36.17.5 D-15 comment + 36.17.7 D-01 both lock this. Don't add singletons that mutate shared state mid-flight.
- **Typed external-tagged JSON variants for ws events** — 36.17.4 D-03 / D-11. New variants go through the same channel.
- **Tools registered in inspection registry separately from session registry** — established by 36.17.6 (sentinel key). 36.17.7 must NOT collapse these — the "registered" indicator (D-06) depends on them remaining distinct.
- **`#[serde(default)]` on `ToolsetEntry`** — keeps configs forward-compatible (empty `voice:` parses cleanly). New config keys for `audio_cache.*` follow the same pattern.

### Integration Points
- **Gateway path:** `run_gateway` → per-turn `AppRuntimeFactoryInput { session_key: Some(SessionKey { platform: Telegram, chat_id, user_id }), telegram_adapter: Some(telegram_adapter_arc) }` → `build_app_runtime_bundle` → `register_tts_tools` fires.
- **Web path:** iron_hermes_ui ws handler → per-turn `AppRuntimeFactoryInput { session_key: Some(SessionKey { platform: Web, chat_id: session_id, user_id: Some("web") }), web_adapter: Some(WebAudioDispatcher::new(ws_tx, audio_cache_dir)) }` → same factory call. **New struct field required:** add `web_adapter: Option<Arc<dyn AudioDispatcher>>` to `AppRuntimeFactoryInput` (mirrors `telegram_adapter`), OR collapse to a single `audio_dispatcher: Option<Arc<dyn AudioDispatcher>>` per session — planner picks the cleaner shape.
- **TUI path:** `tui_rata/event_loop.rs` → per-turn `AppRuntimeFactoryInput { session_key: Some(SessionKey { platform: Local, .. }), local_adapter: existing rodio dispatcher }` → factory call. May reuse the existing `rodio`-backed dispatcher used by `hermes tts play`.
- **Deferred-platform path:** Discord/Slack ws/event handler → per-turn input with `session_key: Some(...)` + `audio_dispatcher: Some(Arc::new(NotSupportedAudioDispatcher::new("discord")))` → tools still register; `send_audio` returns the unsupported `Err`.

<specifics>
## Specific Ideas

- The audio file naming scheme uses uuids, matching 36.17.5's existing `audio_cache/{uuid}.mp3` convention (see 36.17.5 Plan 04 SUMMARY's UAT transcript). New files in this phase don't introduce a different convention.
- The HTTP replay route (D-02-c) lives inside the iron_hermes_ui axum router (NOT a new top-level server). It uses the same auth/session middleware iron_hermes_ui already applies to its other endpoints. Planner determines the exact route shape — recommend `GET /audio/:uuid` returning the bytes with `Content-Type: audio/mpeg`.
- A live operator UAT mirroring 36.17.5 Gate 5 is the canonical proof-of-life:
  - **UAT-T** (Telegram): operator sends a message that triggers `text_to_speech` + `send_audio` → expects voice message in Telegram chat.
  - **UAT-W** (Web): operator opens iron_hermes_ui, asks the agent the same → expects an inline audio control in the transcript with audible playback.
  - **UAT-TUI** (TUI): operator runs the TUI, asks the same → expects audible rodio playback on the host.
  - **UAT-R** (Web reload-replay): after UAT-W, refresh the browser, expand the message → audio plays back from the GET /audio/:uuid route.
- The user's HN-podcast-style request that surfaced this gap is the unofficial "real" UAT — once 36.17.7 lands, re-running it should produce the audio inline in the chat (Web) or as voice messages (Telegram), not via `say` fallback.

</specifics>
