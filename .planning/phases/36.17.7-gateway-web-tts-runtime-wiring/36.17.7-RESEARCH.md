## Summary

Phase 36.17.7 closes the runtime gap identified in 36.17.5 D-15: `AgentRuntime::from_config` hard-codes `session_key: None, telegram_adapter: None` at `crates/ironhermes-agent/src/agent_runtime.rs:215-217`, so `register_tts_tools` inside `build_app_runtime_bundle` never fires for live sessions. The fix is to stop constructing `AgentRuntime` with a static single bundle and instead pass a real `AppRuntimeFactoryInput` per-turn (or augment the existing per-turn path).

The architecture research reveals a critical structural challenge: `AgentRuntime::from_config` builds the `AppRuntimeBundle` (including the ToolRegistry) once at startup. The `run_turn` method reuses `self.bundle.registry`. To make TTS tools appear per-session, the planner must choose between: (A) adding a per-turn registry mutation path to `AgentRuntime::run_turn`, or (B) threading a second `AppRuntimeFactoryInput`-equivalent per-turn bundle alongside `TurnRequest`. The CONTEXT.md D-01 decision ("per-turn `AppRuntimeFactoryInput` bundle, rebuilt per `run_turn`") points strongly to option B — a new per-turn factory input that `run_turn` uses to (re)register TTS tools into the existing registry before the turn runs.

The three surfaces each need their `session_key` and dispatcher threaded into the per-turn input. Gateway has `Arc<TelegramAdapter>` available at `runner.rs:645` (process-lifetime singleton, safe to `Arc::clone` per turn). The web surface needs a new `WebAudioDispatcher` that writes a `ChatStreamEvent::AudioOut` variant to the per-turn `mpsc::UnboundedSender<ChatStreamEvent>` (the `tx` already used for Delta/Finished). The TUI surface already has `AgentRuntime` constructed at `event_loop.rs:464` — a per-turn input with `Platform::Local` and the rodio dispatcher from Plan 03 completes the wiring.

**Primary recommendation:** Add `audio_factory: Option<AppRuntimeFactoryInput>` (or a lightweight `AudioFactoryInput { session_key, audio_dispatcher }`) to `TurnRequest`, and have `run_turn` call `registry.register_tts_tools(...)` at the start of the turn when `audio_factory` is `Some`. This avoids rebuilding the full bundle per turn while satisfying D-01's per-turn semantics.

### Pattern 1: Per-Turn TTS Registration (D-01 implementation path)

The existing `TurnRequest` struct (in `agent_runtime.rs`) needs a new optional field for per-turn audio wiring. `AgentRuntime::run_turn` calls `register_tts_tools` on the shared registry at the start of the turn when this field is `Some`.

**Key insight from code reading:** `AgentRuntime` builds its `AppRuntimeBundle` (including `registry: Arc<RwLock<ToolRegistry>>`) once in `from_config`. The `run_turn` method reuses `self.bundle.registry`. The planner must decide whether to:

1. **Option A — Mutate registry per-turn:** Add to `TurnRequest`: `tts_wiring: Option<TtsPerTurnWiring>` where `TtsPerTurnWiring { session_key, audio_dispatcher }`. In `run_turn`, before the agent loop, call `self.bundle.registry.write().await.register_tts_tools(...)`. After the turn, optionally unregister (or just let subsequent turns overwrite — tools are idempotent-registered by name).

2. **Option B — Re-build bundle per-turn:** Have each callsite (gateway handler, ws.rs, event_loop.rs) call `build_app_runtime_bundle` with a full `AppRuntimeFactoryInput` per turn (matching D-01 literal wording). This is heavier: rebuilds all tool registries, MCP, browser sessions each turn.

**Recommendation: Option A** — The CONTEXT.md D-01 says "per-turn bundle rebuilt per `run_turn`" but the code reality is that `AgentRuntime` holds a single durable bundle. Option A achieves the same semantic (TTS tools registered per-turn with the correct session_key) without the enormous overhead of Option B. The planner should implement a lightweight `TtsPerTurnWiring` field on `TurnRequest`.

> ⚠ **Circular dependency issue (planner must resolve):** `WebAudioDispatcher` needs to send a `ChatStreamEvent::AudioOut` event. `ChatStreamEvent` lives in `iron_hermes_ui::protocol`. `ironhermes-tools` cannot import `iron_hermes_ui` (it would create a circular dep — tools → ui → tools). The planner has two options:
> 1. **Define an `AudioOutSender` trait** in `ironhermes-tools` with a single method `send_audio_out(mime, uuid, bytes) -> Result<()>`, and implement it in `iron_hermes_ui` as a wrapper around the `ChatStreamEvent` channel. `WebAudioDispatcher` holds an `Arc<dyn AudioOutSender>`.
> 2. **Use `Box<dyn Fn>` callback** — inject a closure `Box<dyn Fn(String, String, Vec<u8>) -> Result<()> + Send + Sync>` into `WebAudioDispatcher`. This avoids the trait.
> 3. **Move `WebAudioDispatcher` entirely into `iron_hermes_ui`** (not in `ironhermes-tools`). Implement `AudioDispatcher for WebAudioDispatcher` there — safe per orphan rules since both the trait (from `ironhermes-tools`) and the type (in `iron_hermes_ui`) can meet in `iron_hermes_ui`'s impl block, same as `TelegramAdapter` in `ironhermes-gateway`.
>
> **Recommended:** Option 3 — mirrors the exact pattern used for `TelegramAdapter` (trait in `ironhermes-tools`, impl in gateway crate). Place `WebAudioDispatcher` in `crates/iron_hermes_ui/src/server/web_audio_dispatcher.rs`, implement `ironhermes_tools::AudioDispatcher for WebAudioDispatcher`. No new crate, no circular dep.

### Pattern 3: ChatStreamEvent::AudioOut Encoding

**Current `ChatStreamEvent` enum** (`crates/iron_hermes_ui/src/protocol.rs:19-44`):
```rust
// Source: protocol.rs:19-44 — external tagging (no serde attributes on enum)
pub enum ChatStreamEvent {
    Delta { text: String },
    ToolCallStart { name: String, args: String },
    ToolCallEnd { name: String, success: bool },
    Finished { total_tokens: u32 },
    Error { message: String },
    SubagentEvent {},                              // {"SubagentEvent":{}}
    QueueUpdated { depth: u32, paused: bool },     // {"QueueUpdated":{"depth":3,"paused":false}}
}
```

**Wire encoding question for AudioOut:** D-02-a says "WS layer encodes as a binary frame". The existing `ws.rs` send path uses exclusively `Message::Text(json)` (confirmed: all `send_raw` calls use `Message::Text`). `Message::Binary` IS defined in `dioxus_fullstack::Message` (confirmed: `warp_hermes.rs:181`), but the server side never currently sends it.

**Option 1 — Full binary frame:** Serialize `ChatStreamEvent::AudioOut` as JSON to bytes, send as `Message::Binary(bytes)`. The WASM client receives `Message::Binary(b)` (handler already exists at `warp_hermes.rs:181`) and JSON-parses it as a `ChatStreamEvent`. No new protocol; audio bytes are embedded as base64 in the JSON.

**Option 2 — Custom binary framing:** Prefix bytes with a tag byte + length. Avoids base64 overhead but requires new client parsing logic.

**Option 3 — Text frame with base64 bytes:** Serialize `bytes: Vec<u8>` as `bytes: String` (base64). Send as `Message::Text`. No new client Binary arm. 3× bandwidth cost (CONTEXT.md D-02-a explicitly rejects this).

**Planner recommendation:** Option 1 for v1 simplicity. The base64 overhead on mp3 is ~33% size increase — for a typical 5-15 second TTS clip at 64kbps that is ~40-120 KB raw → ~53-160 KB base64. Acceptable for first-play. Alternative: send as truly binary (raw mp3 bytes after a JSON header frame `AudioOutStart { uuid, mime }` followed by `Message::Binary` payload). This is Option 2 and avoids base64. The CONTEXT discretion note says single vs split variant is a planner call.

// 1. Run startup sweep
gc_sweep_audio_cache(&audio_cache_dir, max_age_days);

let gc_cancel = CancellationToken::new();

```rust
fn gc_sweep_audio_cache(dir: &Path, max_age_days: u32) {
    let cutoff = std::time::SystemTime::now()
        - std::time::Duration::from_secs(max_age_days as u64 * 86400);
    match std::fs::read_dir(dir) {
        Ok(entries) => {
            for entry in entries.flatten() {
                if let Ok(meta) = entry.metadata() {
                    if let Ok(mtime) = meta.modified() {
                        if mtime < cutoff {
                            if let Err(e) = std::fs::remove_file(entry.path()) {
                                // NEVER panic — match existing tracing pattern
                                tracing::warn!(
                                    path = %entry.path().display(),
                                    error = %e,
                                    "audio_cache GC: failed to remove file"
                                );
                            }
                        }
                    }
                }
            }
        }
        Err(e) if e.kind() == std::io::ErrorKind::NotFound => {
            // audio_cache dir not yet created — no-op
        }
        Err(e) => {
            tracing::warn!(error = %e, "audio_cache GC: failed to read dir");
        }
    }
}
```

## Common Pitfalls

### Pitfall 1: Tool Re-registration Duplicate
**What goes wrong:** `ToolRegistry::register` is called per-turn with the same tool name. If the registry appends rather than upserts, `text_to_speech` + `send_audio` accumulate duplicate entries, causing duplicate tools in the LLM schema.
**Why it happens:** The TUI and web surfaces share a single `AgentRuntime` across many turns. Per-turn registration adds to the same registry.
**How to avoid:** Inspect `ToolRegistry::register` implementation. If it appends, add a `register_or_replace` variant, or call `unregister("text_to_speech"); unregister("send_audio")` before re-registering per turn. Alternatively, register only on the first turn for a given session_key (track session_key changes on `AgentRuntime`).
**Warning signs:** LLM schema contains `text_to_speech` listed multiple times; `toolset show voice` shows more than 2 tools.

### Pitfall 2: WebAudioDispatcher Circular Dependency
**What goes wrong:** Placing `WebAudioDispatcher` in `ironhermes-tools` and importing `ChatStreamEvent` from `iron_hermes_ui` creates a circular dep (`tools → ui → agent → tools`).
**How to avoid:** Place `WebAudioDispatcher` in `iron_hermes_ui/src/server/web_audio_dispatcher.rs`, implement `ironhermes_tools::AudioDispatcher for WebAudioDispatcher` there. Mirrors `TelegramAdapter` pattern.

### Pitfall 3: `Message::Binary` on Server Side
**What goes wrong:** The existing ws.rs server uses only `Message::Text`. Adding `Message::Binary` on the server requires the existing WASM client binary-frame handler to JSON-parse the frame. `warp_hermes.rs:181` currently uses `String::from_utf8_lossy(&b).to_string()` to convert binary frames — this means the client treats binary frames as UTF-8 text. If `AudioOut` is serialized as JSON and sent as `Message::Binary`, the existing client code in `warp_hermes.rs` will attempt to JSON-parse it as a `ChatStreamEvent` — which will FAIL if `ChatStreamEvent` doesn't have `AudioOut` yet, or work correctly after `AudioOut` is added.
**How to avoid:** Add `AudioOut` to `ChatStreamEvent` BEFORE sending any `Message::Binary` frames from the server. The variant must exist on the WASM client build.

### Pitfall 4: Audio Cache Path Traversal
**What goes wrong:** The HTTP replay route receives `uuid` from user. If not sanitized, a crafted uuid like `"../../../etc/passwd"` could leak files.
**How to avoid:** Mirror `tts_tool.rs:T-output-path` mitigation: `audio_cache_dir.join(uuid).canonicalize()` + `starts_with(audio_cache_dir)` check. Reject with 400 if outside cache dir. UUID format validation (parse as `uuid::Uuid`) is a first line of defense.

### Pitfall 5: Per-Session vs Per-Turn Session Key
**What goes wrong:** Gateway handler builds `session_key` multiple times per request (for running_agent guard, for queue push, etc.). The TTS session_key must use the same triple (`platform + chat_id + user_id`) as the other sites.
**How to avoid:** Reuse the `session_key` already built at `handler.rs:434` (`let session_key = SessionKey::new(event.platform.clone(), &event.chat_id).with_user(&event.sender_id)`). Do NOT build a new SessionKey for TTS; clone the existing one.

### Pitfall 6: D-05 `include_str!` Path Resolution
**What goes wrong:** `include_str!("../../iron_hermes_ui/src/server/ws.rs")` from `crates/ironhermes-agent/tests/invariants_36_17_7.rs` requires the cross-crate path to be stable relative to the test source file location.
**How to avoid:** Verify path at plan time by checking the directory structure. The path `crates/ironhermes-agent/tests/` → `../../` → `crates/` works for any other crate in `crates/`. The negative assert (no `session_key: None,` in `agent_runtime.rs`) must be the FIRST test to run so a build failure is obvious.

### Pitfall 7: `AgentRuntime::from_config` still passes `None` after the change
**What goes wrong:** The D-05 negative assert checks `!SRC.contains("session_key: None,")`. But `default_input()` in `app_runtime_factory.rs` test helpers also use `session_key: None`. The negative assert would false-fail.
**How to avoid:** The negative assert targets `agent_runtime.rs`, not `app_runtime_factory.rs`. The test helper struct in `app_runtime_factory.rs:347` uses `session_key: None` which is correct (test helper without TTS). The `agent_runtime.rs:215` line is the production code to change. The assert `!SRC.contains("session_key: None,")` on `agent_runtime.rs` is correctly scoped.

## Open Questions

1. **`ToolRegistry::register` upsert vs append semantics**
   - What we know: `register_tts_tools` calls `self.register(Box::new(...))` for `TextToSpeechTool` and `SendAudioTool`. The method is `pub fn register(&mut self, tool: Box<dyn Tool>)`.
   - What's unclear: Does `register` replace an existing tool with the same `name()`, or append a duplicate?
   - Recommendation: Executor reads `ToolRegistry::register` implementation before writing per-turn registration. If it appends, add a guard: check `registry.get_definition("text_to_speech").is_some()` and skip re-registration if already present for this session; OR add `unregister` + re-register.

2. **`run_web_turn` signature change scope**
   - What we know: `run_web_turn` is called from `ws.rs` and internally builds `TurnRequest`.
   - What's unclear: How many callers does `run_web_turn` have? If it has test-only callers, the signature change ripples.
   - Recommendation: Grep all callers of `run_web_turn` at plan time. If only called from `ws.rs`, add `tts_wiring` parameter cleanly.

3. **`Message::Binary` client-side parse path in HermesApp**
   - What we know: `warp_hermes.rs:181` (legacy-shell component) handles `Message::Binary` by treating it as UTF-8 text. HermesApp is the active root (project memory note).
   - What's unclear: Does HermesApp's ws event handler also have a `Message::Binary` arm?
   - Recommendation: Executor must verify HermesApp's ws handler (in `components/hermes_app/`) has a `Message::Binary` arm before the audio PR lands.

4. **`serde_bytes` workspace availability**
   - What we know: `serde_bytes` is needed if `Vec<u8>` in `AudioOut` should serialize as base64 rather than integer array.
   - What's unclear: Is `serde_bytes` already a workspace dep?
   - Recommendation: `grep serde_bytes /Users/twilson/code/ironhermes/Cargo.toml` at plan time. If absent, add `serde_bytes = "0.11"` to workspace deps.

5. **iron_hermes_ui auth model for `GET /audio/:uuid`**
   - What we know: The server is operator-local; existing routes don't show explicit auth gates.
   - What's unclear: Is there a session cookie check anywhere?
   - Recommendation: For v1, validate uuid format + path-containment only. Add a comment noting auth upgrade is deferred until the server has a public-facing auth layer.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | Partial | `GET /audio/:uuid` — UUID format + path-containment validation; full auth deferred (see Open Q5) |
| V3 Session Management | No | Audio route is stateless read from cache |
| V4 Access Control | No | Audio cache is per-server, not per-user |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Path traversal via uuid param (`../../../etc/passwd`) | Tampering | `uuid::Uuid::from_str(uuid)` parse + `canonicalize + starts_with(audio_cache_dir)` |
| Unbounded disk growth | Denial of Service | D-02-d GC sweep with configurable `max_age_days` |
| Audio file serving to unauthenticated users | Information Disclosure | UUID is unguessable (v4); accept as sufficient for v1 operator-local deployment |
| WS binary frame injection | Spoofing | Client only receives frames from the server's `tx.send`; no client-to-server binary path added |
