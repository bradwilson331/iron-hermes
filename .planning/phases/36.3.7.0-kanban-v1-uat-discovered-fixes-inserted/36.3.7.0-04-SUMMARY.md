## Meta-finding — bilateral-tracing rule for verifiers

Five receiver-end bugs across two phases (36.3.7 + 36.3.7.0) all followed the same pattern: emitter ✓ wired, receiver ✗ missed. The gsd-verifier in Phase 36.3.7 returned 17/17 PASS; this UAT round surfaced 5 bugs the verifier didn't catch.

**Concrete rule for future verifier prompts:**

> For every wire-up claim ("X is registered" / "X argv is constructed" / "X event bumps Y counter"), the verifier MUST trace BOTH ends:
> - PRODUCER: where does the value get emitted/registered/incremented?
> - CONSUMER: who reads it, accepts it, dispatches on it, acts on it?
>
> Stop at the producer side only when the consumer side is explicitly out-of-scope (and document why). Otherwise, every "registered" check must be paired with a "received" check, every "added flag" check with an "ALL sibling gates updated" check, every "schema defined" check with an "EVERY provider accepts this schema" check.

Concrete examples from this UAT round:
- "`worker_spawn` emits `--skills`" should have paired with "`Cli` struct accepts `--skills`" → would have caught Bug #1.
- "`CommandDef::new(\"kanban\", ...)` registers /kanban" should have paired with "`handlers.rs::dispatch` has a `\"kanban\" =>` arm" → would have caught Bug #2.
- "`-q` flag added to `Chat` enum + `run_single` short-circuit wired" should have paired with "ALL preflight/interactive sibling gates also exclude `chat -q`" → would have caught Bug #4.

This rule belongs in a LEARNINGS.md entry at phase close.
