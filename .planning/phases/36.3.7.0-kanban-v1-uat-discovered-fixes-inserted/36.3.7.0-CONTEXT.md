## Locked Decisions

### BUG-36.3.7-01 — Drop the `--skills kanban-worker` auto-pass

**Decision:** Modify `crates/ironhermes-kanban/src/worker_spawn.rs` (around line 183) to NOT prepend `--skills kanban-worker [extras]` to the worker's argv. The worker process gets the kanban tools + KANBAN_GUIDANCE overlay via Plan 05's env-gated path (`inject_kanban_guidance_if_worker` + `register_kanban_tools_if_applicable` — both already conditional on `HERMES_KANBAN_TASK`), so the `--skills` arg is structurally redundant.

**Rejected alternative:** Add a top-level `--skills <NAME>` clap flag to the `Cli` struct in `crates/ironhermes-cli/src/main.rs`. Rejected because Plan 05's env-gated injection already provides the required behavior — adding a flag duplicates the wiring and creates two sources of truth for "is this a worker session."

**Rationale:** The doc comments in `worker_spawn.rs` (lines 37 and 142) reference the now-rejected argv shape. They must be updated to reflect the env-only contract. Skill extras from `task.skills` (the JSON array on the Task row) must be carried via a different mechanism — either via env var passing on the same path that `HERMES_KANBAN_TASK` uses, OR deferred to a separate phase if no such mechanism currently exists. Inspect the existing skill-extras-passing path during planning; if there isn't one, the plan must scope the question explicitly and propose a minimal addition (e.g., `HERMES_KANBAN_TASK_SKILLS` env var with a JSON array value) so the executor doesn't get blocked mid-task.

**Receiver verification (mandatory):** the fix MUST include a test that exercises the receiver end — either (a) an integration test that constructs the worker argv via `build_kanban_worker_env` + `Command` shape and asserts the binary parses without error via `--version` or `--help`, OR (b) a static-grep assertion that `--skills` does NOT appear in the constructed argv. Either is acceptable; option (a) is stronger because it would have caught Bug #1 pre-merge.

### BUG-36.3.7-02 — Add `cmd_kanban` handler in `handlers.rs`

**Decision:** Add a new `fn cmd_kanban(args: &[&str], ctx: &CommandContext) -> CommandResult` in `crates/ironhermes-core/src/commands/handlers.rs` and add a `"kanban" => cmd_kanban(args, ctx),` arm in the giant `match cmd.name` (around line 18). Mirror the structure of `cmd_cron` at line 1062 — match on `args.first().copied()`, dispatch to in-process `KanbanStore` method calls for each subverb.

**Subverb coverage (MINIMUM):** the handler must implement at least the subverbs needed to satisfy UAT-09-B's PASS criteria — `list`, `show <id>`, `tip`. Aspirational subverbs (claim, complete, block, etc.) MAY be added but are not required for this phase's PASS criteria; mark them as TODO stubs that return a "use `ironhermes kanban <verb>` from CLI" message until a follow-up phase covers them. Document the deferred subverbs in SUMMARY.md.

**KanbanStore handle source:** The `CommandContext` does not currently have a `kanban_store` field. Add one (`Option<Arc<...>>` mirroring the `cron_store` field). Wire it through the existing `build_cmd_ctx` builder in `crates/ironhermes-cli/src/main.rs` so both `run_chat`'s prompt-time dispatch and the mid-turn slash dispatch arm get the same handle. Plan 05's `KanbanStore::open_default()` pattern is the open path. Failure to open is non-fatal (return `CommandResult::Output("/kanban: kanban store not configured.")` — same fallback shape `cmd_cron` uses at line 1064).

**Routing pattern:** each subverb calls the same `KanbanStore` methods that the CLI's `kanban/commands.rs` calls. By construction, the LLM tool surface (Plan 04) + CLI verb surface (Plan 06) + slash command surface (this bug fix) all route through the same store. This is the D-20 backend-portability promise.

**Receiver verification (mandatory):** the fix MUST include a test that exercises the full dispatch chain — `dispatch_command(extensions, "kanban", &["list"], &router, &ctx)` returns a `CommandResult::Output` containing the CLI table format (assert on `"STATUS"` and `"ASSIGNEE"` substring), NOT `"not yet available"` from `todo_stub`. This test must compile and run as part of the existing test surface; ideally it lives near the existing `is_bypass_locked_list` test (which proves the bypass entry, this proves the dispatch arm).

### BUG-36.3.7-03 — Failure circuit-breaker off-by-one

**Decision:** Read the current circuit-breaker check in `crates/ironhermes-kanban/src/dispatcher.rs` (the `respawn-guard` step, step 7 in the 8-step tick). Confirm the comparison operator currently used (`>` vs `>=`). Confirm D-12 intent by reading the locked-decision text in `.planning/phases/36.3.7-kanban-multi-agent-board-kanban-tools/36.3.7-CONTEXT.md` for D-12. If D-12 reads "stop AT N failures" → use `>=`. If D-12 reads "stop AFTER exceeding N failures" → use `>` (and update the comment + add a test pinning the semantics; the bug becomes "spec was ambiguous, now isn't").

**Default if D-12 is ambiguous:** prefer `>=` semantics ("`failure_limit = 2` means stop at 2 failures") — that's the intuitive meaning of "limit" and matches operator expectation per UAT-09-A's observation. Update D-12 in `36.3.7-CONTEXT.md` only if the planner explicitly chooses that path (otherwise leave the locked decision alone and document the resolution as a clarification).

**Receiver verification (mandatory):** the fix MUST include a test that exercises both sides of the bound — `consecutive_failures = failure_limit` should block (verify `skipped_nonspawnable` event fires) and `consecutive_failures = failure_limit - 1` should still spawn. This test goes in `crates/ironhermes-kanban/tests/dispatcher_logic.rs` near the existing 8-step coverage.

**Decision:** After all three bug fixes land + automated tests pass, re-run the UAT-09-A and UAT-09-B procedures from the 36.3.7-09 SUMMARY addendum (Section "Deferred Live Verification — UAT Use Cases"). **PASS criteria for UAT-09-A re-run:** worker subprocess actually completes a real LLM round-trip and calls `kanban_complete`; task reaches `status: done` (not `blocked`); `consecutive_failures` stays at 0; `kanban runs <id>` shows `outcome: completed`. The non-bypass `chat -q "/kanban list"` path is intentional (per Plan 05 + the run_single comment at main.rs:875) — do NOT change that; UAT-09-B only covers the interactive REPL path.

**If the re-run reveals additional bugs:** halt this phase, document the new bugs in a checkpoint summary, surface to the user. Do NOT silently fix new bugs under this phase — they go to 36.3.7.1.
