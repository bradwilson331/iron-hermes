## Discovered: Bug #5 — `delegate_task` tool schema incompatible with Anthropic

**Severity:** HIGH (blocks ALL worker round-trips going through Anthropic — including via OpenRouter's routing layer)
**File:** `crates/ironhermes-tools/src/delegate_task.rs` line 735
**Surface:**
```rust
"oneOf": [
    { "required": ["task"] },
    { "required": ["tasks"] },
]
```
This `oneOf` lives at the TOP LEVEL of the tool's `input_schema`. Anthropic's Messages API rejects top-level `oneOf` / `allOf` / `anyOf` in tool input_schemas.

**Why this is pre-existing, not phase 36.3.7.0 scope:**
- `delegate_task` lives in `ironhermes-tools` (Phase 21.7-class infrastructure), not in the kanban crate.
- The `oneOf` was deliberately added to enforce mutual-exclusion of `task` vs `tasks` at the schema level (see comments at lines 1221–1239 referencing a bug fix that introduced this constraint).
- Anthropic's restriction on top-level boolean schema combinators is a long-standing API constraint, not a 36.3.7-era regression.
- The kanban worker path happens to exercise this bug because workers register the full default tool surface (which includes `delegate_task`) and the LLM provider is Anthropic-via-OpenRouter.

**Smallest fix candidates (for a follow-up phase, e.g. 36.3.7.1 or a dedicated tool-schema-compat phase):**
- (a) Move the `oneOf` INTO a single nested level (e.g., `"properties": { "_oneof_marker": { "oneOf": [...] } }`) so it's not at the top.
- (b) Drop the schema-level mutual-exclusion and rely on runtime validation in `execute()` (the comments suggest runtime validation already exists).
- (c) Render different schema variants for different providers (Anthropic vs OpenAI) — heavier lift.

Option (b) is the smallest diff and best matches existing comment "Runtime validation in `execute()` still enforces mutual exclusion." Recommended.

**Out of scope for 36.3.7.0.** The phase goal was the three kanban-kernel receiver-end gaps + UAT. The three plus the UAT-discovered Plan 05 are all merged and PASS. The schema bug belongs to `ironhermes-tools` and should be its own phase.

## Meta-finding (carried from Phase 36.3.7-09 Addendum + reinforced this session)

The receiver-end-gap pattern repeated FIVE times across phases 36.3.7 + 36.3.7.0:

| Bug | Emitter side (✓ wired) | Receiver side (✗ missed) | Discovered by |
|---|---|---|---|

| #4 | Phase 36.3.7 Plan 01 added `chat -q` flag + `run_single` short-circuit | `run_preflight` gate at `main.rs:402` didn't exclude chat-with-query | UAT-09-A re-run #3 |
| #5 | Bug fix added top-level `oneOf` to `delegate_task` schema for runtime mutex enforcement | Anthropic's tool API rejects top-level `oneOf` | UAT-09-A re-run #5 (this session) |

**Pattern:** every wire-up has at least two ends. The verifier consistently traced emitters successfully but stopped at the first sign of "registered" / "defined" / "added," never following through to "received" / "dispatched" / "accepted." Future verifier prompts must explicitly require **bilateral tracing** — for every claim "X is wired," trace BOTH the producer AND the consumer of X.

Examples of bilateral-trace requirements that should be encoded:
- "X argv is constructed" → ALSO require: "X argv is accepted by the binary's `Cli` struct"
- "X command is registered" → ALSO require: "X command has a dispatch arm in the handler match"
- "X event bumps counter" → ALSO require: "Counter is read AND acted on by the consumer step"
- "X flag is added" → ALSO require: "ALL sibling gates that filter on the same predicate set are updated"
- "X tool is registered" → ALSO require: "X tool's schema is accepted by EVERY provider in the active routing layer"
