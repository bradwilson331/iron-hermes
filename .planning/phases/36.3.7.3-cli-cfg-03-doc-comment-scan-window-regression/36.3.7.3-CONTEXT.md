<domain>
## Phase Boundary

This is a regression fix + a receiver-end hardening. The pre-existing static-grep test `phase_amendment_doc_comment_present` in `crates/ironhermes-cli/tests/invariants_26_4_1_cfg_03.rs` is failing because Phase 36.3.7.0 commit `c453411f` inserted an 11-line Phase 36.3.7.0 Plan 05 comment block (lines 400-410 in current `main.rs`) between the original `Phase 26.4.1 (CFG-03) AMENDMENT:` doc-comment block (lines 384-399) and the `let run_preflight = matches!(...)` binding (line 415-417).

**Concrete measurement (post-36.3.7.0):**
- CFG-03 marker line: `// Phase 26.4.1 (CFG-03) AMENDMENT:` at main.rs:384
- Gate pattern line: `Some(Commands::Chat { .. }) | Some(Commands::Gateway { .. }) | None` at main.rs:417
- Byte distance: ~1700 chars (33 lines × ~50 chars/line avg)
- Test scan window: 1500 chars BEFORE the gate
- Result: marker is now ~200 chars OUTSIDE the test's window → `.contains("Phase 26.4.1") || .contains("CFG-03")` returns false → test panics

The test is NOT measuring a runtime regression — `main.rs` still contains the CFG-03 marker, the widened gate, and the preserved sibling gates. The test is a static-grep regression-lock from Phase 26.4.1 that was tuned for the file shape at that time. Phase 36.3.7.0's legitimate Plan 05 comment-block addition (BUG-36.3.7-04 documentation for the `chat -q` fix) shifted the layout enough to break the assertion without breaking the underlying behavior.

This is a bilateral-tracing class of bug: the producer (`CFG-03 amendment` comment) still exists in the file; the consumer (the scan-window test) is brittle to comment-layout shifts. Fix BOTH ends in the same phase per the LEARNINGS meta-rule.

In scope:
- **BUG-CLI-CFG-03-DOC-COMMENT-01** — restore a short, greppable `CFG-03` marker IMMEDIATELY above the `let run_preflight = matches!(` binding at main.rs:415. One line: `// Phase 26.4.1 CFG-03: run_preflight gate widening — see doc-comment block above for full rationale.` This brings a CFG-03 marker inside the test's 1500-char window without bloating the file and without removing the canonical doc-comment block.
- **BUG-CLI-CFG-03-DOC-COMMENT-02** — harden `phase_amendment_doc_comment_present` to anchor on marker presence within the FUNCTION containing the gate (rather than a fixed 1500-char byte window). New approach: find the function body via the surrounding `pub async fn main()` braces (or use the gate's enclosing 100-line window as a proxy) and assert the CFG-03 marker exists somewhere in that scope. This makes the test resilient to future comment rewrites.

Out of scope:
- Removing or rewriting Phase 36.3.7.0 Plan 05's BUG-36.3.7-04 comment block at lines 400-410. That documentation is correct and load-bearing — operators reading the gate code need it.
- Touching `run_preflight`, `is_interactive_repl`, `is_chat_or_bare`, or any other gate logic — `main.rs` runtime behavior is correct.
- Any change to `gate_widened_to_gateway_for_run_preflight` (INV-01) or `sibling_gates_not_widened_to_gateway` (INV-02) tests — they pass and are correctly scoped.
- Backporting the test-hardening pattern to Phase 22.4 / Phase 23 / Phase 24 sibling tests (`invariants_22_4.rs`, etc.) — separate hardening initiative.
- Any change to commit `c453411f`. That commit is correct; the test should have been resilient.

<locked_decisions>
## Locked Decisions

### Restore a short CFG-03 marker line directly above the gate

**Decision:** Add a single comment line at main.rs:414 (immediately above `let run_preflight = matches!(`):

```rust
// Phase 26.4.1 CFG-03: run_preflight gate widening — see doc-comment block above for full rationale.
let run_preflight = matches!(
```

**Rejected alternatives:**
- (a) Re-locate the original Phase 26.4.1 AMENDMENT doc-comment block from lines 384-399 to immediately above line 415 — too disruptive, pushes the BUG-36.3.7-04 block out of position, and re-orders comments that were intentionally chronological.
- (b) Delete the BUG-36.3.7-04 comment block (lines 400-410) — out of scope; that block documents the chat-q preflight fix and is operator-facing documentation.
- (c) Widen the scan window in the test from 1500 → 2500 chars — works but ignores the underlying brittleness; any future legitimate comment addition retriggers the same regression.

**Rationale:** A short marker line is the smallest-possible producer fix. The original 16-line doc-comment block at 384-399 stays untouched (correct chronology preserved). The test sees its required marker substring (`Phase 26.4.1` AND `CFG-03`) within 1 line of the gate. Future legitimate comment additions in the same region cannot push the new marker out of the test's window because the marker is glued to the gate.

### Harden the test by anchoring on the gate's enclosing scope, not a byte window

**Decision:** Rewrite `phase_amendment_doc_comment_present` to:
1. Find the gate index (existing logic).
2. Walk backwards from the gate to find the enclosing `pub async fn main()` opening brace (or, simpler: search backwards for `async fn main` and use that as the scope start — since `main.rs` has exactly one `async fn main`).
3. Assert that the slice from `main()` opening to the gate contains both `"Phase 26.4.1"` and `"CFG-03"` (or, equivalently, `"Phase 26.4.1 CFG-03"` if the new marker line uses that compact form — but allow either to keep the test robust to phrasing changes).
4. Failure message must cite BOTH the bug ID (BUG-CLI-CFG-03-DOC-COMMENT-02) and the function-scope semantics so future regressions are immediately diagnosable.

**Rejected alternatives:**
- (a) Search the whole `MAIN_RS` for the marker without scope qualification — risks false positives if some other phase elsewhere mentions "Phase 26.4.1" in an unrelated comment.
- (b) Use a line-count window (e.g., 50 lines before the gate) instead of byte-count — slightly more robust to multi-line comment expansion but still brittle. Function-scope is the right semantic anchor.

**Rationale:** The test's purpose is "the CFG-03 amendment is documented near where it's implemented". The right "near" semantics is "in the same function body as the implementation", not "within N bytes". This eliminates the entire class of "marker pushed out of window" regressions.

### Single-plan, orchestrator-inline execution (no worktree)

**Decision:** Execute this phase as a single PLAN with 5 tasks, run inline by the orchestrator. No subagent dispatch, no worktree.

**Rejected alternatives:**
- (a) Two plans (one per bug) in two worktrees — Phase 36.3.7.1 demonstrated cwd-drift cost; two surgical edits don't justify the worktree overhead.
- (b) Single plan dispatched to a single executor subagent — extra context budget for a 2-file mechanical fix is wasteful.

**Rationale:** Same playbook as Phase 36.3.7.0 Plan 05 (inline orchestrator execution for a surgical preflight gate fix). 36.3.7.0-05 SUMMARY explicitly justified the inline approach: "the fix is a one-line predicate add + one `&& !chat_has_query` term on each of two sibling lines + a single test file. Dispatching a subagent for a surgical edit this small would burn more tokens than the work." 36.3.7.3 is the same shape: one 1-line marker add + one test-function body rewrite.
