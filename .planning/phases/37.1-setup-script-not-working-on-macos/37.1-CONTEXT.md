# Phase 37.1: setup script not working on macos - Context

**Gathered:** 2026-06-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the fragmented, broken set of IronHermes setup scripts with **one unified cross-platform installer** that handles the full lifecycle (**install / update / reinstall / uninstall**), and stand up a **GitHub Actions release pipeline** that produces the prebuilt binaries the installer downloads. This fixes the reported macOS bug — `install.sh` "fails after OS detection" — at its root.

**Root cause (verified during discussion):**
1. **No release pipeline exists** — only `.github/workflows/ci.yml`; nothing builds/uploads `ironhermes-<os>-<arch>.tar.gz` to GitHub Releases, so `install.sh::download_binary()` *always* fails (every platform).
2. **Wrong repo name** — `install.sh` (`REPO_NAME="ironhermes"`) and the README curl command both point at `bradwilson331/ironhermes`, but the real GitHub remote is `bradwilson331/iron-hermes` (hyphen). The Releases API call 404s → `VERSION=""` → no binary.
3. **Non-viable fallback** — the `cargo install ironhermes` fallback fails because the crate is not published to crates.io (primary remote is the self-hosted Gitea at `192.168.7.6:8418/twilson/ironhermes`).

Net effect on macOS: OS detection passes → GitHub API 404 → no prebuilt binary → `cargo install ironhermes` → "not found in registry" → exit. (Would also fail on Linux.)

**In scope:**
1. **Unified installer** — one bash script (macOS Apple Silicon + Intel, Linux x86_64 + aarch64) with `install|update|reinstall|uninstall` subcommands; a **minimal new `install.ps1`** for Windows (`install` verb only — see D-12); fix the repo-name bug in installer + README; consolidate/retire the redundant scripts.
2. **Release pipeline** — GitHub Actions build + upload tarballs (ad-hoc signed for now; notarization deferred — see D-07).
3. **Config completeness + setup wizard** — bring `cli-config.yaml.example` to full parity with the typed `Config` structs (incl. a NEW `kanban:` section for all `KanbanConfig` fields), and extend the setup wizard (`ironhermes-core/src/wizard.rs`) so every config section is accounted for. The wizard must detect/coexist with existing installs.

**Out of scope (boundary with Phase 36.12 — Packaging & distribution parity):** Homebrew tap, Nix flake, Termux/Android, **crates.io publication** (explicitly deferred — do NOT publish this phase), and any other packaging formats. The build-from-source fallback therefore uses `cargo install --git <repo>` (or clone + `cargo build --release`), **never** crates.io. **Full Apple notarization is also deferred** (D-07).

</domain>

<decisions>
## Implementation Decisions

### Unified script & lifecycle
- **D-01:** Consolidate the existing setup scripts into **one** canonical cross-platform bash installer (name TBD by planner, e.g. `ironhermes-setup.sh` / keep `install.sh`). Retire/reconcile: root `install.sh`, `scripts/deploy/install.sh`, `uninstall.sh`, `quick_setup_script.sh`, `setup-ironhermes.sh`, `install-gitea.sh`. The researcher must inventory what each currently does before the planner picks the canonical one and deletes the rest.
- **D-02:** Lifecycle is invoked via **subcommands**: `install | update | reinstall | uninstall`. First positional arg = verb; **default (no arg) = install**. Must remain curl-pipe friendly (no TTY) for the `install` path.
- **D-03 (builder default — confirm if wrong):** `uninstall` removes the binary (from `~/.local/bin`) + the installer-added PATH lines in shell rc files, and **preserves `~/.ironhermes/` user data by default** (API keys, sessions); a `--purge` flag also removes `~/.ironhermes/`. `update` = fetch latest release, swap the binary, leave config untouched (re-seed only *missing* templates). `reinstall` = force re-fetch + re-scaffold even if present (repair), preserving `.env`/`config.yaml`.
- **D-12 (Windows scope — RESOLVED post-research, supersedes D-02's Windows clause):** Research found `quick_setup_script.ps1` is an unrelated LoRA-tooling script — there is **no** existing IronHermes Windows installer to update. Resolution: this phase ships a **minimal new `install.ps1`** implementing the **`install` verb only** (download the prebuilt Windows binary from the release pipeline + set up PATH). The `update | reinstall | uninstall` lifecycle for Windows is **deferred** to a later phase. Consequence: the release pipeline (D-06) **must also build and upload a Windows binary artifact** (e.g. `ironhermes-windows-x86_64.zip`/`.tar.gz`) matching whatever name `install.ps1` fetches.

### Binary acquisition
- **D-04:** Installer prefers a **prebuilt tarball download** (from the new release pipeline) and falls back to **build-from-source via `cargo install --git`** (NOT crates.io — see boundary). Keep the existing artifact naming `ironhermes-${os}-${arch}.tar.gz` that `install.sh` already expects.
- **D-05:** **Configurable distribution source** via an env var (e.g. `IRONHERMES_REPO`). Default to **GitHub** (`bradwilson331/iron-hermes` — public, works for external installs); allow overriding to the Gitea remote. Fix the hardcoded wrong `ironhermes` → `iron-hermes` repo name in both `install.sh` and `README.md`.

### Release pipeline
- **D-06:** Stand up the release pipeline **this phase**, running on **GitHub Actions** (free macOS arm64+x64 + Linux multi-arch runners — Gitea is a LAN IP with no macOS runner). Builds tarballs for macOS (Apple Silicon + Intel) and Linux (x86_64 + aarch64), uploads to **GitHub Releases**; **both** GitHub and Gitea can serve downloads (optionally mirror artifacts to Gitea). Trigger on a version tag — ties to the workspace version (just bumped to **0.2.0** in Phase 37).
- **D-07 (REVISED — notarization deferred):** Full Apple notarization is **DEFERRED** — the paid Apple Developer account is not set up yet. **This phase:** the release pipeline **ad-hoc signs** macOS binaries (`codesign -s -`) and the installer strips the quarantine xattr after download (`xattr -d com.apple.quarantine`); build-from-source on macOS remains quarantine-free. Full Developer-ID signing + notarization (needs the Apple Developer account + Developer ID cert + notarytool API key as CI secrets) moves to a **future phase** once the account is provisioned. The installer/pipeline should be structured so notarization can be slotted in later without rework.

### Config completeness & setup wizard
- **D-08:** Bring `cli-config.yaml.example` to **full parity with the typed `Config` structs** — every field documented with its default + a comment. Add a **drift/coverage test** asserting no struct field is undocumented in the example (so the example stays authoritative as code evolves). Researcher must enumerate the canonical `Config` struct(s) in `ironhermes-core/src/config.rs` (+ nested per-crate configs) to build the field inventory.
- **D-09:** Add a **new `kanban:` section** to `cli-config.yaml.example` covering all 17 `KanbanConfig` fields (`crates/ironhermes-kanban/src/config.rs`): `dispatch_in_gateway`, `dispatch_interval_seconds`, `max_in_progress`, `failure_limit`, `stranded_threshold_seconds`, `dispatch_stale_timeout_seconds`, `default_workdir`, `notification_sources`, `notifier_poll_seconds`, `auto_decompose`, `auto_decompose_per_tick`, `orchestrator_profile`, `default_assignee`, `decomposer_model`, `auto_promote_children`, `judge_model`, `goal_inner_max_iterations`. Confirm how `KanbanConfig` mounts into the top-level `Config` (research) so the YAML key path is correct.
- **D-10:** Extend the setup wizard (`ironhermes-core/src/wizard.rs`) so **every config section is accounted for**. Model: the wizard **interactively prompts the essentials** (model / provider / API keys / memory / gateway / tools / hermes_home / learning + a kanban enable/disable) and, for **every other section** (`agent`, `terminal`, `web`, `exec`, `cron`, `compression`, `skills`, `delegation`, `rate_limit`, `batch`, `security`, `custom_providers`, `hooks`, + advanced kanban), **writes a commented, default-valued block** into `config.yaml` so nothing is silently absent — pointing power users to edit `config.yaml` for the advanced knobs. Current wizard covers ~9 of ~20 sections (`apply_{model,provider,api_key,learning_loop,memory_provider,hermes_home,gateway_section,tools_section,auxiliary}_answer`); the gap is the 13 sections above.
- **D-11 (existing-install awareness):** The wizard + installer must **detect and coexist with existing installs**, never silently clobbering user config on `update`/`reinstall`:
  - **Existing IronHermes** (`~/.ironhermes/config.yaml` / `.env` present) → preserve user values, only *fill missing* sections/keys (additive merge), never overwrite a set value.
  - **Legacy hermes-agent** (the Python predecessor) → detect a prior install/config and offer awareness/migration (research: where hermes-agent stores config + what's migratable; do NOT auto-migrate destructively).
  - **Forward-compat: future `openclaw` installs** → structure detection so a future `openclaw` install can be recognized/coexist; do not hard-code assumptions that block it. (`openclaw` does not exist yet — design for awareness, don't build it.)

## Existing Code Insights

### Reusable Assets
- `install.sh::detect_platform()` — working `uname -s`/`uname -m` → `${os}-${arch}` mapping (Linux/Darwin, x86_64/aarch64). Reuse as-is for the unified script.
- `install.sh::download_binary()` / `resolve_version()` / `scaffold_home()` / `seed_templates()` / `update_shell_path()` — the install path is already well-structured (subshell-scoped temp cleanup, `~/.ironhermes/{cron,sessions,logs,hooks,memories,skills,workspace}` scaffold, `.env` chmod 600, idempotent PATH edits). The bug is upstream (no binary to download + wrong repo), not in these helpers.
- `ironhermes doctor` — referenced at install end; the in-process doctor (Phase 35.1) can verify a post-install setup.

### Established Patterns
- Artifact naming `ironhermes-${PLATFORM}.tar.gz`, install dir `~/.local/bin`, home `${IRONHERMES_HOME:-$HOME/.ironhermes}` — keep these contracts so the release pipeline artifacts match what the installer fetches.
- `IS_INTERACTIVE` TTY guard (`[ -t 0 ]`) — install path must stay non-interactive (curl-pipe); the interactive menu was rejected for that reason.

### Integration Points
- Release workflow ↔ installer: the workflow's artifact names + Release tag must exactly match `download_binary()`'s `${artifact}`/`${url}` expectations.
- Repo-name fix touches both `install.sh` (`REPO_NAME`) and `README.md` (curl URL).
- macOS notarization (D-07) is a CI-secret + Apple-account dependency, not a code change — flag as a provisioning task.

## Specific Ideas

- The user explicitly wants the scripts **unified** and handling **new install, update, reinstall, and uninstall** — `install.sh` (option 3) is the one referenced in the main README for installing.
- macOS signing: the *eventual* target is full Apple **notarization** (directly informed by the Gatekeeper/codesign first-launch behavior seen throughout the Phase 37 session), but the **Apple Developer account is not set up yet** → defer; ship ad-hoc sign + quarantine-strip now (D-07).
- Distribution should be **configurable** between Gitea (primary remote) and GitHub (`iron-hermes`), defaulting to whichever works for external installs (GitHub).
- The setup wizard must "account for" **every** config section and gain a **kanban** section; bring `cli-config.yaml.example` to full struct parity (D-08/09/10).
- The installer/wizard must be **aware of existing installs** — current `~/.ironhermes`, the legacy Python **hermes-agent**, and a future **openclaw** — and never clobber set user values (additive-merge on update/reinstall) (D-11).

</specifics>
