## Summary

Phase 37.1 resolves a multi-root installation failure: the root `install.sh` references the wrong GitHub repo name (`ironhermes` vs `iron-hermes`), there is no release pipeline to produce the prebuilt tarballs it tries to download, and the `cargo install ironhermes` fallback is dead because the crate is not published to crates.io. The fix involves three coordinated workstreams: (1) unifying seven scattered scripts into one canonical bash installer with `install|update|reinstall|uninstall` lifecycle, (2) creating a GitHub Actions release pipeline that builds and uploads platform tarballs, and (3) bringing `cli-config.yaml.example` + the setup wizard to full `Config` struct parity with a new `kanban:` section.

The script inventory below reveals that `install.sh` (root) has the best-structured helper functions and is already referenced from `README.md` as the canonical installer — it is the correct base to build on. The `scripts/deploy/install.sh` is a separate gateway service installer (launchd/systemd), NOT a binary installer; it must not be confused with the root installer and should remain for gateway-service deployment. The `quick_setup_script.sh` and `quick_setup_script.ps1` are unrelated LoRA/AI-training scripts that happen to live in the repo — they are irrelevant to IronHermes install and should be left alone or removed; they are NOT IronHermes installers.

The Config struct inventory reveals 12 top-level typed sections currently missing from `cli-config.yaml.example`: `autonomous`, `mcp_servers`, `browser`, `extract`, `prompt_caching`, `dashboard`, `tts`, `audio_cache`, plus the `kanban` raw-YAML value. The wizard currently covers 6 interactive prompts and 2 stub pass-throughs; approximately 13 sections need commented-default blocks written by the wizard at first-run.

**Primary recommendation:** Build on root `install.sh`'s helper structure. Add subcommand dispatch, fix `REPO_NAME`, replace the dead cargo-install fallback with `cargo install --git`, add the release pipeline targeting `macos-15` (ARM64) + `macos-15-intel` (x64) + `ubuntu-24.04` (x86_64) + `ubuntu-24.04-arm` (aarch64) — all four are native runners available at no extra cost on public repos.

## Q5: GitHub Actions Release Pipeline (D-06/D-07)

### Available Runner Images (confirmed)

[VERIFIED: GitHub Docs — docs.github.com/en/actions/reference/runners/github-hosted-runners]

| Target | Runner Label | Architecture | Free for public repos |
|--------|-------------|--------------|----------------------|
| macOS ARM64 (Apple Silicon) | `macos-15` or `macos-latest` | arm64 | Yes (standard runner) |
| macOS Intel (x86_64) | `macos-15-intel` | x64 | Yes (standard runner) |
| Linux x86_64 | `ubuntu-24.04` | x64 | Yes |
| Linux aarch64 | `ubuntu-24.04-arm` | aarch64 | Yes (same spec as x64: 4 CPU, 16GB RAM, 14GB disk) |

macOS 26 runners (`macos-26`, `macos-26-intel`) are also now generally available (GA 2026-02-26) and may be used instead of macOS 15. `macos-15` is the safer conservative choice for broadest binary compatibility.

**Important:** `macos-latest` currently resolves to an ARM64 runner (M1/M2). For the Intel build, the label `macos-15-intel` must be used explicitly — `macos-15` alone will NOT produce an x64 binary on a native Intel runner.

### Linux aarch64 — Native Runner (Recommended)

**Recommendation (Claude's Discretion):** Use `ubuntu-24.04-arm` native runner for Linux aarch64. It is available on public repos at no extra cost, produces a true native binary without cross-compilation complexity, and avoids the `cross` toolchain overhead. The `cross` crate (used via `--target aarch64-unknown-linux-gnu` on an x86_64 host) adds Docker-in-Docker complexity and crate feature gating that `ubuntu-24.04-arm` sidesteps entirely.

### Release Workflow Design (coexisting with ci.yml)

Current `ci.yml` triggers on push to `develop`/`main` and PRs to those branches. The release workflow must:

1. Use a SEPARATE file (e.g., `.github/workflows/release.yml`) — never modify `ci.yml`.
2. Trigger on tag push: `on: push: tags: ["v*"]` — completely orthogonal to ci.yml triggers.
3. No conflict possible because they share no trigger conditions.

Recommended workflow structure:
```yaml
on:
  push:
    tags:
      - "v*"

jobs:
  build:
    strategy:
      matrix:
        include:
          - os: macos-15           # ARM64 Apple Silicon
            target: aarch64-apple-darwin
            artifact: ironhermes-macos-aarch64
          - os: macos-15-intel     # Intel x86_64
            target: x86_64-apple-darwin
            artifact: ironhermes-macos-x86_64
          - os: ubuntu-24.04       # Linux x86_64
            target: x86_64-unknown-linux-gnu
            artifact: ironhermes-linux-x86_64
          - os: ubuntu-24.04-arm   # Linux aarch64 (native)
            target: aarch64-unknown-linux-linux-gnu
            artifact: ironhermes-linux-aarch64
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - run: cargo build --release --bin ironhermes
      - name: Ad-hoc sign (macOS only)
        if: runner.os == 'macOS'
        run: codesign -s - target/release/ironhermes
      - name: Package tarball
        run: |
          cp target/release/ironhermes ironhermes
          tar czf ${{ matrix.artifact }}.tar.gz ironhermes
      - uses: softprops/action-gh-release@v2
        with:
          files: ${{ matrix.artifact }}.tar.gz
```

### Artifact Naming Contract

The installer's `download_binary()` constructs:
```bash
artifact="ironhermes-${PLATFORM}.tar.gz"
# where PLATFORM="${os}-${arch}"
# os: "macos" or "linux"
# arch: "x86_64" or "aarch64"
```

So artifact names expected by installer: `ironhermes-macos-x86_64.tar.gz`, `ironhermes-macos-aarch64.tar.gz`, `ironhermes-linux-x86_64.tar.gz`, `ironhermes-linux-aarch64.tar.gz`.

The release workflow MUST name tarballs to match this pattern exactly. The matrix `artifact` field above already follows this convention.

### macOS Ad-hoc Signing + Quarantine Strip (D-07)

**Ad-hoc signing** (`codesign -s -`): Marks the binary as signed with a self-generated ephemeral identity. This does NOT satisfy Gatekeeper for binaries downloaded from the internet, but it provides code integrity (prevents modification after signing) and is a zero-cost step that does not require any Apple Developer account.

**Quarantine strip** (`xattr -d com.apple.quarantine /path/to/ironhermes`): The installer must call this after extracting the downloaded tarball. On macOS, any file downloaded via curl/browser gets the quarantine extended attribute, which triggers Gatekeeper and blocks execution. Stripping it allows the binary to run without the "cannot be verified" dialog — equivalent to right-clicking "Open" once.

**Notarization slot-in design:** Structure the pipeline with a comment block at the signing step that documents the future `notarytool` commands. When the Apple Developer account is provisioned, the implementer replaces `codesign -s -` with `codesign --sign "Developer ID Application: ..."` + `xcrun notarytool submit ... --wait` + `xcrun stapler staple`. The quarantine-strip step in the installer becomes unnecessary (notarized binaries pass Gatekeeper without quarantine strip) but can remain as a no-op safety net.

## Architecture Patterns

### Unified Installer: Subcommand Dispatch Pattern

```bash
#!/bin/bash
set -euo pipefail

VERB="${1:-install}"  # default verb is install (D-02)

case "$VERB" in
    install)   cmd_install ;;
    update)    cmd_update ;;
    reinstall) cmd_reinstall ;;
    uninstall) cmd_uninstall ;;
    *)
        log_error "Unknown subcommand: $VERB"
        log_error "Usage: ironhermes-setup.sh [install|update|reinstall|uninstall]"
        exit 1
        ;;
esac
```

### Additive-Merge for `update`/`reinstall`

The installer must NOT use `cp` (overwrites) for config files during update/reinstall. Pattern:

```bash
seed_templates() {
    local mode="${1:-install}"  # install | update | reinstall

    # For install: skip if file exists (existing guard already in install.sh)
    # For update: skip all — only re-seed if file is completely absent
    # For reinstall: re-seed absent files; use additive-merge for existing yaml
    if [ ! -f "$IRONHERMES_HOME/.env" ]; then
        # download/copy .env.example → .env
        chmod 600 "$IRONHERMES_HOME/.env"
    fi

    if [ ! -f "$IRONHERMES_HOME/config.yaml" ]; then
        # download/copy cli-config.yaml.example → config.yaml
    elif [ "$mode" = "reinstall" ]; then
        # additive merge: download example, insert only missing keys
        # (simple: append new sections as commented blocks at end of file)
        log_warn "config.yaml exists — only missing sections will be added"
    fi
}
```

### Config Drift Test (D-08)

The simplest reliable mechanism that does not require reflection (Rust has no runtime reflection):

**Option A: Field-list test (recommended)** — Maintain a const `KNOWN_CONFIG_SECTIONS: &[&str]` in a test file. The test deserializes `cli-config.yaml.example`, collects top-level YAML keys, and asserts they match the const list. When a new field is added to `Config`, the struct compiles fine, but the test fails until the example is updated. This is O(n) maintenance cost per new field but zero runtime overhead.

**Option B: Serde round-trip** — Serialize `Config::default()` to YAML, deserialize `cli-config.yaml.example` stripping comments, compare field presence. More automated but harder to write because the example uses commented fields (all lines begin with `#`), so it deserializes to mostly-empty values.

**Recommendation:** Option A for the drift test. The planner should create a test in `crates/ironhermes-core/tests/config_parity.rs` or `crates/ironhermes-cli/tests/config_parity.rs`.

## Common Pitfalls

### Pitfall 1: Artifact Name Mismatch Between Pipeline and Installer

**What goes wrong:** The release pipeline produces `ironhermes-macos-arm64.tar.gz` but the installer constructs `ironhermes-macos-aarch64.tar.gz`. The download silently 404s.

**Why it happens:** `uname -m` returns `arm64` on macOS Apple Silicon but `aarch64` on Linux. The installer normalizes both to `aarch64` — the pipeline must match.

**How to avoid:** The `detect_platform()` in `install.sh` normalizes `arm64 → aarch64`. The pipeline matrix's `artifact` field must use `aarch64` not `arm64`. Lock the artifact naming contract in a comment in both files.

**Warning signs:** `download_binary` returns 1 on Apple Silicon despite a release existing.

---

### Pitfall 2: `macos-latest` Produces ARM64 Binary Only

**What goes wrong:** Using `macos-latest` for both macOS builds produces two ARM64 binaries and no Intel binary.

**Why it happens:** `macos-latest` now resolves to an ARM64 runner. Intel x64 requires the explicit `macos-15-intel` (or `macos-26-intel`) label.

**How to avoid:** Use explicit labels in the matrix: `macos-15` for ARM64, `macos-15-intel` for Intel x64.

---

### Pitfall 3: Quarantine Attribute Not Stripped Before PATH Check

**What goes wrong:** macOS Gatekeeper blocks the newly installed binary when the user first runs `ironhermes`, showing "cannot be verified" dialog. User thinks install failed.

**Why it happens:** `curl` downloads set the quarantine xattr. `install -m 755` preserves xattrs. Even after PATH is set, the binary is blocked.

**How to avoid:** Call `xattr -d com.apple.quarantine "$INSTALL_DIR/ironhermes" 2>/dev/null || true` immediately after the `install -m 755` line. The `|| true` prevents failure when the attribute is absent (Linux).

---

### Pitfall 4: `seed_templates` URL Uses Wrong REPO_NAME

**What goes wrong:** During curl-pipe install, `seed_templates` fetches templates from `https://raw.githubusercontent.com/bradwilson331/ironhermes/...` (wrong name). The downloads 404. User gets partial config.

**Why it happens:** `seed_templates` uses `REPO_NAME` which currently has the wrong value. Fixing `REPO_NAME` at the top fixes both `download_binary` and `seed_templates`.

**How to avoid:** Single fix at the top: `REPO_NAME="iron-hermes"`. Both functions inherit it.

---

### Pitfall 5: `kanban:` YAML Key Deserializes to `serde_yaml::Value`, Not `KanbanConfig`

**What goes wrong:** The drift test asserts `kanban:` is a field in Config — that's true. But documenting it in `cli-config.yaml.example` requires knowing the field names of `KanbanConfig`, which lives in a different crate. Attempting to import `KanbanConfig` from `ironhermes-core` tests would create a circular dependency.

**Why it happens:** The circular dep `ironhermes-core ← ironhermes-kanban` is intentional. The solution in production is raw `serde_yaml::Value`.

**How to avoid:** The `cli-config.yaml.example` kanban section is written manually (not generated). The drift test for kanban checks that `kanban:` key exists in the example, not that all 17 subfields are present (field-level drift for kanban is the responsibility of `ironhermes-kanban`'s own tests).

---

### Pitfall 6: Wizard Writes Commented Defaults That Overwrite User Values

**What goes wrong:** On `reinstall`/`update`, the wizard re-runs and writes commented-default blocks for sections the user has already configured, clobbering their values.

**Why it happens:** Using `cp cli-config.yaml.example config.yaml` is destructive. Simple string append of commented blocks also fails if the section header already exists.

**How to avoid:** Use additive-merge: load existing config.yaml as `serde_yaml::Value`, check for each top-level key — if absent, insert the commented block; if present, leave untouched. The raw-YAML splice pattern from `apply_learning_loop_answer` is the established precedent.
