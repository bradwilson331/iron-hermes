## Open Threats (BLOCKERs)

### T-37.1-02-02 — OPEN BLOCKER: Uninstall RC cleanup silently fails under `set -euo pipefail`

**Disposition declared:** mitigate
**Claimed mitigation:** removal keyed on literal `"# Added by IronHermes installer"` marker; no interpolation

**Gap:** `install.sh:412-419`:

```bash
for rc in "$HOME/.bashrc" "$HOME/.zshrc" "$HOME/.profile"; do
    if [ -f "$rc" ]; then
        grep -v "# Added by IronHermes installer" "$rc" | \
        grep -v "export PATH=\"${INSTALL_DIR}:" > "${rc}.ironhermes_tmp" \
            && mv "${rc}.ironhermes_tmp" "$rc" \
            || rm -f "${rc}.ironhermes_tmp"
    fi
done
```

The script runs under `set -euo pipefail` (line 21). `grep -v` exits with status 1 when every input line matches the inverted pattern — i.e., nothing passes through to stdout. Confirmed empirically: `printf "# Added by IronHermes installer\n" | grep -v "# Added by IronHermes installer"` exits 1.

For any rc file whose only content is the installer-added lines (the common state after a fresh install on a machine without a pre-existing `.bashrc`), the second `grep -v "export PATH=..."` exits 1. Under `set -euo pipefail`, this causes the `&&` branch to fail: `mv` is skipped. The `||` branch then `rm -f`s the temp file. The original rc is untouched and the PATH entry is not removed — uninstall silently fails for its primary purpose.

Additionally, the match `"export PATH=\"${INSTALL_DIR}:"` is an unanchored substring. Any user-authored rc line that merely contains that prefix (e.g. a comment or a different tool's export) is deleted — data loss of user shell configuration.

**Files searched:** `install.sh:21,412-419`
**Required fix (implementation-side):** Replace the pipeline with a `sed`-based approach (or `grep -v ... || true`) that handles zero-match exit codes as success and anchors the full `export PATH="..."` line rather than a prefix substring.

### T-37.1-04-01 — OPEN BLOCKER: Actions pinned to mutable tags; no `permissions:` block

**Disposition declared:** mitigate
**Claimed mitigation:** approved actions, pinned to major version tags

**Gap:** `release.yml` pins all four third-party actions to mutable major-version tags:

- `actions/checkout@v4` (line 38)
- `dtolnay/rust-toolchain@stable` (line 41 — a **branch**, not a release tag)
- `Swatinem/rust-cache@v2` (line 44)
- `softprops/action-gh-release@v2` (line 84)

Major-version tags and branches are mutable refs. A force-push or tag-move by a compromised upstream repository executes attacker code inside jobs that have write access to GitHub Releases. This is not a supply-chain `mitigate` — it is at best a `transfer` (trust the upstream maintainers) or `accept`. No `permissions:` block is declared anywhere in `release.yml` (confirmed: zero grep hits for `permissions:`), so `GITHUB_TOKEN` inherits the repository/organization default for all matrix build jobs, including those where Cargo fetches and compiles arbitrary dependency crates.

The plan's rationale for accepting major-version tags as the mitigation is inconsistent with a `mitigate` disposition against supply-chain tampering.

**Files searched:** `.github/workflows/release.yml` (all 87 lines)
**Required resolution:** One of:
1. Pin all actions to full 40-character commit SHAs and add a least-privilege `permissions:` block — closes threat as mitigated.
2. Change disposition to `accept` with documented rationale and add an accepted-risk log entry, then re-run this audit.
