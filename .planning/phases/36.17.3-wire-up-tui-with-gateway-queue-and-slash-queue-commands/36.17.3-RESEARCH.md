## Summary

This phase wires real FIFO queueing into the ratatui TUI and extracts a shared `MessageQueue` trait so all future consumers (web UI, Discord, Slack, REST) share the same FIFO abstraction. The gateway's `SessionQueue` becomes the first concrete implementor; the TUI is the first non-gateway consumer.

**The current TUI `/queue` handler** (`commands.rs:978-999`) pre-populates the textarea — it does NOT buffer anything. The `map_core_to_slash_outcome` fallback at `commands.rs:1127-1129` simply renders `Queued: {message}` as a transcript line. The explicit deferral marker at `commands.rs:1123-1126` ("Phase 36.17.1 Plan 03 Task 1: the SessionQueue lives on GatewayRunner only") is the anchor this phase closes.

**Crate dependency situation is favorable.** `ironhermes-cli` already depends on both `ironhermes-core` AND `ironhermes-gateway` (`Cargo.toml:30`). `ironhermes-gateway` already depends on `ironhermes-core`. `SessionKey` lives in `ironhermes-gateway::session`, not core. This creates a choice: move the trait (and optionally `SessionKey`) to `ironhermes-core`, or define the trait in `ironhermes-gateway` and re-export it. No dep-cycle risk for either option since CLI already depends on gateway.

**The drain insertion point is clearly located.** The `run_app_inner` loop in `event_loop.rs:677-708` checks `app.pending_tx.is_some()` and calls `spawn_turn`. Turn completion is signaled by `StreamEvent::Finished | Cancelled | Error` which sets `app.pending_rx = None` and `app.cancel_child = None` in `handle_stream_event`. The drain check belongs immediately after this signal — in `handle_stream_event` at the `Finished | Cancelled | Error` arms — not in the spawn gate.

**`/stop` has a functional cancel path** via `CancellationToken`. The `/stop` slash handler delegates to core `cmd_stop` which calls `ProcessRegistry::drain_and_kill_session`; the TUI-level cancel fires the `cancel_child` token. Queue clear is a one-liner layered on top.

**Primary recommendation:** Put the `MessageQueue` trait in `ironhermes-core` (zero new crate, no dep cycle); `SessionKey` stays in `ironhermes-gateway` but the trait is generic over `K: Hash + Eq + Clone`. Planner must decide on the generic bound vs concrete `SessionKey` approach.

## Trait Design and Crate Home

### Dep-Cycle Analysis (VERIFIED from Cargo.toml files)

```
ironhermes-core    (no ironhermes deps)
ironhermes-gateway → ironhermes-core
ironhermes-cli     → ironhermes-core
ironhermes-cli     → ironhermes-gateway   ← CLI already depends on gateway
```

**Option A — Trait in `ironhermes-core`:**
- Zero new crate, zero new dep edge.
- Trait must be generic over `K` (or a `SessionKey`-like type must move to core).
- `SessionKey` is currently in `ironhermes-gateway::session` (importing `ironhermes_core::Platform`). It could move to `ironhermes-core` trivially (it only uses `Platform` which is already in core).
- Result: `ironhermes-core::queue::MessageQueue<K>` where `K: Hash + Eq + Clone`.

**Option B — Trait in `ironhermes-gateway`:**
- CLI already depends on gateway, so no new dep edge for the CLI consumer.
- Future `iron_hermes_ui` would need to dep on gateway just for the trait — bad long-term.
- Rejected for shared-trait purpose.

**Recommended: Option A.** Move `SessionKey` to `ironhermes-core` (it uses only `Platform` which already lives there), define `MessageQueue<K>` in `ironhermes-core::queue`. Re-export `SessionKey` from `ironhermes-gateway::session` for backward compat (`pub use ironhermes_core::SessionKey`). [VERIFIED: crate structure]

### Exact Trait Signature (proposed)

```rust
// ironhermes-core/src/queue.rs
use std::hash::Hash;

pub trait MessageQueue<K: Hash + Eq + Clone>: Send + Sync {
    /// Push a text message onto the per-key FIFO.
    /// Returns Err if the queue is at capacity.
    fn try_push(&self, key: &K, message: String) -> Result<(), QueueError>;

    /// Pop the oldest message for the given key, or None if empty.
    fn pop(&self, key: &K) -> Option<String>;

    /// Current depth for the given key, or 0 if no queue allocated.
    fn len(&self, key: &K) -> usize;

    /// Drop all queued messages for the given key.
    fn clear(&self, key: &K);

    // peek() is optional — omit from trait; add on concrete type if needed
}
```

**Key divergence from current `SessionQueue`:** The current `SessionQueue::try_push` takes `MessageEvent` (a rich gateway struct), not `String`. Two options:
- **Option A (preferred):** The trait operates on `String` (the message text). `SessionQueue` implements `MessageQueue<SessionKey>` with an adapter that wraps the `String` in a minimal `MessageEvent` internally.
- **Option B:** The trait takes `MessageEvent` — requires `iron_hermes_ui` and future consumers to also construct `MessageEvent`, which is gateway-centric overhead.

**Recommendation: Option A (String-based trait).** The TUI and web UI only care about the text content; the gateway's `MessageEvent` wrapping is an implementation detail of the concrete `SessionQueue`. [ASSUMED — planner must confirm this tradeoff is acceptable or whether `MessageEvent` is needed at the trait level]

`SessionKey` struct (`gateway/src/session.rs:12-17`) uses only `Platform` from `ironhermes_core`. Moving it to `ironhermes_core` is clean. The TUI's fixed key would be:

## TUI Drain Insertion Point

### Current Turn Lifecycle (VERIFIED: event_loop.rs + app.rs)

```
run_app_inner loop (event_loop.rs:677-708):
  1. Per-frame: if app.pending_tx.is_some() && cancel_child.is_some()
       → spawn_turn(app, tx, cancel)          [line 685: synchronous tokio::spawn]
  2. tokio::select! arms:
       - terminal event → app.handle_event(ev, ...)
       - stream event   → app.handle_stream_event(se)    [← turn completion here]
       - ctrl+c         → app.handle_ctrl_c_signal()
       - tick           → app.on_tick()
  3. app.reconcile_scroll(transcript_area)
  4. terminal.draw(|f| ui(f, app))
```

`spawn_turn` is SYNCHRONOUS — it calls `tokio::spawn(async move {...})` and returns immediately. The `async` block inside does the actual `runtime.run_turn(request).await`. The spawned future sends `StreamEvent::Finished | Cancelled | Error` when done, which is received by `recv_pending(app)` in the select arm.

### Turn Completion Signal (VERIFIED: app.rs:734-763)

`handle_stream_event` sets `pending_rx = None` and `cancel_child = None` on Finished, Error, and Cancelled. These are the "turn just finished" signal.

### Drain Insertion Point

**Exact location:** `app.rs::handle_stream_event`, at the end of all three completion arms (`Finished`, `Error`, `Cancelled`):

```rust
StreamEvent::Finished { total_tokens } => {
    self.commit_assistant_buffer();
    // ... existing code ...
    self.pending_rx = None;
    self.cancel_child = None;
    self.status.hint = String::new();
    // ← NEW: auto-drain check goes here
    self.maybe_drain_queue();
}
StreamEvent::Cancelled => {
    // ... existing code ...
    self.pending_rx = None;
    self.cancel_child = None;
    // ← NEW: do NOT drain on cancel (D-08 /stop clears queue; no drain after cancel)
    // Note: if cancelled by /stop, queue was already cleared before cancel fired
}
StreamEvent::Error(e) => {
    // ... existing code ...
    self.pending_rx = None;
    self.cancel_child = None;
    // ← NEW: drain on error? Planner should decide. Recommend: drain (error is transient)
}
```

**`maybe_drain_queue` pattern:**

```rust
fn maybe_drain_queue(&mut self) {
    if self.queue_paused.load(Ordering::Relaxed) {
        return;
    }
    if let Some(text) = self.queue.pop(&self.queue_key) {
        // Push as user message to history
        self.history.push(user_message(text));
        // Set up the pending channel (same as submit())
        let (tx, rx) = tokio::sync::mpsc::unbounded_channel::<StreamEvent>();
        self.pending_rx = Some(rx);
        self.pending_tx = Some(tx);
        self.cancel_child = Some(self.cancel_parent.child_token());
        self.auto_follow = true;
        self.assistant_buffer = None;
    }
}
```

**Why NOT in `run_app_inner` loop directly:** The spawn gate at `event_loop.rs:682-687` runs at the TOP of each loop iteration, BEFORE the select. If `maybe_drain_queue` is called from `handle_stream_event` (inside the select arm), `pending_tx` is set before the loop body advances to the next iteration — the spawn gate will pick it up on the very next tick. This is the correct pattern — no "turn just finished" signal needs to be added; the existing `StreamEvent` termination arms ARE that signal.

**No Notify/JoinHandle integration needed.** The TUI uses mpsc channels + `pending_rx` state, not `Notify`. The drain is purely `app`-state-driven. [VERIFIED: event_loop.rs architecture]

## /stop Cancellation Path

### Existing Cancel Mechanism (VERIFIED: app.rs, commands.rs)

The TUI has a **complete and functional in-flight cancellation path:**

1. `app.cancel_child: Option<CancellationToken>` — child token parented under `cancel_parent`, set in `submit()` at `app.rs:811`.
2. `spawn_turn` clones this token and passes it to `TurnRequest { cancel_token: Some(cancel_token) }` (`event_loop.rs:839`).
3. `AgentRuntime::run_turn` uses the cancel token internally.
4. In `handle_ctrl_c_key` (`app.rs:680-710`): `cancel_child.take().cancel()` fires the token.
5. `StreamEvent::Cancelled` arrives → clears `pending_rx` + `cancel_child`.

**The `/stop` slash handler** (`commands.rs:833-837`) currently delegates entirely to `map_core_to_slash_outcome(core_result)`. Core `cmd_stop` calls `ProcessRegistry::drain_and_kill_session` — this handles background processes but does NOT cancel the `cancel_child` token. The TUI's Ctrl+C path explicitly calls `app.cancel_child.take().cancel()` but `/stop` does not.

**Gap identified:** `/stop` does NOT currently cancel the in-flight `AgentRuntime::run_turn`. It fires `ProcessRegistry::drain_and_kill_session` (background processes) but leaves `cancel_child` un-fired. The agent turn continues running until it finishes naturally. The `agent_running` flag (a separate `Arc<AtomicBool>`) does check for running agent before accepting new input at `commands.rs:388` (AGENT_RUNNING_REJECT_MSG), but the cancel token is not triggered.

**What D-08 requires for this phase:**
1. `/stop` must fire `cancel_child.take().cancel()` — add this to the TUI `/stop` handler alongside the existing `map_core_to_slash_outcome`.
2. `/stop` must call `queue.clear(&queue_key)` — new addition.
3. `queue_paused` should be reset to `false` on `/stop` (not specified in D-08 but consistent with D-07 pattern).

**Verdict:** D-08 ships FULLY in this phase. The cancel mechanism is already present — the `/stop` handler just needs a 3-line addition. This is not a split. [VERIFIED: full code trace]

### The /stop TUI handler after this phase:

```rust
"stop" => {
    // Cancel the in-flight turn (D-08)
    if let Some(tok) = app.cancel_child.take() {
        tok.cancel();
    }
    // Clear the queue (D-08)
    if let Some(ref q) = app.queue {
        q.clear(&app.queue_key);
    }
    app.queue_paused.store(false, Ordering::Relaxed);
    // Core cmd_stop handles ProcessRegistry drain
    map_core_to_slash_outcome(core_result.clone())
}
```

## Status Bar and Transcript Wiring

### Status Bar Architecture (VERIFIED: status_line.rs)

`StatusLineState` struct has named fields for each pill. The pill renderer `build_pills()` conditionally adds pills (e.g., `agents` pill is hidden when `active_subagents == 0`). The same hide-when-zero pattern is established for `cost_usd_micros` and `session_total_tokens`.

**Adding `Queue: N` pill:**
1. Add `queue_depth: usize` and `queue_paused: bool` fields to `StatusLineState`.
2. In `build_pills()`, add after the existing cost/token pills:
   ```rust
   if state.queue_depth > 0 {
       if state.queue_paused {
           pills.push(format!("Queue: {} (paused)", state.queue_depth));
       } else {
           pills.push(format!("Queue: {}", state.queue_depth));
       }
   }
   ```
3. Update `status.queue_depth` from `app.queue.len(&app.queue_key)` on each tick or on queue mutation.

**Update frequency:** The status bar is re-rendered every tick (`on_tick` → `terminal.draw`). The cleanest approach is to read `app.queue.len(&app.queue_key)` directly in `ui.rs` (passed via `&App`) rather than maintaining a separate cached field. The existing pattern reads `app.status` fields which are `Copy`/`Clone` types — adding `queue_depth: usize` fits the existing pattern. [VERIFIED: status_line.rs + ui.rs pattern]

### Inline Transcript Message Pattern (VERIFIED: app.rs::apply_slash_outcome)

System messages are pushed as `Role::System` chat messages into `app.history`:
```rust
let mut msg = ChatMessage::user(&text);
msg.role = Role::System;
self.history.push(msg);
self.scroll_to_bottom();
```

System messages render in `dim DarkGray` style in `transcript_text()` (app.rs:860). This is the correct channel for:
- `Queued: "<text>" (N in queue)` — informational system line
- `Queue is full (128/128). /stop or /flush to drain.` — error system line

**Red styling for cap-hit:** The current transcript rendering doesn't support per-message color override; all System messages get `DarkGray`. For the red cap-hit error, the planner has two options:
- Add a `Role::SystemError` variant (heavier change)  
- Use a special prefix in the message text (e.g., `[ERROR] Queue is full...`) without red styling — simpler
- Accept `DarkGray` for all system messages including the cap-hit error

The existing `status.hint` field (shown in the status bar) IS colored per-pill. The cap-hit could set `status.hint` to a red-styled string temporarily. This is likely the lightest path. [ASSUMED — planner should decide on styling approach given transcript-rendering constraints]

### Terminal Bell

No terminal bell (`\a` / `\x07`) is currently emitted anywhere in `crates/ironhermes-cli/src/`. Crossterm does not provide a bell function in its `execute!` macro set (it handles terminal control but not BEL). To emit a bell, the simplest approach is `print!("\x07")` or `eprint!("\x07")` — but ratatui owns stdout in alt-screen mode.

**Crossterm bell:** `crossterm::style::Print("\x07")` via `execute!(stdout(), Print("\x07"))` should work since BEL is a control character, not a visual character. However, many modern terminals suppress BEL by default. D-10 says "planner can drop" — this is low-risk to omit. [ASSUMED — crossterm BEL feasibility; bell suppression is terminal-dependent]

### AgentRuntime Test Seam Analysis (VERIFIED: agent_runtime.rs)

`AgentRuntime` is a concrete struct (not a trait). `TurnRequest` has `cancel_token: Option<CancellationToken>` and `messages: Vec<ChatMessage>`. There is NO existing test-seam interface (no `dyn AgentRuntime` trait, no mock injection point for `run_turn`).

**Implication for D-11/D-12:** A headless TUI test that actually calls `AgentRuntime::run_turn` requires a configured LLM provider — unsuitable for a pure regression test. 

**Viable approaches:**

**Option A (recommended) — Test the queue directly, stub the turn dispatch:**
Instead of running a full headless TUI, test the queue state machine directly by calling `App` methods in a unit-test style:
1. Create an `App` (using `App::new` with minimal deps or a test constructor).
2. Call `app.submit()` equivalents to push queue items.
3. Call `app.handle_stream_event(StreamEvent::Finished { total_tokens: 0 })` to simulate turn completion.
4. Assert `history` contains the right messages in FIFO order.
This avoids needing a live LLM while still testing the drain state machine.

**Option B — Headless TUI with mock adapter:**
Mirror the gateway test pattern: create a `stub_turn` that fires `StreamEvent::Finished` after a sleep, injected via a mock `pending_tx`. This requires making the turn dispatch hookable — currently `spawn_turn` calls `app.agent_runtime.clone()` which is `Arc<AgentRuntime>` (concrete). Would need a `Box<dyn TurnSpawner>` seam added to `App`.

**Recommendation: Option A for initial test; note Option B as a future enhancement.** The negative-control requirement (D-12: test must FAIL against pre-fix textarea-prepopulate behavior) is achievable with Option A because the pre-fix behavior at `commands.rs:978-999` sets `app.textarea` and returns `SlashOutcome::Handled` — the queue state won't be touched, so queue assertions will fail.

**Test structure outline:**

```rust
// crates/ironhermes-cli/tests/tui_queue_drain.rs
// D-11: FIFO drain + pause/resume + /new clear
// D-12: negative control — see assertions below

#[tokio::test]
async fn test_queue_fifo_drain_sequence() {
    // 1. Create app with test deps (minimal — no LLM)
    let mut app = App::new_for_test(test_deps());
```

## Common Pitfalls

### Pitfall 1: Drain on `Cancelled` fires after `/stop`
**What goes wrong:** `maybe_drain_queue()` called on `StreamEvent::Cancelled` re-enqueues the next item even though `/stop` was supposed to hard-stop everything.
**Why it happens:** `/stop` clears the queue synchronously, then the cancel fires, then `Cancelled` arrives. Since the queue is already empty by then, `queue.pop()` returns `None` and no drain fires. BUT: if the order is wrong (drain before clear), a queued item fires.
**How to avoid:** `/stop` must call `queue.clear()` BEFORE firing the cancel token. Then the `Cancelled` arm should NOT call `maybe_drain_queue()` — cancelled means user-initiated stop, not natural turn completion.
**Warning signs:** Test: queue 3 items, `/stop`, assert queue empty and no new turn starts.

### Pitfall 2: `SessionKey` borrowed from gateway but trait is in core
**What goes wrong:** `MessageQueue<SessionKey>` references `SessionKey` from `ironhermes-gateway` but the trait lives in `ironhermes-core` — circular dep.
**Why it happens:** If `SessionKey` is NOT moved to core, the trait signature `MessageQueue<SessionKey>` in core would need to import from gateway.
**How to avoid:** Move `SessionKey` to `ironhermes-core` and re-export from gateway. Or make the trait unbound generic (`MessageQueue<K>`) and let each crate instantiate with its own key type.
**Warning signs:** `cargo build` cycle error on `ironhermes-core`.

### Pitfall 3: Double-drain on rapid successive completions
**What goes wrong:** If `handle_stream_event(Finished)` is called twice in a row (e.g., from a test), two items are drained and two `pending_tx` channels are opened, but the event loop only picks up one.
**Why it happens:** `maybe_drain_queue` doesn't check whether a turn is already in-flight (i.e., `pending_tx.is_some()`).
**How to avoid:** Guard in `maybe_drain_queue`: `if self.pending_tx.is_some() { return; }`.
**Warning signs:** Queue drains faster than expected; turns overlap.

### Pitfall 4: `resume` command name collision
**What goes wrong:** Adding `/pause` with alias `/resume` conflicts with the existing `CommandDef::new("resume", "Resume a previous session")` at `registry.rs:88`.
**Why it happens:** The `CommandRouter::new()` panics on duplicate name/alias (`panic!("Duplicate command name in registry")`).
**How to avoid:** Choose a different alias (`/unpause`) or make the queue-resume a separate meaning of the existing `/pause` toggle (no alias needed).
**Warning signs:** Panic at startup: "Duplicate command name in registry: 'resume'".

### Pitfall 5: Status bar queue count stale by one tick
**What goes wrong:** User sees `Queue: 3` for one frame after the 3rd item was already drained.
**Why it happens:** `StatusLineState` fields are updated at `on_tick` time, but the queue state changes inside `handle_stream_event` which is also tick-driven. If the field is read once and cached, it's one tick stale.
**How to avoid:** Read `app.queue.len(&app.queue_key)` directly in `ui.rs` render pass rather than caching in `StatusLineState`. The `ui()` function receives `&App` and can call this directly. No caching needed.
**Warning signs:** Off-by-one queue depth in UI.

### Pitfall 6: `queue_paused` AtomicBool vs `Arc<AtomicBool>`
**What goes wrong:** `queue_paused` is a plain `AtomicBool` field on `App` (not `Arc<AtomicBool>`). If slash handlers run in a spawned context that only has a `&App` reference, they can't mutate it.
**Why it happens:** All existing TUI toggle booleans (`fast_enabled`, `yolo_enabled`, etc.) are `Arc<AtomicBool>` because they're shared across closures. Planner should follow the established pattern.
**How to avoid:** Use `Arc<AtomicBool>` for `queue_paused` matching the `fast_enabled` pattern at `app.rs:120`.
**Warning signs:** Borrow check error on `queue_paused` mutation in async context.

## Open Questions for Planner

1. **Trait generic key vs concrete `SessionKey`:** Should `MessageQueue` be `MessageQueue<K: Hash + Eq + Clone>` (generic, future-proof) or `MessageQueue<SessionKey>` (concrete, simpler)? The generic approach requires `SessionKey` to move to core OR the trait uses a bound. Option set: (A) generic + move `SessionKey` to core, (B) concrete with `SessionKey` in trait signature (requires `SessionKey` in core), (C) trait defined in gateway re-exported to CLI.

2. **`/resume` alias collision:** The existing `CommandDef "resume"` in registry.rs is the session-resume command. D-06 names `/resume` as an alias for the queue-unpause. Options: (A) use `/unpause` instead, (B) overload `/resume` contextually (dangerous), (C) rename the session-resume command. Research recommends option A.

3. **Drain on `StreamEvent::Error`:** Should a turn error trigger queue drain (try the next item) or suspend the queue? The error could be transient (network timeout) or permanent (auth failure). Options: (A) drain on error (optimistic — try next), (B) do not drain on error (user must manually `/resume`), (C) drain on error but set `queue_paused = true` so user sees the paused state. Research is neutral; planner decides.

4. **`MessageEvent` vs `String` at trait surface:** The gateway's `SessionQueue::try_push` takes `MessageEvent`. The trait could use `String` (simpler for TUI/web consumers) with an adapter impl in `SessionQueue`, or use `MessageEvent` directly (no adapter needed but burdens non-gateway consumers). Research recommends `String`; planner confirms.

5. **`App::new_for_test` constructor:** The test harness needs a minimal `App` without a live LLM. Options: (A) add `#[cfg(test)] fn new_for_test(...)` to `app.rs`, (B) use `Default` derive for the parts of `AppDeps` that can be defaulted, (C) build the full `AppDeps` in tests using `Config::default()` (as gateway tests do). The gateway test pattern (option C, using `Config::default()` with a `RecordingFailingAdapter`) is the proven model.

6. **Bell implementation:** `print!("\x07")` via `execute!(io::stdout(), crossterm::style::Print("\x07"))` in ratatui alt-screen — feasible but many terminals suppress BEL. D-10 says planner can drop. Recommend: omit from initial implementation, add as a follow-up if users request it.
