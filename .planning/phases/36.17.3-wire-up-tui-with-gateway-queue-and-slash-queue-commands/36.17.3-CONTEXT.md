# Phase 36.17.3: wire up TUI with gateway queue and slash queue commands - Context

**Gathered:** 2026-05-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Bring real FIFO queueing to the `ironhermes-cli` ratatui TUI (`crates/ironhermes-cli/src/tui_rata`) so `/queue <message>` and the queue-aware slash commands behave the same way they do on Telegram (post-36.17.2.1): items typed while a turn is in flight are buffered FIFO and become real agent turns once the current turn ends. Today's TUI `/queue` is a UX placeholder (`commands.rs:978-999`) that pre-populates the textarea — it does not buffer anything. The "Phase 36.17.1 Plan 03 Task 1" comment at `commands.rs:1123` is the explicit deferral marker that this phase closes.

To enable parity across the *upcoming* surfaces (iron_hermes_ui web in 36.17.4, plus future Discord/Slack/REST), this phase also **extracts a shared `MessageQueue` trait** from the gateway's `SessionQueue` so every consumer references the same FIFO abstraction. The gateway is migrated to the trait in this phase (so the trait is exercised by production code, not just the TUI), but its dispatch + worker orchestration stays untouched.

**In scope:**
- Extract `MessageQueue` trait (FIFO data ops only — see D-01) into a shared crate; refactor `crates/ironhermes-gateway/src/session_queue.rs::SessionQueue` to implement it. No behavior change for the gateway.
- TUI gains a `MessageQueue` instance keyed by a single fixed `SessionKey` (`"tui:local"`) owned by `App`.
- TUI `/queue <text>` pushes onto the queue and prints an inline "Queued: '<text>' (N in queue)" message (D-09).
- TUI status bar shows `Queue: N` whenever N > 0; shows `Queue: N (paused)` when paused.
- After each `App::spawn_turn` finishes, the TUI auto-drains one queued item as the next turn — unless paused (D-04, D-05).
- `/pause` (alias `/resume`) toggles a `queue_paused: AtomicBool` on `App`. Items still accept into the queue while paused; only the drain is suspended (D-06).
- `/new` and `/reset` clear the queue alongside the session in a single atomic step (D-07).
- `/stop` cancels the in-flight turn AND clears the queue (D-08), mirroring gateway semantics from Phase 36.17.2.
- Cap behavior matches gateway: cap=128, `try_push` returns `QueueError::CapacityReached` → TUI prints inline red error "Queue is full (128/128). /stop or /flush to drain." and a terminal bell (D-10).
- Regression test asserts: 5 `/queue` events while a turn is in flight produce 5 sequential turns FIFO after the first finishes; `/pause` then 3 `/queue` items hold; `/resume` drains all 3; `/new` clears 3 queued items before clearing the session (D-11).

**Out of scope (carried forward):**
- `iron_hermes_ui` (web) wiring — Phase 36.17.4. Will reuse the `MessageQueue` trait extracted here.
- Discord, Slack, REST queue wiring — separate phases per `[[project_multiplatform_gateway_scope]]`. Same trait.
- `/status` slash command — redundant with the status-bar `Queue: N` counter (D-09).
- `/flush` slash command — niche; if needed, will be added in a follow-up after live use surfaces the need.
- Dedicated "queue items" panel/widget — overengineered for typical depths (≤5 items).
- Persistence of the queue across TUI restarts — gateway is in-memory only; TUI matches (drops on restart).
- Per-turn pause / sticky-pause variants — picked toggle semantics; other variants deferred.
- Trait-level "drain protocol" or "visual observer hooks" — explicitly NOT in the trait surface (D-01); each consumer owns its own drain + UI.

</domain>

<decisions>
## Implementation Decisions

### Queue Infrastructure
- **D-01:** Extract a shared `MessageQueue` trait NOW. Trait surface = FIFO data ops only: `try_push`, `pop`, `peek` (optional), `len`, `clear`. Keyed by a generic key type (default `SessionKey`). **Justification:** user has concrete future consumers — iron_hermes_ui (36.17.4), Discord, Slack, REST — so YAGNI is overridden by enumerable demand. Surface is intentionally minimal: each consumer owns its own dispatch + drain orchestration (the gateway keeps UQM + per-chat workers + Notify; TUI uses a simpler in-loop drain). This keeps the abstraction true to what's actually common (the FIFO buffer) without forcing gateway-specific concepts on single-user surfaces.
- **D-02:** Gateway's existing `SessionQueue` is refactored to implement the trait. No behavior change. All existing call sites in `runner.rs` / `handler.rs` / `user_queue.rs` keep working through the trait or the concrete type (whichever the call site already uses). Producing only a trait without migrating the gateway would leave the trait unexercised by production — phase requires gateway-on-trait to ship.
- **D-03:** TUI owns a single `Arc<dyn MessageQueue>` (or `Arc<SessionQueue>` impl) on `App` keyed by a fixed `SessionKey { platform: "tui", chat_id: "local", user_id: "local" }`. The key is a constant — TUI never multiplexes chats, but using `SessionKey` keeps the trait honest for the multi-chat consumers.

### Drain Trigger
- **D-04:** Hybrid auto-drain. After `App::spawn_turn` completes the in-flight turn (post `runtime.run_turn`), the TUI's main loop checks `queue.pop(&key)` and, if `Some(text)` AND `!queue_paused`, immediately invokes `spawn_turn` with the popped text as the next user message. Mirrors gateway's auto-progression.
- **D-05:** Drain is sequential — one queued item per `run_turn` cycle. The user sees each queued item rendered as its own turn (user message + agent response). No batch dispatch.
- **D-06:** `queue_paused: AtomicBool` on `App` (default `false`). When `true`, the post-`run_turn` drain check skips popping. `/queue` still pushes into the queue while paused. `/pause` flips the flag; **`/unpause`** is an alias that sets it to `false` explicitly (no-op if already false — informational message). `/new` and `/reset` clear the queue AND set `queue_paused = false`. Visible in the status bar as `Queue: N (paused)`.
  - **Amended 2026-05-28 during plan-phase:** original D-06 specified `/resume` as the alias; researcher found `/resume` is already registered as "Resume a previous session" in `crates/ironhermes-cli/src/tui_rata/commands/registry.rs:88`, which would panic at startup. User chose `/unpause` to avoid the collision and preserve session-resume semantics.

### Slash Commands in Scope
- **D-07:** `/new` and `/reset` clear the queue before (or atomically with) clearing the session. Failure to do so leaves stale buffered items that will fire against a fresh session — surprising and was the parity gap. Implementation: at the `CoreCommandResult::ClearSession` / `CoreCommandResult::NewSession` arm in TUI, drop `queue.clear(&key)` + `queue_paused = false` before forwarding to the session-clear path.
- **D-08:** `/stop` cancels the in-flight turn (via the existing TUI cancel mechanism — to be located in PLANNING; if not present, this is a gap to flag) AND clears the queue. Matches the gateway pattern from 36.17.2 where /stop is a hard stop including buffered items.
- **D-09:** Status bar shows `Queue: N` (only when N > 0; absent when N = 0) and `Queue: N (paused)` when paused. Each `/queue <text>` also prints an inline transcript line: `Queued: "<text>" (N in queue)`. Both signals — ambient via status bar, immediate confirmation via transcript. No dedicated panel, no `/status` command (status bar IS the status).
- **D-10:** Cap behavior: 128 items (matches gateway constant). On `QueueError::CapacityReached`, TUI prints inline red text `Queue is full (128/128). /stop or /flush to drain.` (note: `/flush` is out of scope for this phase but mentioned in the hint for forward-compat) and rings the terminal bell (`\a`). No silent drop.

### Regression Test Surface
- **D-11:** New integration test in `crates/ironhermes-cli/tests/` (parallel to `tests/uqm_session_queue_unification.rs` in the gateway). Test sequence:
  1. Start TUI with a stub agent that takes ≥500ms per turn (controllable via a test seam).
  2. Send a free-text message — assert turn 1 starts.
  3. While turn 1 is in flight, send `/queue alpha`, `/queue bravo`, `/queue charlie`, `/queue delta`, `/queue echo`.
  4. Wait for turns 1..6 to complete. Assert ordering: free-text → alpha → bravo → charlie → delta → echo.
  5. Send another long-running message. While in flight: `/queue foxtrot`, `/queue golf`. Send `/pause`. Assert `is_paused=true`, queue.len=2.
  6. Send `/resume`. Assert drain happens FIFO: foxtrot then golf.
  7. Queue 3 items. Send `/new`. Assert queue empty AND session cleared.
- **D-12:** Test must FAIL against the pre-fix TUI (the textarea-prepopulate behavior) — the new test should fail closed if the wiring isn't done, same negative-control discipline as 36.17.2.1-02.

### Claude's Discretion
- Trait crate location (whether `ironhermes-core::queue` or a new tiny `ironhermes-queue` crate) — planner picks. Prefer not creating a new crate unless cycles force it.
- Exact name of the trait (`MessageQueue` is a placeholder; `SessionFifo` or `ChatQueue` are fine too) — planner picks based on what reads naturally at the call sites.
- Whether `peek` is on the trait or only on the concrete type — defer to planner; only `try_push`, `pop`, `len`, `clear` are mandatory.
- Terminal bell vs no bell on cap-hit — D-10 specifies bell, but planner can drop if the project conventions avoid it.
- Whether `/pause` toggles silently or prints `Queue paused. (3 queued)` / `Queue resumed.` — recommend printing, planner finalizes.

<code_context>
## Existing Code Insights

### Reusable Assets
- `SessionQueue` (gateway): the FIFO data structure is already correct (cap=128, FIFO, `try_push`/`pop`/`len`/`clear`, returns `QueueError::CapacityReached` on overflow). It just needs to (a) implement a trait, (b) be reachable from the TUI crate.
- `CommandRouter::Queued { message }` result variant: the router already produces a typed result for `/queue <text>`. The TUI just needs to push it onto the queue instead of pre-filling the textarea.
- `App::spawn_turn`: existing turn dispatcher. Auto-drain is "after spawn_turn completes, check queue, spawn_turn again with popped text".
- `App::queue_paused: AtomicBool` — new field, but a one-line addition fitting the existing pattern of `fast_enabled: AtomicBool` already on `App`.
- Status bar renderer (`status_line.rs`): already conditionally renders multiple states; adding a `Queue: N` segment fits the existing layout.

### Established Patterns
- The TUI uses `Arc<T>` extensively for shared subsystems on `App` — `MessageQueue` impl will be `Arc<dyn MessageQueue>` matching this pattern.
- Slash commands route through `CommandRouter` → typed `CommandResult` → TUI-side `SlashOutcome` mapping (`commands.rs:1102`). New `/pause` and `/resume` will follow this pattern: add a `CommandResult::PauseQueue` / `CommandResult::ResumeQueue` variant in `ironhermes-core`, map to a TUI `SlashOutcome::Handled` that toggles the AtomicBool.
- Auto-drain pattern mirrors `event_loop.rs`'s post-turn cleanup hooks — natural insertion point.
- Inline error rendering with red text + terminal bell is the established TUI affordance for hard-fail states.

### Integration Points
- The `MessageQueue` trait lives in a shared location reachable by both `ironhermes-gateway` and `ironhermes-cli`. The gateway crate currently doesn't depend on `ironhermes-cli` (and shouldn't); a downstream-of-both home is needed. Best candidate: `ironhermes-core` (both already depend on it). Planner decides definitively.
- `CommandResult` enum addition (`PauseQueue`, `ResumeQueue`) — affects every CommandRouter consumer. Planner must verify each existing surface (CLI prompt, gateway handler, current TUI) handles the new variants gracefully or routes them to a default no-op.
- `/stop` integration depends on whether tui_rata has an existing in-flight cancellation path. If yes, queue clear is layered on top. If no, this phase either (a) skips `/stop` and scopes it to a follow-up, or (b) implements minimum cancel-and-clear. Planner determines after reading event_loop.rs.

</code_context>

<specifics>
## Specific Ideas

- User explicitly cited future consumers: "there will be the webui, discord, slack and others coming" — this is why the trait-extraction option was chosen over a TUI-only `VecDeque`. The trait is FOR those future consumers; the TUI is just the first non-gateway consumer.
- User picked the hybrid drain trigger (auto + `/pause`) and toggle semantics for `/pause` with `/resume` as an alias — favoring "magical" parity with the gateway over a "user-explicit" model.
- Status-bar counter + inline transcript was confirmed as the visual pattern; rule out dedicated panel.

</specifics>

<deferred>
## Deferred Ideas

- `iron_hermes_ui` (web) queue wiring: Phase 36.17.4 — already inserted in the roadmap.
- Discord, Slack, REST adapter queue wiring: separate phases per existing `[[project_multiplatform_gateway_scope]]`. The trait extracted here is the contract.
- `/status` slash command (queue depth + state): redundant with status bar; revisit only if a non-TUI consumer needs a programmatic answer.
- `/flush` slash command (drain without firing turns): niche; revisit if live use surfaces a need.
- Sticky-pause variant (`/pause` requires explicit `/resume`, no-op on double-toggle): not picked; can be added later if double-toggle confusion surfaces.
- Per-turn pause (`/pause` skips only the next drain then auto-resumes): not picked; less powerful for long sessions.
- Persistence of the queue across TUI restarts: gateway is in-memory only; TUI matches. Revisit only if a user case appears.
- Trait-level drain-protocol surface (`on_turn_complete`, `pause`, `resume`, `is_paused`): explicitly out of the trait per D-01. If parity across surfaces drifts and we re-converge on a shared orchestration pattern, the trait can grow then.
- Trait-level observer hooks (`on_queued`, `on_drained`, `on_cap_hit`): same as above — out of scope for the minimal trait.
