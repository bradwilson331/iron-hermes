# Phase 36.17.3 Plan 02: PauseQueue/UnpauseQueue Variants + /pause Registry + Defensive Match Arms Summary

**Two new unit variants `CommandResult::PauseQueue` and `CommandResult::UnpauseQueue` plus a `/pause` registry entry aliased to `/unpause` (avoiding the existing `/resume` collision per D-06 amended) — workspace compiles with defensive no-op arms in all three exhaustive consumers, ready for Plan 05 to wire active `App::queue_paused` toggling.**

## Accomplishments
- Appended two `CommandResult` unit variants (`PauseQueue`, `UnpauseQueue`) with the doc-comment style of the existing `Queued { message }` variant, citing "Phase 36.17.3 (D-06 amended)".

- Patched three exhaustive `match` sites with defensive no-op arms so the workspace compiles: `tui_rata::commands::map_core_to_slash_outcome`, `gateway::handler` (match core_result), and the legacy `tui::commands::map_core_to_tui` mapper.

## Decisions Made
- Alias choice `/unpause` (D-06 amended) confirmed at execution time by reading `registry.rs:88` — the `/resume` slot is owned by "Resume a previous session" and a `&["resume"]` alias on `/pause` would have panicked `CommandRouter::new()` at startup before any tests could load. No rename needed (plan called this exactly).
- `/pause` is `CliOnly` (matching PATTERNS §4 guidance) rather than `Universal`. Gateway worker-drain pause semantics are a separate concern (not in scope this phase) so exposing `/pause` on Telegram/Discord/Slack would mislead. Gateway match arm is exhaustiveness scaffolding only.
